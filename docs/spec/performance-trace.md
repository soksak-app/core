# Performance trace

[한국어](performance-trace.ko.md)

The performance trace is one of the records of [diagnostics](diagnostics.md): the event form. It is a permanent instrument, present in every build, that records what the application spends time and memory on. It is not a diagnostics-build feature and is never removed after use. The switch is the declared setting `diagnostics.performance` ([settings](settings.md)); while it is false no layer does any logging work — no file is created and no formatting runs.

The page does not format or relay events while disabled or awaiting enable acknowledgment. An event of the page is the event `page.trace.<event>` of the [event contract](logging.md#writers): the page queues it without waiting and relays the events of one turn to the host in one batch through the host call `log`, and the host stores them in the event log `logs/host-<boot>.jsonl`. Switch requests preserve their order: disabling stops new events immediately and waits until the events that were already accepted are relayed. Switch failures reject the settings operation; relay failures are reported explicitly with the number of events of the batch and do not replace the result of the measured command.

## Output

Every event of the trace is an event of the [event contract](logging.md): the page stores `page.trace.<event>`, the host `host.trace.<event>` and the sampler `host.sampler.<event>` in the event log `logs/host-<boot>.jsonl`, all of level `debug`, with the name of the event in the event name and not in the fields, and a sidecar stores `sidecar.<name>.<event>` in its own event file under `logs/` ([sidecars](sidecars.md)). One timeline, the [debug view](debug.md), reads the files together. When the switch turns on the host stores the event `host.trace.on`, and before it turns off the event `host.trace.off`. There is no trace file, no marker line and no rotation of its own: the event files rotate by the rules of the contract.

## Producers

Every layer is a producer; the trace is not defined by one of them.

- **Page** — every `core.*` and plugin command with name, duration, and result class; exposure watch notification volume; layout queue waits and supersessions; grid renders; card and tab operations; surface mount lifecycle; surface registration phases (`pending`, `registered`, `closed`, `disposed`) with document `timeOrigin`, `hasPort`, and registered `names` at the event; compositor publishes and clip updates; screen-event handling time; settings, project, and reload markers; JS heap readings; user action markers with values (a window resize carries its size, a tab switch its ids). The page owns no filesystem, so its lines relay through a host command that appends them.
- **Host** (both hosts as a parity pair) — every endpoint method with name, duration, and result class; every answer to a frame of an image region as an `image.frame` event `{surface, name, response}`, where `response` is the `consumed` answer or the refusal with its reason; window events with values (size, move, focus, occlusion, scale); surface lifecycle with geometry (created, destroyed, placed, visibility); document, image, and composition operations including presentation barrier wait durations; each raster decision for an image region is an `image.raster` event `{surface, name, phase, from, width, height, scale}`, where `phase` is `configured` when the host sets the size it sends to the sidecar `deferred` when the region's surface has no native size yet, and `sent` when the host has handed the configuration to the sidecar connection, and `from` is `composition`, `refresh`, or `reconnect` (`sidecar` for `sent`); protocol rejections with the offending payload values; a process registry naming every spawned pid and its role; sidecar spawn and exit.
- **Sidecars** (`vt-core`, `files`, `shell`) — each stores its events in its own event file under `logs/` whether or not the trace is on; request handling with operation, duration, and result. `vt-core` writes each request as a `request` event `{operation, surface, owner, connection, idle_us, us}`, where `us` is the time from reading the request to reading the next one, `idle_us` the time the input loop waited for it, and `connection` the service's sequence number of the connection, and a `read_wait` event `{waited_us, pending_polls, since_last_poll_us, bytes}` when a read of the connection received data after waiting a second or more, which tells a task that was not woken (one poll) from a read that kept finding no data (several polls); and an `output_blocked` event `{us, bytes}` when writing one output line to the host took 10 ms or more, because a host that stops reading stops the sidecar's input loop once its output channel is full. `vt-core` adds frame events with the reason the frame was drawn (`output`, `blink`, `resize`, `metrics`, `selection`), the draw, transfer, and consumed-wait timings as separate fields, and the raster size; PTY read byte counts and PTY resizes with the grid before and after; and session lifecycle.
- **Sampler** — every five seconds, the resident size of every process the registry names, so memory readings attribute themselves. A reading that cannot obtain a size records `error` instead of the size.

## The switch

The process of the host holds the switch; no file holds it and no flag reaches a sidecar. The page reads `diagnostics.performance` from the settings it already loads and tells the host through the host call `performance` — `on` when the setting turns true, `off` when it turns false, and once at startup when a stored setting is already true. The call accepts the actions `on` and `off` only and refuses any other action with an error; a request that does not change the switch stores nothing. Turning the trace on stores `host.trace.on` and starts the sampler, which stores `host.sampler.memory` every five seconds while the trace is on; turning it off stores `host.trace.off` and ends the sampler, and turning it on again starts a new one. A start of the process always starts with the trace off. Passive instrumentation reports failures without replacing the measured operation result.

## Reading

The event files are JSON lines, so field tools answer questions directly: the frame reasons of an idle terminal (`select(.event=="frame") | group_by(.reason)`), the raster values a drag through collapse produced (`select(.event=="configure")`), whether tab switching recreated webviews (`select(.event=="surface")`), and what memory did around a user action (`select(.event=="action")`).
