# Performance trace

[한국어](performance-trace.ko.md)

The performance trace is one of the records of [diagnostics](diagnostics.md): the event form. It is a permanent instrument, present in every build, that records what the application spends time and memory on. It is not a diagnostics-build feature and is never removed after use. The switch is the declared setting `diagnostics.performance` ([settings](settings.md)); while it is false no layer does any logging work — no file is created and no formatting runs.

The page does not format or relay events while disabled or awaiting enable acknowledgment. An event of the page is the event `page.trace.<event>` of the [event contract](logging.md#writers): the page queues it without waiting and relays the events of one turn to the host in one batch through the host call `log`, and the host stores them in the event log `logs/host-<boot>.jsonl`. Switch requests preserve their order: disabling stops new events immediately and waits until the events that were already accepted are relayed. Switch failures reject the settings operation; relay failures are reported explicitly with the number of events of the batch and do not replace the result of the measured command.

For each received body addressed to an active owner, both transports emit the existing `sidecar.receive` trace before image-envelope handling. A handled image keeps its native-only delivery path; its receipt and consumed/refused `image.frame` response can be joined by surface, image name, generation, raster and sequence. Trace gating and bounded body serialization remain unchanged.

The receive timestamp follows envelope decoding and owner routing. The image response trace precedes outbox delivery. Their interval does not include socket-read waiting, decoding, owner lookup or return transport.

## Surface dispatch measurements

While the trace is on, each existing UI admission and asynchronous callback on the surface `sync` and `present` paths writes `host.trace.surface.dispatch`. A record names the window, operation, host-specific stage and optional layout ticket. `queued_ns` is sampled immediately before the existing dispatch or native callback registration, `entered_ns` at the UI closure or callback entry, and `returned_ns` at its end. These decimal nanosecond values use the same host event clock as `mono_ns` (CLOCK_UPTIME_RAW on macOS). A callback may run inline before its registration call returns. The record excludes the caller's resumption after a synchronous dispatch and adds no dispatch or wait. The existing `host.trace.view.presentation-join` records remain the source for root-view join registration and completion.

## Output

Every event of the trace is an event of the [event contract](logging.md): the page stores `page.trace.<event>`, the host `host.trace.<event>` and the sampler `host.sampler.<event>` in the event log `logs/host-<boot>.jsonl`, all of level `debug`, with the name of the event in the event name and not in the fields, and a sidecar stores `sidecar.<name>.<event>` in its own event file under `logs/` ([sidecars](sidecars.md)). One timeline, the [debug view](debug.md), reads the files together. When the switch turns on the host stores the event `host.trace.on`, and before it turns off the event `host.trace.off`. There is no trace file, no marker line and no rotation of its own: the event files rotate by the rules of the contract.

## Producers

Every layer is a producer; the trace is not defined by one of them.

- **Page** — the registry commands (`page.command`), the host calls (`page.call`: exposure watch notifications as `exposureChanged`, composition publishes and clip updates, settings and project stores, surface document attachments) and the start of each document (`page.start`, with the `time_origin` of its clock and its address; a reload starts a new document) are recorded by their [entrances](logging.md#entrances) whether or not the trace is on. The trace adds `page.trace.command` (every `core.*` and plugin command with name, duration, and result class), `layout` (queue waits and supersessions), `surface.registration` (the phases `pending`, `registered`, `closed`, and `disposed` with document `timeOrigin`, `hasPort`, and the registered `names` at the event), `surface.mount` (the `plugin` and `surface` of a surface whose module mount completed, and `ms`, the time from the start of its mount to the end of the module mount, measured with `performance.now()`; a failed mount writes no event), `focus`, `modal.answer` (the `key` of each answer of a native modal that the page receives, stamped at its receipt, because the overlay document has no trace switch and cannot write the event itself), `picker.close` (the `reason` of each close of the native picker: `replaced`, `settled`, `fullscreen`, `toggle`, `pick`, `dismiss`, or `command`), and user action markers with values (`action`: a window resize carries its size, a tab switch its ids, a card focus its card, a project open its root); every event carries the JS heap reading `jsHeapMB`. The page owns no filesystem, so its events leave in the batches of the host call `log`. The `mono_ns` of a page event is derived from `performance.now()`, which WebKit coarsens to about 1 ms, so an interval between two page events (such as `modal.answer` and `picker.close`) has a resolution of about 1 ms: an interval shorter than that reads as 0 or 1 ms.
- **Surface composition diagnostics** — while tracing is enabled, `page.trace.surface.composition` records a view-composition declaration outcome and page-local disposal. Its fields are `page` (the document's `String(document.defaultView.performance.timeOrigin)`), `surface`, `attempt` (the page-local `registration.attempt`, or `null` if no registration is available), and `action`. A declaration records `action: "declare"` with `outcome: "accepted"` after the native reply or `outcome: "rejected"` when the call fails; disposal records `action: "dispose"` and a page-local `reason` (`close`, `unload`, `released`, or `mount-failure`). A `dispose` record says only that the page disposed that mount attempt; it does not claim that the native composition table was cleared. The page also records `page.trace.surface.sync` after each `syncSurfaces` request with `page`, the per-document `requestId`, `views` (the exact view surface IDs in that request paired with each page-local `attempt`, or `null` if unavailable), and `outcome: "accepted"` or `"rejected"`. The event is written after the host call settles, and does not contain surface payloads or error text. A successful sync is a complete surface list: native declaration removal may be inferred only by comparing its included IDs with the prior successful sync in the same page, under the omission-clears rule of [native surfaces](native-surfaces.md#region-lifetime). These records are built only while the trace is enabled; they do not change placement or disposal behavior.
- **Host** (both hosts as a parity pair) — every endpoint method is recorded by its [entrance](logging.md#entrances) as `host.endpoint.call`, whether or not the trace is on; every answer to a frame of an image region as an `image.frame` event `{surface, name, response}`, where `response` is the `consumed` answer or the refusal with its reason; window events as `host.window.event` with the window and the kind (the [entrance](logging.md#entrances) records no further value; the size of a resize is the action marker of the page); surface lifecycle as the event `surface` `{phase, surface}`, where `phase` is `created` when the host makes the native view, `placed` when it fixes the view's frame (the event adds `x`, `y`, `w`, `h` and `visible`), or `destroyed` when the page's list no longer holds the surface; document, image, and composition operations including presentation barrier wait durations; each raster decision for an image region is an `image.raster` event `{surface, name, phase, from, width, height, scale}`, where `phase` is `configured` when the host sets the size it sends to the sidecar `deferred` when the region's surface has no native size yet, and `sent` when the host has handed the configuration to the sidecar connection, and `from` is `composition`, `refresh`, or `reconnect` (`sidecar` for `sent`); protocol rejections with the offending payload values; a process registry naming every sidecar process the host started or connected to, as the event `process` `{role, name, pid}`, which leaves the registry when the process or its connection ends; sidecar start and exit as the `host.sidecar.*` entrances.
- **Sidecars** (`vt-core`, `files`, `shell`) — each stores its events in its own event file under `logs/` whether or not the trace is on; request handling with operation, duration, and result. `vt-core` writes each request as a `request` event `{operation, surface, owner, connection, idle_us, us}`, where `us` is the time from reading the request to reading the next one, `idle_us` the time the input loop waited for it, and `connection` the service's sequence number of the connection, and a `read_wait` event `{waited_us, pending_polls, since_last_poll_us, bytes}` when a read of the connection received data after waiting a second or more, which tells a task that was not woken (one poll) from a read that kept finding no data (several polls); and an `output_blocked` event `{us, bytes}` when writing one output line to the host took 10 ms or more, because a host that stops reading stops the sidecar's input loop once its output channel is full. `vt-core` adds frame events with the reason the frame was drawn (`output`, `blink`, `resize`, `metrics`, `selection`), the draw, transfer, and consumed-wait timings as separate fields, and the raster size; PTY read byte counts and PTY resizes with the grid before and after; and session lifecycle.
- **Sampler** — every five seconds, the resident size of the host (`rss_host_kb`) and of every process the registry names (`role`, `name`, `pid`, `rss_kb`), and of the processes of every open window: the page web content process of each window (`role` `page`, `window`, `pid`, `rss_kb`), the web content process of each document web view (`role` `document`, `window`, `surface`, `pid`, `rss_kb`), and each registered plugin-host web view (`role` `plugin-host`, `window`, `plugin`, `pid`, `rss_kb`). Each reading is one event `host.sampler.memory`, so memory readings attribute themselves. Each process reading also holds `footprint_kb`, the physical footprint of the process (macOS: `ri_phys_footprint` of `proc_pid_rusage`), which counts the pages that the process owns and not the shared pages that the resident size counts. Rows identify owners, not unique processes: repeated PIDs refer to the same physical process, and consumers deduplicate by PID when totaling process memory. A web view whose process has not started (`pid` 0) records `error` instead of the sizes. A window whose facts cannot be read records `role`, `window` and `error`. A reading that cannot obtain a size records `error` instead of the size.

## Plugin-host frame measurement

A built plugin host can be measured with a test fixture that runs a `requestAnimationFrame` counter in its host page and returns the cumulative count, `performance.now()` timestamp, and `performance.timeOrigin` through a declared command. The fixture reads the count at the start and end of the observation; it does not publish a snapshot for each frame. The collector requires both origins to be finite, positive, and equal before computing elapsed time and count delta, so a page replacement cannot join readings from different page clocks. The existing `host.sampler.memory` events identify the measured plugin-host process and provide host-side sample timestamps during the observation; those timestamps are a separate clock and are not subtracted from page values. Zero callbacks is a valid measurement. This procedure records observed rate and process identity without asserting a frame-rate threshold or changing plugin-host behavior.

## The switch

The process of the host holds the switch; no file holds it and no flag reaches a sidecar. The page reads `diagnostics.performance` from the settings it already loads and tells the host through the host call `performance` — `on` when the setting turns true, `off` when it turns false, and once at startup with the stored value, so a switch of the host that a page which ended left on returns to the stored state. The call accepts the actions `on` and `off` only and refuses any other action with an error; a request that does not change the switch stores nothing. Turning the trace on stores `host.trace.on` and starts the sampler, which stores `host.sampler.memory` every five seconds while the trace is on; turning it off stores `host.trace.off` and ends the sampler, and turning it on again starts a new one. A start of the process always starts with the trace off. Passive instrumentation reports failures without replacing the measured operation result.

## Reading

The event files are JSON lines, so field tools answer questions directly: the frame reasons of an idle terminal (`select(.event=="frame") | group_by(.reason)`), the raster values a drag through collapse produced (`select(.event=="configure")`), whether tab switching recreated webviews (`select(.event=="surface")`), and what memory did around a user action (`select(.event=="action")`).
