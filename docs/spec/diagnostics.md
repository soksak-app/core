# Diagnostics

[한국어](diagnostics.ko.md)

A defect that appears once on a user's machine is located only from records that the application wrote before the defect appeared. This document is the one place that states which records exist, who writes them, their form, and where each failure leaves its record. [Hosts](hosts.md#application-log), the [performance trace](performance-trace.md) and the [debug view](debug.md) state the details of their own parts and refer here for the table of files and the rules.

The same callback artifact records `writerEnqueuedTime`, `writerStartTime`, and `writerCompleteTime` as raw Mach ticks encoded as decimal strings, or null when that writer stage did not run. Enqueue time belongs to the sample callback; writer start and completion belong to the serial frame writer and bracket compression and the file write, close and rename attempt. Completion is not a successful-write assertion or a durable-storage guarantee. The final artifact joins writer-owned measurements by the existing frame filename after a serial-queue snapshot; it does not mutate callback dictionaries from the writer thread. Writer measurements have the existing per-recording callback bound and are cleared with the callback trace before the next recording.

A recording plans at most 4096 stills, and a start whose plan holds more is refused. It admits at most 64 pending frame writes: a still that finds the writer full fails with `capture pending writer capacity exceeded (64 frames)`, an explicit recording error, and the stills after it are still requested. It admits at most 8 stills whose image the window server has not given yet: a still whose request finds 8 of them fails at once with `capture in-flight capacity exceeded (8 stills)`, an explicit recording error, takes no window, and the stills after it are still requested. A still takes a median of 0.5 ms, so only a still that takes longer than 8 gaps reaches the limit, and a window server that does not answer is not given further requests.

A diagnostic recording owns its output directory until the native recording has ended and finish transfers it, or abort removes it. A stop ends the native recording also when it fails, so a stop error and the end of the recording are distinct. A stop closes the requests, waits for every requested still and the frame writer, and writes the records before it returns, so nothing of the recording completes after it. Finish preserves the directory and reports finalization errors while releasing ownership of the ended recording. A failed directory removal retains cleanup ownership and blocks another start; a removal retry does not stop the ended recording again. The Rust recording owner attempts cleanup before resuming a start panic; the host panic policy still terminates the process and may leave crash artifacts. A failed directory creation does not acquire or remove the requested path. Poisoned document-frame lifecycle and pending-start locks return explicit errors instead of continuing with uncertain state.

## Folder

Every diagnostic file of an application is under `<config-dir>/logs/`. A person who meets a defect hands over this folder, and the [debug view](debug.md) lists and saves it. No other folder holds a diagnostic file. Operating files such as `process.lock` are not records and stay outside `logs/`.

`<time>` is the UTC time `YYYYMMDDTHHMMSSZ`. A stall sample is written by the window-check harness and not by the application, because a host that does not answer cannot sample itself; the harness then sends `diagnostics.stall.dump` so that the host stores the path of the file as an event.

The harness reports each sample in one record: the path of each file, joined by `, `, and then `host.stall.dump at <boot>:<seq>` or the reason why the host did not store it. The record of a page process is its path, or `page <pid> not sampled: <reason>`. When a thread of the sample of a page process is at the top of its stack in `flock` of `libsystem_kernel` (the section `Sort by top of stack, same collapsed` of `sample`), its path is followed by the fields of that wait, each after `; `:

| Field | Value |
|---|---|
| `flock.file=<path>` | the one regular file that the process has open on a numbered descriptor (`lsof -n -P -F pcftn -p <pid>`) on which `fcntl(F_GETLK)` finds a lock with `l_pid` -1, the form of a lock of `flock` on macOS |
| `flock.holder=<pid> <command>` | after `flock.file`: the one process other than the waiting one that has the file open (`lsof -n -P -F pcftn -- <path>`), or the waiting process when it has the file open more than once, because a lock of `flock` belongs to an open file description |
| `flock.holder.error=<reason>` | after `flock.file`, in place of `flock.holder`: no such process, or the several processes that have the file open |
| `flock.file.error=<reason>` | in place of both: no regular file open, no file or several files with a lock of `flock`, or a file whose lock was not read |
| `flock.error=<reason>` | in place of all: the sample, `lsof` or the lock probe could not be read |

macOS names no holder of a lock of `flock`: `lsof` reports no such lock, and `F_GETLK` answers it with `l_pid` -1, so the holder is read from the processes that have the file open. `lsof` sees the processes of the same user only. The lock probe is `fcntl(F_GETLK)` of `/usr/bin/perl`, the one program of macOS that asks the lock of another file. A record of a page process that waits in no `flock` has none of these fields.

A recording is a series of stills. Each still is the image of the recorded windows that the window server composited, which the application asks for with `CGWindowListCreateImageFromArray`. The image that the call returns refers to the surfaces of the windows until its pixels are read, so the capture copies its pixels as part of the still. The capture reads the request time right before that call and the completion time right after the copy: the window showed the content of the still at some time between the two. The header of each frame file carries both times in milliseconds on the clock of `sp_capture_clock`, the mach absolute time. Still n is planned at the request of still 0 plus n·`gap` and is requested at its planned time whether or not the stills before it completed, so a slow still does not move the stills after it. A still does not report every display refresh and does not identify the drawable that the application presented. Two stills can hold the same unchanged pixels; each keeps its own times, because an unchanged image does not identify a new drawable. Still times and a drawable's presented time describe separate observations; convert and compare cadence within each source, report their signed offset, and do not assume their timestamps are equal or ordered. ScreenCaptureKit is not used: the stream of a covered window stopped delivering frames one to two seconds after its start, and its still could not follow a refresh of 8.3 ms (F746). A frame and a still PNG hold the bytes that the window server composited, in the colour space of its image, which is the colour space of the display, and convert no colour: a conversion to sRGB changed composited values by 1 to 3 (sRGB `32c8c8` was composited as `64c5c7` of the display and came back as `31c8c9`), and so did a conversion of the sRGB value to the display space (`65c5c7`). The recording names that space by `colorSpace` and `colorProfile` of each still. The PNG names it by an ICC profile that ImageIO writes: for a display profile that equals a standard one, the standard profile (Display P3 for the 4076-byte "Color LCD" profile of a built-in display), which reads every byte as the same colour. Stills are evidence and no check judges their pixels: a check judges that the stills are taken as planned, their request and completion times, the windows that each still holds, and the format of the record and the frame files. When a check fails, its stills are read as its evidence.

Each recording's `stills.jsonl` has one row per planned still, at most 4096, in the order of `index` from 0. `planned`, `requested`, and `completed` are raw mach absolute ticks encoded as decimal strings: `requested` and `completed` are `null` for a still that was not requested, and `completed` is `null` for a still whose windows could not be taken. `outcome` is `written`, `failed`, or `not-requested`; `error` is the reason of a failed still or `null`; `frame` is the file name `frame-NNNN.bgra` of a written still, numbered by its `index`, or `null`; `windows` lists the window server numbers that the still took, front to back. `colorSpace` is the Core Graphics name of the colour space of a written still, or `null` for a space without a name, such as the profile of a display; `colorProfile` is the file name `color-<first 16 hex digits of the SHA-256 of the profile>.icc` of its ICC profile in the recording folder, which the first still in that space writes. Both are `null` for a still without a frame. `requestedGap` is the `gap` of the recording in milliseconds, and `machTimebaseNumerator` and `machTimebaseDenominator` give the timebase of the recording. `writeStartTime`, `writeCompleteTime`, `writerEnqueuedTime`, `writerStartTime`, and `writerCompleteTime` are raw mach absolute ticks encoded as decimal strings when present; stage fields are JSON `null` when that stage did not run. `writeStartTime` and `writeCompleteTime` bracket the synchronous processing of the still after its completion; the three writer ticks bracket the asynchronous frame write. These measurements add no converted duration. A still never waits for pending disk writes: a still that finds 64 frames waiting for the writer fails with `capture pending writer capacity exceeded (64 frames)`, so it does not move the requests after it. A still never waits for the images of earlier stills either: a still whose request finds 8 stills waiting for their image fails with `capture in-flight capacity exceeded (8 stills)`, with its `requested` time, no `completed` time and an empty `windows`. The stop reply counts `missed`, the planned stills without a written frame, failed or not requested; `late`, the stills requested more than one `gap` after their planned time; and `longestGap`, the longest interval in milliseconds between the request times of two consecutive written frames. Low still latency does not establish presentation cadence. IME functional acceptance follows the stage-proof contract in [verification](verification.md); capture gaps remain separate measurements. A missing stage pair is not a zero-duration measurement.

Capture stop with `after` above 0 waits until a still requested at or after `after`, in milliseconds on the clock of `sp_capture_clock`, has completed; a still that completed before the stop registers its wait already qualifies. A plan whose last still is requested before `after` ends the stop with the error `the recording ended at <t> ms, before the requested time <after> ms`. Otherwise stop waits without a limit, until one of the ends that `diagnostics.capture.stop` names ([endpoint](endpoint.md)), and that end is its explicit error, `no still was requested at the requested time before <end>`. With `after` 0 the stop requests no later still. The stop then closes the requests: every still whose planned time has come is requested first, also when the timer that requests it has not fired yet (such a still is late), and the stills planned after the close stay `not-requested`; the stop waits for every requested still and the frame writer, and writes `stills.jsonl` and `display-link.json`. The close of the recorded window ends the recording: the stills not yet requested fail with `the recorded window <n> closed`, which is also the error of the recording.

A still takes the recorded window and its child windows as the window server composited them, also while another window covers the window; a window that the window server does not list on screen has no still and fails it with `window <n> is not on screen`. The windows of the next still follow the display-link callbacks of the recording: a callback reads on the main thread only the windows that AppKit shows, and the window server is asked for their order and bounds on a capture queue, so the main thread never waits for the window server. While an earlier read waits there, a callback reads no windows and the next still keeps the windows of the earlier read; `skippedWindowReads` of the lifecycle events counts these callbacks.

The standard error holds only what no writer of the contract writes. The Wails framework writes the line `[AssetFileServerFS] Handling request` at the level `info` for every file that a page requests, which filled the file with 2.0 MB of lines that state no failure. The Wails host therefore gives the logger of the framework the level `warn` (`FrameworkLogLevel`): the request lines are left out and the warnings and errors of the framework stay. The requests that matter are stated by `host.binding.call`, `workbench.call` and the `error` records of the host. The Tauri host writes no such line to the standard error, so it sets no level.

## Forms

Three forms of record exist, and each fact has the form that fits it. The two line forms, the text record and the event, put the time first and the same layer names in them, so one reader can order both.

1. **Text record.** One line of a service log, and the view of a record event: `<time> <level> <layer> <where>: <text>`, separated by single spaces.
   - `<time>` is the UTC time `YYYY-MM-DDTHH:MM:SS.mmmZ` of the write, the form of `ts` of an event.
   - `<level>` is `error` for a failure and `info` for a state without a failure.
   - `<layer>` is who wrote the record: `page`, `host`, `native`, or `sidecar`.
   - `<where>` names the operation or the object, may contain spaces, and ends at the first `: `.
   - `<text>` is the rest of the line. A line feed in it is written as the two characters `\n`, so one record is always one line.

   Every failure writes a record of level `error`, and every other record is of level `info`. A writer has one helper for each level (`LogError` and `LogInfo` in Go, `log_error` and `log_info` in Rust, `sp_log_error` and `sp_log_info` in the native library, `report` with the level in the page); the helpers of the hosts and `report` store the event `<layer>.record.<level>` with the fields `where` and `text` in the event log, and the text form is the view that the window-check harness and the debug view show for it, and a site that both hosts have writes the same `<where>` and `<text>` in both. A host writes each line of the standard error of a sidecar that it reads as a record of level `info`, layer `sidecar`, and `<where>` the name of the sidecar; a persistent service writes its own standard error in this form with the same layer and `<where>`. The crash output of a runtime (the Go panic and fatal signal report, and the message of the Rust default panic hook) is the only text that has no form, because the runtime writes it.
2. **Event.** One line of an event file: a JSON object of the [event contract](logging.md#event) with `ts_us`, `seq`, `level`, `layer` and `event`, and the fields of its event. An event records what happened and when, in the order of one timeline across the layers.
3. **State file.** `state-<time>.json`: the state of the application at one time, with `time`, `host`, `versions`, `windows` and `page`. A part that the writer cannot read is recorded with its error and does not stop the file.

## Rules

- A failure point has its record in the table below. A failure point that the table does not list is a defect of this document.
- `make check-docs` reads the place of each error record that a source of a host or of the native library writes at a literal place (the first argument of `LogError`, `log_error`, `log_failure` and `sp_log_error`) and requires the table below, and its translation, to write `error <layer> <place>`; a place that a source takes from a variable or a constant (the path of a file, a label that the caller computed) has no literal text, so the check does not read it.
- A record is written at the moment of the failure, by the event that reports it. A timer or polling does not search for failures. One cause writes one line; a repeated report of the same cause adds nothing.
- Each file has a size bound that its writer applies when it opens the file. The performance trace, which has one writer, also applies it while it writes; the application log and the service logs have several writers of one descriptor, so they grow until the next open.
- A record of the input path holds everything that the layer saw: the typed text, every range and flag, every byte read from or written to the PTY, the state of the input document before and after, and a time. A defect of the input is located from the files alone, so a record is never cut and a layer never leaves out a value that it can see. The files are in `logs/` of the computer of the person, and the text that a person typed, a password included, is in them; the person hands the folder over when a defect is reported. The content of a file that a person opens is not an input and is not recorded.
- The records of the input path: the native library writes `info native input method` for each callback of the input method (`keyDown`, `insertText`, `setMarkedText`, `unmarkText`, `doCommandBySelector`, `commitThrough`, `reportPreedit`, `clearDocument`, `commitPending`, `becomeFirstResponder`, `resignFirstResponder`) as a JSON object with its arguments and the `before` and `after` state of the document (`document`, `committed`, `marked`, `selected`, `reportedPreedit`, `source`, `focus`, `closed`, `reports`, `active`, `keyWindow`), and `info native input report` for each JSON report that it sends to the page; a callback that drops its input says so in its record (`"dropped":"noop"` for a `noop:` command, `"dropped":"not text"` for an insert or marked text that is not text), and a report to a region that is closed is written as `info native input report dropped`; the native library writes `info native input inject` for each pointer or key input that the endpoint injects, as a JSON object with its arguments (`x`, `y`, `phase`, `button`, `deltaX`, `deltaY`, or `key`, `text`, `modifiers`, `down`), its `result` (`delivered`, `rejected`, `inactive`, `unreceived`, `button held`, `press open`) and the `reason` of a refusal, and for a key the class of the first responder (`responder`), whether the window is the key window (`keyWindow`), whether a key down of the [virtual key window](exposure.md#virtual-key-window) was taken as a key equivalent (`equivalent`), and whether it typed its stated text through the text input of a web view (`virtualKeyText`); the plugin writes the trace events `region`, `ime`, `input`, `send`, `send.result` and `sidecar.event` with their whole bodies; the hosts write the trace events of the layer `host` `region` (each event of a native region, with `surface`, `name` and the whole `body`), `sidecar.send` and `sidecar.receive` (each request to and message from a sidecar, with `sidecar`, `surface` and the whole `body`); the terminal sidecar writes `request` with the whole body, `pty_write` and `pty_read` with the length, the text and the hexadecimal bytes of every chunk, and `session_open`, `pty_eof`, `pty_read_error` and `session_exit`.
- A writer that cannot write its record reports the error where it can: the host that cannot open its application log does not start.
- Each failure point has a test that causes the failure and reads the record.
- The state file is complete from values that the host holds, so a window whose page did not start is in it with its `ready` value and its last error line.
- A drag paces each step by one display period of the window's display, read from `host.window.refreshRate` at that step; no period is assumed. A window on no display fails the drag with `the window is on no display with a refresh rate`. Each leg runs for its time on the host clock, so the number of steps follows the period. The reply reports the real count as `steps` and the requested time as `asked` in milliseconds.

## Reading

The application log answers what failed and where, the performance trace answers when and in what order, and the state file answers what the application held at one time. A report of a defect names the files of `logs/` and the time of the defect.

Diagnostic `diagnostics.fixture` accepts optional `debugEntries`: an ordered array of `{path,size,modified}` renderer-list inputs. Paths are unique portable relative paths below `logs/`, size and modified are nonnegative safe integers. Invalid input fails before project/settings mutation. The ordinary debug model and list renderer consume these exact entries instead of host-dependent listing results; recording, file read/save behavior and actual logs remain unchanged. Each subsequent fixture without the field restores the live provider, and reload creates an unset provider. This diagnostic-only input must be supplied identically on every compared host and checked through public `core.debug.entries`; it is not a second layout implementation or an acceptance normalization.
