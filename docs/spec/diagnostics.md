# Diagnostics

[한국어](diagnostics.ko.md)

A defect that appears once on a user's machine is located only from records that the application wrote before the defect appeared. This document is the one place that states which records exist, who writes them, their form, and where each failure leaves its record. [Hosts](hosts.md#application-log), the [performance trace](performance-trace.md) and the [debug view](debug.md) state the details of their own parts and refer here for the table of files and the rules.

## Folder

Every diagnostic file of an application is under `<config-dir>/logs/`. A person who meets a defect hands over this folder, and the [debug view](debug.md) lists and saves it. No other folder holds a diagnostic file. Operating files such as `process.lock` are not records and stay outside `logs/`.

## Files

| File | Writer | Form | Bound |
|---|---|---|---|
| `host-<boot>.stderr` | the raw standard error of the host process: the crash output of the runtime and the fatal lines of the native library | text | renamed to `host-<boot>.stderr.1` at 100 MB, when a run opens it, and the five earlier generations are kept |
| `crash-found.txt` | the host, at each start | text: the path of each crash report of the system that the host announced as `host.crash.found`, one in each line ([logging](logging.md#entrances)) | rewritten at each start to the reports that the lookup still sees, at most 64 lines |
| `stall-<pid>-<ms>.txt`, `stall-<pid>-<ms>-page-<pid>.txt` | the window-check harness, with `sample`, when a request of a host does not answer; the host stores the path as `host.stall.dump` | text | none; one file for each stall |
| `host-<boot>.jsonl` | the host process: its own records, the records of the page (a failure and an observation as `page.record.<level>` events, relayed in a batch of the host call `log`), and the events of the native library, of the levels `error`, `warn` and `info` | events of the [logging contract](logging.md) | rotated at 100 MB; the closed file is the generation `host-<boot>.jsonl.<n>` (`.1` the oldest) and no generation is removed; the [retention](logging.md#retention) bounds the folder at 6 GiB |
| `host-<boot>.debug.jsonl` | the same process: the events of the levels `debug` and `trace`, created at the first such event | events of the [logging contract](logging.md) | rotated like the main file, to `host-<boot>.debug.jsonl.<n>` |
| `log-policy.json` | the host, from the setting `diagnostics.log` | one JSON document, the [policy](logging.md#policy) of the event log, which every process watches | rewritten when the setting changes |
| `<executable-name>.log` | a persistent service, opened by the host as the standard error of the service | text records of the same form, written by the service | renamed to `<name>.1` at 100 MB, when the host starts the service, and the five earlier generations are kept |
| `heap-<pid>-<ms>.pprof` | the Wails host, in a diagnostic build, for `diagnostics.heap.profile` | heap profile of the Go runtime (`runtime/pprof`) | none; one file for each request |
| `state-<time>.json` | both hosts, when the debug view opens | one JSON document | none; one file for each opening |
| `captures/…` | both hosts, in a diagnostic build | PNG and frame files, `callback-status.jsonl`, and `display-link.json`; when image-source matching is requested, bounded source raster files and a manifest | the requester removes them |

`<time>` is the UTC time `YYYYMMDDTHHMMSSZ`. A stall sample is written by the window-check harness and not by the application, because a host that does not answer cannot sample itself; the harness then sends `diagnostics.stall.dump` so that the host stores the path of the file as an event.

For a ScreenCaptureKit frame event, `displayTime` is the mach absolute time at which WindowServer displayed that captured frame. It is not the time at which the capture callback ran, and it does not report every display refresh. `minimumFrameInterval` is a desired minimum interval between received updates that can throttle the stream; it does not promise an update at that cadence. A capture trace alone therefore cannot distinguish a missed capture sample from a longer interval between the application's actual pixel presentations. A presentation comparison must use a documented signal that reports a presented drawable and must match captured pixels to the exact drawable identity; a rendering callback or refresh notification alone is not evidence that those pixels were displayed. ScreenCaptureKit can report the same unchanged pixel ID in more than one complete sample; retain each sample and its display time, because it does not identify a new drawable. Missing unique IDs make the comparison incomplete. ScreenCaptureKit's captured-frame display time and a drawable's presented time describe separate API observations; convert and compare cadence within each source, report their signed offset, and do not assume their timestamps are equal or ordered for a matching pixel.

Each capture's `callback-status.jsonl` has one bounded record per ScreenCaptureKit callback, up to 4096 records. `callbackTime`, `writeStartTime`, `writeCompleteTime`, `displayTime`, `imageMatchStartTime`, `imageMatchCompleteTime`, `identityDecodeEnqueueStartTime`, and `identityDecodeEnqueueCompleteTime` are raw mach absolute ticks encoded as decimal strings when present; stage fields are JSON `null` when that stage did not run. `frameIdentityDecodeStartTime` and `frameIdentityDecodeCompleteTime` remain `null` in callback records because Vision runs asynchronously. `machTimebaseNumerator` and `machTimebaseDenominator` give the timebase captured for that callback. Image-match ticks bracket the call to `sp_image_capture_match_sample`. Identity enqueue ticks bracket source/region snapshot, ROI copying, and bounded decoder admission; they do not include Vision execution. Each decoded-frame row records `decodeEnqueuedTime`, `decodeStartTime`, and `decodeCompleteTime` as raw Mach ticks, with `null` when Vision did not run for that row. `writeCompleteTime` marks the end of synchronous callback processing; it does not mark completion of the asynchronous frame writer or identity decoder. These measurements add no converted duration and do not change the 33 ms complete-frame acceptance limit. Offloaded Vision decode timing and low callback latency do not prove that every full-recording frame gap meets that limit. A missing stage pair is not a zero-duration measurement.

With `frameIdentity:true`, sample intake snapshots the active session, issued payloads, source eligibility, and mapped geometry before it queues Vision work. Each mapped region is copied into an owned compact ROI buffer; no queued task retains a ScreenCaptureKit sample, pixel buffer, or full-frame image. A bounded `NSOperationQueue` runs at most two Vision decode operations concurrently. The existing serial identity lane waits for each operation and hands its result to the artifact writer asynchronously in sample order; Vision never waits on or blocks the raw-frame writer. Each admitted frame remains pending through its ordered artifact write, with at most eight running, queued, or completed-awaiting-commit jobs. Queued crop bytes continue to share the existing 64 MiB pending artifact budget while ROI buffers are retained. Admission overflow fails the identity capture explicitly; it does not drop an accepted frame or silently omit a decoded row. The existing failure reason identifies `stage` (`roi-copy` or `job-admission`), frame, `pendingJobs` and `jobLimit`, `pendingCropBytes`, `incomingCropBytes`, `artifactPendingBytes`, `byteLimit`, `jobLimitExceeded`, and `byteLimitExceeded`. These are measurements at rejection; no separate history is created. An Objective-C exception from decode is converted to an explicit identity failure after the Vision request, image/provider, ROI buffers, and pending-byte accounting are released; ordered commit reports the failure and drains normally. `callback-status.jsonl` uses `identityDecodeEnqueueStartTime` and `identityDecodeEnqueueCompleteTime` for synchronous snapshot and queue admission. Each decoded-frame row records `decodeEnqueuedTime`, `decodeStartTime`, and `decodeCompleteTime` as raw Mach ticks or `null` when Vision did not run. Capture start completes an actual encode-and-decode readiness check before it starts ScreenCaptureKit; a readiness error fails capture start. After sample intake closes, finalization closes decoder intake, drains the serial identity lane while its session remains active, then drains the artifact writer before it counts and writes the manifest.

Capture stop waits for the later of its call time and the requested absolute display time. If the sample queue has already processed a callback whose display time reaches that boundary before stop registers its wait, stop is already caught up and does not wait for another callback. Idle callbacks with a valid display time qualify as they do when the wait is armed. A pending resize still requires a callback at the new device-pixel size. Otherwise the existing one-second wait and its explicit error remain.

During diagnostic image-source matching, `latestRetainedSource.screenBounds` and `captureFrame.screenRect` use the primary display's top-left screen coordinates, and `latestSourceCrop` uses the ScreenCaptureKit frame's top-left pixel coordinates. An `unmatched` callback record includes `differentPixels` and `firstDifference` when a retained source with matching bounds, scale, and color metadata has the same dimensions as the mapped crop. The count is the number of pixels whose four BGRA bytes differ; the first difference records one crop-relative coordinate and its expected and captured BGRA bytes. This bounded sample does not relax exact matching and does not expose the rest of the image. The comparison duration includes this full pixel scan. A bounded-retention drop keeps the result `unknown-retention` even when this diagnostic sample is available.

An opt-in diagnostic frame-identity channel may embed a visible QR code inside a reserved pixel-space region outside the measured glyph region. For each image-region raster, reserve a fixed 192×192 top-right ROI at integer top-left pixel coordinates: `(width - 192, 0, 192, 192)`. Measurement fixtures keep their glyph ROI outside this reserved area. A raster too small to contain this ROI cannot be tagged. CoreImage encodes the payload as QR modules at an integer pixel scale, with a four-module white quiet zone; the ROI must fit the complete code and quiet zone or encoding fails. The code and quiet zone are centered at integer pixel coordinates; when the unused width or height is odd, the extra pixel remains on the right or bottom. Vision decodes only within the expected ROI, converting its top-left pixel rectangle to Vision's normalized bottom-left coordinates. Vision observation boxes are mapped from the request ROI with `VNImageRectForNormalizedRectUsingRegionOfInterest` and then converted to top-left image coordinates. Exactly one complete QR code inside the ROI is accepted; QR codes outside the ROI are ignored, while zero, multiple, or cropped codes inside it return an explicit unknown reason. The canonical payload contains a version, a nonce unique to one capture and region, the source `{generation,raster,sequence}`, and a SHA-256 checksum. Decoding accepts only an exact issued payload bound to the expected capture and region; malformed or unissued payloads return an explicit unknown reason. Encoding preserves every source BGRA byte outside the reserved region and preserves source color metadata. Returned raster data is immutable and cannot mutate the image. On encode success, the caller owns the image, immutable raster, and payload outputs; on encode failure, it owns the error output. Decode writes the identity on success, an unknown reason for non-matches, or an API error for a failed Vision operation; the caller owns either returned string. The channel is diagnostic evidence of a matching embedded identity only; it does not establish physical scanout. It does not change the exact image-source matcher or the capture cadence limit.

The source matcher exposes an identity session for opt-in capture wiring. Session start creates one secure random 32-byte capture nonce. A region nonce is the first 16 bytes of SHA-256 over the capture nonce followed by that region's stable 16-byte token, encoded as 32 lowercase hexadecimal characters. Reusing a `{generation,raster,sequence}` tuple in another region produces a different payload. The session issues canonical payloads only for its current capture and region and bounds the global issued set to 512 identities. Reissuing one region and source tuple is idempotent. Explicit eviction removes that payload and releases one slot; eviction of an unknown tuple is idempotent. `sp_image_capture_match_begin` and `sp_image_capture_match_end` clear the session state, and a new session creates a new nonce. The capture integration starts the session only when `frameIdentity` is true and evicts issued payloads with source-history eviction. When identity encoding or artifact writing fails, the image region still presents the unmodified source image, marks the identity session failed, and reports that failure during capture finalization. It does not claim identity success without a tag. The opt-in capture writes the original raw source artifacts unchanged and writes each tagged BGRA raster and its region token, source tuple, nonce, payload, and ROI to a separate `frame-identities` artifact. With `frameIdentity` absent or false, the layer and artifacts stay on the existing untagged path.

For `frameIdentity:true`, each complete BGRA ScreenCaptureKit sample is decoded against the retained source regions whose screen bounds map into that frame through the same crop geometry as source matching. The tag ROI is mapped from its source raster coordinates into the sample pixels; the decoder examines only that ROI and accepts only the exact payloads still issued for its region. It never infers identity from display time or nearby source sequence. The unchanged raw sample bytes and exact-match result remain in their existing artifacts. A separate `frame-identities/decoded-frames.jsonl` records one result per sample and expected region, with the source frame number, region token, mapped ROI, and either the decoded source tuple or an explicit unknown reason (`no-code`, `cropped`, `ambiguous`, `unissued`, `unknown-retention`, `unknown-geometry`, or `duplicate-roi`). A Vision API failure records an error and fails capture finalization. `frame-identities/manifest.json` describes tagged-source and decoded-frame files and their counts; its format is 1. The opt-in stop response includes `frameIdentity` with status and manifest path. The field is absent when the option is false. These results establish only that an issued code was present in a captured sample ROI; they do not prove physical scanout.

The format-1 identity manifest contains `format: 1`, `pixelFormat: "BGRA8"`, bounded `limits`, byte and artifact counts, `artifacts`, drop/write/cleanup counts and details, `decodedFramesFile`, `decodedFrames`, `decodedRecords`, `decodedWriteFailures`, and `identityFailure`. Each `artifacts` entry names a relative `.bgra` file and records the source tuple, `regionToken`, nonce, payload, source ROI, raster dimensions and stride, pixel format, alpha mode, color space, byte count, and SHA-256. Each decoded JSONL row contains `frame`, decimal-string `displayTime`, `region`, `roi`, `status`, `identity`, and `reason`; a matched row has `status: "matched"` and an identity object with decimal-string `generation` and `raster` plus integer `sequence`. An unknown row has `status: "unknown"`, a null identity, and its explicit reason. The `diagnostics.capture.stop` result returns `frameIdentity: {status: "complete", manifest: <path>}` only when identity capture was requested and finalization succeeded. A consumer reads the manifest and every decoded row from that returned path, preserves unknown and non-target rows, and checks that an observed matched tuple for a stable source equals the declared current `host.window` presented tuple and a listed issued source artifact. This equality validates the observed sample against the current source snapshot; it does not require every historical decoded row to equal that current tuple. A decoded result is evidence of the code in the captured sample; the host status establishes the current presented-source tuple. Neither establishes physical scanout or capture cadence.

While a diagnostic capture retains image sources for matching, it writes one source artifact per unique `{generation,raster,sequence}` identity to the capture folder's `sources` directory as soon as it accepts the snapshot. Repeating an identity with identical metadata and bytes is idempotent; reusing it with different metadata or bytes is rejected as an `identity-conflict` drop. Each `.bgra` file contains the exact bytes received from the accepted immutable image snapshot, without conversion. Format-2 `manifest.json` records each complete artifact's identity, relative file name, dimensions, stride, alpha and color representation, screen bounds, scale, byte count, and SHA-256. Artifact output is limited to 512 identities; each source raster must fit the 64 MiB in-memory matching history. Queued and active source raster bytes on the serial capture writer are bounded to 64 MiB independently of the total artifact bytes. A source that exceeds this pending-byte budget is explicitly rejected and recorded; enqueueing does not wait while holding the history lock. The matching history remains bounded to 64 MiB and 512 snapshots, and eviction remains visible as `unknown-retention`. A source above the per-raster or identity bound, an identity conflict, or a write failure is reported as dropped; partial files are removed, and an absent artifact does not establish that ScreenCaptureKit omitted the source. The manifest reports write failures, partial-file cleanup failures, and at most 32 cleanup error details; `cleanupErrorsOmitted` reports omitted details. Any artifact write failure makes capture finalization fail. Artifact writes use the existing capture writer queue and do not run on the image presentation thread. These files are diagnostic evidence and add disk I/O while capture is active; ordinary application operation creates none.

The standard error holds only what no writer of the contract writes. The Wails framework writes the line `[AssetFileServerFS] Handling request` at the level `info` for every file that a page requests, which filled the file with 2.0 MB of lines that state no failure. The Wails host therefore gives the logger of the framework the level `warn` (`FrameworkLogLevel`): the request lines are left out and the warnings and errors of the framework stay. The requests that matter are stated by `host.binding.call`, `page.call` and the `error` records of the host. The Tauri host writes no such line to the standard error, so it sets no level.

## Forms

Three forms of record exist, and each fact has the form that fits it. The two line forms, the text record and the event, put the time first and the same layer names in them, so one reader can order both.

1. **Text record.** One line of a service log, and the view of a record event: `<time> <level> <layer> <where>: <text>`, separated by single spaces.
   - `<time>` is the UTC time `YYYY-MM-DDTHH:MM:SS.mmmZ` of the write, the form of `ts` of an event.
   - `<level>` is `error` for a failure and `info` for a state without a failure.
   - `<layer>` is who wrote the record: `page`, `host`, `native`, or `sidecar`.
   - `<where>` names the operation or the object, may contain spaces, and ends at the first `: `.
   - `<text>` is the rest of the line. A line feed in it is written as the two characters `\n`, so one record is always one line.

   Every failure writes a record of level `error`, and every other record is of level `info`. A writer has one helper for each level (`LogError` and `LogInfo` in Go, `log_error` and `log_info` in Rust, `sp_log_error` and `sp_log_info` in the native library, `report` with the level in the page); the helpers of the hosts and `report` store the event `<layer>.record.<level>` with the fields `where` and `text` in the event log, and the text form is the view that the window-check harness and the debug view show for it, and a site that both hosts have writes the same `<where>` and `<text>` in both. A host writes each line of the standard error of a sidecar that it reads as a record of level `info`, layer `sidecar`, and `<where>` the name of the sidecar; a persistent service writes its own standard error in this form with the same layer and `<where>`. The crash output of a runtime (the Go panic and fatal signal report, and the message of the Rust default panic hook) is the only text that has no form, because the runtime writes it.
2. **Event.** One line of an event file: a JSON object of the [event contract](logging.md#event) with `ts_us`, `seq`, `level`, `layer` and `event`, and the fields of its event. An event records what happened and when, in the order of one timeline across the layers.
3. **State file.** `state-<time>.json`: the state of the application at one time, with `time`, `host`, `versions`, `windows` and `page`. A part that the writer cannot read is recorded with its error and does not stop the file.

## Rules

- A failure point has its record in the table below. A failure point that the table does not list is a defect of this document.
- `make failures-check` (part of `make docs-check`) reads the place of each error record that a source of a host or of the native library writes at a literal place (the first argument of `LogError`, `log_error`, `log_failure` and `sp_log_error`) and requires the table below, and its translation, to write `error <layer> <place>`; a place that a source takes from a variable or a constant (the path of a file, a label that the caller computed) has no literal text, so the check does not read it.
- A record is written at the moment of the failure, by the event that reports it. A timer or polling does not search for failures. One cause writes one line; a repeated report of the same cause adds nothing.
- Each file has a size bound that its writer applies when it opens the file. The performance trace, which has one writer, also applies it while it writes; the application log and the service logs have several writers of one descriptor, so they grow until the next open.
- A record of the input path holds everything that the layer saw: the typed text, every range and flag, every byte read from or written to the PTY, the state of the input document before and after, and a time. A defect of the input is located from the files alone, so a record is never cut and a layer never leaves out a value that it can see. The files are in `logs/` of the computer of the person, and the text that a person typed, a password included, is in them; the person hands the folder over when a defect is reported. The content of a file that a person opens is not an input and is not recorded.
- The records of the input path: the native library writes `info native input method` for each callback of the input method (`keyDown`, `insertText`, `setMarkedText`, `unmarkText`, `doCommandBySelector`, `commitThrough`, `reportPreedit`, `clearDocument`, `commitPending`, `becomeFirstResponder`, `resignFirstResponder`) as a JSON object with its arguments and the `before` and `after` state of the document (`document`, `committed`, `marked`, `selected`, `reportedPreedit`, `source`, `focus`, `closed`, `reports`, `active`, `keyWindow`), and `info native input report` for each JSON report that it sends to the page; a callback that drops its input says so in its record (`"dropped":"noop"` for a `noop:` command, `"dropped":"not text"` for an insert or marked text that is not text), and a report to a region that is closed is written as `info native input report dropped`; the native library writes `info native input inject` for each pointer or key input that the endpoint injects, as a JSON object with its arguments (`x`, `y`, `phase`, `button`, `deltaX`, `deltaY`, or `key`, `text`, `modifiers`, `down`), its `result` (`delivered`, `rejected`, `inactive`, `unreceived`, `button held`, `press open`) and the `reason` of a refusal, and for a key the class of the first responder (`responder`) and whether the window is the key window (`keyWindow`); the plugin writes the trace events `region`, `ime`, `input`, `send`, `send.result` and `sidecar.event` with their whole bodies; the hosts write the trace events of the layer `host` `region` (each event of a native region, with `surface`, `name` and the whole `body`), `sidecar.send` and `sidecar.receive` (each request to and message from a sidecar, with `sidecar`, `surface` and the whole `body`); the terminal sidecar writes `request` with the whole body, `pty_write` and `pty_read` with the length, the text and the hexadecimal bytes of every chunk, and `session_open`, `pty_eof`, `pty_read_error` and `session_exit`.
- A writer that cannot write its record reports the error where it can: the host that cannot open its application log does not start.
- Each failure point has a test that causes the failure and reads the record.
- The state file is complete from values that the host holds, so a window whose page did not start is in it with its `ready` value and its last error line.

## Reading

The application log answers what failed and where, the performance trace answers when and in what order, and the state file answers what the application held at one time. A report of a defect names the files of `logs/` and the time of the defect.
