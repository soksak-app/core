# 진단

[English](diagnostics.md)

사용자 컴퓨터에서 한 번 나타난 결함은 결함이 나타나기 전에 애플리케이션이 써 둔 기록으로만 원인을 찾는다. 이 문서는 어떤 기록이 있는지, 누가 쓰는지, 형태가 어떤지, 각 실패가 어디에 기록을 남기는지를 정하는 한 곳이다. [host](hosts.ko.md#애플리케이션-로그), [performance trace](performance-trace.ko.md), [debug view](debug.ko.md)는 자기 부분의 세부를 정하고 파일 표와 규칙은 여기를 가리킨다.

동일한 callback artifact는 `writerEnqueuedTime`, `writerStartTime`, `writerCompleteTime`을 10진수 문자열의 raw Mach tick으로 기록하며 실행하지 않은 writer 단계는 null로 기록한다. Enqueue 시각은 sample callback에 속하고 writer 시작과 완료 시각은 serial frame writer에 속하며 압축 및 file write, close, rename 시도를 감싼다. 완료 시각은 쓰기 성공 또는 durable storage를 보장하지 않는다. 최종 artifact는 serial queue snapshot 뒤에 기존 frame 파일명으로 writer 소유 측정을 연결하며 writer thread에서 callback dictionary를 변경하지 않는다. Writer 측정은 기존 recording별 callback 제한을 따르고 다음 recording 전에 callback trace와 함께 비운다.

Recording은 still을 최대 4096장까지 계획하고, 그보다 많은 계획의 start는 거부된다. Still은 자기 worker에서 그리고 압축하며, 그 pixel(header 76 bytes와 pixel 하나당 4 bytes)은 압축 직후 unmap한다. Frame writer를 기다리는 것은 encoded frame(header 88 bytes와 LZ4 block)뿐이다. Writer를 기다리는 encoded frame은 최대 128 MiB(134217728 bytes)이고, writer는 frame을 쓴 뒤 그 bytes를 돌려준다. 그리기 전에, 또는 encoded frame으로 상한에 닿은 still은 명시적 recording 오류인 `capture pending writer capacity exceeded (134217728 bytes)`로 실패하고, 그 뒤의 still은 그대로 요청된다. 상한은 장수가 아니라 bytes를 세므로 작은 창이든 display 전체든 writer의 메모리를 묶는다. Buffer는 system에서 map하고 돌려줄 때 unmap하므로, 기록된 still은 host footprint에 해제된 메모리를 남기지 않는다. 값은 7680x4320 display의 압축되지 않는 still 하나의 encoded frame 133 231 064 bytes(header 88 bytes와, pixel bytes `p`에 대한 LZ4 block `p + ⌊p/255⌋ + 144` bytes)를 담는 가장 작은 2의 거듭제곱이다. 2026-11-12 window run에서 2400x1520 창의 encoded still은 pixel 14 592 000 bytes에 대해 중앙값 208 346 bytes였으므로 644장이 들어간다(120 Hz에서 5.4 s). Writer가 뒤처진 것은 기계가 멈춘 동안뿐이었고, 그때 still 64장이 기다리고 125장이 더 거부되었다(still 189장, encoded로 38 MiB). 이 상한이 대신한 64장 상한은 그 창의 raw frame 64장을 기다리게 했고(writer 안의 frame까지 949 MB), host footprint는 805 MB에 이르렀으며 그중 668 MB가 allocator가 쥐고 있던 해제된 still이었다. In flight인 still은 최대 8개다. Still은 window server에 image를 요청한 때부터, 어느 출구로든 압축 뒤 pixel을 unmap할 때까지 in flight다. 요청 때 그런 still이 8개면 그 still은 명시적 recording 오류인 `capture in-flight capacity exceeded (8 stills)`로 즉시 실패하고 창을 받지 않으며, 그 뒤의 still은 그대로 요청된다. Window server에 요청한 image, 복사한 image, still의 pixel frame이 모두 그 안에 있으므로 두 상한이 함께 녹화의 메모리를 묶는다. 압축 전에는 pixel frame 최대 8장(8 × (76 + 4 × pixel 수) bytes, window run의 2400x1520 창에서 117 MB), 압축 뒤에는 writer를 기다리는 encoded frame 최대 128 MiB다. Still은 window server에서 중앙값 0.5 ms, 압축에 몇 ms가 걸리므로 8 gap보다 오래 걸리는 still만 이 상한에 닿고, 앞 still을 끝내지 못한 window server나 압축에 still이 더 쌓이지 않는다.

Diagnostic recording은 native recording이 끝난 뒤 finish가 넘기거나 abort가 삭제할 때까지 출력 directory를 소유한다. Stop은 실패해도 native recording을 끝내므로 stop 오류와 recording의 끝은 별개다. Stop은 요청을 닫고, 요청한 모든 still과 frame writer를 기다리고, 기록을 쓴 뒤 돌아오므로 그 뒤에 완료되는 것이 없다. Finish는 directory를 보존하고 finalization 오류를 보고하면서 끝난 recording의 소유권을 해제한다. Directory 삭제 실패는 cleanup 소유권을 유지하고 다음 start를 차단한다. 삭제 재시도는 끝난 recording을 다시 stop하지 않는다. Rust recording owner는 start panic을 다시 전달하기 전에 cleanup을 시도하며 host panic 정책은 여전히 프로세스를 종료하고 crash artifact가 남을 수 있다. Directory 생성 실패는 요청한 path의 소유권을 얻거나 삭제하지 않는다. Poison된 document-frame lifecycle 및 pending-start lock은 불확실한 상태로 진행하지 않고 명시적 오류를 반환한다.

## 폴더

애플리케이션의 모든 진단 파일은 `<config-dir>/logs/` 아래에 있다. 결함을 만난 사람은 이 폴더를 넘기고, [debug view](debug.ko.md)가 이 폴더를 나열하고 저장한다. 진단 파일을 담는 다른 폴더는 없다. `process.lock` 같은 운영 파일은 기록이 아니므로 `logs/` 밖에 둔다.

## 파일

| 파일 | 쓰는 쪽 | 형태 | 한계 |
|---|---|---|---|
| `host-<boot>.stderr` | host 프로세스의 raw 표준 오류: 런타임의 crash 출력과 native 라이브러리의 fatal 줄 | 글 | 실행이 열 때 100 MB이면 `host-<boot>.stderr.1`로 이름을 바꾸고 이전 세대 다섯 개를 남긴다 |
| `crash-found.txt` | 시작할 때마다 host | 글: host가 `host.crash.found`로 알린 시스템 crash report의 경로, 한 줄에 하나([로깅](logging.ko.md)) | 시작할 때마다 lookup이 아직 보는 report만 남기도록 다시 쓴다. 최대 64줄 |
| `stall-<pid>-<ms>.txt`, `stall-<pid>-<ms>-page-<pid>.txt` | host가 응답하지 않을 때 창 검사 harness가 `sample`로 쓴다. host는 경로를 `host.stall.dump`로 저장한다 | 글 | 없음. 정지마다 파일 하나 |

| `host-<boot>.debug.jsonl` | 같은 프로세스: level `debug`와 `trace`의 event. 첫 event에서 만든다 | [로깅 계약](logging.ko.md)의 event | main 파일처럼 회전하며 `host-<boot>.debug.jsonl.<n>`이 된다 |
| `log-policy.json` | host. 설정 `diagnostics.log`에서 쓴다 | JSON 문서 하나, event 로그의 [정책](logging.ko.md#정책)이며 모든 프로세스가 감시한다 | 설정이 바뀔 때 다시 쓴다 |
| `<executable-name>.log` | 상주 service. host가 service의 standard error로 연다 | service가 쓰는 같은 형식의 글 기록 | host가 service를 시작할 때 100 MB이면 `<name>.1`로 이름을 바꾸고 이전 세대 다섯 개를 남긴다 |
| `heap-<pid>-<ms>.pprof` | 진단 build의 Go host가 `diagnostics.heap.profile`에 쓴다 | Go runtime의 heap profile(`runtime/pprof`) | 없음. 요청마다 파일 하나 |
| `cpu-<pid>-<ms>.pprof` | 진단 build의 Go host가 `diagnostics.cpu.profile`에 쓴다 | 시작과 멈춤 사이 Go runtime의 CPU profile(`runtime/pprof`) | 없음. 시작마다 파일 하나 |
| `state-<time>.json` | debug view가 열릴 때 두 host | JSON 문서 하나 | 없음. 열 때마다 파일 하나 |
| `captures/…` | 진단 빌드의 두 host | PNG와 frame 파일, `stills.jsonl`, `display-link.json`. Image-source matching을 요청하면 상한이 있는 source raster 파일과 manifest도 기록한다 | 요청한 쪽이 지운다 |

`<time>`은 UTC 시각 `YYYYMMDDTHHMMSSZ`다. 응답 정지 sample은 애플리케이션이 아니라 창 검사 harness가 쓴다. 응답하지 않는 host는 자신을 sample할 수 없기 때문이며, harness는 이어서 `diagnostics.stall.dump`를 보내 host가 파일 경로를 event로 저장하게 한다.

harness는 sample 하나를 record 하나로 알린다. 각 파일의 경로를 `, `로 이은 뒤 `host.stall.dump at <boot>:<seq>` 또는 host가 저장하지 않은 이유가 온다. page process의 record는 그 경로이거나 `page <pid> not sampled: <reason>`이다. page process의 sample에서 한 thread가 `libsystem_kernel`의 `flock`에서 stack의 맨 위에 있으면(`sample`의 `Sort by top of stack, same collapsed` 구역), 그 경로 뒤에 그 대기의 field가 각각 `; ` 뒤에 붙는다.

| Field | 값 |
|---|---|
| `flock.file=<path>` | process가 번호 있는 descriptor로 연 regular file 가운데(`lsof -n -P -F pcftn -p <pid>`) `fcntl(F_GETLK)`가 `l_pid` -1인 lock을 찾는 단 하나의 파일. macOS에서 `flock`의 lock은 이 형태다 |
| `flock.holder=<pid> <command>` | `flock.file` 뒤. 기다리는 process 말고 그 파일을 연 단 하나의 process(`lsof -n -P -F pcftn -- <path>`), 또는 기다리는 process가 그 파일을 두 번 이상 열었으면 그 process. `flock`의 lock은 open file description에 속하기 때문이다 |
| `flock.holder.error=<reason>` | `flock.file` 뒤, `flock.holder` 대신. 그런 process가 없거나, 파일을 연 process가 여럿이다 |
| `flock.file.error=<reason>` | 둘 대신. 연 regular file이 없거나, `flock`의 lock을 가진 파일이 없거나 여럿이거나, lock을 읽지 못한 파일이 있다 |
| `flock.error=<reason>` | 모두 대신. sample, `lsof` 또는 lock probe를 읽지 못했다 |

macOS는 `flock`의 lock을 가진 process를 알려 주지 않는다. `lsof`는 그 lock을 보고하지 않고 `F_GETLK`는 `l_pid` -1로 답하므로, holder는 그 파일을 연 process에서 읽는다. `lsof`는 같은 user의 process만 본다. lock probe는 `/usr/bin/perl`의 `fcntl(F_GETLK)`이다. macOS에서 다른 파일의 lock을 묻는 program은 이것뿐이다. `flock`에서 기다리지 않는 page process의 record에는 이 field가 없다.

녹화는 still의 연속이다. 각 still은 window server가 합성한 녹화 창의 image이며, application이 `CGWindowListCreateImageFromArray`로 요청한다. 호출이 돌려준 image는 pixel을 읽을 때까지 창의 surface를 가리키므로, capture는 still의 일부로 그 pixel을 복사한다. Capture는 그 호출 직전에 요청 시각을, 복사 직후에 완료 시각을 읽는다. 창은 두 시각 사이의 어느 시점에 still의 내용을 보여 주었다. 각 frame 파일의 header는 두 시각을 `sp_capture_clock`의 clock, 곧 mach absolute time의 millisecond로 담는다. Still n은 still 0의 요청 시각에 n·`gap`을 더한 시각으로 계획되고, 앞 still이 완료됐는지와 관계없이 계획 시각에 요청된다. 그래서 느린 still이 뒤 still을 밀지 않는다. Still은 모든 display refresh를 보고하지 않으며 application이 present한 drawable을 식별하지 않는다. 두 still이 바뀌지 않은 같은 pixel을 담을 수 있다. 바뀌지 않은 image는 새 drawable을 뜻하지 않으므로 각 still은 자기 시각을 보존한다. Still 시각과 drawable 표시 시각은 별도 관측값이다. 각 source의 cadence를 변환해 비교하고 signed offset을 기록하되, 두 timestamp가 같거나 앞뒤 순서가 정해졌다고 가정하지 않는다. ScreenCaptureKit은 쓰지 않는다: 가려진 창의 stream은 시작 1–2초 뒤 frame을 멈췄고, 그 still은 8.3 ms refresh를 따라가지 못했다(F746). Frame과 정지 PNG는 window server가 합성한 byte를 그 image의 colour space, 곧 display의 colour space 그대로 담고 색을 변환하지 않는다: sRGB로 변환하면 합성된 값이 1–3 달라졌고(sRGB `32c8c8`은 display의 `64c5c7`로 합성되었고 `31c8c9`로 돌아왔다), sRGB 값을 display 공간으로 변환해도 달랐다(`65c5c7`). 녹화는 그 공간을 still마다 `colorSpace`와 `colorProfile`로 밝힌다. PNG는 ImageIO가 쓰는 ICC profile로 그 공간을 밝힌다: 표준 profile과 같은 display profile이면 그 표준 profile을 쓰며(내장 display의 4076 byte "Color LCD" profile이면 Display P3), 모든 byte를 같은 색으로 읽는다. Still은 증거이며 어떤 검사도 그 pixel을 판정하지 않는다: 검사는 still이 계획대로 찍히는지, 요청·완료 시각, 각 still이 담는 창, 기록과 frame 파일의 형식을 판정한다. 검사가 실패하면 그 still을 증거로 읽는다.

녹화마다 `stills.jsonl`은 계획한 still 하나당 row 하나를 0부터 `index` 순서로 쓰며 최대 4096개다. `planned`, `requested`, `completed`는 raw mach absolute tick을 10진 문자열로 기록한다. 요청하지 않은 still은 `requested`와 `completed`가 `null`이고, 창을 받지 못한 still은 `completed`가 `null`이다. `outcome`은 `written`, `failed`, `not-requested` 중 하나다. `error`는 실패한 still의 reason 또는 `null`이고, `frame`은 기록한 still의 파일명 `frame-NNNN.bgra`(번호는 `index`) 또는 `null`이며, `windows`는 still이 받은 window server 번호를 앞에서 뒤 순서로 담는다. `colorSpace`는 기록한 still의 colour space의 Core Graphics 이름이며, display의 profile처럼 이름이 없는 공간이면 `null`이다. `colorProfile`은 녹화 폴더 안 그 ICC profile 파일의 이름 `color-<profile SHA-256 앞 16 hex 자리>.icc`이며, 그 공간의 첫 still이 쓴다. Frame이 없는 still은 둘 다 `null`이다. `requestedGap`은 녹화의 `gap`(ms)이고 `machTimebaseNumerator`와 `machTimebaseDenominator`는 녹화의 timebase다. `writeStartTime`, `writeCompleteTime`, `writerEnqueuedTime`, `writerStartTime`, `writerCompleteTime`은 값이 있으면 raw mach absolute tick을 10진 문자열로 기록한다. 단계가 실행되지 않은 tick 필드는 JSON `null`이다. `writeStartTime`과 `writeCompleteTime`은 압축을 포함한 완료된 still의 동기 처리를 감싸고, 세 writer tick은 encoded frame의 비동기 기록을 감싼다. 이 측정은 변환 duration을 추가하지 않는다. Still은 대기 중인 디스크 쓰기를 기다리지 않는다. Writer를 기다리는 encoded frame이 상한에 닿아 있으면 still은 `capture pending writer capacity exceeded (134217728 bytes)`로 실패하므로 뒤 요청을 밀지 않는다. Still은 in flight인 앞 still도 기다리지 않는다. 요청 때 image 요청부터 pixel 해제 사이에 있는 still이 8개면 그 still은 `capture in-flight capacity exceeded (8 stills)`로 실패하며, `requested` 시각은 있고 `completed` 시각은 없으며 `windows`는 비어 있다. Stop 응답은 `missed`(기록한 frame이 없는 계획 still, 곧 실패했거나 요청하지 않은 still), `late`(계획 시각보다 `gap` 하나를 넘겨 요청한 still), `longestGap`(연속한 두 기록 frame의 요청 시각 사이의 가장 긴 간격, ms)을 센다. 짧은 still latency만으로 presentation cadence를 입증하지 않는다. IME 기능 acceptance는 [검증](verification.ko.md)의 stage-proof contract를 따르며 capture gap은 별도 측정으로 남긴다. 단계 tick이 빠졌다고 0 duration으로 간주하지 않는다.

`after`가 0보다 큰 capture stop은 `after`(`sp_capture_clock`의 clock, ms) 이후에 요청한 still이 완료될 때까지 기다린다. Stop이 wait를 등록하기 전에 완료된 still도 조건을 만족한다. 마지막 still이 `after` 전에 요청된 계획은 `the recording ended at <t> ms, before the requested time <after> ms` 오류로 stop을 끝낸다. 그 밖에는 stop이 제한 없이 `diagnostics.capture.stop`이 드는 끝([endpoint](endpoint.ko.md)) 가운데 하나까지 기다리며, 그 끝이 명시적 오류 `no still was requested at the requested time before <end>`다. `after`가 0이면 stop은 더 이상 still을 요청하지 않는다. 그다음 stop은 요청을 닫는다. 계획 시각이 이미 온 still은 그것을 요청하는 timer가 아직 울리지 않았어도 먼저 요청하고(그런 still은 late다), 닫은 뒤에 계획된 still은 `not-requested`로 남는다. stop은 요청한 모든 still과 frame writer를 기다린 뒤 `stills.jsonl`과 `display-link.json`을 쓴다. 녹화 창이 닫히면 녹화가 끝난다: 아직 요청하지 않은 still은 `the recorded window <n> closed`로 실패하고, 이것이 녹화의 오류이기도 하다.

Still은 녹화 창과 그 child window를 window server가 합성한 그대로 받으며, 다른 창이 창을 가려도 같다. Window server가 화면에 있다고 나열하지 않는 창은 still이 없고 `window <n> is not on screen`으로 실패한다. 다음 still의 창은 녹화의 display-link callback을 따른다. Callback은 main thread에서 AppKit이 보이는 창만 읽고, 그 순서와 bounds는 capture queue에서 window server에 묻는다. 그래서 main thread는 window server를 기다리지 않는다. 앞선 읽기가 그 queue에서 기다리는 동안 callback은 창을 읽지 않고 다음 still은 앞선 읽기의 창을 그대로 쓴다. Lifecycle event의 `skippedWindowReads`가 이런 callback 수를 센다.

표준 오류에는 계약의 어떤 writer도 쓰지 않는 것만 남는다. Wails 프레임워크는 page가 파일을 요청할 때마다 `[AssetFileServerFS] Handling request` 줄을 level `info`로 쓰며, 이 줄이 실패를 뜻하지 않는 2.0 MB를 파일에 채웠다. 그래서 Wails host는 프레임워크 logger의 level을 `warn`(`FrameworkLogLevel`)으로 정한다. 요청 줄은 빠지고 프레임워크의 warning과 error는 남는다. 의미 있는 요청은 `host.binding.call`, `workbench.call`, host의 `error` 기록이 밝힌다. Tauri host는 표준 오류에 그런 줄을 쓰지 않으므로 level을 정하지 않는다.

## 형태

기록은 세 형태이고, 각 사실은 맞는 형태로 기록한다. 줄 형태인 글 기록과 event는 시각을 맨 앞에 두고 같은 layer 이름을 쓰므로, 한 독자가 둘을 같은 순서로 읽는다.

1. **글 기록.** service log의 한 줄과 기록 event의 보기 `<time> <level> <layer> <where>: <text>`. 요소는 공백 하나로 구분한다.
   - `<time>`은 쓴 시각의 UTC `YYYY-MM-DDTHH:MM:SS.mmmZ`로, event의 `ts`와 같은 형태다.
   - `<level>`은 실패면 `error`, 실패가 아닌 상태면 `info`다.
   - `<layer>`는 기록을 쓴 쪽으로 `page`, `host`, `native`, `sidecar` 중 하나다.
   - `<where>`는 동작이나 대상의 이름이고 공백을 담을 수 있으며 처음 나오는 `: `에서 끝난다.
   - `<text>`는 줄의 나머지다. 그 안의 줄바꿈은 두 글자 `\n`으로 써서 기록 하나가 항상 한 줄이다.

   모든 실패는 level `error`의 기록을 쓰고, 그 밖의 기록은 level `info`다. 쓰는 쪽은 level마다 helper 하나를 가진다(Go `LogError`와 `LogInfo`, Rust `log_error`와 `log_info`, native 라이브러리 `sp_log_error`와 `sp_log_info`, page는 level을 받는 `report`). host의 helper와 `report`는 `where`와 `text` field를 가진 event `<layer>.record.<level>`를 event log에 저장하고, 글 형태는 window-check 하네스와 debug 화면이 그 event를 보이는 보기다. 두 host에 모두 있는 지점은 두 host에서 같은 `<where>`와 `<text>`를 쓴다. host는 읽는 sidecar의 표준 오류 줄마다 level `info`, layer `sidecar`, `<where>`가 sidecar 이름인 기록으로 쓰고, 상주 service는 같은 layer와 `<where>`로 자기 표준 오류를 이 형식으로 쓴다. 형식이 없는 글은 runtime이 쓰는 runtime의 crash 출력(Go panic과 fatal signal 보고, Rust 기본 panic hook의 메시지)뿐이다.
2. **Event.** event 파일의 한 줄: [event 계약](logging.ko.md#event)의 JSON 객체로 `ts_us`, `seq`, `level`, `layer`, `event`와 그 event의 필드를 가진다. event는 무슨 일이 언제 일어났는지를 계층을 가로지르는 한 시간선의 순서로 기록한다.
3. **State file.** `state-<time>.json`: 한 시점의 애플리케이션 상태로, `time`, `host`, `versions`, `windows`, `page`를 가진다. 쓰는 쪽이 읽지 못한 부분은 그 오류와 함께 기록하고 파일 쓰기를 멈추지 않는다.

## 규칙

- 실패 지점의 기록은 아래 표에 있다. 표에 없는 실패 지점은 이 문서의 결함이다.
- `make check-docs`는 host와 네이티브 라이브러리의 소스가 리터럴 장소로 쓰는 오류 기록마다(`LogError`, `log_error`, `log_failure`, `sp_log_error`의 첫 인자) 장소를 읽고, 아래 표와 그 번역이 `error <layer> <place>`를 적을 것을 요구한다. 소스가 변수나 상수(파일 경로, 호출자가 계산한 label)에서 가져오는 장소는 리터럴 텍스트가 없으므로 검사가 읽지 않는다.
- 기록은 실패가 일어난 순간 그것을 알리는 event가 쓴다. timer나 polling으로 실패를 찾지 않는다. 한 원인은 한 줄을 쓰고, 같은 원인의 반복 보고는 아무것도 더하지 않는다.
- 각 파일의 크기 한계는 쓰는 쪽이 파일을 열 때 적용한다. 쓰는 쪽이 하나인 performance trace는 쓰는 동안에도 적용하고, 한 descriptor를 여럿이 쓰는 application log와 service log는 다음에 열 때까지 커진다.
- 입력 경로의 기록은 계층이 본 모든 것을 담는다: 입력한 글자, 모든 범위와 플래그, PTY에 쓰고 읽은 모든 바이트, 전과 후의 입력 문서 상태, 시각. 입력의 결함을 파일만으로 찾으므로 기록은 자르지 않고 계층은 볼 수 있는 값을 빼지 않는다. 파일은 사람의 컴퓨터의 `logs/`에 있고, 사람이 친 글자는 비밀번호를 포함해 그 안에 있다. 결함을 알릴 때 사람이 그 폴더를 넘긴다. 사람이 여는 파일의 내용은 입력이 아니므로 기록하지 않는다.
- 입력 경로의 기록: native 라이브러리는 입력기의 각 콜백(`keyDown`, `insertText`, `setMarkedText`, `unmarkText`, `doCommandBySelector`, `commitThrough`, `reportPreedit`, `clearDocument`, `commitPending`, `becomeFirstResponder`, `resignFirstResponder`)을 인자와 문서의 `before`, `after` 상태(`document`, `committed`, `marked`, `selected`, `reportedPreedit`, `source`, `focus`, `closed`, `reports`, `active`, `keyWindow`)를 담은 JSON 객체의 `info native input method`로, page로 보내는 각 JSON 보고를 `info native input report`로 쓴다. 입력을 버리는 콜백은 그 기록에 이유를 쓰고(`noop:` 명령은 `"dropped":"noop"`, 글이 아닌 insert나 marked text는 `"dropped":"not text"`), 닫힌 영역으로 가는 보고는 `info native input report dropped`로 쓴다. native 라이브러리는 endpoint가 주입하는 각 pointer·key 입력을 인자(`x`, `y`, `phase`, `button`, `deltaX`, `deltaY` 또는 `key`, `text`, `modifiers`, `down`), `result`(`delivered`, `rejected`, `inactive`, `unreceived`, `button held`, `press open`), 거부의 `reason`을 담은 JSON 객체의 `info native input inject`로 쓰며, 키는 first responder의 class(`responder`)와 창이 key window인지(`keyWindow`), [virtual key window](exposure.ko.md#virtual-key-window)의 key down이 key equivalent로 처리되었는지(`equivalent`)와 밝힌 text를 web view의 text input으로 입력했는지(`virtualKeyText`)도 담고, plugin은 trace event `region`, `ime`, `input`, `send`, `send.result`, `sidecar.event`를 본문 전체와 함께 쓰고, host는 layer `host`의 trace event `region`(native 영역의 각 event, `surface`, `name`, 본문 전체), `sidecar.send`와 `sidecar.receive`(sidecar로 보내는 각 요청과 받는 각 메시지, `sidecar`, `surface`, 본문 전체)를 쓰며, terminal sidecar는 본문 전체를 담은 `request`, 덩어리마다 길이와 글과 16진수 바이트를 담은 `pty_write`와 `pty_read`, 그리고 `session_open`, `pty_eof`, `pty_read_error`, `session_exit`를 쓴다.
- 기록을 쓰지 못하는 쪽은 할 수 있는 곳에 오류를 알린다. application log를 열지 못한 host는 시작하지 않는다.
- 각 실패 지점에는 그 실패를 일으키고 기록을 읽는 test가 있다.
- state file은 host가 가진 값만으로 완성된다. 그래서 page가 시작하지 못한 창도 `ready` 값과 마지막 오류 줄과 함께 그 안에 있다.
- drag는 단계마다 그 순간 `host.window.refreshRate`에서 읽은 창의 표시 주기 한 개만큼 기다린다. 주기를 가정하지 않는다. 디스플레이에 없는 창은 `the window is on no display with a refresh rate`로 drag를 실패시킨다. native drag 는 주기를 이전 단계의 host 시각부터 세므로 입력 전달 시간은 주기 안에 든다. 앞 입력을 전달하는 동안 시각이 지난 단계는 바로 보내고, 다음 주기는 그 단계부터 센다. 각 구간은 host 시계로 정해진 시간만큼 이어지므로 단계 수는 주기를 따른다. 응답은 실제 단계 수를 `steps`로, 요청한 시간을 밀리초 단위 `asked`로 보고한다.

| host가 실행되는 동안 표준 입출력 sidecar process가 끝난다 | `error host sidecar <name>: failed: output closed: <exit status>` |
| webview에서 합성 pointer 입력이 끝나지 않는다 | 기다림을 끝낸 이벤트(`WebKit handled the mouse events without the receipt`, `the application received another press or key event`, `the window closed`, `the web process stopped answering`)를 담은 `error native webview input: wait for <type> ended: <event>`, `send of <type> was refused`, `_setIgnoresMouseMoveEvents: is unavailable`, `_doAfterProcessingAllPendingMouseEvents: is unavailable`, `receipt message ignored: <reason>`; 기다림이 receipt 없이 끝나면 `error native webview input: the receipt listener of the document at the end of the wait for <type>: <present, absent 또는 not answered: <reason>>`, 그 뒤에 온 receipt 는 `error native webview input: receipt of <type> arrived <ms> ms after its wait ended`; 받지 못한 press 나 release 는 `error native input inject: <JSON>` 으로 남는다. | host가 시작할 때 설치 상태를 읽을 수 없다: `installed.json`이나 사용 중인 plugin의 `plugin.json`이 없거나 parse되지 않거나 이전 형식이다 | `error host installed plugins: <error>`. host는 sidecar를 선언하지 않고 시작하며, `/installed-plugins.json`이 page가 보여 주는 오류를 담는다([사이드카](sidecars.ko.md#선언과-시작)) |
| image region event의 `cids`가 식별자 목록이 아니거나 `type`이 없어 host가 그 중계를 기록하지 못한다 | `error host input relay: <reason>` |
| 딥링크가 거부된다: URL을 해석할 수 없거나 [딥링크](native-host.ko.md#딥링크) 형식에 맞지 않거나, 열린 창이 없거나, 가리키는 command가 실패한다 | `error host deep link: <url>: <reason>`, URL마다 한 번 |
| Tauri host가 딥링크의 실행 URL을 읽지 못한다 | `error host deep link: launch URL: <reason>` |
| mygo 창에 놓인 경로가 더 이상 파일을 가리키지 않는다([native surface](native-surfaces.ko.md)) | `error host file drop: <reason>` |
| Tauri host가 logs 폴더 저장의 진행이나 끝을 요청한 창에 전달할 수 없다 | `error host debug save: debug-save-progress: <reason>` 또는 `error host debug save: debug-save-done: <reason>` |
| 호스트의 시작 단계가 실패한다 | `error host startup: <reason>`, 그리고 프로세스가 상태 1로 끝난다 |

호출자가 받아 오류 표시로 보이는 실패는 그 표시가 기록한다. endpoint 요청은 실패를 client에 답하고, `sok` 명령은 상태와 메시지를 표준 오류로 끝내며, plugin은 host가 문서의 `failure`로 알린 document region의 탐색 실패를 `tab.error`([plugins](plugins.md))로 보이고 그 표시가 `error workbench tab error <tab id>: <text>`를 쓴다.

## 읽기

application log는 무엇이 어디서 실패했는지, performance trace는 언제 어떤 순서였는지, state file은 한 시점에 애플리케이션이 무엇을 가졌는지를 답한다. 결함 보고는 `logs/`의 파일과 결함의 시각을 밝힌다.

진단 diagnostics.fixture의 선택 debugEntries는 {path,size,modified}의 순서 있는 목록 renderer 입력이다. Path는 logs/ 아래의 유일한 이식 가능한 상대경로이며 size와 modified는 음수가 아닌 안전한 정수다. 잘못된 입력은 project/settings 변경 전에 거부한다. 기존 debug model과 목록 renderer가 같은 입력을 사용하고 실제 record·file read/save·logs는 바꾸지 않는다. 다음 fixture가 필드를 생략하면 실제 host provider로 복원하고 reload는 미설정 provider로 시작한다. 비교하는 모든 host에 같은 목록을 주고 공개 core.debug.entries로 일치를 검증해야 하며 별도 layout 구현이나 acceptance 정규화가 아니다.
