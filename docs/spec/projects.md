# Projects, settings, and windows

[한국어](projects.ko.md)

The independent window declaration, placement, association and rail-border contract is [external window sidebars](external-sidebars.md). The internal card-side contract remains independent.

This specification defines the application project registry, persistent settings, and project windows. [Features](../features.md) records implementation and validation separately.

## Project identity

A project represents one existing directory. Native hosts expand the current user's `~`, resolve an absolute path and symbolic links, require a directory, and report its filesystem identity: on macOS `<volume UUID>:<inode>`, the UUID that the volume stores (`getattrlist` with `ATTR_VOL_UUID`) and the inode number, which stay the same across boots and remounts, because the device number of a volume is renumbered at each boot; on Windows the volume serial number and the file index. The reader of `projects.json` refuses a record whose identity is not of the form of the platform (on macOS `<volume UUID>:<inode>`: a UUID of 36 characters in the uppercase 8-4-4-4-12 hexadecimal form, a colon and a decimal inode) with the error `projects.json: project <root> has the identity <identity>, not <volume UUID>:<inode>`, and the stored identity of the earlier form `<device>:<inode>` is not converted. The project registry rejects duplicate identities and duplicate canonical paths. Opening the same directory again selects its existing project and window; it does not create another project. Project names are editable and do not determine identity.

## Project home

Application startup and the New Window action show the project home in an ordinary application window with no selected project. Creating or opening the first project replaces the home with its workspace in that same OS window. The project home is a screen, not a separate window type or a placeholder project. Reloading an existing workspace retains that window's selected project. A missing directory produces a visible error without deleting its saved project data; project selection remains available.

The project home is a launcher: one screen with no tabs and no plugin entry. Plugins are managed on the settings tab ([settings](settings.md#plugins)). The home shows these elements from top to bottom. Each element that acts names its declared command.

## Project opening

Opening a project has a native ownership step and a page data step. `projectOpen` records ownership, returns `{local, staged}`, and leaves the committed shown project unchanged without sending a project message. `staged` is true when this call reserved ownership that has not yet been committed by `projectShown`; a repeated open of an already committed owner returns false. Geometry is applied before a new owner reservation; if geometry fails, a new separate window is closed and a reused window restores its previous geometry. After a local open succeeds, the main page prepares the declared project-data context and selects the project's settings scope, then installs the context and calls `projectShown({id, root, title})`: the host commits the shown project. A native open failure leaves the previous data context and committed shown project unchanged. If settings selection or native validation fails before commit, the page restores its previous settings and data context and releases only the staged owner. Each plugin data call captures the context active when the call begins: calls that started before context installation keep the previous project's access functions, and later calls use the prepared context. A request owned by another window is published only by that owner after it handles `project-activate` and prepares its own data context. At startup, the page completes this sequence before `windowReady`. The first DOM layout may draw from the start-document snapshot before this sequence completes, but native views and background sidecar sessions do not start until the page commits its shown-project context and installs the corresponding layout. The startup gate opens after the synchronous layout load, before waiting for native presentation, so the project transition can wait for surface composition. If the initial project cannot be activated, the page clears its preview to the project home before opening the gate; if initialization itself fails, startup waiters reject and later background-session updates remain stopped. A start document without a project has no gate. These rules keep the first visual layout available while ensuring each first native or background session receives the committed project root.

When the project is owned by another window, `projectOpen` sends that window `project-activate` and orders it in front of the other windows of the application as the key window, without activating the application. A request from inside the application finds the application already active; a request through the endpoint or the command line does not take the keyboard from the application that the person uses, and the result does not depend on whether the system grants an activation.

Project activation and project home clearing share one serialized transition lane, including a clear caused by removal of the active project from the registry. A later activation waits until that clear finishes before loading its layout.

A terminal or shell surface opened in a project starts in the project's canonical root unless it was split from a surface that reported a directory ([tab reports](plugins.md#tab-reports)).

## Shared appearance

The project home and project workspace use the same typography, color, border, corner, and spacing definitions in `app.css`. `library.css` defines the project home layout and its component placement. It does not define a separate type scale or fixed theme colors and corner radii.

The configured font family and base size apply to both screens. At the default 13px base size, project names and controls use 12px, secondary content uses 11px, and metadata and status text use 10px. These sizes scale with the base size. Body and control text use the same line height and normal letter spacing; section captions share one letter-spacing value. Screen headings use the base size rather than a separate large display style.

Project home controls, forms, rows, and the key hint line use the workspace's compact spacing and theme-derived borders and corners. Changing font, size, theme, or corner settings applies the same definitions in both screens.

## Settings

The project home applies defaults and common settings only. A project workspace additionally applies its project’s explicit overrides. The selected settings project determines effective values, default write targets, and available scopes. The project home clears this selection while preserving the window’s projects and their saved overrides. Workspace selection restores the settings project.

Every settings page provides a scope segment, Global and the project name, above its controls ([page head](settings.md#page-head)). The settings menu lists the pages and the plugins and has no scope. Each project window has one settings tab ([opening and closing](settings.md#opening-and-closing)); its scope is the project of its window. The project home has no project scope and provides only Global; Global and the project scope are available in a project workspace. Returning to the project home resets the editing scope to Global without changing the project’s saved overrides. Selecting another category preserves the chosen scope for its controls. A project value can be removed to resume inheriting the common value. Changing a common value updates every open project that has no override for that value.

Project opening mode is common-only: `tabs` opens projects in the current window, and `windows` opens another project in a separate top-level OS window when the current window already owns a project. An unassigned window always opens its first project in place. Project-folder settings cannot override this mode; `core.settings.change` with this key in the project scope fails with -32602 (invalid params) and changes nothing. Existing project windows are reused when their project is selected; changing the opening policy applies to subsequent project opens and does not close running windows or shells.

Project windows are independent OS windows. The settings tab and the add and split menus remain in-window native webviews governed by [native modals](native-modals.md). Each project window owns its active project, surfaces, modal, theme, input state, and shell subscriptions. One window's layout preparation, reload, settings, or closure must not alter another window's native state.

Removing a project from the registry, by its project tab's × or by the project home's remove button (`core.home.remove`) in any window, ends that project in the window that shows it, the same way in each case. A window that shows the project in its plane asks for each modified tab before the removal ([plugins](plugins.md#tab-reports)). A window that removes a project that another window shows asks that window through the host (`windows.askRemoveProject`): the window that shows the project asks for each modified tab and answers, the removal waits for the answer, and a kept tab keeps the project in the registry and answers `closed: false`. The removal ends by the answer of that window or by the end of its page: a window that closes while it is asked, and a window whose page ends while it is asked, because its WebContent process ended or its next page started, answers that the removal is allowed in the turn of that end, because the ended page keeps no tab and the new page never received the request. That window reads the removal from the registry change notification. It disposes the surface modules of the project's tabs, then ends their sidecar sessions ([persistent services](persistent-services.md#closing-and-recovery)), and opens its first remaining project. A window that shows no other project shows the project home in the same OS window and stays open as a window without a project: `host.windows` reports it with `project` null, and `core.projects` no longer lists the removed project. Closing a window's last project tab has the same result. A close request of a window runs after the registry reads that the window started before the request, so a window that answered for the tabs of a project that another window then removed ends that project before the close asks for modified tabs, and its tabs are not asked about again.

## Persistence

The application persists the ordered project registry, common settings, folder overrides, spaces, active space, card and tab state, the session history of document regions (`tab-sessions/`), focused card (`focusedId`, `null` while no card is focused ([focus of group cards](groups.md#focus)); a stored `focusedId` that names no card of the layout opens with no focused card, as `null` does, because the workbench chooses no card for the ring; the value `null` widens the values of the member, every earlier file stays valid, so it is no format change and raises no format number), sidebar and card sidebar widths (including hidden sidebars), the selected tab and folded sections of each sidebar, and project window size and position. Window ownership and live shell processes are runtime state. Closing a project window preserves its saved project and screen settings. The host answers every write of the registry with `workspace-changed` to all windows, also to the writing window, and a window reads the registry again. A read that finds the same projects and the same open project ids draws nothing.

Native hosts load common settings from `settings.json` in the application configuration directory and project overrides from `.soksak/settings.json` inside the project directory. Missing settings files contain no overrides. The project file contains only explicit overrides; removing a key resumes inheritance. The common-only keys `projectOpening`, `textSize`, `memorySaver` and `memorySaverDelay`, one list in the settings of `packages/workbench/workbench.json` that each language host library reads from its embedded copy ([settings](settings.md#values)), are not accepted in project settings: a project settings file with one of them is refused with `<path>: <key> is common-only`, and a project write fails with `<key> is common-only`. A project settings file that is refused, because it has a common-only key, another form or does not parse, is reported at its project: the snapshot gives that project `settingsError` with the error and no `settings`, and the other projects keep their settings. The window does not open such a project, because no settings take the place of the refused file: opening it fails with that error before the window, the plane or the stored records change, and a start document that names it draws the project home and reports the error once. When the settings file of the shown project becomes refused, the next snapshot reports the error and the applied settings stay. A refused `projects.json` or `settings.json` of the configuration directory does not fail the snapshot: a refused `projects.json` gives `projectsError` with the error and no project, a refused `settings.json` gives `settingsError` with the error and no common setting, and the page shows each error and starts. Adding, changing, moving or removing a project then fails with the error of `projects.json`, and a common settings write fails with the error of `settings.json`; neither file changes. The frame text factor is common-only because the host sets a window's title bar from it before the page starts ([title bar height](native-surfaces.md#title-bar-height)).

The default configuration directories are:

| Tauri | `~/Library/Application Support/app.soksak.tauri` | `%AppData%/app.soksak.tauri` | `$XDG_CONFIG_HOME/app.soksak.tauri`, or `~/.config/app.soksak.tauri` when unset |
| mygo | `~/Library/Application Support/app.soksak.mygo` | `%AppData%/app.soksak.mygo` | `$XDG_CONFIG_HOME/app.soksak.mygo`, or `~/.config/app.soksak.mygo` when unset |

The directory name is the application identifier. Builds with the `dev` flag (the Go tag and the Cargo feature `dev`), which the debug targets make, append `.dev` (`app.soksak.wails.dev`, `app.soksak.tauri.dev`, `app.soksak.mygo.dev`), so a development build never reads or writes the data of a release application; a diagnostic release, which is built without `dev`, keeps the release identifier. The command-line package of each language holds the identifier (`src/identity.go` of `packages/sok/go` by the application name of each Go host, `src/identity.rs` of `packages/sok/rust`). A Go host takes the identifier of the application name of its framework adapter, so a build tag does not choose the folder of a host; the build tag `mygo` names only the host of the `sok` command (`src/wailsv3.go` and `src/mygo.go`).

`--config-dir PATH` selects another application configuration directory. The host rejects an empty path, creates missing directories of the path with mode 0700 (owner only), keeps the mode of an existing directory, and uses the canonical path. Project override paths remain inside their projects. Global edits update the common settings file; Project edits update the selected project's settings file. **Use global value** removes an individual override. Project tabs can be reordered by dragging. The project home does not use that order. A tab's × removes the project from the registry and preserves its folder and settings file. The OS window's close button preserves the project in the registry.

The application configuration directory also contains `projects.json`, which stores the ordered registry, project screen state, and each project's plugin data under `plugins` ([project data](plugins.md#project-data)); the file carries its form in the member `format` beside the `projects` member (format 4 is the current form, whose tabs each hold the member `role` of [agent roles](agent-roles.md#tab-role-state), and whose space layouts hold the slicing tree of the grid with the group cards as its boxes and the leader of each level); a file of another form, including formats 1 to 3 and a bare array of projects, is refused, [stored data formats](installation.md#stored-data-formats)). Wails and Tauri use their own application configuration directories. Native hosts serialize changes, reread the affected file before updating it, write a temporary file in the same directory, and replace the destination after the write completes. Open windows receive a change notification after successful replacement. Settings files are reread on reload and project selection. A storage failure is reported visibly; it does not reset or silently overwrite saved data with defaults. Closing a ready project window completes pending saves before closing its native resources. A main-page reload asks a ready page to complete its pending saves (`core.projects.flush`) before it replaces the page. Application quit requests the same save from each ready window before termination.

A write of the layout or of the settings that the host refuses fails the call that made it. The next write is still delivered to the host, and the next save of a refused layout writes it again.

The application configuration directory also contains `tab-state.json`, the tab state store of the [memory saver](plugins.md#memory-saver), format 1 in the member `format`. It holds in the member `tabs`, per tab identifier and per [section surface](plugins.md#sections) id of the layout, an entry with three optional fields: `state: {format, value}`, the state that the tab's plugin wrote through `context.tab.state`; `kept: true`, the person's mark of `core.tab.keep`; and `label`, the last title that the surface reported, written only for a tab whose plugin declares `surface.unload` as `{format, maxBytes}`, whatever the setting, and removed by a `null` title report. An entry is stored only while one of the fields is present, and a tab without an entry reads `null`. The label is a display cache for a tab that is not mounted: the surface stays the owner of its title, the layout `title` stays the tab's name, and the first title report after a restore replaces the cache. Footer and directory are not stored, and whether a tab is unloaded is not stored. Writes of one tab are coalesced to at most one per second and flushed at quit, so a crash loses at most the last second of state, and each write is the event `workbench.tab.state.stored`. An entry is removed only after the layout write that drops its tab is confirmed. At load the store is reconciled with the tab identifiers of `projects.json`, and each orphan entry it removes is an event. An entry of a section surface `<space>/<sidebar>/<section>` is kept while its space is a space of `projects.json` and its sidebar is a window sidebar (`left`, `right`) or a sidebar `<card>:<side>` of a card of the layout of that space, because a load does not resolve the sets of the sidebars. A reader accepts only format 1 and refuses another with an error that names the file and the format found. Tab state is not stored in `projects.json`, whose format does not change: a separate store keeps the frequent state writes away from the whole layout file, and plugin `data` is keyed per project and declared key, not per tab.

The application configuration directory also contains the folder `tab-sessions/`, the tab sessions of the [memory saver](plugins.md#memory-saver): one file `<name>.json` per tab identifier or section surface id; the document regions of a [dialog surface](plugins.md#dialogs) keep no session, because the dialog ends with its close and no layout opens it again, so the workbench neither reads nor writes a session of a dialog id; where `<name>` is the percent-encoding of the identifier by RFC 3986, which keeps the unreserved characters, so the name of a tab identifier is the identifier itself and a section surface id `spc-2wcnnb/left/files.tree` has the file `spc-2wcnnb%2Fleft%2Ffiles.tree.json`; the host refuses an identifier that is neither a tab identifier nor a section surface id, and the listing of the sessions refuses a file `<name>.json` of the folder that names neither, with an error that names the file, `{format: 1, regions: {<region name>: {session}}}`, where `session` is the base64 serialized session history (`interactionState`) of the document region of that name, at most 1 MiB decoded. Each tab has its own file, so a write replaces only that file by the atomic replace of the other files and never rewrites `tab-state.json`, whose whole document each put rewrites. A file is removed on the paths that remove the entry of its tab from `tab-state.json`: after the layout write that drops its tab is confirmed, and by the reconciliation at load, which removes the file of each tab that no layout of `projects.json` holds with the event `workbench.tab.session.orphan`; it keeps the file of a section surface by the rule of the tab state store. A reader accepts only format 1 and refuses another with an error that names the file and the format found.

Opening a space validates its content tabs, active tab, fixed sidebar IDs and `{width}` and `{height}` records ([external window sidebars](external-sidebars.md#fixed-placement-and-persistence)) before replacing the displayed layout. The stored layout is read only in its current form: a layout that holds `edgeWidth` or `railWidth`, a card whose data holds `panels` or `sidebar`, or a sidebar choice stored under a content card's ID fails with an error that names `projects.json`, the project root, the space and what it found, and it is not converted. Tabs of plugins that are not loaded open as placeholder cards ([plugins](plugins.md#plugins-that-are-not-loaded)). A content card holds zero or more tabs: a card without tabs is an empty card and stores `activeId` `null`, a card with tabs stores the id of one of them, and any other `activeId` fails with `invalid stored active tab <card>`. Persistent owner fields, plugin-specific sidebar IDs and obsolete rail cards fail explicitly with their reason, which the project home shows on the project’s row. Stored sidebar settings fail on unregistered sections or invalid links ([stored sets and links](settings.md#stored-sets-and-links)). The project home applies the same validation to the active space of each project; a project whose saved layout fails shows that error on its row in place of its path and reports it in `core.home` `previewErrors`. Explicit null width or section-choice records are invalid; only an absent optional field has the declared empty-record default. A refused view origin is refused per tab, not per space: the tab stays in the layout, is shown as refused, and opening and saving the space still succeed ([tab origin](#tab-origin)).

A space's layout stores `sidebars`: for each sidebar id (`left`, `right`, or `cardId:side` for an internal card sidebar) `{tab, folded, sizes}`, the selected section id of a `tabs` set or `null`, the folded section ids of a `list` set, and `sizes`, an object from a section id to the height that the person dragged it to, an integer from 32 to 4096, which the layout omits when no section of the sidebar is sized ([sections](plugins.md#sections)). A `sizes` value of another form is refused with `sidebar <sidebar> stores an invalid size of <section>: <value>`. Keep choices per space. An override changes the content of the same fixed sidebar, not its identity. A choice changes the saved space like any other layout change. A layout without `sidebars` has no stored choice; retained section choices apply only when that section is in the selected set.

A space's layout stores `lastCard`, the largest card number that the space issued, `leader`, the leader of its root level, and `groups`, the group tree beside the grid, each group card as a node `{card, name, leader, members}`, in the form and with the refusals of [group storage](groups.md#storage).

The layout cases of `docs/spec/cases/layout` state these forms as values: `stored.json` the check of a stored space layout and the `{width}` and `{height}` records of the fixed sidebars, `window-sidebars.json` the arrangement of the fixed window sidebars in their order, `spaces.json` the spaces, the active space and the space counter of a project record, and `grid.json` and `outline.json` the grid and the outline of `packages/soksak` that a layout stores. The tests of `packages/soksak` and `packages/workbench` and the Go layout model of `packages/workbench-mygo` ([workbench](hosts.md#workbench)) run the same files, so a case is one statement of the stored format that every implementation meets.

### Tab origin

Each content-card tab of the stored layout may carry the optional member `origin`, in its entry of the card's `tabs`: `{id, plugin, origin: {directory}}`. `directory` is an absolute path or null: the directory that the source tab reported when the tab was opened, or null when that tab reported none or there was no source tab (the first tab of a new space, and a tab opened after the last tab of a card closed). The member is written with the layout write that creates the tab, so a tab and its origin persist together. The format stays 1. The member is optional, and no released core has view tabs, so no released file holds the changed shape and the format rule of AGENTS.md does not apply.
An origin ends only when its tab leaves the stored layout of its own space: the previous stored layout of the space held the tab and the next one does not, or the space is closed. The display of another space does not change it, so a tab of a space that is not displayed keeps its origin until that space stores a layout without the tab. A tab that leaves the stored layout while its surface is still mounted keeps its origin until that surface is disposed; the refusal of a missing origin still names the operation that stored the layout that dropped it. A tab that a stored layout holds again before its surface is disposed keeps its origin and is not left.

The layout read restores the origin of each tab once, before the tabs are created. Before a project becomes locally owned, the window restores origins from every stored space, including inactive spaces whose retained views can start without drawing their layout. A view tab (a tab whose plugin declares a view surface, [native surfaces](native-surfaces.md#view-surfaces)) without a valid member is refused per tab: its member is absent, null, not `{directory}`, or its `directory` fails the path check of [native surfaces](native-surfaces.md#view-surfaces). Its refusal text names the tab and is written to the log and shown on the tab; the tab stays in the layout, the view does not start, and opening and saving the space still succeed. A refusal is never thrown. A non-view tab without the member reads its released origin `{directory: null}`, through the one function of the workbench that holds that reading rule (`releasedNonViewOrigin`); this reading is the released rule of format 1 for non-view tabs and is not a fallback for any other tab. A tab with neither a recorded origin nor a loaded one has no origin, and reading it throws. The error names the tab, its plugin, the space and project that the window shows, the path that created the tab, whether this session held it, and the operation whose stored layout last dropped its origin: the writing path of a save with its space and project (`drawn layout` for the save after a render), `recreate` with its space and project, `close space` with the space and project, or `no stored layout` when no stored layout dropped it. Origin is not stored in `tab-state.json` or `tab-sessions/`: their files are removed for plain tabs, so they cannot hold it. Layouts saved before this change have no origin member on their tabs; a view tab of such a layout is refused on open, and it is not converted. A layout saved by this build is not supported on an earlier build, which drops the member on its next save.

A layout write names its writing path: `add space` (a new space of the shown project), `saved layout` (the save of the displayed layout before a space, project or window change), `recreate` (the layout that a window restores at its start), or `library replacement` (a project activated in a window that shows the project home or another project). A write records each view tab that it stores without an origin member as one error record that names the tab, its plugin and the writing path; the record is written to the application log at the write. A layout read names no path and records nothing.

The browser example uses browser windows and IndexedDB storage; it does not write settings into native folders. It cannot establish native filesystem identity from a typed path; directory identity and native window placement require a native host.

## Acceptance

- Equivalent folder paths and symbolic links select one project, including concurrent opens from separate windows.
- Project creation, renaming, removal, order, pins, and last-opened times survive application restart; startup displays the project home without starting projects.
- The project home uses and edits common settings only, including after leaving a workspace with project overrides. Returning to the workspace restores its overrides and provides both editing scopes.
- Common settings and explicit folder overrides survive reload and restart. Resetting an override restores inheritance. The opening mode is absent from project-folder settings.
- Startup and New Window show the project home without native content surfaces or shells. First-project creation/opening reuses that OS window in both opening modes. Selecting another project from an occupied window follows the common opening mode. Reopening an already open project selects its existing window.
- Layout, tabs, sidebar widths, theme settings, and normal window geometry restore for the selected project. Closing a window keeps its saved data.
- A saved space that names unregistered plugins fails to open with the validation error, and its row on the project home shows the same error; the saved record is not changed.
- A project whose folder the host cannot read shows the reason under the folder path of its row on the project home, and `core.home` reports the host's message under `folderErrors`. Both hosts use the messages of [`workspace.folder.messages`](host-contract.md); the row shows the declared ones as a reason without the path (missing folder, no read permission, a file) and any other message as it is; the project home asks the host again each time it is shown and each time the registry changes. The row's open button is disabled, and opening that project by command fails with the host's message. The record stays on the project home until the user removes it with the row's remove button and its 빼기 confirmation (`core.home.confirm`, then `core.home.remove`), which deletes the record and its spaces like closing a project tab and leaves the folder unchanged. The window that shows the removed project ends it as the project window rules in [settings](#settings) define for a removal.
- Two windows can render and receive input independently. Settings effects, native surfaces, shells, and cleanup remain limited to their owning window.
- Existing surface placement, fractional rendering, and modal checks continue to pass in both native hosts. Native behavior on each operating system is recorded separately.
