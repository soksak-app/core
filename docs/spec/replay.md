# Replay

[한국어](replay.ko.md)

A screen-producing sidecar stores the inputs of a session completely and a hash of each screen it produces, and the page stores a hash of each screen it receives. A replay rebuilds the screen of a session from the stored inputs and compares every stored hash with the replayed one. The frame content is not stored ([logging](logging.md#catalog), decision in [observability audit](../plans/observability-audit.md)); until a replay reproduces the screen, the stored hashes verify nothing. This document defines the records, the screen hash, the replay executable and the command. The events themselves are declared by the catalog of the sidecar and of the plugin ([logging](logging.md#catalog)); this repository names neither.

## Records

A *replay input* is an event of the layer `sidecar` that carries `session` (the identifier of the session, the member of the line), `fields.sequence` and the complete input of one occurrence:

| Input | Required fields |
| --- | --- |
| output of the program of the session (bytes read from the pseudo terminal) | `sequence`, `hex` |
| input to the program (bytes written to the pseudo terminal) | `sequence`, `hex` |
| resize | `sequence`, `rows`, `cols` |
| selection | `sequence`, `action` (`start`, `update`, `end` or `clear`); `edge` and `row` for `start` and `update` |
| scroll of the viewport | `sequence`, and `lines` (a non-zero integer) or `newest` (`true`) |
| theme | `sequence`, `colors` |

The selection, the scroll of the viewport and the theme are defined in [View state](#view-state). `hex` is the lowercase hexadecimal text of the complete bytes of the occurrence. An input event has no derived copy of its bytes, such as a text. `sequence` is an integer counted per session from 1, with one step for each replay input of any kind, so the sequences of a session have no gap and the replay applies the inputs in the order of `sequence`. A key input that causes a write also carries `cids` ([logging](logging.md#event)).

A *frame record* is an event of the class `frame` that carries `session`, `fields.sequence`, `fields.rows`, `fields.cols` and `fields.hash`. `sequence` is the sequence of the last replay input that the screen includes; `hash` is the [screen hash](#screen-hash) of the screen after that input. The sidecar writes one frame record, layer `sidecar`, for each screen it produces. The page writes one frame record for each screen message it receives and draws; the plugin of the page writes it through `runtime.log` ([plugin logging](plugins.md#logging)), so it has the layer `plugin`, and the page of core, which draws no screen, writes none. The record carries the `sequence` and `rows` and `cols` of the screen that it received from the sidecar and the hash of the grid it received: the hash is computed from the cells of the message ([View state](#view-state), Page), not copied from a hash that the message carries. The page draws only screens that the sidecar produced, so each page frame record has a sidecar frame record with the same `session` and `sequence`.

## Segments

A session lasts as long as its identifier, and the sidecar that serves it can restart (a new run of the process, with a new `boot`). `sequence` counts the inputs that one run applied, so it restarts at 1 in a new run, with a theme input first ([View state](#view-state)). A *replay segment* (a segment) is the set of the events of the layer `sidecar` that one run produced for a session; its identifier is the `boot` of the event file of that run (`logs/<role>-<boot>.jsonl`). The rules of a session in [Records](#records) (a theme first, a sequence without a gap) hold inside each segment, and the segments are numbered by the time of their first event.

- A frame record of the sidecar belongs to the segment of its event file. A frame record of the page carries `fields.segment`, the `boot` of the segment of the screen that it received from the sidecar (the [screen message](persistent-services.md#screen-message) carries it as `segment` with the sequence). A page frame record without `segment` is an error, because the sequence alone does not say which screen the page drew.
- A replay starts one process of the replay executable for each segment, so each segment is applied to an empty screen with its own count, and compares the stored hashes of a segment with the hashes of that segment only. A segment with no frame record of the sidecar runs nothing, and its page frame records, if any, diverge as a page frame without a sidecar frame record.
- The events of two segments that alternate in time (an event of the first run after an event of the second) are not a restart; the replay refuses them.
- *Memory.* The replay holds the frame records of the session (a sequence, a 64-character hash, a layer and a segment each) and the event lines of one segment at a time. It reads the files twice: the first scan collects the frame records and the segments, the second scan collects the lines of the segment that is being replayed and drops them after the comparison. The greatest number of lines held at once is the number of events of the largest segment, and `ReplayResult` reports it as `held_lines`. The lines of the session are never held together.

## Screen hash

The screen hash is the SHA-256, as 64 lowercase hexadecimal characters, of the canonical bytes of the screen. All integers are unsigned and big endian.

| Part | Bytes |
| --- | --- |
| magic | the 6 ASCII bytes `SKSCR1` |
| `rows` | 4 |
| `cols` | 4 |
| cursor visible | 1 (`1` visible, `0` hidden) |
| cursor row | 4, from 0, less than `rows` |
| cursor column | 4, from 0, less than `cols` |
| cells | `rows` × `cols` cells in row-major order |

Each cell is: the byte length of the grapheme in 4 bytes, the UTF-8 bytes of the grapheme, the width in 1 byte, the foreground in 4 bytes, the background in 4 bytes and the attributes in 1 byte.

- The *grapheme* is the text of the cell: the empty string for a blank cell and for the continuation cell of a wide character, and otherwise one grapheme cluster. It is well-formed Unicode.
- The *width* is `1` for a cell, `2` for the first cell of a wide character, and `0` for its continuation cell.
- A *color* is 4 bytes: the default color is `00 00 00 00`, an indexed color is `01 00 00 <index>` (index 0 to 255), and a true color is `02 <red> <green> <blue>`.
- The *attributes* are one byte of flags: bold `01`, dim `02`, italic `04`, underline `08`, blink `10`, inverse `20`, hidden `40`, strikethrough `80`.

In the JSON form of a screen (`@soksak/plugin-api/screen-hash`, the golden vectors) a screen is `{rows, cols, cursor: {row, col, visible}, cells}`, a cell is `{grapheme, width, fg, bg, attributes}`, a color is `null` (default), an integer from 0 to 255 (indexed) or `"#rrggbb"` in lowercase (true color), and `attributes` is an integer from 0 to 255. The hash function rejects a value outside these forms with an error that names the member. The golden vectors are `packages/log-contract/fixtures/replay/screen-hash.json`: for each screen the canonical bytes in hexadecimal and the hash, and the screens that the function refuses with their error text. Every implementation of the hash, in any language, reproduces them.

## Golden vectors

`packages/log-contract/fixtures/replay/screen-hash.json` holds the vectors of the screen hash. Each vector gives the screen, its canonical bytes in hexadecimal and its hash:

| Vector | What it fixes |
| --- | --- |
| `empty one cell` | the smallest screen: one blank cell, a visible cursor, default colors |
| `ascii with hidden cursor` | graphemes of width 1 and a hidden cursor |
| `wide character and its continuation` | a wide character (width 2) followed by its continuation cell (width 0, empty grapheme) |
| `colors and attributes` | indexed and true colors, every attribute flag |
| `scrolled viewport with the cursor outside it` | a scrolled viewport: the cursor is hidden, its row is `0` and its column is kept ([View state](#view-state)) |
| `selected cells with the highlight colors` | selected cells with the highlight colors in their foreground and background |
| `the same text under another theme` | the same graphemes as the selected screen under other colors, which gives another hash |

The same file lists the screens that the hash function refuses, each with its error text: `cell count differs from rows times cols`, `cursor row outside the grid`, `width outside 0, 1, 2`, `indexed color outside 0 to 255`, `true color in upper case`, `attributes outside one byte` and `grapheme with a lone surrogate`.

`packages/log-contract/fixtures/replay/inputs.json` holds the cases of the replay inputs: the inputs that `replayInputProblem` accepts, the inputs it refuses with their text, and the sessions that `replaySessionProblem` judges: `a session with a scroll and a selection`, `a session that does not start with a theme`, `a session with a gap in the sequence`, `a selection update before a selection start`, `a selection start before any resize`, `a selection start below the grid`, `a selection update after the grid shrank`, `a selection update after the gesture ended`, `a theme change in the middle of a session` and `viewport moves stored as the effective change`.

## View state

A screen that a sidecar produces is the screen as it is drawn: the cells of the viewport, with the selected cells in their highlight colors and every color resolved through the theme. Three states of that screen do not come from the output bytes or the resizes: the *selection*, the *viewport* (the offset into the scrollback) and the *theme*. Each change of one of them is a replay input of its own, so the hash definition above does not change and a replay reaches the drawn cells by applying the inputs.

- **Selection.** `action` is `start`, `update`, `end` or `clear`. `start` and `update` carry `edge` (the cell boundary, from 0 to the number of columns of the grid at that moment) and `row` (the row of the viewport, from 0 to the rows minus one), as the sidecar resolved them from the pointer at the moment it applied them; a replay has no pixel metrics. `end` finishes the gesture, and an `update` after it is refused. `end` and `clear` carry neither. The sidecar stores only a call that took effect: an update outside the grid or without a start is an error of the sidecar, not an input. Whether output, a resize or a switch of the alternate screen keeps, moves or removes the selection, and the removal of an empty selection at `end`, are behavior of the engine that the replay executable reproduces; they are not inputs. A hyperlink of a cell is not part of the hash, so a divergence of a link is not detected.
- **Viewport.** `lines` is a non-zero integer, positive toward older lines: the change of the offset into the scrollback after it was limited to the lines the engine retains. `newest` is `true` for a move to the newest output. The sidecar stores the move that it applied, whatever caused it: a wheel, a key that scrolls to the newest output, a request of the page. A move that changed nothing is not stored. Storing one input for several wheel events is allowed only when it holds their effective sum. Output does not produce a viewport input: the offset change that follows from output, and the removal of lines at the limit of the scrollback, are behavior of the engine that the replay executable reproduces. While the alternate screen is active no viewport input is stored, because it has no scrollback.
- **Theme.** `colors` is the complete set of colors that the sidecar resolves through its theme, an object of `#rrggbb` values in lowercase with at least `foreground`, `background` and `selection`; the cursor color and each entry of the palette (`ansi0` to `ansi255`) are further members, and the sidecar states every entry it resolves a color with, so a custom palette replays. It is the complete set and not the name of a theme, because a theme that the person defined has no name that a replay can look up. The first input of every session, `sequence` 1, is a theme; each change of the theme is another. A theme input replaces the theme only: colors that the program set with its own output sequences stay in the engine and take the precedence that the engine gives them. The blank cells that the engine trims at the end of a row depend on the theme, and the hash covers the padded grid, so the theme enters the hash through the trimming as well.
- **Order.** The sidecar assigns `sequence` in the order in which it applied the inputs to the engine, not in the order in which it received them, under one lock for all kinds.
- **Cursor.** The cursor of the hash is the cursor of the viewport: `visible` is the visibility that the program set, and `false` when the cursor row is outside the viewport (then `row` is `0` and `col` is the column of the cursor). The blink phase, the focus and the preedit of the input method are not part of the hash.
- **Page.** The screen message that a sidecar sends to a page ([persistent services](persistent-services.md#screen-message)) carries the cells that the hash covers (grapheme, width, resolved colors and the attributes), the cursor and the `sequence` of the frame record, with the highlight of the selection already in the cells. The page hash is the hash of the grid that the page *received*: the page computes it from the message with `screenFromMessage` and `screenHash` and stores it with the `sequence` of the message. A difference from the hash of the sidecar for the same `sequence` therefore finds a loss or a change in the relay of the host and the page (a cell, a color, an attribute, the cursor or the size that changed or was dropped on the way, or a message that the page refuses). The raster itself stays outside what the comparison covers: the sidecar draws the pixels, and a defect of the raster (a wrong glyph, a wrong position of a correct cell) leaves both hashes equal and is not detected.
- **Engine.** The scrollback limit and the default theme before the first theme input belong to the replay executable of the sidecar, which is also the engine that produced the session. A replay is defined against the sidecar version that stored the session; a session of another version may diverge and the divergence is reported as such.
- **Classes.** These inputs are stored with the class `input`, which stores them complete. A policy that does not store the classes `io` and `input` leaves a gap in the sequence, and the replay refuses the session at the first missing `sequence`; so does a `log.dropped` that covers inputs of the session, with the dropped count in the error. The wheel and the pointer moves of the class `frame` in [logging](logging.md#classes-and-policy) are the events of the page before the sidecar applies them; the inputs that the sidecar stores for the applied change are of the class `input`. A replay executable refuses an event of the session with a `sequence` whose kind it does not know; it never ignores one. The replay command runs `replaySessionProblem` on the inputs of the session before it starts the executable.

`replayInputProblem(kind, fields)` and `replaySessionProblem(inputs)` of `@soksak/log-contract` check these forms and the rules of a session (a theme first, a sequence without a gap, an update or an end only after a start), and `packages/log-contract/fixtures/replay/inputs.json` holds the golden cases for the sidecars.

### Decision

Three candidates were examined for how the selection, the viewport and the theme enter the hash: replay inputs with defined events (chosen), exclusion from the hash, and state fields in the frame record.

- *Exclusion.* The hash would cover a live-bottom screen without highlight and with theme-independent colors. Objections: it verifies a screen that nobody sees and no loss or change of the highlight, the scrollback or the colors in the relay to the page can diverge; the colors are already resolved through the theme in the cells that the engine produces, and the trimming of blank cells depends on the theme, so no theme-independent form exists without a new unresolved color path; a second screen at the live bottom doubles the work of every frame while the view is scrolled; the page receives the scrolled screen and cannot remove an offset or a highlight that is in the cells, so it could not hash the live-bottom screen; the closing condition (a replay of a session with a scroll and a selection equals the drawn hashes) would be true by construction. No solution inside the candidate answers these, so it is rejected.
- *State in the frame record.* The replay would set the offset, the selection and the theme from the frame record that it verifies. Objections: the check is circular for exactly these states (a wrong offset or a never cleared selection is recorded and replayed as it is); a complete theme with its palette in each frame record is more than two kilobytes at the frame rate in the class `frame`, which aggregates, and a theme identity does not replay a theme that the person defined; the engine has no setter for an absolute offset or a selection extent, so the replay would need a path that production never runs; the extent of a selection is not stated for every kind of selection. The answers (the state as inputs at their cause) are the chosen candidate, so it is rejected.
- *Inputs (chosen).* The objections and their answers, all in the rules above: the theme and the scrollback limit that the engine starts from (the first input is a theme; the limit belongs to the replay executable and the replay is defined against the sidecar version); the selection geometry that depends on pixel metrics (the inputs store the resolved cell boundary and the viewport row, in the order of application); the reactions of the sidecar to an input, such as the scroll to the newest output on a key (a viewport input at the moment of the call, so the replay needs no rule about keys); the order against the output (one `sequence` in the order of application); the rate of the wheel and the pointer (class `input`, complete, one input for each applied wheel event or pointer move, or one input for their effective sum); the cursor that depends on the viewport, the blink and the focus (the cursor rule above); the class policy that can switch `input` off (the replay refuses the session at the first missing `sequence`, which is the gap rule); the screen that the page cannot rebuild (the screen message carries the hashed cells); the replay executable that ignored unknown events (it refuses them). The review repeated until no objection remained.

The golden vectors that fix the drawn screen under a scroll, a selection and another theme are `scrolled viewport with the cursor outside it`, `selected cells with the highlight colors` and `the same text under another theme`.

## Replay executable

A sidecar that produces screens declares `replay` in its `sidecar.json` ([sidecars](sidecars.md#declaration-and-startup)): `{"role": <role>, "executable": <path inside the sidecar>}`. `role` is the role of the event files of the sidecar (`logs/<role>-<boot>.jsonl`), which `log.open` of its files states. The executable is the replay engine of the sidecar: it holds the terminal engine, so the command line tool names none.

The tool starts the executable in the folder of the sidecar without arguments, once for each [segment](#segments), and writes to its standard input the lines of the layer `sidecar` events of the segment from the files of the role, in the order of the [query](logging.md#query) (time, process, `seq`), unchanged, each ending with a newline, up to the `sequence` that `--until` gives. The executable applies the replay inputs in the order of `sequence` to an empty screen and, for each frame record it reads, writes to its standard output one line `{"sequence": <n>, "hash": <hash>}` with the hash of its screen at that sequence. It ends with exit status 0 when its input ends; any other exit status, a line that is not that object, a hash that is not 64 lowercase hexadecimal characters, or a frame record that gets no line is a failure of the replay, reported with the error text of the executable.

## Command

`sok debug replay <session> [--until <sequence>] [--config-dir <directory>]` ([command line](cli.md#commands)) reads the events of the session from the event files of the configuration directory through the [query](logging.md#query), finds the installed sidecar whose `replay.role` is the role of the sidecar events of the session, runs its replay executable for each [segment](#segments), and compares, segment by segment in their order and inside a segment in the order of `sequence`, the sidecar record before the page record of the same sequence:

Before it starts the executable of a segment, the tool checks the replay inputs of the segment, the events that `replay.inputs` of the sidecar names, with the rules of `replaySessionProblem` (each input in its form, the sequences from 1 without a gap, a theme first, a selection start or update inside the grid of the last resize, a selection update or end after a start) and refuses a segment that breaks one, without a divergence, with `sok: replay session <session>: segment <boot>: <problem>` in the text of `replaySessionProblem`; `--until` bounds the inputs it checks. The cases of `packages/log-contract/fixtures/replay/inputs.json` fix the texts for both tools.

1. each sidecar frame record with the replayed hash of its sequence: a difference is a divergence of the layer `sidecar`;
2. each page frame record with the replayed hash of its sequence: a difference, or a page frame record without a sidecar frame record at its sequence, is a divergence of the layer `plugin`.

The first divergence ends the comparison. The tool stores the event `sok.replay.divergence` (level `error`) with `session`, `segment` (the `boot` of the segment), `sequence`, `layer`, `expected` (the replayed hash, or `none` for a page frame without a sidecar frame record) and `found` (the stored hash), writes `sok: replay divergence: session <session> segment <boot> sequence <n> layer <layer> expected <expected> found <found>` to its standard error and ends with exit status 1. When every hash is equal, it writes `replay session <session>: <n> sidecar frames and <m> page frames equal in <k> segments` to its standard output and ends with status 0. A session without events of the layer `sidecar`, without a frame record, with sidecar events of more than one role, or with no installed sidecar that declares the role is an error that names the session and the role. A page frame record whose `fields.segment` is not text or names a boot that the session does not have, a page frame record without `fields.segment` in a session with several segments, sidecar events of two segments that alternate in time, a frame record without an integer `fields.sequence` from 1 and a string `fields.hash`, a stored hash that is not 64 lowercase hexadecimal characters, an executable that fails or prints a line that is not `{"sequence", "hash"}`, and a frame record of the sidecar for which the executable prints no hash are errors, not divergences. The tool holds the event lines of one segment in memory ([Memory](#segments)). Both tools give the same output and the same error text.
