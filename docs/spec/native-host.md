# Native host interfaces

[한국어](native-host.ko.md)

The workbench page uses the interfaces exported by [host.js](../../packages/workbench/host.js). The application's runtime module (`@soksak/runtime`, see [plugins](plugins.md#runtime-module)) supplies runtime calls, events, and document URLs. In a plain browser, `native` is false, `chrome` is null, and native drawing operations do nothing.

| Interface | Operations | Responsibility |
| --- | --- | --- |
| `surfaces` | `kinds`, `report`, `theme`, `place` | Native surface creation, preparation, presentation, visibility, and dimming |
| `shapes` | `set`, `clear` | Native outlines above surfaces |
| `chrome` | `draggable`, `controls` | Main-window dragging and actual native button geometry |
| `overlay` | `show`, `place`, `update`, `hide` | The marked DOM element in a native webview |

`surfaces.place(record)` returns the host's placement promise. An undrawn record requests `syncSurfaces`; a drawn record also requests `presentSurfaces`. The page waits for presentation before preparing the latest pending layout. Each preparation carries the title bar height `titlebar` and returns one `ticket`, a `placements` array for the complete layout, and the window's `chrome` after the host set the title bar ([title bar height](native-surfaces.md#title-bar-height)). Tickets are local to the owning window. The host checks the whole `syncSurfaces` request before it begins the layout transaction and fails it without a change to the window when a surface id is empty or repeated, a surface rectangle or window overlay rectangle contains a non-finite number (`surface "<id>" geometry must contain finite numbers`, `window overlay geometry must contain finite numbers`) or has a negative size (`surface "<id>" geometry must not have a negative size`, `window overlay geometry must not have a negative size`), a composition declaration is invalid or differs from the one the surface declared before, or `titlebar` is not a number from 32 through 200 points (`title bar height must be a finite number from 32 through 200 points`). The [surface specification](native-surfaces.md) defines placement and presentation. Each step of a presentation has its own limit and error: the host fails `syncSurfaces` and `presentSurfaces` when the application documents or the image raster do not present within 10 seconds. A failed layout is reported as the page error and does not stop the next layout.

`onSurfaceInput({press, input})` receives a surface press and drag phases in main-page coordinates. An overlay's `(key, value)` response reaches the callback registered by its owner. [Native modals](native-modals.md) defines required attributes, frame coordinates, and content updates.

## Project and settings operations

`projects.js`, `library.js`, and `storage.js` use the runtime bridge for `projectFolder`, `projectCreate`, `folderChoose`, `projectOpen`, `projectRelease`, `windowNew`, `windowState`, `windowReady`, `windowClose`, `windowCloseKept`, `appUpdateState`, `appUpdateStage`, `projectRemoveAsk`, `projectRemoveAnswer`, and `workspace`. The main page starts with its [start document](#page-start). Navigation callbacks of the main webview perform none of the page-start work, because their delivery order relative to requests from the replacement page is not guaranteed; they only refresh the WebKit child-process record. `folderChoose` uses the host’s public directory dialog API; cancellation returns no path. `projectCreate` creates a new directory and returns its canonical identity. `windowNew` creates an unassigned application window. Workspace snapshots include the project IDs owned by open windows. The [project specification](projects.md) defines their file storage and window behavior. Wails selects native state from the calling window supplied by the framework's service context. Tauri selects it from the command's window. Events, surfaces, overlays, input monitors, and sidecar surface registrations belong to that window. Surface and modal labels are unique across windows. When a window closes, the host removes its input monitors, closes the document regions and image regions of each surface and then the surface, and reports its surfaces to the [sidecars](sidecars.md) as closed. A surface holds the main webview, and a document region has its own web content process, so a surface or region left open would keep those webviews and their web content processes after the window closes. A webview's native input registration ends when the webview is released.

## Application addresses

An application document inside a webview has the address `sok://<owner>/<path>`. The owner `core` names a document of core, and a plugin id names a file of that plugin ([document regions](native-surfaces.md#document-regions)). The `soksak` scheme is for deep links that open from outside the application and is not an address of a document inside a webview.

## Page start

A window's main page starts from a start document `{ workspace, controls }` that the host builds for that window when the page requests it. `workspace` is the snapshot that the `workspace` call returns for `snapshot`, and `controls` is the window's `windowControls` answer: the native button rectangle and the title-bar row. The row is 0 while the window shows no title bar, as in full screen; a window without standard buttons or a content view cannot have a title bar, and `windowControls` fails for it. Answering the request starts the page: before the host sends the document, it marks the window not ready, ends the requests sent to the previous page, cancels the window's open layout, closes the previous page's surface documents and images, announces those surfaces closed, and discards the open modal; it then sets the window's title bar to the first-row height of the stored frame factor, inside a start transaction that commits with the new page's first presentation when the window shows a previous page, and reads `controls` after that ([title bar height](native-surfaces.md#title-bar-height)). The request precedes every call of the replacement page, because the page's module graph includes the document and its code runs only after the graph has loaded. Wails serves `/start.json` from its asset server for the window that the request names (`x-wails-window-id`). Tauri serves `sok://core/start.json` from a custom URI scheme handler for the requesting webview and allows the page origin with `Access-Control-Allow-Origin`. A request that names no window fails with an error and starts nothing; Tauri also rejects a webview that is not a window's main webview. The runtime file `runtime/start.js` exports the document as its default export; the browser runtime reads its stored workspace with a top-level await and exports `controls: null`.

The main page's module script is a render-blocking script in the `head` (`blocking="render"`); the HTML standard accepts render-blocking elements only before the `body` exists. The module runs after the document is parsed, imports `environment.json`, `exposure.json` and `/installed-plugins.json` as JSON modules and the start document through `runtime/start.js`, and draws the window chrome with the control gap and row, and the library or the cards of the window's project space, before its first `await`; plugin content, native surfaces and the asynchronous reads follow. The document is not rendered before that point, and WebKit keeps the previous page of a reload on screen until the new page renders, so the first frame of a reload is that complete first screen. A main-page reload keeps its WebContent process.

WebKit draws a web view only while its window is on screen and does not wait for that drawing when the window is ordered on screen, so a window shown before its page has drawn shows an empty window while it opens. Both hosts therefore create every window hidden, make it transparent, put it on screen, and make it opaque once the main webview's first load has ended, successfully or not, and the presentation update after that has completed (`sp_window_reveal_after_load`). The first screen is drawn before the load ends, so the first visible frame of a new window, including the first window at startup, is that complete first screen, and a page that fails to load still appears with its failure.

The first module that the start document imports installs the start error handler. While the page has not drawn its first screen, an `error` event (a module of the start document that fails to load, fails to parse or throws while it evaluates) and an `unhandledrejection` event write `error page start: <text> @ <file>:<line>` to the application log through the `report` host call, once for each distinct text. The page removes the handler (`finishPageStart`) after its first screen, when the page's own error display ([application log](hosts.md#application-log)) takes over. A window whose page failed to start therefore leaves its error in `<config-dir>/logs/application.log`.

## Page reload

`host.window.reload` reloads the main page of a window in a new WebContent process, and the previous process ends with the previous document ([private native APIs](../operations/private-native-apis.md)); a page change of the main page does the same. A ready page first completes its pending saves (`core.projects.flush`). The host then sends that page the `page-reload` event instead of reloading the web view itself, because a host reply written after the reload has stopped its request is lost and Wails logs it as an error. The page stops sending host calls, waits until every call it has sent is answered, and reloads itself. A call that the page makes after the event is not sent and ends with the document, as a call that a reload stops would. The host reloads a page that has not reported ready itself, because such a page may have no `page-reload` listener. The command resolves after the new page reports ready and returns 1005 when it does not within 10 seconds.

## Host calls

The main page sends every host call through one call path in both applications (`packages/workbench/host-calls.js`). JSON writes NaN, Infinity, and -Infinity as `null`, and a host refuses `null` in a numeric field without naming the number the page held, so the page refuses a call whose argument contains such a number before it sends the call. The call fails with a `TypeError` whose message is `host call <name>: <path> is <value>, which JSON sends as null`, where `<path>` names the field (for example `surfaces[0].y`) or is `the argument` when the argument itself is the number.

Each host decodes every argument of a host call, and of a call that a surface page sends through the page runtime, with its own argument decoder before the call runs; the framework's own argument decoding receives the argument as raw JSON and refuses nothing, so both hosts refuse the same arguments with the same text. A field is optional when its declaration says so: an `Option` field or a field with `#[serde(default)]` in the Tauri host, a pointer field or a field whose `json` tag has `omitempty` in the Wails host. A field whose value is `null` counts as missing, so an optional field may be missing or `null`. The decoder refuses an argument with the message `argument <path> <problem>`:

- `<path> is missing`: a field that is not optional is missing or `null`.
- `<path> must be <expected>, not <actual>`: the value has another JSON type; `<expected>` and `<actual>` are `null`, `a boolean`, `a number`, `a string`, `an array`, or `an object`.
- `<path> must be an integer from <min> to <max>`: a number in an integer field is not an integer of the field's range.
- `<path> must be an array of <n> items`: an array of a fixed length has another length.

`<path>` starts with the argument name and adds `.<field>` and `[<index>]`, for example `request.rect.h` and `request.surfaces[0].x`. An argument that the runtime adapter does not send is `null`. Fields that the argument type does not declare are ignored. Two arguments have different types in the two hosts: the Tauri runtime adapter sends the exposure reply and the value of a status change as JSON text so that the host relays the page's key order ([exposure](exposure.md)), and the Tauri host checks that text after it decodes the argument. A status change whose value is missing or `null` changes the status to `null` in both hosts.

A failed image region call names the call: after its arguments decode, a failure of `imageAttach`, `imageFocus`, `imageCaret`, `imageText`, or `imageDetach` is `<call>: <reason>`, for example `imageDetach: image "view" is not attached`, in both hosts and on both the main page and the surface page path.

## macOS implementation

Wails uses application-owned additional `WKWebView` instances. Tauri uses its child-webview API. Both place those views inside their owning project `NSWindow`; settings and menus create no additional OS window. Framework dependencies are unchanged by the current surface and backdrop changes.

Shared AppKit code manages the window title bar, input selection, the surface layout transaction, and the window resize animation. Both hosts register `NSWindowResizeTime` as 0.001 before their first window, so zooming and animated resizes finish within one display frame; a window frame and its web content are presented separately, so a longer animation shows the previous content for the whole animation. A value the user set stays in effect. The input code uses hit testing and `_setIgnoresMouseMoveEvents:` so pointer tracking reaches the visible webview. This does not change delayed cursor responses. Surface presentation commits the layer transaction after `_doAfterNextPresentationUpdate:` completes for the main document and visible application documents. The presented-state wait waits for the window's open transactions to commit, then for that presentation update, then reads the next refresh time from the screen's `CADisplayLink`. It does not wait for external documents or block the UI thread. Settings and menus use transparent webview backgrounds; ordinary surfaces use opaque rendering. Shared CSS defines modal shading and blur.

Wails completes its initial webview size correction before applying saved window geometry. Its frame-size and position getters and setters then use matching coordinates.

The window-controls container repositions buttons when AppKit reparents them during recording. Position queries only read geometry. Fullscreen transitions temporarily restore the buttons to their standard title-bar container.

Windows and Linux native-host behavior is unverified. On Windows both hosts implement only directory identity, and application startup fails; [native hosts](hosts.md#windows-state) describes this state. Linux has no implementation. [Feature status](../features.md) records validation and release separately.
