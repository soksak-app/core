# Messaging

[한국어](messaging.ko.md)

This document defines the messaging contract between terminals and agents. Implementation and verification are tracked in [features](../features.md). Items listed in [open decisions](#open-decisions) are not settled by this document; they are not implemented until their decision is recorded here.

## Decisions in force

- Decision D3 of the [terminal plan](../plans/terminal-plan.md#32-event-path-decision-d3): file events observed by the terminal sidecar are the only messaging event path. Agent hooks (Claude Code `FileChanged`, Codex hook events) are not on the delivery path. A message is delivered the same way whichever agent wrote the file.
- Decision D4 of the [terminal plan](../plans/terminal-plan.md#33-delivery-channel-to-the-agent-decision-d4): input injection into the registered terminal is the baseline channel. The MCP tools `messages_read` and `messages_wait` are the better channel where the agent supports MCP tools. Delivery does not depend on a skill.
- The sidecar does not poll. It observes folder changes through an event source, the Rust crate `notify` ([settled](#settled-decisions)). The rule of [AGENTS](../../AGENTS.md#implementation) applies: file watching uses a maintained library of the ecosystem.

## Registered folder

A terminal registers a folder with the request `messages.register` to its terminal sidecar, with the parameter `folder`, an absolute path. The request carries the `surface` of the terminal, as every sidecar request does ([sidecars](sidecars.md#messages)). The sidecar sends events only for a surface that sent it a request ([sidecars](sidecars.md#failure), the failure rule for a message to a surface the host never sent to that process).

The reply is `{registration, folder}`, where `registration` is an identifier that the sidecar assigns: a version 4 UUID created from random bits when the folder is registered, so it is unique across processes ([wire decisions](#wire-decisions), point 3). The sidecar creates a folder that does not exist, with each missing parent, before it watches it: a creation that fails fails with `folder-create-failed`, which names the folder and the reason of the system, and a path that is not a directory fails with `not-a-directory` ([folder of a terminal](#folder-of-a-terminal)). A folder that is removed between its creation and the start of its watch fails with `folder-missing`, and a watch that the system refuses fails with `folder-missing` and the reason of the system. A request for a folder that another surface has registered, or for a second folder of a surface that already holds a registration, fails with `already-registered`. A repeated request from the same surface for the same folder returns the same reply, because the operation is idempotent ([AGENTS](../../AGENTS.md#implementation)). These rules are decided in [wire decisions](#wire-decisions). Each error is an explicit error reply and is not replaced by an empty result.

When the host sends `closed` for a surface, the sidecar releases the resources of that surface, such as its watches, and then replies `{"surface": id, "closed": true}`; it replies with `error` when it cannot release them ([sidecars](sidecars.md#messages)).

## Folder of a terminal

The page of a terminal registers the folder `<root>/.soksak/messages/<surface>`, where `<root>` is the `root` of the `project` of its start values, the canonical root of the project that the window shows, and `<surface>` is the identifier of its surface ([view surfaces](native-surfaces.md#view-surfaces), start values). The folder belongs to the project because the terminals of one project exchange messages, and `.soksak/` of the project root already holds the project files of the application ([projects](projects.md#persistence)); each surface has its own folder, because a folder has one registering surface ([wire decisions](#wire-decisions), point 9).

- Creation: the terminal sidecar creates the folder and its missing parents at `messages.register`, because the page has no file operation and the sidecar of the terminal is the native code of its domain ([AGENTS](../../AGENTS.md#structure)). The page creates nothing.
- Time: the page sends `messages.register` once its sidecar port is connected, before or without an open session ([wire decisions](#wire-decisions), point 8), and again after each reconnection of the sidecar, because a repeated registration returns the same reply ([wire decisions](#wire-decisions), point 10). A page that loads again for the same surface sends the same request and receives the same registration.
- No project: a terminal in a window without a project registers no folder, so its reads and its wait fail with `unknown-terminal` from the sidecar, which names the surface that holds no registration.
- Status: the page reports the registration as the status `<plugin>.messages`, `{folder, registration}` after the reply, and `null` before it and without a project, so that a sender learns the folder of a terminal and writes into it with `sok message send` ([cli](cli.md#commands)). A refused registration keeps `null` and is shown through the error display path of the plugin with the text `<plugin>.messages: <code>: <reason>`, which writes it to the application log ([AGENTS](../../AGENTS.md#structure)).
- End: the folder and its messages stay after the surface closes; the sidecar releases only the watch ([registered folder](#registered-folder)).

## File event

A file event is delivered to the page of the surface as a sidecar message. The host delivers each sidecar message only to the window that first sent for the surface, as the `sidecar-message` event `{sidecar, surface, cids, body}` ([sidecars](sidecars.md#messages)). A page receives the body through `on(surface, fn)` ([page interface](sidecars.md#page-interface)).

The body of a file event is `{registration, path, from, kind, seq}`:

- `registration` is the identifier of the registration that observed the change.
- `path` is the path of the changed file relative to the registered folder.
- `from` is the identifier of the sending surface, read from the name of the message file ([message](#message)). Only message files produce an event, so each event has a `from`.
- `kind` is `created`, `modified` or `removed`.
- `seq` is the sequence number of the event.

The sidecar sends one event per change of a message file, which is a direct child of the folder whose name ends in `.txt` and carries a sender ([message](#message), [wire decisions](#wire-decisions)). The sequence number `seq` counts per registration and starts at 1 for each registration in one sidecar process. The source of the event is the registration, which the body names. The `seq` rule of [logging](logging.md#event) assigns one counter per writer process to log records; this contract applies the same counter form to each registration, so a reader orders the events of one folder by one counter. The plan requires a sequence number per event and does not define its scope ([terminal plan, 3.5](../plans/terminal-plan.md#35-red-and-green-for-f899-7)).

On the wire the event name is the member `body.event`, `file.changed` ([wire decisions](#wire-decisions), point 1); the name below is the name of the event-log record. Each terminal sidecar watches the folders of its own surfaces and delivers their messages: `alacritty` for the plugin `term` and `vt` for the plugin `terminal`, because each holds the terminal sessions of its plugin, and both implement this contract and run its [shared cases](#shared-cases). The event name in the catalog of a sidecar is `sidecar.<sidecar>.file.changed` (`sidecar.alacritty.file.changed`, `sidecar.vt.file.changed`). The catalog form requires that prefix for every sidecar event ([logging](logging.md#sidecar-catalogs)); the names given without it are not valid catalog names. The gate level is `debug`, and the class is `io`, which holds sidecar messages ([logging](logging.md#classes-and-policy)). The default policy stores only `error` ([logging](logging.md#policy)), so a file event is stored only when the person enables the `debug` level of the class.

## Message

A message is a file written directly in a registered folder, not in a subfolder. Its file name is `<from>.<token>.txt`: `from` is the identifier of the sending surface, which the sender reads from `SOKSAK_SURFACE` in its environment ([processes of a surface](sidecars.md#processes-of-a-surface)), and `token` is a non-empty string without a `.` that makes the name unique. The sidecar takes `from` as the text before the last `.` of the name without `.txt`, so a surface identifier may contain a `.`. Its content is UTF-8 text, and its size is at most 64 KiB. Other files, in a subfolder or with a name that does not end in `.txt`, produce no event and no message ([wire decisions](#wire-decisions)). A `.txt` file directly in the folder whose name gives no non-empty `from` or `token` produces no event, and `messages.read` refuses it with `invalid-sender`, which names the path, until the file is removed or renamed ([wire decisions](#wire-decisions), point 16). A file larger than 64 KiB is refused by `messages.read` with the explicit error `message-too-large`, which names the path. The bound is stated because a sidecar buffer must not grow without a limit, and a larger file is reported instead of truncated ([AGENTS](../../AGENTS.md#implementation)). A message whose content is not UTF-8 is refused by `messages.read` with `invalid-text`, which names the path, because a boundary rejects an invalid value instead of replacing its bytes ([AGENTS](../../AGENTS.md#implementation)).

A writer creates the message under a temporary name that does not end in `.txt`, such as `.tmp-<random>` in the same folder, writes its text, closes the file, and then renames it to its `<from>.<token>.txt` name. The rename is the only point at which the message becomes visible: a new file is reported when it is created, which can precede the end of its writing, and the sidecar reads only names that end in `.txt`. The send command of `sok` writes messages this way; [cli](cli.md#commands) defines the command, and this rule is its contract. A writer other than `sok` must follow the same rule, because the sidecar cannot tell a complete file from one that is still being written ([wire decisions](#wire-decisions), point 17). Measured on macOS for both sidecars: a message written in steps under a temporary name gives no event, and its rename gives one `created`, whose read returns the whole text (the tests of the write rule in `alacritty-core/tests/serve_contract.rs` and `vt-core/tests/serve_contract.rs`).

A message is not consumed. `messages_read` returns the messages with a sequence number greater than `after`, in increasing `seq` order. A repeated read with the same `after` returns the same messages while the folder does not change, because the operation is idempotent ([AGENTS](../../AGENTS.md#implementation)). A file that is written again produces a new `created` or `modified` file event with a new `seq`; it is returned as a new message with that `seq`, and the earlier event is not replaced. The text of a message is read when the reply is built. A `removed` event is not a message: the messages of a reply are the `created` and `modified` events whose file exists when the reply is built, and `last` is the greatest `seq` of every event of the registration.

## Report request

A message asks its receiver for a report, and a report asks for none. `sok message send <folder> <text>` writes `<text> (끝나면 결과를 sok message send --reply <sender folder> "<보고>"로 보고하라)`, where `<sender folder>` is `<root>/.soksak/messages/<SOKSAK_SURFACE>`, the folder of the sending surface beside the folder of the receiver, `<root>/.soksak/messages/<surface>` ([folder of a terminal](#folder-of-a-terminal)). The command adds exactly one request and does not look for one in the text, so a sender writes none. A folder of another form names no root, and the send fails with an explicit error and writes no file. `sok message send --reply <folder> <text>` writes `<text>` alone and names the file `<from>.report-<token>.txt`.

- Reason for the tail in the file: the request is part of the message, so an agent that reads it with `messages_read` or `messages_wait` reads the same request as the injected paste ([injected message](#injected-message)), whose text is the text of the file. With the request in each message the receiver needs no separate instruction, and the sender needs no second submit to learn the result.
- Reason for the mark in the token: a report is marked in the part of the name that the readers do not interpret. The sidecars take `from` as the text before the last `.` and require a non-empty token without a `.` ([message](#message)); `report-<token>` is such a token, so every reader of the folder contract reads a report as a message without a change, and the name still states that the file is a report. A mark in the text, such as a first line, would be pasted into the terminal of the receiver.
- An agent in a soksak terminal receives each message as injected input, so it answers a request once with `--reply` and answers no report; `messages_read` and `messages_wait` serve an agent outside a soksak terminal or read the history ([agent skill](cli.md#agent-skill)).

## Folder removed or renamed

When the registered folder is removed or renamed, the sidecar sends the event `sidecar.<sidecar>.registration.closed` with `{registration, reason: "folder-removed"}` at the gate level `info`, and it ends the watch of that registration. The event is explicit, and the sidecar does not poll for the folder ([AGENTS](../../AGENTS.md#implementation)). A folder that is created again at the same path does not resume the watch: the agent registers the folder again, and the new registration starts its `seq` at 1.

## Cursor across restart

The sequence number `seq` counts per registration, and a sidecar process that starts again creates new registrations, so `seq` starts at 1 again. Each registration gets a new random version 4 UUID when it is created (source: `alacritty-core/src/pty.rs:365`, `Uuid::new_v4().to_string()`), so the registrations of a restarted process never equal an earlier registration, and a cursor from an earlier process names an identifier that no current registration has. A cursor that an agent kept from an earlier process would then skip or repeat messages. The registration is therefore the epoch of the cursor: each reply of the reads gives `registration`, the caller passes it with `after`, and a read or a wait whose `registration` is not the current registration of its surface fails with `epoch-changed`, which names the given and the current registration. The caller then reads again from `after` 0 with the current registration. A read with `after` above 0 and no `registration` fails with `invalidParams`. The epoch is the registration and not a count of the folder's messages, because a count changes when a message is removed: the greatest `seq` would then fall below the cursor and new messages would be skipped ([wire decisions](#wire-decisions), point 18).

## Missing folder

The sidecar creates a missing folder at registration ([folder of a terminal](#folder-of-a-terminal)), so a missing folder is no failure of `messages.register`; a creation that fails is `folder-create-failed`. A folder that is removed after its creation and before its watch is `folder-missing`, and a folder removed after registration ends the registration with the event of [Folder removed or renamed](#folder-removed-or-renamed). The rules that apply are that sidecar errors are failures and are not replaced or discarded ([sidecars](sidecars.md#messages)), and that a boundary rejects an invalid value with an explicit error ([AGENTS](../../AGENTS.md#implementation)).

## Hand-off is not a message

A hand-off gives a task to another terminal and receives its result. It is a record, not a message: a message is text that the reader receives in order, and a result sent as a message cannot show which attempt of the task it answers. The record has the states `assigned`, `started`, `result`, `integrated` and `abandoned`. `assigned` starts an attempt, and `started`, `result` and `integrated` follow in that order. `abandoned` ends an attempt that has not reached `integrated`, and a new assignment after it starts the next attempt. Each record holds an `attempt` number that starts at 1 and rises by one with each assignment. A state change names its attempt, and a change or a result of an earlier attempt is refused with `stale-attempt`, which names the current attempt. The record has no heartbeat, time limit or lock: a stalled attempt stays `started` until its owner or a person abandons it, and a waiting caller waits for the state event, as [AGENTS](../../AGENTS.md#implementation) requires for event waits.

### Hand-off record

Each terminal sidecar owns the record in its module `handoff` beside its messaging module (`vt-core/src/handoff.rs` and `alacritty-core/src/handoff.rs`), because messaging owns the registered folder beside whose messages the record lives.

- File: one record per task is the file `<task>.handoff.json` directly in a registered folder, the folder of the terminal that receives the task. Its name does not end in `.txt`, so it produces no file event and no message ([wire decisions](#wire-decisions), point 12). `task` is a non-empty name without `/`, `.` or NUL; another name is refused with `invalid-task`, which names it.
- Content: the JSON object `{task, attempt, state, result}`: `attempt` is an integer of at least 1, `state` one of the five states, and `result` the text of the result, a string in the states `result` and `integrated` and `null` in the others. A file with another form is refused with `invalid-record`, which names the path and what it found; it is not replaced by a new record.
- Write: the module writes the record under a temporary name `.tmp-<random>` in the same folder and renames it to its name, as a message is written ([message](#message)), so a reader reads either the earlier or the new record. A write that fails is refused with `record-write-failed`, which names the record and the reason of the system, and a failed rename removes the temporary file.
- Assignment: `assign` writes `attempt` 1 and `assigned` when the task has no record, and the next attempt and `assigned` when the current attempt is `abandoned`; while the current attempt is `assigned`, `started` or `result`, or after `integrated`, it is refused with `invalid-transition`, which names the attempt and its state.
- Change: `update` names the task, its attempt and the new state, with the text for `result`. An attempt other than the current one is refused with `stale-attempt`, which names the given and the current attempt, before the state is judged. The changes are `assigned` to `started`, `started` to `result`, `result` to `integrated`, and `assigned`, `started` or `result` to `abandoned`; any other change is refused with `invalid-transition`, which names the attempt, its state and the requested state. A task without a record is refused with `unknown-task`.
- One attempt: the record holds the current attempt only, so a result of an earlier attempt has no record to change and is refused.
- No wire operation reaches the record yet; the operations, which decide which process writes a record of another terminal's folder, are not defined.

## Input injection

A trigger acts through the terminal. It injects input into the registered terminal, or it runs a declared command. No agent API is used ([terminal plan, 3.2](../plans/terminal-plan.md#32-event-path-decision-d3)).

The sidecar receives input through the `input` and `paste` operations of its session ([persistent services](persistent-services.md#destructive-command-guard)). Each submitted line that these operations carry is judged by the destructive command guard. A line that a declared rule matches, or whose command cannot be decided, is refused with the error `guardRefused` and writes no byte to the session ([persistent services](persistent-services.md#destructive-command-guard)). An injected message is judged by this guard ([settled](#settled-decisions)).

The page of the terminal injects each message in the form, the order and under the hold that [injected message](#injected-message) defines.

### Injected message

The page of a terminal injects each message of its registration into the input of its session, the baseline channel of decision D4, in the form that the [settled decisions](#settled-decisions) state.

- Form: the visible text is `[메시지 from <title>] <text>`. `<title>` is the text that the sending tab shows when the message is injected: in `core.grid` of the window, for the tab whose `id` is the `from` of the message, its `label`, the title that its surface reported, or its `title`, the stored name such as `탭 2`, when `label` is `null` ([tab reports](plugins.md#tab-reports), [card tabs](example-model.md#card-tabs)); the page reads it at each injection, so a changed label names the next message. The text loses its control characters and line breaks and is cut to 40 characters, the last of which is `…` when it is cut. Reason: a person recognizes a sender by what its tab shows, and an unbounded title that a program sets, such as the whole first prompt of an agent, made the prefix read as part of the input of the person; the strip also cuts a long title with an ellipsis. The page follows `core.grid` with `runtime.status.watch` ([view surfaces](native-surfaces.md#view-surfaces)). `<text>` is the text of the message that `messages.read` returns. The terminals of one project share the folders of the project, which one window shows, so the sender is a tab of the same window. A message whose `from` names no tab of `core.grid` is not injected: its delivery is `refused` with the reason `sender <from> has no tab in the window`, and the message stays readable.
- Submission: the page sends the visible text through the `paste` operation of the session and then the key Enter as a separate input, in the order of its input queue, as `<plugin>.submit` sends its text and Enter. The sidecar writes the paste as a bracketed paste when the program enabled bracketed paste mode and as the text otherwise, so a line break of the text stays inside a bracketed paste and submits a line without it, as a pasted text does. The page waits for the reply of the paste and of the Enter: a refused paste sends no Enter, and a reply that is an error other than `guardRefused` is shown through the error display as `<plugin>.messages: <path>: <error>: <reason>` and is the delivery `refused` with the reason `<error>: <reason>`.
- Order: the page injects the messages in increasing `seq`, one at a time, and injects a message after the reply of the input of the one before it. The messages are those of the `created` and `modified` file events that the page receives while it is attached to the registration: for each event the page reads `messages.read {after: seq - 1, registration}` and injects the message with that `seq`; an event whose message the reply does not hold, because its file was removed, is `skipped` with the reason `message <seq> is not in the folder`. The `path` and `from` of a decision are those of the file event. A message that exists before the page attaches is not injected and stays readable with the MCP tools, so a page that loads again does not inject a message that an earlier page injected.
- Busy receiver: a receiver whose foreground program is busy, a running command or an agent at work, receives the paste and Enter in its input as typed text. The bytes wait in the input of the session until the program reads them, and an agent that queues typed input takes the message as a queued submission. No key of the TUI adapter is sent ([settled decisions](#settled-decisions)).
- Guard: the destructive command guard judges each line that the paste submits ([input injection](#input-injection)); a refused message has the delivery `refused` with the reason `guardRefused: <rule>: <reason>`.

#### Hold for the person

The page injects no message while the terminal waits for the person or while the person types in it, because the paste and Enter would answer a prompt for the person: Enter selects the default answer of a permission prompt, and the text can select an option ([evidence](#evidence-of-the-hold)). The page holds the injection while one of these holds, and the hold names the first of them in this order:

1. `blocked`: `<plugin>.program` holds a record whose `state` is `blocked`, so the program waits for an approval or an answer of the person exactly while its prompt is open; the hold names the `kind` of that record (`permission`, `question`, `auth` or `null`). `<plugin>.program` is the program status of the terminal state contract (`docs/spec/terminal-state.md`), which takes the state from the OSC 7501 reports of the program and from no text of the screen.
2. `notice`: `<plugin>.program` holds no record and its `notice` is `true`, so a program that writes no record called the person. A notice ends when the person focuses or types into the terminal, whether the program still waits or not, so it holds the injection only for a program without records.
3. `composition`: the `text` of `<plugin>.compose` is not empty, so the person composes text with an input method.
4. `typing`: the person has sent an insert, a paste or a drop to the terminal since the person's last Enter or Ctrl+C or the last change of `<plugin>.state` to `idle`, so a line of the person waits on the input line.
5. `input-held`: `inputHeld` of `<plugin>.session` is not `null`, so the session holds input that the program does not read and refuses a paste above its bound.
6. `role-pending`: the role of the tab of the terminal is `pending` or `unconfirmed` in the status `core.tab.role` ([role confirmation](agent-roles.md#confirmation)), so the agent has not confirmed the role it was given. The hold applies to the work messages only; the change messages and the reread requests of the role are not held.

A running command without records and without a notice is a program whose wait is unknown; it does not hold the injection, because a busy receiver takes a message as typed input ([settled decisions](#settled-decisions)). A held message stays in the folder and is readable with `messages_read` and `messages_wait`. The page injects the held messages in order at the status change that ends the last hold; it follows the changes and does not poll.

#### Delivery

The status `<plugin>.messages` holds the delivery of the messages beside the registration: `{folder, registration, held, last}`. `held` is `null` while nothing holds the injection, and `{reason, kind, pending}` while a hold applies, where `reason` is the first reason of the list above, `kind` the `kind` of the `blocked` record or `null` for another reason, and `pending` the number of messages that wait. `last` is `null` before the first decision, and then `{kind, seq, path, from, state, reason}` of the last message that the page decided: `state` is `injected`, `refused` or `skipped`, and `reason` is `null` for `injected`. Each decision writes the record `plugin.<plugin>.messages.delivered` at `info` with `{kind, seq, path, from, state, reason}`, where `kind` is `message` for a file of the folder, `first` for the first message of a session, `role-change` for a change message and `role-reread` for a reread request. For a kind without a file, `seq` and `path` are `null`, and `from` is `soksak`, the sender of the application; and each start and end of a hold writes `plugin.<plugin>.messages.held` at `info` with `{reason, kind, pending}`, the end with `reason` `null`, so each delivery is observable in the status and in the event log.

`sok message send` reads the hold of the receiver after it writes the message and prints `{path, receiver}` ([cli](cli.md#commands)): `receiver` is `{surface, plugin, held}`, with `held` of the status `<plugin>.messages` of the receiving surface, so a `held` other than `null` states that the message is not injected and why, with the reason and the record kind; `receiver` is `null` when no application runs, when the folder is not the folder of a terminal (`<root>/.soksak/messages/<surface>`) when its surface is in no window, or when the status `<plugin>.messages` of the surface is `null`, because the surface holds no registration. The message is written in each case, and the sender follows `last` of `<plugin>.messages` of the receiver to learn the decision of its path.

#### Role confirmation

The terminal plugin matches the line `soksak role <fingerprint>` in the output that the program of its session writes, where `<fingerprint>` is 16 lowercase hexadecimal characters, and confirms the role of the tab through the same per-surface serialization as `core.tab.role.confirm` ([confirmation](agent-roles.md#confirmation)). The line is compared after the spaces at both ends are removed. The text that the page writes to the input is not matched, so an injected message, which holds `<fingerprint>` as a placeholder, never matches. A line that the terminal wraps at its width does not match; the state stays `pending` and a reread request asks again.

#### Evidence of the hold

Measured in a pseudo terminal of 120 columns and 40 rows with Codex CLI 0.171.0 (`-a on-request -s read-only`) and Claude Code 2.1.329 (`--permission-mode default`), each asked to run `touch approved.txt` in a scratch folder (`docs/spec/cases/messaging/permission-prompts.json`):

- Both showed a permission prompt whose selected answer was Yes. A bracketed paste of `[메시지 from test] hello` without Enter left the prompt open, ran no command and appeared nowhere on the screen, in the prompt or later in the input line: neither program queued it. The Enter that followed answered the prompt with Yes, and the command ran.
- Codex CLI reported `state=blocked:kind=permission` (OSC 7501) from the opening of the prompt until its answer, and `done` after the command. Claude Code sent the query `OSC 7501;?` in one write with XTVERSION, `CSI ? u` and `CSI c`; the pseudo terminal of the observation answered it with bytes that lack ESC and the terminator, after the reply to `CSI c`, so the program received no valid answer, and the run states nothing about the reports of Claude Code.
- A prompt that a program shows by itself takes the Enter of an injection in the same way: a Codex CLI update prompt that opened at start, with no OSC 7501 report, took the Enter after a pasted request and ran its selected answer, the update, and the folder trust prompt of Claude Code, whose status query received the same invalid answer, took an Enter and ran its selected answer, `No, exit`.

So a paste followed by Enter answers a prompt for the person with its selected answer, and a paste during a prompt is lost. The `blocked` hold is required for both programs. A prompt of a program that writes no record and gives no notice is not observable, so the hold does not cover it.

## MCP tools

The sok MCP server exposes a fixed set of tools, and no tool is made from the exposure ([cli](cli.md#mcp-server), the rule of the tool table). The messaging tools are `messages_read` and `messages_wait`. Each reaches the sidecar operation of the same dotted name, `messages.read` and `messages.wait`, through the command of the terminal page ([path of the reads](#path-of-the-reads)).

| Tool | Arguments | Reply |
| --- | --- | --- |
| `messages_read` | `{terminal, after, registration}`; `after` is optional and defaults to 0; `registration` is optional and is required when `after` is above 0 ([cursor across restart](#cursor-across-restart)) | `{registration, messages: [{seq, path, text, from}], last}`; `registration` is the current registration of the surface, the epoch of the cursor; `last` is the greatest `seq` of the registration when the reply is built, and the caller passes it as the next `after` with that `registration`. An unknown terminal fails with `unknown-terminal`; a `registration` that is not current fails with `epoch-changed`; a message with no valid sender fails with `invalid-sender`. |
| `messages_wait` | `{terminal, after, registration}`, with `after` and `registration` as in `messages_read` | On arrival, the same shape as `messages_read`, and the same errors. The call has no time limit and no timer: it ends on arrival, on the cancellation of the caller, when the registration of its folder is closed, which fails with `registration-closed` and the reason of the close, or when the sidecar connection of the page ends. An unknown terminal fails with `unknown-terminal`. |

The wait ends on arrival or on an event that closes the registration; no timer ends it, because a wait is an event wait and the rule of [AGENTS](../../AGENTS.md#implementation) allows a timer only when no event source exists. No relay bounds it either: a command has no time limit and declares none, and a relayed command ends by its reply or by the end of its peer ([exposure](exposure.md#relay), command `timeout`). A cancelled call ends without a result, as the status watch does ([cli](cli.md#mcp-server)).

### Path of the reads

A tool call reaches the sidecar through the endpoint, the page of the terminal and its sidecar port; no endpoint method sends to a sidecar, because the sidecar answers the window of the page that sent for the surface ([sidecars](sidecars.md#messages)) and the page holds the sidecar port of its surface.

1. Window: `sok` sends `surface.window {surface: terminal}`. The answer 1012 fails the call with `unknown-terminal: surface <terminal> is in no window`.
2. Plugin: `sok` sends `exposure.snapshot {window, surface: terminal}` and takes `plugin` of the group of the surface ([window snapshot](exposure.md#window-snapshot)). A surface whose group registers no command `<plugin>.messages.read` or `<plugin>.messages.wait` fails the call with `unknown-terminal: surface <terminal> of plugin <plugin> registers no command <name>`.
3. Command: `sok` sends `command.run {window, surface: terminal, name: "<plugin>.messages.read"}` or `"<plugin>.messages.wait"`, with `params` holding the `after` and the `registration` of the call that are present.
4. Page: the command sends `{operation: "messages.read"}` or `{operation: "messages.wait"}` with the same `after` and `registration` and one correlation identifier, and answers the body of the reply that echoes it. A reply `{error, reason}` rejects the command with the text `<plugin>.messages.read: <error>: <reason>` (or `.wait`), and the end of the sidecar connection rejects each pending command with `<plugin>.messages.wait: the sidecar connection ended`, because the sidecar ends the waits of a connection without a reply ([wire decisions](#wire-decisions), point 7). The page checks no member of the parameters that the sidecar checks, so the sidecar gives each refusal of a cursor (`invalidParams`).
5. Result: the tool answers the result of the command, and a command error is the tool error with its text.

Each terminal plugin declares the commands `<plugin>.messages.read` and `<plugin>.messages.wait` with the parameters `{after, registration}` and the status `<plugin>.messages`; `terminal` and `term` hold them in their repositories.

A cancelled `messages_wait` ends its call without a result, and the server keeps the endpoint request open: the endpoint has no cancellation of one request, so the command ends at the next message or close of the registration, and the server discards its answer. `core.plugin.open-calls` reports the open command until then ([plugin processes](plugin-processes.md)).

Every tool of the table in [cli](cli.md#mcp-server) has an underscore name, such as `windows_list` and `status_get`; the messaging tools follow the same form ([settled](#settled-decisions)).

A refused or failed call returns an explicit error and is never reported as an empty result, because every error is reported ([AGENTS](../../AGENTS.md#implementation)). A tool call that fails returns a tool error, as [cli](cli.md#mcp-server) defines for the other tools.

The agent uses the MCP tools only where its client supports MCP tools ([terminal plan, 3.3](../plans/terminal-plan.md#33-delivery-channel-to-the-agent-decision-d4)). The agents that receive the MCP tools are Claude Code and Codex, the two that `sok mcp install` registers; a test checks this set against that registration ([wire decisions](#wire-decisions), point 15).

## Shared cases

`docs/spec/cases/messaging/names.json` holds the cases of the name rule of [message](#message): each case has a file name directly in the folder and its result, `ignored` for a name that is not a message, `invalid-sender` for a `.txt` name that gives no `from` or no `token`, or the `from` of a message. Each terminal sidecar copies the file into its fixtures and runs each case through its own name rule, and its contract tests run the behaviour of this document with real folders and files.

## Wire decisions

Each decision follows the existing wire of the terminal sidecars and states its source in the `main` branch of the sidecar `alacritty`; the sidecar `vt` has the same wire in `vt-core/src/protocol.rs`, `vt-core/src/pty.rs` and `vt-core/src/platform/darwin/file_watch.rs`: `protocol.rs` is `alacritty-core/src/protocol.rs`, `pty.rs` is `alacritty-core/src/pty.rs` and `file_watch.rs` is `alacritty-core/src/platform/darwin/file_watch.rs`. Each decision is one sentence, followed by its reason and its source.

1. **Event name.** A sidecar event names itself in the member `event` of its `body`, in the dotted form, so a file event is `{surface, body: {event: "file.changed", registration, path, from, kind, seq}}`. Reason: the host relays `body` without reading it ([sidecars](sidecars.md#messages)), and every existing wire event names itself this way. Source: `protocol.rs:3630` (`session`), `protocol.rs:3469` (`clipboard.store`), `protocol.rs:4923` (`screen.rows`). The catalog and log form keeps the prefix (`events.json:162`, `sidecar.alacritty.shell.state`), and the wire keeps the short name (`protocol.rs:2225`, `selection.copy`).
2. **Operation parameters.** A request names its operation in the member `operation` of its `body`, in the dotted form `messages.register`, `messages.read` or `messages.wait`, and each parameter is a member of `body` beside `operation`: `folder` for the registration, `after` and `registration` for the reads and the wait; the terminal is the envelope member `surface`, so the tool argument `terminal` is sent as `surface`, and a `folder` that is not an absolute path fails with `invalidParams`. Reason: the existing dotted operations `screen.read` and `screen.watch` name their operation this way, and the envelope already carries the surface. Source: `protocol.rs:5837` (dispatch on `body.operation`), `protocol.rs:6212` (`screen.watch`), `protocol.rs:6229` (`screen.read`), `protocol.rs:5867` (`open directory must be an absolute path`).
3. **Registration type.** The member `registration` is a string, a version 4 UUID that the sidecar generates when it registers the folder. Reason: the registration is an identifier that the sidecar generates, returns in its reply and names in its events, which is the role of the `sessionId` string; the `generation` integer of `protocol.rs:155` names an image attachment and is not a sidecar-owned object. Source: `pty.rs:365` (`Uuid::new_v4().to_string()`), `protocol.rs:3630` (`sessionId`).
4. **Error field.** A failed request replies `body: {error: <code>, reason: <text>}`, where `error` holds the code (`folder-create-failed`, `folder-missing`, `not-a-directory`, `already-registered`, `unknown-terminal`, `message-too-large`, `invalid-text`, `invalid-sender`, `epoch-changed`) and `reason` names the folder or path that failed. Reason: the existing refusals put the code in `error` and the cause in `reason`, and the reply error text reads both. Source: `protocol.rs:6236` (`invalidParams` with `reason`), `protocol.rs:4410` (`guardRefused` with `rule` and `reason`), `protocol.rs:84-96` (`reply_error`).
5. **Event reason field.** A close event carries its cause in the member `reason` of its `body`, `{event: "registration.closed", registration, reason: "folder-removed"}`. Reason: `reason` is the member that the existing sidecar events use for their cause. Source: `protocol.rs:3550` (`sequence.rejected`), `protocol.rs:3292` (`error`).
6. **Correlation.** Each messages request carries one `cids` identifier in the envelope, and its reply echoes that `cids` for an answer and for an error; a file event carries no `cids`, because no request causes it. Reason: existing requests carry `cids` and each reply echoes them, so `cids` is the existing correlation form, and a `messages.wait` reply comes after other lines of the surface, which the surface and the operation alone do not identify. Source: `protocol.rs:5497` (the envelope `cids` of a request), `protocol.rs:111-117` (`Request::answer` writes `cids` into each reply), `protocol.rs:459-462` (`reply` calls `answer`).
7. **Caller cancellation.** When the caller closes its input, the sidecar ends a pending `messages.wait` without a reply. Reason: a call that the client cancels ends without a result, as the status watch does ([cli](cli.md#mcp-server)), and the closed input is the cancellation that the protocol observes. Source: `protocol.rs:5457-5471` (the end of input detaches the persistent connection and writes no reply), `cli.md` line 229.
8. **Session requirement.** `messages.register`, `messages.read` and `messages.wait` do not require an open session, while `input` is refused without one. Reason: a registration watches a folder and not a PTY session, so an agent can register before it opens a terminal. Source: `protocol.rs:4913-4915` (`screen.watch` replies without a session), `protocol.rs:4396` (`Session not open` for `input`).
9. **Already registered.** A surface holds one registration, so a request for a folder that another surface has registered, or for a second folder of a surface that holds one, fails with `already-registered`. Reason: `messages.read` and `messages.wait` take only `after`, so a surface with two folders would name no folder for its reads; the sidecar refuses a second entry under one key with an explicit error. Source: `protocol.rs:757` (`session surface already exists`).
10. **Repeated registration.** A repeated `messages.register` from the same surface for the same folder replies with the same `{registration, folder}` as the first and creates no new registration, so `seq` does not restart. Reason: operations are idempotent ([AGENTS](../../AGENTS.md#implementation)), and `sok` operations return the same result for the same identifiers. Source: `cli.md` line 160.
11. **64 KiB boundary.** A message file of 65536 bytes is accepted, and a message file of 65537 bytes is refused with `message-too-large`. Reason: a buffer needs an explicit bound ([AGENTS](../../AGENTS.md#implementation)), and the bound is stated in bytes so that the refusal is exact. Source: the messaging contract tests of the sidecar, `alacritty-core/tests/serve_contract.rs`, which write `64 * 1024 + 1` bytes and expect `message-too-large`; the boundary at 65536 has no test yet.
12. **Subfolder and other files.** A change to a file in a subfolder, or to a direct child whose name does not end in `.txt`, produces no event and no message: such a file is ignored, not refused, because it is not a message. Reason: an event exists only for a message, so `seq` counts messages and not other files. Source: `file_watch.rs:44-46` (the `Change` report names each change by its vnode, `folder` or `file`, so the sidecar filters the name before it sends an event).
13. **Folder rename.** A rename of the registered folder ends the registration as a removal, and the sidecar sends `registration.closed` with `reason: "folder-removed"`. Reason: the registered path names no folder after the rename, and the watch reports the rename on the folder vnode. Source: `file_watch.rs:25` (`NOTE_RENAME` in the vnode events), `file_watch.rs:141` (the folder vnode is registered with those events). The darwin watch treats `NOTE_RENAME` as a replacement only for the file vnode (`file_watch.rs:212-216`), so the folder rename is not implemented yet.
14. **MCP tool layer.** `messages_read` and `messages_wait` are fixed entries of the tool list in `packages/sok/go/src/agents/mcp.json`, with the input schema `{terminal, after, registration}`, and they are not made from the exposure. Reason: the MCP tool set is fixed and holds no tool per declared command ([cli](cli.md#mcp-server)). Source: `cli.md` lines 126 and 292, `packages/sok/go/src/agents/mcp.json` (`tools`).
15. **Agent MCP support.** Claude Code and Codex are the agents that receive the MCP tools, because `sok mcp install` registers the MCP server with the `claude` command and, when it is on `PATH`, with the `codex` command. Reason: the terminal sidecar repository has no agent catalog, and the `sidecar.json` manifest has no member that names agents ([sidecars](sidecars.md#declaration-and-startup)). Source: `cli.md` lines 250-257 (MCP registration), `sidecars.md` lines 14-22 (the `sidecar.json` fields).
16. **Sender.** The sender of a message is the `from` part of its file name, which is the surface that `SOKSAK_SURFACE` names in the environment of the sender; a `.txt` file whose name gives no `from` is refused with `invalid-sender`. Reason: a request names its surface in the envelope member `surface`, and every process of a surface receives `SOKSAK_SURFACE` for that surface, so the surface identifier is the identity that the wire already uses. The name carries it, so the sidecar reads the sender from the name that it filters already ([point 12](#wire-decisions)), without opening the file; a header line in the text would need the file read and parsed before the sender is known. Source: `protocol.rs:127-130` (the `surface` member of a line), `file_watch.rs:44-46` (the `Change` names each change, so the sidecar filters names before it sends an event), and the processes-of-a-surface section of `sidecars.md` (`SOKSAK_SURFACE`).
17. **Write rule.** A message becomes visible at its rename to a name that ends in `.txt`, and a writer creates it under a temporary name first. Reason: the sidecar already publishes its endpoint file with a temporary name and a rename in the same folder, so the same form is the wire's own pattern. Source: `alacritty-core/src/platform/darwin/service.rs:129` (the temporary name `endpoint.json.<uuid>.tmp`) and `service.rs:139` (`fs::rename` into `endpoint.json`).
18. **Cursor epoch.** The registration is the epoch of the reads: the reads and the wait take `registration`, and a read whose `registration` is not the current one of its surface fails with `epoch-changed`. Reason: each registration has a new identifier, which a new sidecar process creates when the folder is registered again, so the identifier changes when `seq` restarts; a count of the folder's messages does not survive the removal of a message that the agent already read. Source: `alacritty-core/src/pty.rs:365` (`Uuid::new_v4().to_string()` for a new identifier), wire point 3.

## Settled decisions

- Watcher library: the Rust crate `notify`, a maintained library that uses FSEvents on macOS. Reason: [AGENTS](../../AGENTS.md#implementation) requires a maintained library for file watching instead of a new implementation. The one folder-watching library this repository uses, `@parcel/watcher`, serves its Node test tooling, and that use does not decide the sidecar's library. Source of the sidecar language: the terminal sidecar is implemented in its own repository, which this repository does not declare; the choice of `notify` follows the Rust implementation named in the plan.
- Transport of the file-watching sidecar: `transport: "persistent"`. Reason: a registration must survive a reconnection of the persistent service, and [persistent services](persistent-services.md#service-transport) states that reconnection restores the sessions of the service ("Reconnection restores the same session, child process, and session state"). That rule names sessions and not watches, so the watch survival is a requirement of this contract. [Sidecars](sidecars.md#failure) states that a new process after a failure has none of the sessions of the failed process, so a standard input and output sidecar would lose its watches when its process ends.
- Request: `messages.register` with the parameter `folder`, an absolute path. Reason: it uses the dotted operation style of `screen.read` ([persistent services](persistent-services.md#screen-message)).
- Registration reply and errors: `{registration, folder}`; `folder-create-failed`, `folder-missing`, `not-a-directory` and `already-registered`. Reason: a reply and explicit errors are required, and the sidecar reports each of these conditions. The reply shape is the one given in [Registered folder](#registered-folder).
- Sequence scope: per registration, starting at 1 in one sidecar process. Reason: [logging](logging.md#event) assigns `seq` as a counter per writer, and a per-registration counter gives a reader one order per folder.
- Message format: a file `<from>.<token>.txt` in the registered folder, UTF-8, at most 64 KiB, with the refusal `message-too-large` for a larger file. Reason: a text file is the simplest format that a terminal agent writes, and the bound follows [AGENTS](../../AGENTS.md#implementation) for bounded buffers.
- Consumption: messages are not consumed; `messages_read` takes `after` and `registration` and returns the messages with a greater `seq`, and a repeated read with the same `after` returns the same result. Reason: [AGENTS](../../AGENTS.md#implementation) requires idempotent operations.
- Order and rewritten files: messages are delivered in increasing `seq`; a rewritten file is a new file event with a new `seq`, not a replacement of the earlier one. Reason: the `seq` rule of [logging](logging.md#event) orders the events of one counter, and [AGENTS](../../AGENTS.md#implementation) requires idempotent operations, which a replacement would break.
- Removed or renamed folder: the sidecar sends `sidecar.<sidecar>.registration.closed` with `reason: "folder-removed"`; a re-created folder does not resume the watch. Reason: [AGENTS](../../AGENTS.md#implementation) forbids polling where an event source exists, and the removal of a folder is an event that the watch receives.
- Waiting call: `messages_wait` takes `{terminal, after}` and has no time limit. Reason: the wait is an event wait that ends on arrival, on caller cancellation, or on the close of its registration, so no timer is needed ([AGENTS](../../AGENTS.md#implementation)). The time limit of a waiting call is closed by this decision.
- Event names and gate levels: `sidecar.<sidecar>.file.changed` at `debug` in class `io`, `sidecar.<sidecar>.messages.registered` at `info` and `sidecar.<sidecar>.registration.closed` at `info` in class `lifecycle`, where `<sidecar>` is `alacritty` or `vt`. Reason: a sidecar event carries the sidecar prefix ([logging](logging.md#sidecar-catalogs)); `info` is a change of an object's lifetime and `debug` is a crossing of a boundary ([logging](logging.md#event)); the class follows the table of [logging](logging.md#classes-and-policy).
- Agent MCP support: the set of agents is decided in [wire decisions](#wire-decisions), point 15, from the MCP registration of the `sok` command ([cli](cli.md#mcp-registration)).
- Tool names: the two MCP tools are named with underscores, as every tool of [cli](cli.md#mcp-server) is (`messages_read`, `messages_wait`). This document uses these names in its tool table.
- Form of an injected message: the page of the receiving terminal sends `[메시지 from <title>] <text>` through the `paste` operation of the session, as a bracketed paste when the program enabled bracketed paste mode, and then Enter; `<title>` is the text that the sending tab shows at the injection, on one line and cut to 40 characters ([injected message](#injected-message)). Reason: the visible text is the wording that a person reads on the agent's input line, which the contract and the plan do not determine ([terminal plan, 3.3](../plans/terminal-plan.md#33-delivery-channel-to-the-agent-decision-d4)); this form is the decision recorded for it, and the title of the tab names the sender in the words that the person sees in the window, where a surface identifier is a random string.
- Busy receiver: a message to a receiver whose foreground program is busy goes into its input as typed text does, and the program or the agent takes it when it reads its input; an agent that queues typed input takes it as a queued submission, and no key of the TUI adapter is sent. Reason: the paste and Enter are the submission that the agent queues as typed input, so a busy agent needs no background or send-now key ([terminal plan, 4.1](../plans/terminal-plan.md#41-tui-key-adapters-decision-d6)); the injection then depends on no key table, which is empty.
- Hold for the person: the page injects nothing while the program of the terminal waits for the person (a `blocked` record, or a notice of a program without records) or while the person types in it ([hold for the person](#hold-for-the-person)). Reason: a paste and an Enter in a prompt for the person answer it, as the [evidence](#evidence-of-the-hold) shows for a permission prompt of an agent, and a message must never answer for the person.
- Guard: an injected message is submitted through the `paste` operation and Enter, the input of a typed line, so the destructive command guard judges each line that it submits like any submitted line ([persistent services](persistent-services.md#destructive-command-guard)). A refused message gets the reply `guardRefused` with its `rule` and `reason`.
- Carrier: an injected message reaches the terminal through the `paste` operation of its session and the key Enter of its `input` operation ([persistent services](persistent-services.md#destructive-command-guard)). The parameters of these operations are declared by the terminal sidecar in its own repository, not by this repository ([AGENTS](../../AGENTS.md#structure)).
