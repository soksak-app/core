# Local endpoint

[한국어](endpoint.ko.md)

The macOS hosts implement this specification; [feature status](../features.md) records its validation. Windows and Linux transports are not implemented.

The native host serves the [exposure](exposure.md) methods to local clients over a JSON-RPC 2.0 endpoint. Every build includes the endpoint because exposure is a product feature.

## Transport

| OS | Transport | Address and access |
| --- | --- | --- |
| macOS | Unix domain socket | Socket `<application>-<pid>.sock` in `soksak/` under the per-user temporary directory (`$TMPDIR`, as returned by Go `os.TempDir` and Rust `std::env::temp_dir`). The host creates the directory with mode 0700 and refuses to listen when the path is not a directory, belongs to another user, or has another mode. The socket has mode 0600 |
| Linux | Unix domain socket | Socket in `$XDG_RUNTIME_DIR/soksak`. The host creates the directory with mode 0700 |
| Windows | Named pipe | `\\.\pipe\soksak-<id>`. The security descriptor allows only the current user |

The socket is not placed in the configuration directory because socket paths are limited to 104 bytes on macOS and 108 bytes on Linux.

Implementation: `src/platform/<os>/endpoint.*` in each [native host](hosts.md).

## Discovery

The host listens first and writes `<config-dir>/endpoint.json` only after its first window is registered. A client that reads the file can therefore send requests for that window at once: `windows.list` lists it, and its host entries answer. Page entries return 1003 until `host.windows` reports the window as `ready`, so a client waits for that status notification. A host that cannot register its first window does not write the file and ends startup with an error.

The host opens `<config-dir>/process.lock` (creating it when it is missing) before listening and takes an exclusive advisory lock on the open file (`flock`, `LOCK_EX | LOCK_NB`), which it holds for the life of the process. The lock alone determines ownership. After it takes the lock, the host writes one JSON object `{"pid": <owning host PID>, "boot": <boot identifier of the host run>}` into the file; the boot identifier is the one that the event log names (`logs/host-<boot>.jsonl`). A configuration directory has exactly one owning application process; that process may own multiple windows. A writing command of `sok` takes the same advisory lock (`flock`, `LOCK_EX | LOCK_NB`) on the open `process.lock` and holds it until the command ends, so the lock alone decides ownership in both directions. It writes the same form in the file after it takes the lock: the owner is `{"pid": <its process identifier>, "boot": <its boot identifier, `<seconds>-<pid>`, which names its event file>}`. A held lock refuses the command with the hosts' texts: `configuration directory <directory> is already owned by process <pid>` when the content is the current form, `configuration directory <directory> is already owned by a live process` when the content is empty, and that text followed by `; process.lock is not the current form: <content>` when the content has another form, the content cut to 256 bytes. A free lock file is taken over, whatever its content, as an earlier owner that ended without removing it. The command removes the file while it holds the lock, then unlocks. A second host on the same configuration directory while the lock is held exits before writing or replacing `endpoint.json`, with `configuration directory <directory> is already owned by process <pid>` when the content is the current form, with `configuration directory <directory> is already owned by a live process` when the content is empty or not yet written, and with that text followed by `; process.lock is not the current form: <content>` when the content has another form. The content of a held lock is the content of the owner, cut to 256 bytes in a refusal. A process using a different configuration directory has independent settings, endpoint, lock, and sidecar state and may run at the same time. A file that is present and not locked was left by an owner that ended without removing it, whatever its content, except an empty file: the starting host takes it over, writes its own record under its lock, and stores the event `host.run.unrecorded-end` (see [logging](logging.md#writers)). A starter creates the file before it locks it, and no lock call can be placed between the creation and the lock, so an empty file that is not locked can be the file of a starter that has not locked it yet. An owner writes its record only after it holds the lock, so an empty file names no earlier run, and the starting host takes it over without storing `host.run.unrecorded-end`. Normal shutdown removes the file while the lock is held and then releases the lock. A lock that cannot be opened or read fails with `<path>: <reason>`, with the same texts in both hosts.

```json
{
  "transport": "unix",
  "address": "/path/to/socket",
  "pid": 1234,
  "application": "wailsv3",
  "version": "0.0.8",
  "executable": "/path/to/sok-wailsv3",
  "started": "2026-09-17T09:00:00Z"
}
```

| Field | Value |
| --- | --- |
| `transport` | `unix` or `pipe` |
| `address` | Socket path or pipe name |
| `pid` | Host process id |
| `application` | `wailsv3`, `tauriv2` or `mygo` |
| `version` | Application version |
| `executable` | Absolute path of the host executable with symbolic links resolved |
| `started` | Start time in ISO 8601 |

The host removes the file and its socket on exit, including an exit that a termination signal (SIGTERM, SIGINT, SIGHUP) starts, which runs the same quit as `host.quit`. A process that ends without that exit, such as one killed with SIGKILL, leaves its socket; the next host of the same application removes sockets named `<application>-<pid>.sock` whose process is no longer running before it listens. A client reads the file to connect. When the process with `pid` is not running, the client reports an error and does not connect.

## Framing

Each message is a 4-byte big-endian unsigned length followed by that many bytes of one UTF-8 JSON-RPC 2.0 object. The maximum length is 16 MiB.

A connection stays open for many requests. Requests are multiplexed by `id`, and replies can arrive in any order. Server notifications have no `id`.

Requests that change the subscriptions of a connection (`status.watch`, `status.unwatch`, `diagnostics.transcript`) are applied in the order the host receives them, including the messages the host forwards to the page for them. A client that ends one subscription and starts the same one again sends the two requests in that order.

## Closing

The host closes the connection when it receives any of the following:

- a length prefix larger than the maximum;
- a body that is not valid JSON;
- a JSON value that is not a JSON-RPC 2.0 object;
- an undeclared method.

An HTTP request line is read as a length prefix larger than the maximum or as invalid JSON, so the host closes the connection before any method runs.

## Responses and termination

Each request has one response context. Its completion is one of four outcomes: the response was written, the request was a notification without a response, the write failed, or the answer was abandoned. A failed write is not a written response. The context completes once, after the write and flush attempt of the response and after the connection writer lock is released. Work registered after completion runs at once with the same outcome. Dropping a copy of the context does not complete it.

The termination that a request causes runs after the completion of its response, so the client receives the response before the endpoint closes:

- `host.quit` quits after its response.
- The operating system quit request that the native work of `host.menu.select` or `host.dock.select` causes, such as the Quit item of the application menu, quits after the response of that request. Such native work runs one at a time.
- A quit request outside such work, or one that a request without a response causes, quits at once.

The boundary is per request: termination does not wait for other requests that are still running. In Rust the context is the `ReplyScope` argument of `Service::call`; in Go it is the `*ReplyScope` argument of each endpoint method and of `HostCommand`. A call that does not come from an endpoint request, such as a deep link, has no context.

## Startup

The host creates the endpoint before it shows windows. If the host cannot create the endpoint, the application exits with an error.

Registered WebView pointer receipt completion requires pending mouse processing to drain before sending and after receipt. Registration rejects an unavailable drain API. Capability loss before sending rejects delivery without sending the event; loss after receipt must fail completion and report the unavailable API. A wait that ends by timeout or unregistration before the pre-send drain finishes completes once and cancels that drain, so the event is not sent afterwards. Native non-WebView targets and deliberately unregistered WebViews retain their declared delivery-only contract.

## Recording

The host stores every request of a client that names a declared method as the event `host.endpoint.call`, whether or not the performance trace is on: the method, the params as received (cut to 1024 bytes), the result and the microseconds ([logging](logging.md#entrances)). A frame that closes the connection (a frame over the limit, malformed JSON, a value that is not a JSON-RPC 2.0 request, an undeclared method) is not a request of a method; the host stores the reason of the closing as a record of the place `endpoint`.

## Log query

<a id="log-query"></a>The method `log.query` exists in every build and takes no `window`: it reads the event files of the configuration directory of the host through their indexes ([logging](logging.md#query)). Its params are the object of the query parameters (`channel`, `level`, `class`, `layer`, `event`, `event_prefix`, `surface`, `session`, `cid`, `run`, `text`, `from_us`, `to_us`, `order`, `limit`, `after`, `since`, `around`, `earlier`, `later`; `{}` is a query of the first 500 rows of the channel `other`) and its result is the page `{rows, next, tail, scanned}` (with `around`, the rows around one row, each with `context`, [logging](logging.md#query)). A parameter that the query refuses is the invalid-params error (-32602) with the text of the query (`log query level "x" is not one of error, warn, info, debug, trace`), a file that breaks the event structure or an index that is damaged is the error -32000 with the text `<file>:<line>: <reason>` or the text that names the index, and the host answers one page of at most 5,000 rows and 8,388,608 bytes of lines in a frame under the limit above. The page of the debug view is the same query as the host call `logQuery` ([debug](debug.md#timeline)).

## Diagnostic builds

The following methods exist only in diagnostic builds (Go build tag `diagnostics`, cargo feature `diagnostics`). Other builds reject them as undeclared methods. `make build-wailsv3`, `make build-tauriv2` and `make build-mygo` produce diagnostic builds; the release targets do not.

A diagnostic hold or recording that a request opens ends at the first of its own end, the close of its window, the end of the page or workbench that holds it and the close of the endpoint connection of the request that opened it; no limit ends it. At its end it sends what it held in the order held, and each request that waits on it answers in that turn. These are the modal content hold of `diagnostics.modal.hold`, the reply hold of `diagnostics.surface.hold` and the drag record of the workbench between `diagnostics.drag` and `diagnostics.drag.end`. A host waits for a callback of the native library without a limit: the library answers each call once on every path, and a native wait for an event that may not come (`diagnostics.native.objects`, `diagnostics.process.exit`) ends with that event or, as a hold does, with its window, its page and the connection of its request.

| `diagnostics.input.reference` | `{window, action, document?}` | Opens, reads, focuses, waits for, or closes the input reference described below; diagnostic builds only |

The **input reference** is an independent, ordinary AppKit `NSTextView` in the target application window. `action` is `open`, `read`, `focus`, `wait-document`, `wait` or `close`; `wait-document` and `wait` accept `document`, a required string. `open` creates one plain-text control above the window composition, without activating the application or changing the first responder. Ranges use UTF-16 units; `marked` is `null` without marked text, and `frame` uses the current top-left window content coordinates of native input. An unopened reference reads `{open: false}`. `focus` selects an open control with public `NSWindow.makeFirstResponder` without activating the application; a closed reference rejects `focus`. This explicit target setup makes the independent keyboard comparison deterministic while preserving an ordinary text view. `input.key` supplies exactly the same keys as the tested document; the interface cannot insert text.

`wait-document` returns that state once the document equals `document`, even when marked text remains. It observes text, selection and text-storage notifications before checking the current state, without polling. `wait` uses the same notification path but also requires marked text to be absent before it completes. One wait may be pending per window. No limit ends either action: a wait that has not reached its document ends with the close of the endpoint connection of the request or the end of the page of its window, and fails with `input reference did not reach the expected document before <end>: <state>`, naming the actual document and marked range, `<end>` as for `diagnostics.native.objects`. A check closes its reference and verifies the closed state before disconnecting. A successful reference comparison is input-method evidence only in the approved activation tier.

The control belongs above the composition because composition hit testing routes native surface input before its child views. The returned frame is measured from the current view, so a resize cannot leave stale click coordinates. Notification-based waiting keeps input-method replies independent from the timing of endpoint requests; its owning check includes committing marked text without changing the document.

The `layouts` of `diagnostics.layout.trace` and of `diagnostics.drag` is an array of `{ticket, begun, requested, presented, committed, commitPath, openAtCommit, flushed, displayed}` transactions since the start of the trace, with times in milliseconds on the clock of `diagnostics.clock`, which is also the clock of the recorded frames: `requested` is when the page asked the host to wait for the presentation of the drawn DOM, and `presented` is when that presentation was confirmed; on the mygo host `requested` is when its workbench asked for the frame of the transaction, and `presented` is when U3 reports that frame presented. `commitPath` names what committed the native surface layout transaction of macOS: `present` the presentation of the host, `start` the start transaction of a new page, `view-join` the presentation callback of the last view that joined the transaction (the deferred commit), `view-abandon` the abandon of that view, or `cancel`. `openAtCommit` is the number of the other CATransaction begin/commit pairs of the native code that were open when that transaction committed; a pair that the system opened is not counted. `flushed` is when the outermost Core Animation transaction of the thread that carried that commit had been sent to the render server: not later than `committed` when the commit closed the outermost transaction, and later when a transaction that the native code or the system opened was still open at the commit. `displayed` is the display refresh that carried that commit to the screen: at the first refresh callback of the display of the window after `flushed`, the target time of the refresh that follows (`targetTimestamp` of `CADisplayLink`), the refresh whose frame the render server composes with the content sent before that callback; it is null for a window on no screen and when the trace ended before that callback. The four are null for a transaction that did not commit and on a host without the native surface layout of macOS. A preparation that starts while the transaction of its window is open takes the earlier preparation over, and the commit of the transaction sends the changes of both, so the record of the earlier ticket has the `committed`, `commitPath`, `openAtCommit`, `flushed` and `displayed` of that commit. Stages that did not occur are null; no transactions means an empty array. A direct capture.start returns its frame directory before capture.stop; a capture-stop failure preserves that directory and returns the error so the requester can retain the failed recording. Successful recordings remain owned by the requester, which removes the directory after its checks finish.

Two stills can hold the same pixels, because a still does not identify a new drawable; the stills are evidence, and no check judges their pixels ([diagnostics](diagnostics.md)). A still never waits for pending disk writes: a still whose encoded frame would pass the 128 MiB that the encoded frames waiting for the writer may hold fails with `capture pending writer capacity exceeded (134217728 bytes)`, an error of the recording; it is not a successful partial capture. A still never waits for earlier stills either: a still whose request finds 8 stills in flight, between the request of their image to the window server and the release of their pixels after compression, fails at once with `capture in-flight capacity exceeded (8 stills)`, an error of the recording ([diagnostics](diagnostics.md)). Stop preserves recording errors and appends any stop error. A still that the window server gives no image of fails with `the window server gave no image of window <n>`, and its row records the reason.

Recording frame files `frame-NNNN.bgra` are named by the index of their still from 0 with at least four digits, so readers order frames by the number, not by the file name text. They use one lossless LZ4 block format. The little-endian header contains three uint32 values (width, height, BGRA row stride), eight float64 values (content x/y/width/height, content scale, device scale, and the request time and the completion time of the still in milliseconds on the clock of `sp_capture_clock`), the four ASCII bytes `LZ4S`, a uint32 compressed-block byte count and a uint32 CRC-32 of every decoded pixel byte. The header is 88 bytes; exactly the declared compressed bytes follow it. The LZ4 block restores exactly stride × height bytes, including row padding, without downsampling or color conversion. Reject wrong markers, incomplete or extra bytes, invalid blocks, decoded-size mismatches and checksum errors; do not interpret a frame of another marker as this format. Compression failure fails the recording explicitly.


Layout timeline replies have a capacity of 4096 transactions. When the actual record count exceeds capacity, the host returns an error and removes the recording directory that the requester cannot receive. A truncated timeline is never a successful reply.

The host writes large data, such as captures, to files under `<config-dir>/logs/captures`, and the reply contains the file paths. The requester removes the capture files after measurement.

Without `native`, `diagnostics.drag` drives the page's existing surface-input route with host-timed steps. Its native recording measures composition during that gesture; it does not establish OS mouse-button delivery. A composition check must also measure actual card movement and every requested round trip. Native pointer delivery is a separate `input.pointer` check, and `diagnostics.drag` with `native: true` delivers the gesture as native pointer input. The mygo host has no page and always delivers it so, through `sp_input_pointer`, without activating the window or the application; each input reaches the mygo surface view as a nested step of the step that delivers it. Its reply holds `from`, `steps`, `took`, `asked` and `pressWaits` of the gesture, `boundary` from the workbench, and `handled` as the milliseconds from the entry of each step to the return of its callback.

## Checks

Each platform runs these checks against the endpoint:

- an HTTP request line closes the connection, and no method runs;
- a different user cannot connect;
- an undeclared method closes the connection;
- the host removes `endpoint.json` on normal exit;
- a termination signal requests the normal exit once, and the next one ends the process;
- sockets of ended processes of the same application are removed before listening.
- a second process using the same configuration directory is refused, and normal close removes `process.lock`.

### Window activation observation

`host.window.activationObservation` preserves the native window-facts object:
`registered` is a boolean reporting whether the activation observer is installed,
and `count` is a canonical unsigned 64-bit decimal string (`"0"` or digits without
leading zeroes). The string preserves counts beyond JavaScript's safe integer
range. Missing or invalid native evidence fails the status read; the host does
not substitute an unregistered observer or a zero count. This observation does
not activate a window and is separate from the current `active` state.
