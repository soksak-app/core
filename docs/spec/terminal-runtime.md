# Terminal runtime

Owner cleanup and retain attempt closure and await termination for every selected surface actor even when one actor has already ended or fails. They report every failed surface explicitly instead of abandoning the remaining actors. A reported failure is not a successful cleanup.


When a newer connection attaches a persistent surface, EOF from the previous connection detaches only that previous connection's output sender. It must not clear the newer attachment's sender or close its output stream.


[한국어](terminal-runtime.ko.md)

This contract defines the approved terminal runtime. Implementation and verification are tracked in [features](../features.md); approval of this contract does not establish implementation.

## Ownership and process count

One persistent terminal service owns PTYs, VT state, scrollback, and rendering for one application configuration directory. PTY management, emulation, rendering, and client transport are separate modules in that process, not separate executables. Independent sessions own separate PTY devices and shell processes. A PTY device is not a process. Three independent terminals require one service and three shells, in addition to the application host. WebKit processes and programs launched by shells are counted separately.

A surface attachment is not a session. The first open for a surface key creates one registry actor and allocates a stable session identifier before starting its shell; repeated requests with the same creation identifier return the same result. Attaching a replacement surface does not create a PTY. The active attachment owns input and size changes, and stale attachments receive an explicit error. A session preserves its terminal dimensions when no surface is attached.

A session starts the shell that the terminal setting `terminal.shell` names. The default `login` is the login shell of the account's user database entry; any other value must be an absolute path to an executable file. The shell starts as a login shell: `argv[0]` is `-` followed by its file name and `SHELL` is its path. The terminal page sends the value as `shell` in its `open` request, and the workbench sends it for a background session through the plugin's `background.settings`. A missing value, a relative path, a missing or non-executable file, and an account without a login shell are explicit errors, and no other shell is started instead. A change of the setting applies to sessions opened after it.

The `open` request may carry `directory`, an absolute path of an existing directory, in which the shell starts; another value is an explicit error and no other directory is used instead. Without it the shell starts in the account's home directory. The terminal page sends its surface's `origin.directory` ([tab reports](plugins.md#tab-reports)) when it is not `null`, so a terminal split from a terminal starts in the directory that terminal reported last; otherwise it sends the surface context's `project.root`, so a new terminal in a project starts in the project's root. In a window without a project it sends no `directory`.

The sidecar starts zsh and bash with shell integration that reports OSC 133 marks, and changes no file of the user. The integration scripts are embedded in the sidecar and are written to `<temporary directory>/soksak-shell-<content hash>/` (mode 0700) before a session starts. For zsh, the sidecar sets `ZDOTDIR` to that directory and keeps an existing `ZDOTDIR` in `SOKSAK_ZSH_ZDOTDIR`; the directory's `.zshenv` restores the original `ZDOTDIR`, sources the user's `.zshenv`, and installs the hooks in an interactive shell, and zsh reads the remaining startup files from the restored directory. For bash, the sidecar exports `SOKSAK_BASH_INTEGRATION` with the script path and `PROMPT_COMMAND` whose first entry records the current `DEBUG` trap and then sources the script, because a file read by `source` in bash 3.2 does not see the `DEBUG` trap. The entry has no trailing separator, so that startup files may add entries before or after it with `;`. The shell reads its startup files unchanged; at the first prompt the script removes its entry from `PROMPT_COMMAND` (an entry between other entries becomes `:`), stops exporting both variables, and places its hooks before and after the user's entries. The sidecar does not start bash in POSIX mode with `ENV`, because bash 3.2 reads `ENV` only when it runs as `sh`, and the shell must remain a login shell with `argv[0]` `-bash`. When the user's startup files replace `PROMPT_COMMAND`, the script never runs and the session behaves as a shell without integration. Other shells start without integration.

The hooks report `133;A` before each prompt (bash reports `133;A;redraw=last`, because readline redraws only the last line of the prompt), `133;C` before a command runs, and `133;D;<status>` before the next prompt. Before each prompt they also report the working directory as `7;file://<host name><path>` with the path percent-encoded outside the unreserved characters and `/`. zsh reports `C` from its `preexec` hook. Bash 3.2 has no such hook, so a `DEBUG` trap reports `C` at the first command after a prompt; the first `PROMPT_COMMAND` entry cancels the wait, because an empty input line runs `PROMPT_COMMAND` without a command. At the prompt where the script installs itself, the entries after its own run after the trap exists, so a command whose text equals one of those entries is not reported at that prompt. The trap passes `$_` as its last argument, which keeps `$_` for the next command. When the startup files have set a `DEBUG` trap, the script does not replace it and reports no marks, because `A` without `C` would clear command output on a resize.

The service endpoint is scoped to the configuration directory, authenticated, versioned, and protected by a single-instance lock. A test configuration cannot discover a service belonging to another configuration. Session state and input queues are isolated. A busy session must not hold a global lock while reading, writing, emulating, or rendering.

## Closing and recovery

### Service transport

The sidecar declaration selects `transport: "persistent"`. A sidecar without that field uses its domain's stdio transport. A host starts the declared executable with `--service-dir <config-dir>/services/<executable-name>`. The service takes the exclusive lock in that directory before creating its listener. It creates the socket in a private, short temporary directory to respect Unix socket path limits and atomically publishes `endpoint.json` containing `{protocol: 1, pid, socket, token}`. Directory permissions are 0700 and token-bearing files are 0600. The ready line on stdout contains that endpoint only after the listener is ready. The service loads the default terminal font before it publishes the endpoint, so the first CoreText call of a service process delays the first terminal of that process and no later one. This cost is accepted because it occurs once per service process and the service outlives application restarts. The host waits at most 30 s for the ready line, a bound far above that cost, so that a service that never becomes ready does not keep the requests to its sidecar and the host's stop waiting; it then ends and reaps the service it started and fails with `sidecar <name>: the service did not print its endpoint within 30s`. A service that ends before its ready line fails the start with `sidecar <name>: service exited before endpoint`. The host waits at most 5 s for the hello reply and then fails with `sidecar <name>: the service did not answer hello within 5s`.

The first newline-delimited JSON message is `{operation: "hello", protocol: 1, token, client}`. The service replies `{operation: "hello", protocol: 1, ok: true}` or `{operation: "hello", ok: false, error}`. After authentication, surface messages retain the declared sidecar envelope. `{operation: "close-owner", request}` closes the authenticated client's sessions and replies `{operation: "closed-owner", request, ok: true}` after cleanup, or `ok: false` with `error`. `{operation: "shutdown", request}` is accepted only after owner close, replies `{operation: "shutdown", request, ok: true}`, and authorizes the service to exit after its client connections finish. Socket EOF preserves sessions. An endpoint file alone does not authorize killing its PID, and protocol or authentication failure must not start a competing service. A process that only lingers as a zombie — an unwaited spawn of a dead client — does not count as an existing service, so the stale endpoint it published is replaced.

Hiding a surface, visiting the library, or losing the application connection preserves sessions. Closing a terminal explicitly ends that session. Closing a window normally ends its owned sessions; normal application quit ends all owned sessions. Closing is complete only after the managed jobs are terminated, the child is reaped, PTY handles are released, output completion or failure is reported, and attachment tasks are removed. Shutdown errors are reported, not converted into success.

Application crashes and explicit update restarts leave the service alive. Reconnection restores the same session, shell process, VT state, and scrollback; the native image is recreated for the new application process and is never reused across processes. The service continues consuming and interpreting output while detached. EOF is a connection loss, not a session-close command, and so is a client whose output side closes before the service reads its EOF: the service detaches it and keeps its sessions. A close intent is recorded before acknowledgement so an interrupted close cannot restore a deliberately closed session.

A connection that is lost while the application runs is revived immediately, without waiting for the next send. The host's persistent reader notices the socket EOF and restarts the transport through the same single creation path: a live service is reattached — its preserved sessions answer with a `session` event — and a dead service is respawned after its stale endpoint is removed. The restart attempts once per disconnect; a failure is reported, and the next send retries the same path. The image registry dies with the acknowledged connection: the host invalidates the configure state of exactly that sidecar's images and re-sends their configure at the same size, because the new service holds no image state. Every surface that has sent to the sidecar receives the `sidecar-message` body `{"event": "connection", "connected": true}`, or `{"event": "connection", "connected": false, "reason"}` on a failed restart. The terminal page treats this as its reconnection signal: it resolves the stale sidecar error, closes its session gate so input queues again, and re-runs its session bootstrap — `open` (a no-op on a preserved session, a new session on a respawned service) followed by the last theme, the declared font, and the cursor policy. Background sessions of hidden tabs re-send their manifest open operation the same way. A respawned service cannot preserve the sessions of the process that died; a hidden tab that never remounts starts its fresh session when the connection notice arrives.

The host reads the service connection one line at a time and applies the [message limit](sidecars.md#messages) of the stdio transport to each line. A line over the limit, a line that is not a JSON object, a reply whose `operation`, `request`, `ok`, `error` or `closed` field has the wrong type, or a surface event without a string `surface` and a `body` ends the connection with that reason: the host closes the connection, fails the waiting close-owner, shutdown and retain requests, writes the reason to the application log, and delivers `sidecar-failure` with the reason to each surface that has sent to the sidecar, as the stdio [failure](sidecars.md#failure) rules do. The service is shared and keeps running. The host does not reconnect immediately, because the same message would end the next connection again; the next send reconnects through the creation path and announces the connection.

The service exits only after an explicit shutdown request and after no clients remain. A session is recoverable while a project layout holds its surface. `{operation: "retain", request, surfaces: [{surface, root}]}` closes every session of the authenticated client whose root and surface are not listed and replies `{operation: "retained", request, ok: true, closed}` with the number closed, or `ok: false` with `error`. The page sends the surfaces of every space layout of every project, with the project root, when it starts and after it removes a project or closes a space; the host adds every surface that this application process has sent and delivers the request to each persistent service that runs or has published its endpoint. A session whose surface no layout holds, which a crash or a failed page leaves without a closed notice, therefore ends when the application starts again. Service failure and OS restart are outside live-process recovery; a new shell is not evidence of recovery. The shared service is one process failure domain. Session isolation does not claim process-level crash isolation.

An application update may reconnect to the live service only when their protocol versions agree. A protocol mismatch is an explicit failure; it does not start a second service, close existing work, or use a compatibility path. Replacing the service itself waits until its sessions end.

## Terminal input and display

A single pointer click on a terminal transfers keyboard ownership to its native image region through the declared `terminal.focus` command. The host restores the target document WebView as the responder before delivering a later synthetic pointer after native terminal input, so a native image responder cannot strand the next click. The DOM anchor prevents the pointer's default DOM-focus action so WebKit cannot take ownership back during the same click. Card selection still receives the event. No second click, delayed refocus, or test-only focus command is required. Focus-request errors remain observable. Modal focus restoration and image focus notifications are deferred past the active AppKit/Tauri callback; they must not synchronously re-enter the WebView event path.

The engine, PTY, and displayed raster agree on the applied dimensions. Narrowing reflows soft-wrapped primary-screen lines; widening joins those same logical lines. Explicit newlines remain. Alternate-screen applications retain their terminal-controlled layout semantics. Divider movement never changes font metrics or animates raster geometry. A raster with no room for one cell is a composition transient, not an invalid request: the sidecar keeps the current grid, adopts the raster, and presents the frame — the drawing is clipped to the raster, so a smaller-than-cell raster shows only what fits — and the PTY keeps its size, so the child sees no window change. A surface opened while its raster has no room for a cell stays closed until a raster that fits one arrives; no error is reported for either.

The engine keeps a shell state from OSC 133 marks. `A` and `B` set the prompt state with the `redraw` parameter of the mark (`1` when absent, `0`, or `last`; another value is rejected), and `C` and `D` set the output state. `A` first moves the cursor to the start of the next line when it is not at column 0, and records that row as the prompt start; an ED 2 in the prompt state moves the prompt start to the top row, because the shell redraws its prompt there without a new mark. The redraw region starts at the prompt start for `redraw=1` and at the first row of the cursor's logical line for `redraw=last`. When the primary screen changes dimensions in the prompt state with `redraw` other than `0`, the engine reflows, clears the rows from the first row of the redraw region to the bottom of the screen, and moves the cursor to column 0 of the row that lies as many rows below that first row as the cursor lay below it before the reflow; it scrolls the screen up when that row is below the bottom. The reflow keeps logical lines, so the engine finds the first row again by the number of logical lines between it and the cursor. zsh redraws the whole prompt after `SIGWINCH` and bash (readline) redraws the last line of the prompt; both move up the cursor row count of the width at which they last drew, so they start again at the first row of the region, and the cleared rows leave no rows of the previous width. A prompt that ends its own line, such as a prompt of two lines or one that fills its last row, therefore keeps the output above it. The prompt start remains correct after the scrollback drops its oldest rows; when it no longer lies between the oldest history row and the cursor, the engine reports an error and clears nothing. When the size changes again before the shell has redrawn, the shell can draw at a width that is no longer current and overwrite rows above the prompt. A resize to the current dimensions changes nothing, because the PTY sends no `SIGWINCH` for it. A shell without integration sends no marks; its own redraw after a resize can leave rows of the previous width.

Erase in display 2 (`ESC[2J`) erases every cell of the screen with the current background and keeps the history and the cursor, so `clear`, which erases the history (`ESC[3J`) and then the screen, leaves nothing to scroll back to and no scrollbar. Erase in display 1 (`ESC[1J`) erases every line above the cursor and the cursor's line through the cursor cell. The engine applies both itself at their position in the output instead of passing them to its grid library, because the library moves the visible lines into the history on `ESC[2J` and keeps the first line on `ESC[1J` when the cursor is on the second line.

The sidecar draws a raster and sends the page's `screen` event together, and only after the host has answered `consumed` for the previous raster. Output, scrolling, and input that change the screen while the host holds a raster mark it as changed without drawing or sending; when the host answers, the sidecar draws the current screen once and sends that one `screen` event. A flood of output therefore produces one raster and one `screen` event per host answer instead of one per output chunk, so the page does not fall behind the output. A cell of the page's `screen` event carries `ch` when it has text, `width`, `link` when it is linked, and `bold`, `italic`, `underline`, and `inverse` only when they are set; it carries no colors, because the raster draws them.

The terminal raster follows the effective application appearance. The surface page sends `theme` to the terminal sidecar when it starts and whenever the application theme or mode changes, with `mode` (`dark` or `light`) and four colors taken from the theme tokens the page receives: `background` is `--card` and `foreground` and `cursor` are `--fg`, the colors of the card the terminal fills, so the terminal reads as part of its card like every other surface of the application; `selection` is `--rail`, the theme's accent rail, so selected text is visibly distinct from the card and its border. A theme has no separate surface colors: the shell page, the terminal, and the stand-in shown before a native surface draws all use `--card` and `--fg`, so no surface shows a color that nothing else in the application uses. The sidecar rejects another mode and any color that is not `#rrggbb`. The colors change the default background and foreground, the cursor, and the selection background (a selected cell keeps its text color on that background unless a program sets OSC 17 or 19 highlight colors); `mode` selects the indexed ANSI palette, which the theme does not change, because programs choose those colors for contrast with the standard palette. The page reports the applied mode and background in `terminal.session` as `theme` and `background`. The raster fills the image outside the cell grid, right of the last column and below the last row, with the current default background: the theme background, or the color a program set with OSC 11. The screen reports that color as `background`. These changes apply to subsequent and existing screen cells; it does not recreate the PTY, session, text, cursor position, or cell metrics. The mode is an image-surface property and is applied to the next complete frame; an in-flight transfer remains immutable.

The terminal tab shows the program title. The page reports an OSC 0 or OSC 2 title with `tab.title` and removes it on a title reset. The terminal setting `terminal.title` selects `program` (the default) or `name`; with `name` the page reports no title and removes a shown one, and changing back to `program` shows the last title the program set. A title that `tab.title` rejects is a session error. A cell inside an OSC 8 hyperlink carries its URI as `link` in the screen, and the raster underlines it as it underlines SGR 4 text. The pointer over a linked cell is a hand. A Command-click on a linked cell runs the declared command `terminal.link.open` with that URI, which opens it through `runtime.links.open` ([opening links](plugins.md#opening-links)); the click does not start a selection. A click without Command keeps the selection behavior. A URI that the host rejects is an input session error. The page passes each OSC 9 notification to `tab.notify` with the `terminal.notifications` policy (`tab` by default or `system`); a notification that it rejects is a session error. The `tab` policy shows a tab notice. The `system` policy sends only to the host notification center; if the host cannot provide it, the native error remains observable and the page does not fall back. The page records the directory of each OSC 7 event with `tab.directory`: the sidecar's `directory` event carries the URI and `path`, which is the percent-decoded absolute path when the scheme is `file` or `kitty-shell-cwd` and the host is empty, `localhost`, or this machine's host name, and `null` for a directory of another machine, which removes the recorded directory. A URI with another scheme or a relative or undecodable path is rejected as an engine error.

Cursor state includes position, visibility, shape, blink policy, and colors. The cursor policy is explicit: shape is `block`, `underline`, or `beam`; blink is `Never`, `Off`, `On`, or `Always`; interval is a positive millisecond value (default 750); idle timeout is a nonnegative millisecond value (default 5000, with zero disabling the timeout); and unfocused rendering is `hollow`, `solid`, `underline`, `beam`, or `unchanged`. Defaults are a filled block with `Off` blinking while focused and a steady hollow block while unfocused. `Never` and `Always` override the program blink request; `Off` and `On` permit it. A program cursor shape overrides the configured default. Program visibility is authoritative. The terminal module reports a policy in `terminal.cursor` after the sidecar answers the `cursor` operation, which it sends after it has presented the frame drawn with that policy. `terminal.cursor` also reports `drawn`: the shape (`block`, `underline`, `beam`, `hollowBlock`, or `hidden`) and blink request that the sidecar drew after the program's request and the focus rule. Every raster the sidecar presents carries the screen event of the screen it draws, so a focus change or any other redraw updates the position, focus, and `drawn` together with the pixels. Rendering changes only the cursor pixels: it has no fade or size animation and never recreates the PTY or changes cell metrics. The cursor covers the display width of the character at its position, including preedit text shown there: a wide character is covered by a two-cell cursor, and the cursor never extends past the last column. During preedit, a supplied `selectedRange.location` moves the drawn cursor to that UTF-16 grapheme boundary; the location at the end places it after the preedit. A location inside a grapheme is invalid. The cursor stays inside the final terminal column. A wide character whose glyph advance is narrower than its two cells, such as Hangul drawn from a substituted font, is drawn at its own size centred horizontally in the two cells; a glyph at least as wide as its cells starts at its first cell.

The policy is declared by the terminal plugin in `plugin.json`, receives the application's initial value from `environment.json`, and then follows the effective common/project settings. The workbench validates each value against the declaration before persistence, publishes the effective plugin-local settings to mounted terminal surfaces, and reports an explicit error without applying a partial patch when a value is invalid. A terminal surface sends the complete policy to its sidecar at startup and after every effective settings change.

Terminal-program clipboard access is separate from explicit user paste. The declared `clipboard.program` setting is `deny` or `allow` and defaults to `deny`. When denied, OSC clipboard store/query requests produce an observable policy error and do not write to the host clipboard or leave a pending query callback. When allowed, only the declared text clipboard target is handled; unsupported selection targets and absent/non-text values remain explicit errors. The user `terminal.paste` command is not subject to this program permission.

Native IME owns marked text. Preedit is displayed without writing partial syllables to the PTY. Committed text is delivered exactly once in the same ordered queue as ordinary input. Caret coordinates anchor the candidate window. Unsupported native text values and failed input operations are explicit errors.

The native input adapter distinguishes preedit from committed input through the text-input client's marked-text callbacks, not by inspecting Unicode ranges; the only exception is the commit timing for the macOS Korean input method described below. Every `insert` callback is forwarded byte-for-byte in order; a plugin must not silently discard or rewrite it based on script or code point. A platform adapter must use the OS text-input lifecycle and expose each committed callback exactly once. An empty `compose` callback clears or cancels preedit; it never commits the previous marked string. Only an `insert` callback commits text to the PTY. When the platform accepts marked text as input (on macOS, `unmarkText`), the adapter reports that text as one `insert`.

An input method may edit text it inserted earlier instead of using marked text; for example, the macOS Korean input method inserts `ㅎ` and then replaces it with `하` and `한` through replacement ranges, and it remembers the document position of the syllable it is composing. While the selected input source is an input method rather than a keyboard layout, the platform adapter therefore keeps the text that the input method inserted in its input document, applies replacements there, and reports the part that the input method can still edit as preedit. Text before the start of the latest insert is committed as one `insert`; committed text stays in the input document so positions do not change. The macOS Korean input method composes only Hangul letters (jamo and syllables) and, in this replacement protocol, sends no callback when a composition ends: Space or a digit after a syllable may leave both the syllable and the non-Hangul character in the editable suffix; earlier observed callbacks replaced the syllable with itself and then inserted the space or digit. While this input method is selected, the adapter therefore commits the editable suffix at once when its last character is not Hangul. This covers a final syllable and Space in one suffix, while a new Hangul jamo remains preedit. The rule decides only when text is committed; no input is discarded or changed. Other input methods keep the general rule. While uncommitted input-method text exists, a special key without Control or Option goes to the input method first, so Backspace edits the composition (`한` becomes `하`) as in a text view; when the input method does not handle the key, AppKit asks the client to perform the key's command, and the adapter then commits the remaining text and reports the original key instead of the command. If AppKit handles Enter by invoking `insertNewline:`, the terminal input path sends one Enter key after the committed text. AppKit’s `noop:` selector is consumed locally without changing or committing input, because its command has no effect. Other unsupported native command selectors are reported explicitly. Before any other special key, a command, focus loss, input-source change, or region close, the adapter commits the remaining text, ends the input method's composition, and clears the document. Text from a keyboard layout is committed immediately. A replacement of text that was already committed is reported as an explicit error. The adapter is an AppKit text view whose text storage is the input document. It turns off every text-system edit that the terminal does not declare: automatic substitution, replacement, spelling and grammar checking, detection, completion, and text checking types, undo, rich text, graphics, the find bar, the font panel, and the ruler; the Services menu cannot read or replace the input document, and pointer, menu, and drag input never target the view. A plain view that keeps its own document produced the same Korean result but, as the input client, left freed memory in use after regions closed, so the text view remains.

The terminal plugin declares `terminal.compose.update` in its `diagnostics.json` ([diagnostic declarations](plugins.md#diagnostic-declarations)), so it exists only in diagnostic builds. The command injects preedit that the OS input method otherwise produces. It is for explicitly setting the current preedit state through the same ordered sidecar path used by native callbacks. It accepts a string `text`, optional `selectedRange` and `replacementRange` values (`null` or nonnegative integer `{location, length}`), and optional boolean `attributed`; absent ranges are `null` and absent `attributed` is `false`. An empty string clears preedit. The command never writes PTY bytes. The existing `terminal.compose` status reports the effective preedit, and the native image presents each accepted update after the previous image transfer is consumed. This command validates preedit rendering and ordering; it does not substitute for real OS IME verification.

The terminal plugin also exposes an explicitly started, bounded IME diagnostic trace through the `terminal.ime.trace` command and status, declared in its `diagnostics.json`. While enabled, it records native `key`, `compose`, and `insert` callbacks and each corresponding ordered terminal input operation, preserving event order and text. Reaching the trace capacity fails the trace visibly; it does not silently discard events. Stopping the trace returns its entries and overflow state. The trace is disabled by default and is diagnostic evidence, not a substitute for the native-pixel composition check.

Selection, clipboard, paste, file drop, image paste, and terminal-generated image display are distinct operations. Pasted images are stored as owned files and their paths are inserted without automatic execution. The declared `terminal.paste` command is the only text-paste entry point. Edit > Paste (Command+V) and Paste and Match Style on a focused terminal region report a `paste` action that runs `terminal.paste` through the command registry; Edit > Copy (Command+C) reports a `copy` action that runs `terminal.copy`, which sends a `copy` request, and the sidecar answers with a `copy` event carrying the current selection text, which the terminal module writes to the clipboard with `userInitiated: true`, or with `copied: false` when there is no selection, which leaves the clipboard unchanged; the region never inserts pasteboard contents into its input-method document, and Cut, Select All, and Delete are disabled for it. The command reads the text clipboard through the scoped clipboard capability with `userInitiated: true`, rejects an absent or non-text payload explicitly, and sends one `paste` operation to the sidecar. It never converts a clipboard failure into empty input. Bracketed paste respects terminal mode, preserves the supplied UTF-8 payload byte-for-byte, and rejects an embedded bracketed-paste terminator instead of deleting it. The sidecar acknowledges the operation only after the complete payload is written once. No input is silently sanitized, discarded, or reordered. Terminal protocol support is recorded per sequence and reference revision; an unimplemented operation does not count as supported because its parser accepts it.

Wheel input over a terminal is a scroll gesture. The terminal page converts the DOM wheel deltas of its view to whole lines, accumulating pixel deltas by the cell height, and sends `{operation: "scroll", lines, col, row}`, where a positive `lines` moves toward older output and `col` and `row` are the pointer cell. The sidecar applies the first rule that matches the terminal modes: when mouse reporting (modes 1000, 1002, or 1003) is on, it writes one wheel button event per line (button 64 toward older output, 65 toward newer) at the pointer cell in the active mouse encoding (SGR 1006, UTF-8 1005, or the default); otherwise, on the alternate screen with alternate scroll (mode 1007) on, it writes one cursor-up or cursor-down key per line in the current cursor-key mode; otherwise it moves the primary-screen viewport through the scrollback by `lines`, limited to the retained history. The screen event shows the viewport, and the cursor is reported hidden when its row is outside the viewport. Keyboard input, text input, and paste return the viewport to the newest output before the bytes are written. `terminal.session` reports `scrollback: {offset, history}`, the number of lines the viewport is above the newest output and the number of retained history lines. Selection coordinates are viewport coordinates when the gesture happens.

While the terminal retains history (`scrollback.history` greater than 0), the terminal page shows a scrollbar in the declared DOM overlay `scrollbar` at the right edge of the view, above the native image; at the newest output its thumb is at the bottom of the track. The track is painted with the terminal's current default background, which the screen event reports as `background` (including a change by OSC 11), because the host cuts the native image out under the overlay. The thumb height is the track height times `rows / (rows + history)`, at least 16 points, and its top is at `(history - offset) / (rows + history)` of the track. The pointer over the thumb is an open hand, and a closed hand while the thumb is dragged. Dragging the thumb runs the declared command `terminal.scrollback.set` with the offset under the pointer, which sends `{operation: "viewport", offset}`; the sidecar moves the primary viewport to that offset, limited to the retained history, writes nothing to the program, and answers with a screen event. Without history the scrollbar is hidden. Four plugin settings configure it: `terminal.scrollbar.track` is `terminal` (the terminal's current default background, the default) or a color; `terminal.scrollbar.thumb` is the thumb color (default `#8f98a080`); `terminal.scrollbar.width` is the track width in points from 4 to 24 (default 10); and `terminal.scrollbar.shape` is `rounded` (default) or `square`. A color is `#rrggbb` or `#rrggbbaa`; any other value is reported as an input error and not applied. A change applies to the shown scrollbar at once.

Four plugin settings set the terminal padding: `terminal.padding.top`, `terminal.padding.right`, `terminal.padding.bottom` and `terminal.padding.left` are integers in points from 0 to 64 (default 0). The page insets the native image region `view` by them, so the cell grid takes the area inside the padding, and keeps the scrollbar at the right edge of that region. The ancestors of a native anchor have no background ([surface composition](surface-composition.md)), so the padding of each side is a declared DOM overlay strip (`padding-top`, `padding-right`, `padding-bottom`, `padding-left`) painted with the terminal's current default background; a strip of size 0 is hidden. Any other value is reported as an input error and not applied. A change applies at once.

Terminal selection is a native-region gesture, not a DOM text selection. The native region reports a left-button press, movement, and release in its CSS-local coordinates with modifier state; the sidecar maps those coordinates to the configured cell grid and owns selection state. Movement is a pointer move with the left button held; a move without it, such as the pointer location WebKit reports when the window becomes key, does not start or update a selection. After a press inside the view, the page moves a drag point outside the view to the nearest point inside it, because a drag to the start or end of a line crosses the view edge; a press outside the view does not start a selection. The sidecar maps the press and each drag point to the nearest cell edge of its row, so a selection covers a cell once the pointer passes the cell's horizontal midpoint, as in macOS Terminal; in either drag direction it covers the cells between the two edges, and the rendered selection covers exactly the cells whose text is copied. The region extends past the last whole column and row by less than one cell; a point in that padding maps to the last row and to the nearest edge, which past the last column is its right edge, and a point outside the region is an invalid coordinate. A normal drag creates a simple selection, updates the rendered selection pixels, and on release emits one explicit user-selection copy event containing the selected text. The terminal module writes that text through the scoped clipboard capability with `userInitiated: true`; the `clipboard.program` policy does not deny this user gesture. A release whose selection covers no text, such as a drag over blank cells, clears the selection, leaves the clipboard unchanged, and emits `selection.end` with `copied: false`; it is a normal gesture, not an error. A press and release without movement, such as a click, or a drag that does not pass a cell's midpoint, starts and ends an empty selection at one edge, so a click clears the previous selection. `terminal.session` reports `selecting` while a left-button gesture is in progress and counts the releases the sidecar answered, with a copy or with `selection.end`, in `selectionReleases`. Missing clipboard capability, invalid coordinates, a copy event without text, and failed writes are explicit errors. Selection input is never sent to the PTY and a DOM fallback is not used.

The page also sends every left-button press, movement while pressed, and release, and each movement without a button that enters another cell, as a `mouse` operation `{phase, x, y, pressed, shift, alt, ctrl}`. When the program has enabled mouse reporting, a press without Shift starts a reported gesture and clears any previous text selection: the sidecar latches that gesture's motion ownership at the press, then writes the press, the release, and, when the latched ownership includes ?1002 or ?1003, each movement into another cell while pressed. Changes to the child's mouse modes during the drag do not transfer ownership to text selection, and the selection operations of that gesture select nothing and are answered as usual. With ?1003 a movement without a button into another cell is reported as well. Every accepted pointer phase emits a `mouse` event and updates `terminal.session.mouse` with the phase, cell, modifiers, active report modes, whether a PTY report was selected, the write result, and exact base64 PTY bytes when present; an unreported phase is emitted with `reported: false` and `bytes: null` instead of being dropped. This is the measurement source for whether the child program received the gesture. Reports use the default encoding, UTF-8 coordinates with ?1005, or SGR with ?1006, and carry the Alt (8) and Control (16) bits; a coordinate the default encoding cannot represent is an explicit error. A press with Shift selects text while mouse reporting is on. The terminal view uses the text-selection pointer over raster text unless an OSC 22 pointer shape or a link changes it; slow movement must not briefly show the arrow pointer. The region reports only the left button. When the program has enabled focus reports (?1004), the sidecar writes `ESC[I` when the region gains native focus and `ESC[O` when it loses it, once per change. The region reports numeric-keypad keys by name (`Keypad0`–`Keypad9`, `KeypadDecimal`, `KeypadPlus`, `KeypadMinus`, `KeypadMultiply`, `KeypadDivide`, `KeypadEquals`, `KeypadEnter`) instead of passing them to the input method; after `ESC =` the sidecar sends an unmodified keypad key as `ESC O` followed by `p`–`y`, `n`, `k`, `m`, `j`, `o`, `X`, or `M`, and otherwise the key's character or carriage return.

## Session errors

`terminal.session.error` is the most recent unresolved error of the surface. The plugin keeps the latest error of each source, and an event of one source never removes the error of another. A snapshot source is resolved by the next valid event of the same kind; any other source stays until the surface closes, because no later event shows that the failed operation succeeded.

| Source | Error | Resolved by |
| --- | --- | --- |
| `state` | Invalid `state` event | Next valid `state` event |
| `session` | Invalid persistent `session` event | Next valid `session` event |
| `theme` | Invalid theme acknowledgement | Next valid `theme` event |
| `screen` | Invalid cursor in a `screen` event | Next `screen` event with a valid cursor |
| `trace` | IME trace capacity exceeded (diagnostic builds) | Starting a new trace |
| `sidecar` | Sidecar `error` event or error reply; the reply does not name the rejected operation | Not resolved |
| `native image` | Native image region `error` event | Not resolved |
| `input` | Failed input, paste, clipboard, or selection operation, and invalid one-time sidecar events | Not resolved |
| `key` | Native key event with non-boolean modifiers | Not resolved |
| `cursor` | Invalid cursor position from the sidecar | Not resolved |

The `sidecar` and `native image` sources also report the surface error that the card shows. Neither is resolved, so the card indicator and `terminal.session.error` show the error until the surface closes.

## Verification

- Record a failing baseline before each correction and run the same assertion after correction.
- Measure service processes, shell identities, PTY descriptors, attachments, and output sequences through creation, normal close, crash, and reconnection.
- Exercise at least three terminals in both native hosts. Capture complete fast divider gestures, unchanged glyph metrics, native clipping, coverage, and restored regions.
- Observe real native keyboard and IME input, not only injected committed strings. Test semantic state and displayed pixels independently.
- Keep loading, ready, and error distinct. Ready includes actual first native presentation, not only successful session creation.

Each mouse operation and its result carry the same non-empty `inputId`. The page assigns a fresh ID to every operation; a result for an earlier input cannot complete a later gesture. `written` means that the PTY write succeeded, not that the child consumed the bytes or rendered a selection. Diagnostic builds expose `terminal.pointer.trace` with `start` and `stop` actions and bounded ordered entries for DOM pointer/capture events, native focus notifications, queued mouse operations, and results. Overflow is explicit and invalidates the measurement. To separate a successful write from child receipt, the sidecar answers a `pty.pending` operation for the open session with `{event: "pty.pending", pending, written}`: `pending` is the count of master-written input bytes the child has not yet read, taken from the platform PTY input queue (FIONREAD on the master fd, which on macOS reads the tty shared by master and slave), and `written` is the cumulative count of child output bytes the session reader has read; one round trip returns both values from the same instant, and an error reply, including a missing session, carries the same `pty.pending` event marker so the reply identifies its request. Diagnostic builds expose the measurement as the `terminal.pty.pending` command, which resolves to `{pending, written}`, nonnegative integers, and rejects an explicit sidecar error. The queue is a transport observation: a canonical-mode line that has not been assembled yet is not counted, so a raw-mode child is the measured contract, and a drained queue proves delivery to the child, not that the program interpreted the bytes. Growth of `written` between two samples is the observable of the child having produced output, which separates program parsing from selection rendering.

Repeat acceptance uses the full-screen fixture TUI (`e2e/fixture-tui.mjs`), which enables `?1003` motion and `?1006` SGR reporting and draws its own selection, and OS pointer input: drag, click a third point inside the same TUI, then immediately drag again without refocusing or resetting state. Only after a failure may the check click another card and return to observe recovery; recovery never changes that failed attempt into a pass. Each host must pass three uninterrupted cycles, one per third-point region (input, output, blank), with the middle cycle at the slow speed; an intermittent failure is reproduced and accepted through the repeat target. Every gesture has correlated input results and complete capture measurements of its visible effect. Shift selection is a separate control.
