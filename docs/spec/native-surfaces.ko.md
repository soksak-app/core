# 네이티브 표면 배치

[English](native-surfaces.md)

승인된 단일 DOM 모델은 [표면 합성](surface-composition.ko.md)과 [플러그인 모듈](plugins.ko.md#표면-소유권)이 정의한다. 논리 표면은 WebView가 아니다. 네이티브 창 상태는 그리기 순서가 아닌 등록한 네이티브 뷰로 앱 DOM을 식별하며 문서 WebView는 앱 DOM 아래에 있다. `appDomWebviews`와 `documentWebviews`는 네이티브 계층에서 측정한다. 상수를 개수로 보고하거나 첫 자식을 메인 뷰로 추정해서는 안 된다. [기능 상태](../features.ko.md)는 통합과 검증을 분리하여 기록한다.

이 명세는 예제 애플리케이션의 표면 배치를 정의한다. 구현 및 검증 상태는 [기능 상태](../features.ko.md)에 기록한다.

## 책임

- 배치 라이브러리는 카드 사각형을 계산하고 카드 DOM 요소를 갱신한다.
- 예제 컴포지터는 카드 사각형과 DOM 내부 여백으로 표면 사각형을 계산한다.
- 호스트는 네이티브 뷰를 생성하고 표면 사각형을 적용한 뒤 실제 좌표를 반환한다.
- macOS 표시 처리는 창의 단일 앱 DOM이 표시를 확인하고 보이는 모든 그림 영역에 정확한 현재 래스터가 준비된 뒤 네이티브 좌표를 커밋한다.

호스트는 DOM과 네이티브 렌더링의 차이가 최대 한 프레임이라고 가정하지 않는다.

## 배치 순서

1. 카드 DOM을 갱신하기 전에 페이지가 다음 표면 사각형을 제출한다.
2. 호스트는 해당 창의 배치를 위해 UI 스레드의 레이어 트랜잭션 사용을 시작하고 네이티브 사각형 전체를 적용한다. 응답에는 실제 좌표와 준비 전체의 식별자 하나를 포함한다.
3. 준비가 완료되면 페이지가 카드 DOM을 갱신하고 해당 식별자의 표시를 요청한다.
4. 창의 앱 DOM이 표시를 확인하고 필요한 그림 래스터가 준비되면 호스트가 트랜잭션을 커밋하고 실제 좌표를 반환한다. [문서 영역](#문서-영역)은 독립적으로 렌더링하며 URL 출처와 무관하게 DOM 표시 대기에 참여하지 않는다.
5. 응답 후 페이지가 대기 중인 최신 배치의 준비를 시작한다. 시작하지 않은 이전 배치는 더 새 배치로 대신되며, 대신된 배치의 준비와 그리기는 실행되지 않는다. 가장 새 배치는 앞선 입력을 모두 담는다. 표시가 정착하면 페이지는 대신된 배치의 수를 애플리케이션 로그에 기록한다.

워크벤치 배치 콜백은 대상 표면의 식별자·흐림·대상 슬롯 여백을 카드 사각형과 함께 캡처한다. 대상 여백은 측정한 슬롯에서 이전에 그린 사이드바 영역을 빼고 요청한 카드 상태의 영역을 더한다. 컴포지터는 이전 사이드바 배치를 다시 읽지 않고 캡처한 기하를 사용한다. 측정할 수 없는 기존 슬롯은 null로 명시하고 준비 동안 숨긴다. 잘못된 여백 값은 오류다.

페이지는 현재 compositor record에 없는 보존 surface도 host placement request에 포함할 수 있다. 페이지는 전체 request의 모든 ID를 기준으로 host 응답을 검증한다. 각 요청 ID는 배치되거나, 그려지지 않은 preparation 중에만 deferred되어야 하며, 누락·추가·중복 ID와 잘못된 deferred ID는 오류다. 현재 compositor record를 기록하기 전 검증된 응답을 해당 record의 ID로 투영한다. Record 밖의 보존 surface는 retention 경로가 소유하며 활성 compositor 배치로 기록하지 않는다.

Host는 비동기 view-module loading과 composition 확인 전에 `surfaces.place` 호출을 호출 순서대로 직렬화한다. 뒤의 layout은 준비 중인 앞 placement를 앞지를 수 없다. Placement가 거부되어도 그 turn을 해제하고 오류를 caller에 전달하며 이후 placement를 막지 않는다.

Workbench는 현재 page가 소유한 surface로 요청을 구성한다. Initial project context가 commit되고 startup layout이 presentation된 뒤에 authoritative placement consumer를 등록한다. 이후 current compositor record를 발행한 뒤 후속 placement에서 이 consumer를 사용한다. Startup layout presentation이 실패하면 이미 보고된 layout error를 유지하고 consumer를 등록하거나 첫 record를 발행하지 않는다. Start snapshot에서 그린 project preview는 아직 host가 소유하는 project 상태가 아니며, 불완전한 surface 목록을 보내면 보존된 native surface가 제거될 수 있다. 아직 undrawn compositor record에 없는 활성 tab은 dormant로 취급하지 않고 drawn record에서 보낸다. 이미 mount된 활성 view라면 undrawn 요청에도 보이지 않는 surface로 포함한다. 아직 mount되지 않았다면 drawn placement까지 요청을 미룬다. 이미 mount된 dormant view는 host가 native handle을 유지하도록 요청에 남긴다. Undrawn record 밖의 cold view는 drawn placement까지 기다리며, preparation이 이를 생성하거나 배치하면 안 된다. Drawn placement 전에는 project tab state store가 성공적으로 열리고 memory saver가 startup tab을 분류할 때도 기다린다. Tab state open 실패는 placement를 거부하며, 별도 tried 신호는 tab state 호출이 store 미사용 상태를 보고하도록 계속 resolve한다. `surface.unload`를 선언한 plugin의 hidden tab은 memory saver가 startup 시 unloaded로 분류하면 host request에서 제외하며 tab은 state와 함께 layout에 남긴다. Background 선언이 없는 loaded hidden view는 hidden workbench slot에서 mount하고 listener를 설치한 뒤 composition을 선언해야 host에 placement를 보낼 수 있다. Background 선언이 있고 아직 mount되지 않은 view는 background session이 소유하며 native view를 만들지 않는다. 요청에 포함한 모든 view에는 host composition barrier를 계속 적용한다.

네이티브 표면을 대기 중인 사각형들의 교집합으로 일시 축소하지 않는다. 다음 슬롯과 일치하지 않는 표면은 DOM 변경 전에 숨긴다. 페이지가 다음 슬롯을 잰 표면은 준비 동안 새 사각형에 보인 채로 둔다. 준비의 변경은 창의 열린 트랜잭션 안에 있어 화면에 나오지 않으며, 그때 표면을 숨기면 화면에 아직 그 표면이 보이는 자리의 누름이 표면 대신 페이지로 간다. 그리기 후 측정으로 새 사각형을 제공한다. 첫 응답자를 담은 뷰를 숨기면 AppKit은 첫 응답자를 다른 뷰나 창으로 옮기므로, 배치 중에 숨긴 표면은 키보드 소유자를 기록하고 다시 보일 때 포커스를 그 소유자에게 되돌린다. 숨긴 동안 포커스가 옮겨졌으면 되돌리지 않는다.

`hidden` 속성을 가진 요소 안의 표면은 마운트를 유지하지만 표시하지 않는 상태로 제출한다. 카드 전체 화면은 이 속성으로 다른 카드를 숨기며, 원래 배치를 복원할 때까지 해당 표면과 세션을 유지한다.

폭 또는 높이가 0인 네이티브 슬롯은 표시 영역이 없으므로 표면을 제거하지 않고 숨긴 상태로 제출한다. 영역이 다시 생기면 표시를 복원한다.

기존 표면을 숨길 때 적용된 네이티브 프레임과 이미지 스냅샷을 보존한다. 표시하지 않는 요청의 빈 사각형은 1×1 대체 뷰포트가 아니다. 바깥 표면이 숨겨져 있으면 공급자에게 래스터 설정을 보내지 않는다. 다시 표시할 때 보이는 사각형을 적용하고 필요한 경우 정확한 결과 래스터를 설정한다. 새로 부착한 숨긴 표면도 표시 배치를 갖기 전에는 그림 렌더링을 시작하지 않는다. 페이지는 호스트가 카드의 사각형을 적용하기 전에 새 카드를 그리므로, 표면 페이지는 준비가 표면에 네이티브 프레임을 주기 전에 보이는 그림 영역을 배치할 수 있다. 이런 영역은 래스터 크기가 없고, 호스트는 준비가 표면을 배치할 때 그 영역을 설정한다. 배치된 표면 안의 보이는 영역에 래스터 크기가 없으면 오류다.

바깥 표면의 사각형을 적용하면 페이지에 준비 응답을 돌려주기 전에 필요한 이미지 설정을 시작한다. 이미지 렌더링은 DOM 그리기·표시와 병행할 수 있다. 문서가 앵커 여백을 바꿀 수 있으므로 최종 표시 검사는 DOM 표시 후 네이티브 래스터 좌표를 다시 읽는다. 병행 준비가 오래된 래스터의 커밋을 허용하지는 않는다.

페이지는 해당 DOM을 그리기 전에 네이티브 준비 응답을 기다린다. 비동기 준비 요청을 시작한 것만으로 네이티브 트랜잭션이 시작됐다고 볼 수 없다. 페이지는 그 DOM을 응답이 도착한 자리가 아니라 응답 뒤 다음 task 에서 그린다: 응답은 ResizeObserver callback 의 checkpoint 를 포함한 어느 microtask checkpoint 에서든 도착할 수 있고, 거기서 그리면 관찰 round 가 이미 전달한 요소가 바뀌어 WebKit 이 그 관찰을 다음 frame 으로 미루고 ResizeObserver loop 오류를 낸다. task 는 rendering update 와 그 관찰 round 안에서 실행되지 않는다. 페이지는 그 뒤 호스트에 그리기의 표시를 기다리게 하고, 그 기다림은 곧바로 rendering update 를 시작해 그리기를 담으므로, 그리기는 animation frame 처럼 화면 갱신을 기다리지 않는다. 그 task 전에 배치 세대가 바뀌면 그리기를 취소한다. 준비가 거부되면 해당 DOM을 바꾸지 않고 오류를 전파한다. 실패한 준비는 시작한 트랜잭션을 남기지 않는다: 호스트는 트랜잭션을 시작하기 전에 창 덮개를 놓으므로 거부된 덮개는 트랜잭션을 시작하지 않고, 준비의 뒤 단계가 실패하면 시작한 트랜잭션을 취소한다. 준비 중 페이지 배치 세대가 바뀌면 이전 DOM 그리기를 취소한다.

이전 표시 확인은 이후 준비의 트랜잭션을 커밋하지 않는다. 메인 문서 탐색은 해당 창의 활성 준비와 대기 중인 준비를 취소한다. 네이티브 호출은 UI 스레드에서 실행하며 WebKit 응답을 기다리는 동안 UI 스레드를 차단하지 않는다.

창의 트랜잭션이 열린 동안에는 그 창의 어떤 변경도 화면에 나가지 않고, 같은 창의 새 준비는 열린 트랜잭션을 연장한다. 따라서 창의 표시 상태 대기(`host.window.presented`)는 그 창의 열렸거나 대기 중인 모든 준비가 커밋된 뒤의 표시 갱신이 끝나야 완료되며, 그 갱신 뒤 화면의 다음 갱신 목표 시각을 보고한다.

앱 배경의 페인트 구멍은 호스트가 해당 DOM을 그린 배치의 표시를 확인한 뒤에만 바뀐다. 준비 응답은 표시 확인이 아니다. 확인 뒤 기존 한 애니메이션 프레임 지연을 유지하고 해당 표시 스냅샷의 네이티브 적용 사각형·표시 여부를 뷰포트 좌표로 사용한다. 새 진행 중 DOM 배치는 자신의 표시가 확인되기 전에 이 구멍을 바꾸지 않는다. 배치 좌표 변환은 네이티브 표시 여부를 보존한다. 요청한 네이티브 표면, 불리언 표시 여부 또는 유한한 좌표·음수 아닌 크기가 없는 확인 응답은 명시적 오류이며 페인트 구멍 갱신을 예약하지 않는다.


표면은 호스트가 적용한 프레임을 유지한다. 웹 인스펙터는 메인 문서 웹뷰만 켜며, 그것을 붙이면 그 웹뷰의 크기가 바뀔 뿐 표면은 움직이지 않으므로 호스트는 바깥 변경에 맞서 표면 프레임을 붙잡지 않는다.

레이어 트랜잭션은 UI 스레드에서 공유한다. 다른 프로젝트 창의 준비는 현재 창의 커밋 또는 취소까지 대기한다. 창을 다시 로드하거나 닫으면 해당 창의 활성 준비와 대기 중인 준비만 취소한다. 대기 요청은 UI 스레드를 차단하지 않는다.

호스트는 네이티브 뷰의 좌표를 관리한다. 각 콘텐츠 웹뷰는 문서를 독립적으로 렌더링한다. 웹 문서 렌더러의 지연이 메인 창의 배치 갱신을 중단시키지 않아야 한다.

앱 DOM에는 모든 플러그인 DOM이 마운트된다. 앱 DOM의 표시 콜백은 해당 DOM 평면을 확인하며 다른 웹뷰의 콘텐츠를 확인하지 않는다. 문서 영역은 콘텐츠를 독립적으로 렌더링하며, 표면의 하위 뷰이므로 네이티브 프레임은 트랜잭션에서 카드 좌표를 따른다. URL 출처 비교로 표시 소유권을 정해서는 안 된다.

view 표면은 호스트가 해당 네이티브 표면 핸들을 준비한 뒤에만 승인한다. 승인 알림은 현재 표면 세대마다 정확히 한 번 전달되며, 그 전에는 view가 합성을 선언하거나 이미지 영역을 붙이거나 사이드카 세션을 열 수 없다. 승인이 없다고 무기한 불러오는 중 상태를 유지해서는 안 되며, 호스트는 작업 제한시간 안에 귀속 가능한 오류를 보고해야 한다.

예제는 장치 픽셀 단위 배치를 유지하며, 배율이 2인 화면에서는 0.5 CSS 픽셀 크기를 포함한다. 카드, 구분선, 디바이더와 준비된 표면 사각형에 같은 격자를 적용한다. 렌더링된 콘텐츠는 푸터 앞에 빈 영역 없이 네이티브 표면을 채워야 한다. 배치 정밀도를 낮추거나 네이티브 배경색을 변경하는 것은 이 요구사항을 충족하지 않는다. 설정과 메뉴의 투명도는 별도로 설정한다.

macOS 콘텐츠 웹뷰는 장치 픽셀을 좌표 단위로 사용하는 공통 네이티브 컨테이너에 배치한다. 호스트는 네이티브 뷰 계층을 통해 창 사각형을 변환한다. 각 콘텐츠 웹뷰의 페이지 줌은 화면 배율과 같고, 로컬 좌표 한 단위는 backing 픽셀 하나다. CSS 크기와 장치 픽셀 배율을 유지하면서 정수 단위의 네이티브 렌더링 크기를 제공한다. 창 크기와 화면 배율이 변경되어도 이 변환을 유지한다. WebKit은 휠 이동량을 뷰의 좌표 단위로 쓰므로, 앱의 이벤트 모니터와 네이티브 스크롤 입력은 컨테이너 안 웹뷰로 가는 휠 이벤트의 이동량에 화면 배율을 곱한다. 스크롤은 모든 배율에서 포인트와 같은 수의 CSS 픽셀만큼 문서를 움직인다. 메인과 모달 웹뷰는 창의 포인트 좌표를 유지한다.

[비공개 네이티브 API 목록](../operations/private-native-apis.ko.md)에 좌표·표시·입력 의존성, 필요성, 네이티브 업데이트 후 우선 검토 절차를 기록한다.

그림 표시를 기다리기 전에 호스트는 표시 중인 모든 그림 영역의 실제 네이티브 래스터를 읽고 필요한 설정을 보낸다. 영역은 요소 크기나 인셋이 바뀌지 않고도 표시될 수 있으므로 이 검사는 새 DOM resize 알림에 의존하지 않는다. 설정 묶음 전송이 실패하면 오류를 보고하고 보내지 않은 모든 설정의 전송 예약을 해제해 다음 명시적 작업에서 설정할 수 있게 한다. 보내지 않은 작업을 완료로 처리하지 않는다.

바깥 표면은 문서 세대와 별개로 표시 상태를 소유한다. 문서의 첫 로드나 이동을 위해 그림 영역을 제거해도 이 표면 상태를 제거하면 안 된다. 바깥 표면 자체가 닫힐 때만 표시 상태의 소유권을 끝낸다.

## 제목줄 높이

창 제목줄은 배치 트랜잭션에 들어가므로, 창 단추는 페이지의 첫 행을 그리는 표시 프레임에서 함께 움직인다([창 단추](hosts.ko.md#창-단추)).

- 모든 준비는 `titlebar` 를 담는다. 준비 뒤에 오는 그리기가 끝나면 페이지가 보이는 첫 행의 높이(point)이며, 그 그리기의 프레임 배율에 대해 `round(max(40, 36 × 프레임 배율))` 이다. 그리기 뒤에 보내는 준비는 그린 행의 높이를 담는다.
- 호스트는 트랜잭션을 시작하기 전에 요청의 나머지와 함께 높이를 검사한다. 창의 트랜잭션을 시작한 뒤, 표면을 놓고 준비에 답하기 전에 창의 제목줄을 그 높이로 정하므로, 새 높이는 DOM 프레임의 커밋과 함께 화면에 나간다. 높이를 정하지 못하면 시작한 트랜잭션을 취소하고 그 오류로 준비를 실패시킨다. 준비의 뒤 단계가 실패하면 제목줄을 준비 전의 높이로 되돌린 뒤 트랜잭션을 취소한다. 취소는 트랜잭션을 커밋하므로, 되돌리지 않으면 새 제목줄이 이전 행과 함께 표시되기 때문이다.
- 준비의 답은 `chrome` 을 담는다. 호스트가 높이를 정한 뒤의 창 단추 영역과 제목줄 높이이며, `windowControls` 답의 형태(`{controls, row}`)다. 검증 W 는 첫 행을, 호스트가 표시를 확인한 가장 최근 준비의 `chrome` 에 있는 단추 영역, 곧 커밋된 상태와 비교하고 이전의 `windowControls` 답과 비교하지 않는다.
- 프레임 배율의 변경은 준비한 배치가 그린다. 페이지는 새 배율을 설정이 바뀔 때가 아니라 그 배치의 그리기에서 문서에 쓴다. 배치를 준비하기 전에 같은 task 안에서 배율을 쓰고, 판을 읽고, 그린 배율을 다시 써서 새 배율이 주는 판 크기를 잰다. 그 사이에 문서는 아무것도 렌더링하지 않고, 준비의 카드 사각형은 새 행에 맞는다. 판이 없는 창(라이브러리)은 높이를 담고 표면이 없는 준비로 배율 변경을 그린다. 라이브러리로의 전환도 같은 방식으로 그린다. 그 준비는 현재 배율의 행을 담고, 그 그리기는 판을 지우고 그 배율을 쓰고 라이브러리 화면을 보인다. 라이브러리 화면은 작업 영역을 숨기므로 ResizeObserver 가 관찰하는 그 요소가 0×0 이 된다. 이 화면은 그 그리기, 곧 준비 뒤 관찰 round 밖의 task 에서 보이며, WebKit 이 ResizeObserver callback 의 microtask checkpoint 에서 실행할 수 있는 이후 호스트 답의 반응에서 보이지 않는다. 전환은 그 전에 준비한 배치의 그리기를 취소하고(배치 epoch 가 바뀐다) 그 그리기가 새 배율을 쓰는 그리기였을 수 있다. 전환이 현재 배율을 그리므로 취소된 그리기의 배율은 사라지지 않는다.
- 전체 화면인 창은 제목줄을 보이지 않는다. AppKit 은 창이 전체 화면에 들어갈 때 제목줄 높이를 저장하고 지우며, 나올 때 저장한 높이를 되돌리므로 그 사이에 정한 높이는 바뀐다. 그래서 호스트는 창이 전체 화면인 동안 준비에서 제목줄을 바꾸지 않는다. 준비는 성공하고 그 `chrome.row` 는 0 이다.
- 페이지의 첫 그리기는 준비를 기다리지 않으므로([페이지 시작](native-host.ko.md#page-시작)) 제목줄은 그 그리기의 행을 이미 가져야 한다. 호스트는 창 페이지의 시작 문서에 답하기 전에, 보내는 작업 공간 스냅샷의 공통 설정 `textSize` 에 대해 창의 제목줄을 `round(max(40, 36 × textSize))` 로 정하고(설정이 없으면 40), 문서의 `controls` 는 그 뒤에 읽는다. `textSize` 는 공통 전용이므로([설정](projects.ko.md#저장)) 페이지는 같은 값으로 첫 행을 그린다. 아직 보이지 않는 창, 곧 첫 페이지가 표시될 때까지 투명한 새 창은 이전 페이지를 보이지 않으므로 호스트는 높이를 바로 정하고, 첫 보이는 프레임의 행과 제목줄은 같은 배율의 것이다. 보이는 창은 다시 읽기처럼 새 페이지가 첫 그리기를 표시할 때까지 이전 페이지를 보이므로, 호스트는 시작 트랜잭션 안에서 높이를 정한다. 페이지 시작이 창의 활성 준비와 대기 중인 준비를 취소한 뒤, 새 ticket 으로 창의 준비 하나인 배치 트랜잭션을 시작하고, 그 안에서 제목줄을 정하고, 시작 문서에 답한다. 메인 웹뷰의 읽기가 끝나고 그 다음 표시 갱신이 끝나면, 곧 첫 그리기가 표시되면 그 트랜잭션을 커밋한다. 시작 트랜잭션이 열린 동안 도착한 새 페이지의 준비는 그 트랜잭션을 연장하고 자기 표시와 함께 커밋하며, 그때 시작 커밋은 ticket 이 바뀐 것을 보고 아무것도 커밋하지 않는다. 높이를 정하지 못한 시작 트랜잭션은 취소하고 그 오류로 시작을 실패시킨다. 열린 트랜잭션은 새 페이지를 막지 않는다. 새 WebContent 프로세스는 창의 트랜잭션이 열린 동안 첫 화면을 그려 표시하고 표시 갱신은 끝난다([`window_titlebar_reload_test.m`](../../native/darwin/tests/window_titlebar_reload_test.m)). 0.5 이상 3 이하의 수가 아닌 `textSize` 는 `common setting textSize must be a number, not <type>` 이나 `common setting textSize must be from 0.5 through 3` 으로 시작을 실패시킨다. 창이 전체 화면인 동안에는 준비에서처럼 제목줄을 바꾸지 않는다.
- 창이 전체 화면에서 나올 때 AppKit 은 들어갈 때 저장한 높이를 되돌리며, 전체 화면 동안 프레임 배율이 바뀌었으면 그 높이는 행과 다르다. 페이지는 창 크기가 바뀔 때마다 `windowControls` 를 읽고, 전체 화면에서 나오면 창 크기가 바뀐다. 답에 제목줄이 있고(`row` 가 0 보다 큼) 그 높이가 현재 프레임 배율의 행과 다르면, 페이지는 그 행을 담은 배치를 준비하고 그 준비가 마지막으로 보낸 요청과 같아도 보낸다.

## view 표면

view는 `view` 합성을 가진 표면의 native 웹뷰다([plugins](plugins.ko.md#view-표면)). 각 view는 탭마다 하나의 웹뷰이며 `soksak://<plugin id>` origin에서 그 plugin의 페이지를 실행한다. 워크벤치 페이지는 plugin 코드를 실행하지 않는다.

워크벤치는 mount 전에 tab에서 활성 surface descriptor를 만들고 compositor의 placement record까지 같은 descriptor를 보존한다. Dormant surface는 저장된 `params`를 포함해 저장 tab에서 descriptor를 만든다. Host request는 이 descriptor에서 계산한 view start values를 기존 `start` member에 담으며 별도 `params` member를 추가하지 않는다. Slot이 placeholder가 되면 surface descriptor도 더 이상 제공하지 않는다.

- **구성.** 호스트는 view를 다음을 가진 웹뷰 구성으로 만든다.
  - `isView` 설정. 이 구성만 `core` scheme을 core root resolver로 보낸다([문서 영역](#문서-영역));
  - 표면 plugin의 plugin id. view의 origin과 core root 응답의 `Access-Control-Allow-Origin`을 정한다. 요청은 plugin id를 제공하지 않는다;
  - `packages/plugin-api/view-start.js`의 text를 담은 document-start 사용자 script. view channel script이며 staged 사본에서 가져온다;
  - view import map: native view handler가 view 구성 페이지의 doctype 뒤에 넣으므로 view 페이지는 자기 import map을 갖지 않는다([plugin 처리](plugin-processes.ko.md), rule 4);
  - 테마 토큰을 담은 document-start 사용자 script(아래 테마 참조);
  - surface의 시작 값을 담은 document-start 사용자 script(아래 시작 값 참조);
  - [호스트 계약](host-contract.ko.md)이 이름으로 선언한 script message handler `sok-view`;
  - 그 plugin의 영구 website data store. plugin id로 구분하며, 문서 영역의 store와 같이 설정 디렉터리의 `document-data` 아래에 둔다([문서 영역](#문서-영역)).

  두 document-start script는 모든 페이지 script보다 먼저 실행된다. 둘은 서로에 의존하지 않으므로 주입 순서는 이 계약의 일부가 아니다.
- **load.** 구성을 만든 뒤 호스트는 `soksak://<plugin id>/<page>`를 load한다. `<page>`는 합성의 `page`다. view의 파일은 문서 영역에 주는 plugin 파일과 같이 제공한다([문서 영역](#문서-영역)). 즉 `plugins/installed.json`이 기록한 폴더에서 가져오며, 같은 거부와 log 줄을 쓴다. view는 core root `soksak://core/<path>`를 [문서 영역](#문서-영역)의 규칙과 [plugin process](plugin-processes.ko.md) 규칙 4의 grant 규칙에 따라 요청한다.
- **배치.** view의 frame은 card 사각형과 요소의 DOM inset에서 합성기가 구한 표면 사각형이다. 모든 표면의 outer surface와 같다([배치 순서](#배치-순서)). native view를 만들 수 있는 배치를 보내기 전에 workbench는 해당 surface의 첫 view call을 처리하는 main-page listener를 등록하고 composition을 선언할 때까지 기다린다. 호스트는 현재 main-page document가 그 surface의 plugin과 composition을 선언한 경우에만 view 배치를 허용한다. Page reload는 기존 선언을 폐기하며 교체 page가 배치 전에 다시 선언한다. 호스트는 그 frame을 card의 transaction에 적용하므로, 매 frame마다 view와 card가 함께 움직인다. view의 웹뷰는 plane의 하위가 아니라 표면 host에서 native plane 아래에 있는 하위 view다. view의 선언된 overlay는 view 자신의 DOM이 그리므로, plane의 overlay mask는 view의 영역만 자르고 보이는 overlay 아래의 입력은 view 웹뷰로 간다. `hidden` 속성이 있는 요소 안이거나 너비나 높이가 0인 view는 보이지 않음으로 제출하며, 다른 표면과 같이 웹뷰와 process를 유지한다. 준비 중에는 surface host를 숨긴 상태에서 view를 배치할 수 있다. surface를 표시할 때는 host를 먼저 표시한 뒤 view와 native region의 요청된 표시 상태를 다시 적용하며, 명시적으로 숨겨 배치한 view는 계속 숨긴다.
- **영역.** view는 [view bridge](plugins.ko.md#view-표면)의 `composition.create({regions, overlays})`로 선언된 영역과 overlay의 composition을 만든다. key는 선언과 같고 값은 view document의 element다. controller는 각 element의 inset을 view frame인 view의 viewport에 대해 재고, 완전한 snapshot을 제출한다([surface composition](surface-composition.ko.md#페이지-api)). 각 동작은 아래 view call 경로의 view call로 보내며, 메인 page는 hybrid composition이 쓰는 것과 같은 표면의 page 동작으로 그것을 실행한다:
  - `composition.declaration`은 표면에 선언된 `{kind, regions, overlays}`를 돌려주며, 없는 `regions`와 `overlays`는 빈 배열이다.
  - `composition.place`는 `{regions, overlays}`로 완전한 snapshot 하나를 배치한다. 메인 page는 그것에 자기 document의 composition revision 번호를 매기고, 표면을 빼는 place가 실행되는 동안에는 배치를 보내지 않는다([영역 수명](#region-lifetime)).
  - `document.attach`는 `{name}`으로 memory saver의 영역 기록을 거쳐 붙으므로 영역은 저장된 interactionState를 한 번 복원하고, `{history}`로 답한다([memory saver](plugins.ko.md#메모리-절약)). `document.load` `{name, url}`, `document.zoom` `{name, zoom}`, `document.go` `{name, action, offset?}`, `document.post` `{name, message}`, `document.subscribe` `{name, stream}`, `document.unsubscribe` `{name, handle}`, `document.detach` `{name}`은 표면의 document 동작을 실행한다.
  - `image.attach` `{name, sidecar}`, `image.focus` `{name}`, `image.caret` `{name, x, y, width, height}`, `image.text` `{name, text}`, `image.detach` `{name}`은 표면의 image 동작을 실행한다.
  - `composition.report`는 text로 composition의 실패를 표면의 `report` 호스트 호출로 알린다.

  view는 영역 이벤트를 `runtime.native.on`으로 `document-state`, `document-message`, `document-stream`, `image-event` 이름에 대해 받는다. page는 받은 순서대로 view에 전달하며, 앞선 event 전달이 pending인 동안 뒤 event 전달을 시작하지 않는다. 호스트는 view call을 보낸 view의 표면과 함께 전달하고, 메인 page는 그 표면의 범위에서만 call에 답한다. 모든 호스트 호출을 그 표면으로 보내고 params의 이름 붙은 field만 넘긴다. 그래서 영역을 배치하거나 바꾸는 호출마다 호출 envelope의 view id로 확인되며, view는 다른 view의 영역을 조작할 수 없다. composition이나 영역의 호스트 호출 이름(`compositionDeclare`, `compositionPlace`, 각 `document`·`image` 호스트 호출)을 가진 `runtime.native.call`은 `view call runtime.native.call <name> is not served: a view operates its regions through its composition`으로 거부된다. 그 호출은 revision 번호 매김, 영역 수명, 영역 기록을 건너뛰기 때문이다. 영역은 view의 표면 host 아래, view 위에 배치되며 inset은 view frame에 상대적이다. 호스트는 inset을 저장하고 view의 frame이 바뀔 때 같은 native transaction에서 다시 적용하므로, 영역의 표시는 view frame과 같은 window transaction에 있다([plugin processes](plugin-processes.ko.md) 규칙 6과 9). view process가 끝나면 호스트는 view를 다시 만들기 전에 표면의 document·image 영역을 닫는다. 그 영역은 끝난 document의 composition에 속하기 때문이다. 새 view는 composition을 다시 만든다. 호출과 view event는 수신 시점의 view document에 귀속된다. `view-process-ended`가 오면 page는 pending call reply와 event delivery를 취소하고 해당 document의 구독을 끝내되, host 재시작을 위해 surface는 mounted 상태로 둔다. 종료된 document의 handler나 callback은 재시작한 document가 ready가 된 뒤에도 취소 상태를 유지한다. 재시작한 document는 구독을 다시 등록하며, 활성 document의 거부는 계속 오류로 보고한다.
호스트는 각 native message callback을 이를 설치한 view document의 local identity에 귀속한다. Document를 닫거나 교체하면 native resource를 해제하기 전에 identity를 retire한다. Retire된 identity의 callback은 current view channel을 바꾸거나 main page에 도달할 수 없으며, performance trace가 켜져 있을 때 호스트는 `host.trace.view.callback-cancelled {surface, reason}`을 기록한다. 해당 document가 보낸 `view.error`는 callback이 캡처한 plugin과 surface를 사용해 오류로 기록한다.

각 view source는 window 범위 generation도 받는다. Host는 native view channel을 기록하고 첫 provider message callback을 연결하거나 page를 load하기 전에 `declared-ui-source-registered {plugin, surface, generation}`을 보낸다. Snapshot, call, reply, end metadata에는 이 generation이 포함된다. View를 retire할 때 캡처한 generation으로 `declared-ui-source-ended`를 보내며, 이 event는 replacement view의 source를 제거할 수 없다. Main page는 원자적인 `declaredSourceOrigins` query로 현재 instance를 seed하고 listener를 설치한 뒤 받은 lifecycle event를 적용한다.

View surface mount는 native view 생성을 시작하는 composition을 선언하기 전에 native listener를 설치한다. 따라서 mount 시작 시 source generation이 없을 수 있다. Workbench는 이 상태에서 generation을 만들거나 mount를 거부하지 않는다. Ordered source registration으로 current generation을 확인한 뒤 view command와 subscription을 연결한다. Call은 현재 generation을 담은 경우에만 처리한다. Workbench는 document 수명에 accepted generation을 캡처하므로 `declared-ui-source-ended`가 current-origin map에서 source를 제거한 뒤 도착하는 `view-process-ended`도 처리할 수 있다. 이후 registration은 캡처 generation을 갱신하며, 이전 generation의 늦은 end는 replacement를 지울 수 없다. 종료된 document의 callback은 replacement 등록 뒤에도 취소 상태를 유지한다.

- **플러그인 host 호출.** plugin 페이지(view 또는 DOM surface)의 native 핸들은 허용 목록의 host 명령 `exposureReply`만 보내고, 명시 목록의 native event만 구독한다. 이 목록은 `packages/workbench/view-calls.js`의 `PLUGIN_NATIVE_EVENTS`로, region event `document-stream`, `document-state`, `document-message`, `image-event`와 view exposure의 선언된 경로인 `exposure-request`([exposure](exposure.ko.md#전달))를 담는다. 이 밖의 event 이름은 구독할 수 없다. 이 목록 밖의 host 명령이나 native event는 `host call <name> is not served to plugins` 또는 `native event <name> is not served`로 거부되며, region 호출과 view bridge 호출은 각자의 문구로 거부된다.
- **view channel.** view channel은 위 구성의 script와 handler `sok-view`다.
  1. document start에서 script는 `sok-view`로 ready message `{event: "view.ready", plugin, document}`를 보낸다. `document`는 script가 문서마다 만드는 식별자다. 호스트는 그것을 view의 ready 문서로 기록한다. view의 새 탐색(navigation)은 기록을 지우며, 새 문서의 ready message가 올 때까지 ready 문서가 없다. 탐색은 document 상태의 `navigations` 값이 올라갈 때 시작한다(아래). 탐색의 progress는 상태에서 `loading`이 true로 보이지만 기록을 유지한다. ready message를 보낸 문서가 아직 load 중인 문서이기 때문이다.
  2. 호스트는 `window.postMessage(message, location.origin)`을 page world에서 실행해 view에 message를 보낸다. 이것은 [문서 영역](#문서-영역)의 문서 post와 같은 형식이다. 호스트 message마다 `sok: 1` 필드가 있다. ready 문서가 기록되지 않은 view에 대한 post는 false를 반환하고, 호출자가 `error: view channel: <view> has no ready document`를 application log에 쓴다. 테마는 예외다. 호스트는 테마를 그런 문서에 보내지 않는다(테마 참조).
  3. script는 event source가 window이고 `sok: 1`을 가진 message 이벤트를, document start부터 페이지가 `window.sokView.attach`를 부를 때까지 queue에 보관한다. attach는 queue의 message를 순서대로, 이어서 나중 message를 모두 전달한다. 전달 대상은 [view bridge](plugins.ko.md#view-표면)의 `createViewChannel()`이 붙이는 `onMessage` handler다. queue는 한 문서의 message만 담으며 최대 256개다.
  4. `sok: 1`이 없는 message는 application log에 error로 쓰고 어떤 handler에도 넘기지 않는다. queue가 256개인 상태에서 도착한 message는 queue에 들어가지 않는다. script는 `sok-view`를 거쳐 `view.error` message의 이유로 `queue full for <plugin>`을 보내고, 호스트는 `error: view channel: queue full for <plugin>`을 application log에 쓰며, view를 닫고 재시작 한도 안에서 다시 만든다. 기록 없이 버리는 호스트 message는 없다.
  5. `core.plugin.views`는 `queued`를 보고한다. 이는 view가 attach하지 않아 queue에서 기다리는 현재 문서의 message 수다.
  6. `{event: "view.error", plugin, reason}` message는 첫 호출 전 page의 실패를 보고한다. start script는 로드되지 못한 script(해결되지 않는 import가 있는 module graph), 처리되지 않은 오류, 처리되지 않은 거부에 대해 이를 보낸다. host는 각각을 오류 표시 경로에 `error: view <plugin> <surface>: <reason>`으로 쓰고 view는 계속된다. queue overflow 이유는 `error: view channel: queue full for <plugin>` 기록을 유지하고 view를 닫는다([view channel](#view-표면), 항목 4). 빈 이유는 거부한다.
- **view 작업.** view 안에서 시작하는 작업(자기 클릭이나 키)은 view page에서 시작한다. view 브리지의 `runtime.beginOperation(event, fields)`는 page의 `beginOperation` 형식(`packages/plugin-api/operation.js`)으로 `p<view page의 time origin>.<n>` 식별자를 정하고, 첫 event `event`를 `fields`와 함께 `runtime.log`로 그 식별자를 달아 저장하며, 목록을 돌려준다. view는 작업을 수행하는 호출에 이 목록을 실어 보낸다: `runtime.sidecar(name).send(id, body, cids)`, `runtime.command(name, params, {cids})`, `runtime.log`. `cids`를 가진 명령 호출은 view-call 경로를 거친다. plugin의 명령은 exposure registry에서 요청의 `cids`로 받고, core 명령은 handler의 context `{cids}`로 받아 handler가 하는 각 호스트 호출(`host.call(name, arg, {cids})`)에 넘긴다.
- **view call.** view는 `sok-view`로 call 요청 `{sok: 1, id, command, params}`을 호스트에 보내며, view가 `cids`를 주면 요청은 멤버 `cids`를 싣고 호스트는 그 멤버를 `view-call`로 전달하며, `{sok: 1, id, cancel: true}`로 대기 중인 call을 취소한다. 요청은 [plugin process](plugin-processes.ko.md) 규칙 3의 call envelope이며, 그 응답은 view channel의 2번 항목 post 경로로 돌아온다. 호스트는 같은 현재 view generation에 응답을 게시한 뒤에만 call을 열린 목록에서 제거한다. 오래된 generation이거나 게시에 실패하면 call은 계속 열어 두며, 그 전에 view process가 끝나면 `process-ended` 사유로 처리한다.
  1. 호스트는 `id`가 정수이고 `command`가 빈 문자열이 아닌 요청을 `view-call {surface, plugin, id, command, params}` event로 창의 메인 page에 전달한다. `id`가 정수이고, `cancel`이 `true`이며, command를 담지 않은 취소는 `view-call {surface, plugin, id, cancel: true}` event로 전달한다. `surface`와 `plugin`은 메시지를 보낸 view의 값이다. 그 밖의 필드가 올바르지 않거나 `cancel`이 `true`가 아닌 메시지는 `error: view channel: <reason>`으로 application log에 쓰고 전달하지 않는다.
  2. 메인 page는 요청에 DOM surface context가 쓰는 handler로 답한다.
     - `tab.state.read`는 surface의 tab state를 돌려주고, `tab.state.write`는 params를 tab state로 저장한다. 저장 값은 `surface.unload`의 크기 한도 안에 있어야 한다. 두 call은 plugin이 `surface.unload`를 선언하지 않았으면 실패한다.
     - `runtime.native.call`은 `{name, payload}`로 surface의 host call `name`을 `payload`와 함께 실행한다. `name`은 빈 문자열이 아닌 문자열이다.
     - `runtime.sidecar.send`는 `{id, sidecar, body, cids}`를 `sidecar`가 이름 댄 선언된 sidecar로 보낸다. `runtime.sidecar(name).send`와 같다.
     - `runtime.clipboard.read`는 `"text"` 또는 `"fileURLs"`로 그 형식의 클립보드 값을 돌려주고, 그 형식의 payload가 클립보드에 없으면 `null`을 돌려준다. `"png"` 읽기는 `{present: true, type: "png", data}`를 돌려주며, `data`는 base64 형식의 payload이고 클립보드에 PNG payload가 없으면 `null`을 돌려준다. 읽기는 clipboard bridge가 만들듯 user-initiated다. `runtime.clipboard.writeText`는 문자열을 쓴다. `runtime.clipboard.persistPNG`는 `{data}`(`data`는 base64 형식의 PNG payload)로 payload를 저장하고 surface context의 clipboard bridge처럼 `{path, shellQuotedPath}`를 돌려준다.
     - `runtime.links.open`은 빈 문자열이 아닌 URL 문자열로 링크를 연다.
     - `tab.title`, `tab.footer`, `tab.directory`, `tab.modified`, `tab.error`는 값을 params로 받아 surface의 tab report를 surface context 항목과 같은 방식으로 실행하며, 올바르지 않은 값은 같은 방식으로 거부한다. `tab.notify`는 `{text, policy}`를, `tab.keep`은 `{reason, on}`을 받는다. 각각은 `null`로 답한다.
     - `runtime.log`는 `{level, event, fields, cids?}`를 받아 페이지의 event writer로 기록을 쓰며, writer는 surface context와 같이 view의 plugin과 surface를 더한다. `cids`는 기록이 이어 가는 chain의 correlation identifiers를 담은 선택적 목록이다([logging](logging.ko.md#작업-사슬)). surface context의 log는 모든 log call처럼 이를 검사한다. view에는 gate가 없다. view는 기록의 field를 만들어 page 배치로 보내고, host의 writer가 기록의 class로 정책을 적용하며 거부를 `log.gated`에 센다. 조용히 버려지는 것은 없다. 이 call은 `null`로 답한다.
     - `runtime.error`는 view가 자기 page에 보여 주는 오류의 오류 줄 `{where, text}`를 받아, page의 오류 표시의 기록 경로로 `error page surface <surface> <where>: <text>`를 application log에 쓴다. 그래서 view는 main page의 오류 표시와 같이 각 오류를 보여 주는 순간 기록한다. `where`는 control 문자와 `: `가 없는 비어 있지 않은 문자열이고, `text`는 비어 있지 않은 문자열이다. 다른 값은 `view call runtime.error requires a non-empty where without a control character or ": "`나 `view call runtime.error requires a non-empty text`로 거부되고 아무것도 쓰이지 않는다. 이 call은 `null`로 답한다.
     - `runtime.log.levels`는 지원되지 않는다. view에는 level 질의가 없으므로 call은 `view call runtime.log.levels is not served`로 거부된다. 기록은 `runtime.log`로 넘기고, 저장 여부는 event log의 writer가 정한다([logging](logging.ko.md#정책)).
     - `runtime.contributions`는 `{point}`를 받아, surface context의 `contributions(point)`가 돌려주는 것처럼 view의 plugin의 extension point `point`에 연결된 항목을 각각 `{plugin, index, item, module}`로 돌려준다. `index`는 그 plugin의 `contributes` 안에서 항목의 위치이고, `module`은 core root 위 module의 URL(`soksak://core/modules/...`)이다. plugin이 선언하지 않은 point는 surface context의 오류로 거부된다. `runtime.contributions.fail`은 `{point, plugin, index, reason}`을 받아 surface context의 `fail(reason)`처럼 그 연결된 항목을 `reason`과 함께 `invalid`로 만들고 `null`로 답한다. 비어 있지 않은 문자열이 아닌 `reason`은 `view call runtime.contributions.fail requires a non-empty reason`으로, 연결되지 않은 항목은 `view call runtime.contributions.fail: <point> has no connected item <index> of <plugin>`으로 거부된다.
     - `runtime.textSize.read`는 surface의 text scale을, `runtime.settings.read`는 plugin 설정의 값을 돌려준다. `runtime.textSize.on`과 `runtime.settings.on`은 아래 view event의 변경 구독을 등록한다. read가 아닌 각 call은 `null`로 답한다.
     - `runtime.status.watch`는 `{name}`을, `runtime.status.unwatch`는 `{name}`을 받는다. 둘 다 view가 값을 따르는 status를 이름으로 정한다. 이름은 owner가 `core`인 core status이거나, owner가 view plugin의 id인 그 plugin의 status다. 빈 이름, 문자열이 아닌 이름, 다른 owner의 이름은 아무것도 실행하지 않고 거부된다: `view call <command> requires a non-empty name` 또는 `view call <command> <name> is neither a core status nor a status of <plugin>`. exposure가 선언하지 않은 plugin status의 watch는 `view call runtime.status.watch <name> is not a declared status`로 거부된다. watch는 페이지가 따라가기를 등록하면 `null`로 답하며, 같은 이름의 두 번째 watch는 아무것도 등록하지 않는다. view가 watch하지 않는 이름의 unwatch는 `null`로 답하고 아무것도 바꾸지 않는다. watch의 거부는 `runtime.error`와 같이 `surface <surface> status <name>: <text>`를 application log에 기록한다.
     - `core.*` command는 `runtime.command`가 실행하듯 실행한다. view plugin의 command는 exposure의 주인 검사를 거쳐 실행하므로, plugin이 등록한 command만 실행된다. 다른 주인의 이름은 `command <name> belongs to <owner>, not <plugin>`으로, 주인이 없는 이름은 `view call <name> names no owner`로 거부한다. 위 목록이 제공하지 않는 `tab.` 또는 `runtime.` 이름은 `view call <name> is not served`로 거부한다.
     - 이미 대기 중인 `id`의 요청은 `view call <id> is already pending`으로 거부한다.
  3. 메인 page는 `viewReply {page, surface, generation, id, result}` 또는 `viewReply {page, surface, generation, id, error: {code, message}}`로 답한다. `page`는 비어 있지 않은 현재 문서 identity `String(performance.timeOrigin)`이다. 값을 돌려주지 않는 handler는 `result: null`을 보낸다. generation 검증 뒤 호스트는 `host.view.reply.dispatch`를 기록하며, current 대상은 native post 작업이 반환된 뒤 기록한다. `posted`는 해당 작업이 message post를 받아들였다는 뜻이고, `discarded`는 대상 generation이 더 이상 current가 아니었다는 뜻이다. native post 오류는 host call을 실패시키고 dispatch 기록을 쓰지 않는다. 이 기록은 JavaScript 수신이나 처리를 증명하지 않는다. post된 응답은 `{sok: 1, id, result}` 또는 `{sok: 1, id, error}`로 view의 ready 문서에 간다. ready 문서가 없는 view에 대한 응답은 page에서 `<surface> has no ready document`로 실패한다. 취소 message는 자신의 응답이 없다. 취소가 이름 붙인 대기 중인 call은 `{code: -32000, message: "cancelled"}` 오류로 답하며, 그 call의 handler는 계속 실행하고 결과는 버린다. 대기 중인 call이 없는 취소는 아무것도 끝내지 않는다.
  4. view의 call layer가 call을 resolve 또는 reject한다. 제한 시간은 command의 `timeout`이다. 그 시간이 지난 뒤 도착한 응답은 늦은 응답이며 버린다(plugin process 규칙 3). 호스트는 전달한 요청의 기록을 남기지 않는다. 취소된 call의 응답은 call layer가 그 call을 이미 끝낸 뒤 도착하므로, layer는 이를 늦은 응답으로 센다.
  - 페이지는 구독 call `runtime.native.on`(`{name}`), `runtime.sidecar.on`(`{id, sidecar}`), `runtime.sidecar.onFailure`(`{id, sidecar}`), `runtime.textSize.on`, `runtime.settings.on`, `runtime.status.watch`, `runtime.status.unwatch`에 아래 view event에서 정한 대로 답하고, 등록 call `runtime.command.register`(`{name}`)에 아래 view command에서 정한 대로 답한다. 각각은 적용되면 `null`로 답한다. 구독 등록의 각 결과는 off 함수의 promise다. 페이지는 key를 한 번만 등록하고 등록의 off 함수를 보관하며, 결과가 promise가 아닌 등록은 등록 함수의 이름을 밝힌 오류로 거부한다.
  - `runtime.theme`은 call이 아니다. 테마는 테마 message로 view에 가므로(테마 참조), `runtime.theme` call은 `view call runtime.theme is not served`로 거부한다.
- **view event.** view는 구독 call로 페이지의 event를 구독한다. 페이지는 구독의 각 event를 호스트 message `{sok: 1, event, data}`로 view에 보낸다.
  - `runtime.native.on`(`{name}`)은 surface의 호스트 event `name`을 전달한다. `data`는 DOM surface context가 받는 event 객체다.
  - `runtime.sidecar.on`(`{id, sidecar}`)은 세션 `id`의 sidecar message를 `event: "sidecar.message"`와 `data: {id, body}`로 전달한다.
  - `runtime.sidecar.onFailure`(`{id, sidecar}`)는 세션 `id`의 실패를 `event: "sidecar.failure"`와 `data: {id, reason}`로 전달한다.
  - `runtime.textSize.on`은 surface의 text scale이 바뀔 때마다 `event: "textSize"`와 `data`로 scale을 전달하고, `runtime.settings.on`은 plugin 설정이 바뀔 때마다 `event: "settings"`와 `data`로 값을 전달한다. 값이 바뀌지 않은 변경은 surface context가 전달하지 않듯 view에 전달하지 않는다.
  - workbench는 저장되는 level이 바뀔 때마다 `event: "log.levels"`와 `data`로 그 level을 보낸다. gate의 시행 중인 policy가 바뀔 때마다 level을 다시 읽고([logging](logging.ko.md#정책)), 마지막에 보낸 level과 다를 때만 보낸다. 어떤 view call도 view를 이 구독에 등록하지 않으므로 어떤 view도 받지 않는다.
  - `runtime.status.watch`는 watch한 status의 각 값(첫 값을 포함)을 `event: "status"`와 `data` `{name, value}`로 전달한다. `value`는 exposure registry가 그 이름에 대해 보고한 값이다. SDK는 `value`를 그 이름의 listener에게 전달하며, `runtime.status.watch(name, listener)`는 그 listener의 watch를 끝내는 함수를 돌려준다. 페이지는 `runtime.status.unwatch`가 그 이름에 대해 호출될 때와 surface가 닫힐 때 구독을 끝낸다. host는 call과 event의 command나 status 이름을 읽지 않고 전달한다(host contract의 `view.status.relay`). `status`는 이 event에 예약된 이름이며, `theme`, `settings`, `textSize`, `log.levels`와 같이 plugin은 이 이름의 native event를 구독할 수 없다.

  메인 page는 선택된 view 원천에 `viewEvent {surface, generation, event, data}`로 `declared-ui.expanded`를 보내며 `data`는 `{status, tree, path, expanded}`다. `generation`은 선택된 view source의 generation이다. `status`는 plugin 안의 이름이다. view는 `runtime.native.on(\"declared-ui.expanded\")`로 이를 받고 plugin 값을 갱신한 뒤 새 declared UI snapshot을 push한다. workbench는 그 snapshot을 받아들인 뒤에만 그리기를 바꾼다.

페이지는 구독을 한 번만 등록한다. 같은 name이나 id의 두 번째 call은 다시 등록하지 않고 `null`로 답한다. 페이지는 구독한 view document의 generation을 사용해 각 event를 `viewEvent {surface, generation, event, data}`로 보낸다. Restart는 해당 document의 구독을 끝내며, 그 document의 pending 또는 늦은 callback은 취소 상태를 유지하고 replacement generation으로 이름을 바꾸지 않는다. 호스트는 current generation의 event만 받아들이고 generation을 `sok-view`에 노출하지 않은 채 `{sok: 1, event, data}`를 ready 문서에 post한다. current view에 ready 문서가 없으면 `<surface> has no ready document`로 실패하고, 페이지가 그 오류를 application log에 쓴다. 재시작한 view는 다시 구독한다. view는 event 이름의 listener에 각 event를 전달하고, listener가 없는 event는 무시한다.
- **view command.** view는 시작할 때 자기가 제공하는 각 command를 `runtime.command.register`(`{name}`) call로 선언한다.
  1. 페이지는 등록을 exposure의 registry로 적용한다. plugin의 `exposes`가 선언하지 않은 name이나 다른 plugin의 name은 registry 오류로 거부되며, call은 그 오류로 답한다.
  2. core exposure의 command 요청이 페이지에 도착하면, 페이지는 `viewRequest {surface, id, command, params}`를 보낸다. `id`는 exposure 요청의 id이고 `params`는 그 params다. 요청이 `cids` 멤버를 가지면 페이지는 이를 함께 보낸다. 이는 요청을 일으킨 작업이나 입력의 상관 식별자다([작업 사슬](logging.ko.md#작업-사슬)). 명령 요청을 시작하는 실행은 이 식별자를 요청의 `cids`로 넘긴다(exposure registry의 `run(name, params, surface, cids)`와 `runOwned(name, params, owner, cids)`). 빈 목록은 식별자가 없는 것이다. 호스트는 `{sok: 1, id, command, params}`를 view의 ready 문서에 post하며, 요청이 `cids`를 가지면 그 멤버도 함께 보낸다. 한 줄에 담을 수 없는 목록(빈 식별자, 또는 따옴표, 역슬래시, 제어 문자가 있는 식별자)은 exposure registry가 view에 닿기 전에 코드 `-32602`로 거부하며, 호스트도 그런 목록의 `viewRequest`를 오류로 거부해 어떤 view에도 post하지 않는다. ready 문서가 없는 view에 대한 요청은 `<surface> has no ready document`로 실패한다.
  3. view는 `sok-view`로 `{sok: 1, reply: id, result}` 또는 `{sok: 1, reply: id, error: {code, message}}`로 답한다. view는 `command`의 handler를 첫 번째 인자 `params`와 두 번째 인자 context `{cids}`로 실행한다. `cids`는 요청의 목록이며, 요청이 없으면 멤버가 없다. handler가 `context.log.<level>(event, fields, {cids: context.cids})`로 남기는 기록이나 `context.cids`로 보내는 sidecar 요청은 원인의 사슬에 이어진다. handler가 던진 오류가 응답의 error가 된다. view가 등록하지 않은 command의 요청은 `{code: 1002, message: "view command <command> is not registered"}` 오류로 답한다.
  4. 호스트는 `id`가 정수이고 `result`와 `error` 중 하나만 있으며 error에 message가 있는 응답을 `view-reply {surface, plugin, id, result}` 또는 `view-reply {surface, plugin, id, error: {code, message}}` event로 메인 page에 전달한다. 그 밖의 응답은 `error: view channel: <reason>`으로 application log에 쓰고 어떤 page에도 전달하지 않는다.
  5. 페이지는 응답으로 exposure 요청에 답한다. command가 선언한 timeout(plugin process 규칙 3, 기본 10000 ms, 1부터 600000까지)이 대기를 제한한다. view가 제때 답하지 않으면 페이지는 `{code: -32000, message: "command <name> did not reply within <ms>ms"}`로 요청에 답하며, 그 뒤 도착한 응답은 버리고 늦은 응답으로 센다.
  6. Surface를 닫거나 교체하면 진행 중인 view call과 event 전달을 끝낸다. 페이지는 pending call의 대기를 abort한다. 이미 시작한 handler는 끝날 수 있지만 결과를 버리고 종료한 view에 reply를 보내지 않는다. 종료 뒤 host가 거부한 대기 event는 취소한다. 페이지는 각 취소를 debug 수준 `page.view.call.cancel` 또는 `page.view.event.cancel`로 기록한다. Surface가 열린 상태에서 발생한 거부는 계속 오류이며 application log에 쓴다. 종료가 call을 끝낸 경우 reply가 없는 call receipt에는 대응하는 취소 기록이 있다.
- **view exposure.** view는 status와 dom 항목 및 core document command `core.surface.hit`를 `runtime.native.call`의 `{name: "registered", payload: {kind, name}}`로 등록한다. main page는 선언을 검사하고 registry 및 surface의 `exposureRegister` 호출로 등록한다. host는 이를 저장하고 `exposure-registered`로 알린다([exposure](exposure.ko.md#전달)). plugin command는 `runtime.command.register`를 사용한다. 전달된 요청은 `exposure-request`라는 `runtime.native.on` 구독을 통해 `{id, surface, method, params}`로 view에 도착한다. main page는 모든 전달된 view 요청을 소비하며 placeholder에서 답하지 않는다. core bridge는 자기 document 항목 세 개에 한 번 답하고 그 요청을 plugin listener로 전달하지 않는다. 다른 요청은 plugin listener에 도착한다. view는 `runtime.native.call`의 `{name: "exposureReply", payload: {id, result|error}}`로 답하며 page는 surface의 `exposureReply` 호출로 전달한다. 답이 없는 요청은 host timeout으로 끝난다.
- **declared UI snapshot.** view는 status의 declared UI snapshot을 message `{event: "declared-ui.snapshot", plugin, status, seq, value, skipped}`로 `sok-view`를 거쳐 push한다. 호스트는 field가 온전한 snapshot을 event `declared-ui.snapshot {surface, plugin, status, seq, value, skipped}`로 창의 메인 page에 전달하고, 페이지는 이를 확인하고 그린다([declared UI](declared-ui.ko.md#status-대응)). 호스트는 snapshot에 대한 자체 event는 쓰지 않는다([plugin process](plugin-processes.ko.md) 규칙 2). plugin이 없거나 view의 plugin이 아닌 plugin을 naming하거나, `status`가 없거나, 1 이상의 정수 `seq`가 없거나, `skipped` count가 없거나, `value`가 없는 snapshot은 `error: view channel: <reason>`으로 application log에 쓰고 어떤 page에도 전달하지 않는다. 메인 page는 snapshot을 view event `declared-ui.snapshot.ack`로 확인하며 그 `data`는 `{plugin, status, seq}`이고, status의 현재 값은 view command 경로의 call `declared-ui.snapshot.request`(`{status}`)로 pull하며 그 응답은 `{seq, value}`를 담는다. source가 아직 값이 없으면 `seq`는 0이고 값은 `null`이다.
- View surface 수명에는 native view 생성 전에 단조 증가 generation을 부여한다. Host는 이 값만 main-page lifecycle 및 snapshot metadata에 포함하고, acknowledgement, pull, expanded 요청의 기대 generation을 dispatch 전에 검사하며 pull 응답에도 붙인다. 이 field는 공개 `sok-view` message에 추가하지 않는다. 종료된 generation을 대상으로 한 요청은 명시적 취소 disposition을 반환하며 합성한 빈 snapshot을 반환하지 않는다.
- **presentation wait.** view는 card 배치가 바뀐 뒤 처음 표시될 때만 presentation wait에 참여한다. divider 끌기 같은 계속되는 gesture에서는 view의 frame이 매 frame마다 card와 같은 commit에 배치되며, commit은 그 뒤 view가 그리는 내용을 기다리지 않는다. wait는 다음 중 처음 일어나는 것으로 끝난다. view의 presentation 완료, view process의 종료, 변경이 끝날 때 view가 보이지 않게 되는 것, `host.trace.view.unresponsive` 알림. native 트랜잭션은 참여한 각 view가 표시되거나 wait가 끝날 때까지 commit을 잡는다. wait는 timer로 끝나지 않는다. host가 commit을 하고 각 끝을 보므로 wait는 host가 소유하며, presentation 완료 없이 끝나면 성능 trace가 켜져 있을 때 host가 `host.trace.view.presentation-abandoned {surface, reason}`을 쓴다. view는 변경마다 한 번만 wait에 참여한다. presentation 완료 없이 끝나면 commit은 그 view 없이 계속되고, host는 `view-presentation-abandoned {surface, reason}` 알림을 surface로 보내며, 손실은 `core.plugin.losses`의 `abandoned`로 센다.
- **테마.** view가 포함된 `syncSurfaces` 요청을 보내기 전에 workbench는 최신 `setTheme` 호출의 host reply를 기다린다. theme reply가 실패하면 view 배치를 거부하고 host 오류 log에 남긴다. view가 없는 배치는 theme reply를 기다리지 않는다. 생성할 때 호스트는 현재 테마의 `{scheme, tokens}` 값을 동결해 `window.sokTheme`에 넣는 document-start script를 view 구성에 준다. 그래서 페이지의 첫 script가 어떤 페이지 script보다 먼저 `window.sokTheme`에서 토큰을 읽는다. 호스트는 view의 page를 불러오기 전에 이 script를 더한다. 나중의 테마 변경은 post 경로로 host message가 되어 view에 간다. 다만 ready 문서가 기록되지 않은 문서에는 보내지 않는다. 호스트는 ready message마다 현재 테마를 보내므로, ready 전의 변경은 오류도 아니고 유실도 아니다. 테마 message는 `{sok: 1, event: "theme", data: {scheme, tokens}}`이며, `data`는 호스트가 가진 현재 테마 값이다. view는 마지막 테마 message를 보관하며, 나중에 구독하는 `runtime.theme`의 listener는 그 값을 즉시 받는다.
- **시작 값.** 생성할 때 호스트는 테마 script와 함께 view 구성에 document-start script를 더해, 그 surface의 동결된 시작 값 `{surface, params, origin, project, declarations}`를 `window.sokSurface`에 넣는다. 그래서 페이지의 첫 script가 어떤 페이지 script보다 먼저 이를 읽는다. `surface`는 surface의 식별자이며 URL query가 아닌 context 멤버다. `params`는 탭의 매개변수 또는 `null`이다. `origin`은 탭을 연 탭이 그때 기록한 directory를 담은 동결된 `{directory}`이고, 그 탭이 기록하지 않았으면 `{directory: null}`이다. 이는 surface context의 `origin`과 같은 형식이다([plugins](plugins.ko.md#탭-알림)). 준비는 `origin`을 반드시 담아야 하며, `origin`이 없거나, `null`이거나, `{directory}`에 경로 또는 `null`이 아닌 값이면 거부된다. 시작 값이 없는 view surface도 `origin`이 없으므로 거부된다. `project`는 창이 보이는 project의 동결된 `{id, root}`(project id와 정규 root)이고, project가 없는 창에서는 `null`이다. `declarations`는 plugin의 `exposes`와 [exposure](exposure.ko.md#표면-문서)의 core document 항목 세 개를 담는다. 페이지는 surface의 준비(`syncSurfaces`)로 이 값들을 보내며, 호스트는 요청의 나머지와 함께 검사하고, 형식이 맞지 않는 값은 그 검사의 이유로 거부된다. 다른 구성의 surface는 이 값을 담지 않는다. Workbench는 tab의 전체 descriptor에서 이 값을 계산해 host request의 기존 `start` member에 전달하며 별도 `params` member를 추가하지 않는다. 호스트는 view의 page를 불러오기 전에 이 script를 더하고, view를 다시 만들 때 surface의 기록에서 이 값을 다시 주입한다.
- **origin 거부.** view의 origin은 뷰가 시작하기 전 레이아웃을 읽을 때 검사하며, 거부된 view는 어떤 뷰도 시작하지 않는다([프로젝트](projects.ko.md#탭-origin)). 검사는 이 순서로 하며 첫 일치가 문구를 정한다. `<id>`는 surface 식별자다. origin 멤버가 없으면 `surface "<id>": view start origin is missing`. origin이 `null`이거나, 객체가 아니거나(JSON 배열은 객체가 아니다), `directory` 외의 멤버를 가지거나, `directory`가 문자열도 null도 아니면 `surface "<id>": view start origin is not {directory} with a path or null`. 문자열이 비었으면 `surface "<id>": view start origin directory is empty`. 문자열이 `/`로 시작하지 않거나, `//` 또는 `/<문자>:`로 시작하거나, NUL 바이트를 담으면 `surface "<id>": view start origin directory is not an absolute path`. 경로 규칙은 플랫폼 경로 API 없이 하나의 문자열 검사이므로 모든 호스트와 페이지가 같다. `/a`는 받고 `//server/share`, `/C:/x`, `C:\x`, `relative`, NUL 바이트를 담은 경로는 거부한다. `//` 형식은 Windows의 UNC 공유 접두이고 POSIX에서는 구현에 따른다. `/<문자>:` 형식은 드라이브 접두이며, 같은 규칙이 POSIX의 합법 이름인 `/a:b`도 이식성 선택으로 거부한다. `/\`는 POSIX의 합법 이름이므로 받는다. 레이아웃 읽기에서 거부된 view 탭은 탭을 레이아웃에 남기고, 문구를 보이며, 로그에 기록한다. 페이지는 `createSurfaceContext`에서 같은 결함을 같은 문구로 거부하며, 없는 origin을 채우지 않는다.
- **surface phase.** workbench는 view가 composition을 선언하면 view surface의 phase `ready`를 보고한다. module surface가 module mount 뒤 보고하는 것과 같다. view mount가 실패하면 mount 오류와 함께 `error`를 보고한다. view 페이지는 phase를 보고하지 않는다. 그 `status.report("ready")`는 받아들여 무시하며, 상태는 workbench가 보관한다. 표면을 기다리는 core 명령은 같은 선언에서 풀린다(`waitSurfaceCompositionDeclared`).
- **호출 기록.** workbench는 view 호출을 받으면 `page.view.call {plugin, surface, generation, id, command}`을, 회신을 보내면 `page.view.reply {plugin, surface, generation, id, outcome}`을, 회신을 취소하면 `page.view.call.cancel {plugin, surface, generation?, id, command}`을 debug 수준으로 쓴다([event 목록](events.json)). 회신이나 취소는 page, plugin, surface, generation, id가 모두 같은 수신 기록과만 짝을 이룬다. 취소 event에 유효한 generation이 없으면 취소 기록에도 generation이 없다. 성공한 native `viewReply` host call의 인수에는 page, 받아들인 generation, surface, id가 있다. `host.view.reply.dispatch`는 같은 page, window, surface, generation, id로 native post 결과를 기록한다. `posted`는 native post 수락이며 JavaScript 수신이 아니고, `discarded`는 오래된 대상에 대한 no-op이다. 성공한 page call과 이 기록은 각각 현재 page identity와 일치해야 한다.
- **입력.** view에는 단축키 표도 키 listener도 없으며, bridge는 키 event에 대해 어떤 call도 보내지 않는다. view가 주인인 키(글 입력, 자기 Escape 동작)는 기본 동작을 유지하고 view의 first responder가 받아 view가 처리한다. view는 넘길 키에 대해 `runtime.command(name, params)`로 workbench 명령을 실행한다([plugin 프로세스](plugin-processes.ko.md) 규칙 7). host는 view의 키로 아무것도 하지 않는다. view는 view call `runtime.shortcuts.read`로 [단축키 표](exposure.ko.md#키보드-단축키)의 행을 읽는다. 주인이 `workbench` 또는 `view`인 행을 `{key, owner, command}`로 답하며, native 메뉴 행은 돌려주지 않는다. Escape는 보통의 키다. 자기 Escape 동작이 있는 view는 자기 handler에서 정하고, 없는 view는 page picker가 열려 있을 때 Escape에 `core.picker.close`를 실행한다. bridge는 이 규칙들을 강제하지 않는다. view가 실행한 workbench 명령이 실패하면 그 명령이 표의 행일 때 `page.input.shortcut.failed {plugin, command}`를 error 수준으로 쓰고 오류로 답한다. view call에는 `runtime.shortcuts.missing`, `runtime.shortcuts.run`과 등록이 없다. 입력기 조합은 view의 first responder에 간다. view는 비활성 창의 첫 마우스 누름을 받는다. AppKit은 첫 마우스를 거부하는 web view에 그 누름을 전달하지 않고 창만 활성화하기 때문이다. view가 받으므로 누름은 view의 페이지에 닿고, 활성 창에서의 누름과 같이 view가 first responder가 된다. 문서 영역은 거부를 유지한다.
- **process 시작.** 호스트는 view를 만들 때 `host.trace.view.process-request {plugin, surface}`를 쓰고, 그 view의 첫 ready message에서 `host.trace.view.process-ready {plugin, surface}`를 쓴다.
- **응답성.** WebKit이 view의 WebContent process가 응답성 검사에 답하지 않는다고 알리면, 호스트는 `host.trace.view.unresponsive {plugin, surface}`를 쓰고 `view-responsiveness {surface, plugin, generation, responsive: false}`를 창의 메인 page에 보낸다. process가 다시 답하면 호스트는 `host.trace.view.responsive {plugin, surface}`를 쓰고 같은 generation의 `responsive: true`를 보낸다. 호스트는 callback을 설치한 view의 generation을 보관하고 retired view의 callback을 거부하며, 알림은 ordered main-page source event stream으로 보낸다. 메인 page는 해당 generation이 current일 때만 알림을 적용하고 오래된 알림은 `event: view-responsiveness`인 `page.view.event.cancel`로 기록한다. 이 알림은 view의 어떤 call도 끝내지 않는다. 메인 page는 view surface마다 상태를 `core.plugin.views {plugin, surface, responsive}`에 보관하고, surface가 dispose되면 이를 지운다. 문서 영역은 알림을 받지 않는다. `view-presentation-abandoned` 알림은 완료된 presentation wait를 기록하고 plugin의 abandoned-presentation count에 더한다. Live view state를 바꾸지 않으므로 기존 presentation event 경로를 유지한다.
- **process 종료.** view process가 끝나면 호스트는 view가 열어 둔 각 call을 `process-ended` 이유로 끝내고, `host.call.peer-lost`를 쓰며, view의 presentation wait를 끝낸다. 호스트는 표면의 document·image 영역을 닫고 창의 메인 page에 `view-process-ended {surface}` event를 보내며, 메인 page는 새 view가 영역을 다시 붙일 때까지 그 표면의 영역을 잊는다. 그 뒤 호스트는 view를 다시 만들고, 새 view는 저장된 탭 상태에서 상태를 복원한다. 재시작 한도는 [plugins](plugins.ko.md#view-표면)의 한도다. 같은 표면의 실패가 300초 안에 4번 일어나면 재시작을 멈춘다. 네 번째 실패에서 호스트는 `error: view channel: <surface>: the view failed 4 times within 300 seconds and is created again when its tab is reopened`을 application log에 쓰고, 창의 메인 page에 `view-stopped {surface, plugin, reason}` event를 보낸다. reason은 `the view failed 4 times within 300 seconds and is created again when its tab is reopened`이다. 메인 page는 reason을 표시 경로로 card에 보여 주며, 사용자가 탭을 다시 열 때까지 card가 이를 유지한다.

## plugin host

plugin host는 manifest가 선언하는 plugin의 숨은 web view로, 창에 붙고 surface host에는 붙지 않는다. 아무것도 보여 주지 않는다. surface frame을, region을, presentation wait을 가지지 않고, 입력을 받지 않으며, 어떤 hit test도 그것에 닿지 않는다. channel, exposure 등록, snapshot, restart limit, state의 계약은 [plugin host](plugin-host.ko.md)에 있다.

## 영역

영역은 표면에서 네이티브 콘텐츠를 표시하는 장소다. 소유권, 계층, 완전한 스냅샷 위치, 쌓임, 입력, 세대, 래스터 규칙은 [표면 합성](surface-composition.ko.md)이 정의한다. 이 문서는 문서·그림 공급자에만 해당하는 동작을 정의한다.

모든 네이티브 영역은 자기 표면 `SurfaceHost.NativePlane`의 하위 뷰다. 호스트나 DOM 평면의 형제일 수 없다. 호스트는 적용한 완전한 합성에서 영역 프레임을 계산하고 호스트에 맞게 클리핑한다. 영역은 표면과 동기적으로 이동하고 숨겨지고 어두워지고 닫힌다.

영역은 모달 대화 상자 아래에 있다. 문서 영역 렌더러는 표시 대기에서 빠지지만, 보이는 그림 영역은 준비된 배치를 커밋하기 전에 정확한 현재 래스터를 가져야 한다. 각 영역은 표면 안에서 고유한 이름을 갖는다. 호스트는 영역의 이름, 사각형, 표시 여부, 초점 여부를 `host.window`로 보고한다.

영역의 공급자는 둘이다.

- **문서 영역**: 코어가 표면의 하위 뷰로 만들며, 웹 문서를 호스팅한다.
- **그림 영역**: 바깥 사이드카가 만들며, 공유 이미지를 네이티브 표면으로 공급한다.

### Region lifetime

place가 빼는 표면의 영역 종료는 호스트가 맡는다. 두 호스트는 place가 답하기 전에 page가 더 이상 나열하지 않는 각 표면의 문서 영역과 그림 영역을 모두 닫는다. page는 place를 먼저 실행하고, place가 성공한 뒤에만 그런 표면의 모듈을 release한다. 그 release는 영역의 page 쪽 handle만 버리고 `documentDetach`, `documentUnsubscribe`, `imageDetach`를 호출하지 않는다. place를 실행하기 전에 page는 place가 빼는 각 표면의 composition을 멈춘다: 호스트가 place 중에 그런 표면의 composition을 지우므로, 그 표면에 대해 `compositionPlace`와 `imagePlace`를 보내지 않고 아무것도 detach하지 않는다. 실패한 place는 아무것도 release하지 않으므로, 뺐을 표면은 마운트된 채 남고 그 composition은 다시 시작해 현재 형태를 다시 place한다. place는 host에서 그런 surface의 sidecar session도 끝내므로, place가 도는 동안 모듈이 sidecar로 보내는 send는 결과를 기다린다: 실패한 place 뒤에는 보내고, 성공한 place 뒤에는 그 send와 dispose가 보내는 session 종료 같은 모듈의 이후 send를 보내지 않는다. host로 보내면 project root 없는 session이 열리기 때문이다. 표면이 배치된 채로 page가 스스로 detach하는 영역은 호스트를 거쳐 detach하고, 그 detach의 실패는 보고한다. 이는 place를 거친 모든 제거에 적용된다: 탭 닫기, 탭 unload, commit이 더 이상 유지하지 않는 표면.

## 네이티브 뷰 위의 입력

네이티브 뷰는 DOM 위에 놓인다. 네이티브 뷰는 자신이 놓인 DOM 요소를 그리고, 그 요소의 입력을 소유하지 않는다. 그 위의 입력은 네이티브 뷰가 없는 것처럼, 페이지가 그 점 아래의 DOM 요소를 기준으로 정한다.

- 포인터와 휠 이벤트는 그림 영역을 지나 페이지로 가며, 커서를 포함한 그 의미는 페이지가 정한다.
- 네이티브 뷰는 커서 영역도 끌기 형식도 등록하지 않는다.
- 다른 애플리케이션에서 창으로 끈 파일은 창의 파일 놓기 뷰로 간다. 이 뷰는 창 합성 뷰의 유일한 네이티브 끌기 대상이다. 합성 뷰의 웹뷰들 위에 있고, 파일 URL만 받으며, 적중 검사에서 뷰를 돌려주지 않으므로 포인터 이벤트와 다른 끌기는 아래 뷰로 간다. 이 뷰는 Finder가 끌기 대지에 두는 파일 참조 URL을 파일 경로 URL로 바꾸고, 참조가 더 이상 파일을 가리키지 않는 놓기는 거절한다. 놓기는 페이지에 파일 URL과 페이지 좌표의 놓인 점인 `{urls, x, y}`의 JSON 문자열을 `files-dropped`로 보낸다. 호스트는 문자열을 바꾸지 않고 넘기며 페이지가 해석한다. 페이지는 그 점의 DOM 요소가 속한 표면을 찾고, 그 표면의 플러그인이 `plugin.json`에 `surface.drop`으로 선언한 놓기 명령을 그 표면에서 `{urls}`로 실행한다. `core.drop`은 마지막 놓기를 `{urls, x, y, surface, command, error}`로 알린다. 어느 표면에도 놓이지 않았거나 놓기 명령을 선언하지 않은 플러그인의 표면에 놓이면 `error`에 그 이유를 두고 아무것도 실행하지 않는다. 그런 객체가 아닌 문자열도 같다.
- 호스트는 프레임워크의 파일 놓기 처리를 끄므로, 놓인 파일은 파일 놓기 뷰만 받는다.

## 문서 영역

표면 페이지는 문서 영역으로 자기 요소 하나에 웹 문서를 표시한다. 표면은 항상 플러그인의 페이지를 표시하며([플러그인](plugins.ko.md)), 웹 주소는 표면이 아니다.

- manifest가 `^[a-z0-9][a-z0-9-]{0,63}$`와 일치하는 고유 이름을 선언한다. 페이지는 `createSurfaceComposition`에서 문서 손잡이를 얻는다. 개별 attach, place, detach 연산은 공개하지 않는다.
- 호스트는 호출한 표면의 `SurfaceHost.NativePlane` 아래에 웹뷰를 만들고, 호출마다 호출한 웹뷰가 요청에 적힌 표면에 속하는지 확인한다. 그 웹뷰는 [view 표면](#view-표면)의 view다. 표면은 다른 표면의 영역을 조작할 수 없다.
- 완전한 합성이 뷰포트 가장자리에서 요소까지의 여백을 CSS 픽셀로 보고하고 요소가 보이는지를 함께 보낸다. 호스트는 여백을 저장하고 바깥 표면이 바뀔 때 그림 영역(image region)에 한해 같은 네이티브 트랜잭션에서 다시 적용한다. 문서 영역은 배치할 때와 프레임이 바뀔 때 네이티브 트랜잭션 밖에서 여백을 다시 적용하며, 명세는 문서 영역에 트랜잭션을 주장하지 않는다.
- 페이지는 요소를 숨겨 영역을 숨긴다. 그러면 합성이 영역을 보이지 않는 것으로 보고하고, 호스트는 네이티브 뷰를 숨겨 그 뷰는 그리지도 입력을 받지도 않는다. 브라우저 플러그인은 `browser.location`이 빈 `url`을 보고하는 동안, 즉 첫 주소를 열기 전에 문서 요소를 숨긴다. 저장된 주소가 없는 브라우저 표면은 마운트할 때 브라우저 설정 `browser.home`(라벨 `홈 주소`, 기본값이 빈 주소 설정)의 주소를 연다. 그 설정이 비어 있으면 표면은 빈 상태로 시작한다. 그 자리에는 `주소를 입력하세요` 문구의 빈 상태 `browser.empty`를 표시하고, 이를 누르면 `browser.address.select`가 실행되어 주소창에 초점을 주고 값을 선택한다. 상태가 비어 있지 않은 `url`을 보고하면 플러그인은 빈 상태를 없애고 문서 요소를 다시 표시한다.
- 영역은 `http`, `https`, `file`, `soksak` 주소를 연다([애플리케이션 주소](native-host.ko.md#애플리케이션-주소)). 앱 자체 스킴은 요청할 때와 문서가 이동할 때 모두 거부한다. `file` 주소는 loadFileURL:allowingReadAccessToURL: 로 열어 파일이 있는 디렉터리까지 읽기 권한을 준다. 영역 문서는 앱 문서와 분리된 영구 웹사이트 데이터 저장소 하나를 사용하며 앱 브리지를 받지 않는다. 저장소는 쿠키, 로컬 저장소, 캐시 같은 사이트 데이터를 앱 설정 디렉터리 안의 `document-data` 디렉터리에 둔다. 설정 디렉터리는 앱이 `--config-dir`로 시작하면 그 디렉터리이고, 아니면 기본 설정 디렉터리다. 따라서 두 설정 디렉터리는 사이트 데이터를 공유하지 않고, 설정 디렉터리를 지우면 그 사이트 데이터도 지워진다. 공개 `dataStoreForIdentifier:`는 모든 저장소를 앱의 WebKit 컨테이너에 두므로, 호스트는 `_WKWebsiteDataStoreConfiguration` `initWithDirectory:`로 저장소를 만든다([비공개 네이티브 API](../operations/private-native-apis.ko.md)).
- plugin 주소 `soksak://<plugin id>/<path>`는 그 영역을 가진 표면의 plugin 안의 파일을 가리킨다. composition 선언은 표면의 `plugin`을 담고, host는 그 plugin이 설치되어 켜져 있으면 `plugins/installed.json`이 그 plugin에 기록한 폴더에서 `<path>`를 내보낸다. 다른 owner의 주소, 빈 부분이나 `.`, `..` 부분이 있는 경로, 없는 파일은 찾을 수 없다고 답한다. 거부된 페이지 요청마다 정규화된 주소 `<URL>`을 담아 응용 프로그램 log에 `error: document view: plugin file not found: <URL>`을 error 수준으로 쓰므로, log는 거부마다 URL과 사유를 남긴다. plugin이 자기 release에 없는 파일을 요청하면 그 plugin의 결함이므로 이 거부는 관찰이 아니라 오류다. host는 파일 확장자의 content type을 보낸다: `.html`은 `text/html`, `.js`와 `.mjs`는 `text/javascript`이고, `text/css`, `application/json`, `application/wasm`, `image/svg+xml`, `image/png`, `image/jpeg`, `image/webp`, `image/x-icon`, `font/woff2`, `font/woff`, `font/ttf`, `font/otf`, `text/plain`은 각자의 확장자에, 다른 확장자에는 `application/octet-stream`을 보낸다. plugin 문서의 origin은 `soksak://<plugin id>`이므로, 한 plugin의 문서들은 사이트 데이터를 함께 쓰고 두 plugin의 문서들은 함께 쓰지 않는다.
- core root `soksak://core/<path>`는 view가 요청하며 region은 요청하지 않는다. view 구성은 `isView`를 설정하여 만들며, 그 구성만 scheme의 host `core`를 처리한다. 요청은 host가 platform에 등록한 core root resolver로 간다([host contract](host-contract.ko.md#contract-cases), `document.core-root.native`). resolver는 view 구성의 plugin id와 path를 받아 파일과 content type을 내보내거나 path를 거부한다. 내보낸 응답은 그 view 구성의 `Access-Control-Allow-Origin: soksak://<plugin id>`를 담으며, 요청의 Origin을 되돌려 보내지 않고 `*`도 보내지 않는다. 거부 응답은 이 헤더를 담지 않으므로 page의 fetch나 module import가 실패한다. 문서 영역(region)은 core root 허용을 받지 않는다. 그 `soksak://core` 요청은 not found로 답하며 resolver는 호출되지 않는다. view가 받을 파일을 정하는 규칙은 [plugin 프로세스 rule 4](plugin-processes.ko.md)가 정한다.
- plugin 문서는 자기 영역의 binary store에 byte를 보관한다. 이 store는 영역의 plugin만을 위해 binary id 아래에 byte를 둔다. `POST soksak://<plugin id>/.binary`는 요청 body를 저장하고 JSON 객체 `{"id", "length"}`를 답한다. `id`는 host가 만드는 소문자 16진수 32자이고, `length`는 저장한 byte 수다. host는 body를 `HTTPBody`에서 읽고, WebKit이 body를 stream으로 전달하면 `HTTPBodyStream`에서 읽는다. WebKit이 Blob body처럼 두 형태 중 어느 것으로도 전달하지 않는 요청은 400으로 거부하므로, 페이지는 byte를 ArrayBuffer view로 보낸다. byte는 요청의 `Content-Type`을 유지하며, `Content-Type`이 없는 upload는 `application/octet-stream`을 유지한다. `GET soksak://<plugin id>/.binary/<id>`는 저장된 byte를 그 `Content-Type`과 `Content-Length`로 답하며, host는 응답이 끝날 때 id를 해제하므로 같은 id에 대한 두 번째 요청은 찾을 수 없다고 답한다. upload는 body가 비어 있으면(400), 16 MiB(16777216 byte)를 넘으면(413), 또는 영역이 저장한 byte가 64 MiB(67108864 byte)를 넘게 되면(413) 거부한다. 다른 plugin의 origin에 대한 요청은 403으로, `/.binary`에 대한 POST가 아닌 method나 `/.binary/<id>`에 대한 GET이 아닌 method는 405로, 저장되지 않은 id는 404로 거부한다. 각 거부는 `application/json`으로 `{"error": <reason>}`을 답하고, 그 사유를 응용 프로그램 log에 `error: document view: <reason>` 형식으로 쓴다. 다른 origin의 페이지는 응답에 CORS 헤더가 없어서 응답 body를 읽지 못하며, 네트워크 오류를 보고 사유는 log에 남는다. host는 native 코드에서 영역의 id를 가져가는 동작도 두며, 그 동작은 byte를 돌려주고 id를 해제한다. 영역을 닫으면 그 영역이 가진 모든 id를 해제한다. plugin release는 경로에 `.binary` 부분이 있는 파일을 거부한다. host가 그 경로를 파일 조회 전에 응답하기 때문이다.
- host는 document 영역의 binary id가 가진 byte를 플랫폼의 take 작업으로 가져온다. native take는 byte를 돌려주고 id를 놓으므로, 같은 id의 두 번째 take는 native 오류 문구로 실패한다. 연결되지 않은 document는 `document "<name>" is not attached`로 take를 거부한다. 이는 다른 document 작업의 문구다. binary id를 이름으로 받는 첫 명령은 view와 함께 온다.
- plugin 문서는 page와 메시지를 주고받는다. document handle의 `post(message)`는 JSON 값을 영역에 보낸다. host는 문서의 page world에서 `window.postMessage(message, location.origin)`을 실행하고, 현재 문서가 영역 plugin의 plugin 문서가 아니면 `document <name> shows no plugin document`로 실패한다. host content world의 스크립트는 문서의 window가 window 자신을 `source`로 받은 각 `message` 이벤트를 전달하므로, page는 자기가 보낸 메시지도 받는다. host는 `document-message {surface, document, message}`를 소유 표면에만 보내며, `message`는 이벤트의 data를 JSON으로 담는다. content world 스크립트는 null, boolean, 유한한 number, string 또는 이런 값으로 된 array나 plain object가 아닌 값(순환이 있거나 JSON이 버리는 property가 있는 값 포함, 예: ArrayBuffer, typed array, Date, Map)을 거부하고, `the message holds an ArrayBuffer, which is not JSON`처럼 type을 밝히는 이유로 `{error}`를 보내며, host는 애플리케이션 로그에 `error page document message <name>: <reason>`을 쓴다. 다른 문서에는 메시지 통로가 없다.
- 영역 문서는 소유 창의 다크 또는 라이트 모양을 따른다. `prefers-color-scheme`은 앱 모드와 일치하고 모드와 함께 바뀐다. 호스트는 같은 WebKit 위의 Safari 사용자 에이전트를 보낸다. 호스트는 `applicationNameForUserAgent`로 WebKit 사용자 에이전트 뒤에 `Version/<major>.<minor> Safari/605.1.15`를 붙이며, 버전은 `/Applications/Safari.app`에 있는 시스템 Safari의 `CFBundleShortVersionString`이다. 영역이 Safari로 자신을 밝히는 이유는 사이트가 사용자 에이전트의 브라우저 이름으로 페이지를 고르고 브라우저 이름이 없는 WebKit 사용자 에이전트에 축소된 페이지를 보내기 때문이다. Google 검색은 그 사용자 에이전트에 회색 버튼이 있는 기본 페이지를 보내고 Safari에는 현재 페이지를 보낸다. 사이트 자체의 라이트 또는 다크 디자인은 바꾸지 않는다. Google 검색은 Safari에서처럼 두 모드에서 같은 모양으로 남는다. 사이트는 같은 설정 디렉터리로 한 이전 방문에서 저장한 모양을 보일 수 있다. 호스트는 Safari 버전을 읽지 못하면 문서 생성에 실패한다.
- `go`는 `back`, `forward`, `reload`, `stop`, 또는 0이 아닌 정수 `offset`과 함께 `entry`를 실행하고 실행 여부를 반환한다. `entry`는 현재 항목에서 그 거리만큼 떨어진 세션 기록 항목을 연다. 기록 밖의 `offset`은 false를 반환하고, 다른 동작에 `offset`을 주거나 `entry`에 주지 않으면 오류다.
- WebKit은 영역이 떠난 각 page를 back-forward cache에 WebContent process와 함께 멈춰 두고, cache가 용량을 넘을 때까지 유지한다. 5분 동안 숨겨진 영역은 back-forward cache를 비우고, host의 [memory pressure](hosts.ko.md#memory-pressure) source가 `warn` 또는 `critical`을 알리면 모든 영역이 비우고, `normal` 알림은 아무것도 비우지 않는다. back 또는 forward 항목이 없는 영역은 비울 것이 없다. 비울 때마다 `reason`이 `hidden` 또는 `pressure`인 이벤트 `native.document.backforward_cleared`로 기록한다. 그 뒤 그 영역에서 뒤로 또는 앞으로 이동하면 page를 다시 불러오며, 기록 항목은 유지된다.
- 영역은 [메모리 절약](plugins.ko.md#메모리-절약)의 질의에 `{media, capture, form}`으로 답한다. `media`는 웹뷰의 private `_isPlayingAudio`, 곧 페이지의 media 요소가 재생 중이고 mute가 아니며 volume이 0보다 큰지이고, `capture`는 공개 `cameraCaptureState` 또는 `microphoneCaptureState`가 active인지이며, `form`은 어느 frame 문서가 form 표시를 가졌는지다. 공개 `requestMediaPlaybackStateWithCompletionHandler:`는 쓰지 않는다. 답이 `paused`인 것은 페이지의 media session이 paused일 때뿐이라서 WebKit은 한 번도 재생하지 않은 media 요소가 있는 페이지에 `playing`을 답한다. 영역의 content world 스크립트는 모든 frame에서 실행되어 자기 frame 문서의 식별자를 만들고, form field(`input`, `textarea`, `select`) 또는 `contenteditable` 요소의 첫 trusted `input` 이벤트를 알린다. 영역은 식별자마다 표시를 두고, 그 frame 문서의 `pagehide` 또는 form `submit`이 표시를 지우며, reload를 포함한 main frame navigation commit이 모든 표시를 지운다. 닫힌 영역의 질의는 오류로 답한다.
- 영역은 공개 `interactionState`를 base64로, 웹뷰가 주지 않으면 빈 글로 돌려준다. 아무것도 불러오지 않은 영역은 base64 `interactionState`를 복원한 뒤 그 기록의 현재 항목을 불러온다. 이미 문서를 불러온 영역(`the document region has already loaded a document`), base64가 아닌 값(`the interactionState is not base64`), 웹뷰가 기록 항목을 하나도 복원하지 않는 값(`the web view refused the interactionState`)은 거부한다.
- 호스트는 `document-state {surface, document, state}`를 소유 표면에만 보낸다. `state`는 `{url, title, loading, progress, canGoBack, canGoForward, error, scroll: {x, y}, history: {entries, index}, link, navigations}`이다. `navigations`는 문서가 시작한 탐색의 수이며, 각 탐색이 시작할 때 한 번 센다. 따라서 탐색의 progress는 그 값을 바꾸지 않는다. `link`는 문서에서 포인터 아래에 있는 링크의 주소이거나 빈 글이며, 영역의 분리된 content world 스크립트가 `mouseover`와 `mouseout`에서 알린다. `error`는 마지막 로드 실패 또는 null이고, `scroll`은 CSS 픽셀 단위의 문서 스크롤 위치이며, `history`는 영역의 세션 기록이다. `entries`는 가장 오래된 항목부터 가장 새 항목까지 `{url, title}`을 나열하고 `index`는 현재 항목의 위치다. 첫 로드 전에는 `entries`가 비어 있고 `index`는 -1이다. 기록은 웹뷰의 뒤로-앞으로 목록에서 오므로 그 목록이 유지하는 항목을 가진다. 요소와 요청 스트림은 `document-state`에 들어가지 않으며 [문서 스트림](#문서-스트림)에서 정의한다.
- 호스트는 표면이 제거될 때, 그리고 표면 페이지가 새 문서를 표시하기 시작할 때 그 문서가 다시 붙이기 전에 표면의 영역을 닫는다. 새 문서는 자기 영역을 직접 붙인다.
- 대화 상자가 열려 있는 동안 호스트는 표면 문서 블러와 같은 반경으로 영역을 흐리게 한다.
- 영역은 표면과 같이 네이티브 입력에 참여한다. 포인터 입력은 앱을 활성화하지 않고 좌표의 영역에 도달하며, 페이지 초점 변경은 앱의 키보드 초점을 옮기지 않는다. `host.window`는 영역을 `documents`로 나열하며, 각각 자기 web view의 WebContent process(`process`, 그 process가 시작되기 전에는 0)를 가지고, 문서 웹뷰 또는 그 자손이 창의 네이티브 first responder일 때만 `focused`를 참으로 보고한다. `host.hit`은 `{kind: "document", surface, document}`를 보고한다([공개 항목](exposure.ko.md)).
- 표시 완료 대기에는 영역이 포함되지 않는다. 영역의 콘텐츠는 독립적으로 렌더링된다.

### 문서 스트림

문서 영역의 요소와 요청 데이터는 스트림이다. 스트림은 페이지가 구독하는 동안에만 모으므로, 구독자가 없는 영역은 요소나 요청 데이터를 보내지 않는다. 스트림 메시지는 구독을 만든 표면에만 도달한다.

- `subscribe {document, stream}`은 구독을 열고 `handle`로 답한다. `stream`은 `elements` 또는 `requests`다. `unsubscribe {document, handle}`은 구독을 끝낸다. 알 수 없는 document나 handle, 또는 호출한 표면이 소유하지 않은 document를 지정한 호출은 명시적 오류로 거부한다.
- plugin-api의 document 손잡이는 `subscribe(stream, listener)`를 가지며, 이것은 `close()`가 구독을 끝내는 handle을 돌려준다. listener는 자기 구독의 메시지를 순서대로 받는다.
- 호스트는 영역과 스트림마다 구독 수를 센다. 첫 구독이 스트림의 수집을 시작하고, 마지막 제거가 수집을 멈춘다. 호스트는 구독을 만든 표면 페이지가 새 문서를 로드할 때, 그 페이지의 web content process가 종료할 때(`webViewWebContentProcessDidTerminate:`), 또는 구독의 영역이나 창이 닫힐 때 그 구독을 제거한다. 영역의 마지막 `requests` 구독이 제거되면 그 영역의 요청 기록이 해제된다.
- 스트림을 노출하는 plugin의 status는 subscribe 함수에서 구독하고 stop 함수에서 구독을 끝낸다([노출](exposure.ko.md)). 감시 없이 그 status를 읽으면 구독하여 첫 메시지를 기다린 뒤 구독을 끝내며, 10초 안에 메시지가 없으면 명시적 오류로 실패한다.
- `elements`는 스냅샷 스트림이다. 문서 스크립트는 문서 해석이 끝날 때와 요소 트리 또는 `id`, `class` 속성이 바뀔 때 트리를 바뀐 것으로 표시하며, 변경마다 트리를 순회하지 않는다. 트리가 바뀐 것으로 표시되었거나 구독이 시작되었고 확인되지 않은 스냅샷이 없으면, 네이티브는 문서에서 스냅샷을 모아 `seq` N으로 호스트에 보낸다. 네이티브는 호스트가 `stream.ack {document, stream, seq}`로 N을 확인할 때까지 다음 스냅샷을 보내지 않는다. 호스트는 스냅샷을 스트림의 모든 구독에 전달한 뒤 확인을 네이티브에 보낸다. 호스트는 영역과 스트림마다 전달 중인 스냅샷 하나를 보관한다. 구독은 받은 가장 최근 스냅샷 하나만 보관한다. 확인되지 않은 스냅샷 중에 시작된 구독은 확인 뒤 네이티브가 보내는 다음 스냅샷을 받는다. 확인되지 않은 스냅샷 동안의 변경은 확인 뒤 스냅샷 한 개를 더 만들므로, 순회는 변경마다가 아니라 확인된 스냅샷마다 한 번 실행된다.
- 스냅샷은 `{seq, nodes, total, truncated}`다. `nodes`는 주 프레임 문서의 요소를 문서 순서로 최대 500개 나열하며, 각각 `{depth, tag, id, class}`로 소문자 태그 이름과 `id`, `class` 속성 값 또는 빈 문자열이다. `total`은 주 프레임 문서의 요소 수이고, `total`이 500보다 크면 `truncated`가 참이다. 순회는 주 프레임 문서의 요소 트리만 대상으로 하며, shadow root와 프레임은 그 밖에 있다. `seq`는 영역과 스트림의 스냅샷마다 증가하고 이동을 지나도 계속 증가한다.
- `requests`는 항목 스트림이다. 문서 스크립트는 resource 항목을 `buffered: true`로 관찰하고, 새 항목의 묶음을 보내며 전체 목록을 다시 보내지 않는다. 각 항목은 `{url, type, start, duration}`이다. 탐색 항목이 먼저 오고 그다음 각 자원이 기록된 순서대로 온다. `type`은 `navigation` 또는 자원의 initiator 형식(`img`, `script`, `link`, `fetch`, `xmlhttprequest`, `css`, `other` 등)이고, `start`와 `duration`은 탐색 시작부터의 밀리초다. Performance API는 요청 메서드, 헤더, 본문, 응답 상태, 하위 프레임의 요청, 호스트 스크립트가 실행되기 전에 페이지가 만들고 자원 타이밍 버퍼가 버린 요청을 기록하지 않으므로 스트림에는 이것들이 없다. 스크립트는 페이지의 스크립트가 소유하는 자원 타이밍 버퍼를 비우지 않는다. 관찰자는 버퍼가 가득 찼는지와 관계없이 모든 항목을 받으므로, 가득 찬 버퍼가 스트림의 항목을 버리지 않는다.
- 영역은 최대 200개 항목의 기록을 보관한다. 새 구독은 첫 `entries` 메시지로 기록을 받고 그 뒤에 새 항목을 받는다. 각 `entries` 메시지는 마지막 `reset` 이후 기록이 버린 항목 수 `dropped`를 담는다.
- 영역의 새 문서는 두 스트림의 모든 구독에 `reset`을 보낸다. reset은 확인되지 않은 스냅샷을 버리고 요청 기록을 비운다. `seq`는 계속 증가하므로, reset 전에 보낸 스냅샷에 대한 확인은 아무것도 해제하지 않으며 오류도 아니다. 네이티브는 보내지 않은 `seq`에 대한 확인을 문서, 스트림, `seq`를 밝히는 명시적 오류로 거부한다. `reset` 뒤에는 각 스트림이 새 문서의 데이터를 모이는 대로 보낸다.
- 호스트는 `document-stream {surface, document, stream, handle, message}`를 구독을 만든 표면에만 보낸다. `message`는 `{type: "snapshot", seq, nodes, total, truncated}`, `{type: "entries", entries, dropped}` 또는 `{type: "reset"}`이다. `elements` 스트림은 `snapshot`과 `reset` 메시지를, `requests` 스트림은 `entries`와 `reset` 메시지를 보낸다.
- 호스트가 스냅샷을 확인하지 않으면 다음 스냅샷은 대기한다. 구독은 그 페이지, web content process 또는 영역과 함께 끝나며, 구독이 끝나면 대기 중인 스냅샷이 해제된다.
- 문서 스크립트는 호스트 자체 콘텐츠 월드에서 실행되고 그 월드의 스크립트 메시지 처리기로 보낸다. 페이지 스크립트는 다른 월드에서 실행되어 그 처리기에 보낼 수 없으므로, 페이지는 스트림 데이터를 쓸 수 없고 자기 문서를 바꿔서만 스트림이 보고하는 내용을 바꿀 수 있다.

## 그림 영역

그림은 사이드카가 만들고 영역을 통해 코어에 공급한다. 코어는 불투명한 토큰과 픽셀 크기만 받으며, 그림 버퍼도 공급자의 정체도 토큰 외에는 알 수 없다.

- **그림 공급과 크기 검증**: manifest가 공급 사이드카를 지정한다. 호스트는 적용한 네이티브 프레임에서 래스터 리비전과 정확한 크기를 계산해 공급자에게 보낸다. 프레임은 부착 세대, 래스터 리비전, 단조 증가 시퀀스, 실제 토큰 크기, 예상 크기, 창 배율이 모두 맞아야 한다. 불일치는 거절하며 이전 유효 스냅샷을 교체하지 않는다.
- **장치 픽셀 보고**: 영역은 CSS 픽셀이 아닌 장치 픽셀 단위로 크기를 보고한다.
- **입력 처리**: 포인터 event는 아래 surface document로 통과하고 cursor는 그 document가 결정한다. Region은 cursor rectangle이나 cursor tracking area를 등록하지 않는다. Keyboard input, composition, accessibility는 region이 소유한다. Native region은 terminal history를 담지 않는 전용 marked-text buffer를 소유하는 `NSView` input client다. Glyph, marked-text decoration, selection, insertion point, focus ring, automatic editing indicator를 그리지 않으며 sidecar image만 표시한다. 각 outer input scope는 `{type: "input", actions, preedit, errors}` event 하나를 보내며 consumer는 해당 transaction의 ordered action과 최종 preedit/focus state를 표시 전에 적용한다. 이 경계는 뒤늦게 도착하는 비동기 PTY output까지 같은 표시로 묶지 않는다. 나중 event로 받은 output은 이후 frame에서 표시될 수 있다. Key는 page에 전달하고 command-key 조합은 application menu에 맡기며 focus는 host 요청으로 바꾼다. `host.window`는 현재 위치를 보고한다. Pointer press는 page로 통과한다. Press 준비 중 AppKit responder handoff는 region focus를 바꾸지 않는다. 다른 image region 내부 press는 region 간 focus를 직접 옮긴다.
- **Input callback state**: 각 `native.input.callback` record에는 `before`, `after` state object가 포함된다. 두 object의 `active`, `keyWindow`는 각각 해당 state를 캡처할 때의 `NSApp.isActive`, 소유 window의 `isKeyWindow`에서 가져온 JSON boolean이다. 현재 marked buffer 밖을 지정하는 marked-text replacement는 변경 전에 거부하고 input error를 기록하며 같은 input scope의 후속 callback을 latch한다. 마지막 유효 preedit을 보존하고 잘못된 action을 publish하지 않는다.
- **최종 preedit snapshot**: Native 입력 client는 AppKit replacement range로 편집되는 UTF-16 pending-text buffer와 selection만 소유한다. Buffer에는 현재 pending composition만 있고 commit된 terminal history는 없다. `markedRange`와 `selectedRange`는 이 buffer 기준이다. 유효한 partial replacement는 Foundation으로 적용하며 양쪽 pending text를 보존한다. Region API에는 terminal text-context query가 없으므로 native는 accessibility snapshot을 입력 text로 재사용하거나 PTY history를 editable context로 노출하지 않는다.
- **Insert action**: `insertText`는 명시적 유효 replacement를 pending buffer에 적용한 결과 전체를 한 ordered committed insert action으로 한 번 보낸다. `replacementRange == NSNotFound`이면 전달된 text를 현재 marked composition의 replacement로 commit한다. 일반 `NSTextView` reference에서 `setMarkedText("abc", selectedRange: {1,1})` 뒤 `insertText("x", replacementRange: NSNotFound)`의 결과도 동일하다. `setMarkedText`도 유효한 replacement를 적용해 양쪽 pending text를 보존하고 변경된 buffer 전체를 preedit으로 보낸다. `unmarkText`와 명시적 commit 경계(command, focus 상실, input-source 변경, close)는 현재 pending text를 한 번 commit하고 buffer를 지운다. 앞선 `insertText`가 buffer를 비웠다면 뒤의 `unmarkText`는 추가 action을 만들지 않는다. 빈 `setMarkedText` callback은 cancel이며 buffer를 지우고 commit하지 않는다. Range metadata는 입력 출처 기록이며 PTY consumer가 replacement를 다시 적용하지 않는다. Region을 닫을 때는 responder를 분리하기 전에 pending text를 commit하고 input context에 marked state 폐기를 요청하며 diagnostic context override를 지운 뒤 view를 해제한다.
- **Input transaction**: 가장 바깥 native input scope는 action, 변경된 최종 preedit 또는 callback error가 있을 때 최대 한 개의 `{type: "input", actions, preedit, errors}` event를 보낸다. `actions`에는 committed `insert`와 정확한 callback 순서의 `key`, `command`, `focus`가 들어간다. Insert action은 중간 preedit 없이 `text`, `replacementRange`, `attributed`를 담는다. `preedit`는 AppKit의 실제 marked range만 담는 필수 최종 strict snapshot이며 marking이 해제되면 명시적 empty snapshot을 보낸다. 중간 composition report는 최종 snapshot으로 대체한다. `errors`에는 callback 실패를 발생 순서대로 `{reason}`에 담으며 error는 action이 아니다. Input client는 callback range를 소유한 marked buffer 기준으로 mutation 전에 검증하며 invalid range는 scope를 latch하는 callback error로 보고한다. 물리적 `keyDown:` scope는 그 안에서 동기적으로 발생한 AppKit text-input callback을 하나의 correlation identifier로 묶는다. Key scope 밖의 단독 text-input callback은 자체 transaction이 된다. Action이나 변경된 preedit 또는 error가 없는 key scope는 event를 보내지 않는다. 첫 callback error는 scope 안에서 latch된다. 이후 text-input callback은 입력 문서를 바꾸거나 action을 추가하지 않고 error reason 및 전후 state와 함께 거부 기록을 남긴다. Transaction은 error 전에 유효했던 action과 마지막 preedit을 유지하며, 새 outer scope가 latch를 초기화한다. Consumer는 transaction 전체를 side effect 전에 검증한 뒤 순서 있는 byte-producing action을 batch 하나로 제출하고 write 결과 뒤 최종 preedit/focus state를 적용한 후 그린다. 중간 frame은 내지 않는다. Callback error가 있는 유효 transaction도 앞선 유효 action을 제출하고 마지막 유효 preedit을 적용한 뒤 error를 표시한다. 잘못된 transaction은 write나 state effect 전에 거부한다. Batch write가 error를 반환하면 consumer는 제출한 batch와 byte 진행 상태를 알 수 없음을 보고하며 rollback이나 재시도를 주장하지 않는다. 이 경계는 PTY echo를 기다리거나 timer/local echo를 사용하지 않는다.
- **구현 참고**: 아래 공개 macOS client는 callback batching의 서로 다른 방식을 보여주는 참고이며 이 contract의 추가 요구사항은 아니다. [Ghostty](https://github.com/ghostty-org/ghostty/blob/fa141a726203224c12b831e0513530fa2406ef26/macos/Sources/Ghostty/Surface%20View/SurfaceView_AppKit.swift#L991-L1044)는 `keyDown:` 중 insert text를 모으고 key 해석 뒤 preedit을 동기화한다. [WezTerm](https://github.com/wez/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/window/src/os/macos/window.rs#L1873-L2009)는 별도 IME buffer를 유지하고 insert text를 전달한다. [kitty](https://github.com/kovidgoyal/kitty/blob/81535d9b338e60c481dbdd5a4da286685f694b5d/glfw/cocoa_window.m#L1207-L1255)는 key event 주변에서 text callback과 preedit 갱신을 묶는다. 이런 callback 경계는 나중에 비동기로 도착한 PTY output이 같은 frame에 표시된다는 근거가 아니다.
- **Input trace sequence**: Native input transaction과 대응 terminal request를 보존하는 diagnostic record는 각 trace 안에서 0부터 시작하는 sequence를 사용한다. 첫 record의 sequence는 `0`이고 이후 record는 더 큰 sequence를 가진다. Consumer는 0 이상의 안전한 정수만 받고 terminal request가 native report 뒤에 오는지 계속 확인한다.
- Focused image region 안의 click-through press는 application을 활성화하지 않고 hit view에 직접 전달되는 diagnostic `input.pointer` press를 포함해 focus loss가 아니다. Physical AppKit input과 diagnostic pointer input 모두에서 region은 paired release까지 focus를 유지한다. Region 바깥 또는 다른 image region 안의 press는 focus를 바꾼다.
- **접근성**: 영역은 접근성 요소다. 그 값은 소유자가 `setAccessibleText`로 주는 화면 텍스트다.
- **그림 소비**: 호스트는 받은 전송 그림을 호스트 소유 불변 표시 저장소로 복사한 뒤 `consumed`로 답한다. 공급자는 그 답 전까지 전송 그림을 수정하거나 재사용하면 안 된다. 네이티브 레이어는 공급자가 덮어쓸 수 있는 저장소를 가리키지 않는다. 소유 창이 없는 표면의 전송 그림에는 `{image:{error:"closed",name,generation,raster,sequence}}`로 답하므로, 공급자는 그 그림을 놓고 같은 id 표면의 이후 답을 그 그림에 맞추지 않는다.
- **그림 색 공간**: macOS에서 IOSurface는 Core Graphics color space의 직렬화 property list로 `kIOSurfaceColorSpace`를 선언할 수 있다. 호스트는 불변 이미지 snapshot을 만들 때 선언된 color space를 사용하고, 태그가 있는 픽셀을 DeviceRGB라고 다시 지정하지 않는다. 태그가 없으면 기존 DeviceRGB 해석을 유지한다. 선언은 있지만 Core Graphics가 해석하지 못하는 property list는 `presentFailed`로 표시를 거절한다. Image-capture 진단은 color-space 선언이 없거나 해석되지 않으면 unknown으로 처리하고 색이 일치한다고 인정하지 않는다.
- **그림 프레임 identity**: 네이티브 그림 영역은 불변 snapshot과 함께 받은 프레임의 `{generation,raster,sequence}` identity를 보존한다. 이는 레이어가 보유한 source transfer를 식별하며 Core Animation이나 디스플레이가 해당 프레임을 실제로 표시했다는 뜻은 아니다. image-capture 진단이 매칭을 요청하는 동안 호스트는 정확한 source raster bytes, identity, 배율, 색 표현, 네이티브 화면 경계의 제한된 이력(64 MiB, 512 snapshots)을 보존한다. 각 완전한 ScreenCaptureKit sample은 기하 정보와 일치하는 이력 crop과 픽셀을 정확히 비교한다. Crop 좌표 변환과 배율이 호환되어야 하며 source와 capture의 pixel format 및 색 표현이 알려지고 호환되어야 한다. 기하, 배율, 색 metadata가 없거나 호환되지 않으면 사유를 포함해 unknown으로 보고하고, 픽셀이 다르면 unmatched로 보고한다. 같은 픽셀이 반복되면 일치하는 identity를 모두 ambiguous로 보존하며 최근 값 하나를 선택하지 않는다. 보고는 sample의 `displayTime`을 관측된 capture 상관값으로 기록하지만 Core Animation이나 디스플레이가 그 시각에 source transfer를 실제 표시했다고 주장하지 않는다. Source history 용량 초과로 snapshot이 밀려나면 관측 가능해야 하며, 후보가 밀려났을 수 있는 미일치는 unknown으로 보고한다. 추가 source snapshot은 matching 진단이 활성화된 동안만 보존하고, 화면 표시를 위해 필요한 현재 snapshot은 계속 보존한다. 진단 복사와 픽셀 비교는 메모리 및 callback 처리 비용을 추가하므로 측정한 callback 시간은 이 계측을 포함하며 계측이 없는 비용을 입증하지 않는다.
- **Diagnostic frame identity cleanup**: 선택 capture는 image layer에 identity code를 표시하면서 immutable untagged source snapshot을 별도로 보존할 수 있다. Identity capture가 중지되거나 실패하면 host는 producer frame을 기다리지 않고 모든 live image-region layer를 최신 raw snapshot에서 즉시 복원한다. Cleanup은 idempotent하며 region geometry, visibility, focus, input state를 바꾸지 않는다.
- **Image capture raster evidence**: Exact pixel equality는 긍정적인 match 증거다. Byte가 다르면 unmatched로 보고하지만 source image가 없다는 뜻은 아니다. Pixel format 및 color-space metadata가 같아도 image rendering 또는 capture pipeline이 pixel 값을 변환할 수 있다. Capture matching이 활성화된 동안 호스트는 snapshot을 수락하는 즉시 고유 source identity마다 capture의 `sources` folder에 artifact를 쓴다. 동일 identity 반복은 metadata와 byte가 모두 같을 때만 멱등 처리하며, 값이 다른 재사용은 drop으로 거절한다. `.bgra` 파일에는 수락된 원본 snapshot byte를 변환 없이 보존한다. Format 2 `manifest.json` 항목은 identity, byte file name, width, height, stride, alpha 및 color 표현, screen bounds, scale, byte count, SHA-256을 기록한다. Artifact는 identity 512개로 제한하며 source raster 하나는 64 MiB in-memory matching history에 들어가야 한다. Serial capture writer의 queued 및 active source raster byte 합계는 artifact 총 byte와 별개로 64 MiB 이하로 제한한다. Pending-byte budget을 넘는 source는 명시적으로 거절해 기록하며 history lock을 잡고 enqueue를 기다리지 않는다. Matching history는 64 MiB와 snapshot 512개로 제한되며 eviction은 계속 `unknown-retention`으로 관측된다. Source가 raster 또는 identity 한도를 넘거나 identity가 충돌하거나 기록에 실패하면 drop으로 보고하고 partial file을 제거한다. Manifest는 write failure, partial-file cleanup failure와 최대 32개의 cleanup error 상세 및 생략된 상세 개수를 기록한다. Artifact write가 실패하면 capture finalization도 실패한다. Artifact는 기존 capture writer queue를 사용하며 image presentation thread에서 쓰지 않는다. Artifact는 diagnostic capture에서만 생기며 캡처 중 disk I/O를 추가한다.
- **권한**: 영역이 공급을 허가할 사이드카를 지정한다. 호스트는 등록되지 않은 사이드카의 그림을 오류와 함께 거절한다.
- **오류 보고**: 호스트가 그림을 표시할 수 없으면 영역이 오류 이벤트를 보낸다: `{type: "error", reason}`. 사유에는 `notFound`(IOSurface를 찾지 못함), `forbidden`(접근 거부), `size`(선언한 크기가 IOSurface의 실제 크기와 맞지 않음), `scale`(창 배율과 다른 배율로 그린 그림), `presentFailed`(플랫폼 표시 실패)가 있다.
- **끝난 사이드카**: 어떤 plugin도 선언하지 않는 사이드카의 그림, 예를 들어 카드가 열린 채 plugin을 제거할 때 오가던 그림은 buffer와 함께 끝난 process의 것이다: 호스트는 그것을 표시하지 않고 `stale`로 답하고 기록하며, 오류 이벤트를 보내지 않고 복구를 시작하지 않는다. 끝난 사이드카에 닿지 못하는 답은 보내지 않음으로 기록된다.

`host.window.regions[].error`는 유효한 프레임이 표시될 때까지 마지막 네이티브 표시 거절을 유지한다. 이전의 유효 스냅샷이 이후 거절을 없애지는 않는다. 그림 픽셀은 네이티브 백킹 배율에서 크기를 유지하며, 레이어 크기 변경으로 글자를 늘려 새 영역을 채우면 안 된다.

두 호스트는 각 네이티브 그림 이벤트를 `image-event {surface, name, event}`로 소유 표면 웹뷰에만 전달한다. 빈 콜백, 전체 전송, 키보드 전달을 직접 사이드카 명령으로 대체하는 것은 계약 위반이다. 잘못된 이벤트 JSON과 전달 실패는 보고하며 null 이벤트로 대체하지 않는다.

터미널은 최신 셀 행을 `terminal.screen`으로 공개하고 사이드카 화면 이벤트마다 구독자에게 알린다. 입력 검사는 네이티브 클릭과 키를 사용하고 이 알림을 기다리며, 보이는 터미널 최소 3개에서 편집·명령 출력·입력 격리를 확인한다. `terminal.input`은 직접 사이드카 입력만 검사하며 네이티브 키보드 전달을 검증하지 않는다.

입력기 preedit activation 검사는 AppKit reference의 전체 document를 terminal의 committed screen cell 및 `terminal.compose`와 비교한다. 같은 document여도 AppKit reference와 image region의 marked state는 다를 수 있으므로 각 owner의 marked/selected range를 따로 검증한다. Cursor와 preedit을 제공한 screen event의 정확한 `{generation,raster,sequence}`를 `terminal.cursor`가 담아야 한다. `terminal.screen.read.frame`은 base cell 행을 가리키며 image region은 그 행을 바꾸지 않고 이후 overlay frame을 표시할 수 있다. Region의 presented identity는 같은 generation/raster의 진행 watermark이며 cursor source보다 sequence가 늦을 수 있다. 이 값은 exact cursor source identity를 대신하지 않으며 marked glyph가 보인다는 증거도 아니다.

각 terminal key의 native 또는 terminal input callback은 key가 input 경로에 도달했음을 확인할 뿐, terminal이 key 처리를 끝냈다는 뜻은 아니다. Activation 검사는 coherent status notification과 reread를 기다려 committed text와 preedit을 합친 전체 document가 같은 window의 AppKit reference document와 일치하는지 확인한다. Coherent하더라도 중간 document라면 이후 status notification을 기다린다. 기존 key별 1500 ms 제한은 유지하며, 기대한 document가 도착하지 않으면 검사는 실패하고 모든 중간 status와 capture frame을 보존한다.

Visual stage planning은 `terminal.screen.read.frame`을 base-row identity로, `terminal.cursor.frame`/`terminal.cursor.render.frame`을 overlay identity로 취급한다. Cursor와 render identity는 정확히 같아야 한다. Base screen은 같은 generation과 raster를 가져야 하며 sequence는 cursor frame보다 늦을 수 없다. 그 rows는 index된 observer event의 rows와 같아야 한다. 관측한 presented watermark는 cursor frame과 같은 generation/raster를 가지며 sequence가 cursor frame보다 작지 않아야 한다. Host presentation state는 image region에 적용된 최신 frame을 보고하므로 cursor source를 읽은 뒤 더 늦은 presentation이 watermark를 진행시킬 수 있다. Exact source identity는 cursor/render frame과 index된 row state이며 retained source candidate와 capture pixel이 visual proof를 판단한다. Overlay draw는 rows가 바뀌지 않은 상태에서 sequence를 진행할 수 있고 rows-only screen status는 같은 값을 생략하므로 screen과 cursor의 sequence 일치는 잘못된 조건이다. Row source는 active observer stream에서 index한 가장 최근 이전 `terminal.screen` event여야 한다. 이후 event, 분리된 read 또는 최신 presented sequence로 이를 대체하지 않는다. Input receipt는 transaction의 key action에 맞춰 판정한다. Korean input source의 `k` receipt는 공백이 아닌 insert 또는 non-empty compose-only preedit일 수 있지만, Backspace command나 공백 insert가 함께 든 transaction은 `k` receipt가 아니다. Backspace는 해당 key 또는 `deleteBackward:` command와, Space는 해당 key 또는 공백 insert와 일치한다. Focus, coherent state와 AppKit document 비교는 각 key에 대해 실행하지만 visual planning과 pixel evaluation은 10개 key, callback, 전체 recording을 보존한 뒤 실행한다. 그래야 초반 visual mismatch가 승인된 gesture의 나머지 기록 수집을 중단시키지 않는다.

Terminal의 `terminal.screen` status는 rows를 담고 JSON 값이 같으면 notification을 생략한다. 따라서 rows가 그대로인 screen event는 `terminal.screen` notification 없이 `terminal.cursor.frame`과 preedit/render metadata만 갱신할 수 있다. Image generation 또는 raster만 바뀌어도 rows status 값은 image identity와 독립적이므로 기존 rows를 무효화하지 않는다. Capture index는 cursor event와 인접한 event만 요구하지 않고, 그 앞에 있는 최신 `terminal.screen` status event를 사용한다. Cursor의 base screen 출처인 screen event index와 rows를 기록한다. 이미 관측한 같은 stream의 이전 event만 재사용할 수 있으며 이후 event나 분리된 screen read로 출처를 채우지 않는다. 이전 screen status event가 없으면 frame에 rows 출처가 없으므로 측정은 no proof다. Cursor frame과 render frame은 계속 정확히 일치해야 하며 compose/preedit도 의미상 같아야 한다.

각 capture sample에서 검사는 전체 raster `imageMatch` 결과를 변경하지 않고 보존된 capture source에서 별도 candidate를 계산한다. Declared capture content rectangle, display bounds, scale 및 color representation으로 각 source를 캡처 frame에 매핑한다. Committed text와 preedit을 포함한 전체 입력 span 및 guard cell의 정확한 pixel byte를 source crop과 capture crop 사이에서 비교한다. Crop이 일치한 모든 source identity를 유지하며 `latestRetainedSource`만으로는 candidate를 만들지 않는다. 각 candidate에는 기대 전체 document, compose/preedit text, owner별 marked/selected range, focus와 cell geometry를 담은 cursor frame 및 status state 기록이 있어야 한다. Target `terminal.cursor.frame`이 그 집합에 있어야 하고 모든 candidate의 semantic state가 기대값과 같아야 한다. 여러 identity가 일치하면 모호함을 그대로 기록하고 최근 identity를 선택하거나 물리적으로 유일한 frame이라고 주장하지 않는다.

진단 build를 명시적인 `SOKSAK_VT_TRACE_DIR`로 시작하면 terminal cursor status는 일치하는 `frame`, `preedit`와 함께 `screen.render` object를 원자적으로 공개한다. Startup option이 없으면 `render`는 null이고 glyph bounds를 계산하지 않는다. Non-null object는 정확한 frame identity를 반복하고 `pixel` `{width,height,bytesPerRow,format:'bgra8',alpha:'premultiplied',colorSpace:'sRGB',origin:'top-left'}`, `grid` `{rows,cols,origin:{x,y},cellWidth,cellHeight}`, `font` `{family,size,ascent,descent,leading,baselineFromCellTop}`을 담는다. Top-level `underline`은 `positionFromBaseline`, `positionCoordinate:'CoreText y-up'`, `thickness`, `minimumThickness`, `colorSource:'glyph.foreground'`를 담는다. `cursor`는 nullable `rect`, shape, visibility, blink visibility, focus, blend (`normal` 또는 `difference`), effective color (`null` 또는 opaque sRGB `#rrggbb`), border를 담는다. 각 `glyphs[]` 항목은 row, column, cell width, 양수 `fontRuns`, grapheme, overlay 및 inverse를 해석한 draw-time opaque sRGB `foreground`와 `background`, leading-cell origin 기준 nullable finite signed fractional `bounds`, nullable `underline.rect`를 담는다. Preedit overlay가 PTY text를 대체해도 원래 PTY screen cell은 바뀌지 않으므로 glyph 색은 draw-time 값이다. Glyph bounds는 leading-cell origin만 뺀 raw `CTFont`/`CTLine` ink bounds이며 underline rectangle도 같은 leading-cell coordinate origin을 사용한다. 둘 다 cell span을 넘어갈 수 있고 원래 값을 보존한다. Difference blend block cursor는 destination pixel을 반전하므로 `color:null`을 보고한다. Renderer는 측정한 draw 입력과 geometry만 공개하며 test threshold나 coverage 판정은 공개하지 않는다. 기본 경로는 glyph bounds를 계산하거나 cell별 render record를 할당하지 않는다. Frame과 render metadata는 같은 성공한 draw에서 image와 screen message를 보내기 전에 생성되며, 실패하거나 지연된 draw의 pending screen state에는 metadata가 없다.

Native capture source artifact는 자체 표현을 유지한다. `manifest.json`은 `pixelFormat:'BGRA8'`, `alpha:'premultiplied-first'`를 기록하고 `.bgra`는 변환하지 않은 원본 byte를 담는다. 이 label은 producer의 `bgra8`/`premultiplied` 별칭이 아니다. Consumer는 각 interface를 따로 검증한다. Producer `bgra8` byte는 artifact의 선언된 BGRA 순서로 대응시키고 premultiplied channel은 artifact alpha 선언으로 decode한다. Alpha `a > 0`인 sample의 저장된 B, G, R byte `c`는 producer hex color와 비교하기 전에 opaque sRGB `round(c * 255 / a)`로 변환한다. Alpha가 0이면 색이 없다. 이 변환은 비교에만 쓰며 artifact byte를 다시 쓰거나 label을 바꾸지 않는다.

검사는 동일 frame renderer 값으로 glyph ink와 underline을 따로 측정한다. Predicate는 glyph별 effective `foreground`와 `background`, 각 glyph의 nullable `underline.rect`를 사용하며 판단 중인 capture에서 geometry, threshold 또는 color를 추론하지 않는다. Glyph bounds는 leading-cell origin만 뺀 raw `CTFont`/`CTLine` ink bounds다. 유한한 fractional coordinate는 음수이거나 glyph의 leading-cell span을 넘어갈 수 있으며, validation은 원래 값을 보존하고 ink를 cell 안으로 clamp하지 않는다. Consumer는 rectangle을 frame coordinate로 옮기고 왼쪽/위쪽에 `floor`, 오른쪽/아래쪽에 `ceil`을 적용한 뒤 실제 사용 가능한 raster에 pixel rectangle을 clip한다. Capture raster의 pixel origin은 source `screenBounds`, capture `screenRect` 및 `contentRect`, 그리고 같은 scale에서 계산한다: `frameOrigin = (screenRect.origin - contentRect.origin - source.screenBounds.origin) * scale`. Source raster frame identity는 `terminal.cursor.frame` 및 `render.frame`과 같아야 하며 다른 frame의 geometry는 이 sample의 증거가 아니다. Mapping은 row stride를 반영하며 fractional origin 또는 다른 scale은 거부한다. Raster와 교차하지 않는 rectangle은 no proof다. Block cursor의 `difference` blend는 해당 glyph의 effective color로 계산한다. `normal` blend cursor는 실제 effective color를 공개하며, 그려진 non-difference cursor와 glyph가 겹치면 no proof다. Cursor draw 조건은 `visible && blinkVisible && shape != 'hidden'`이다. 조건이 참이면 `rect`는 non-null이어야 하고, 거짓이면 `rect`와 `color`가 모두 null이어야 한다. Drawn `normal` cursor는 effective color를 보고하며 `difference` cursor는 destination pixel을 반전하므로 `color:null`을 보고한다. 이 값은 PTY screen cell이 아닌 `screen.render`에서 온다. 고정 U+314F (`ㅏ`) fixture에는 glyph 아래쪽 획만 있는 경우, 잘못된 범위의 underline, 빈 block cursor cell을 negative control로 둔다. Predicate는 color-distance threshold와 필요한 coverage를 지정한다. 같은 frame의 public status와 source metadata에 renderer metric이 없으면 visual result는 no proof이며 acceptance는 미완료 상태다. 기대 grapheme마다 glyph ink가 있어야 하며 underline은 terminal의 marked cell에만 있어야 한다. Committed cell에는 underline이 없어야 하고 guard cell에 초과 glyph가 없어야 한다. Cell 경계는 같은 frame의 screen row, cursor와 grid dimensions에서 얻는다. Source width/columns와 source height/rows가 정수 cell edge를 만들어야 한다. Fractional grid cell, 분리된 glyph, offscreen cell mapping 또는 여러 후보 경계는 no proof로 거부한다. 전체 raster 매칭은 정확히 같은 pixel에 대해서만 긍정적인 증거다. 측정한 cell crop만 일치하고 나머지가 다른 unmatched 전체 raster는 marked glyph가 없다는 증거가 되지 않는다.

Review는 glyph 획이 cell 아래쪽까지 내려올 수 있고 cursor color는 appearance에 따라 달라지므로 고정 cell-percentage band를 거부했다. Renderer가 자기 출력의 정답을 제공하지 않도록 producer-supplied pass threshold도 거부했다. 따라서 renderer는 측정된 draw geometry와 resolved style 값만 공개하고 consumer가 pixel threshold와 coverage test를 소유한다. 별도 review는 CoreText rectangle의 fractional edge가 정상일 수 있다고 지적했다. 검사는 이를 거부하지 않고 값을 보존해 선언된 floor/ceil/clip 규칙을 적용한다. Fixture는 낮은 위치의 glyph stroke, 잘못된 underline 범위, 빈 inverse cursor, 비대칭 fractional bounds를 검사한다.

## 인수 기준

- 측정 가능한 모든 녹화 프레임에서 네이티브 콘텐츠가 해당 카드 내부에 있어야 한다. 네이티브 본문, 카드 UI, 레일 사이드바, 외곽 레일의 상대 좌표는 같은 프레임에서 유지되어야 한다. 일시적인 내부 여백 증가도 이 요구사항을 충족하지 않는다.
- 레일 외곽선처럼 카드를 따라가는 페이지 그리기는 마지막 그리기가 카드 요소에 쓴 사각형과 판의 CSS 픽셀을 쓴다. 준비가 대기 중인 동안 격자는 이미 다음 배치를 가지므로, 격자로 그리면 그림이 카드보다 먼저 움직인다.
- 경계를 끄는 동안 녹화된 프레임은 격자가 한 걸음의 배치를 떠난 뒤 최대 화면 네 프레임 안에 그 배치를 보여주고, 끌기 전체에서 지연의 중앙값은 2.5 프레임, 90번째 백분위수는 3 프레임 이하다(60Hz에서 66.7ms, 41.7ms, 50ms). 배치는 입력 도착, 앞 배치의 프레임, WebKit 렌더링 갱신, 화면 갱신의 네 프레임 경계를 지나 화면에 나온다. 배치는 앱 DOM 웹뷰의 다음 표시를 기다리므로, 그 웹뷰는 WebKit 기본값인 60fps 근처 렌더링 대신 화면의 갱신 주기로 렌더링한다. 같은 이유로 앱 DOM 웹뷰는 창이 가려져도 문서를 visible로 유지하고 animation frame을 계속 실행한다. 그렇지 않으면 배치와 그 배치를 기다리는 모든 command가 창이 드러날 때까지 끝나지 않는다. 붙인 surface 웹뷰도 같게 동작하므로, 창이 가려진 동안에도 그 비활성 capture와 paint 확인이 끝난다.
- 이 그리기는 요소의 상자에 맞춰지는 좌표계를 쓰지 않는다. 그 좌표계는 이전 그림을 새 상자에 맞추므로 그림이 카드보다 먼저 움직인다.
- 표시되기 전에 대신된 배치는 화면에 나오지 않으므로, 빠른 두 왕복 사이의 시작 위치처럼 포인터가 한 번의 표시보다 짧게 머문 위치는 녹화에 없을 수 있다. 드래그 녹화는 시작 위치에서 시작하고 끝나며, 왕복마다 먼 끝에 도달한다.
- 드래그 입력은 요청한 속도로 완료되어야 하며 녹화는 드래그 전체를 포함해야 한다. 입력 전에 녹화를 시작한다. 제어 검사는 캡처에서 최종 좌표를 확인한 뒤 녹화를 종료한다. 표시 콜백이나 프레임 시각만으로 종료하지 않는다.
- 녹화 프레임이 부족하거나 대부분의 프레임에서 표면과 카드를 식별하지 못하면 검사는 실패해야 한다.
- 연속 입력 중에도 화면 배치가 갱신되어야 한다. 입력 종료까지 모든 렌더링을 연기하는 구현은 이 명세를 충족하지 않는다.
- 표면 생성, 교체, 숨김, 창 크기 변경, 문서 다시 로드 중에도 이 요구사항을 유지해야 한다.
- 문서 영역은 표면이 이동하거나 크기가 바뀌어도 자기 요소 위에 있고, 앱을 활성화하지 않고 네이티브 스크롤 입력을 받으며, 표면과 함께 닫힌다.
- 소수점 크기 검사는 실제 CSS 사각형과 녹화된 픽셀을 측정한다. 정수 값을 반환하는 뷰포트 조회만으로 렌더링된 문서 영역을 판단하지 않는다.
- 네이티브 표면 내부의 마지막 장치 픽셀도 문서 히트테스트에 포함해야 한다.
- 창 크기 변경과 화면 배율 전환 후에도 네이티브 포인터 좌표가 문서 좌표와 일치해야 한다.
- 설정과 메뉴 웹뷰는 표면 위에 표시해야 한다. 동작은 [data-native-modal](native-modals.ko.md)에 정의한다.

## 플랫폼 범위

표면 배치, 표시 여부, 겹침 순서와 입력은 모든 호스트와 운영체제에서 같은 계약을 따른다. 네이티브 구현은 대상 플랫폼의 API와 좌표계를 사용한다.

플랫폼과 프레임워크의 결함은 필요한 경우 이 저장소 내부의 호스트 네이티브 코어에서 수정한다. 공개 API로 필요한 동작을 정확히 구현할 수 없으면 비공개 API를 사용할 수 있다. 각 수정은 원인을 확인하고, API의 실제 동작으로 사용 이유를 설명하며, 요구사항을 충족하는 최소 구현을 사용하고, 해당 플랫폼에서 좌표·렌더링·입력·생명주기를 검증해야 한다. 해롭거나 불필요한 수정은 제거한다. 테스트 통과는 검사한 동작의 근거이며, 구현 검토에서 필요성과 올바른 API 사용도 확인해야 한다. API 가용성과 유지보수 위험은 수정의 기술적 타당성과 구분해 기록한다. 호스트 간 차이는 프레임워크 연동과 네이티브 동작을 진단해야 하며, 차이 자체로 원인을 확정하지 않는다.

현재 네이티브 표시 검증 대상은 macOS다. Windows와 Linux 동작은 검증하지 않았다. 이 구현은 프레임워크 포크를 포함하지 않는다.

### darwin

macOS 그림 영역의 토큰은 전역 IOSurface 식별자와 그 표면에 붙인 16바이트 논스로 이루어진다. 호스트가 그림을 받으면 식별자로 표면을 조회하고, 논스가 일치하지 않으면 거절한다. 이는 재사용된 32비트 식별자를 방지한다.

IOSurface 식별자는 프로세스 소유자의 전역 사용자 네임스페이스에 있다. 같은 사용자의 다른 프로세스도 표면을 조회해 열 수 있다. 이 신뢰 경계는 사이드카 통신에 쓰는 엔드포인트 소켓과 같다.
