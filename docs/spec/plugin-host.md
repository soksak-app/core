# Plugin host

[한국어](plugin-host.ko.md)

A plugin host is a process of a plugin, with a platform web view attached to the window, that serves the declared statuses of its plugin. It exists only when a [declared status](declared-ui.md#declared-status) of a sidebar section must be served while no view of the plugin is open, and it serves its declared statuses whenever it is their chosen declared status source: the view of the active tab first, the plugin host second. It holds the DOM-free presentation of those statuses, because a sidecar holds the native functionality of one domain, and the sidecar supplies their data. A sidecar or a state module is not a declared status source.

Plugin code does not run on the workbench page, and the main page never runs the code of a plugin host: the host page is a separate web view on the `soksak://<plugin id>` origin, like the view of a view surface ([plugin processes](plugin-processes.md) rule 1). The native hosts and the workbench implement this specification; [feature status](../features.md) records its implementation. Plugin host code does not run on the workbench page, and the workbench imports no plugin code.

## Declaration

The manifest declares the plugin host in `plugin.json` under `host`:

```json
{
  "host": {
    "page": "ui/host.html",
    "state": { "format": 1, "maxBytes": 65536 }
  }
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `page` | yes | The page of the host web view. It follows the page rules of a `view` composition: a path inside the plugin release, relative, without a leading slash, with no empty, `.` or `..` segment and no `.binary` segment, ending in `.html`, and listed in the `files` of `package.json`; `sok plugin pack` fails when the page is not listed |
| `state` | no | The state that the host page saves across a restart of its process, as `{ "format": <positive integer>, "maxBytes": <positive integer> }`, in the form of `surface.unload` ([plugins](plugins.md#memory-saver)); an object with other fields or with a value that is not a positive integer is an error that names the plugin. Without it the host saves no state ([state](#state)) |

The `host` declaration requires nothing beyond the requirement of a plugin to declare `surface`, `sections` or `contributes`. The host web view of a plugin exists only while the manifest of the loaded plugin declares it.

## Web view and configuration

The host creates one plugin host web view per plugin per window, with the configuration of a [view](native-surfaces.md#view-surfaces):

Each plugin-host and view source receives a positive generation from one monotonically increasing counter per window. A generation is a JavaScript safe integer from 1 through 9007199254740991. The host includes the generation in native-to-main-page lifecycle, call, reply and declared snapshot metadata. Main-page `pluginHostReply`, `pluginHostRequest` and `pluginHostEvent` bridge calls carry the expected generation; the host checks it before forwarding a reply, posting a request or event, and returns a stale cancellation for a request or event. The main page obtains the current plugin-host and view generations and the greatest issued generation in one startup snapshot after installing listeners. The generation never enters the page message `{sok, event, data}` or `{sok, id, command, params}`.

The host emits `declared-ui-source-registered {plugin, surface?, generation}` after it records a source and before it creates or loads a provider that can send a message. It emits `declared-ui-source-ended` with the same identity only after retiring that exact generation. These lifecycle events describe source instances, not exposure registrations. A view includes its surface; a plugin host omits it. Plugin-host disposal also emits `plugin-host-ended` for the existing registration and request cleanup contract. The main page listens for these lifecycle events before querying `declaredSourceOrigins` and buffers them with declared UI snapshots until it seeds the registry.

The Tauri main page registers one `declaredSourceEventStream` channel before querying `declaredSourceOrigins`. The host sends `{name, value}` envelopes through that channel for `declared-ui-source-registered`, `declared-ui-source-ended`, `declared-ui-snapshot`, `plugin-host-call`, `plugin-host-reply`, `plugin-host-ended`, `view-call`, `view-reply`, `view-process-ended`, `view-stopped` and `view-responsiveness`, preserving the original event payloads and their send order. A `view-responsiveness` payload carries the generation of the view whose callback produced it. The channel registration resolves only after the host installs the receiver. The page does not start views or mark the window ready for plugin hosts until both channel registration and the atomic origin query complete. A page reload retires the old channel before registering the new one. A send without a registered channel or a failed send is reported as an error; Tauri does not fall back to separate window events. Wails sends the same event records through its FIFO frontend event transport.

- `isView` set, so that the configuration dispatches the `core` scheme to the core root resolver;
- the plugin id of the plugin, which sets the `soksak://<plugin id>` origin of the page and the `Access-Control-Allow-Origin` of its core root responses;
- the document-start user script with the text of `packages/plugin-api/view-start.js`, the [view channel](native-surfaces.md#view-surfaces) script;
- the document-start user script with the theme tokens;
- the document-start user script of the plugin start values, which sets `window.sokHost` to the frozen `{project, declarations}` of the plugin host. The host builds the values itself: `project` is the frozen `{id, root}` of the project that the window shows when the host creates the plugin host, with the project id and its canonical root, or `null` in a window that shows none, and `declarations` are the `exposes` of the plugin manifest, or `{}` when the manifest declares none; an `exposes` that is not an object is refused. The host has no surface and no origin. The script is added before the page loads, and the host adds it again when it creates the plugin host again. A later project change is sent to each plugin host with a ready document as the message event `project` with `data` `{id, root}` or `null`; a host without a ready document does not receive that change immediately. After each `view.ready` message, the host sends the project currently shown by the window as `project`, including `null`, so a change that occurred while the document was not ready is delivered to it;
- the script message handler `sok-view`;
- the persistent website data store of the plugin, keyed by the plugin id.

The host loads `soksak://<plugin id>/<page>` from the folder that `plugins/installed.json` records for the plugin, as it loads the page of a view. The page begins with a doctype and holds no import map of its own, as checked by `checkViewPage`. The host inserts the [view import map](plugins.md#view-surfaces). The page imports the [view bridge](plugins.md#view-surfaces) and calls `createViewChannel()` over the `sok-view` handler.

The web view is attached to the window, not to a surface host. It is not a surface: it holds no `SurfaceHost`, no surface frame, no regions, and no presentation wait. The host places it hidden and shows nothing: the web view holds a zero frame, is submitted as invisible, draws nothing on the screen, takes no hit testing, and never becomes the first responder. The host page receives no input and registers no shortcut table. `host.hit` never reports it.

## Lifetime

The host creates the plugin host web view of a plugin when the main page of the window loads a plugin whose manifest declares `host`, so the declared sections of the plugin have their source before any view of the plugin is open. It disposes the web view when the plugin is removed or disabled, when the application applies a plugin change that reloads the window, and when the window closes. The host page process ends with its web view and is created again within the [restart limit](#restarts).

The host page holds no surface context: it receives the synchronous values of the plugin (`icon(name)`, `origin`, `project` and `declarations`, without `params`, which belong to a tab) as a view page does, reaches asynchronous operations through the view bridge, and gets `contributions(point)` as the connected items of the point.

## Channel

The plugin host channel is the [view channel](native-surfaces.md#view-surfaces) on the web view configuration above: the same document-start script, the same `sok-view` handler, the same ready message with the document identifier that makes the ready document, the same queue of at most 256 messages, the same `sok: 1` marker of host messages, the same delivery with `window.postMessage(message, location.origin)`, and the same refusal of a message without the marker. A message that arrives with the queue full is not queued: the script reports the reason `queue full for <plugin>` through `sok-view` in a `view.error` message, the host writes `error: plugin host channel: plugin <plugin>: queue full for <plugin>` to the application log, and the host closes the plugin host and creates it again within the restart limit. A `view.error` with another nonempty reason is written once as `error: plugin host channel: plugin <plugin>: <reason>`; if its reason already begins with that exact `plugin <plugin>: ` prefix, the host writes it once without adding the prefix again. If its reason begins with a different plugin prefix, the actual channel plugin prefix is added and the reason is preserved. A `view.error` without a nonempty reason is refused with `plugin <plugin>: view.error has no reason`. No host message is dropped without a record.

What differs from a view is the peer and the calls:

- Every relayed message carries the plugin and no surface, because the host page holds no surface.
- The host forwards each call request `{sok: 1, id, command, params}` of the page whose `id` is an integer and whose `command` is a served call of the channel, which the next clause lists, to the main page of the window as the event `plugin-host-call {plugin, id, command, params}`, and each cancel `{sok: 1, id, cancel: true}` as `plugin-host-call {plugin, id, cancel: true}`. The main page answers with `pluginHostReply {plugin, id, result}` or `pluginHostReply {plugin, id, error: {code, message}}`, and the host posts `{sok: 1, id, result}` or `{sok: 1, id, error}` to the ready document. A message with any other invalid field is written to the application log as `error: plugin host channel: <reason>` and is not forwarded.

  A plugin host reply has an integer `reply` id and exactly one of the `result` and `error` members. The presence of `result` determines that a result was supplied, including when its value is JSON `null`. A reply with both members or neither member is invalid. An error has an integer code and a nonempty message.
- The page answers a request with `{sok: 1, reply: id, result}` or `{sok: 1, reply: id, error: {code, message}}` through `sok-view`, as a view answers a [view command](native-surfaces.md#view-surfaces). The declared `timeout` of the command bounds the wait, and a reply after the limit is discarded as a late reply.
- The calls of the page that the channel serves are the registration calls of [exposure](#exposure), which the main page answers, the sidecar calls `runtime.sidecar.send`, `runtime.sidecar.on` and `runtime.sidecar.onFailure`, which the main page answers for the sidecars that the plugin declares ([sidecars](sidecars.md#plugin-host-sessions)), the project data calls `runtime.data.get` and `runtime.data.set`, which the main page answers for the project that the window shows ([project data calls](#project-data-calls)), the error call `runtime.error`, which the main page answers as [error call](#error-call) states, the command call `runtime.command`, which the main page answers as [command call](#command-call) states, the log call `runtime.log`, which the main page answers as [log call](#log-call) states, the registration notice `runtime.native.call` with the name `registered` and the payload `{kind, name}`, which the main page answers as `page.exposure.register` does, the subscription call `runtime.native.on` for the events `exposure-request` and `declared-ui.expanded`; subscribing to `declared-ui.expanded` does not enable the DOM exposure relay, which requires `exposure-request`; and the reply call `runtime.native.call` with the name `exposureReply`, which the main page serves for the dom entries that the host registered: it delivers each `dom.*` request of such an entry to the host page as the message event `exposure-request` with `data` `{id, method, params}`, and it answers the request with the reply that the host page sends through `runtime.native.call` as `{name: "exposureReply", payload: {id, result}}` or `{id, error}` ([exposure](exposure.md#relay)); `declared-ui.expanded` delivers the selected declared status tree's `{status, tree, path, expanded}` update to the source, which updates its value and publishes a snapshot ([declared UI](declared-ui.md#tree-keys)); and the calls of [state](#state), which the host answers itself; a [snapshot](#declared-ui-snapshots) is a message of the page, not a call. The host answers a call request of any other non-empty command itself with `{sok: 1, id, error: {code: -32000, message: "plugin host call <name> is not served"}}` and forwards nothing. A plugin host has no `tab.state` call, no region operation, and no clipboard or link call. Its sidecar send serves only the operations that its manifest declares for a sidecar dependency (`hostOperations`) and that the sidecar declares read-only (`hostReadOperations`, [plugins](plugins.md#pluginjson), [sidecars](sidecars.md#messages)); the main page refuses every other operation with `plugin host <plugin>: operation <op> is not served`. The host serves only the calls listed in this clause, and holds no logic beyond the presentation of its declared statuses, the relay of the calls listed here, the [state](#state) calls and its [restart](#restarts) record ([plugin processes](plugin-processes.md#layer-rules)).
- The theme reaches the host page as it reaches a view: the document-start script carries the tokens, and each later theme change is sent as a host message after each ready message.
- The project reaches the host page as the host message `project`. Each later project change is sent to ready documents. After each ready message, the host also sends the project currently shown by the window, including `null`, even when it has not changed since the document-start value. The page receives both through `runtime.project(listener)`; the listener gets the most recently delivered project at once, and the page makes no call to the host for it. The first ready response sends the current theme before this project value.
- The first ready message after the host created the web view writes `host.trace.plugin-host.process-ready {plugin, window}` at level `debug`, as the first ready message of a view writes `host.trace.view.process-ready`.
- When the host disposes the plugin host web view of a plugin on its removal or disable or on a queue overflow, or the page process of the host ends, it sends the event `plugin-host-ended {plugin, generation}` to the main page of the window. The main page removes every registration under `plugin:<plugin id>` ([exposure](#exposure)), removes the sidecar subscriptions of the plugin host, and ends each of its open requests to the host with `surface-closed`, as the close of a view ends them. The sidecar sessions of the host are closed by the host, as [sidecars](sidecars.md#plugin-host-sessions) states. A reload or the close of the window sends no `plugin-host-ended` event, because the main page that holds the registrations is replaced or ends with it.

## Exposure

A plugin host page registers its declared statuses, commands and dom entries through the channel, with the calls a view page uses: `runtime.command.register` for a command, and the exposure registration (`page.exposure.register(kind, name)`) of [exposure](exposure.md) for a status and a dom entry. The owner key of every registration of the plugin host is `plugin:<plugin id>`; a surface page registers under its surface id with the owner from its plugin. A name that the `exposes` of the plugin does not declare is refused with the registry error. The registration of a plugin host ends with its process, and a process that is created again within the restart limit registers again under the same key.

The plugin host is not a surface: a request without `surface` for a name that a plugin host registered is answered by its registration when no surface page registered the name ([choosing a surface](exposure.md#choosing-a-surface)). A request that names a `surface` is never answered by a plugin host. The plugin host answers `command.run` by running the registered command through the channel within its declared time limit, and `status.get` by the pull of the status ([declared UI snapshots](#declared-ui-snapshots)), whose reply `{seq, value}` is returned as `{value, version: seq}`. It pushes its statuses as declared UI snapshots, so a `status.watch`, a `status.unwatch` or a dom request that only a plugin host would answer is refused with `plugin host <plugin id> does not serve <method>`.

For status.get, the exposure registry and endpoint use the qualified status name, such as files.tree. The workbench removes the registered plugin id and separator before calling declared-ui.snapshot.request; the status parameter is the plugin-local name (tree) used by the snapshot store. It does not try the qualified name as a second key.

## Declared UI snapshots

A native message callback is bound to the local host instance that installed it. The native message callback, host creation and host disposal run on the main thread, so the instance check and synchronous dispatch are serialized with replacement. After disposal, a delayed callback from that instance is canceled before dispatch, even if a host of the same plugin has been recreated; the host writes `host.trace.plugin-host.message-stale {plugin}` while performance tracing is on. An explicit error from the retired provider is logged with its plugin context and does not close or restart the replacement host. When the window records have already been removed, the Tauri host still logs an explicit provider error using the callback's captured plugin id; an ordinary late message remains a canceled callback.

A plugin host pushes a [declared UI snapshot](declared-ui.md) of each declared status that it registered and answers the pull request, as a view does. The snapshot carries the plugin and no surface; the pull is the `declared-ui.snapshot.request` call and its reply is `{seq, value}` ([plugin processes](plugin-processes.md) rule 2). When the plugin host starts or starts again, the first snapshot of each status is the full value of that status, and a restarted plugin host builds its values from its saved state ([state](#state)); the workbench discards the stopped snapshot and the pending acknowledgement of the previous process ([plugin processes](plugin-processes.md) rule 2). A status that only a state module registers has no source, and a declared status that the host registered is served again by the new host process, which registers it again and pushes the full first snapshot, as the transitions of [declared status](declared-ui.md#declared-status) state; a view of the plugin that registers it becomes the source ([declared status](declared-ui.md#declared-status)).

## Restarts

The restart limit of a plugin host is the limit of a sidecar of standard input and output ([sidecars](sidecars.md#failure)): the failure record and the restart limit are per plugin: the failures of the host pages of the plugin in every window count in one record, and the stop of the limit stops the host page in every window. The saved state of the state calls is one value per plugin, which the host page of every window reads and writes. The host counts the failures of the plugin host by the time of each failure, which is taken when its failure event arrives; no timer runs. A failure more than 300 seconds before a new failure is not counted (a sliding window). A failure of a plugin host is an end of its page process that the host did not cause by its own disposal (plugin removal or disable, a plugin change that reloads the window, the close of the window), or the queue-full error of its channel. When the fourth failure is counted, the host writes `error: plugin host <plugin>: restart limit: 4 failures within 300 s` to its log, writes the event `host.plugin-host.restart-limit {plugin}` at level `error`, and stops the restarts of that plugin host. Each restart of the page process writes the event `host.plugin-host.restart {plugin, attempt}` at level `error`, where `attempt` counts the restarts of the plugin host since the last reset.

While the plugin host is stopped, the host creates it again for no request: its registrations are removed, a request for one of its names returns the error of a name that is declared but not registered, and the declared sections it served stay cleared. The stop clears no failure record by itself.

Only the person's open of a surface of the plugin or the person's enable of the plugin clears the stop. When the person opens a surface of the plugin while its plugin host is stopped, the host clears the failure record of its plugin host, writes the event `host.trace.plugin-host.restart-reset {plugin}` at level `debug`, and creates the plugin host again in every window, as the stopped sidecar of [sidecars](sidecars.md#failure) is cleared. The open of a surface while the plugin host is not stopped clears nothing, and the creation of a surface of another plugin clears nothing. The open of a surface of the plugin and its enable clear the stops of the sidecars that its `dependencies` list in the same step, as [sidecars](sidecars.md#failure) states; the two records share these triggers. The enable of the plugin creates the plugin host again in every window in the same way.

A restart restores the state from the last saved value ([state](#state)). A state that was not saved is lost, and each plugin states in its own documentation which state that is.

## State

The plugin host state is the value that the host page of a plugin saves through its channel and that the host keeps for the next start of the page.

- When the `host` declaration names `state`, the channel serves the calls `state.write {value}` and `state.read`, which the host answers itself and forwards to no page. `state.write` refuses params without a `value` and a value whose compact JSON exceeds `maxBytes` bytes with an error that names the plugin and the size, and otherwise replaces the saved value of the plugin and returns `null`. `state.read` returns `{value}`, the last saved value, or `{value: null}` when nothing is saved. A page reads its state at its start and saves it whenever it changes, so a restart within the limit restores it.
- The host keeps the last saved value until the application ends or the plugin is removed or disabled. The value is held in the host process and survives a restart of the plugin host page, not the end of the application.
- The saved value carries the declared `format`. A page that reads a value of another format is refused with an error that names the plugin, the format found and the declared format, as a tab state of another format is refused ([plugins](plugins.md#memory-saver)).
- Without the `state` field both calls are refused with an error that names the plugin, and a restart starts the page with no saved state.

## Project data calls

A plugin host reads and writes the [project data](plugins.md#project-data) of its plugin through two calls of the channel, which the main page answers for the project that the window shows. `projectOpen` records ownership without changing the committed shown project or sending a project message, and returns whether that ownership is still staged. After a successful local open, the page prepares the project's declared data context, selects the project's settings scope, installs the context, then calls `projectShown({id, root, title})`; only that call commits the native shown project and sends the `project` message to ready plugin hosts. The page restores the previous settings scope if selection or native publication fails before commit. The page sends `projectShown(null)` after installing the library context. Each data call captures the active context when that call begins: calls that began before the context installation keep the previous project's access functions, and calls that begin after installation use the prepared new context, including a callback delivered before the `projectShown` command reply. When a project is already owned by another window, the requesting page does not publish that project: the owner handles `project-activate`, prepares its own context and calls `projectShown`.

- `runtime.data.get {key}` returns the value of the key, the stored value or its default.
- `runtime.data.set {key, value}` stores the value of the key and returns `null` after the store accepted the write.

The checks are those of [project data](plugins.md#project-data): the key must be declared in the `data` field of the manifest, a value must match the schema of its key, and a stored value whose format is not the declared format is refused by the read. A key that the manifest does not declare is refused with an error that names the plugin and the key. While the window shows no project, both calls are refused with `plugin host <plugin>: no project is shown`, the text of a sidecar send in the same state. The refusals return to the page as the error of its call. The window sends no event when the shown project changes; the host page reads the project data again at its next call.

## Error call

A host page reports a listing error of its declared tree through the call `runtime.error {where, text}`. The channel forwards it to the main page as `plugin-host-call` like the registration calls, and the main page answers it with the checks of the view call `runtime.error` ([native surfaces](native-surfaces.md#view-surfaces)): `where` must be a non-empty string without a control character and without `: `, and `text` must be a non-empty string. Another value is refused with the error of the call, and nothing is written. An accepted call writes the line `error plugin <plugin> <where>: <text>` to the application log through the error display of the main page, and the call replies `null`. The declared tree draws no error for it ([declared UI](declared-ui.md#element-kinds)).

## Command call

A host page runs a command with the call `runtime.command {name, params}`. The channel forwards it to the main page as `plugin-host-call` like the registration calls, and the main page answers it with the checks and the reply of the view call `runtime.command` ([native surfaces](native-surfaces.md#view-surfaces)): a `core.*` name runs the core command with `params`, a name of the plugin runs the command that the plugin host registered under its owner key `plugin:<plugin id>` ([exposure](#exposure)), and any other name is refused with the error of the view call, whose text names the caller as `plugin host call` (for example `plugin host call open names no owner`). `name` must be a non-empty string, otherwise the call is refused with `plugin host call runtime.command requires a non-empty name` and runs nothing. A call without `params` runs the command with `null`. The call replies with the result of the command, or with its error. A host page opens a core surface, such as a file through `core.file.open`, through this call.

## Log call

A host page writes an event of its plugin with the call `runtime.log {level, event, fields, cids?}`. The channel forwards it to the main page as `plugin-host-call` like the registration calls, and the main page answers it with the checks and the writes of the view call `runtime.log` ([native surfaces](native-surfaces.md#view-surfaces)): `level` is one of `error`, `warn`, `info`, `debug` and `trace`, another value is refused with `plugin host call runtime.log log level must be one of error, warn, info, debug, trace`, and `event`, `fields` and `cids` are checked by the log of the plugin context ([plugins](plugins.md#logging)). The record is stored as `plugin.<plugin>.<event>` through the event writer of the page with its level gate, as the log of the plugin context stores it, and a gated record is counted by the writer. A plugin host has no surface, so its record carries the plugin and no surface id. The call replies `null` when the record is accepted, and with the error of the check otherwise, and nothing is written for a refused call.
