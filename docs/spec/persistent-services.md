# Persistent services

Owner cleanup and retain attempt closure and await termination for every selected surface actor even when one actor has already ended or fails. They report every failed surface explicitly instead of abandoning the remaining actors. A reported failure is not a successful cleanup.

When a newer connection attaches a persistent surface, EOF from the previous connection detaches only that previous connection's output sender. It must not clear the newer attachment's sender or close its output stream.

[한국어](persistent-services.ko.md)

This contract defines the approved persistent service contract. Implementation and verification are tracked in [features](../features.md); approval of this contract does not establish implementation.

## Ownership and process count

One persistent service owns the sessions of one application configuration directory and their resources. Independent sessions own separate child processes; a device handle is not a process. Three independent sessions require one service and three child processes, in addition to the application host. Application host processes and programs launched by child processes are counted separately.

A surface attachment is not a session. The first open for a surface key creates one registry actor and allocates a stable session identifier before starting its child process; repeated requests with the same creation identifier return the same result. Attaching a replacement surface does not create a child process. The active attachment owns input and size changes, and stale attachments receive an explicit error. A session preserves its size when no surface is attached.

The service endpoint is scoped to the configuration directory, authenticated, versioned, and protected by a single-instance lock. A test configuration cannot discover a service belonging to another configuration. Session state and input queues are isolated. A busy session must not hold a global lock while reading, writing, or processing its output.

## Closing and recovery

### Service transport

The sidecar declaration selects `transport: "persistent"`. A sidecar without that field uses its domain's stdio transport. A host starts the declared executable with `--service-dir <config-dir>/services/<executable-name>`. The service takes the exclusive lock in that directory before creating its listener. It creates the socket in a private, short temporary directory to respect Unix socket path limits and atomically publishes `endpoint.json` containing `{protocol: 1, pid, socket, token}`. Directory permissions are 0700 and token-bearing files are 0600. The ready line on stdout contains that endpoint only after the listener is ready. The service completes its startup work before it publishes the endpoint, so that cost occurs once per service process, and the service outlives application restarts. The host waits at most 30 s for the ready line, a bound far above that cost, so that a service that never becomes ready does not keep the requests to its sidecar and the host's stop waiting; it then ends and reaps the service it started and fails with `sidecar <name>: the service did not print its endpoint within 30s`. A service that ends before its ready line fails the start with `sidecar <name>: service exited before endpoint`. The host waits at most 5 s for the hello reply and then fails with `sidecar <name>: the service did not answer hello within 5s`.

The first newline-delimited JSON message is `{operation: "hello", protocol: 1, token, client}`, where `client` is the configuration directory of the application. The service replies `{operation: "hello", protocol: 1, version, ok: true}`, where `version` is the version of its sidecar, or `{operation: "hello", ok: false, error}`. After authentication, surface messages retain the declared sidecar envelope. `{operation: "close-owner", request}` closes the authenticated client's sessions and replies `{operation: "closed-owner", request, ok: true}` after cleanup, or `ok: false` with `error`. `{operation: "shutdown", request}` is accepted only after owner close, replies `{operation: "shutdown", request, ok: true}`, and authorizes the service to exit after its client connections finish. Socket EOF preserves sessions. An endpoint file alone does not authorize killing its PID, and protocol or authentication failure must not start a competing service. A process that only lingers as a zombie — an unwaited spawn of a dead client — does not count as an existing service, so the stale endpoint it published is replaced.

Hiding a surface, visiting the library, or losing the application connection preserves sessions. An explicit close of a session ends that session. Closing a window normally ends its owned sessions; normal application quit ends all owned sessions. Closing is complete only after the managed jobs are terminated, the child is reaped, device handles are released, output completion or failure is reported, and attachment tasks are removed. Shutdown errors are reported, not converted into success.

Application crashes and explicit update restarts leave the service alive. Reconnection restores the same session, child process, and session state; the native image is recreated for the new application process and is never reused across processes. The service continues consuming and processing output while detached. EOF is a connection loss, not a session-close command, and so is a client whose output side closes before the service reads its EOF: the service detaches it and keeps its sessions. A close intent is recorded before acknowledgement so an interrupted close cannot restore a deliberately closed session.

A connection that is lost while the application runs is revived immediately, without waiting for the next send. The host's persistent reader notices the socket EOF and restarts the transport through the same single creation path: a live service is reattached — its preserved sessions answer with a `session` event — and a dead service is respawned after its stale endpoint is removed. The restart attempts once per disconnect; a failure is reported, and the next send retries the same path, within the restart limit below. The image registry dies with the acknowledged connection: the host invalidates the configure state of exactly that sidecar's images and re-sends their configure at the same size, because the new service holds no image state. Every surface that has sent to the sidecar receives the `sidecar-message` body `{"event": "connection", "connected": true}`, or `{"event": "connection", "connected": false, "reason"}` on a failed restart. A surface page treats this as its reconnection signal: it resolves the stale sidecar error and re-runs its session bootstrap, `open` (a no-op on a preserved session, a new session on a respawned service), followed by the settings that its sidecar declares. Background sessions of hidden tabs re-send their manifest open operation the same way. A respawned service cannot preserve the sessions of the process that died; a hidden tab that never remounts starts its fresh session when the connection notice arrives.

The restarts of a persistent service have the [restart limit](sidecars.md#failure) of the standard input and output transport: the host counts each failure by its time, a failure more than 300 seconds before a new failure is not counted, and no timer runs. A failure of a persistent service is one of:

- the service process ends while the host is neither stopping its sidecars nor replacing the sidecar: the revival of the lost connection counts that end when it finds no live service, after it removes a stale endpoint or when none remains, and before it spawns the service;
- a start of the creation path fails with `the service did not print its endpoint within 30s`, `service exited before endpoint` or `the service did not answer hello within 5s` while the host is neither stopping its sidecars nor replacing the sidecar;
- the reader ends the connection for one of the reasons of the next paragraph or for a close answer that the [failure](sidecars.md#failure) rules reject, while the host is not stopping its sidecars; the reader counts it when it ends the connection, and the service keeps running.

A disconnect whose revival reattaches a live service is not a failure. One disconnect counts at most one failure: a revival that retries the connect after a refusal counts once together with its retry, and a revival whose respawned service then fails its start counts once, as that start failure. A start that a send runs counts its own failure. The fourth failure within 300 seconds writes `error: sidecar <name>: restart limit: 4 failures within 300 s` and the event `host.sidecar.restart-limit` `{sidecar}` at level `error`, and stops the restarts before the revival or the send runs the creation path again. A fourth failure that is a failed start is reported as any failed start is: the notice of a revival carries its start error, and a send fails with it. When the fourth failure is the end of the service process, the revival spawns nothing, and the surfaces that have sent to the sidecar receive `{"event": "connection", "connected": false, "reason": "restart limit"}`. While the sidecar is stopped, the host runs no revival and no creation: a send fails with `sidecar <name>: restart limit`, the host writes `error: sidecar <name>: restart limit: request for <surface> refused`, and the surface that sent receives `{"event": "connection", "connected": false, "reason": "restart limit"}`. No other connection notice is written until the stop is cleared, and the stop adds no `sidecar-failure` delivery. The open of a surface clears the stop as [failure](sidecars.md#failure) states, and the next send runs the creation path. The failure record lives in the application process, so a new application process starts with none.

The host reads the service connection one line at a time and applies the [message limit](sidecars.md#messages) of the stdio transport to each line. A line over the limit, a line that is not a JSON object, a reply whose `operation`, `request`, `ok`, `error` or `closed` field has the wrong type, or a surface event without a string `surface` and a `body` ends the connection with that reason: the host closes the connection, fails the waiting close-owner, shutdown and retain requests, writes the reason to the application log, and delivers `sidecar-failure` with the reason to each surface that has sent to the sidecar, as the stdio [failure](sidecars.md#failure) rules do. The service is shared and keeps running. The host does not reconnect immediately, because the same message would end the next connection again; the next send reconnects through the creation path and announces the connection, unless the restart limit below stops the sidecar.

The service exits after an explicit shutdown request once no clients remain, on SIGTERM or SIGINT, and when its service folder or its `endpoint.json` is removed or names another service; each exit runs the same cleanup of the endpoint, the socket folder and the event file, and a service removes `endpoint.json` only while it names itself. A session is recoverable while a project layout holds its surface, and while it is, the session is not closed and its surface does not start another child process: an `open` for a surface that has a session starts nothing, and the start settings of an `open` apply only when a child process starts. An `open` without `image` for a surface that was opened with an image or holds a configured image is refused with `{error: "imageAttached", reason}` and changes nothing, because it would make the surface headless, feeding the output of its session without drawing it, while its image stays shown. Each `open` and each applied `image.configure` records the drawing mode that it leaves on the surface as `sidecar.<name>.surface_mode` `{mode, cause}`, `mode` being `image` or `headless`. Every `retain` entry carries the root of the project whose layout holds the surface; an entry without a root is refused, and its sender is at fault. `{operation: "retain", request, surfaces: [{surface, root}]}` closes every session of the authenticated client whose root and surface are not listed and replies `{operation: "retained", request, ok: true, closed}` with the number closed, or `ok: false` with `error`. The page sends the surfaces of every space layout of every project, with the project root, when it starts, after it closes a space, and after a project leaves the registry, which every window reads from the registry change notification after it disposes the surface modules of that project's tabs ([project windows](projects.md#settings)); the host adds every surface that this application process has sent and delivers the request to each persistent service that runs or has published its endpoint. A session whose surface no layout holds, which a crash or a failed page leaves without a closed notice, therefore ends when the application starts again. Service failure and OS restart are outside live-process recovery; a new child process is not evidence of recovery. The shared service is one process failure domain. Session isolation does not claim process-level crash isolation.

An application update may reconnect to the live service only when their protocol versions agree. A protocol mismatch is an explicit failure; it does not start a second service, close existing work, or use a compatibility path.

### Updates

When the `version` of the `hello` reply differs from the version that `installed.json` records for the sidecar, after an update of the sidecar or when an application start finds a service that an earlier application left, the host keeps the service and its sessions and reports the sidecar in `host.sidecars` as `outdated: [{sidecar, running, installed, sessions}]`, sorted by sidecar, where `running` is `null` for a service that sent no `version`, which is a service of an earlier version, and `sessions` is the number of open surfaces of the application that have sent to the service. The host notifies the watchers of `host.sidecars` when the list changes. The host replaces the service when `sessions` becomes 0 and when a page runs the host call `sidecarsReplace({sidecar})`: it sends `close-owner` and `shutdown`, closes its connection, waits until the process of the service endpoint ends, and starts the installed executable through the creation path; the sessions of the replaced service end, and each surface that has sent to the sidecar receives the connection notice and opens a new session. The plugin screen shows each outdated sidecar with the action 세션 <sessions>개를 끝내고 적용 bound to `core.plugins.replace {sidecar}`. A replacement that fails is reported with its reason and the sidecar stays outdated; the host does not end the service by any other path. The application log records `sidecar <name>: service <running> replaced by <installed>`.

## Screen message

The `screen` event from the sidecar to the page carries the complete drawn screen, so the page computes the [screen hash](replay.md#screen-hash) from the message alone. The page draws no cells; the sidecar draws the raster, and the cells of the message are the screen that the raster shows. The reply of a sidecar screen read is `{rows, frame}`: the rows of those cells, and the `frame` of the event, which names the frame that shows them ([sidecars](sidecars.md)).

| Member | Form |
| --- | --- |
| `event` | `"screen"` |
| `sequence` | An integer from 1: the `sequence` of the frame record that the sidecar stores for this screen ([replay](replay.md#records)), the sequence of the last replay input that the screen includes |
| `segment` | A non-empty string: the `boot` of the event file of the sidecar run that drew the screen, the [segment](replay.md#segments) to which `sequence` belongs |
| `rows`, `cols` | Positive integers: the size of the grid |
| `cursor` | `{visible, row, col}` as the hash covers it ([replay](replay.md#view-state), Cursor): `visible` is `true` or `false`, `row` is from 0 to `rows` minus 1 (`0` when the cursor is outside the viewport) and `col` is from 0 to `cols` minus 1. The cursor members of the runtime (`shape`, `blinking`, `blinkVisible`, `focused`) are further members that the hash does not cover: a page checks each one that is present (`shape` is `Block`, `Underline`, `Beam`, `HollowBlock` or `Hidden`, or the same word in lowercase; `blinking` and `focused` are booleans) and keeps the previous value of one that is absent |
| `cells` | `rows` × `cols` cells in row-major order |

Each cell has `grapheme` (the text of the cell: the empty string for a blank cell and for the continuation cell of a wide character, otherwise one grapheme cluster), `width` (`1`; `2` for the first cell of a wide character; `0` for its continuation cell), `fg` and `bg` (the color after the theme, the inverse attribute and the selection highlight are resolved: `null` for the default color, an integer from 0 to 255 for an indexed color, or `"#rrggbb"` in lowercase for a true color) and `attributes` (the integer from 0 to 255 whose flags the screen hash defines: bold `01`, dim `02`, italic `04`, underline `08`, blink `10`, inverse `20`, hidden `40`, strikethrough `80`). A cell may carry `link`, which the hash does not cover. Every member listed above is required: the message has no absent color and no default for a missing member, and the sidecar states `null` for the default color.

A screen-producing sidecar of any kind follows the same rule: the message that carries its screen to a page holds the members of the screen hash, with `sequence` of its frame record, so the page's frame record and the sidecar's frame record are comparable. The sidecar writes the members and the frame record; the page does not derive a member that the message lacks.

`screenFromMessage(message)` of `@soksak/plugin-api/screen-hash` validates a message of this form and returns the screen that `screenHash` takes. It throws an error that names the member for a message without `sequence`, `segment`, `cursor` or `cells`, and for a cell without a resolved `fg`, `bg` or `attributes`; the ranges of the values are refused by the hash. The page stores the page frame record with `message.sequence`, `message.segment` as `segment`, the size and the hash of that screen. `packages/log-contract/fixtures/replay/screen-message.json` holds a message for each vector of the screen hash with the same hash, and the messages that the function refuses with their error text: `sequence missing`, `sequence zero`, `segment missing`, `event is not screen`, `foreground missing`, `background missing`, `attributes missing`, `cursor missing`, `cells missing` and `color outside the forms`. A sidecar writes messages that reproduce these hashes, and a page reproduces them with `screenFromMessage` and `screenHash`.
