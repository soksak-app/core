# Native surface layout

[한국어](native-surfaces.ko.md)

The approved single-DOM model is defined by [surface composition](surface-composition.md) and [plugin modules](plugins.md#surface-ownership). A logical surface is not a WebView. Native window facts identify the app DOM by its registered native view, not by its drawing order; document WebViews are below the app DOM. `appDomWebviews` and `documentWebviews` are measured from the native hierarchy. Counting a constant or inferring the main view from the first child is invalid. [Features](../features.md) tracks integration and verification separately.

This specification defines surface placement in the example applications. Implementation and validation status are recorded in [features](../features.md).

Prepared surface frames in a placement reply are read in one main-thread turn, preserving request order and visibility. A frame-read error rejects the reply instead of returning a partial list.

The Tauri host runs native image presentation commits through the native UI queue outside framework event callbacks. The sidecar receives its consumed or refused response only after the native presentation result; enqueue and native errors remain explicit failures.

## Ownership

- The layout library computes card rectangles and updates their DOM elements.
- The example compositor derives surface rectangles from card rectangles and DOM insets.
- The host creates native views, applies surface rectangles, and reports actual geometry.
- The macOS presentation code commits native geometry after the window's single app DOM confirms presentation and every visible image region has its exact current raster.

The host must not assume that DOM and native rendering differ by at most one frame.

## Placement sequence

1. Before updating card DOM, the page submits the next surface rectangles.
2. The host acquires the UI thread's layer transaction for the owning window and applies the full native rectangles. The response contains actual geometry and one identifier for the complete preparation.
3. After preparation completes, the page updates card DOM and requests presentation for that identifier.
4. After the window's app DOM confirms presentation and the required image rasters are ready, the host commits the transaction and returns actual geometry. [Document regions](#document-regions) render independently and never join the DOM presentation wait, regardless of their URL origin.
5. The page starts the next preparation after that response, using the latest pending layout. A newer layout replaces an older layout that has not started, and neither the preparation nor the draw of the replaced layout runs. The newest layout contains every earlier input. When a presentation settles, the page writes the number of replaced layouts to the application log.

The workbench layout callback captures each target surface identity, dimming state, and target slot insets together with its card rectangles. Target insets remove the previously drawn sidebar bands from the measured slot and add the bands of the requested card state. The compositor uses this captured geometry rather than re-reading the previous sidebar layout. An unmeasurable existing slot is explicitly represented by null and is hidden during preparation; invalid inset values are errors.

The page may include retained surfaces that are outside the current compositor record in the host placement request. It validates the host response against every identifier in that complete request: each requested identifier is placed or, only during an undrawn preparation, deferred; missing, extra, duplicate, or invalid deferred identifiers are errors. Before seating the current compositor record, the page projects the validated response onto that record's identifiers. A retained surface outside the record remains owned by the retention path and is not recorded as an active compositor placement.

The host serializes `surfaces.place` calls in invocation order before asynchronous view-module loading and composition checks. A later layout cannot overtake an earlier placement while that preparation is pending. A rejected placement releases its turn and is reported to its caller; it does not block later placements.

The workbench forms that request from surfaces it owns in the current page. An active tab that is not yet in an undrawn compositor record waits for its drawn record instead of being treated as dormant. If that active view is already mounted, the undrawn request keeps it as an invisible surface; if it is not mounted, the request defers it until the drawn placement. An already mounted dormant view stays in the request so the host retains its native handle. A cold view outside an undrawn record waits for the drawn placement; that preparation must not create or place it. Before a drawn placement, the workbench waits until project tab state has opened successfully and the memory saver has classified startup tabs. A tab-state open failure rejects the placement; the separate tried signal still lets tab-state calls report that the store is unavailable. A hidden tab of a plugin that declares `surface.unload` is then excluded when the memory saver starts it as unloaded; the tab stays in the layout with its state. A loaded hidden view without a background declaration mounts in a hidden workbench slot, installs its listeners, and declares its composition before the host receives its placement. An absent view with a background declaration remains owned by the background session and is not created as a native view. The host composition barrier still applies to every view in the request.

A native surface is never temporarily reduced to the intersection of pending rectangles. A surface without a matching future slot is hidden before the DOM changes. A surface whose future slot the page measured stays visible at its new rectangle during the preparation: the preparation's changes stay in the window's open transaction and do not reach the screen, and hiding a surface there would send a press at the place where the screen still shows it to the page instead. Measurement after drawing supplies the new rectangles. Hiding a view that contains the first responder makes AppKit move the first responder to another view or the window, so a surface hidden during a placement records its keyboard owner and returns the focus to it when it is shown again, unless the focus moved while the surface was hidden.

A surface inside an element with the `hidden` attribute remains mounted but is submitted as invisible. Card fullscreen hides sibling cards through that attribute; their surfaces and sessions remain alive until the original arrangement is restored.

A native slot with zero width or zero height has no presented area and is submitted as invisible without removing its surface. A positive area restores visibility.

Hiding an existing surface preserves its applied native frame and image snapshot. An invisible request's empty rectangle is not a 1×1 replacement viewport. Hidden outer surfaces do not send raster configurations to suppliers; showing one applies its visible rectangle and configures the exact resulting raster if needed. A newly attached hidden surface must not start image rendering before it has a visible placement. A surface page can place a shown image region before a preparation has given its surface a native frame, because the page draws a new card before the host applies the card's rectangle; such a region has no raster geometry, and the host configures it when a preparation places the surface. A shown region in a placed surface without raster geometry is an error.

The outer surface owns visibility independently of the document generation. Removing image regions for a document's first load or navigation must not remove that surface state. Only closing the outer surface ends its visibility ownership.

Before waiting for image presentation, the host reads every visible image region's actual native raster and sends any required configuration. This check does not depend on a new DOM resize notification: a region can become visible without changing its element size or insets. A failed configuration batch reports the error and releases every unsent configuration so a later explicit operation can configure it; it does not silently mark unsent work as completed.

Applying an outer-surface rectangle starts required image configurations before returning the preparation to the page. Image rendering can proceed alongside DOM drawing and presentation. The final presentation check rereads native raster geometry after DOM presentation, because the document may have changed its anchor insets; parallel preparation never permits a stale raster to commit.

The page awaits the native preparation response before drawing the matching DOM. Starting an asynchronous preparation request does not establish that the native transaction has begun. The page draws that DOM in the next task after the response, not where the response arrives: a response can arrive in any microtask checkpoint, including the checkpoint of a ResizeObserver callback, and a draw there changes elements that the observation round has already delivered, which WebKit defers to the next frame and reports as a ResizeObserver loop error. A task never runs inside a rendering update and its observation round. The page then asks the host to wait for the presentation of the draw; that wait starts a rendering update at once, which carries the draw, so the draw does not wait for the display refresh as an animation frame would. A layout epoch change before that task cancels the draw. Rejected preparation leaves that DOM unchanged and propagates the error. A preparation that fails leaves no begun transaction: the host places the window overlays before it begins the transaction, so a refused overlay begins none, and it cancels a begun transaction when a later step of the preparation fails. If the page layout epoch changes while preparation is pending, its old DOM draw is cancelled.

An older confirmation must not commit a newer preparation. Main-document navigation cancels that window's active and queued preparations. Native calls execute on the UI thread without blocking it while waiting for WebKit.

While a window's transaction is open, none of that window's changes reach the screen, and a newer preparation of the same window extends the open transaction. A wait for the window's presented state (`host.window.presented`) therefore ends only after a presentation update that follows the commit of every open or queued preparation of the window, and reports the target time of the screen's next refresh after that update.

The app background paint holes change only after the host acknowledges presentation of the matching drawn layout. A preparation response does not acknowledge presentation. Keep the existing one-animation-frame delay after that acknowledgement, and use that presentation snapshot’s native applied rectangles and visibility in viewport coordinates. A newer pending DOM layout must not replace these holes before its own presentation is acknowledged. Placement conversion retains native visibility. An acknowledgement missing a requested native surface, a boolean visibility value or finite geometry with nonnegative dimensions is an explicit error; it cannot schedule a paint-hole update.


A surface keeps the frame the host applied. Only the main document web view enables the Web Inspector; attaching it resizes that web view and does not move a surface, so the host holds no surface frame against outside changes.

Native layer transactions are shared by the UI thread. Preparations from different project windows are queued until the current window commits or cancels. A window's reload or closure cancels only that window's active and queued preparations. Waiting requests do not block the UI thread.

The host controls native view geometry. Each content webview renders its document independently; a delayed web document renderer must not stop the main window's layout updates.

The app DOM contains every mounted plugin DOM. Its presentation callback confirms that DOM plane, not another webview's content. Document regions retain independent content rendering; as subviews of their surface, their native frames still follow the card geometry in the transaction. URL-origin matching must not determine presentation ownership.

A view surface is authorized only after the host has prepared the corresponding native surface handle. The authorization notification is delivered exactly once for each current surface generation before the view may declare composition, attach an image region, or open its sidecar session. A missing authorization is a lifecycle failure, not an indefinite loading state; the host must report an attributable error within the operation's bound.

The example preserves device-pixel placement, including 0.5 CSS pixel dimensions on a display with a scale factor of two. Card edges, rules, dividers, and prepared surface rectangles use that same grid. Rendered content must cover its native surface without a gap at the footer. Reducing placement precision or recoloring native backgrounds does not satisfy this requirement. Settings and menu transparency is configured separately.

On macOS, content webviews use a shared native container whose coordinates are device pixels. The host converts window rectangles through the native view hierarchy. Each content webview uses the display scale as its page zoom and one backing pixel per local coordinate unit. This preserves CSS dimensions and device-pixel ratio while providing integral native rendering sizes. Window resizing and display-scale changes preserve the conversion. WebKit takes wheel distances in the view's coordinate units, so the application's event monitor and native scroll input multiply the distances of a wheel event for a webview in the container by the display scale; a scroll moves the document by the same number of CSS pixels as points at every scale. Main and modal webviews retain window-point coordinates.

The [private native API inventory](../operations/private-native-apis.md) records the geometry, presentation, and input dependencies, their necessity, and the first review steps after native updates.

## Title bar height

The window title bar joins the layout transaction, so the window buttons move in the presented frame that draws the page's first row ([window buttons](hosts.md#window-buttons)).

- Every preparation carries `titlebar`, the height in points of the first row that the page shows after the draw that follows the preparation: `round(max(40, 36 × frame factor))` for the frame factor of that draw. A preparation sent after a draw carries the height of the drawn row.
- The host checks the height with the rest of the request before it begins the transaction. After it begins the window's transaction, and before it places the surfaces and answers the preparation, it sets the window's title bar to that height, so the new height reaches the screen with the commit of the DOM frame. A failure to set the height cancels the begun transaction and fails the preparation with that error. A failure of a later step of the preparation sets the title bar back to the height it had before the preparation and then cancels the transaction, because cancelling commits the transaction and would otherwise present the new title bar with the earlier row.
- The answer of a preparation carries `chrome`, the window's button area and title bar height after the host set the height, in the form of the `windowControls` answer (`{controls, row}`). Verification W compares the first row with the button area in the `chrome` of the latest preparation whose presentation the host confirmed, which is the committed state, and not with an earlier `windowControls` answer.
- A change of the frame factor is drawn by a prepared layout: the page writes the new factor into the document in the draw of that layout, not when the setting changes. Before it prepares the layout, it measures the plane size that the new factor gives by writing the factor, reading the plane, and writing the drawn factor back in the same task, so the document renders nothing in between and the card rectangles of the preparation fit the new row. A window without a plane (the library) draws a factor change with a preparation that carries the height and no surfaces. A switch to the library is drawn the same way: its preparation carries the row of the current factor, and its draw removes the plane, writes that factor, and shows the library screen. The library screen hides the workspace, so its elements that ResizeObservers observe become 0×0; it is shown in that draw, in the task after the preparation and outside an observation round, and not in the reaction to a later host reply, which WebKit can run in the microtask checkpoint of a ResizeObserver callback. A switch cancels the draw of a layout that was prepared before it (the layout epoch changes), and that draw may have been the one that writes a new factor; the switch draws the current factor, so the factor of a cancelled draw is not lost.
- A window in full screen shows no title bar. AppKit saves the title bar height when the window enters full screen, clears it, and restores the saved height when the window leaves full screen, so a height set in between would be replaced. The host therefore leaves the title bar unchanged in a preparation while the window is in full screen; the preparation succeeds and its `chrome.row` is 0.
- The first draw of a page does not wait for a preparation ([page start](native-host.md#page-start)), so the title bar must already have the row of that draw. Before the host answers the start document of a window's page, it sets the window's title bar to `round(max(40, 36 × textSize))` for the common setting `textSize` of the workspace snapshot it sends, 40 when the setting is absent, and the document's `controls` are read after that. `textSize` is common-only ([settings](projects.md#persistence)), so the page draws its first row from the same value. A window that is not visible yet, such as a new window that stays transparent until its first page presents, shows no earlier page, so the host sets the height directly, and the first visible frame has the row and the title bar of the same factor. A visible window still shows its previous page until the new page presents its first draw, as on a reload, so the host sets the height in a start transaction: after the page start has cancelled the window's active and queued preparations, it begins a layout transaction as one preparation of the window with a new ticket, sets the title bar in it, and answers the start document; it commits the transaction after the main webview's load has ended and the following presentation update has completed, which presents the first draw. A preparation of the new page that arrives while the start transaction is open extends that transaction and commits it with its own presentation, and the start commit then finds its ticket replaced and commits nothing. A start transaction that cannot set the height is cancelled and fails the start with that error. The open transaction does not hold back the new page: the new WebContent process draws and presents its first screen while the window's transaction is open, and the presentation update completes ([`window_titlebar_reload_test.m`](../../native/darwin/tests/window_titlebar_reload_test.m)). A `textSize` that is not a number from 0.5 through 3 fails the start with `common setting textSize must be a number, not <type>` or `common setting textSize must be from 0.5 through 3`. While the window is in full screen the title bar is left unchanged, as in a preparation.
- When the window leaves full screen AppKit restores the height saved on entering, which differs from the row if the frame factor changed during full screen. The page reads `windowControls` on every window resize, which leaving full screen causes. When the answer has a title bar (`row` greater than 0) whose height differs from the row of the current frame factor, the page prepares a layout that carries the row and sends that preparation even when it equals the request it sent last.

## View surfaces

A view is the native web view of a surface whose composition is `view` ([plugins](plugins.md#view-surfaces)). Each view is one web view on the `soksak://<plugin id>` origin, one per tab, and it runs the page of its plugin. The workbench page runs no plugin code.

The workbench derives each active surface descriptor from the tab before mounting it and preserves that same descriptor through the compositor's placement record. A dormant surface uses the descriptor derived from its stored tab, including its stored `params`. The host request carries view start values computed from that descriptor in its existing `start` member; it does not carry a second `params` member. A slot that becomes a placeholder no longer contributes a surface descriptor.

- **Configuration.** The host creates each view with a web view configuration that has:
  - `isView` set, so that only this configuration dispatches the `core` scheme to the core root resolver ([document regions](#document-regions));
  - the plugin id of the surface's plugin, which sets the origin of the view and the `Access-Control-Allow-Origin` of its core root responses. A request never supplies the plugin id;
  - a document-start user script with the text of `packages/plugin-api/view-start.js`, the view channel script, taken from the staged copy of that file;
  - the view import map, which the native view handler inserts after the doctype of the view composition page ([plugin processes](plugin-processes.md), rule 4), so the view page holds no import map of its own;
  - a document-start user script with the theme tokens (see Theme below);
  - a document-start user script with the start values of the surface (see Start values below);
  - the script message handler `sok-view`, which the [host contract](host-contract.md) declares by name;
  - the persistent website data store of the plugin, keyed by the plugin id, kept in the `document-data` directory of the configuration directory as the store of document regions is ([document regions](#document-regions)).

  The two document-start scripts run before any page script. Neither depends on the other, so their injection order is not part of this contract.
- **Load.** After it creates the configuration, the host loads `soksak://<plugin id>/<page>`, where `<page>` is the `page` of the composition. The files of a view are served as plugin files are served to a document region ([document regions](#document-regions)): from the folder that `plugins/installed.json` records for the plugin, with the same refusals and log lines. The view requests `soksak://core/<path>` for the core root under the rules of [document regions](#document-regions) and the grant rule of [plugin processes](plugin-processes.md) rule 4.
- **Placement.** The frame of a view is the surface rectangle that the compositor derives from its card rectangle and the DOM insets of its element, as for the outer surface of every surface ([placement sequence](#placement-sequence)). Before the compositor sends a placement that can create a native view, the workbench waits until that surface has declared its composition after installing the main-page listeners that answer its first view calls. The host accepts a view placement only when the current main-page document has declared the same plugin and composition for that surface. A page reload retires those declarations; the replacement page must declare them again before placement. The host applies the frame in the transaction of the card, so the view and its card move together in every frame. The web view of a view is a subview of its surface host below the native plane, not a subview of the plane: the declared overlays of the view are drawn by its own DOM, so the overlay mask of the plane cuts only the regions of the view, and the input under a visible overlay goes to the view web view. A view inside an element with the `hidden` attribute, or with a zero width or height, is submitted as invisible and keeps its web view and process, as any surface does. The preparation can place a view while its surface host is hidden. Revealing the surface reapplies the requested visibility of both the view and its native regions after the host is visible; a view explicitly placed as hidden stays hidden.
- **Regions.** A view creates the composition of its declared regions and overlays with `composition.create({regions, overlays})` of the [view bridge](plugins.md#view-surfaces). The keys equal the declaration and the values are elements of the view document. The controller measures the insets of each element against the viewport of the view, which is the view frame, and submits complete snapshots ([surface composition](surface-composition.md#page-api)). It sends each operation as a view call on the route of view calls below, and the main page runs it with the page operations of the surface, the operations of the composition of a view:
  - `composition.declaration` returns the declared `{kind, regions, overlays}` of the surface, with empty arrays for absent `regions` and `overlays`.
  - `composition.place` with `{regions, overlays}` places one complete snapshot. The main page numbers it with the composition revision of its document, and it sends no placement while a place that leaves the surface out runs ([region lifetime](#region-lifetime)).
  - `document.attach` with `{name}` attaches through the region record of the memory saver, so the region restores its stored interactionState once, and replies `{history}` ([memory saver](plugins.md#memory-saver)). `document.load` `{name, url}`, `document.zoom` `{name, zoom}`, `document.go` `{name, action, offset?}`, `document.post` `{name, message}`, `document.subscribe` `{name, stream}`, `document.unsubscribe` `{name, handle}` and `document.detach` `{name}` run the document operations of the surface.
  - `image.attach` `{name, sidecar}`, `image.focus` `{name}`, `image.caret` `{name, x, y, width, height}`, `image.text` `{name, text}` and `image.detach` `{name}` run the image operations of the surface.
  - `composition.report` with a text reports a failure of the composition through the `report` host call of the surface.

  The view receives the region events through `runtime.native.on` with the names `document-state`, `document-message`, `document-stream` and `image-event`. The page forwards these events to the view in the order it receives them, and it does not start a later event delivery while an earlier delivery is pending. The host forwards a view call with the surface of the view that sent it, and the main page answers the call only in the scope of that surface: it sends every host call with that surface and passes only the named fields of the params. So each call that places or changes a region is verified against the view id of the call envelope, and a view cannot operate the regions of another view. `runtime.native.call` with the name of a host call of the composition or the regions (`compositionDeclare`, `compositionPlace`, and each `document` and `image` host call) is refused with `view call runtime.native.call <name> is not served: a view operates its regions through its composition`, because that call would skip the revision numbering, the region lifetime and the region record. A region is placed under the surface host of the view, above the view, and its insets are relative to the view frame. The host stores the insets and reapplies them when the frame of the view changes, in the same native transaction, so the presentation of the region is in the same window transaction as the frame of the view ([plugin processes](plugin-processes.md) rules 6 and 9). When the view process ends, the host closes the document and image regions of the surface before it creates the view again, because they belong to the composition of the ended document; the new view creates its composition again. At receipt, the page binds each call and event to the current view document. On `view-process-ended`, it cancels pending call replies and event deliveries and ends that document’s subscriptions while keeping the surface mounted for host restart. A handler or callback from the ended document stays canceled even after the restarted document is ready. The restarted document registers its subscriptions again, and refusals from its active document remain errors.

The host also binds each native message callback to the local identity of the view document that installed it. Closing or replacing that document retires the identity before its native resources are released. A callback from a retired identity cannot change the current view channel or reach the main page; the host writes `host.trace.view.callback-cancelled {surface, reason}` when performance tracing is enabled. A `view.error` produced by that document remains an error and is written with the plugin and surface captured by that callback.

Each view source also receives a window-wide generation. The host records the native view channel and emits `declared-ui-source-registered {plugin, surface, generation}` before it connects the first provider message callback or loads the page. Snapshot, call, reply and end metadata carry that generation. Retiring the view emits `declared-ui-source-ended` with the captured generation; it cannot remove a replacement view's source. The main page seeds these instances from the atomic `declaredSourceOrigins` query and applies lifecycle events received after its listeners are installed.

Mounting a view surface installs its native listeners before it declares the composition that starts native view creation. The source generation can therefore be absent at the beginning of the mount. The workbench does not invent a generation or reject the mount for that state; it binds view commands and subscriptions when the ordered source registration has made the current generation available. It accepts a call only when the call carries that current generation. The workbench captures the accepted generation for the document lifetime, so it can process `view-process-ended` after `declared-ui-source-ended` has removed the source from the current-origin map. A later registration replaces that captured generation, and a delayed end from an earlier generation cannot clear the replacement. Callbacks from an ended document remain canceled after a replacement registers.
- **Plugin host calls.** The native handle of a plugin page (a view or a DOM surface) sends only the host commands of its allowlist, `exposureReply`, and subscribes only to the native events of its explicit list, `PLUGIN_NATIVE_EVENTS` in `packages/workbench/view-calls.js`: the region events `document-stream`, `document-state`, `document-message` and `image-event`, and `exposure-request`, the declared route of view exposure ([exposure](exposure.md#relay), `exposure-request` to a view). No other event name is subscribable. A host command or native event outside these lists is refused with `host call <name> is not served to plugins` or `native event <name> is not served`, and the region calls and the view bridge calls are refused with their own texts.
- **View channel.** The view channel is the script and the handler `sok-view` of the configuration above:
  1. At document start the script posts the ready message `{event: "view.ready", plugin, document}` through `sok-view`, where `document` is an identifier that the script generates for the document. The host records it as the ready document of the view. A new navigation of the view clears the record until the ready message of the new document arrives. A navigation starts when the document state's `navigations` count rises (below); the progress of a navigation, which the state reports as `loading` true, keeps the record, because the document that sent the ready message is still the one that loads.
  2. The host sends a message to a view with `window.postMessage(message, location.origin)` in the page world, the form of the document post of [document regions](#document-regions). Each host message carries the field `sok: 1`. A post to a view without a recorded ready document returns false, and the caller writes `error: view channel: <view> has no ready document` to the application log. The theme is the one exception: the host does not post it to such a document (see Theme).
  3. The script keeps each message event whose source is the window and that carries `sok: 1` in a queue, from document start until the page calls `window.sokView.attach`. Attaching delivers the queued messages in order, and then every later message, to the handler of `onMessage`, which `createViewChannel()` of the [view bridge](plugins.md#view-surfaces) attaches. The queue holds the messages of one document, at most 256.
  4. A message without `sok: 1` is written to the application log as an error and passed to no handler. A message that arrives while the queue holds 256 messages is not queued: the script reports the reason `queue full for <plugin>` through `sok-view` in a `view.error` message, the host writes `error: view channel: queue full for <plugin>` to the application log, and the host closes the view and creates it again within the restart limit. No message is dropped without a record.
  5. `core.plugin.views` reports `queued`, the number of messages in the queue of the current document that wait because the view has not attached.
  6. A `view.error` message `{event: "view.error", plugin, reason}` reports a failure of the page before its first call: the start script sends it for a script that fails to load (a module graph with an import that does not resolve), an uncaught error and an unhandled rejection. The host writes each one as `error: view <plugin> <surface>: <reason>` on the error display path and the view continues. A reason of the queue overflow keeps its record `error: view channel: queue full for <plugin>` and closes the view ([view channel](#view-surfaces), item 4). A reason that is empty is refused.
- **View operations.** An operation that starts inside a view (its own click or key) starts in the view page: the view bridge's `runtime.beginOperation(event, fields)` assigns the identifier `p<time origin of the view page>.<n>` in the form of the page's `beginOperation` (`packages/plugin-api/operation.js`), stores the first event `event` with `fields` through `runtime.log` with the identifier, and returns the list. The view passes the list with the calls that carry the operation out: `runtime.sidecar(name).send(id, body, cids)`, `runtime.command(name, params, {cids})` and `runtime.log`. A command call with `cids` reaches the command through the view-call route: a command of the plugin receives them as `cids` of its request in the exposure registry, and a core command receives them as `{cids}` in the context of its handler, which passes them on each host call that the handler makes (`host.call(name, arg, {cids})`).
- **View call.** A view calls the host through `sok-view` with a call request `{sok: 1, id, command, params}`, and the call request carries the member `cids` when the view passes it; the host forwards the member with `view-call`, and it cancels a pending call with `{sok: 1, id, cancel: true}`. The request is the call envelope of [plugin processes](plugin-processes.md) rule 3, and its reply returns through the post path of item 2 of the view channel. The host removes the call from its open-call set only after posting the reply to that same current view generation. A stale or failed post leaves the call open, so a view process that ends first settles it with reason `process-ended`.
  1. The host forwards a request whose `id` is an integer and whose `command` is a non-empty string as the event `view-call {surface, plugin, id, command, params}` to the main page of the window. It forwards a cancel whose `id` is an integer, whose `cancel` is `true` and which names no command as the event `view-call {surface, plugin, id, cancel: true}`. The `surface` and `plugin` are those of the view that sent the message. A message with any other invalid field, or with a `cancel` that is not `true`, is written to the application log as `error: view channel: <reason>` and is not forwarded.
  2. The main page answers a request with the handlers that a DOM surface context uses:
     - `tab.state.read` returns the tab state of the surface, and `tab.state.write` stores its params as the tab state, within the size limit of `surface.unload`. Both fail when the plugin declares no `surface.unload`.
     - `runtime.native.call` with `{name, payload}` runs the host call `name` of the surface with `payload`. `name` is a non-empty string.
     - `runtime.sidecar.send` with `{id, sidecar, body, cids}` sends through the declared sidecar named by `sidecar`, as `runtime.sidecar(name).send` does.
     - `runtime.clipboard.read` with `"text"` or `"fileURLs"` returns the clipboard value of that type, or `null` when the clipboard holds no payload of that type. With `"png"` it returns `{present: true, type: "png", data}`, whose `data` is the payload as base64, or `null` when the clipboard holds no PNG payload; the read is user-initiated, as the clipboard bridge makes it. `runtime.clipboard.writeText` with a string writes the text. `runtime.clipboard.persistPNG` with `{data}`, whose `data` is a PNG payload as base64, persists the payload and returns `{path, shellQuotedPath}`, as the clipboard bridge of the surface context does.
     - `runtime.links.open` with a non-empty URL string opens the link.
     - `tab.title`, `tab.footer`, `tab.directory`, `tab.modified` and `tab.error` take the value as their params and run the tab report of the surface, as the surface context entry runs it, with the same refusal of an invalid value. `tab.notify` takes `{text, policy}` and `tab.keep` takes `{reason, on}`. Each replies `null`.
     - `runtime.log` takes `{level, event, fields, cids?}` and writes the record through the event writer of the page, which adds the plugin and surface of the view as the surface context does; `cids` is the optional list of the correlation identifiers of the chain that the record continues ([logging](logging.md#operation-chains)); the log of the surface context validates it as every log call does. A view has no gate: it builds the fields of the record and sends it to the page batch, and the writer of the host applies the policy to the record by its class and counts a refusal in `log.gated`; nothing is dropped silently. The call replies `null`.
     - `runtime.error` takes `{where, text}`, the error line of an error that the view shows on its own page, and writes `error page surface <surface> <where>: <text>` to the application log through the record path of the error display of the page, so the view records each error at the moment it shows it, as the error display of the main page does. `where` is a non-empty string without a control character and without `: `, and `text` is a non-empty string; another value is refused with `view call runtime.error requires a non-empty where without a control character or ": "` or `view call runtime.error requires a non-empty text`, and nothing is written. The call replies `null`.
     - `runtime.log.levels` is not served: a view has no level query, so the call is refused with `view call runtime.log.levels is not served`. A record is passed to `runtime.log`, and the writer of the event log decides whether it is stored ([logging](logging.md#policy)).
     - `runtime.contributions` takes `{point}` and returns the connected items of the extension point `point` of the view's plugin, as `contributions(point)` of the surface context returns them, each as `{plugin, index, item, module}`, where `index` is the position of the entry in the `contributes` of its plugin and `module` is the URL of the module on the core root (`soksak://core/modules/...`). A point that the plugin does not declare is refused with the error of the surface context. `runtime.contributions.fail` takes `{point, plugin, index, reason}` and makes that connected item `invalid` with `reason`, as `fail(reason)` of the surface context does, and replies `null`; a `reason` that is not a non-empty string is refused with `view call runtime.contributions.fail requires a non-empty reason`, and an item that is not connected with `view call runtime.contributions.fail: <point> has no connected item <index> of <plugin>`.
     - `runtime.textSize.read` returns the text scale of the surface, and `runtime.settings.read` returns the values of the settings of the plugin. `runtime.textSize.on` and `runtime.settings.on` register the change subscription of the view events below. Each replies `null` except a read.
     - `runtime.status.watch` takes `{name}` and `runtime.status.unwatch` takes `{name}`. Each names a status that the view follows: a core status, whose owner is `core`, or a status of the plugin of the view, whose owner is the plugin id. A name that is empty, not text, or has another owner is refused and runs nothing, with `view call <command> requires a non-empty name` or `view call <command> <name> is neither a core status nor a status of <plugin>`. A watch of a status of the plugin that the exposure does not declare is refused with `view call runtime.status.watch <name> is not a declared status`. The watch replies `null` once the page has registered its follow, and a second watch of the same name registers nothing. An unwatch of a name that the view does not watch replies `null` and changes nothing. A refusal of a watch writes `surface <surface> status <name>: <text>` to the application log, as `runtime.error` does.
     - A `core.*` command runs as `runtime.command` runs it. A command of the view's plugin runs through the owner check of exposure, so only a command that the plugin registered runs. A name of another owner is refused with `command <name> belongs to <owner>, not <plugin>`, and a name without an owner with `view call <name> names no owner`. A `tab.` or `runtime.` name that the list above does not serve is refused with `view call <name> is not served`.
     - A request whose `id` is already pending is refused with `view call <id> is already pending`.
  3. The main page replies with `viewReply {page, surface, generation, id, result}` or `viewReply {page, surface, generation, id, error: {code, message}}`. `page` is the non-empty current document identity `String(performance.timeOrigin)`. A handler that returns no value sends `result: null`. After generation validation, the host records `host.view.reply.dispatch`; for a current target it records after the native post operation returns. `posted` means that operation accepted the message for posting, and `discarded` means the target generation was no longer current. A native post error rejects the host call and writes no dispatch record. This record does not prove that JavaScript received or handled the message. A posted reply is `{sok: 1, id, result}` or `{sok: 1, id, error}` for the ready document of the view. A reply to a view without a ready document fails at the page with `<surface> has no ready document`. A cancel has no reply of its own. The pending call that it names replies with the error `{code: -32000, message: "cancelled"}`, and the handler of that call keeps running with its result discarded. A cancel of a call that has no pending call ends nothing.
  4. The call layer of the view resolves or rejects the call. The time limit is the `timeout` of the command. A reply that arrives after that limit is a late reply and is discarded (plugin processes rule 3). The host keeps no record of a forwarded request. The reply to a cancelled call arrives after the call layer has ended the call, so the layer counts it as a late reply.
  - The page answers the subscription calls `runtime.native.on` with `{name}`, `runtime.sidecar.on` with `{id, sidecar}`, `runtime.sidecar.onFailure` with `{id, sidecar}`, `runtime.textSize.on` and `runtime.settings.on`, `runtime.status.watch` and `runtime.status.unwatch` as stated in view events below, and the registration call `runtime.command.register` with `{name}` as stated in view commands below. Each replies `null` when it applies. Each subscription registration of the page is a promise of its off function: the page registers a key once, keeps the off function of the registration, and refuses a registration whose result is not a promise, with an error that names the registrar.
  - `runtime.theme` is not a call. The theme reaches a view as the theme message (see Theme), so a call of `runtime.theme` is refused with `view call runtime.theme is not served`.
- **View events.** A view subscribes to an event of the page with a subscription call of the route above. The page delivers each event of a subscription to the view as the host message `{sok: 1, event, data}`:
  - `runtime.native.on` with `{name}` delivers each host event `name` of the surface, and `data` is the event object that the DOM surface context receives.
  - `runtime.sidecar.on` with `{id, sidecar}` delivers each sidecar message of the session `id` as `event: "sidecar.message"` with `data: {id, body}`.
  - `runtime.sidecar.onFailure` with `{id, sidecar}` delivers each failure of the session `id` as `event: "sidecar.failure"` with `data: {id, reason}`.
  - `runtime.textSize.on` delivers each change of the text scale of the surface as `event: "textSize"` with the scale as `data`, and `runtime.settings.on` delivers each change of the settings of the plugin as `event: "settings"` with the values as `data`. A change while the value is unchanged is delivered to no view, as the surface context delivers none.
  - The workbench sends each change of the stored levels as `event: "log.levels"` with the levels as `data`. It reads the levels again at each change of the policy in force of its gate ([logging](logging.md#policy)) and sends only levels that differ from the levels it sent last. No view call subscribes a view to it, so no view receives it.
  - `runtime.status.watch` delivers each value of the watched status, the first one included, as `event: "status"` with `data` `{name, value}`, where `value` is the value that the exposure registry reports for the name. The SDK passes `value` to the listeners of the name, and `runtime.status.watch(name, listener)` returns the function that ends the watch of that listener. The page ends the subscription at `runtime.status.unwatch` of the name and when the surface closes. The host relays the call and the event without reading the command or the status name ([host contract](host-contract.md#contract-cases), `view.status.relay`). `status` is reserved for this event, as `theme`, `settings`, `textSize` and `log.levels` are, and a plugin cannot subscribe a native event of that name.

  - The main page sends `declared-ui.expanded` to the selected view source as `viewEvent {surface, generation, event, data}` with `data: {status, tree, path, expanded}`. `generation` is the selected view source generation. `status` is the name inside the plugin. The view receives it through `runtime.native.on(\"declared-ui.expanded\")`, updates the plugin value, and pushes a new declared UI snapshot; the workbench changes the drawing only after accepting that snapshot.

  The page registers a subscription once; a second call with the same name or id replies `null` without a second registration. The page sends each event with `viewEvent {surface, generation, event, data}` using the generation of the subscribed view document. Restart ends that document's subscriptions; pending and late callbacks from it remain canceled and are never relabeled with the replacement generation. The host accepts an event only for the current generation and posts `{sok: 1, event, data}` to the ready document without exposing the generation to `sok-view`. An event for a current view without a ready document fails with `<surface> has no ready document`, and the page writes that error to the application log. A view that restarts subscribes again. The view passes each event to the listeners of its event name and ignores an event that no listener has.
The Tauri host decodes one current view-message envelope once and dispatches it by reply, call, declared snapshot and readiness precedence. Dispatch retains the existing field validation and forwards the full payload without parsing it again for unrelated handlers.

- **View commands.** A view declares each command it serves with the call `runtime.command.register` with `{name}` at its start:

  A command registration belongs to one view source generation. Each replacement document registers its commands once in its new generation; a second registration in the same generation is an error. The surface keeps one forwarding handler per registered command, which sends through the current view command layer.

  1. The page applies the registration through the registry of the exposure. A name that the `exposes` of the plugin does not declare, or a name of another plugin, is refused with the registry error, and the call replies with that error.
  2. A command request from the exposure of the core reaches the page, which sends `viewRequest {surface, id, command, params}`, where `id` is the id of the exposure request and `params` are its params. When the request has the member `cids`, the page sends it too: the correlation identifiers of the operation or input that caused the request ([operation chains](logging.md#operation-chains)). The run that starts a command request passes these identifiers as `cids` of the request (`run(name, params, surface, cids)` and `runOwned(name, params, owner, cids)` of the exposure registry), and an empty list has none. The host posts `{sok: 1, id, command, params}` to the ready document of the view, with the member `cids` when the request has it. A list that a line cannot hold (an empty identifier, or one with a quote, a backslash or a control character) is refused by the exposure registry with the code `-32602` before the request reaches the view, and the host refuses a `viewRequest` with such a list with an error that names the request, so it is posted to no view. A request to a view without a ready document fails with `<surface> has no ready document`.
  3. The view answers through `sok-view` with `{sok: 1, reply: id, result}` or `{sok: 1, reply: id, error: {code, message}}`. The view runs the handler of `command` with `params` as its first argument and the context `{cids}` as its second argument, where `cids` is the list of the request and is absent when the request has none. A record that the handler makes with `context.log.<level>(event, fields, {cids: context.cids})`, or a sidecar request that it makes with `context.cids`, joins the chain of the cause. An error that the handler throws is the error of the reply. A request for a command that the view did not register replies with the error `{code: 1002, message: "view command <command> is not registered"}`.
  4. The host forwards a reply whose `id` is an integer and that has exactly one of `result` and `error`, whose error has a message, as the event `view-reply {surface, plugin, id, result}` or `view-reply {surface, plugin, id, error: {code, message}}` to the main page. Any other reply is written to the application log as `error: view channel: <reason>` and forwarded to no page.
  5. The page answers the exposure request with the reply. The declared timeout of the command (plugin processes rule 3, default 10000 ms, from 1 to 600000) bounds the wait: when the view does not reply in time, the page answers the request with `{code: -32000, message: "command <name> did not reply within <ms>ms"}`, and a reply that arrives later is discarded and counted as a late reply.
  6. Closing or replacing a surface ends its in-flight view calls and event deliveries. The page aborts its wait for each pending call; a handler that already started may finish, but its result is discarded and no reply is sent to the ended view. A queued event that the host refuses after closure is canceled. The page records each cancellation as `page.view.call.cancel` or `page.view.event.cancel` at debug level. A refusal while the surface remains open is still an error and is written to the application log. A call receipt without `page.view.reply` is explained by the matching cancellation record when closure ended it.
- **View exposure.** The view registers status and dom entries, and the core document command `core.surface.hit`, through `runtime.native.call` with `{name: "registered", payload: {kind, name}}`. The main page checks the declaration and registers it through the registry and the surface's `exposureRegister` call. The host stores it and announces `exposure-registered` ([exposure](exposure.md#relay)). Plugin commands use `runtime.command.register`. A forwarded request reaches the view through the `runtime.native.on` subscription named `exposure-request`, with `{id, surface, method, params}`. The main page consumes every forwarded view request without answering from a placeholder. The core bridge answers its three document entries once and does not deliver those requests to plugin listeners. Other requests reach the plugin listener. The view replies through `runtime.native.call` with `{name: "exposureReply", payload: {id, result|error}}`, which the page forwards through the surface's `exposureReply` call. A request without an answer ends at the host timeout.
- **Declared UI snapshots.** A view pushes the declared UI snapshot of a status as the message `{event: "declared-ui.snapshot", plugin, status, seq, value, skipped}` through `sok-view`. The host forwards a snapshot whose fields are valid as the event `declared-ui.snapshot {surface, plugin, status, seq, value, skipped}` to the main page of the window, which acknowledges it and draws it ([declared UI](declared-ui.md#status-mapping)); the host writes no event of its own for a snapshot ([plugin processes](plugin-processes.md) rule 2). A snapshot that names no plugin or another plugin than the view's, that has no `status`, no integer `seq` from 1, no `skipped` count, or no `value` is written to the application log as `error: view channel: <reason>` and forwarded to no page. The main page acknowledges a snapshot as the view event `declared-ui.snapshot.ack` whose `data` is `{plugin, status, seq}`, and it pulls the current value of a status with the call `declared-ui.snapshot.request` with `{status}` through the view command route, whose reply carries `{seq, value}`, with the `seq` 0 and the value `null` when the source has no value yet.
- A view surface incarnation has a monotonically increasing generation assigned before its native view is created. The host includes it only in main-page lifecycle and snapshot metadata, checks the expected generation of acknowledgement, pull and expanded requests before dispatch, and tags pull replies with it. These fields are not added to the public `sok-view` message. A request for a retired generation returns an explicit cancellation disposition, not a fabricated empty snapshot.
- **Presentation wait.** A view joins the presentation wait only at the first display after a card layout change. During a continuing gesture, such as a divider drag, the frame of the view is placed in the same commit as its card in every frame, and the commit does not wait for the content that the view draws afterwards. The wait ends with the first of: the presentation completion of the view; the end of the view process; the view becoming invisible when the change ends; the notification `host.trace.view.unresponsive`. The native transaction holds its commit until each joined view presents or its wait ends. The wait is not ended by a timer. The host owns the wait, because the host commits the transaction and observes each end, so the host writes `host.trace.view.presentation-abandoned {surface, reason}` with the reason of the end when the wait ends without presentation completion, while the performance trace is on. A view joins the wait once per change. When it ends without presentation completion, the commit continues without that view, the host sends the notice `view-presentation-abandoned {surface, reason}` to the surface, and the loss is counted as `abandoned` in `core.plugin.losses`.
- **Theme.** Before the workbench sends a `syncSurfaces` request containing a view, it waits for the host reply to the latest `setTheme` call. A failed theme reply refuses that view placement and remains in the host error log; placement without a view does not wait for a theme reply. At creation the host gives the view configuration a document-start script that sets `window.sokTheme` to the frozen value `{scheme, tokens}` of the current theme, so the first script of the page reads the tokens from `window.sokTheme` before any page script runs. The host adds the script before it loads the page of the view. A later theme change is sent to the view as a host message through the post path, except that the host does not post it to a document without a recorded ready document. The host sends the current theme after each ready message, so a change before ready is neither an error nor lost. The theme message is `{sok: 1, event: "theme", data: {scheme, tokens}}`, where `data` is the value of the theme that the host holds. The view keeps the last theme message, and a listener of `runtime.theme` that subscribes later receives it at once.
- **Start values.** At creation the host gives the view configuration a document-start script, beside the theme script, that sets `window.sokSurface` to the frozen start values `{surface, params, origin, project, declarations}` of its surface, so the first script of the page reads them before any page script runs. `surface` is the identifier of the surface, which is a context member and not a URL query; `params` are the parameters of the tab or `null`; `origin` is the frozen `{directory}` with the directory that the tab that opened the tab recorded, or `{directory: null}` when that tab recorded none, the form of the `origin` of the surface context ([plugins](plugins.md#tab-reports)). The preparation must carry `origin`: a missing origin, a `null` origin, and a value that is not `{directory}` with a path or `null` are refused, and a view surface whose preparation carries no start values has no origin and is refused; `project` is the frozen `{id, root}` of the project that the window shows (the project id and its canonical root), or `null` in a window without a project; and `declarations` contain the plugin’s `exposes` together with the core document, input and hit declarations. The page sends the values with the preparation of the surface (`syncSurfaces`), the host checks them with the rest of the request, a value of the wrong form is refused with the reason of its check, and a surface of another composition carries none. The workbench derives those values from the complete descriptor for the tab and passes them in the existing `start` member of the host request; it does not add a second `params` member. The host adds the script before it loads the page of the view, and it injects the values again from the record of the surface when it creates the view again.
- **Origin refusal.** The origin of a view is read at the layout read, before the view starts, and a refused view starts none ([projects](projects.md#tab-origin)). The check runs in this order, and the first match gives the text, with `<id>` the surface identifier: `surface "<id>": view start origin is missing` when the origin member is absent; `surface "<id>": view start origin is not {directory} with a path or null` when the origin is `null`, is not an object (a JSON array is not an object), has a member other than `directory`, or has a `directory` that is neither a string nor null; `surface "<id>": view start origin directory is empty` when the string is empty; `surface "<id>": view start origin directory is not an absolute path` when the string does not start with `/`, starts with `//` or `/<letter>:`, or contains a NUL byte. The path rule is one string test with no platform path API, so every host and the page agree: `/a` is accepted, and `//server/share`, `/C:/x`, `C:\x`, `relative`, and a path with a NUL byte are refused. The `//` form is the UNC share prefix on Windows and is implementation-defined on POSIX. The `/<letter>:` form is the drive prefix; the same rule refuses `/a:b`, a legal POSIX name, as a stated portability choice. `/\` is a legal POSIX name and is accepted. A view tab refused at the layout read keeps its tab in the layout, shows the text, and is logged. The page refuses the same faults with the same text in `createSurfaceContext`, and it never fills a missing origin.
- **Surface phase.** The workbench reports the phase `ready` of a view surface once the view declares its composition, as a module surface reports it after its module mounts. A view mount that fails reports `error` with the mount error. The view page reports no phase: its `status.report("ready")` is accepted and ignored, because the workbench keeps the state. Core commands that wait for the surface resolve at the same declaration (`waitSurfaceCompositionDeclared`).
- **Call records.** The workbench writes `page.view.call {plugin, surface, generation, id, command}` when it accepts a view call, `page.view.reply {plugin, surface, generation, id, outcome}` when it sends its reply, and `page.view.call.cancel {plugin, surface, generation?, id, command}` when it cancels the reply, all at the debug level ([event catalog](events.json)). A reply or cancellation matches a receipt only when page, plugin, surface, generation and id all match. The cancellation generation is absent only when its incoming event had no valid generation. The successful native `viewReply` host call carries `page`, accepted generation, surface and id in its arguments. `host.view.reply.dispatch` records the result of the native post operation with the same page, window, surface, generation and id. `posted` is native post acceptance, not JavaScript receipt; `discarded` is a stale-target no-op. The page's successful `viewReply` call and this record are separate evidence and both must match the current page identity.
- **Input.** A view has no shortcut table and no key listener, and the bridge sends no call on a key event. A key that the view owns (its text input, its own Escape action) keeps its default action and reaches the view's first responder, which the view handles. A view runs a workbench command for a key that it forwards with `runtime.command(name, params)`, as [plugin processes](plugin-processes.md) rule 7 states; the host never acts on a key from a view. The view reads the rows of the [shortcut table](exposure.md#keyboard-shortcuts) with the view call `runtime.shortcuts.read`, which answers with `{key, owner, command}` for each row whose owner is `workbench` or `view`; rows of the native menu are not returned. Escape is an ordinary key: a view with its own Escape action decides it in its handler, and a view with none runs `core.picker.close` for Escape while a page picker is open; the bridge enforces neither rule. A workbench command that a view runs and that fails writes `page.input.shortcut.failed {plugin, command}` at error level when the command is a row of the table, and replies with its error. The view calls have no `runtime.shortcuts.missing`, `runtime.shortcuts.run` or registration. Input composition goes to the first responder of the view. A view accepts the first mouse down of an inactive window. AppKit does not deliver that press to a web view that refuses the first mouse; it only activates the window. Because the view accepts it, the press reaches the page of the view and the view becomes the first responder, as for a press in an active window. A document region keeps the refusal.
- **Process start.** The host writes `host.trace.view.process-request {plugin, surface}` when it creates a view, and `host.trace.view.process-ready {plugin, surface}` at the first ready message of that view.
- **Responsiveness.** When WebKit reports that the WebContent process of a view stopped answering its responsiveness check, the host writes `host.trace.view.unresponsive {plugin, surface}` and sends `view-responsiveness {surface, plugin, generation, responsive: false}` to the main page of the window. When the process answers again, the host writes `host.trace.view.responsive {plugin, surface}` and sends `responsive: true` with the same generation. The host captures the generation of the view that installed the callback, refuses a callback from a retired view, and sends the notice through the ordered main-page source event stream. The main page applies the notice only while that generation is current and records a stale notice as `page.view.event.cancel` with event `view-responsiveness`. The notice ends no call of the view. The main page keeps the state of each view surface in `core.plugin.views {plugin, surface, responsive}`, which it removes when the surface is disposed. A document region receives no notice. A `view-presentation-abandoned` notice records a completed presentation wait and contributes to the plugin's abandoned-presentation count; it does not change the live view state and remains on the presentation event path.
- **Process end.** When the view process ends, the host ends each call that the view has open with the reason `process-ended`, writes `host.call.peer-lost`, and ends the presentation wait of the view. It closes the document and image regions of the surface and sends the event `view-process-ended {surface}` to the main page of the window, which forgets the regions of that surface until the new view attaches them again. The host then creates the view again, and the new view restores its state from its saved tab state. The restart limit is the one of [plugins](plugins.md#view-surfaces): four failures of the same surface within 300 seconds stop the restarts. At the fourth failure the host writes `error: view channel: <surface>: the view failed 4 times within 300 seconds and is created again when its tab is reopened` to the application log and sends the event `view-stopped {surface, plugin, reason}` to the main page of the window, with the reason `the view failed 4 times within 300 seconds and is created again when its tab is reopened`. The main page shows the reason on the card through the error display, and the card keeps it until the person reopens the tab.

## Plugin host

A plugin host is a hidden web view of a plugin whose manifest declares one, attached to the window and not to a surface host. It shows nothing: it holds no surface frame, no regions and no presentation wait, takes no input, and no hit test reaches it. Its channel, exposure registration, snapshots, restart limit and state are the contract of [plugin host](plugin-host.md).

## Regions

A region is a place on a surface where native content is displayed. Its ownership, hierarchy, complete-snapshot geometry, stacking, input, generation, and raster rules are defined by [surface composition](surface-composition.md). This document defines behavior specific to document and image suppliers.

Every native region is a descendant of its surface's `SurfaceHost.NativePlane`. It is never a sibling of the host or DOM plane. The host derives region frames from the applied complete composition and clips them to the host. A region moves, hides, dims, and closes synchronously with its surface.

Regions are below modal dialogs. Document-region renderers are excluded from the presentation wait; visible image regions must have the exact current raster before the prepared layout commits. Each region has a unique name within its surface. The host reports the region's name, rectangle, visibility, and focused state through `host.window`.

There are two kinds of region suppliers:

- **Document regions**: Created by the core as subviews of surfaces, hosting web documents.
- **Image regions**: Created by external sidecars, supplying shared images as native surfaces.

### Region lifetime

A native document callback keeps its closure alive until the invocation returns, including when it closes or replaces its own document. Closing unregisters the stored receiver immediately; it does not release a closure that is still executing.

The page serializes each placement from retained-view preparation through host placement and page-side release. A later placement cannot prepare a mount while an earlier placement can still release it. A rejected placement reports its error to its caller and does not prevent the next placement from running.

The host owns the end of the regions of a surface that a place leaves out: before the place replies, both hosts close every document and image region of each surface that the page no longer lists. The page runs the place first and releases the module of such a surface only after the place succeeded; that release drops the page-side handles of its regions and does not call `documentDetach`, `documentUnsubscribe` or `imageDetach`. Before the place runs, the page stops the composition of each surface that the place leaves out: it sends no `compositionPlace` and no `imagePlace` for it and detaches nothing, because the host removes the composition of such a surface during the place. A failed place releases nothing, so the surfaces it would have left out stay mounted, and their compositions resume and place their current geometry again. The place also ends the sidecar sessions of such a surface in the host, so a send of its module to its sidecar while the place runs waits for the outcome: a failed place sends it, and after a successful place it and every later send of the module, such as the end of the session that its dispose sends, are not sent, because a host send would open a session without a project root. A region that the page detaches while its surface stays placed is detached through the host, and a failure of that detach is reported. This holds for every removal through a place: closing a tab, unloading a tab and the surfaces that a commit no longer retains.

## Input over native views

A native view is placed on the DOM: it draws the DOM element it is placed on and does not own that element's input. The page decides input over it for the DOM element under the point, as if the native view were absent:

- Pointer and wheel events pass through image regions to the page; the page decides their meaning, including the cursor.
- A native view registers no cursor rectangles and no dragged types.
- Files dragged from another application onto a window go to the window's file drop view, the only native drag destination of the window composition. It lies above the composition's web views, accepts only file URLs, and returns no view from hit testing, so pointer events and other drags reach the views below. The view converts file reference URLs, which Finder places on the drag pasteboard, to file path URLs, and refuses a drop whose reference no longer resolves to a file. A drop sends the page `files-dropped` with the JSON text of `{urls, x, y}`, the file URLs and the drop point in page coordinates; the hosts pass the text unchanged, and the page parses it. The page finds the surface of the DOM element at the point and runs the drop command that the surface's plugin declares as `surface.drop` in `plugin.json`, on that surface, with `{urls}`. `core.drop` reports the last drop as `{urls, x, y, surface, command, error}`; a drop outside every surface, or on a surface whose plugin declares no drop command, sets `error` to its reason and runs nothing, as does text that is not such an object.
- The hosts disable the file-drop handling of their frameworks, so the file drop view is the only receiver of dropped files.

## Document regions

A surface page shows a web document in one of its elements through a document region. Surfaces themselves always show a page of their plugin ([plugins](plugins.md)); a web address is never a surface.

- The manifest declares a unique name that matches `^[a-z0-9][a-z0-9-]{0,63}$`. The page obtains the document handle from `createSurfaceComposition`; individual attach, place, and detach operations are not public.
- The host creates a web view under the calling surface's `SurfaceHost.NativePlane` and verifies on every call that the calling web view belongs to the surface named in the request: the view of a [view surface](#view-surfaces). A surface cannot operate another surface's regions.
- The complete composition reports the element's position as insets in CSS pixels from the edges of its viewport and whether it is shown. The host stores the insets and reapplies them when the outer surface changes in the same native transaction for an image region. A document region reapplies its insets at placement and when its frame changes, outside a native transaction; the spec does not claim a transaction for document regions.
- A page hides a region by hiding its element. The composition then reports the region as not shown, and the host hides the native view, so it neither draws nor takes input. The browser plugin hides its document element while `browser.location` reports an empty `url`, which is its state before the first address. A browser surface without a stored address opens the address of the browser setting `browser.home` (label `홈 주소`, an address setting whose default is empty) when it mounts; while that setting is empty, the surface starts in the empty state. In the element's place it shows the empty state `browser.empty` with the text `주소를 입력하세요`; a click on it runs `browser.address.select`, which focuses the address field and selects its value. When a state reports a nonempty `url`, the plugin removes the empty state and shows the document element again.
- Regions load `http`, `https`, `file`, and `soksak` addresses ([application addresses](native-host.md#application-addresses)). The application's own scheme is rejected, both when requested and when the document navigates. A `file` address loads with `loadFileURL:allowingReadAccessToURL:` granting read access to the file's containing directory; a path outside the granted directory is refused by WebKit itself. Region documents use one persistent website data store, separate from the application documents, and receive no application bridge. The store keeps its site data, such as cookies, local storage, and caches, in the directory `document-data` inside the application's configuration directory: the `--config-dir` directory when the application starts with it, otherwise the default configuration directory. Two configuration directories therefore never share site data, and removing a configuration directory removes its site data. The host creates the store with `_WKWebsiteDataStoreConfiguration` `initWithDirectory:` ([private native APIs](../operations/private-native-apis.md)), because the public `dataStoreForIdentifier:` keeps every store in the application's WebKit container.
- A plugin address `soksak://<plugin id>/<path>` names a file of the plugin whose surface owns the region. The composition declaration carries the surface's `plugin`, and the host serves `<path>` from the folder that `plugins/installed.json` records for that plugin when it is installed and enabled. An address of another owner, a path with an empty, `.` or `..` segment, and a missing file answer not found. Each refused page request writes `error: document view: plugin file not found: <URL>` to the application log at the error level, where `<URL>` is the normalized address of the request, so the log holds the URL and the reason of every refusal. A page that requests a missing file of its own plugin release is a defect of that plugin, so the refusal is an error, not an observation. The host sends the content type of the file's extension: `text/html` for `.html`, `text/javascript` for `.js` and `.mjs`, `text/css`, `application/json`, `application/wasm`, `image/svg+xml`, `image/png`, `image/jpeg`, `image/webp`, `image/x-icon`, `font/woff2`, `font/woff`, `font/ttf`, `font/otf` and `text/plain` for their extensions, and `application/octet-stream` for another one. A plugin document has the origin `soksak://<plugin id>`, so the documents of one plugin share their site data and the documents of two plugins do not.
- A view, never a region, sends a request for the core root `soksak://core/<path>`. A view configuration is created with `isView` set, and only that configuration dispatches the host `core` of its scheme. The request goes to the core root resolver that the host registers with the platform ([host contract](host-contract.md#contract-cases), `document.core-root.native`). The resolver receives the plugin id of the view configuration and the path, and it returns the file with its content type or refuses the path. A served response carries `Access-Control-Allow-Origin: soksak://<plugin id>` of that view configuration; the request Origin is never echoed, and `*` is never sent. A refused response carries no such header, so the page's fetch or module import fails. A document region has no core root grant: its `soksak://core` requests answer not found, and the resolver is not called. The rule that decides which files a view receives is [plugin processes rule 4](plugin-processes.md).
- A plugin document keeps bytes in the binary store of its region, which holds them under binary ids for the region's plugin only. `POST soksak://<plugin id>/.binary` stores the request body and answers the JSON object `{"id", "length"}`, where `id` is a 32-character lowercase hexadecimal string that the host mints and `length` is the number of stored bytes. The host reads the body from `HTTPBody`, or from `HTTPBodyStream` when WebKit delivers the body as a stream. A request that WebKit delivers with neither form, such as a Blob body, is refused with 400, so a page sends its bytes as an ArrayBuffer view. The bytes keep the request's `Content-Type`, and an upload without one keeps `application/octet-stream`. `GET soksak://<plugin id>/.binary/<id>` answers the stored bytes with that `Content-Type` and their `Content-Length`, and the host releases the id when the response finishes, so a second request for the id answers not found. An upload is refused when its body is empty (400), when it is over 16 MiB (16777216 bytes, 413), or when the bytes stored by the region would be over 64 MiB (67108864 bytes, 413). A request for another plugin's origin is refused with 403, a method other than POST on `/.binary` or GET on `/.binary/<id>` with 405, and an id that is not stored with 404. Each refusal answers `{"error": <reason>}` with `application/json` and writes the reason to the application log as `error: document view: <reason>`. A page of another origin reads no response body, because the responses carry no CORS headers, so it sees a network error and the log holds the reason. The host also takes an id from the region in native code, which returns its bytes and releases the id. Closing the region releases every id it holds. A plugin release refuses a file whose path has a `.binary` segment, because the host answers that path before it looks up a file.
- A host takes the bytes of a binary id of a document region with the take operation of the platform: the native take returns the bytes and releases the id, so a second take of the same id fails with the native error text. A document that is not attached refuses the take with `document "<name>" is not attached`, the text of the other document operations. The first command that names a binary id arrives with the view.
- A plugin document exchanges messages with its page. `post(message)` of the document handle sends a JSON value to the region: the host runs `window.postMessage(message, location.origin)` in the document's page world, and it fails with `document <name> shows no plugin document` when the current document is not a plugin document of the region's plugin. A script of the host's content world forwards each `message` event that the document's window receives with the window itself as its `source`, so the page also receives the messages it posted; the host sends `document-message {surface, document, message}` only to the owning surface, where `message` is the event's data as JSON. Only plain JSON is sent: the content-world script refuses a value that is not null, a boolean, a finite number, a string, an array or a plain object of such values, or that has a cycle or a property that JSON would drop (for example an ArrayBuffer, a typed array, a Date or a Map), and it reports `{error}` with a reason that names the type, such as `the message holds an ArrayBuffer, which is not JSON`, so the host writes `error page document message <name>: <reason>` to the application log. Other documents have no message channel.
- A region document follows the owning window's dark or light appearance: `prefers-color-scheme` matches the application mode and changes with it. The host sends the user agent of Safari on the same WebKit: it appends `Version/<major>.<minor> Safari/605.1.15` to the WebKit user agent through `applicationNameForUserAgent`, where the version is the `CFBundleShortVersionString` of the system Safari at `/Applications/Safari.app`. The region identifies itself as Safari because sites select their page by the browser name in the user agent and send a reduced page to a WebKit user agent without one; Google Search sends that user agent its basic page with gray buttons and sends Safari its current page. A site's own light or dark design is not changed: Google Search keeps the same appearance in both modes, as in Safari. A site can show the appearance it stored in an earlier visit with the same configuration directory. The host fails document creation when it cannot read the Safari version.
- `go` performs `back`, `forward`, `reload`, or `stop`, or `entry` with an integer `offset` other than 0, which loads the session history entry at that offset from the current entry, and returns whether it ran. An `offset` outside the history returns false; `offset` with another action, or `entry` without it, is an error.
- WebKit keeps each page that a region navigated away from in its back-forward cache, suspended with its WebContent process, until the cache exceeds its capacity. A region that stays hidden for 5 minutes clears its back-forward cache, and every region clears it when the [memory pressure](hosts.md#memory-pressure) source of the host reports `warn` or `critical`; a report of `normal` clears nothing; a region without back or forward entries has nothing to clear. Each clear is recorded as the event `native.document.backforward_cleared` with `reason` `hidden` or `pressure`. Going back or forward in that region then loads the page again, and the history entries are kept.
- A region answers the query of the [memory saver](plugins.md#memory-saver) with `{media, capture, form}`: `media` is the private `_isPlayingAudio` of its web view, whether a media element of the page plays, is not muted and has a volume above zero, `capture` is whether the public `cameraCaptureState` or `microphoneCaptureState` is active, and `form` is whether a frame document holds a form flag. The public `requestMediaPlaybackStateWithCompletionHandler:` is not used: WebKit answers `playing` for a page whose media element has never played, because the reply is `paused` only when a media session of the page is paused. A script of the region's content world runs in every frame, generates an identifier for its frame document, and reports the first trusted `input` event on a form field (`input`, `textarea` or `select`) or a `contenteditable` element; the region keeps the flag per identifier, and `pagehide` or a form `submit` of that frame document clears it, and a main frame navigation commit, a reload included, clears every flag. A query of a closed region answers an error.
- A region returns its public `interactionState` as base64, or an empty string when the web view yields none. A region that has loaded nothing restores a base64 `interactionState` and then loads the current entry of that history; it refuses a region that has already loaded a document (`the document region has already loaded a document`), a value that is not base64 (`the interactionState is not base64`) and a value from which the web view restores no history entry (`the web view refused the interactionState`).
- The host sends `document-state {surface, document, state}` only to the owning surface. `state` is `{url, title, loading, progress, canGoBack, canGoForward, error, scroll: {x, y}, history: {entries, index}, link, navigations}`; `navigations` is the number of navigations that the document has started, counted once when each starts, so the progress of a navigation does not change it; `link` is the address of the link under the pointer in the document, or an empty string, reported from a script in the region's separate content world on `mouseover` and `mouseout`; `error` is the last load failure or null, `scroll` is the document scroll position in CSS pixels, and `history` is the session history of the region: `entries` lists `{url, title}` from the oldest entry to the newest and `index` is the position of the current entry, or `entries` is empty and `index` is -1 before the first load. The history comes from the web view's back-forward list, so it has the entries the list keeps. The element and request streams are not part of `document-state`; they are defined in [document streams](#document-streams).
- The host closes a surface's regions when the surface is removed and when the surface page begins to show a new document, before that document can attach again. The new document attaches its regions itself.
- While a dialog is open, the host blurs regions with the same radius as the surface document blur.
- Regions participate in native input like surfaces: pointer input reaches the region under the point without activating the application, and page focus changes do not move the application's keyboard focus. `host.window` lists regions as `documents`, each with the WebContent process of its web view (`process`, 0 before that process starts), with `focused` set only when the document WebView or one of its descendants is the window's native first responder, and `host.hit` reports `{kind: "document", surface, document}` ([exposure](exposure.md)).
- The presentation wait excludes regions. Their content renders independently.

### Document streams

The element and request data of a document region are streams. A stream is collected only while a page subscribes to it, so a region without a subscriber posts no element or request data. A stream message reaches only the surface that made the subscription.

- `subscribe {document, stream}` opens a subscription and replies with a `handle`, where `stream` is `elements` or `requests`. `unsubscribe {document, handle}` ends it. A call that names an unknown document or handle, or a document that the calling surface does not own, is refused with an explicit error.
- The document handle of plugin-api has `subscribe(stream, listener)`, which returns a handle whose `close()` ends the subscription. The listener receives the messages of its subscription in order.
- The host counts the subscriptions of each region and stream. The first subscription starts the collection of the stream and the last removal stops it. The host removes a subscription when the surface page that made it loads a new document, when that page's web content process terminates (`webViewWebContentProcessDidTerminate:`), or when the region or the window of the subscription closes. The removal of the last `requests` subscription of a region releases the request log of the region.
- A status of a plugin that exposes a stream subscribes in the subscribe function of the status and ends the subscription in its stop function ([exposure](exposure.md)). A read of such a status without a watch subscribes, waits for the first message, ends the subscription, and fails with an explicit error when no message arrives within 10 seconds.
- `elements` is a snapshot stream. The document script marks the element tree changed when the document finishes parsing and when the tree or an `id` or `class` attribute changes; it does not walk the tree at each change. When the tree is marked changed or a subscription starts, and no snapshot is unacknowledged, native collects a snapshot from the document and sends it to the host as snapshot `seq` N. Native sends no further snapshot until the host acknowledges N with `stream.ack {document, stream, seq}`, which the host sends to native after it has delivered the snapshot to every subscription of the stream. The host holds the one snapshot of each region and stream that it is delivering. A subscription keeps only the latest snapshot it received. A subscription that starts while a snapshot is unacknowledged receives the next snapshot, which native sends after the acknowledgement. A change during an unacknowledged snapshot produces one further snapshot after the acknowledgement, so the walk runs once per acknowledged snapshot and not once per change.
- A snapshot is `{seq, nodes, total, truncated}`. `nodes` lists at most 500 elements of the main-frame document in document order, each `{depth, tag, id, class}` with the lowercase tag name and the `id` and `class` attribute values or empty strings. `total` is the number of elements of the main-frame document, and `truncated` is true when `total` is larger than 500. The walk covers only the element tree of the main-frame document; shadow roots and frames are outside it. `seq` increases with each snapshot of a region and stream and keeps increasing across navigations.
- `requests` is an entry stream. The document script observes resource entries with `buffered: true` and posts each batch of new entries, never the whole list again. Each entry is `{url, type, start, duration}`, the navigation first and then each resource in the order it was recorded, where `type` is `navigation` or the resource's initiator type (`img`, `script`, `link`, `fetch`, `xmlhttprequest`, `css`, `other`, ...) and `start` and `duration` are milliseconds from the navigation start. The Performance API does not record request methods, headers, bodies, or response status, requests of subframes, or requests that the page makes before the host's script runs and that the resource timing buffer dropped, so the stream has none of these. The script never clears the resource timing buffer, which the scripts of the page own. An observer receives every entry whether that buffer is full or not, so a full buffer drops no entry of the stream.
- The region keeps a log of at most 200 entries. A new subscription receives the log in its first `entries` message and then the new entries. Each `entries` message carries `dropped`, the number of entries that the log dropped since the last `reset`.
- A new document of a region sends `reset` to every subscription of both streams. The reset drops an unacknowledged snapshot and clears the request log. `seq` keeps increasing, so an acknowledgement of a snapshot sent before the reset releases nothing and is not an error. Native refuses an acknowledgement of a `seq` that it has not sent with an explicit error that names the document, the stream, and the `seq`. After `reset`, each stream sends the data of the new document as it is collected.
- The host sends `document-stream {surface, document, stream, handle, message}` only to the surface that made the subscription. `message` is `{type: "snapshot", seq, nodes, total, truncated}`, `{type: "entries", entries, dropped}`, or `{type: "reset"}`. The `elements` stream sends `snapshot` and `reset` messages, and the `requests` stream sends `entries` and `reset` messages.
- A host that does not acknowledge a snapshot keeps the next one pending. A subscription ends with its page, its web content process, or its region, and ending it releases the pending snapshot.
- The document script runs in the host's own content world and posts through a script message handler of that world. Page scripts run in another world and cannot post to that handler, so a page cannot write stream data; a page changes what the streams report only by changing its own document.

## Image regions

Images are created by sidecars and supplied to the core through a region. The core receives only an opaque token and pixel size; it knows neither the image buffer nor the supplier's identity beyond the token.

- **Image supply and size validation**: The manifest assigns a supplier sidecar. The host computes the raster revision and exact dimensions from the applied native frame and sends them to the supplier. A frame must match its attachment generation, raster revision, monotonic sequence, actual token dimensions, expected dimensions, and window scale. A mismatch is rejected and never replaces the previous valid snapshot.
- **Device pixel reporting**: The region reports its size in device pixels, not CSS pixels.
- **Input handling**: Pointer events pass through to the surface document below, and the document decides the pointer cursor; the region registers no cursor rectangles or cursor tracking areas. Keyboard input, input composition, and accessibility belong to the region. The native region is an `NSView` input client with a dedicated marked-text buffer, not a text document containing terminal history. It paints no text, marked-text decoration, selection, insertion point, focus ring, or automatic editing indicator; the supplied sidecar image is the only visible region content. The region publishes one `{type: "input", actions, preedit, errors}` event per outer input scope. The consumer applies that transaction's ordered actions and final preedit/focus state before presenting the transaction. This does not make later asynchronous PTY output part of the same presentation; output received in a later event may produce a later frame. Keys go to the page, command-key sequences go to the application menu, focus changes on host request, and `host.window` reports the current position. Pointer presses pass through to the page; AppKit responder handoff during press setup does not change region focus. A press inside another image region transfers focus directly between regions.
- **Input callback state**: Each `native.input.callback` record includes `before` and `after` state objects. Their `active` and `keyWindow` members are JSON booleans sampled from `NSApp.isActive` and the owning window's `isKeyWindow` at the time each state is captured. A marked-text replacement outside the current marked buffer is rejected before mutation, records an input error, and latches later callbacks in the same input scope; the last valid preedit is retained and no invalid action is published.
- **Final preedit snapshot**: The input client owns the UTF-16 pending-text buffer and selection edited by AppKit replacement ranges. The buffer contains only the current pending composition and never stores committed terminal history. `markedRange` and `selectedRange` are relative to this buffer. A valid partial replacement mutates the range with Foundation and preserves pending text on both sides. The region API provides no terminal text context; native never reuses the accessibility snapshot as input text or exposes PTY history as editable context.
- **Insert action**: `insertText` applies a valid explicit replacement to the pending buffer and publishes the fully resolved buffer once as one ordered committed insert action. With `replacementRange == NSNotFound`, it commits the supplied text as the replacement for the current marked composition; an ordinary `NSTextView` reference produces the same result for direct `setMarkedText("abc", selectedRange: {1,1})` followed by `insertText("x", replacementRange: NSNotFound)`. `setMarkedText` applies a valid replacement, preserves pending text on both sides, and publishes the resulting buffer as preedit. `unmarkText` and explicit commit boundaries (command, focus loss, input-source change, and close) commit the current pending text once and clear the buffer. If a preceding `insertText` cleared the buffer, a later `unmarkText` adds no action. An empty `setMarkedText` callback cancels by clearing without commit. Range metadata records input provenance; the PTY consumer does not apply a replacement a second time. Closing a region commits pending text before detaching its responder, asks its input context to discard marked state, clears the diagnostic context override, and releases the view only after detachment.
- **Input transaction**: Each outermost native input scope publishes at most one `{type: "input", actions, preedit, errors}` event when it contains an action, a changed final preedit, or a callback error. `actions` contains committed `insert` actions and `key`, `command` or `focus` actions in their exact callback order; an insert action carries `text`, `replacementRange` and `attributed`, without an intermediate preedit. `preedit` is the required final strict snapshot of only AppKit's actual marked range, including an explicit empty snapshot when marking clears. Intermediate composition reports are replaced by that snapshot. `errors` contains callback failures in occurrence order, each `{reason}`; a failure is not an action. The input client validates callback ranges against its owned marked buffer before mutation and reports invalid ranges as callback errors that latch the scope. A physical `keyDown:` scope includes its synchronous AppKit text-input callbacks under one correlation identifier. A standalone text-input callback outside a key scope forms its own transaction. A key scope with no action, changed preedit or error publishes no event. The first callback failure latches the scope: later text-input callbacks in that scope do not mutate the input document or add actions and are recorded as rejected with the failure reason and before/after state. The transaction keeps valid actions and the last valid preedit from before that failure; a new outer scope clears the latch. Consumers validate the complete transaction before effects, then submit the ordered byte-producing actions as one batch and apply the final preedit/focus state after the write result, before rendering; they do not publish an intermediate frame for each action. A valid transaction that contains a callback error still submits its preceding valid actions and applies the final last-valid preedit before surfacing the error. A malformed transaction is rejected before any write or state effect. If a batch write returns an error, the consumer reports the submitted batch and that byte progress is unknown; it does not claim rollback or retry. This boundary does not wait for PTY echo or use a timer or local echo.
- **Implementation references**: These public macOS clients illustrate different callback batching choices, not additional requirements for this contract. [Ghostty](https://github.com/ghostty-org/ghostty/blob/fa141a726203224c12b831e0513530fa2406ef26/macos/Sources/Ghostty/Surface%20View/SurfaceView_AppKit.swift#L991-L1044) accumulates insert text during `keyDown:` and synchronizes preedit after key interpretation; [WezTerm](https://github.com/wez/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/window/src/os/macos/window.rs#L1873-L2009) keeps a separate IME buffer and dispatches inserted text; [kitty](https://github.com/kovidgoyal/kitty/blob/81535d9b338e60c481dbdd5a4da286685f694b5d/glfw/cocoa_window.m#L1207-L1255) brackets text callbacks and updates preedit around its key event. These callback boundaries do not establish that PTY output arriving asynchronously later is presented in the same frame.
- **Input trace sequence**: Diagnostic native-input and terminal-input entries retain their zero-based input-entry `sequence`, with each terminal request following its native report. This trace contains input receipts only; it does not retain screen-frame history. For frame-state evidence, a capture consumer reads the existing host performance-trace `host.trace.sidecar.receive` screen body and the accepted plugin DEBUG `plugin.terminal.frame` record from one sealed log range. It joins by surface, session, segment, message sequence and the marker native `frame` tuple. Message sequence alone is not a native-frame identity. Identical receive bodies and accepted markers may repeat without equal multiplicities; conflicting full states are rejected. Unmatched bodies and markers remain diagnostics; records outside the retained-source set do not invalidate the proof, but every retained source frame needs its own exact complete join. A `null` marker is a valid no-raster observation and does not prove a source frame. The consumer checks the body and marker frame tuples for equality. The host record’s whole body is subject to the host event-field bound; a truncated or missing required body, missing accepted record for a retained frame, conflicting join, or relevant reported log loss makes that frame unavailable as proof. For this trace, host `call`/`frame` DEBUG gates and page `frame` DEBUG gates are relevant losses; unrelated page `call` gates and sidecar, SOK or native self-gates are not losses of the selected host body or accepted marker. Malformed loss metadata is rejected. A detached screen read or neighboring status cannot fill it. The check keeps its source-frame identity and visual cadence criteria unchanged.
- **Input behavior acceptance**: Compare every acknowledged key with the same-window AppKit reference document, focus and valid composition ranges, and verify committed terminal cells plus the current marked buffer. Exact-source glyph and preedit measurements establish the corresponding visible states. Recording completeness and cadence are separate quality results: the complete-recording 33 ms maximum gap remains required for IME visual recording acceptance. A quality failure does not establish incorrect input when the behavior measurements match, and matching behavior does not make a failed combined recording pass.
- A click-through press inside a focused image region is not a focus loss, including a diagnostic `input.pointer` press delivered directly to the hit view without activating the application. The region keeps its focus through the press and its paired release, for physical AppKit input and diagnostic pointer input. A press outside it or inside a different image region changes focus.
- **Accessibility**: The region is an accessibility element. Its value is the screen text provided by the owner through `setAccessibleText`.
- **Image consumption**: The host copies an accepted transfer image into host-owned immutable presentation storage before replying `consumed`. The supplier must not modify or reuse the transfer image before that reply. The native layer never points at supplier-mutable storage. A transfer image of a surface that no window owns is answered `{image:{error:"closed",name,generation,raster,sequence}}`, so the supplier releases it and does not match a later answer of a surface of the same id to it.
- **Image color space**: On macOS, an IOSurface may declare `kIOSurfaceColorSpace` as the serialized property list of a Core Graphics color space. The host uses that declared color space when it creates the immutable image snapshot; it does not relabel tagged pixels as DeviceRGB. An absent tag keeps the existing DeviceRGB interpretation. A present property list that Core Graphics cannot decode rejects presentation as `presentFailed`. Image-capture diagnostics treat an absent or undecodable color-space declaration as unknown and do not accept it as a color match.
- **Image frame identity**: The native image region retains the accepted frame's `{generation,raster,sequence}` identity with its immutable snapshot. This identifies the source transfer retained by the layer; it does not claim that Core Animation or the display physically presented that frame. While image-capture diagnostics request matching, the host retains a bounded history of the exact source raster bytes, identity, scale, color representation, and native screen bounds (64 MiB and 512 snapshots). Each complete ScreenCaptureKit sample is compared with the geometrically corresponding crop of that history using exact pixel equality. The crop mapping requires compatible capture content geometry and scale; the source and captured pixel formats and color representations must be known and compatible. Missing or incompatible geometry, scale, or color metadata is reported as unknown with its reason, and unequal pixels are reported as unmatched. Repeated identical pixels retain all matching identities as ambiguous; they are never assigned to one identity by recency. The report records the sample's `displayTime` as an observed capture correlation; it does not claim Core Animation or the display physically presented that source transfer at that timestamp. A source history capacity eviction is observable and makes an otherwise absent match unknown when the candidate may have been evicted. Additional source snapshots are retained only while matching diagnostics are active; the current snapshot required to display the image remains retained normally. The diagnostic copies and pixel comparisons add memory and callback processing cost, so measured callback timing includes this instrumentation and cannot establish its uninstrumented cost.
- **Diagnostic frame identity cleanup**: Opt-in capture may place an identity code in the image layer while retaining the immutable untagged source snapshot separately. When identity capture stops or fails, the host restores every live image-region layer from its latest raw snapshot immediately, without waiting for a producer frame. Cleanup is idempotent and does not change region geometry, visibility, focus, or input state.
- **Image capture raster evidence**: Exact pixel equality is affirmative match evidence. Unequal bytes are reported as unmatched and do not establish that the source image was absent; the image rendering or capture pipeline may transform pixel values even when pixel format and color-space metadata agree. While capture matching is active, the host writes one artifact for each unique source identity to the capture's `sources` folder as soon as it accepts the snapshot. Repeating an identity is idempotent only when metadata and bytes match; conflicting reuse is rejected as a drop. The `.bgra` file contains the original accepted snapshot bytes without conversion. Its format-2 `manifest.json` entry records identity, byte file name, width, height, stride, alpha and color representation, screen bounds, scale, byte count and SHA-256. Artifacts are limited to 512 identities, and each source raster must fit the 64 MiB in-memory matching history. Queued and active source raster bytes on the serial capture writer are bounded to 64 MiB independently of the total artifact bytes. A source that exceeds this pending-byte budget is explicitly rejected and recorded; enqueueing does not wait while holding the history lock. The matching history remains bounded to 64 MiB and 512 snapshots, and its eviction remains observable as `unknown-retention`. A source that exceeds the per-raster or identity bound, conflicts with an existing identity, or cannot be written is reported as dropped; a partial file is removed. The manifest reports write failures, partial-file cleanup failures, and up to 32 cleanup error details with a count of omitted details; any artifact write failure fails capture finalization. Artifact writes use the existing capture writer queue and do not run on the image presentation thread. Artifacts exist only in diagnostic captures and add disk I/O while capture runs.
- **History-evicted tag provenance**: Raw image matching remains bounded to its exact pixel history; eviction continues to produce the same `unknown-retention` result and does not add candidates or approximate a match. Opt-in tag decoding may use the existing bounded source-artifact metadata and tagged-artifact metadata after the corresponding raw raster leaves pixel history. Join by exact source tuple and region token, nonce, issued payload, ROI and source geometry; do not add a third provenance cache. Artifact metadata proves a pair was recorded, not that its tag remains eligible. A per-pair disposition distinguishes raw-history eviction, which preserves artifact-backed tag eligibility, from explicit identity eviction, which remains ineligible. Keep that disposition within the existing 512-pair bound; do not forget an explicit-eviction tombstone while its artifact pair remains retained, and fail closed if the disposition cannot be retained. Failed presentation or missing/conflicting provenance cannot establish a candidate. Immutable pending artifact metadata may be used during decode, but evidence becomes valid only after stop drains the writer, finalized manifests and committed files validate the pair, and no source, tag or decoded-record write failure occurred. Preserve the raw matcher result and its retention/drop facts. Omit the duplicate unlocated tag-decoder unknown row for raw history retention only when the bounded pair ledger completely accounts for every tag pair, including region-local unknowns, and all raw-history loss is attributable to pixel-history eviction. Missing or conflicting pairs, non-eviction drops, explicit retirement and overlapping tag ROIs remain explicit unknown results. A pair whose ROI cannot be mapped remains a region-local `unknown-geometry` result; mapping failure does not add a second unlocated result. Any emitted unknown result without an ROI remains fail-closed at the consumer. This provenance identifies accepted source transfers and does not prove physical scanout.
- The raw native color-space name is preserved in capture metadata. The IME visual consumer maps the CoreGraphics name `kCGColorSpaceSRGB` to its semantic `sRGB` label without changing raster bytes. Other names are not aliases and remain unsupported by the strict sRGB crop model.
- **Tag-scoped IME raster evidence**: Opt-in decoded identity may disambiguate a target source tuple in a captured sample, but does not replace the raw `imageMatch` result or its complete crop-candidate and ambiguity record. The consumer records tag-scoped evidence separately and preserves the complete crop evaluation: exact byte matches remain ambiguous, while sources without exact grid or status/render metadata remain unclassified. For each capture frame and expected region, require exactly one issued artifact and one decoded row with the exact tuple, region token, payload, nonce and projected ROI. Multiple distinct captured frames may independently decode the same source tuple. Duplicate rows, duplicate or overlapping target ROIs, or conflicting payloads for one sample and region reject that sample. An unknown ROI overlapping the target tag ROI rejects that sample. An emitted unknown result without an ROI cannot be shown disjoint and rejects that sample. When raw history loss is solely pixel-history eviction and complete bounded artifact provenance accounts for all tag ROIs that can overlap the sample, the native decoder does not emit a redundant null-region `unknown-retention` identity row; the raw matcher `imageMatch` retention and drop facts remain unchanged. Any other unlocated unknown or incomplete provenance rejects the sample. Unknown rows with a known, disjoint ROI remain recorded and do not veto the sample. The target artifact's ROI must be projected through the same capture mapping and remain disjoint from the glyph span and guard cells. The exact target source must have retained raster, semantic state and renderer metadata indexed by the same immutable tuple; repeated identical status events for that tuple may deduplicate, but conflicting row, semantic or render state fails closed. If the stage observation carries renderer metadata, the complete object must equal the indexed metadata; if it is null, only the exact tuple's indexed render may be used. The decoded tuple, stage tuple and raw-source artifact tuple must all match. The issued artifact's width, height, stride, pixel format, alpha mode and color representation must also match the retained raster for that tuple; the existing semantic adapter maps only the declared CoreGraphics sRGB name without changing bytes. The consumer still requires exact source/captured bytes for the full input span and guard cells, compatible crop geometry and color representation, matching semantic state and ranges, focused cursor state, and the existing glyph and underline measurements. A tag does not make a byte mismatch or incomplete target source state pass. A stage is measured only when at least one sample in its half-open input interval has a valid tag and crop proof; other samples and their unknown results remain recorded. Raw equal-crop candidates remain ambiguous in `imageMatch` and the crop evaluation; the separate tag-scoped result names the uniquely decoded tuple without rewriting either record. Neither result proves physical scanout.
- **Decoded identity reason mapping**: The decoder reports a QR symbol detected partly outside its expected ROI as `code-outside-expected-roi`; the matcher records it as `cropped`. A valid decoded payload absent from the issued set remains `payload-unissued` at the helper boundary and `unissued` in the capture record. Use the canonical helper reason so all consumers classify the same condition consistently.
- Sample-local attribution preserves valid repeated observations: distinct callback frames can capture the same retained source, while an unknown result describes only its own frame and region. Therefore neither repeated target tuples nor disjoint unknown rows can invalidate another sample's independently validated tag and crop proof.
- **Authorization**: The region specifies which sidecar is authorized to supply images. The host rejects images from unregistered sidecars with an error.
- **Error reporting**: If the host cannot present an image, the region sends an error event: `{type: "error", reason}`. Reasons include `notFound` (IOSurface not found), `forbidden` (access denied), `size` (declared dimensions do not match the IOSurface's actual dimensions), `scale` (the image was drawn at a scale other than the window's), and `presentFailed` (platform presentation failed).
- **Ended sidecar**: A frame of a sidecar that no plugin declares, such as the frame in flight when a plugin is removed while its card is open, belongs to a process that ended with its buffers: the host answers it `stale` without presenting it, records it, sends no error event and starts no recovery, and an answer that cannot reach the ended sidecar is recorded as not sent.

`host.window.regions[].error` retains the last native presentation rejection until a valid frame is presented. A valid older snapshot does not make a later rejection disappear. Image pixels retain their size at the native backing scale; resizing a layer must not scale text to fill the new geometry.

Both hosts forward each native image event as `image-event {surface, name, event}` only to its owning surface webview. An empty callback, broadcast delivery, or substituting a direct sidecar command for keyboard delivery violates this contract. Invalid event JSON and delivery failures are reported, never replaced with a null event.

The terminal exposes its latest cell rows as `terminal.screen` and notifies subscribers on sidecar screen events. Input checks use native clicks and keys, wait for these notifications, and verify editing, command output, and isolation across at least three visible terminals. `terminal.input` checks only direct sidecar input, not native keyboard delivery.

An activation check of an input-method preedit compares the complete AppKit reference document with the terminal's committed screen cells and `terminal.compose`; it validates the marked and selected ranges separately in each owner because the AppKit reference and image region can retain different marked states for the same document. It also requires `terminal.cursor` to carry the exact `{generation,raster,sequence}` of the screen event that supplied its cursor and preedit. `terminal.screen.read.frame` identifies the base cell rows; the image region can present a later overlay frame without changing those rows. The region's presented identity is a same-generation, same-raster progress watermark and may have a sequence later than the cursor source. It does not replace the exact cursor source identity or prove that the marked glyph is visible.

The activation check sends one key to the same-window AppKit reference, reads and validates its document, then waits for `host.window.presented` before sending the next key. This event-driven checkpoint gives the application window a presentation update between reference inputs; it does not prove that the AppKit text view painted that key or that a particular frame reached physical scanout. It does not replace capture-frame cadence, identity, pixel, glyph, or underline requirements.

For each terminal key, a native or terminal input callback acknowledges that the key reached the input path; it does not establish that the terminal has finished applying the key. The activation check waits for a coherent status notification and reread whose complete committed-plus-preedit document equals the corresponding same-window AppKit reference document. A coherent intermediate document remains pending while later status notifications arrive. The existing 1500 ms per-key deadline remains in force; if the expected document does not arrive, the check fails and preserves every intermediate status and capture frame.

The activation observer reads the initial `terminal.compose` and `terminal.cursor` statuses concurrently, then reads `terminal.screen.read` after both settle. It reads the verification `terminal.compose`, `terminal.cursor`, and `host.window` statuses concurrently after the screen read settles. It retains both status pairs and compares the initial pair with the verification pair; a read failure is reported with every failure from its concurrent batch. This ordering keeps the screen sample between the two status snapshots without serializing independent host reads. It does not change input, state-wait, focus, semantic, visual, frame-identity, or cadence acceptance.

When an activation phase moves focus away from the terminal and later returns it, the observer takes a new accepted screen/cursor/compose baseline after the terminal is focused and its current screen frame is presented. It verifies changed screen rows against the matching `terminal.screen` notification and verifies the empty prompt on the current cursor row before updating the prompt anchor. It does not compare post-transition input against a pre-transition row or reuse a stale prompt location.

Visual stage planning treats `terminal.screen.read.frame` as the base-row identity and `terminal.cursor.frame`/`terminal.cursor.render.frame` as the overlay identity. The cursor and render identities must match exactly. The base screen must share their generation and raster and have a sequence no later than the cursor frame. Its rows must equal the rows in the exact accepted screen message. The observed presented watermark must share the cursor frame's generation and raster and have a sequence no earlier than the cursor frame. Host presentation state reports the latest frame applied to the image region; a later presentation can advance this watermark after the cursor source was sampled. Exact source identity remains the cursor/render frame and its same-message row state, while retained source candidates and capture pixels determine visual proof. Screen and cursor sequence equality is invalid because the overlay draw can advance while rows remain unchanged and the rows-only screen status suppresses that duplicate value. Status observers establish coherent live input state but are not the authority for source-frame rows. For every retained source raster, the consumer joins the exact host performance-trace screen body to the accepted plugin frame record by surface, session, segment, message sequence and native frame tuple. Repeated complete records for one message key do not erase the distinction between message and frame identity. The consumer verifies the exact frame tuple, dimensions, rows, cursor, preedit, renderer metadata, session and screen hash before associating that state with the raster. The host body is recorded before the page handles the message; the matching plugin frame record proves that the message key was accepted and hashed. A render-null record for the same native frame is unavailable proof until a complete record supplements it under the frame indexer's existing conflict and completion rules. Missing, ambiguous, conflicting, truncated or lossy records are unavailable proof; the consumer never substitutes a neighbor status, detached read or latest presented sequence. Input receipts are matched to the transaction key action: a Korean-source `k` receipt may be a non-whitespace insert or compose-only non-empty preedit, but a transaction carrying a Backspace command or whitespace insertion is not a `k` receipt. Backspace matches its key or `deleteBackward:` command, and Space matches its key or whitespace insertion. Focus, coherent state, and AppKit document comparisons run for each key, but visual planning and pixel evaluation wait until all ten keys, callbacks, and the complete recording have been preserved. This keeps an early visual mismatch from stopping collection of the rest of the approved gesture.

The terminal's `terminal.screen` status contains rows and suppresses a notification when its JSON value is unchanged. A screen event can therefore advance `terminal.cursor.frame` and its preedit/render metadata without producing a new `terminal.screen` notification when the rows are unchanged. Image generation or raster changes alone do not invalidate those rows because the status value is independent of image identity. A capture index uses the latest `terminal.screen` status event that precedes the cursor event, not only an adjacent event. It records that screen event's index and rows as the source of the cursor's base screen. It may reuse only an earlier event in the same observed stream; it never uses a later event or a detached screen read to fill a missing source. If no earlier screen status event exists, the frame has no row source and the measurement is no proof. The cursor frame and render frame must still match exactly, and compose/preedit must remain semantically equal.

For each capture sample, the check keeps the whole-raster `imageMatch` result unchanged and independently derives source candidates from the retained capture sources. It maps each source to the captured frame using the declared capture content rectangle, display bounds, scale and color representation. It compares the exact pixel bytes for the complete input span and guard cells, including committed text and preedit, between the source crop and capture crop. It keeps every source identity whose crop matches; `latestRetainedSource` alone is not a candidate. Each candidate must have a recorded cursor frame and status state with the expected complete document, compose/preedit text, owner-specific marked/selected ranges, focus and cell geometry. The target `terminal.cursor.frame` must occur in that set, and every candidate must support the same expected semantic state. Multiple matching identities remain explicitly ambiguous; the check never chooses one by recency or claims unique physical attribution.

In a diagnostic build started with an explicit `SOKSAK_VT_TRACE_DIR`, the terminal cursor status carries the `screen.render` object atomically with the matching `frame` and `preedit`; without that startup option, `render` is null and glyph-bound work is not performed. A non-null object repeats the exact frame identity and has `pixel` `{width,height,bytesPerRow,format:'bgra8',alpha:'premultiplied',colorSpace:'sRGB',origin:'top-left'}`, `grid` `{rows,cols,origin:{x,y},cellWidth,cellHeight}`, and `font` `{family,size,ascent,descent,leading,baselineFromCellTop}`. Its top-level `underline` carries `positionFromBaseline`, `positionCoordinate:'CoreText y-up'`, `thickness`, `minimumThickness`, and `colorSource:'glyph.foreground'`. `cursor` carries a nullable `rect`, shape, visibility, blink visibility, focus, blend (`normal` or `difference`), effective color (`null` or opaque sRGB `#rrggbb`) and border. Each `glyphs[]` entry carries row, column, cell width, positive `fontRuns`, grapheme, effective opaque sRGB `foreground` and `background`, nullable finite signed fractional `bounds` measured from the glyph's leading-cell origin, and `underline.rect` (nullable). These colors are draw-time values after overlay and inverse resolution; the unchanged PTY screen cells may describe text replaced by a preedit overlay. Glyph bounds are raw `CTFont`/`CTLine` ink bounds translated only by the leading-cell origin; underline rectangles use the same leading-cell coordinate origin. Both may overhang the cell span and retain their original values. A difference-blended block cursor reports `color:null` because it inverts destination pixels. The renderer reports measured draw inputs and geometry only, not test thresholds or coverage decisions. The default path does not compute glyph bounds or allocate per-cell render records. A frame and its render metadata are created by the same successful draw before image and screen messages are sent; a failed or deferred draw has no render metadata for its pending screen state.

Native capture source artifacts keep their own declared representation: `manifest.json` says `pixelFormat:'BGRA8'` and `alpha:'premultiplied-first'`, and `.bgra` contains those original bytes without conversion. These labels are not aliases for the producer's `bgra8`/`premultiplied`. Consumers validate each interface separately: the producer's `bgra8` bytes map to the artifact's declared BGRA byte order, and its premultiplied channels are decoded according to the artifact's alpha declaration. For a sample with alpha `a > 0`, convert each stored B, G and R byte `c` to opaque sRGB with `round(c * 255 / a)` before comparing to producer hex colors; alpha zero has no color. This conversion is for comparison only and never rewrites or relabels artifact bytes.

The check measures glyph ink and underline separately using those same-frame renderer values. The predicate uses the effective per-glyph `foreground` and `background` and each glyph's nullable `underline.rect`; it never infers geometry, thresholds or colors from the capture being judged. A glyph's bounds are raw `CTFont`/`CTLine` ink bounds translated only by the leading-cell origin. Their finite fractional coordinates may be negative or extend beyond the glyph's leading-cell span; validation preserves those values and does not clamp ink to a cell. For each floating glyph or underline rectangle, the consumer translates it to frame coordinates, uses `floor` for the left/top edges and `ceil` for the right/bottom edges, then clips the pixel rectangle to the available raster. The consumer maps a capture raster's pixel origin from the source `screenBounds`, capture `screenRect` and `contentRect`, and their equal declared scale: `frameOrigin = (screenRect.origin - contentRect.origin - source.screenBounds.origin) * scale`. The source raster frame identity must equal both `terminal.cursor.frame` and `render.frame`; geometry from another frame is not evidence for this sample. It accounts for row stride while mapping and rejects fractional origins or unequal scales. An empty raster intersection is no proof. A block cursor's `difference` blend is evaluated against those effective glyph colors; a cursor with `normal` blend reports its effective color, and glyph overlap with a drawn non-difference cursor is no proof. The cursor draw condition is `visible && blinkVisible && shape != 'hidden'`: when true, `rect` must be non-null; when false, both `rect` and `color` must be null. A drawn `normal` cursor must report its effective color, while a `difference` cursor must report `color:null` because it inverts destination pixels. These values come from `screen.render`, not from PTY screen cells. Its fixed U+314F (`ㅏ`) fixtures include glyph-only lower strokes, underline in the wrong range, and a blank block-cursor cell as negative controls. The predicate names its color-distance threshold and required coverage. If same-frame public status and source metadata lack renderer metrics, the visual result is no proof and remains incomplete. Every expected grapheme must have glyph ink, underline must cover exactly the terminal's marked cells, committed cells must not be underlined, and guard cells must not contain an extra glyph. Cell boundaries come from same-frame screen rows, cursor and grid dimensions; source width/columns and source height/rows must produce integer cell edges. Fractional grid cells, split glyphs, offscreen cell mappings or multiple candidate boundaries are rejected as no proof. Whole-raster image matching remains affirmative only for exact pixel equality; an unmatched whole raster does not establish that a marked glyph is absent when its measured cell crop matches exactly.

The review rejected fixed cell-percentage bands because glyph strokes can extend into the lower cell and cursor colors vary with the appearance. It also rejected producer-supplied pass thresholds because the renderer cannot validate its own output. The renderer therefore publishes measured draw geometry and resolved style values, while the consumer owns pixel thresholds and coverage tests. A separate review objected that CoreText rectangles can have fractional edges; the check preserves those values and applies the declared floor/ceil/clipping rule instead of rejecting normal fractional font metrics. The fixtures exercise a lower glyph stroke, wrong-range underline, blank inverse cursor and asymmetric fractional bounds.

## Acceptance criteria

- Recorded native content stays within its card on every measurable frame. Native content, card chrome, the card sidebar, and its outer rail must preserve their relative geometry in the same frame; temporary inset growth does not satisfy this requirement.
- Page drawing that follows the cards, such as the card sidebar outline, uses the rectangles that the last draw wrote to the card elements and the plane's CSS pixels. While a preparation is pending, the grid already holds the next layout, so drawing from the grid moves the drawing before the cards.
- During a divider drag, a recorded frame shows the layout of a step at most four display frames after the grid left that layout, and over the drag the median delay is at most 2.5 frames and the 90th percentile at most 3 frames (at 60Hz: 66.7ms, 41.7ms and 50ms). A layout reaches the screen across four frame boundaries: the input's arrival, the frame of the layout before it, WebKit's rendering update and the display refresh. A placement waits for the next presentation of the app DOM webview, so that webview renders at the display rate instead of WebKit's default rendering near 60fps. For the same reason the app DOM webview keeps its document visible and keeps running animation frames while its window is occluded; otherwise a placement and every command that waits for it would not complete until the window is uncovered. Attached surface webviews do the same, so their non-activating captures and paint acknowledgements also complete while the window is covered.
- Such drawing does not use a coordinate system that scales with its element. That coordinate system fits the previous drawing to the new box, which moves it before the cards move.
- A layout that is replaced before it is presented does not reach the screen, so a position that the pointer holds for less than one presentation, such as the start position between two fast round trips, may be absent from a recording. A drag recording starts and ends at the start position and reaches the far end in every round trip.
- Drag input completes at the requested rate and recording includes the complete drag. Recording starts before input. A controlled test stops recording only after the capture contains the final geometry; a presentation callback or frame timestamp alone is insufficient.
- A view drag recording checks every decoded frame timestamp, including frames whose geometry cannot be measured. Timestamps are finite and strictly increasing, and consecutive frames are at most 33 ms apart.
- A run must fail if it records too few frames or cannot identify the surface and card in most frames. Drag latency requires finite capture times and positions and at least one measured frame at or after the first input; absent measurements are an error, not zero latency.
- Continuous input must continue to update the displayed layout; postponing all rendering until release does not satisfy this specification.
- Surface creation, replacement, hiding, window resizing, and document reload must preserve these requirements.
- A document region stays on its element when its surface moves or resizes, receives native scroll input without application activation, and closes with its surface.
- Fractional-size checks measure actual CSS rectangles and recorded pixels. Integer-valued viewport queries alone do not establish the rendered document extent.
- The final device pixel inside a native surface must participate in document hit testing.
- Native pointer coordinates must match document coordinates after window resizing and changes between display scales.
- Settings and menu webviews remain above surfaces. Their behavior is specified in [data-native-modal](native-modals.md).

## Platform scope

Surface placement, visibility, stacking, and input follow the same contract in every host and operating system. Native implementations use the APIs and coordinate systems of their target platform.

Platform and framework defects are corrected in the host's native core within this repository when necessary. Private APIs are permitted when the required behavior cannot be obtained correctly through public APIs. Each correction must identify the cause, justify the API's role using its actual behavior, use the smallest sufficient implementation, and verify geometry, rendering, input, and lifecycle on the affected platform. Remove harmful or unnecessary changes. Passing tests is evidence of tested behavior; implementation review must also establish necessity and correct API use. API availability and maintenance risks are documented separately from the technical validity of the correction. Differences between hosts require diagnosis of the framework integration and native behavior; they do not establish the cause by themselves.

Native presentation validation currently targets macOS. Windows and Linux behavior is unverified. No framework fork is part of this implementation.

### darwin

Image region tokens on macOS consist of a global IOSurface identifier and a 16-byte nonce attached to that surface. When the host receives an image, it looks up the surface by identifier and rejects the image if the nonce does not match. This guards against reuse of recycled 32-bit identifiers.

IOSurface identifiers are in the global namespace of the user who owns the process. Different processes of the same user can look up and open the surface; this trust boundary is the same as the endpoint socket used for sidecar communication.
