# Exposure: status, command, element

[한국어](exposure.ko.md)

Core, the plugin API, the shell and browser plugins, and the macOS hosts implement this specification; [feature status](../features.md) records its validation.

Core (the workbench and the native host) publishes declared status values, commands, and elements to external clients through the [local endpoint](endpoint.md). No method executes arbitrary code.

## Declarations

A plugin declares its entries in `plugin.json` under `exposes` ([plugins](plugins.md)). Core declares its entries in `packages/workbench/exposure.json` with the same format.

```json
{
  "exposes": {
    "status": [],
    "commands": [],
    "element": []
  }
}
```

Registration of an undeclared name fails. A request for a declared name that has no registration returns an error.

Status observations also carry ownership of artifacts created by their public operations. Opening the debug view exposes the exact host-created still PNG paths in `core.debug.captures`; the page and native workbench follow the same record/reset contract ([debug](debug.md)). Automation registers those declared capture directories with its recording lifecycle rather than inferring them from private files or disabling failure-evidence auditing.

### Names

A name has the form `<owner>.<name>`. `owner` is `core`, `host`, or a plugin id. Names use lowercase letters, digits, dots, and hyphens.

### Entry fields

| Kind | Field | Meaning |
| --- | --- | --- |
| status | `name` | Entry name |
| status | `description` | One-sentence description |
| status | `schema` | Value schema |
| command | `name` | Entry name |
| command | `description` | One-sentence description |
| command | `params` | Parameter schema |
| command | `result` | Result schema |
| command | `timeout` | Optional. How long a command may take to reply, in milliseconds from 1 to 600000; the default is 10 seconds. The host applies it to a command forwarded to a surface page, and the main page applies it to the handler of a command it runs itself, which then fails with -32000 and `command <name> did not reply within <ms>ms`. A handler that throws, synchronously or asynchronously, fails the command with its own error, and the timeout ends with it. A core command then waits for its layout to present; that wait is not part of the timeout, because each step of the presentation path fails with its own error within its own limit ([native host](native-host.md)) |
| element | `name` | Entry name |
| element | `description` | One-sentence description |
| element | `many` | Optional. `true` when several elements share the name; requests address one element with `index` |

A schema is a JSON Schema subset with the keywords `type`, `properties`, `items`, and `enum`. `type` is one of the names `string`, `number`, `integer`, `boolean`, `object`, `array`, and `null`, or a non-empty list of those names; any other value is refused, including `null` and a list inside a list. `enum` is a non-empty list, and a value matches an entry when both are the same JSON value, with the members of objects compared without regard to their order.

The element for an element entry carries the attribute `data-expose="<name>"`; its name is an element name. Without `many`, exactly one element has the name. A plugin manifest that declares `exposes.dom` is refused with `plugin <id>: exposes.dom is removed; an exposed element is declared in exposes.element`.

## User interface

People and external clients operate a document through the same entries.

- Every user operation of a document runs a declared command. A control points to its command with `data-command="<name>"` and, for fixed parameters, `data-params` with a JSON object. A control that enters a value adds it as the parameter named by `data-value` (`value` by default). Commands are declared first (`exposure.json`, `plugin.json`); a document connects elements only to declared commands with `createBinder(run)` of `@soksak/plugin-api`: `bind(element, name, params, {event, when, stop, failed})` runs the command on an event, `mark(element, name, params, valueName)` sets the attributes, and `delegate(root)` runs clicks and value changes of marked descendants that `bind` has not connected; an element connected with `bind` runs its command only on its own event, so a text field bound to Enter does not run its command again on the `change` that the same Enter fires. Binding or marking an undeclared name throws. The workbench uses `packages/workbench/commands.js` (a binder over the registry), and a plugin page uses `expose.bind`, `expose.mark`, and `expose.delegate`, which run the commands the page registered. Handlers do not call module functions themselves. A continuous gesture, such as a tab drag, has a command that produces its result (`core.tab.move`), and keyboard shortcuts run commands. When `params` of `bind` is a function, it receives the event at each run and its result is the parameters of that run; such an element gets no `data-params`, so `mark` writes none.
- Every visible state of a document can be read through a status.
- Every interactive element (`button`, `input`, `select`, `textarea`, `role="button"`, and `contenteditable`) is connected to a command, either bound or carrying `data-command` under a delegated root, and has an element name.
- A redraw keeps every control that stays in the document in its place and moves a control only when its order is wrong. WebKit sends no `click` for a press whose element left the document between the press and the release, and moving an element with `insertBefore` takes it out of the document first, so a redraw that moved a control lost a click pressed during it. A plugin page draws a list of controls with `drawList` of `@soksak/plugin-api`, which keeps the element of each key in place.
- A native modal renders a copy of its element and answers with the control's key; the workbench runs the command of the matching control in its own element.

Coverage is judged in the running document. The binder's `audit(root)` lists interactive elements that are not connected or have no element name as `{role, expose, command, text}`, where `role` is the ARIA role of the element: the first token of its `role` attribute, otherwise the implicit role of its tag and input type (`button`, `textbox`, `combobox`, `listbox`, `checkbox`, `radio`, `slider`, `spinbutton`, `searchbox`), `textbox` for a `contenteditable` element, and `null` for an input type that has no role; the workbench publishes it as `core.workbench.audit` and every view surface document as `unbound` in `core.surface.document`. A visible view surface whose page does not expose `core.surface.document` fails the audit, because a view is a separate document that the audit cannot judge otherwise. `e2e/audit.test.mjs` visits every screen, modal section, menu, editing state, and visible plugin surface of both applications and requires empty lists. `scripts/check-exposure.mjs` (`make check-exposure`) checks only what the workbench sources state through `exposure-check.js` of `@soksak/plugin-api`: every name written in a source is declared, every declared status and command is registered, and every declared element name is written as an exposed value. A view may name core statuses and the ids of the sections of its plugin ([sections](plugins.md#sections)), registers a command of its plugin through `commands.register` of the view bridge, and runs through `runtime.command` a command of core or a declared command of its plugin ([view surfaces](native-surfaces.md#view-surfaces)); the core names must be declared by core; the listed core check of the registry ([registry](registry.md)) runs the same module on each plugin release, and it reads the core names from `core-exposure.json` of the package. `make check-exposure` fails when that file differs from the workbench declaration, and `node scripts/check-exposure.mjs --write` writes it.

## Keyboard shortcuts

Every keyboard shortcut of the workbench has one owner and one command. The machine-readable table is [shortcuts.json](../../packages/workbench/shortcuts.json) (`packages/workbench/shortcuts.json`); the table below is its copy. `scripts/test/shortcut-table.test.mjs` requires that both match, that every key equivalent of the [application menu](host-contract.md#application-menu) is a `native menu` row, and that every key comparison of the workbench key handlers has a `workbench` or `view` row. The owners follow [plugin processes](plugin-processes.md) rule 7:

- `native menu`: a key equivalent of an application menu item. The menu receives the key before the view, so the view's default action is not prevented. A row with a core command reaches it through the menu; a row with `framework role` runs the role of the item.
- `workbench`: a key that the workbench page or its native modals handle and prevent by default. The row names the command that the key runs.
- `view`: a key that the view handles itself, or a workbench command that the view runs with `runtime.command` for a key that it forwards under [plugin processes](plugin-processes.md) rule 7. A view row names no command, because the view decides synchronously; it is a rule, not a binding.

In a key, `cmd` is the Command key on macOS and the Control key on the other hosts (`CmdOrCtrl`). `Enter` and `Escape` are key names.

The view reads the rows that it may forward with the view call `runtime.shortcuts.read`: the rows whose owner is `workbench` or `view` ([native surfaces](native-surfaces.md#view-surfaces), Input). A view registers no table.

## Keyboard focus

The status `core.focus` reports the exposed element that has keyboard focus in the document that holds the first responder of the window, as `{name, index, surface}` or `null`. The host observes the first responder of each window with key-value observing of `firstResponder` and sends the window event `window-responder {owner, surface, document}` to the workbench when the workbench reports ready and at each change after that; `owner`, `surface` and `document` have the values of `responder` in `host.window`. A workbench that has not reported ready receives no event, because its ready sends the current value. A view surface is a document of its own: its bridge reads its focused exposed element after each focus move of its document, and reports `{name, index}` or `null` with the view call `tab.focus` when the value changes; the workbench refuses another value with `view call tab.focus requires {name, index} or null, not <value>`, and forgets the value when the view document ends or the surface closes. The workbench combines the two:

| `owner` of the first responder | `core.focus` |
|---|---|
| `workbench` | the focused exposed element of the workbench, including surface modules in shadow roots; `surface` is the surface of a shadow root or `null` |
| `surface` | the value that the view of `surface` last reported with `tab.focus`, with that `surface`; `null` when it reported none |
| `document`, `modal`, `webview`, `native` | `null`: a document region, a native modal, an unregistered web view and a native view report no exposed focus |

### The keyboard follows the focus ring

While the window is key and no modal is open, the active surface of the card with the focus ring holds the keyboard, and the two never disagree. Every path that moves the ring or changes the active surface of its card moves the keyboard: a new tab, a press on a tab, `core.tab.select`, `core.card.focus`, closing a tab or a card, opening a project and restoring a space. Each workbench moves the ring in one function and sends the one host call `surfaceFocus {surface}` ([keyboard of a surface](native-surfaces.md#keyboard-of-a-surface)). For a surface that an earlier placement gave the host, shown or hidden, the call goes out before the placement that shows it, so the host gives the keyboard at the release of the press that moved the ring and a key that follows the release reaches the surface. A surface that the host does not hold yet receives the call after the placement that shows it, and takes the keyboard when it stands. A command that moves the ring answers after the placement that shows the move and after the host answered the keyboard call that follows it, so a key that the caller sends after the answer reaches the surface. A first responder that reaches the workbench while the surface should hold the keyboard goes back to the surface. The host holds the input of the window from the release of each press on the workbench and from each call `keyboardHold {}` until a decided call, `surfaceFocus {surface, decided: true}` or `keyboardDecided {}` while a modal of the host keeps the keyboard ([keyboard of a surface](native-surfaces.md#keyboard-of-a-surface)). Each workbench answers each press on it and each `keyboardHold` with a decided call that follows what the press or the command changed, also when the target stays the same and when the workbench holds the keyboard; presses that one frame of the workbench answers share its one decided call; a press on an empty place, a scroll bar, a divider or any other element of the workbench counts as a press. A command that moves the ring sends `keyboardHold` before its answer and receives the answer of the host first, so the keys that follow the answer of the command wait for the decision.

- While a modal is open the keyboard stays in the modal, and the close of the modal returns it to the surface.
- A card without a surface, which is an empty card or the placeholder of a plugin that is not installed, and the library leave the keyboard with the workbench (`surface: null`).
- An editable element of the workbench, which is a library form field or a rename field, holds the keyboard while it has the focus, because the shortcuts of [keyboard shortcuts](#keyboard-shortcuts) that name those fields require it. The keyboard returns to the surface when the field loses the focus or closes.
- A pointer press on a tab leaves no element focus, and the `Tab` key still stops there and keeps that stop while the keyboard stays in the workbench.
- A section view of a sidebar that the user presses keeps the keyboard, because no ring is on it.

Before the first `window-responder` event, and in a runtime without a host, the workbench holds the focus. A `window-responder` event that is not `{owner, surface, document}` with string or `null` members is reported as `error: window responder: invalid window-responder event <value>`.

## Workbench statuses

Each status and command of the workbench declarations is defined over the workbench of the window, not over a page: a position that it gives is given in window points, and a position in plane coordinates stays in plane coordinates. On the Wails and Tauri hosts the main page draws the workbench; the mygo host draws it in native UI. The workbench order of a list is the order of its elements in the element tree of the workbench, which on the Wails and Tauri hosts is the document order of the main page.

| Status | Value |
| --- | --- |
| `core.window.workbench` | `{start, startedAt, readyState, visibility, scheme, background, scale, width, height}`. `start` identifies one start of the workbench and `startedAt` is its start time in milliseconds since the epoch: the page identity and the time origin of the main page on the Wails and Tauri hosts, and a new value each time the mygo host builds its workbench. `readyState` is `loading`, `interactive` or `complete`; the mygo host reports `loading` until the first presented frame of its workbench and `complete` after it. `visibility` is `hidden` while the window is minimized or not shown and `visible` otherwise. `scheme` is the color scheme of the workbench (`dark` or `light`). `background` tells whether the workbench is drawn with the background blur of an open modal. `scale` is the backing scale of the window. `width` and `height` are the content size of the window in points |
| `core.workbench.error` | The error text that the workbench shows, or `null`. The display records the source of the error: the first placement that succeeds withdraws the failure of the placement before it once every surface has presented, an error of another source stays, and the record of the error stays in the log |
| `core.workbench.audit` | `{unbound}`: the interactive elements of the workbench that the audit lists ([user interface](#user-interface)) |
| `core.pointer` | `{sequence, down, up, pressedConnected, click}`: the last pointer sequence that the workbench received. A press increments `sequence` and the other members start anew. `down`, `up` and `click` name the target: the nearest exposed element around it, and without one its tag. On the Wails and Tauri hosts the target is an element of the page and its tag is the tag name. The mygo host has no tags: the target is the innermost element of the element tree of the last frame at the pointer, its tag is its ARIA role, and a place that no element of the tree holds is `unknown` with `pressedConnected` `null`. Neither the document nor the workbench declares a name for an empty place: the space row beside its tabs, the margin of the plane and the foot of the library beside its controls are `unknown` here and a plain tag on the page, and the body of the library is the role `region` of its scroll area here and a plain tag on the page. A release clicks the nearest element around the press and the release, the primary button alone clicks, and a click is missing when the pressed element left the workbench before the release. A key or an action of assistive technology that presses a button records its `click` without a press. The sequence covers the workbench and the overlays that it draws; a native view and a native modal are documents of their own. The value identifies an observation and is not used for judgment |

On the mygo host a step of the workbench can run after its native window closed. A read of `core.verify` or `core.window.workbench` in such a step calls no native code and shows no workbench error. Any other failure of those reads is shown as `core.workbench.error`.

`host.window.reload` starts the workbench of the window again, and a window that receives `plugins-changed` or runs `core.plugins.apply` starts it again in the same way ([installation](installation.md#applying-a-change)). A window check or measurement target that waits for a new start of the workbench waits for a new `start` of `core.window.workbench`, not for a new page process.

## Registration

The workbench registers core entries in its registry. A plugin surface page registers its entries through `@soksak/plugin-api/page`. A core command answers after its handler has finished, including the asynchronous work that the handler starts, and after the plane has drawn the newest layout, so a caller that reads the layout after a command that changes it reads the drawn layout. The mygo host draws its workbench natively: a command whose run asked for a frame, a move of the focus ring included, answers after the placement of the next frame ran, the host answered the keyboard call that follows it and the watchers received the statuses of that frame, so a request after the answer finds the elements of that frame; a run that asked for no frame answers at once. The mygo workbench sends the statuses of a frame in the step after it, where the element tree of the frame can be read, so a status states what the frame showed, as a page reads its layout after it rendered. On a host with a main page the command then waits until the host answered every ordered call that the page sent, so a modal that the command opened holds the input of the window when the command answers ([native modals](native-modals.md#keyboard)). The wait waits for the newest layout and waits again when a newer layout was scheduled while it waited, because a layout that a newer layout replaces ends without a draw. It then reads the surface slots of that draw and waits for the declared composition of each surface they name. A mount request is observable to composition waits before it waits for a previous disposal of the same surface. A slot that names a surface whose replacement mount is pending waits for that mount; the wait reports the mount failure if it fails. A surface that this command or a later one removed therefore has no slot when the wait reads them; a slot that names a surface that is neither mounted nor being mounted after the newest draw is a defect, and the wait fails with `surface <id> is not mounted`. A dispose with no replacement does not leave a mounted or pending surface. A composition wait that starts while a surface entry is mounted follows that entry even while its mount registration is pending. If disposal begins before the entry declares its composition, the wait ends with `surface <id> was disposed before declaring composition`; a mount failure still returns its original failure. A wait for a replacement mount follows the replacement entry. When the newest layout fails, the layout queue shows that failure, and the wait ends without reading slots, because that layout was not presented. A failure of the wait itself is written as `exposure settled failed: <text>`. In both cases the command answers with its handler's result, and the failure has one line in the [application log](hosts.md#application-log).


Native listener registration does not delay a view mount or composition wait that would otherwise become ready. If a registration rejects before readiness, the mount and its composition wait reject with that error; the workbench releases every listener that registered successfully, closes the view-command layer, and removes the failed mounted entry. This failure observation does not depend on native-surface authorization. If registration rejects after readiness, the workbench reports the error through the surface status, releases the view and removes its mounted entry; an already resolved mount or composition wait keeps its result.

If disposal begins before a listener registration settles, disposal remains the result of the mount operation. The workbench immediately releases the listeners already registered, releases any listener that registers later, and reports a later registration or cleanup failure through the application error path.
The per-surface mount registration is reserved before it waits for disposal of the previous entry, so composition waits can follow the replacement. A reservation has no attempt number until `mountSurfaceNow` creates a new entry; reuse of a mounted entry or pending reservation does not allocate another attempt. Each new entry receives a page-local increasing attempt number, stored with its registration outcome while that entry remains in the desired plane. The registration stays pending until the entry is mounted or fails. If listener registration fails after composition readiness, the outcome changes to failure before the entry is released. A newly created entry that fails emits the error event `workbench.surface.mount.failed` with its plugin, surface, attempt, failure phase, and original reason. A composition wait that starts after release reports the retained attempt and reason instead of only `surface <id> is not mounted`; a wait already completed at composition readiness remains completed. The reservation for a retry supersedes an earlier failed outcome, and an older entry cannot overwrite the newer record when its delayed failure arrives. A successful retry therefore cannot inherit an earlier failure. Normal disposal clears the entry record, and leaving the desired plane clears any retained failure. Normal disposal is not a mount failure and emits no such event. The failure phase is `mount` when failure prevents composition readiness (including listener registration failure before readiness) and `listener-registration` when native listener registration fails after readiness. The same per-surface registration record serves pending waits and retained failure outcomes, avoiding a second failure map. The structured error event is diagnostic only; it does not invoke the error display. Existing surface status and settled-error reporting continue to show failures. The `surface.registration` trace describes exposure registration and has no mount attempt or failure outcome.

| Function | Registers |
| --- | --- |
| `expose.status(name, read, subscribe)` | `read()` returns the current value; `subscribe(fn)` calls `fn(value)` on each change |
| `expose.command(name, run)` | `run(params)` returns the result or a promise of it |
| `expose.element(name, element)` | The element for an element entry, which the exposure marks with the name |
| `expose.element(name, provide)` | For an element entry of `many`, a function that returns the current elements; each request reads it again, so a list that replaces its row elements keeps none that it removed, and the page marks each element with the name (`dataset.expose`) when it draws it |

The native host relays registrations and requests between a surface page and the registry of the workbench in the same way that it relays [sidecar](sidecars.md) messages. When a surface page closes, the registry removes its registrations.

A page registers under a key that identifies it, the owner key of the registration. A surface page registers under its surface id with the owner from its plugin.

### Surface documents

The core view bridge registers these entries in the actual view document when its surface start values are present. Plugins do not implement them. Core passes their declarations with the surface start values and declares them in `exposure.json`. These three names are the only core entries that surface pages register; `core.surface.menu` belongs to the main document. A request for a core document entry is answered once by the bridge and is not delivered to plugin exposure listeners. The main-page surface placeholder reports no document or input state for the view.

The document audit includes the actual connections of every shared binder in that document, including open shadow trees, while each binder's `audit(root)` retains its own binding scope. Disposing a binder removes its connections from the document audit. Document reads traverse the current open shadow trees; document, viewport, observed DOM and binding changes notify watchers. Each discovered shadow root is observed separately. Creating an unbound shadow root on an existing host without a binding change or an observed DOM change supplies no mutation notification; the next document read still includes it. Page exit releases the input listeners, observers, binding subscriptions and exposure watches.

| Kind | Name | Meaning |
| --- | --- | --- |
| status | `core.surface.document` | `{url, timeOrigin, readyState, themed, scale, body, viewport, filter, unbound, params}`: the document address, time origin, ready state, whether the first theme is applied, device pixel ratio, `body`, the size of the surface content (the surface element's box plus the content that overflows or scrolls past it) and `viewport`, the size of the surface element's visible box, both in CSS pixels, so `body` exceeds `viewport` only when the content does not fit, the computed `filter` of the root element, the audit of its interactive elements (as in `core.workbench.audit`), and a snapshot of the exact `window.sokSurface.params` value read when the view bridge starts, including `null`; a missing or non-object, non-null value prevents the observation from starting and reports the field name |
| status | `core.surface.input` | The last 32 trusted or untrusted input events of the document in order: `{sequence, type, trusted, x, y, key, modifiers}` for `pointerdown`, `pointerup`, `pointermove`, `click`, `wheel`, and `keydown`. `modifiers` lists the modifier keys the event carries (`shift`, `alt`, `control`, `command`). `sequence` starts at 1 and increases by one for each recorded event |
| command | `core.surface.hit` | `{x, y}` in CSS pixels; returns `true` when an element of the document is at the point |
| command | `core.surface.clock` | `{}`; returns `{page, timeOrigin, now}`: the page identity of the document, which the view start installs, and the time origin and `performance.now()` of the document in milliseconds, which a check reads between two native clock readings to map document times to the native clock; WebKit derives the time origin from the wall clock at each read and reduces it to whole milliseconds, so the page identity, not the time origin, names the document |

A mounted view owns its exposure in the application document: the request callback of the commands that it registers with `runtime.command.register`, and the status, element and command registrations that the main page relays for it. The dispose of the view removes that callback and those registrations before the same logical surface identifier can be mounted again, also when the view registered no command and while its view process still runs: the host announces the close of the surface when a place leaves it out, when the surface loads another document and when the main page reloads, and a dispose that no place precedes, such as the release of the tabs of a removed project, causes none of them. A closed or unloaded tab is therefore not chosen by the name of an entry, and `exposure.list` does not count its registrations. Repeated disposal has no effect on a later owner of that identifier. Requests after disposal are not dispatched to the disposed view.

A view registers its core and plugin entries only after its native surface is authorized, because the host creates the view when the authorized surface declares its composition. A closure received while authorization is pending cannot remove only the core entries of the subsequent mount.

### Modal documents

A native modal document reports its state to the main page through the modal answer channel with the key `document` after each render, placement, and theme change. The workbench publishes it as status `core.modal`: `null` without an open modal, or `{id, mode, document}`. `document` is reported only on the hosts that create modal web views; it is `null` until the first report and then `{mode, filter, htmlBackground, bodyBackground, scrimBackground, loaded, rect}`: the rendered element's `data-native-modal`, the root's computed `filter`, the computed background colors of the root and the body, the computed `body::before` background used for the dialog scrim, whether the document has handled the answer to its first content request (also when it dropped that answer as older than applied changes), the element rectangle in CSS pixels, and `elements`: `[{name, x, y, width, height}]`, the named elements of the document in document order.

A modal document has no status watch route: the main page forwards a status watch only to a surface. The exposure port of a modal document therefore refuses a watched value with `status <name> of document <id> cannot be sent: a modal document has no status watch route`, so the page API accepts the port at the start of the document and a value never leaves the document unreported.

Escape in a native menu answers with the key `core.modal.dismiss`, which names the declared command that closes the menu, and the answer carries an empty value. The main page runs that command through the registry; the native view runs no command itself.

A reply of a modal document reaches the main page only while that modal is the open one. The host drops a reply whose modal id and instance are not those of the open modal and records `host.overlay.dropped` `{id, instance, key, open}`; the main page drops a reply of a modal that it does not show, or that has no receiver, and records `workbench.overlay.dropped` `{id, shown, key}`. A closing modal still sends its last state report, so a drop is an `info` event and not an error, and no reply is dropped without a record.

### Choosing a surface

Several surface pages can register the same name. A request for such a name can include `surface`, an identifier from `core.surfaces`, in `status.get`, `status.watch`, `status.unwatch`, `command.run`, `element.rect`, and `element.act`. Without `surface`, the workbench chooses the active tab of the focused card, then the visible surfaces in the latest layout, then the latest registration. A `surface` that has not registered the name returns 1002. The choice without `surface` takes only tab surfaces; a section surface answers only a request that names it, or a command that its own view runs ([view calls](native-surfaces.md#view-surfaces)), because several sections of one plugin register the same names and a section follows the tab that `core.sidebars` reports.

## Tab memory

The [memory saver](plugins.md#memory-saver) of the main page has these entries.

- Status `core.tab.memory`: `{enabled, delay, pressure: {level, seq}, tabs: [{tab, kind, plugin, state, reasons, hiddenAt, unloadAt, checkedAt}]}`, notified on each change. `enabled` is the setting `memorySaver`, `delay` the setting `memorySaverDelay` in minutes, and `pressure` the last [memory pressure](hosts.md#memory-pressure) report. `kind` is `tab` or `section`, and `tab` of a section entry is its section surface id ([memory saver](plugins.md#memory-saver)); `state` is `loaded`, `unloaded` or `restoring`; `reasons` lists the reasons that protect the tab, from the one enumeration `shown`, `recent`, `keep:modified`, `keep:busy`, `media`, `media-unknown`, `capture`, `form`, `kept`, `off`, `undeclared`, `background`; `hiddenAt` is the time the tab was hidden or `null`, `unloadAt` its next delay deadline or `null`, and `checkedAt` the time of the last decision that read `media`, `media-unknown` and `capture`, or `null`. `core.surfaces` reports the same `state` for each tab, and a request to an unloaded surface fails with `tab <id> is unloaded`.
- Command `core.tab.unload {tab}` unloads a hidden tab now. As the person's own decision it does not wait for `recent`, `media`, `media-unknown`, `capture` or `form`; it fails with the error `tab <id> is protected: <reasons>` for the remaining reasons (`shown`, `keep:modified`, `keep:busy`, `kept`, `off`, `undeclared`, `background`) and with the reasons that ended the attempt, and with -32602 (invalid params) for an unknown tab.
- Command `core.tab.keep {tab, keep}` sets (`true`) or clears (`false`) the person's mark `kept` and stores it in `tab-state.json`. It is idempotent and emits one `workbench.tab.keep.changed` per change; it fails with -32602 for an unknown tab or a `keep` that is not a boolean, and with `tab <id> can never be unloaded: <reason>`, the reason `undeclared` or `background`, for a tab that can never be unloaded.
- Each tab button carries `data-tab-state` with its `state` (`loaded`, `unloaded` or `restoring`); protections are shown only through `reasons`.
- Command `core.tab.menu {tab, x, y}` opens the tab context menu in the selection layer at `x` and `y` of the window; a right click on a tab button runs it when the menu has an item. It fails with -32602 for an unknown tab and with `tab <id> has no menu items` for a tab that can never be unloaded.
- The tab context menu item with the element name `core.tab.menu-keep` is picked through the binder with `core.picker.pick` and runs `core.tab.keep` with the toggled mark; it is `active` in `core.picker` while `kept` is in the reasons of `core.tab.memory`, and is absent for a tab that can never be unloaded. Its name has the prefix `core.` like every element name that core declares, because the exposure check reads only names with that prefix.

## Plugin processes

The main page publishes four statuses of the [plugin process design](plugin-processes.md#messages-and-events). Each status is a list of records that carry the plugin id. Each list is `[]` until a plugin process reports its state to the main page.

- Status `core.plugin.open-calls`: `[{plugin, count, oldestStartedAt}]`, the open calls of each plugin that has one. `oldestStartedAt` is the start time of the oldest open call, or `null`.
- Status `core.plugin.losses`: `[{plugin, abandoned, lateReplies, timeouts, peerLost}]`, the counts of each plugin's losses, kept until the application ends.
- Status `core.plugin.views`: `[{plugin, surface, responsive}]`, the responsiveness of each plugin view surface.
- Status `core.surfaces`: each surface entry carries `kind`, `tab` for the surface of a tab and `section` for a [section surface](plugins.md#sections), which also carries its `sidebar`, and `composition`, the kind of its declared composition (`view`), or `null` when the plugin declares no surface for it. A mounted view that the compositor record does not hold is a retained view (native-surfaces.md); it is listed with `visible: false`, `dim`, `declared` and `applied` null, its `exposes`, its `status` (`{phase, error}` of its own mount), `composition` and `state`. A retained view has no placement. The status is announced when a mount starts, changes its status or is disposed, and when a registration of the surface changes.

## Windows

An application has one or more windows, and each window has its own workbench and registry. Every method except `windows.list` and `log.query` takes `window`, the identifier that `windows.list` returns. A request for a window that no longer exists returns error 1003 `window "<name>" does not exist`. This includes a window that closes after the host accepted the request: the host reads the native window in the main-thread step that passes it to native code, and a window that closed before that step fails the request with 1003 without reaching native code. A `host.window` change of such a window notifies nothing; the window's removal from `host.windows` reports the close.

`index` is a non-negative integer, and a request with `index` of another type is refused with -32602.

An open dialog makes every element outside it inert. A dialog is a modal of the kind `dialog`, the settings and the debug view; the picker, a modal of the kind `menu`, makes no element inert. An inert element keeps its layout, so `element.rect` answers its rectangle although the dialog covers it, and `host.hit` answers what a point reaches. `element.act` on an inert element, in any document, returns 1010 with the message `element <name> is behind the open dialog and takes no action`.

Native pointer injection retains the pressed view separately for each pointer and button, with the window of the press. Drag and release go to that view even when the pointer crosses another view; release receipt waits for the pressed document. A drag or release without a matching press of the pointer in the window, a second press while that button of the pointer is held, or a removed pressed view returns an explicit input rejection. Scroll and button-free movement continue to use the current pointer position.

The workbench page and its card elements share the application DOM document; a view surface has its own document. The main registry converts a view's local `element.rect` by adding the current applied view origin once when the selected surface answers. It adds no text-size or capture scale: the view's native page zoom is 1 and CSS sizing is already reflected in the element rectangle. The returned rectangles use application-document coordinates and their `document` origin is `{x: 0, y: 0}`. A missing applied frame fails with the surface identifier instead of substituting a zero origin; a hidden or zero-size view still uses its applied origin. A native modal has its own document: its rectangles remain modal-local and its `document` origin is the actual modal frame origin. An element of a native modal that the main document hides, such as an item of a picker, answers this way: the modal document reports the rectangles of its named elements in `elements` of its state, and a request before that report, or for an element that the report lacks, fails. It never answers the empty box of the hidden element. Clients add the reported document origin exactly once; they must not compensate for surface kind or card placement. On the mygo host, for an element of the workbench, `element.rect` returns the frame of the element in window points with `zoom` 1 and `document` `{x: 0, y: 0}`, and `element.act` accepts `click` and `input`; `dispatch` fails with `the mygo workbench has no DOM events`. The elements of view pages keep every action on every host.

The host delivers `input.pointer` and `input.key` as native events, and the page receives trusted events. The application is not activated, except for `move` with `activate: true`. On macOS:

- In an application that is really active, a key to the key window goes through `-[NSApplication sendEvent:]` with the window's number, like a person's key, so AppKit decides key equivalents such as Command+C and Command+V. A key to a window while another window is the key window is not delivered and returns 1006, because a person's key cannot reach that window. In an inactive application, a key makes the window the [virtual key window](#virtual-key-window), which offers a key down with Command or Control as a key equivalent first, and a key that is not taken goes to the window's `-[NSWindow sendEvent:]`, because `-[NSApplication sendEvent:]` reads the real state and drops it. Scroll goes through `-[NSWindow sendEvent:]`. A press goes directly to the view under the point because AppKit does not deliver a press in an inactive window to that view; subsequent drags and release retain that pressed view. That view is a view of the content view: the buttons of the title bar are views of the window frame outside it and track their press in their own event loop, so a press never reaches them. The real-input tier checks the window-server path of a person's pointer, the close button among it.
- A `down` or `up` into a web view returns after that view's document has received the trusted `pointerdown` or `pointerup`. A script in a separate WebKit content world, which the page cannot see, reports the receipt. While a text field has focus, WebKit passes mouse events to the input method asynchronously first, so a press and a release sent one after the other could otherwise reach the document in the opposite order. If the document does not receive the event within 2 seconds, the request returns 1005. A `scroll` is delivered after the web view under the point has presented its current state, because WebKit does not scroll a new document with a wheel event received before its scrolling tree is presented; if the view does not present within 2 seconds, the request returns 1005.
- WebKit updates hover (`pointerover`, `pointermove` without a button, `:hover`) only while the window answers as the key window. In an application that is not really active, a `move` makes its window the [virtual key window](#virtual-key-window), also a window that AppKit holds as its key window; in an application that is really active, a `move` to a window that is not the key window returns 1006. The key window of the active application also receives the system pointer location as a move, for example when it becomes key, and such a move between a synthetic `down` and `up` reaches the document as a drag, so activation-tier checks keep the window away from the system pointer.
- WebKit reads the pressed buttons of a mouse event from AppKit (`+[NSEvent pressedMouseButtons]`), not from the event. If AppKit reports a nonzero button mask, a synthetic press or release may reach the document as `pointermove` instead of `pointerdown` or `pointerup`, so a `down` or `up` is refused with 1007. The mask alone does not identify what produced that state, so the error message reports the mask and the frontmost application measured in the same main run-loop turn as the refusal: `AppKit reports NSEvent.pressedMouseButtons mask <mask> while <application> is frontmost; the synthetic press or release was not delivered`. `<mask>` is the mask in lowercase hexadecimal with a `0x` prefix. `<application>` is `<bundle identifier> (pid <pid>)`, `an application without a bundle identifier (pid <pid>)`, or, when AppKit reports no frontmost application, the clause reads `while no application is frontmost`. Both hosts produce the same text. While a `down` is open, the page sees its button in `buttons` of the events of its pointer, as for a person, and not in the events of another pointer; a press that a person holds stays the only cause of 1007.
- `clicks` is the `clickCount` of the event of a `down` or an `up`, and WebKit makes `dblclick` from the press with the count 2, so a double click is the same event pair that AppKit gives a person.
- A press stays open from a delivered `down` until a delivered `up` of the same pointer and button in that window, and a refused `up` keeps it open, so a later `up` releases it on the view that received the press. A `down` of a button whose press the pointer holds, in any window, is refused with 1008 with the message `pointer <pointer> holds an open press of this button; send up before the next down`. `host.buttons` reports the mask that the 1007 refusal reads, so a press whose `up` was refused can be ended once `host.buttons` reports mask 0. A check session ends every press it left open when it ends: it waits through `status.watch` until `host.buttons` reports mask 0, without a timer, and then sends `up`, which must be delivered.
- With `activate: true`, the host activates the application and makes the window key, waits until every visible webview in the window has sent the active state to its web process, and then delivers the move. This takes the keyboard focus from the application the user is using. If activation does not finish within 5 seconds, the request returns 1006 with the step that stopped: the system did not activate the application, the window did not become key, the webviews did not apply the active state, or the window lost activation before they did. Except for the webview step, the message names the frontmost application. macOS refuses an application's own activation request while the user has not activated it since it was launched in the background (cooperative activation), so an activation-tier check first activates the application through `NSRunningApplication` from the check process, as a person switching to it does, and the host request then completes the key window and webview steps. If timeout occurs before callback registration, the native error record reports that webview activity-state registration is pending and does not invent member IDs. After callback registration, it identifies only unresolved visible webviews by their existing role or view identifier and registration index. Each completion resolves only its own registered webview; duplicate or late completions do not finish the aggregate early or complete it twice.
- The OS input method serves only the active input context of the key window of the active application. `input.key` to a window that is not that key window is either rejected, while another window is the key window, or delivered without reaching the input method, in an application without a key window, so its result is not input-method evidence. A view that passes a character key to its input context, such as the terminal image region, receives no text for it in an application without a key window once the application has been active: the input context accepts the key and the input method does not answer. The terminal image region reports such a key as the error `input method did not answer native keyCode=<code> outside the key window of the active application`; in the [virtual key window](#virtual-key-window) it types the key without the input method. Named keys and Control or Option combinations that the region reports itself are delivered in any window. A web view passes character keys to its input context in the same way, so a document region also takes typed characters through its input context only in the key window of the active application once the application has been active; an application that has never been active, such as a native test that forbids activation, still receives them. In the virtual key window a web view takes a character key with a stated text through its text input instead. Input-method behavior is verified only by activation-tier checks; character typing into a terminal image region and into a web view is verified on the virtual key window.

On Windows the host calls the DevTools protocol of the web view, not `SendInput`. `input.pointer` becomes `Input.dispatchMouseEvent` and `input.key` becomes `Input.dispatchKeyEvent`, and a call starts when the one before it completed, because the protocol does not keep their order. The first input of a web view enables `Emulation.setFocusEmulationEnabled`, so `:focus` holds in a window behind others, and an input takes no system focus. The press rules are those above, and `move` and a key do not answer 1006 for a window that is not active. A page has one mouse pointer, so a window has one press of each button, and all its open presses belong to one pointer: while a pointer holds a press in a window, a `move`, `down`, `drag` or `up` of another pointer in that window returns 1011 with the reason `the page has one mouse pointer`, and its `scroll` is delivered. A call that does not complete in its wait answers its failure, and every later input is refused until it completes. `activate: true` asks the system for the foreground, and the system refusing it is the answer. `diagnostics.capture.still` uses `CapturePreview`. A minimized window, a window that is not shown and a hidden web view are refused at once, because the call is reported to accept and never complete for them, and a capture that does not complete in 10 seconds answers a failure that names a covered window. This path has not run on Windows yet.

On Windows a key with `control`, `option` or `command` and no `text` goes down as `rawKeyDown` with its `code`, its `windowsVirtualKeyCode` and its modifiers, and without `commands`. Blink maps such a key down to an editing command itself on a system other than macOS: `third_party/blink/renderer/core/editing/editing_behavior.cc` lists `{'A', kCtrlKey, "SelectAll"}` beside Copy, Paste, Cut, Undo and Redo in its entries for systems other than macOS (lines 171 to 181), and `EditingBehavior::InterpretKeyEvent` looks a `kRawKeyDown` event up in its table by key code and modifiers (lines 242 to 284). `content/browser/devtools/protocol/input_handler.cc` makes `rawKeyDown` a `kRawKeyDown` event (lines 1225 to 1226) and `windowsVirtualKeyCode` its key code (lines 1251 to 1252). So Control with A selects the page without `commands`, the editing commands that `Input.dispatchKeyEvent` can carry (`third_party/blink/public/devtools_protocol/domains/Input.pdl`, lines 136 to 139). The table has entries with the Meta key only for macOS (`editing_behavior.cc`, lines 150 to 153), so `command` with A selects nothing on Windows: a test that selects, copies or pastes with a key uses `control` on Windows and `command` on macOS. A protocol key does not pass through the input method of Windows and never starts a composition, and `diagnostics.input.source` answers that keyboard input sources are not implemented on this platform, so a test of a composition is refused on Windows, not run.


On Windows `host.buttons` and the presses and drags of a window come from raw mouse input (`RegisterRawInputDevices` with `RIDEV_INPUTSINK`), not from a system hook, so a person's input never waits for the host: a raw input is a copy that the system sends beside the input. Bit 0 is the physical left button, bit 1 the right, bit 2 the middle, and bits 3 and 4 the fourth and fifth buttons. The limits of this source are these: its thread wakes at every move of the mouse, also over other applications; touch and pen input that the system does not send as raw mouse input change nothing; a press is hit-tested where the pointer is when the source reads it, not where the button changed; and the keyboard is not registered, so a key input does not tell the host which view has the focus, as it does on macOS. Whether a raw input reaches the host while an application of higher integrity has the foreground has not been observed.

### Named pointers

`pointer` of `input.pointer` names a pointer, and a request without it is the input of the pointer `main`. Each pointer holds its own position, its pressed buttons, the view that received each of its presses and the origin of each press, so two pointers press and drag at once, in two windows or in one window. The real cursor never moves. On macOS, while the input of a pointer is delivered, `+[NSEvent pressedMouseButtons]` answers the buttons of that pointer, so each page sees the `buttons` of its own gesture, and outside a delivery it answers the buttons of every pointer.

AppKit and WebKit keep some state once per window, page or application, not once per pointer. An input that would share such state with the open press of another pointer is not delivered and returns 1011 with the message `pointer <holder> holds a press that this input would share: <reason>`. On macOS the cases are these:

- A `down` on a page, the web view that contains the view at the point or that view itself, that another pointer holds pressed: `the page at the point holds its press`. WebKit keeps one pressed state per page, and a release while the page still reports a held button becomes `pointermove`, not `pointerup`.
- A `down` in a window that passes presses through `-[NSApplication sendEvent:]`, the key window of an application that is really active, while another pointer holds a press in that window: `AppKit keeps one press of a window that passes the application`. `NSWindow` keeps one target of each button for the presses that pass the application.
- A `move` in a window in which another pointer holds a press: `the window has one hover position`. A window has one set of entered tracking areas and one pointer position for its pages.
- A `move`, `down`, `drag` or `up` while another pointer holds a press, when the input method of the system serves the page of the input or of that press, which holds the current input context in the key window of an application that is really active: `the input method of a page answers after the delivery`. WebKit passes the mouse event to the input method and makes the page event after the delivery has returned, so it would read the buttons of every pointer.

Two pointers therefore press and drag at once in one window when their presses go to different pages or views of a window that does not pass presses through the application: any window but the key window of an application that is really active, such as the [virtual key window](#virtual-key-window). A `scroll` takes no press and is never refused for another pointer. On Windows a page has one mouse pointer, so another pointer waits for the release of the page, as the Windows paragraph above states.

### Virtual key window

In an application that is not really active, `input.key` and a `move` of `input.pointer` make their window the virtual key window on macOS. It answers as the key and main window inside the application, and the application answers as active, so WebKit updates hover and page focus. The system key window and the front application do not change. The rules:

- A process has at most one. Input to another window moves it there.
- AppKit can hold a key window in an application that is not active, such as a window that a host shows while another window is the virtual key window; `host.window` then reports `key` true and `active` false. Input of that window is input of an application that is not active: a `move` makes it the virtual key window, and a press goes directly to the view.
- The methods are replaced at the first entry, so an application that receives no such input has none replaced.
- Input of the window goes to the window or the view, never through `-[NSApplication sendEvent:]`, which reads the real state. A local event monitor therefore does not see it.
- Before dispatch, the native key producer materializes `NSEvent.characters` and `charactersIgnoringModifiers` on the original event. Consumers therefore receive a complete immutable payload, and menu matching cannot depend on an earlier observer reading lazy character fields. This preserves the system input-source translation, physical key code, modifier flags and stated-text metadata; it neither substitutes Latin characters nor changes the input source.

- The virtual key path enforces the `native menu` ownership declared by the shortcut table above: Command/Control key down first calls `-[NSMenu performKeyEquivalent:]` on the main menu. Only an enabled menu equivalent takes ownership; otherwise the window receives `-[NSWindow performKeyEquivalent:]`, preserving view-owned and unclaimed shortcuts. A key down neither accepts goes to `-[NSWindow sendEvent:]`; key up always goes there. This is the project's menu-ownership policy for virtual input, not Apple's default view-first dispatch order. Real active-window input continues through the existing `-[NSApplication sendEvent:]` path. The key's `input inject` record reports `equivalent` and whether it waited behind held input (`held`).
- It stays at its place in the order of windows: `orderFront:`, `makeKeyAndOrderFront:` and `orderFrontRegardless` are refused for it, each with the event `native.input.virtual`.
- A real activation ends it from its first moment, and real state wins. `activate: true` ends it before it activates. A window that closes ends it. Each end writes one `native.input.virtual` with its `reason`.
- A real move, a real cursor position and a real button mask do not enter its pages. `host.window` reports the injected position as `pointer`, and `key` and `active` keep reporting the system state, with `virtualKey` beside them. A real scroll and a real press still arrive, and a real press of the window activates the application.
- A terminal image region types a character key without the input method, which does not answer this window. A key whose `text` the call stated types that text, whatever the input source of the system is: the injected event carries `kCGEventSourceUserData` with the value `SP_INPUT_STATED_TEXT` of `input_inject.h`, also when the region receives it later from the keys that its surface kept. A key without `text` types what the keyboard layout of the current input source makes of it, through `UCKeyTranslate` with the dead key state of that layout, so a dead key types nothing and the next key types the composed character. A key without `text` under an input method, such as Korean or Japanese, is refused with the error `the input source <id> is not a keyboard layout`, because only the system composes and only for the key window of the active application. A check that types characters on the virtual key window therefore states `text`, and the input source of the person is not changed.
- A web view, such as a document region, a surface or the main page, takes a character key down whose `text` the call stated through its text input, and a named key down, without the input method. While the key is delivered, the web view answers without an input context (`-[NSView inputContext]`, through which WebKit and `-[WKWebView inputContext]` read it, is replaced at the first entry), so WebKit interprets the key with the key bindings, as AppKit does for a view without an input context: the stated text reaches `insertText:` of the web view as the command of the key, and a named key runs the command of its binding, so Backspace runs `deleteBackward:`. The page receives what a person's key gives it: `keydown` and `keypress` with the stated text as `key`, `beforeinput` and `input` with the stated text as `data`, and `keyup` for the key up; a page that cancels the `keydown` receives no text. AppKit gives the key up of a text of more than one character the character that the keyboard layout of the system gives the key code, so that character is the `key` of its `keyup`. A character key without `text` goes to the web view as before and passes its input context, which the input method does not serve in this window. The record `input inject` of the key states `virtualKeyText`, which is true only for a stated text.
- A surface or a document region that closes with the keyboard gives it to the content view before it leaves. AppKit otherwise keeps the view until the next change of the first responder, and the closed page and its data store do not end.

Tests that check a real input path use `input.pointer` and `input.key` only. Tests use `element.act` only to set up state.

## Relay

The host and the pages exchange these messages. They are internal to core and not part of the endpoint.

| Direction | Message | Content |
| --- | --- | --- |
| host → main page | event `exposure-request` | `{id, method, params}` for `exposure.list`, `status.*`, `command.run`, `element.*` of core and plugin names. The host waits 10 seconds for the answer, except for `command.run`, which the main page answers within the command's timeout, whether it forwards the command or answers it itself; a main page that is not ready returns 1003, and requests to a main page that reloads or closes end with 1003 |
| main page → host | call `exposureReply` | `{id, result}` or `{id, error: {code, message}}` |
| main page → host | call `exposureChanged` | `{name, surface?, value}` for a watched status; `surface` is present when the watch named one. The host refuses a name that starts with `host.` with `the page cannot change host status <name>`; only the host changes a host status |
| surface page → host | call `exposureRegister` | `{surface, kind, name}`, where `kind` is `status`, `command` or `element`. The page of a view has no surface bridge: it calls `runtime.native.call` with `{name: "registered", payload: {kind, name}}` through the view channel ([view surfaces](native-surfaces.md#view-surfaces)), and the main page relays it with this call. A relay from the main page is accepted only for a surface that has a view |
| host → main page | event `exposure-registered` | `{surface, kind, name}`; `{surface, closed: true}` when the surface is removed. Surfaces outlive a reload of the main page, so after the main page reports ready the host sends every live registration again |
| main page → host | call `exposureForward` | `{id, surface, method, params, timeout?}` for a name that a surface page registered. `timeout` is an integer from 1 to 600000 milliseconds, taken from the command declaration; without it the host waits 10 seconds. An invalid `timeout` returns -32602 |
| host → surface page | event `exposure-request` | `{id, method, params}`. For a view, the event carries `surface` and the main page relays it to the view through the view's `exposure-request` subscription (`runtime.native.on`), with `data` `{id, surface, method, params}` |
| main page → surface page (through `exposureForward`) | `status.watch`, `status.unwatch` | `{name}`. The surface page starts or stops following the value and answers at once. After `status.watch` it sends the current value with `changed`, also when the name is already watched, and each later different value until `status.unwatch` |
| surface page → main page | `changed` | `{name, value, version}` for each value of a watched status; `version` starts at 1 and grows by one with each different value. A surface page in the main document gives it to the registry; the page of a view calls `runtime.native.call` with `{name: "changed", payload: {name, value, version}}` through the view channel ([view surfaces](native-surfaces.md#view-surfaces)). The main page delivers it to each watch of that surface and name whose last version is older, so a change that arrives after a newer one is not delivered; each value that no watch takes is written as the trace event `workbench.trace.surface.change.dropped` `{surface, name, version, reason}`, with `reason` `no watch` or `older than version <n>`. The host carries no message for it |
| host → main page | event `diagnostics-tick` | No payload. Diagnostic builds only: one per step of `diagnostics.drag` |
| surface page → host | call `exposureReply` | `{id, result}` or `{id, error}`; the host returns it to the main page as the result of `exposureForward`. The page of a view answers through `runtime.native.call` with `{name: "exposureReply", payload: {id, result\|error}}`, which the main page sends as this call with the surface of the view |
| surface page → main page | none | A view follows a status with the view call `runtime.status.watch`, which the main page answers with the registry observation of this document: a core status is followed in this document, and a plugin status through the surface that registered it, with `status.watch`, `status.unwatch` and `changed` of this table. The host carries no message for the watch ([view surfaces](native-surfaces.md#view-surfaces)) |

The main page validates names against the declarations before it registers or forwards them. It keeps a registration from a surface that no loaded layout contains yet, and applies or rejects it when a layout containing the surface is loaded. `exposureReply` from the main page answers an `exposure-request` of the host; `exposureReply` from a surface page answers a forwarded request. The host identifies the caller by its webview.

A surface page can answer a forwarded request after its surface was removed, for example a `command.run` that it answers as the surface closes. The host already ended every request to that surface with 1003 when it removed the surface, so the reply has no request to answer: the host discards it and writes the observation `exposure reply <id> of removed surface "<surface>" arrived after its request ended` to the application log instead of refusing the call. The same holds for a request that the host ended with 1003 because its document was closed or reloaded while the surface stayed: a reply to it is discarded and written as the observation `exposure reply <id> arrived after its request ended`. The host remembers the 256 most recent ended requests; a reply to any other id still fails with `exposure reply <id> has no matching request`.

The runtime modules map these calls to framework bindings:

| Call | Wails method | Tauri command |
| --- | --- | --- |
| `exposureReply` | `ExposureReply` | `exposure_reply` |
| `exposureChanged` | `ExposureChanged` | `exposure_changed` |
| `exposureForward` | `ExposureForward` | `exposure_forward` |
| `exposureRegister` | `ExposureRegister` (surface bridge and main page) | `exposure_register` |

The page interface for surface pages is `page.exposure`: `register(kind, name)`, `onRequest(fn)` where `fn({id, method, params})` is called for each forwarded request, and `reply(id, payload)`. The main page uses `host.on("exposure-request", fn)`, `host.on("exposure-registered", fn)`, and `host.call(...)` with the calls above. A reply without `surface` answers a request of the window's main document; a reply with `surface` answers a request of that surface document and names it with a nonempty string. A `surface` that is `null`, empty, or not a string is rejected as an error, not treated as a main-document reply.

## Errors

| Code | Meaning |
| --- | --- |
| -32601 | Undeclared method |
| -32602 | Invalid params, including a value of the wrong type |
| 1001 | Unknown name |
| 1002 | Name is declared but not registered |
| 1003 | Owner document no longer exists |
| 1004 | Native input is not available on this platform |
| 1005 | Request timed out: the owning document did not reply within 10 seconds |
| 1006 | The window is not active: in an application that is really active, a `move` or a key needs its key window, or the system did not activate the application |
| 1007 | AppKit reports a nonzero `NSEvent.pressedMouseButtons` mask, so a synthetic pointer `down` or `up` was not delivered; the message reports the mask and the frontmost application at the refusal |
| 1008 | The press of that button of the pointer is still open, so a pointer `down` was not delivered |
| 1009 | The address of an element request names no element |
| 1010 | The element is inert behind the open dialog, so an action was not delivered |
| 1011 | An open press of another pointer holds state that the input would share, so the input was not delivered; the message names that pointer and the state ([named pointers](#named-pointers)) |
| -32000 | A registered command or status handler failed; `message` is its error message |

A 1005 error of a relayed request has the message `the document did not reply within <ms> ms`. Both hosts remember the 256 most recent requests that timed out, dropping the oldest; a reply to one of them fails with `exposure reply <id> arrived <ms> ms after it was sent; its request timed out after <ms> ms`, and a reply to no remembered request fails with `exposure reply <id> has no matching request`, so the delay of a late reply is in the error that the page reports. A command forwarded to a surface page that times out writes the event `host.call.timeout` with its plugin and command, and a late reply to such a command writes `host.trace.call.late-reply` with its delay.

The [local endpoint](endpoint.md) closes the connection after an undeclared method.

### Window-owned application menu actions

`host.menu.select` performs the item in the window of its request. The window goes through the platform port and the native interface to the selection, and the host does not choose another window. An item with a target sends its action to that target. An item without a target sends its action from the first responder of the requested window up its responder chain and then to the application and its delegate, and not through the responder chain of the key window. The selection works the same when the application is active and when it is not, and it neither activates nor reorders a window.

The selection fails with a distinct reason for each case: the window is missing, the menu or item title is missing or not UTF-8, the menu is missing, the item is missing, the item has no action, and the action has no responder. The error of the Go and Rust hosts adds the requested window, menu and title to the reason.
