[한국어](hosts.ko.md)

Core's native side lives in two language host libraries with the same structure and in one framework adapter per framework. [Native host interfaces](native-host.md) defines the operations the workbench page uses. [Host contract cases](host-contract.md) lists the behaviors that the tests of the hosts execute.

A language host library holds everything that does not name a framework: bindings, windows, workspace, surfaces, documents, images, sidecars, exposure, endpoint, event log, diagnostics and the darwin platform layer. It reaches the framework only through its framework port, the two interfaces `Framework` (application name, whether a window has a main page, main-thread step, quit, dialogs, menus, Dock, and window creation with its title bar) and `Frontend` (event emit, window title, show, focus, the window events, the presentation notice, the settled presentation, the workbench start and the workbench call channel), which have the same names in both languages (`src/framework.*`). A method that both ports have has the same name in both languages (snake case in Rust), and a method that one language has is a row P of the [language table](#language-table). `Frontend` takes and gives sizes and positions in logical pixels. No file of `packages/host/go` imports a package of Wails or mygo, and no file of `packages/host/rust` names a crate of Tauri ([structure checks](#structure-checks)). No identifier and no string of a source or a test of a language host library names a framework, and no contract declaration of its files does: a value that belongs to one framework is in its framework adapter, which passes it through the port or converts a value of the port. The Tauri framework adapter passes the page origin to the start document, converts the key of a menu item to the shortcut of its menu library and decides which lookups of its asset resolver are requests of the page; the Wails framework adapter converts the logical lengths of the port to the integers of Wails, each to its nearest integer. A framework adapter holds `Run` and the implementations of the framework port. A file that only one language needs stays in its language host library; a file that only one framework needs is in its framework adapter. The application name of a framework adapter (`wailsv3`, `tauriv2`, `mygo`) is the `application` of `endpoint.json`, the name of the endpoint socket, the host of the release key of the application update and the `host` of the state file of the debug view.

The applications `apps/wailsv3` and `apps/tauriv2` contain only `src/main.*`, `environment.json`, `runtime/index.js`, tests, manifests, and framework configuration. `apps/wailsv3/src/main.go` reads the command-line flags into `host.Options` of the Go language host library and calls `adapter.Run(assets, options)` of the Wails framework adapter. `apps/tauriv2/src/main.rs` calls `soksak_host_tauriv2::run(tauri::generate_context!(), BACKGROUND)` of the Tauri framework adapter, where `BACKGROUND` is the staged `frontend/background.js`.

The mygo application and its Go dependencies must build with `CGO_ENABLED=0`. Purego is an implementation choice, not a requirement. Changes to the shared Go host or the Wails adapter must preserve this cgo-free mygo path; a framework-specific foreign function binding belongs behind the platform interface and must not impose cgo on another adapter.

The Go callback owner retains a value under a nonzero integer token until its last native use ends and the owner deletes it. Zero and deleted tokens are invalid; deleting twice or reading an invalid token panics. Tokens are not Go pointers and are not reused after deletion. The callback package builds and runs with `CGO_ENABLED=0`; it uses `sync.Map` and atomic token allocation because `runtime/cgo.Handle` links cgo runtime symbols even when only its handle operations are used.

The shared native header `native/darwin/src/host_callbacks.h` declares the native-to-host callback ABI: 36 base callbacks and 7 diagnostic callbacks. Each profile is registered once before its work starts; the native library copies a complete table and rejects missing entries or replacement. Function addresses remain valid until process exit. Native code refers to registered `sp_host_callback_*` and `sp_host_diagnostic_callback_*` entries instead of linking Go exports; each invocation still runs through `hostRunOnWorker` or `ON_WORKER`. A callback invoked before its profile is registered aborts with its entry name. `make create-host-callbacks` generates the cgo registration from the header through clang; `make check-host-callbacks` rejects a stale binding and is a prerequisite of the native build. The diagnostic registration is selected only by the `diagnostics` Go build tag.

## Rules

- Code is in `src/`. Tests are in `tests/`, and test file names end with `_test` in both languages. Go tests in `tests/` import the package of their language host library or framework adapter; Cargo builds each `tests/*_test.rs` file as an integration test of the crate.
- The primary file of each directory has the directory's name: `host.*`, `platform/platform.*`, `darwin/darwin.*`, `windows/windows.*`.
- Rust modules use `#[path = "..."]` attributes, so the crate has no `lib.rs` or `mod.rs`.
- Platform code exists only under `src/platform/<os>/`, where `os` is `darwin`, `windows`, or `linux`.
- No stub files exist. An operation that a platform does not implement returns an error from `src/platform/<os>/unsupported.*`.
- A C name that `native/darwin` exports starts with `sp_` when a framework exports the same name. Wails compiles its own `windowFullscreen`, and the linker picked one of the two: the call reached the framework's function and the host read its return value as a failure.

## Platform selection

Go: each `src/platform/<os>/` directory is a Go package. Its primary file (`darwin.go`, `windows.go`) has no build tag and contains only the package documentation; the other files have a `//go:build <os>` tag, and one of them calls `platform.Register` from `init`. `host.go` of the Go language host library imports every OS package with a blank import, so a build registers only the implementation for its target OS. `Prepare` obtains it with `platform.Current()` and fails when no implementation is registered. The Wails framework adapter imports its own `src/platform/darwin` package in the same way (row H31 of the [framework table](#framework-table)).

Rust: `src/platform/platform.rs` declares each OS module with `#[cfg(target_os = "macos")]` or `#[cfg(windows)]` and `#[path = "<os>/<os>.rs"]`. `platform::current()` returns the implementation for the target OS and returns an error on other targets. Each OS module declares its own files with `#[path]`.

The shell sidecar repository uses the same Go mechanism in its `src/platform/` ([repositories](plugins.md#repositories)).

## Platform interface

`src/platform/platform.*` defines the interface that each `src/platform/<os>/` implements. Operations take native window and view handles. In Go a window handle is `platform.Window`, an integer on every operating system: an HWND is a value that Windows owns and not an address, so no Go pointer holds it, and only the darwin implementation turns a handle into the address of its NSWindow at the call of native code. A view handle is an `unsafe.Pointer` to an object of native code.

Capture first-frame readiness succeeds only after a complete frame is written and no recording error is known at the readiness check. A known asynchronous start or stream failure rejects readiness even when that frame exists; the original error remains available to the caller.

Still capture returns its own caller-owned error string, freed with free(), separately from recording errors. A failed still capture neither clears an existing recording error nor makes a healthy recording fail. Invalid UTF-8 paths are rejected before platform APIs. Late still callbacks retain only their own call state and cannot change recording results. The native sp_capture_still error output pointer is mandatory; success sets its value to NULL, and failure allocates a UTF-8 error string. Both hosts consume and free that per-call output rather than reading sp_capture_error.

On macOS still capture and recording read the window through ScreenCaptureKit, on all three hosts, with a desktop-independent filter of the window taken from the content of the current process (`getCurrentProcessShareableContentWithCompletionHandler:`). The SDK describes that content as available to the current process without user consent through TCC, and capture never asks for the general shareable content, which needs the screen recording permission. Capture asks for no cursor and activates nothing. As an observation of the operating system and not a guarantee: with `CGPreflightScreenCaptureAccess` false, capture wrote its image and no prompt appeared, while the system log recorded `auth_value 0, result false`. A window under another window captures the same bytes as before the cover, with its web view, WebGL canvas, composited layers, Metal layer and IOSurface layer, and a change made while covered shows in the next capture. This holds because a host turns off the occlusion detection of its main web view, of its view pages and of its modal web view; with it on, the web layer is missing from a covered capture, and a modal opened in a covered window is not raised. Document regions keep the detection, so the document of a covered region is hidden and does not draw its animation frames; while `diagnostics.window.draw-covered` is on for the window, the host turns it off for the document regions of that window too, so a still capture of the covered window holds their documents and the changes made while covered ([document regions](native-surfaces.md#document-regions)). Paths that read the layers directly are not used because they do not give these pixels: `takeSnapshot` has no Metal or IOSurface layer, `renderInContext:` has no Metal layer or window background, `cacheDisplayInRect:` has no Metal layer and differs by 1, and a composite of `takeSnapshot`, a Metal readback and the IOSurface has no title bar and differs in text and rounded corners. The message of a failed ScreenCaptureKit call ends with the error domain and code, because the description alone may name neither.

Recording target preparation and start reject an already active recording before changing target, frame counters or recording errors. Each open/start call returns a separate caller-owned UTF-8 error through a mandatory output pointer (NULL on success; free() on failure). Rejected overlapping operations cannot invalidate healthy recording readiness or erase an earlier recording failure.

Target preparation publishes a filter and configuration only when its own query completes successfully within the 10000ms limit. A timed-out query retains only its own callback state; a late failure is reported and a late success cannot overwrite a later target. Preparation releases obsolete inactive target/configuration ownership instead of retaining unused objects. Preparation errors are returned through its per-call output and do not change recording errors. If a recording becomes active before successful preparation is published, the call rejects that publication and preserves the active recording.

Each failed frame-file open, write, close or commit reports its own operation, frame path and captured system error. A failed partial-file removal reports an additional recording error without replacing the original failure. Close is still attempted after a write failure, and its failure is reported separately. Removal is attempted only for a file successfully opened by the writer; an open failure cannot delete a pre-existing path. A failed frame never increments the written count or signals first-frame readiness.

An asynchronous start or delegate-stop failure changes recording errors only when it identifies the current stream. A delayed failure from an earlier stream is reported with its stream identity and cannot change later recording errors or first-frame readiness. Start completion retains its original stream identity through delivery; it must not read the identity of a replacement stream as its own.

The document operation places the web view of a view page in the `SurfaceHost` of its surface, below that host's native plane, not directly in the window's shared surface container. The native library makes that container in the `NSView` that it is given, which on the Wails and Tauri hosts is the window composition around the main web view; the container holds the `SurfaceHost`s, applies the backing scale to their web views and turns a `cursorUpdate:` of one of them into a pointer move at the current position. Besides the main web view, the only web view outside every surface is the modal, which fills the window. Document regions and image regions are descendants of that host's native plane. The platform interface does not expose an operation that can place a region as a sibling of its `SurfaceHost`. Both language hosts validate the [surface composition](surface-composition.md) before calling platform code.


A place closes every document and image region of each surface that it no longer lists before it replies, in both hosts (`closeSurfaceDocuments` and `images.CloseSurface` in Wails, `documents::close_surface` and `images::close_surface` in Tauri); the page then releases that surface without detaching its regions ([region lifetime](native-surfaces.md#region-lifetime)).

### Window buttons

AppKit owns the window's own buttons. The title bar height decides where AppKit places them: AppKit centres the buttons vertically in the title bar and keeps them there after a title change, a resize, and a move. Each host sets the title bar height with AppKit's `-[NSWindow setTitlebarHeight:]` (`windowSetTitlebarHeight`, listed in the [private native API inventory](../operations/private-native-apis.md)); the window has no toolbar. Each host sets the height to 40pt when it creates the window, before the window becomes visible, and sets it to the row of the stored frame factor before it answers the start document of the window's page, inside a start transaction while the window still shows its previous page, so the page's first draw, which waits for no preparation, has its title bar ([title bar height](native-surfaces.md#title-bar-height)).

The page owns the height of its first row: `--chrome-row` in `packages/workbench/app.css` is `round(max(--chrome-h, 36px × frame factor))`, where `--chrome-h` is the fixed 40px minimum and the frame factor is the [text size](text-size.md) of the frame; `chromeRow` in `packages/workbench/frame-text.js` computes the same height for the page's requests. The page does not take the row from the window's answer, so a change of the title bar does not change the row. The title bar height belongs to the layout transaction ([title bar height](native-surfaces.md#title-bar-height)): each preparation (`syncSurfaces`) carries `titlebar`, the height of the first row that the next draw shows, and the host sets the title bar to it in the window's open transaction, so the title bar and the row change in the same presented frame. The page reads `windowControls` on start and on every window resize, reserves the width of the button area in the first row, and prepares a layout that carries its row when the title bar differs from it. `host.window` reports the visible area in `controls`.

`titlebar` is a number of points from 32 through 200. Before the transaction begins, both hosts reject a request without it with the argument decoder's `argument request.titlebar is missing` ([host calls](native-host.md#host-calls)) and another value with `title bar height must be a finite number from 32 through 200 points`. A window without standard buttons or a content view fails with `the window has no standard buttons or content view for a title bar`, and that failure cancels the begun transaction. A window in full screen shows no title bar, and AppKit saves the height when the window enters full screen and restores it when the window leaves, which would discard a height set in between; the host therefore leaves the title bar unchanged while the window is in full screen, and the preparation answers `chrome.row` 0. Leaving full screen resizes the window; the page reads `windowControls` then and prepares its row again when the restored height differs from it.

Moving the buttons into the page's own view is what made AppKit take them back on a title or recording-indicator change, which showed one frame with the buttons missing or at the title bar position in about one of 48 window moves and resizes. The title bar height does not come from a toolbar: an empty toolbar with the unified compact style fixes the title bar at 40pt, so the buttons would leave the centre of a first row that the frame factor enlarges.

## Wayland limits

A client on Wayland cannot place or focus a toplevel: the compositor decides both, and GDK's `set_accept_focus` and `set_focus_on_map` do nothing there. An operation that needs either returns `<operation> is not implemented on wayland`, and a window check that needs either runs on X11. Input into a page needs neither: on X11 and on Wayland a host makes `GdkEvent` values inside the process and gives them to `gtk_main_do_event`, and it uses no XTEST and moves no real pointer.

## Windows state

On Windows both hosts implement directory identity (`platform/windows/identity.*`), the pointer and key input of a WebView2 (`platform/windows/input.*`, `devtools_input.*`), its still capture (`capture.*`) a show that keeps the front (`show.*`, `show_windows.*`), the queue of the UI thread (`ui_queue.*`, `ui_thread.*`), and the watches of the mouse buttons and of window input (`mouse_watch.*`), and the meaning of a process failure of a WebView2 (`process_failure.*`). The Go platform subscribes to `ProcessFailed` of the web view that `SetWebview` names, and the end of its browser process or its render process calls the `ended` that `SetWebview` received, on the UI thread; it writes any other kind to standard error. A framework adapter that sets a web view passes an `ended` that delivers the window event `WindowWorkbenchEnded` of its window, whose listener records `web_process_ended` and writes the error line as on macOS. No framework adapter sets a web view yet. Every other operation in `platform/windows/unsupported.*` returns an error of the form `<operation> is not implemented on windows`. Application startup fails on Windows at its first platform operation: Wails `Run` and Tauri `run` end with `window resize animation is not implemented on windows` and status 1 before any window opens. Linux has no implementation; `platform.Current()` and `platform::current()` return an error there.

`make check-host-files` runs `make check-windows-build`, which vets the sources of the Go language host library and of the Wails framework adapter for `windows/arm64` in the default and the diagnostics build.

`make check-host-files` also runs `make check-host-debug`, which compiles the sources and the tests of the three hosts and the three apps for macOS with the features and the tags of the debug apps. `make build-tauriv2`, `make build-wailsv3`, `make build-mygo`, and this check read that configuration from one definition in the Makefile.

## Main thread of the Wails host

No Go code runs on the main thread of the Wails host, in the host or in its framework. Go code runs on a worker goroutine locked to a thread other than the main thread. Each callback of the native code into Go (a delegate method, a script message, a menu action, a main-thread task) is a C function: it writes a record of its arguments, wakes the worker and waits in C. While it waits, the main thread runs only the C calls that the worker forwards for that step, and the callback returns the answer that the worker writes. A step that Go code starts (`application.InvokeSync`, `EnqueueUI`) dispatches a C function to the main thread that waits in the same way, and the goroutine that started the step forwards its C calls. A main-thread step of the Wails host is therefore the interval in which the main thread waits in C for one callback or one started step: a step that reads registry state of the host and calls native code stays one main-thread step, and each delegate answer stays synchronous. A forwarded call that enters a nested run loop (a modal dialog, a menu, a drag) can deliver another callback; the worker receives its record while it waits for the forwarded call, so the nested step ends inside the outer step. A callback that needs no answer, such as a script message or a commit notice, returns after it writes its record, and the worker hands the record to a goroutine of its webview: the records of one webview are handled in the order in which the main thread delivered them, and the records of another webview do not wait for them. The stall heartbeat is answered by a C function on the main thread, so the stall measurement keeps measuring the main thread. The main thread blocks asynchronous signals before the application run loop starts, so the Go signal handler and its signal stack do not run on it; a synchronous fault on the main thread cannot be blocked and ends the process. The main thread waits for the worker on a condition variable, which passes no priority, so the worker runs at the user-interactive class, the class of the main thread of an application.

The host blocks the signals through `BlockAsyncSignals` of the platform right before `application.Run`, on the main goroutine, which the framework locks to the main thread in its init: every signal except the synchronous faults SIGILL, SIGTRAP, SIGABRT, SIGEMT, SIGFPE, SIGBUS, SIGSEGV and SIGSYS. The kernel delivers a signal that is sent to the process, such as SIGCHLD, SIGINT, SIGTERM or SIGPROF, to a thread that does not block it, and each thread that the Go runtime creates starts with the mask that the runtime recorded when the process started (`initSigmask`), so `signal.Notify` and profiling keep their threads. The Go runtime sends SIGURG to the thread of a running goroutine to preempt it asynchronously (`preemptM`); while the application runs, no goroutine runs on the main thread, and the main goroutine, which runs there before and after the run loop, is still preempted at function calls. A process that the main thread starts inherits the mask; the host starts its child processes from goroutines, which run on other threads.

The header `native/darwin/src/main_thread.h` of the shared native library declares the two main-thread functions `hostRunOnWorker` and `hostRunOnMain` and the macros `ON_WORKER` and `ON_MAIN` that evaluate an expression through them; `native/darwin/src/main_thread.m` holds the functions that a framework adapter installed. The Wails framework adapter installs the functions of the Wails fork (`wailsRunOnWorker` and `wailsRunOnMain`) as these functions in an `init` of its darwin package, before the start of the library, so no file of the library names Wails. The start of the library requires both: before its first native call `Prepare` calls `RequireMainThread` of the platform, which fails with `main-thread functions are not installed` and the name of each missing function. A call of a function that is not installed ends the process with its name, because running the block on the calling thread would run Go code or a native call on the wrong thread. A test that runs the darwin layer without a framework adapter installs a test function for both in its `TestMain`.

`make check-host-files` checks the rule in the C code of the darwin layer of the Go language host library, the cgo preamble of each Go file and each Objective-C file of `packages/host/go/src/platform/darwin/` (`auditMainThreadCalls` of `scripts/check-host-files.mjs`, which reads the Go files with `go/parser` through `scripts/cgo-sources.go` and the C code from the JSON AST of clang, with the macros expanded and each called function resolved to the header that declares it). It fails when C code references a function that a Go file exports (`//export`) other than inside `hostRunOnWorker` or `ON_WORKER`; when Go code calls a function that a header of `native/darwin/src` declares, other than one of the functions that need no thread (`MAIN_THREAD_FREE`, each with its reason: dispatch pointer installation and queries before the host starts, the event ring and its clock, `sp_observe_flush`, `sp_phys_footprint`, `sp_diagnostic_reports_directory`, `sp_capture_clock`, `sp_capture_error`, `sp_facts_free`, `sp_ui_enqueue` and `sp_ui_enqueue_after`), instead of a `main_` wrapper; when a C function of the layer that Go code calls sends an Objective-C message, calls a native function, an `NS` function or a block, or calls another function of the layer that does, outside `hostRunOnMain` or `ON_MAIN`; and when a native function, an Objective-C message or a block runs inside `hostRunOnWorker` or `ON_WORKER`.

Reason: the application process holds JavaScriptCore VMs that WebKit and other in-process clients create, and the lock of a VM adds the thread that takes it, the main thread among them, to the threads that its collector suspends and scans. The collector copies the stack of each such thread from its stack pointer to the origin of the thread's stack and allocates a buffer of twice the summed size. Go code on the main thread runs on a goroutine stack that the Go heap holds outside the stack of the main thread, so the size `origin − sp` of a scan at that moment wraps, the allocation of the buffer fails, and JavaScriptCore ends the process in `pas_panic_on_out_of_memory_error`. The Tauri host needs no such rule: its main thread runs Rust on the stack of the main thread.

Rejected options: carrying script messages and script results through the scheme handler instead of WebKit script messages, because WebKit 7621 also creates the VM when a page stores a `CryptoKey`, which the host cannot prevent, and WebKit 7622 and later create no VM for these calls; a minimum WebKit version, because other in-process JavaScriptCore clients remain. Deferred delegate answers (`NSTerminateLater` for every quit, a refused close that Go repeats later, state that Go pushes into C beforehand) are also rejected, because a synchronous answer such as the surface hit decision of the input monitor reads the current state, and a pushed copy of it is stale.

## Memory pressure

The host owns one native memory pressure source, which starts with the host and is the single registration of the process (the public dispatch memory pressure source on macOS). It observes the levels `normal`, `warn` and `critical`, numbers each report with `seq`, and reports a change of level only. The document region consumer that clears back-forward caches ([native surfaces](native-surfaces.md#document-regions)) subscribes to it instead of owning a source and clears only on `warn` and `critical`. Each host sends every report to the main page of each window as the page event `memory-pressure` `{level, seq}` in the order of `seq`, without holding the thread that receives the report, so a page ends with the level in force. The [memory saver](plugins.md#memory-saver) consumes the event, and `core.tab.memory` reports it as `pressure`; a declared fault injection of the diagnostic builds sends a report for the checks, and a contract case holds both hosts to the same event.

Before the memory saver unloads a tab, the page reads the `interactionState` of each document region of the tab through the declared host method `documentInteractionState` (`DocumentInteractionState` in Wails, `document_interaction_state` in Tauri) with `{surface, document}`, the surface and the name of each document region that the surface attached and has not detached; the page records those names at each `documentAttach` and `documentDetach` reply and forgets them when it releases the surface. The host answers the public `interactionState` of the region's web view as base64, serialized session history that holds no document or process, or an empty string when the region has loaded nothing, whose serialized history holds no entry that a restore could take, or when the read yields nothing, for example because the web content process already ended; restoring the tab passes the value as `interactionState` of `documentAttach`, which restores it into the new region before its first load, and a value that the web view refuses fails the attach with `document <name>: <reason>` ([native surfaces](native-surfaces.md#document-regions)).

At each decision the page asks each document region of the tab with the declared host method `documentQuery` (`DocumentQuery` in Wails, `document_query` in Tauri) with `{surface, document}`. The host replies `{media, capture, form}`: `media` is whether the region plays audible media, `capture` is whether camera or microphone capture is active, and `form` is whether a frame of the region holds a form flag. A region that cannot answer, for example because it is closed, fails the call with `document <name>: <reason>`.

## Process lifecycle

A goroutine or a thread of a host starts only through its entrance: `routine.Go(name, fn)` in Go (`src/routine/routine.go`) and `spawn_named(name, body)` in Rust (`src/routine/routine.rs`). Go recovers a panic of `fn`, writes the message and the stack to the standard error, stores the event `host.panic` ([events](events.json)) with the `name`, the `text` of the panic value and the `stack`, waits up to 2 s until the event is in the event log, and ends the process with status 2. A panic before the writer is attached waits up to 5 s for the writer first, so the event enters the writer and is not left in the start buffer. When no writer attaches in that time, the record with its stack goes to the standard error in full. The Rust panic hook stores the same event with the name of the panicking thread (`<unnamed>` for a thread without one; the `text` is prefixed with `<file>:<line>: `, because a Rust panic value carries no location) and wakes a thread of its own, which waits until the writer is attached (up to 5 s; no wait when it is attached already), then up to 2 s until the event is in the event log, and ends the process with status 101. The Rust host installs the hook as the first action of the process, so a panic before the writer opens leaves the event in the start buffer, and the writer stores it when it opens. The wait ends when the writer attaches; the 5 s bound applies only when no writer opens, for example after a start failure before the writer exists, and then the record with its stack goes to the standard error in full. The hook never waits for the writer, so a panic of the thread of the interface does not hold that thread while the writer is stalled; the hook builds the backtrace on the panicking thread. The policy is the same in both hosts: a state that a panic left behind is not trusted, so a panic ends the process after its record and no mode continues after a panic. A panic on the thread of the interface whose process aborts before the writer wrote the queued event leaves the message on the standard error only. Only a thread whose start returns an error to its caller (the event writer, the performance sampler, the debug follower and the termination watcher of the Rust host) uses `std::thread::Builder` directly; its panic is recorded by the hook like the others.

A failure of a startup step ends the process with its message on the standard error and the status 1, in both hosts. The Tauri host does not return a failure of its setup steps to the event loop, because the launch callback of the event loop cannot unwind: the failure would abort the process and the system would show its crash dialog without the message.

The hosts own three child-process families, each with one rule.

**WebKit XPC die with the application.** WebKit ends a WebContent process when the connection to its application closes (`AuxiliaryProcess::didClose` ends the process), so the end of the application process ends its WebContent processes, and the hosts end no WebContent process themselves. A termination signal requests the normal quit on both hosts, so the windows save and the sidecars stop as for `host.quit`; a second signal ends the process when the quit does not end. `application_end_processes_test` checks that an application that ends through `-[NSApplication terminate:]` leaves none of the WebContent processes of its main web view and its document region, and that the native library offers no operation that kills a WebContent process.

A host that ends without its exit path leaves no WebKit process: launchd runs the WebKit services of an application in the launchd domain of its process and ends them when that process ends (measured on macOS 26.6.2: after `kill -9` of the host, its GPU, Networking and WebContent services ended within 0.2 seconds, twice in each host). A host therefore keeps no record of WebKit processes and ends no process at its start; a process list cannot tell the WebKit processes of this host from those of another application, and a start that ended listed processes ended those of the other applications that ran.

**A quit collects the tab sessions before the regions close.** The save of a window that a quit closes writes the session history of each tab with document regions to `tab-sessions/<tab>.json` ([memory saver](plugins.md#memory-saver)) before the page calls `windowClose`, so the host closes the document regions of the window only after the sessions are stored.

**A quit ends when a window keeps a modified tab.** A quit asks each ready window to close, and the page of a window that keeps a modified tab answers with the host call `windowCloseKept` ([plugins](plugins.md#tab-reports)). The host then ends the quit state: closing the last window afterwards does not quit the application, and the end of a WebContent process is an error line again. `host.window` reports the state as `quitting`.

**Persistent sidecars outlive the application and reconnect.** The persistent service keeps its sessions across application restarts and connection losses; a lost connection is revived at once and a dead service respawned ([persistent services](persistent-services.md)). The application never kills a persistent service on exit. Both hosts start a persistent service in a new session through the platform operation `NewSession` (Go) or `new_session` (Rust), so the service receives no signal of the application's process group or terminal.

**Non-persistent sidecars die with their window.** Removing a surface or closing its window sends the close notice; the process ends with the channel.

## Launch activation

Launch Services activates an application that it launches unless the launch requested no activation (`open -g`, `kLSLaunchDontSwitch`, or `NSWorkspaceOpenConfiguration.activates` false), so a host leaves the activation at launch to the system. A host does not activate itself when it finishes launching while another application is active: the Wails host sets `MacOptions.DisableActivationOnLaunch`, because Wails activates every application with the regular activation policy at launch by default, and the Tauri host sets `activate_ignoring_other_apps(false)`, because Tauri activates regardless of other applications by default, and the mygo host calls `App.SetSelfActivation(false)`, because mygo activates every application with the regular activation policy at launch and at each `Window.Show` by default. tao 0.37.2 still calls `activateIgnoringOtherApps(false)` with the Tauri setting, and that call activates the application when no other application is active, so the workspace uses a tao fork commit that makes no activation call with that setting (`[patch.crates-io]` of `Cargo.toml`). A person who opens the application sees it come to the front, and a background launch, such as the relaunch of `sok app relaunch`, leaves the frontmost application unchanged.

A window that a host shows goes through one rule, whose one value is whether the system holds the application as active (`NSRunningApplication.active`, not `NSApp.isActive`, which a virtual key window answers for). An application that the system holds as active makes the window key and orders it front. An application that the system does not hold as active leaves the front application and its windows where they are: the window goes directly above the frontmost window of the application, or behind every window when the application shows no other window, and becomes the key window of the application. A check and an endpoint run start the executable or `open -g`, so no activation arrives and their windows stay behind what a person uses, where a covered window is the normal case. A person who opens the application through Launch Services sees it come to the front: the activation brings the windows of the application forward, also a window that was shown before the activation arrived. A person who starts the executable from a terminal asked for no activation either, so the window opens behind the terminal. `sp_window_show` (`native/darwin/src/window_reveal.h`) holds the rule. The mygo host passes it to `App.SetWindowShow`, the Wails host to `MacOptions.WindowShow`, and the Tauri frontend calls it in place of `Window::show`, because tao orders every window that it shows front. `Focus` is the request of a person, a notification they clicked, and it activates. `activate: true` of `input.pointer` stays the one request of a check that activates, for the tier that a person checks.

The rule does not cover the restore of a minimized window. `deminiaturize:` orders the window above every other window whether or not the application is active. An application that is not active stays inactive and the front application stays front, so the restored window covers what a person uses. A person restores a window through the Dock, which activates the application, and the endpoint has no command that minimizes a window, so a check or an endpoint run does not reach this case and a host leaves the restore to AppKit.

A window on Windows goes through the same rule, whose one value is whether the foreground window belongs to this process. The Tauri host shows a window through tao, which holds its visibility, and a subclass of the window adds `SWP_NOACTIVATE` and `SWP_NOZORDER` to the position change of that show. The Go platform calls `ShowWindow` with `SW_SHOWNOACTIVATE`, and Wails does not call it yet ([features](../features.md)). This path has not run on Windows, so its effect is not confirmed.

## Application log

[Diagnostics](diagnostics.md) states every record, its form and where each failure leaves it. Every diagnostic file of an application is in one fixed folder, `logs/` under the configuration directory: the application log, the [performance trace](performance-trace.md), the service logs, the stall samples, and still captures and recordings in `logs/captures/`. A person who meets a defect hands over this folder.

Each host writes its records to the event log `logs/host-<boot>.jsonl` (the levels `error`, `warn` and `info`) and `logs/host-<boot>.debug.jsonl` (`debug` and `trace`) under the configuration directory ([logging](logging.md#files)) and its raw standard error to `logs/host-<boot>.stderr`, where `<boot>` is the start time in seconds and the process identifier. Right after the host creates its [endpoint](endpoint.md), which holds the process lock of the configuration directory, it starts the writer of the event log, opens the stderr file for appending with mode 0600, and makes it the standard error of the process through the platform standard-error operation; each run starts with the record `info host run: <application identifier> pid <pid>`. The stderr file holds only what no writer of the contract writes: the crash output of the runtime and the fatal lines of the native library (`<time> error native fatal: <name>`), which a signal handler writes with calls that a signal handler may make. The Wails host also writes the output of a runtime fatal error of Go to `logs/host-<boot>.crash` (`debug.SetCrashOutput`) and sets the traceback level `crash`, so after that output the runtime ends the process with `SIGABRT` and the system writes a crash report with the native frames of every thread; a fault in native code of the Tauri host ends the process with the signal of the fault, and the system writes the report. Output written before the endpoint exists goes to the standard error that the process was started with. The records of the host, the lines of the standard error of every non-persistent sidecar, which the host reads line by line, and the records that the page relays in a batch of the host call `log` are not lines of the stderr file: the host stores them as the events `<layer>.record.<level>` with the fields `where` and `text` in its [event log](logging.md#files), and a record written before the writer of the event log exists waits in a start buffer of 1024 records, whose refused records the writer counts in a `log.dropped`.

A workbench record has the layer `workbench`; its level is `error` when it states an error and `info` otherwise. The workbench reports in this form every error it shows in the main document, every unhandled error and promise rejection, every refused status change, every failed surface mount or background session, and every failed self verification (`error workbench verify: <n> fail — …`). The event log keeps each error record after a later reload removes the error from the document, so a window check judges every error occurrence from the event log. A page without a host writes a failure to its console as an error.

A host record that states an error has the level `error` and the layer `host`: `<where>` names the operation or the object that failed and `<text>` is the failure. Each host writes it as the event `host.record.error` through one helper (`LogError` in Go, `log_error` in Rust), and a site that both hosts have writes the same `<where>` and `<text>` in both. Each record that a record helper of a host writes (`LogError`, `LogWarn` and `LogInfo` in Go; `log_error`, `log_warn`, `log_info` and `log_failure` in Rust) carries the field `site`, `<file name>:<line>` of the call of the helper, so a record whose `<where>` and `<text>` several calls write names its call; the file name is the last component of the source path, so the site does not depend on the folder of the build, and it differs between the hosts because their sources differ. The native library stores its records as the events `native.record.error` and `native.record.info` through `sp_log_error` and `sp_log_info` in the ring of the process, and the writer of the host pulls them into the event log. A fatal failure after the log is open writes its record before the process ends and waits until the writer stored it. A host record of the level `info` is an observation, written as the event `host.record.info` through `LogInfo` in Go and `log_info` in Rust: it records an expected state and states that state, for example `exposure reply <id> of removed surface "<surface>" arrived after its request ended`, or `<operation> arrived after its request ended`, which a completion writes when its caller has already returned its own failure. A host does not write a failure as an observation. The requester that receives a failure of its request reports that failure, and nothing else writes a line for that failure; a host writes an error line only for a failure that no request reports. An image presentation timeout, for example, is the answer of the surface preparation or presentation request that waited for it, so neither host writes a line for it; the page's layout queue receives that answer and shows it as the record `error workbench surface presentation failed: <text>`, which is the only record of that failure. The layout queue answers a failed layout as failed, not as a rejection, to the code that scheduled it and to every wait for it, so a project switch or another command that waited for that layout, and a gesture whose layout no command waits for, write no line for that failure. The error output of the application framework goes through the same helper (where `wails`); the Tauri runtime has no logger installed.

A persistent service outlives the host that started it, so it does not inherit the host's standard error. When a host starts a persistent service, it opens `logs/<executable-name>.log` for appending with mode 0600 and passes that file as the service's standard error. The service writes its standard error in the form of the text record, with the layer `sidecar` and the name of the service as `<where>` ([sidecars](sidecars.md)).

When a host opens a log file of 100 MB or more, it first renames the file to `<name>.1`, moves the earlier generations `<name>.1` to `<name>.4` up by one, drops `<name>.5`, and starts a new file. A host opens a log file only when no other process writes to it: it opens the application log once per run while it holds the process lock, and a service log only when it starts that service. A run or a service appends without a size limit until the next open, so the next run or service start applies the bound.

A host that cannot open its application log or replace its standard error does not start, and it reports the error on the standard error that it was started with. A host that cannot open a service log does not start that service and fails the start with `sidecar <name>: service log: <error>`.

## Application arguments

An application accepts `--config-dir PATH` ([projects](projects.md#persistence)), written as two arguments or as `--config-dir=PATH`. Both hosts read the arguments with one rule before any window opens: an argument that the application does not declare fails with `unknown argument <argument>`, a flag without a value fails with `--<flag> needs a value`, and a repeated flag fails with `--<flag> is given twice`; the application writes the message to its standard error and ends with status 2.

A diagnostic build also accepts `--registry-ca PATH`: a PEM file whose certificate authorities the host's registry fetches trust instead of the operating system's ([fetching](installation.md#fetching)), so a window check can serve a local TLS registry. A file that cannot be read or holds no certificate ends the start with `--registry-ca <path>: <reason>` and status 2. A release build does not declare the argument and rejects it as unknown.

## mygo host

The mygo host is a third host, on the framework mygo. It draws the workbench in native UI, so a window runs without a main page. This section states the mygo host; [features](../features.md) records its implementation and each change of the Wails and the Tauri host that it needs. The [performance goals](#performance-goals) bound its costs.

### Costs of the main page

The Wails and Tauri hosts draw the workbench as a JavaScript page in one WKWebView per window (the main page). Plugin views, document regions and image regions are native views that follow the layout of that page. The measured costs:

| ID | Cost | Measurement |
| --- | --- | --- |
| C1 | Main page memory | 242 MB (Wails) and 291 MB (Tauri) after three days of use; 103.8 MB, peak 181.9 MB, in a window with one project, two sidebar sections and eight tabs; 446.6 MB (Wails) and 399.9 MB (Tauri) after reloads ([plugin processes](plugin-processes.md#reasons)) |
| C2 | Main page CPU | The main page process of each application stayed at 100% CPU after a failing draw |
| C3 | Main page graphics | About five window-sized buffers (71 MB at 1200×760) earlier; 20 MB at 1200×760 now, about 1.4 window buffers: the root tiles of the page and the layers of its surface documents |
| C4 | Processes of an empty window | An empty library-screen instance of the release Wails host costs about 208 MB: host 108, WebContent 54, GPU 32, Networking 14; the WebKit processes are 100 MB of it |
| C5 | Modals | The settings window and each menu are web views with their own documents ([native modals](native-modals.md)); a closed modal leaves no web view and no attached native object (`e2e/modal-release.test.mjs`), so their cost lasts while one is open |
| C6 | View processes | About 11 MB for each WebContent process of a small page, growing linearly with the number of views; an idle browser tab costs 53,808 KB on Wails (documents 29,040 KB, main web view growth 24,768 KB) and 45,504 KB on Tauri (documents 30,880 KB, growth 14,624 KB) against the bound of 51,200 KB of the idle tab benchmark (`IDLE_TAB_BOUND_KB`); the growth is a cost of the main page, which the host process takes on the mygo host |

| C8 | Terminal frames | On the Tauri host, in a window of 760×614 points that was not occluded, at a load average of 14 to 21, a status line updated every 33 ms costs 1.6 ms of application CPU per frame at 27.6 frames per second with the `term` plugin 0.0.4 and the sidecar `alacritty` 0.0.4, and 20 rewritten rows cost 3.1 ms at 27.5, with the CPU and the frame counts taken from separate runs of the same output; no record divides this CPU between the host, the view page and the sidecar; the `term` view page owns the screen state, the input and the exposure of the terminal |
| C9 | Divider drag of a `terminal` tab | At 120 Hz with the trace off: Wails latency median, p90 and worst 68.3, 97.6 and 127.4 ms and cadence 34.1 ms, Tauri 90.0, 141.5 and 196.6 ms and 33.7 ms, against 20.8, 25 and 33.3 ms and 33 ms; at a 60 Hz display mode: Wails 61.0, 88.7 and 116.9 ms and 34.2 ms, Tauri 66.8, 97.9 and 130.6 ms and 33.9 ms, against 41.7, 50 and 66.7 ms. The cohorts differ in display mode and load and do not attribute the latency to a stage |
| C10 | Browser documents | A document web view of a browser tab held 1.31 GB |
| C11 | Browser sections | The four sections of the browser plugin declare no `unload`, so they keep their views while hidden |
| C12 | Host process memory | About 154 MB in each host after three days of use; 108 MB on an empty library screen of the release Wails host; over 30 repetitions of `make measure-object-counts` the Wails host settles between 80 and 89 MB with 3 to 5 MB of Go heap objects and 50 to 52 goroutines, and the Tauri host between 70 and 76 MB |

C1, C4 and C5 are the cost of the workbench as a page: its state, its WebContent process and the WebKit processes that it starts. C3 is the graphics memory of that page; the native workbench replaces it with the drawables of its Metal layer (one window-sized buffer at rest, three while the window animates) and the memory that the Metal driver takes after a pause [S17]. Each layout transaction of C9 waits for the presentation of the main page, the presentation of each joined root view and the required image rasters ([placement sequence](native-surfaces.md#placement-sequence), step 4), and a layout reaches the screen across four frame boundaries (the input's arrival, the frame of the layout before it, WebKit's rendering update and the display refresh). The native workbench removes only the wait for the main page; a divider drag still waits for the root views that it resizes and for the rasters of their image regions, and G4 applies the latency targets of that drag to the mygo host unchanged. C2 is a defect of the main page, not a cost of the page, and the mygo host has no main page; G2 requires that a failing draw does not keep the mygo host busy. C6 and C7 are the cost of plugin views as web views, which the [plugin process decision](plugin-processes.md#decision) keeps. C8 is the cost of terminal frames that pass through the image region of a view page, a path that the mygo host keeps (D5) and that G5 bounds on the three hosts. C10 is WebKit's own document memory and is not a host cost. C11 is a declaration of the browser plugin, which that plugin corrects. C12 is the process that holds the state of the workbench on the mygo host.

### mygo facts (v0.7.4)

Every statement about mygo cites a source of [sources](#sources) as `[Sn]`, a bracketed number apart from the scenarios S0 to S16 of the benchmark, read at the tag v0.7.4; statements about purego and the Go runtime cite the versions that mygo requires.

#### Threading and native calls

- `mygo.go` sets `Version` to `0.7.4` and calls `runtime.LockOSThread()` in `init`, so the main goroutine runs on the thread that started the process [S1]. The module requires Go 1.27.3 and purego v0.11.1 [S3].
- mygo uses no cgo: native APIs are called at run time through purego (`dlopen` and assembly trampolines) [S4][S5]. Objective-C methods that AppKit calls are Go functions registered as callbacks, and purego callbacks are a scarce resource that is never freed [S4][S7]. A purego callback enters Go through `crosscall2` on the thread that calls it, and an Objective-C method is registered as a purego callback (`objc.NewIMP`) [S29].
- The main goroutine stays locked to the main thread; every platform method and every handler runs on the main thread, in Go; listeners run on the main thread and IPC handlers on goroutines [S6]. The main thread is the thread for which `pthread_main_np` answers true; `RunOnMain` runs a function at once on the main thread and otherwise posts it to the main thread and waits for it, and `await` processes native events through `Backend.Step` while it waits on the main thread [S2].

#### Windows, web views and native handles

- A window shows either a page or native UI (`WindowOptions.Content`). `Window.NewWebView` makes a web view only in a window that shows native UI, and fails with `errNoContent` in a window that shows a page [S11][S12].
- In a native-UI window the WKWebView sits in a flipped clip view (`MyGoClipView`) under the Metal surface in the content view. Native UI paints a hole (`OpHole`) where the web view shows, and the surface's `hitTest:` returns nil where the web view takes the pointer [S12][S13].
- `ui.WebView` places only web views that the window made: `surface.WebView` returns the native side of a `*mygo.WebView`, only the web view element paints a hole, and the window gives the placements of its web views (frame, clip and covers) to the surface in the frame that draws them [S14]. mygo has no element that places an arbitrary native view.
- The only public native handle is the window: `Window.NativeHandle` returns the `NSWindow` [S10]. The web view handle (`WebViewHandle`) is in an internal package [S10].
- mygo makes each web view with its own configuration and delegate (`createWebView`) [S10]; v0.7.4 has no operation that takes a `WKWebView` that another library created.
- The mygo surface view registers for file URLs and receives a dropped file itself, as an event of the content [S27].

#### Images

- `ui.NewBitmap` keeps its pixels on the CPU and on the GPU; `Update` replaces the picture and uploads the new pixels [S15]. The Metal renderer uploads the whole image with `replaceRegion:` when its version changes, after waiting for the frames in flight [S15]. The tree at v0.7.4 contains no use of IOSurface.

#### IPC

- The page bridge carries JSON messages; a `[]byte` value is a base64 string [S16]. A custom protocol handler gives the main thread its body in 256 KiB chunks [S16].

#### Application lifecycle

- `applicationShouldTerminate:` stops the run loop when the quit is accepted and returns `NSTerminateCancel`; mygo installs its own handler for the quit Apple Event in `applicationWillFinishLaunching:` [S8][S9].
- `applicationDidFinishLaunching:` activates the application when its activation policy is regular, and `Window.Show` activates the application; `Window.ShowInactive` shows a window without activation and without making it key [S9][S22]. `Window.OnReadyToShow` runs once a window created hidden drew its first frame [S22].
- `App.Run` calls `quitOnSignals`, which makes SIGINT and SIGTERM quit the application [S20]. The application delegate sets a notification center delegate (`MyGoNotificationDelegate`) when notifications are supported [S9][S21], and answers `applicationDockMenu:` with the menu of the mygo `Dock` API [S9].

#### Native UI rendering

- Native UI draws with Metal and lays out text with Core Text; text input uses `NSTextInputClient` [S18].
- A frame is drawn on request: a paused `CADisplayLink` ticks only while frames follow each other [S17]. A frame draws only what changed since its drawable was drawn (`gpu.Ages`, `scene.Differ`) [S17]. A settled window asks for no frame and arms no timer (`TestSettledWindowSleeps`); a small idle native-UI window takes 44 MB on macOS, and the counter example idles at about 0.005% of a core [S5].
- The Metal layer keeps one drawable at rest and three while a window animates, and a timer shrinks the drawables two seconds after the last frame; the Metal driver takes 30 to 45 MB of the process footprint for the first command buffer after a pause and returns it a second or two after the last frame [S17].
- A frame that changes the layer, or that a window showing web views draws, presents with the Core Animation transaction (`presentsWithTransaction`), so the web views move in the same transaction as the frame; such a frame is drawn even when nothing in it changed, and takes its drawable on the main thread after any fetch in flight. Other frames present as soon as the GPU has them, with a drawable that a presenter fetches on a thread of its own, so that the main thread does not wait for the display [S17][S26].
- The engine holds the frames of a window that is out of sight, and a frame request of such a window waits for the display link [S28].
- The engine describes every frame as an accessibility tree once assistive technology asks for a surface's content (`AccessibilityOn`) [S18]; the automation hook builds the tree when the automation plugin reads it. The element keys and actions are handed out only to the automation plugin, when the application links it and `MYGO_AUTOMATION` asks for it, and builds with the tag `mygo_noinspector` leave that hook out [S19].
- Measured native UI frames: 1,000 static labels take 397 µs per frame on the CPU renderer with no allocation, and a warmed view of 1,000 labels retains about 2.50 MB of Go heap; the measurement excludes native window and GPU memory [S23].

#### Maturity

mygo is at version 0.7.4; the history of the tag starts on 2026-09-26 [S25]. A version 0 module may change its API in any release.

### Native workbench

**Page mode gives no gain.** A mygo window that shows the JavaScript workbench as a page keeps the main page with its WebContent process (C1, C4, C5), its graphics memory (C3) and the wait for the presentation of the main page in each layout transaction (one of the three waits of C9). The gain requires the workbench to be drawn by the host in native UI: decision D1.

**mygo violates the main-thread rule.** The application process holds JavaScriptCore VMs as soon as a view page or a document region exists, and Go code on the main thread then ends the process in `pas_panic_on_out_of_memory_error` ([main thread of the Wails host](#main-thread-of-the-wails-host)). mygo runs every handler and every native UI build on the main thread in Go [S6]. The rule is met only by a change of the framework: U1 (D3).

**Native views need an element.** Plugin view pages, document regions and image regions are created by `native/darwin` (`sp_document_create`, `sp_region_create`) inside a `SurfaceHost` that `sp_surface_create` places in the window composition of the main web view ([`webview_geometry.h`](../../native/darwin/src/webview_geometry.h)). mygo places only its own web views [S14] and has no IOSurface path [S15]. The design therefore needs a native view element in mygo (U2) and a surface host without a main web view (N1) (D4).

**A view stands on device pixels.** The framework rounds each edge of a native view element to the nearest device pixel, as it rounds an edge that it paints. The mygo workbench therefore gives a view the slot as the layout states it, fractional or not, so the view and the lines beside it share their device pixels and no pixel of the card shows between them. `core.surfaces` states the slot as `declared` and the device pixels as `applied`. A check of this reads the device pixels across the edges of a view in a still (`e2e/view-edges.test.mjs`), because a comparison of rectangles passes a view that stands where it declared with a row of its card beside it.

**Costs that the native workbench adds.** The host process holds the state of the workbench in the Go heap, which the Go runtime collects at least every two minutes [S30], and, once assistive technology asks for it, the accessibility tree of every frame [S18]. The Metal layer keeps one window-sized drawable at rest and three while a window animates, and the Metal driver takes 30 to 45 MB for the first command buffer after a pause; both return about two seconds after the last frame, when a timer also releases the GPU instance buffers, the atlas, image and backdrop textures and the command queue, so the first frame after a pause takes its drawable inside a step, while the main thread waits, and builds those buffers, textures and queue again [S17]. A focused editable text field draws a frame every 530 ms for 30 seconds after it takes the focus, its text changes or its window becomes key, which keeps the drawables and the driver memory during those 30 seconds [S31]. A frame that changes the layer or the placement (box, clip or covers) of a web view or a native view element, or the placement of a native glass view, presents with the Core Animation transaction and takes its drawable inside a step, while the main thread waits, which costs a pass of the AppKit display cycle and a commit for each such frame [S17]; at v0.7.4 every frame of a window that shows a web view presents that way, even when nothing in it changed [S26], and U2 limits it to the frames that change the layer or a placement. Each step and each forwarded call is one exchange of two thread wakes between the worker and the main thread (U1): a frame that changes no size, layer or placement is 2 steps with 6 forwarded calls, and a pointer move is 1 step with 4 forwarded calls, 6 when the cursor changes, which on the mygo host follows a step of its own for the `hitTest:` that the pointer routing of `native/darwin` sends for each move (D3). Each Objective-C callback that the framework registers stays registered for the life of the process, a process holds at most 2,000 of them, and a registration past that number ends the process with a panic [S7][S32]. G2, G3 and G8 bound these costs; the `hitTest:` step runs only for a move that the event dispatch of the application delivers, so G2 and G8 measure it with HID moves of the real-input tool (`e2e/real/hid.mjs`).

### Workbench

`packages/workbench-mygo` (Go module, package `workbench`) draws the workbench with mygo `ui` widgets and layout. `src/layout` holds the Go layout model: the grid and card geometry of `packages/soksak` and the projects, spaces and tabs of `packages/workbench`, with their stored formats, the values of a card that the layout reads (the order of its tabs, its active tab, the tab name whose width the head measures, its text size and its sidebars with their fold state), and the fold stage of a card head. It imports no mygo package. A path of the mygo `ui` has no arc, so the outline keeps its arcs, as the shared cases and the page workbench state them, and the shell draws each quarter arc as one cubic, which stays within 0.03 % of the radius. The layout cases are JSON files in `docs/spec/cases`, which the tests of `packages/soksak`, `packages/workbench` and `packages/workbench-mygo` read. Screens: rail, library, cards and tab strip, sidebar frame and seats, menus, settings window, plugin screen, debug view, error display, modals. On the mygo host an interactive element is an element of the element tree of U4 whose actions include a press, an increment, a decrement, a value or an expansion (`ActionPress`, `ActionIncrement`, `ActionDecrement`, `ActionSetValue`, `ActionExpand` [S38]); the binder of `packages/workbench-mygo` connects each interactive element to a declared command and gives it its element name when it creates the element, and each visible state is a declared status. `core.workbench.audit`, and `audit(root)` of the plugin API with `unbound` of `core.surface.document`, list each interactive element that has no command or no element name as `{role, expose, command, text}` on every host, where `role` is an ARIA role name: on the mygo host the name that one table of `packages/workbench-mygo` gives each role of `ui.Role` [S38], and in a document the `role` attribute of the element or the implicit ARIA role of its tag, `textbox` for a `contenteditable` element. A modal of the mygo workbench is a part of the workbench, and its controls run their commands through the same binder. `packages/workbench` stays the workbench of the Wails and Tauri hosts.

The two workbenches implement one product, and three mechanisms hold them equal:

- **Declarations.** `packages/workbench-mygo` embeds copies of `exposure.json`, `shortcuts.json` and `workbench.json` of `packages/workbench`, which `make check-exposure` holds equal to their source as it holds `core-exposure.json` today. `make check-exposure` also applies rules 1 and 2 of the exposure check to the Go sources of `packages/workbench-mygo`: every status, command and element name that a Go source passes to the registry or the binder is declared, every declared status and command is registered, and every declared element name is given to an element. Its tests hold copies of `contributions.json` of `packages/plugin-api` and `environment.json` of `apps/mygo` under the same check.
- **Host calls.** `packages/workbench-mygo` calls the host handlers of the language host library only through one table, `hostCalls` in `src/host_calls.go`, which names each handler. The workbench runs each handler of `hostCalls` on a goroutine of its own and receives its answer in a later step, as each service call of the Wails host arrives on a goroutine of its own, because `SyncSurfaces` and `PresentSurfaces` wait for work that runs on the worker of U1; each such goroutine starts through `routine.Go` of the language host library, and a call whose order a specification requires, as the sends to one sidecar, starts only after the previous call of that order has finished. [Host parity](host-parity.md) proposition 1 reads that table as it reads `METHOD` and `COMMAND` of `runtime/index.js`: each name of each table has a handler of its host, and the three tables hold the same names except the calls that the rows B of the framework table list: the calls absent on mygo (the overlay calls of the native modal web views and the shape calls) and the calls only on mygo (the dialog background).
- **Behavior.** Proposition 8 of [host parity](host-parity.md) states that the three applications declare the same statuses, commands and element names and that every window check runs against the three applications, except a check whose subject is the main page or a modal web view, which iterates `MAIN_PAGE_APPS`; `scripts/check-hosts-same.mjs` decides it with the copy rule of `make check-exposure` and the rule of `scripts/check-e2e-host-parity.mjs`.

The element tree of the workbench (U4) gives the binder audit, element rectangles and element actions their answers, so the window checks run against the three applications through `endpoint.json`, except the checks whose subject is the main page or a modal web view. An element that the page keeps under `display:none`, such as a tab that its head hides, stands in the tree without a size: it keeps its index among the elements of its name, `element.rect` answers it with zeros, `element.act` presses it, and neither the pointer nor the keyboard stops at it.

The host sends a request to the workbench as the event `exposure-request` of the [relay](exposure.md#relay), which reaches the workbench through `Frontend.Emit` and `Workbench.Emit`. `Requests` in `src/requests.go` answers each request in a step of the main thread, where the command of a pressed element also runs, through `Registry.Answer`, and returns the answer through the host call `exposureReply`; a watched status sends its values through `exposureChanged`. `Registry.Answer` gives the answers and the refusals of the registry of the page, in the same order. An element request reads the element tree of the last frame in that step: a rectangle is the frame of the element in window points with `zoom` 1 and `document` `{x: 0, y: 0}`, `click` and `input` are the press and the value that assistive technology gives the element, and `dispatch` fails with `the mygo workbench has no DOM events`. The workbench calls `windowReady` when its first screen stands, and the host refuses a request before that with 1003, as it refuses a request to a main page that is not ready.

`Events` in `src/events.go` is the event writer of the layer `workbench` for one window. It has the queue, the bounds, the batch of one step, the clock anchor and the gate that [writers](logging.md#writers) states for the page, and its events reach the writer of the host through the host call `log`. The workbench of a window draws its `start` when the window is built; `workbench.start` states that moment as `started_at` and has the `url` `mygo://workbench`, because the workbench is no document. Every call of `Calls` that the page would record is the event `workbench.call`, every request `command.run` that names a command is the event `workbench.command`, and every error that the workbench shows or fails to relay is the event `workbench.record.error`. The writer reads the policy in force with the action `policy-read` once and follows the host event `log-policy`. The close of a window waits for the events that are queued. The writer holds a timer for the report of the counts of its gate only while a count waits and no batch is in flight; the end of a batch sends a count that is due or waits for the rest of the second. A failure of the writer itself cannot leave through it and is a host record of the place `workbench`.

### Native views

- **View pages and document regions** keep `native/darwin` (`sp_document_create`, document regions) and the view contract unchanged. The container of the surface hosts of a window lies in the native view of the window (U2), which fills the content of the window under the Metal surface; the workbench shows each surface through a native view element (U2) that paints a hole over it and computes the covers where the workbench draws over it, and the layout transaction sets the frames of the surface hosts, in the content coordinates of the window as on the other hosts, in the Core Animation transaction of the frame that draws the cards. Plugin pages, those built with a library and those that load WebAssembly among them, run in view pages unchanged, because the view page, its channel and the view contract are unchanged. The mygo host makes no web view through `ui.WebView`: mygo makes each web view with its own configuration and delegate [S10][S14], and a view page needs the configuration of `native/darwin`, with the soksak scheme handler and the script message handlers of the view channel ([`document_view.m`](../../native/darwin/src/document_view.m)).
- A frame reads the surface host and the web view of the view page of a surface when it draws, and places them later on the main thread, so a surface that closes in between would leave a frame with closed views. The surface list that the frame reads holds those views, and a surface that leaves the list keeps them until the next settled frame of the window, which started after it left. The view page that follows an ended one replaces its web view in the same way.
- A layout transaction hides a surface before its view document leaves and before the frame takes the keyboard from the views that left the frame, so `native/darwin` still finds what held the keyboard in the surface and gives it back when the surface shows.
- A window has no page to reload. A reload of the window (`host.window.reload`, `plugins-changed`, `core.plugins.apply`) ends the workbench of the window, builds it again and runs the start of a main page, so the host leaves the previous workbench as it leaves a previous page, and the new workbench receives a new `start`. The previous workbench ends its host calls with it, as the calls of a page end with its document: it makes no host call after its end and runs no answer of a call that it made before, so the answer of a placement that the start cancelled states nothing in the window.
- One container per window keeps one placer for each geometry: the layout transaction places every surface host in the content coordinates of the window, and `native/darwin` converts that frame into the coordinates of the container when it applies it (`webview_geometry.m`, `webviewSetFrame`), so a holder that mygo moved in the same frame would put the host in the wrong place.
- **Image regions** keep the `CALayer` of `image_region.m` with the leased IOSurface, so the lease's in-use rule, the color handling and the frame identity stay one implementation for three hosts, and the mygo renderer draws no frame for a terminal frame. Importing the IOSurface as a Metal texture is rejected: the mygo renderer would upload each terminal frame and draw a frame for it, and the lease rule would move into the framework.
- **Modals** (settings window, menus, dialogs) are native UI; the native modal web views are not created by the mygo host. While a dialog is open the workbench draws black at 50% opacity over itself, blurred by 3 points, and the host call `setDialogBackground` with `{enabled}` has the host blur each document web view and image region as it does for a modal web view of the mode `dialog` ([regions](native-surfaces.md#regions)).

### Framework changes

The mygo host pins a framework fork with a go.mod `replace`, as the Wails host pins its Wails fork. Each change is a change of the framework's packages; each is verified by a test in those packages and by the core item that uses it.

| ID | Change | Reason |
| --- | --- | --- |
| U1 | Main-thread worker: Go code runs on a goroutine locked to a thread other than the main thread. The worker starts in `App.Run` before `Backend.Init` and ends when `App.Run` returns. `App.Run` runs its Go code before the run loop (`Backend.Init`, the settings made before `Run`, `quitOnSignals` and `Signal`) as one step, and `finish` with its `OnQuit` listeners as another step. The main goroutine starts each step through the function that runs a block on the worker from the main thread, so the main thread waits for each step on its own stack and meanwhile runs the calls that the worker and other threads forward to it. A callback that reaches the main thread during those steps runs on the worker as a nested step. Each Objective-C method and block that mygo makes through purego (`objc.RegisterClass`, `objc.NewBlock`) and each C callback that it passes (`purego.NewCallback`) enters through an assembly trampoline of mygo: after `objc.RegisterClass`, mygo sets the implementation of each method of the class to a trampoline (`method_setImplementation`); mygo replaces the invoke function and the dispose function of the descriptor of each block it makes with trampolines; and mygo passes a trampoline in place of each C callback pointer. A trampoline calls the function that purego made for it, and purego is unchanged. Called on the main thread, the trampoline stores the argument registers, wakes the worker through a Mach semaphore and waits; while it waits, the main thread runs only the calls that are forwarded to it, those of the worker for that step and those of other threads, and returns the answer that the worker writes. Each step runs in an autorelease pool of the worker that the worker drains when the step ends; before that drain the worker retains an object that a callback returns to its caller and autoreleases it through a forwarded call in the pool of the main thread, so that the drain of the worker pool does not deallocate an object that the callback autoreleased on the worker and the autorelease on the main thread does not take a reference that the callback did not give. Called on another thread, the worker among them, it enters Go on that thread. During a step the worker counts as the main thread for `onMain`, `RunOnMain` and `await`, and `await` forwards `Backend.Step`; a forwarded call that delivers another callback (a modal panel, a menu, a drag, `makeFirstResponder:`, which sends `resignFirstResponder` and `becomeFirstResponder`) runs that callback on the waiting worker as a nested step that ends inside the outer step. ### Decisions

Each decision states what the mygo host does and why.

- **D1 Native workbench.** The mygo host draws the workbench in native UI. Reason: page mode keeps C1, C3, C4, C5 and the wait for the main page in C9 (see [native workbench](#native-workbench)).
- **D3 Main-thread worker by assembly trampolines (U1).** Go code of the mygo host runs on a worker thread; each callback that AppKit makes on the main thread enters through an assembly trampoline that hands the step to the worker, and the main thread runs the calls that are forwarded to it. Reason: the [main-thread rule](#main-thread-of-the-wails-host) holds only when no Go code runs on the main thread; a purego callback runs Go on the thread that calls it [S29], AppKit calls the methods that mygo registers on the main thread [S4][S6], and mygo builds without cgo [S5], so the C worker of the Wails fork cannot be the mechanism, and the step with its forwarded calls is the one that the Wails host runs for every callback. The cost of U1 is, for each step and for each forwarded call, one exchange of two thread wakes through a Mach semaphore and the return of the worker from a native wait, which needs a P of the Go scheduler: when sysmon took the P of the waiting worker and no P is idle, as during a garbage collection mark phase, the worker waits on the global run queue until a thread schedules it. A frame of a window whose content changed, without a change of the window size, the layer or a placement, is two steps, the tick of the display link and the callout of the run loop observer that each frame arms, with 6 forwarded calls: the bounds of the superlayer twice, the occlusion state twice, and the layer and its display flag in the tick; a frame that resumes the display link adds its `setPaused:`. The surface keeps the size of the view, the scale of the window and the refresh rate of its screen until AppKit tells of a change, so a frame reads none of them. A frame that presents with the transaction, which U2 limits to a frame that changes the layer or a placement, adds the `present` of its drawable, and a changed placement of a mygo web view adds 4 calls. One change of the window size in a live resize is five steps, `setFrameSize:`, `windowDidResize:`, `wantsUpdateLayer`, `updateLayer` and the callout of the run loop observer that the frame of `updateLayer` arms, with 13 to 15 forwarded calls together and four nested steps of the `isFlipped` that the `setFrameSize:` of `NSView` sends to the surface view, a pointer move is one step with 4 forwarded calls and 2 more when the cursor changes and a nested step of the `isFlipped` that its `convertPoint:fromView:` sends, and on the mygo host, while a view page is registered for input, a second step before it, the `hitTest:` of the mygo surface view that the pointer routing of `native/darwin` sends to the content view for each move, with its own forwarded calls and a nested step of the `isFlipped` that the `hitTest:` of `NSView` sends; a key is one step with 5 forwarded calls, the `release` of the array that hands the event to `interpretKeyEvents:` among them, in which each callback of the input method is a nested step [S33]. Shaping text forwards a call only for the first use of a system font style [S34]. A framework test holds, in a window that holds no web view, as no window of the mygo host holds a web view made through `ui.WebView`, the forwarded calls of each kind of step at most at 15 for a frame, 20 for the steps of one change of the window size, 6 for a pointer move and 7 for a key, and G8 bounds the frame, the pointer step and the steps of a resize at one display period at 120 Hz (8.33 ms), forwarded calls included, in the final phase.
- **D4 Image regions as native layers.** The native view of a window (U2) holds the container of its `SurfaceHost`s, and image regions keep their `CALayer` with the leased IOSurface (N1). Reason: one lease implementation for three hosts, and the mygo renderer draws no frame for a terminal frame.
- **D5 Terminal surfaces keep their view page.** The `term` plugin keeps its view composition with one image region (`input: "dom"`) on the three hosts. Reason: the view page owns the screen state, the input and the exposure of the terminal (C8): its overlays, tab reports, clipboard, links, settings, theme and text size calls, shortcut forwarding and element names. A surface shows a page of its plugin, and the layer of a screen is not chosen by measurement ([plugin processes](plugin-processes.md#layer-rules)).

## Performance goals

The goals G1 to G8 state the costs of the mygo host beside the Wails and the Tauri host. The [three-host benchmark](../operations/examples.md#three-host-benchmark) measures them in its scenarios S0 to S16, and `make check-b3` judges each session of it. The other hosts are the Wails and the Tauri host built from the revision of the mygo host, and the baseline hosts are the Wails and the Tauri host built from the baseline revision that the benchmark defines. `docs/spec/performance-goals.json` holds the numeric bounds of the goals; the two tables of this section are copies of that file, which `scripts/test/performance-goals.test.mjs` holds equal to it, and the idle tab and the split load benchmarks read `IDLE_TAB_BOUND_KB` and `SPLIT_LOAD_GROWTH_BOUND_KB` from it. A value that [plugin processes](plugin-processes.md#pass-values) or [native surfaces](native-surfaces.md#acceptance-criteria) defines is not copied into the file: the benchmark that holds it judges it, and the judge reads only the verdict of that benchmark.

The judge applies these rules:

- A session holds the runs of each application that the condition table states, and a run starts only under the conditions of that table; `make benchmark-b3` fails a run whose conditions do not hold.
- A value judged by its median is the median of its runs; a value judged in each run fails when one of its runs fails its bound. The spread of a value is the range of its runs.
- A bound applies to the values of the mygo host.
- A value that a host records in no run is printed as `not measured`, unless a criterion needs it of that host, which fails. It is neither a pass nor a failure of that host. On the Wails and the Tauri host `frames` and `commandBuffers` of `host.window` are null, so `G2-S0-frames` of those hosts is `not measured`, and an idle wait over their windows reads no frame.
- A value compared with each other host and baseline host fails when the spread of the mygo host lies wholly on the bounded side of the spread of the same value of one of these hosts: its lowest run above the highest run of that host for a time, a CPU time or a footprint (`s`, `ms`, `KB`), and its highest run below the lowest run of that host for a frame rate (`frames/s`). The same value of an other host is a regression when its spread lies wholly on the bounded side of the spread of the same value of its baseline host in the same sense, and a regression fails the session.
- A value compared with another value of the mygo host fails when its spread lies wholly above the spread of that value.
- A value of the unit `verdict` is the verdict that the benchmark of its row recorded for the run.

The values of each goal:

- **G1 Process set.** A window that has shown no view since the start of the application runs no WebContent, GPU or Networking process. A WebKit process starts only when the first view page or document region is shown. After the last web view of the application closes, every WebContent process of a view page or a document region that the application held exits within the time of pass value (ii) of [plugin processes](plugin-processes.md#pass-values); S0b counts the processes that remain after `diagnostics.process.exit` of each such process. A GPU or Networking process that WebKit keeps after that is a cost that G3 counts in S0b. This criterion changes only through an adversarial review that states the evidence.
- **G2 Idle.** With `cursor.idleTimeout` of every `term` and `terminal` tab at the default that the manifest of its plugin declares, after the last input, the cursor idle timeout of each such tab, 3 seconds without a change of `frames` of `host.window` and the time a count of the gate waits for its write ([logging](logging.md#policy)) after the last request of the measurement, every window of S0, S1, S9 and S12 presents no frame and commits no Metal command buffer during 240 seconds: the frame and command buffer values are the largest change of `frames` and of `commandBuffers` of `host.window` among the windows of the scenario over that interval, and the CPU value is the CPU time of the host process over it. In S0 and S1, in a window brought to the front by `bringFront` of the real-input tool, the summed footprint after a pointer move across the window by HID moves of that tool is compared with the summed footprint before that move. In S12 the layout draw that fails writes one `error:` line of its fault to the application log, and the values of S1 then hold.
- **G3 Memory.** A footprint is read after the readings of every process settle (two consecutive readings 5 seconds apart differ by less than 1,024 KB) and at least 3 seconds after the last frame. In S0 and S0b the value is the summed footprint of the host process and of every WebContent, GPU and Networking process of the mygo application, and the footprint of the host process alone of an other host or a baseline host; the sidecar processes, which run the same sidecar builds on every host, are printed apart from that sum. In S1 the value is the summed footprint of the application less its main page process. In S5 and S13, on applications started for the scenario, the values are the sums over the processes of the application of the lifetime peak footprint (`phys_footprint_peak` of `footprint`), read before and after the drag that runs without capture; a peak after the drag above the peak before it is the cost of the drag. In S11 and S15 the value is the footprint that the second window or the open settings window adds to the application. In S14 the value is the summed footprint, read 10 seconds after the key while the caret blinks, without the settle rule and without the rule of the last frame. In S3 the changed counts are the counts of `diagnostics.objects` outside its `runtime` member, the workbench elements, the native view elements and the registered framework callbacks among them, that differ after a repetition from the second on from their value after the first repetition, and the growing figures are the figures among the host footprint and the Go runtime figures except `heapReleasedBytes`, which counts memory returned to the system, whose lowest value over repetitions 21 to 30 is above their highest value over repetitions 11 to 20. In S4 the host footprint after 60 minutes without input is compared with the host footprint of S1. In S10 the value is the growth of the resident set size of the host process over the rounds of the split load benchmark. A figure without growth fails the growth rule of S3 by chance in 1 of 184,756 runs (1/C(20,10)).
- **G4 Views and gestures.** Every pass value of [plugin processes](plugin-processes.md#pass-values) ((i), (ii), (iii), (iii-b), (v), (viii)) applies unchanged to every plugin view on the mygo host. The DOM mount baseline of (iii) and (iii-b) on the mygo host is the lower of the baselines of the Wails and the Tauri host, as (iii) states; the `term` view and each section view have no recorded DOM mount baseline and are judged against the limit alone that (iii) states for a plugin without a recorded value. On the mygo host, (viii)(a) applies to the view of the tab of S5 in every recorded frame of its maximise and restore. The [performance targets](native-surfaces.md#performance-targets) and the catch-up limit of a maximise and restore in the [acceptance criteria](native-surfaces.md#acceptance-criteria) of native surfaces apply unchanged. The benchmark of each G4 row judges these values, and its verdict is the value of the row. A measured floor changes a target only when the floor of each of the three hosts exceeds it, and only through an adversarial review that states the evidence.
- **G5 Terminal.** In a `term` tab in a window of 760×614 points that is not occluded, for a status line and for 20 rows rewritten every 33 ms, the CPU value is the application CPU time divided by the frames that the region presented in the same interval, and the frame rate is the frames per second that the region presents.
- **G6 Browser.** The cost of an idle browser tab on the blank page is the settled footprint of every document process of the tab plus the settled growth of the host process, and its document part is the settled footprint of the document processes. A bound that a later review derives applies only to runs after the review that states it, for every host.
- **G7 Input.** For the 24 keys of the two configurations with the trace off and the default gate, the values are the median and the 90th percentile over the keys of one run of the time from an injected key to the shell prompt, for a `terminal` tab and for a `term` tab.
- **G8 Gesture CPU and frame time.** The CPU values are the summed CPU time of the processes of the application over the drag of S5 and of S13 that runs without capture under the default policy, which the view drag benchmark delivers on every host through `diagnostics.drag` with `native: true` and the plan of the captured drag, and over the pointer move of `STEP=pointer` in S1. Under the policy that stores the class `frame` at `debug`, the frame values are the 90th percentile of the time from the start of a frame to its presentation request less the time the frame waits for a drawable, and the step values are the 90th percentile of the step of each pointer move with its forwarded calls, over the drags of S5, S13 and S16 and over the maximise and restore of S5 without capture. The first-frame values are the time of the first frame of the drag of S5 and of S13, which follows at least 3 seconds without a frame, from its start to its presentation request with its wait for a drawable. The pointer-move value is the 90th percentile, over the moves delivered in the pointer move of S1, of the outermost `mouseMoved:` step together with the `hitTest:` step right before it when there is one; a nested step is part of the step that contains it. The pointer move of S1 is delivered with `input.pointer`, which reaches the window without activating it. Each 90th percentile and each first-frame time is taken over the frames and steps of one run, and their bound is one display period at the refresh rate of the condition table. Over the maximise and restore the step values take every step of U1, not only a pointer move. The first-frame values include the wait for a drawable, because no frame is in flight before the first frame and the timer of [S17] released its drawables, buffers and textures. S16 bounds a drag during a collection, because the worker of U1 needs a P of the Go scheduler for each wake and a collection holds the idle Ps.

A value is never lowered because it is hard to meet; a measured floor that exceeds a value changes it only through an adversarial review that states the evidence.

## Structure checks

`scripts/check-host-files.mjs` compares six pairs: `packages/host/go` with `packages/host/rust` and `packages/sok/go` with `packages/sok/rust` by the [language table](#language-table), and `packages/host/wailsv3` with `packages/host/tauriv2` and with `packages/host/mygo`, and `apps/wailsv3` with `apps/tauriv2` and with `apps/mygo`, by the [framework table](#framework-table). It compares `.go` and `.rs` files by relative path without extension and other files by relative path. A file present on one side passes only when a row of the table of its pair lists it, a row whose ID starts with the letter of the pair (H for the host packages, C for the command lines, A for the applications). The check reads files that Git tracks or would track, so generated `src/frontend/` files are not compared.

The audits of the check that select files by a path prefix fail when one of their prefixes selects no file: the main-thread audit takes `packages/host/go/src/platform/darwin/`, the undecoded command argument audit takes the Rust sources of `packages/host/tauriv2/src/`, and the stub check takes the `src` folders of the language host libraries, of the framework adapters and of `native/darwin`. The library import audit fails when a Go file of `packages/host/go` imports a package of Wails or its `go.mod` requires Wails, and when a Rust file of `packages/host/rust` names a crate of Tauri or its `Cargo.toml` depends on one. The library name audit (`auditLibraryNames`) fails when the code of a source or a test of `packages/host/go` or `packages/host/rust`, outside its comments, has a word that names a framework or its host, and when a contract declaration of those files has one; a word is a part of an identifier or a string split at underscores and at a change of case.

`scripts/check-platform-files.mjs` reports these outside `platform/<os>/`: file names with an OS suffix (`_darwin`, `_windows`, and others), Go `runtime.GOOS` and OS build tags in Go files, Rust OS `cfg` attributes in Rust files, and executable Node `process.platform` member expressions in JavaScript files. JavaScript is parsed as syntax, so strings and comments are not selectors. The only metadata exceptions are `process.platform` as the `platform` property returned by the `environment()` function and the test assertion `assert.equal(result.environment.platform, process.platform)` (or `assert.strictEqual`); all other executable occurrences remain findings, including selectors inside test paths. It skips `native/<os>/`, `scripts/check-tools.sh`, `platform/platform.{go,rs,js}`, and itself. It does not read `Cargo.toml`, so target-specific dependency tables are allowed.

Platform-dependent tests live under `tests/platform/<os>/` in their owning package or the equivalent `platform/<os>/` directory for root scripts. Their Cargo targets or test-runner paths are declared explicitly. Tests in common directories cover behavior that does not select or assume an operating system.

## native/darwin

`native/darwin` is the shared macOS library that both hosts call. Its minimum macOS version is 14.4, because `capture.m` calls `SCShareableContent getCurrentProcessShareableContentWithCompletionHandler:`, which macOS 14.4 introduced. The Makefile declares it in `MACOS_MINIMUM` and builds the library and both applications for it; `Info.plist` of both applications declares it in `LSMinimumSystemVersion`, and `apps/tauriv2/tauri.conf.json` in `bundle.macOS.minimumSystemVersion`, because the Tauri bundler builds the application for that value. `make check-release` fails when a bundle declares another value, when an application executable is built for another macOS version, or when another executable of the bundle is built for a newer one. Every bundled Rust executable uses the same declared Cargo deployment target as its application, so shared dependencies do not acquire different build identities solely from the deployment environment. Every compile and every external link of the repository uses this one declared value, and no build command writes the version again: the root Makefile passes `MACOS_MINIMUM` to the Makefile of `native/darwin` for each clang call and for the ZXing configure, which passes it to the Makefile of the process identity package for its clang calls and the Cflags of its pkg-config file, and each of the two reads it from the root Makefile when it runs alone, every Go command runs with `MACOSX_DEPLOYMENT_TARGET` and with `-mmacosx-version-min` in `CGO_CFLAGS`, every Go command that links passes the value to the external linker through `-extldflags`, and every Cargo command runs with `MACOSX_DEPLOYMENT_TARGET`. A linker warning that an object was built for a newer macOS version than the link therefore means that a compile or a link took another version, and the build or test that printed it fails with the object and both versions. The warning of ld that it ignores a repeated `-lobjc` does not fail a build: cmd/go adds `-lobjc` to the link for each package with Objective-C files, the link of the Wails host holds two such packages, and no link flag of the repository names `-lobjc`.
