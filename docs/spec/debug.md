# Debug view

[한국어](debug.ko.md)

The debug view lets a person who meets a defect hand over every diagnostic record of the application. Every diagnostic file of an application is in `<config-dir>/logs/` ([diagnostics](diagnostics.md)) ([hosts](hosts.md#application-log)); the debug view records the current state into that folder, lists its files, and saves one file or all of them where the person chooses.

## Opening

The Help menu of both hosts has 디버그 (Debug) ([host contract](host-contract.md#application-menu)). It runs `core.debug.open` in the main page of the application's main window, the same window as the text-size items of the View menu ([text size](text-size.md)). The view is a `dialog` [native modal](native-modals.md) that closes with its × button (`core.debug.close`); opening it closes the settings modal, and opening the settings modal closes it. A page without the application host has no debug view, and `core.debug.open` fails there with an error.

Opening records the state, then lists the files:

1. The page collects the value of every status that its registry serves, core statuses and the statuses of every surface, by name and surface, and sends them with the host call `debugRecord({page})`. A status whose read fails is recorded with its error.
2. The host writes `logs/state-<time>.json` with `{time, host, versions, windows, page}`: `host` is `wailsv3` or `tauriv2`; `versions` holds the core version, the macOS version and the content of `plugins/installed.json`; `windows` holds, for each window, `windows.list` entry, `host.window`, `host.sidecars` and `host.screens`; `page` is the value the page sent. `<time>` is the UTC time `YYYYMMDDTHHMMSSZ`. After it writes a state file, the host removes the oldest `logs/state-<time>.json` files beyond the newest 20, so the folder keeps a bounded number of them.
   After it writes the file, the host removes the oldest `logs/state-<time>.json` files beyond the newest 20, so the folder holds a bounded number of them.
3. In a diagnostic build the host writes a still capture of each window to `logs/captures/`.
4. The host call answers `{path}`, the path of the state file relative to `<config-dir>`.

A failure of a step is shown in the view through the error display and the other steps still run.

## Files

The host call `debugFiles()` answers `[{path, size, modified}]` for every file under `<config-dir>/logs/`, sorted by `path`: `path` is relative to `<config-dir>`, `size` is in bytes and `modified` is the modification time in milliseconds since the epoch. The view lists each file with its size and time, newest first (by `modified`, then by `path`), and a 저장 button, and has 모두 저장 above the list.

- `core.debug.save {path}` runs the host call `debugSave({path})`, which shows the macOS save panel with the file name and copies the file to the chosen place. It answers `{saved}`, the chosen path, or `{saved: null}` when the person cancels. A `path` outside `logs/` or of no file is refused with an error that names it.
- `core.debug.save-all` runs the host call `debugSaveAll()`, which shows the save panel with the name `soksak-<host>-debug-<time>.tar.gz`. When the person chooses a place it answers `{saved, total}` at once, `total` the bytes of the listed files, and writes a gzip-compressed tar file of `<config-dir>/logs/` on a thread of its own, so the page and a reload of it never wait for the write; a cancelled panel answers `{saved: null}`. While it writes, the host sends the window that asked the event `debug-save-progress` `{saved, written, total}` each time at least 1 MiB more of the listed bytes is written and once after the last file, and then the event `debug-save-done` `{saved, error}`, `error` being `null` or the text of the failure. A `debugSaveAll` while a write runs is refused with the error `debug: a save of the logs folder is running: <path>`. While the operation runs, the view shows a progress bar of `written` of `total`, shows the 모두 저장 button disabled, and refuses `core.debug.save-all` with that error; a failure that `debug-save-done` reports is shown through the error display path.
- The host call `debugSaveText({name, text})` saves text that the page built (for example the selected rows of the timeline): the host refuses a `name` that is not a file name (empty, `.`, `..`, or holding `/` or `\`) and a `text` that is empty or over 16 MiB with an error that names what it found, shows the save panel with `name`, writes the text to the chosen place, and answers `{saved}` like `debugSave`.
- <a id="following"></a>The host publishes a notice after the index of an event file covers lines that announce a change of the log ([index](logging.md#index)): to every window as the host event `debug-log-changed {path, size, notices, coalesced}`, and to the watchers of the host status `host.log` of the endpoint ([exposure](exposure.md#host-entries)) as its value, which has the same members. `path` is the file (`logs/<name>`), `size` its size in bytes, `notices` the number of notices published since the start, and `coalesced` the number of announcements that were folded into a later notice instead of getting one of their own. The source of the notice is the update of an index: the thread that the write of the writer wakes, and every query that brings an index up to date (the lines of a file that no writer of the host wrote, a file of a sidecar, are announced when a query indexes them). The publication is bounded: at most one notice per 250 ms, and the announcements that arrive while a notice is published or the 250 ms run out become one notice with the latest path and size, counted in `coalesced`; the wait is a timer because no event source can space the notices of a log that grows at any rate. A line announces a change except the record of a call that only reads the log (`host.binding.call` of `logQuery` and `host.endpoint.call` of `log.query`): the view follows by asking `logQuery`, the host records each call as an occurrence (it is stored, indexed and returned by every query, and is not dropped), and the announcement of that record would ask again for ever. The record of a read is shown by the next notice that other lines cause; the page also does not store its own `page.call` of `logQuery`. A view that follows the files asks for the rows that grew with `logQuery` ([timeline](#timeline)); a client of the endpoint watches `host.log` and queries `log.query` with `since` after a notice.

## Viewing

When the person views an image, the native modal has the height of the card that holds the loaded image: the image has no height before it loads, so the view places the modal again when the image reports its load.

Each file has a 보기 button and a 저장 button, in the same columns of every row. `core.debug.view {path}` runs the host call `debugRead({path})`, which answers `{path, size, truncated, kind, text}` for a text file or `{path, size, truncated, kind, image}` for a PNG file. `kind` is `text` or `image`. For a text file, `text` is the content of the file, or its last 262144 bytes (starting at a character boundary) when the file is larger, and `truncated` is true in that case. For a PNG file, `image` is the `data:image/png;base64,` address of the whole file and `truncated` is false. A `path` outside `logs/`, of no file, of a PNG file larger than 16 MB, of a file named `.png` that does not start with the PNG signature, or of another file whose content is not UTF-8 text is refused with an error that names it, and the view shows that error. The view shows the text or the image with the path and the size, says `앞부분 생략` when `truncated` is true, and has a 목록 button that runs `core.debug.list` and shows the list again. The text keeps the order in which it was written, the oldest line first, and the view opens scrolled to the end of the text, where the newest lines are.

## Timeline

The 타임라인 button above the list runs `core.debug.timeline`, which shows the events of the event files of `logs/` as one list of rows. The view never reads an event file: it asks the host for one page of rows with the host call `logQuery(request)` ([logging](logging.md#query)), whose request and answer are those of the endpoint method `log.query` ([endpoint](endpoint.md#log-query)), and pages through the files with the cursor of the answer. The page never loads or draws a whole file; a log of 1,000,000 events opens as one page.

- The timeline opens with the newest page: the query `{channel, order: "desc", limit: PAGE_ROWS}` with the filter below, where `PAGE_ROWS` is 500. The rows of the page are shown oldest first, in the order of the key of a row (`ts_us`, `role`, `boot`, `seq`), and the view opens scrolled to the end, where the newest rows are. The 이전 행 button runs `core.debug.timeline.older`, which asks for the page before the oldest shown row (`after` is the `next` of the earlier answer) and puts its rows in front of the shown ones; the button is hidden while no older row exists. The view holds at most `HOLD_LIMIT` (2000) rows. `core.debug.timeline.older` at that count is refused with the error `the timeline holds 2000 rows; narrow the filter or the time`, shown in the view.
- Each row is one text line: the UTC time with microseconds, `level`, `layer`, `event`, `window=`, `surface=`, `session=` and `cids=` when present, and each field as `name=<JSON value>`. A file that breaks the event structure fails the query with an error that names the file and the line, and the view shows that error; the view shows no row of the rest.
- `core.debug.timeline.filter {channel, level, class, layer, text, event, event_prefix, surface, session, cid, run, from, to}` sets the filter and asks for the newest page again; a member that is not given keeps its value and at least one is required. `channel` is `other`, `debug` or `all`; `level`, `class`, `layer`, `text`, `event`, `event_prefix`, `surface`, `session`, `cid` and `run` are the parameters of the same name of the query, and an empty text leaves a member open; `layer` is `all` or a layer. `from` and `to` are inclusive UTC times like `2026-10-08T22:53:20.123456Z`, or empty. A new timeline starts with `other`, `trace`, `all` and no other member. The view has a selection box for the channel, one for the level, one for the layer and a text field for each of the others, each pointing to this command, and a 목록 button that runs `core.debug.list`. A value that the query refuses is shown with the error text of the query ([logging](logging.md#query)); the shown rows stay.
- Each row has two buttons before it. `core.debug.timeline.context {row}` brings the rows around the row at position `row` (counted like `select`) into the held rows: the view asks `logQuery` for the `CONTEXT_ROWS` (5) rows before it and the 5 rows after it in the channel of the filter without the other members of the filter, and the rows that it did not hold are shown as context, with two spaces before the line and `context` true in the attribute `data-context`. A row that a page of the filter brings later, from following or from older rows, is a row of the filter from then on and loses the indent; a new filter or a new timeline shows only the rows of its own page. The status counts the rows that are only context in `context`. `core.debug.timeline.select {row, selected}` selects (`selected` true) or unselects (false) the row at position `row` among the rows that the view holds, from 0, in the order above, at the time of the call; a `row` that is not one of the rows and a `selected` that is not a boolean are refused with an error that names what was found, and the same call again changes nothing. The selection belongs to the row, which its process and `seq` identify: it stays when the filter changes, when older rows come in front and when following sheds rows, and it ends when the timeline is shown again.
- <a id="timeline-following"></a>The timeline follows the event files while it is shown. The answer of the first page holds `tail`, the greatest `seq` of each process. When `debug-log-changed` names a file of `logs/` and the timeline follows, the view asks for the rows after those positions (`since` is the `tail`, `order` is `asc`) page by page until `next` is `null`, adds the rows that it does not hold, in the order above, and keeps the `tail` of the last answer; the filter and the selection stay, and the status counts the rows added since the timeline was shown (`appended`). When the held rows would pass `HOLD_LIMIT`, the oldest rows leave the view and are counted in `omitted`; the note `core.debug.timeline.omitted` (`앞쪽 <n>행은 보관하지 않음`) states the number and is hidden when it is 0, and `older` is true. A notice that arrives during a read waits for it, so a row is read once; a notice of a file that is not an event file is ignored. `core.debug.timeline.follow {on}` stops (`on` false) or resumes (`on` true) following; resuming first reads what grew while stopped, a read that finishes after a stop is discarded, and the same call again changes nothing. A read that fails stops following and the view shows the error. The view shows a button that runs `core.debug.timeline.follow` with the opposite of the current state. The view has no timer of its own: the host bounds the rate of the notices ([following](#files)), and each notice is answered at once with a query from the `tail`, so no row is lost. A query that adds no row draws nothing, because a draw makes host calls that the host records. The page does not store its `page.call` of `logQuery`; the host stores `host.binding.call` of it, which does not announce a change of the log.
- `core.debug.timeline.save` runs the host call `debugSaveText({name, text})` with the text lines of the selected rows, in timeline order, one line each (the line of each event as the view shows it, without the indent of a context row, each ended by a line feed), and the name `soksak-timeline-<time>.txt` where `<time>` is the UTC time `YYYYMMDDTHHMMSSZ`. It answers `{saved}` like `core.debug.save`; `{saved: null}` is a cancelled save panel and not an error. A selection without a row is refused with the error `no timeline row is selected`, shown in the view. The view shows the 선택한 행 저장 button with the warning `저장한 파일에는 입력한 글자가 들어 있을 수 있다.` beside it ([logging](logging.md#privacy)); the status reports the same text.

<a id="timeline-command"></a>`sok debug query` prints the rows of one page from the command line with the same rows, order, filter and text lines as the view ([command line](cli.md#commands)). It runs the implementation of the query of its language on the files of the configuration directory that `--config-dir` or the application names, and does not connect to the application. The flags are `--channel`, `--level`, `--class`, `--layer`, `--event`, `--event-prefix`, `--surface`, `--session`, `--cid`, `--run`, `--text`, `--from`, `--to` (a UTC time as in the filter), `--order`, `--limit` `--after` (the cursor as `<ts_us>/<role>/<boot>/<seq>`) and `--around` (a cursor of the same form) with `--earlier` and `--later` ([the rows around a row](logging.md#query); the rows that are only context are indented by two spaces, and `--around` takes no other filter flag than `--channel`), with the values and the errors of the parameters of the query; an invalid value is a usage error that names the flag value with the error text of the query. The output is the text lines, one per row, each ended by a line feed. When a row follows the page, the command writes `more: --after <cursor>` to the standard error. It fails with an error that names the folder when the folder has no `logs/` folder, and with the file and the line when a file breaks the event structure. The command writes no JSON, because the lines are the form that the view shows and saves. Both implementations of `sok` print the same lines for the same files; the golden files `packages/log-contract/fixtures/query` hold the files, the parameters, the flags and the expected pages and lines, and the debug view, `sok` for Go and `sok` for Rust run them.


## State

The list shows every file of `logs/`, including the raw `.stderr` and `.crash` files of the processes ([logging](logging.md#files)); `core.debug.view` shows their text like any other text file. A state file `logs/state-<time>.json` also has a 상태 button that runs `core.debug.state {path}`, which reads the file with `debugRead` and shows it as a tree. A `path` that is not a state file of the list is refused with an error that names it.

- A state file must be a JSON object with a string `time`, a `host` of `wailsv3` or `tauriv2`, objects `versions` and `page`, and an array `windows`. A file that breaks this, whose text is truncated at the read limit, or that is not text is refused with an error that names the file and what was found, and the view shows that error.
- The tree has one line for each key in file order, indented by depth: `key: <JSON value>` for a value, `key {n}` or `key [n]` for an object or an array with `n` members, and `key: {}` or `key: []` for an empty one.
- `core.debug.state.compare {with}` compares the shown state file with another state file of the list and lists above the tree each path whose value differs, as `path: <value in the shown file> -> <value in the other file>`. A path is the keys from the top, joined by `.`, with `[index]` for an array element and `["key"]` for a key that is not an identifier. A path that only one file has shows `(없음)` for the other. The differences are the paths of the shown file in file order, then the paths that only the other file has. An empty `with` ends the comparison; a `with` that is not another state file of the list is refused with an error that names it. The view has a selection box of the other state files, pointing to this command, and a 목록 button that runs `core.debug.list`.

## Status

`core.debug` reports `{open, recorded, entries, viewing, timeline, state, scroll, operation, error}`: whether the view is open, the path of the state file that opening wrote or `null`, the listed entries `{path, size, modified}` in the order of the list, the shown file `{path, size, truncated, kind, length}` (`length` is the number of characters of the shown text, 0 for an image) or `null`, the shown timeline `{following, appended, held, older, omitted, context, selected, warning, channel, level, class, layer, text, event, event_prefix, surface, session, cid, run, from, to}` (whether it follows the files, the number of rows added since it was shown, the number of rows held and drawn, whether an older row exists, the number of the oldest rows that following left out, the number of rows that are only context, the number of selected rows, the warning of the save, and the filter) or `null`, the shown state file `{path, lines, with, differences}` (the number of tree lines, the state file it is compared with or `null`, and the number of differences) or `null`, the scroll position of the shown content in points (negative while the content is pulled past its start, as the native modal reports it; a value that is not a number is refused), the running or last operation `{action, path, state}` with `action` `save`, `save-all` or `save-rows`, `path` the saved file (the name of the text file for `save-rows`) or `null`, and `state` `running`, `done` or `failed`, and the error of the last failed step or operation or `null`. `core.screen` reports `modal` `debug` while the view is open.
