# 네이티브 호스트

[English](hosts.md)

코어의 네이티브 쪽은 같은 구조를 가진 두 language host library와 framework마다 하나인 framework adapter에 있다. [네이티브 호스트 인터페이스](native-host.ko.md)가 워크벤치 페이지가 사용하는 연산을 정의한다. [호스트 계약 사례](host-contract.ko.md)는 호스트들의 테스트가 실행하는 동작을 나열한다.

| 패키지 | 언어 | 식별 |
| --- | --- | --- |
| `packages/host/go` | Go | Go language host library. 모듈 `github.com/soksak-app/core/packages/host/go`. `src/`의 패키지 `host`이며 `github.com/soksak-app/core/packages/host/go/src`로 가져온다 |
| `packages/host/rust` | Rust | Rust language host library. 크레이트 `soksak-host`, `[lib] path = "src/host.rs"` |
| `packages/host/wailsv3` | Go | Wails framework adapter. 모듈 `github.com/soksak-app/core/packages/host/wailsv3`. `src/`의 패키지 `adapter`이며 `github.com/soksak-app/core/packages/host/wailsv3/src`로 가져온다 |
| `packages/host/tauriv2` | Rust | Tauri framework adapter. 크레이트 `soksak-host-tauriv2`, `[lib] path = "src/host.rs"` |

Language host library는 framework를 이름으로 부르지 않는 모든 것을 가진다: 바인딩, 창, 작업 공간, 표면, 문서, 이미지, 사이드카, 노출, 엔드포인트, 이벤트 로그, 진단, darwin platform layer. Library는 framework port로만 framework에 닿는다. Port는 두 interface `Framework`(애플리케이션 이름, 창의 main page 유무, main-thread step, 종료, 대화상자, 메뉴, Dock, 제목 표시줄을 포함한 창 생성)와 `Frontend`(이벤트 emit, 창 제목, 표시, 초점, 창 이벤트, presentation notice, settled presentation, workbench 시작, workbench 호출 통로)이며, 두 언어에서 이름이 같다(`src/framework.*`). 두 port가 모두 가진 method는 두 언어에서 이름이 같고(Rust에서는 snake case), 한 언어만 가진 method는 [언어 표](#언어-표)의 P 행이다. `Frontend`는 크기와 위치를 logical pixel로 받고 준다. `packages/host/go`의 어떤 파일도 Wails나 mygo의 패키지를 가져오지 않고, `packages/host/rust`의 어떤 파일도 Tauri의 크레이트를 이름으로 부르지 않는다([구조 검사](#구조-검사)). Language host library의 source와 test의 어떤 identifier와 문자열도 framework를 이름으로 부르지 않고, 그 파일의 contract 선언도 부르지 않는다. 한 framework에 속한 값은 그 framework adapter에 있고, adapter가 그 값을 port로 넘기거나 port의 값을 변환한다. Tauri framework adapter는 page origin을 시작 문서에 넘기고, menu item의 key를 자신의 menu library의 shortcut으로 변환하며, asset resolver의 lookup 중 어느 것이 page의 요청인지 정한다. Wails framework adapter는 port의 logical 길이를 Wails의 정수로, 각각 가장 가까운 정수로 변환한다. Framework adapter는 `Run`과 framework port의 구현을 가진다. 한 언어만 필요로 하는 파일은 그 language host library에 남고, 한 framework만 필요로 하는 파일은 그 framework adapter에 있다. Framework adapter의 애플리케이션 이름(`wailsv3`, `tauriv2`, `mygo`)은 `endpoint.json`의 `application`, 엔드포인트 소켓의 이름, 애플리케이션 업데이트 릴리스 키의 호스트, debug view 상태 파일의 `host`다.

애플리케이션 `apps/wailsv3`와 `apps/tauriv2`는 `src/main.*`, `environment.json`, `runtime/index.js`, 테스트, 매니페스트, 프레임워크 설정만 가진다. `apps/wailsv3/src/main.go`는 명령행 플래그를 Go language host library의 `host.Options`로 읽고 Wails framework adapter의 `adapter.Run(assets, options)`를 호출한다. `apps/tauriv2/src/main.rs`는 Tauri framework adapter의 `soksak_host_tauriv2::run(tauri::generate_context!(), BACKGROUND)`를 호출하며, `BACKGROUND`는 스테이징된 `frontend/background.js`다.

mygo application과 그 Go 의존성은 `CGO_ENABLED=0`으로 빌드되어야 한다. purego는 구현 선택이며 필수 조건이 아니다. 공유 Go host나 Wails adapter의 변경은 이 mygo의 cgo 없는 경로를 유지해야 한다. framework별 foreign function binding은 platform interface 뒤에 두며 다른 adapter에 cgo를 강제하지 않는다.

Go callback 소유자는 마지막 native 사용이 끝나 소유자가 해제할 때까지 0이 아닌 정수 token으로 값을 유지한다. 0과 해제된 token은 무효이며, 이중 해제와 무효 token 조회는 panic으로 거부한다. token은 Go pointer가 아니며 해제 뒤 재사용하지 않는다. callback package는 `CGO_ENABLED=0`으로 build되고 실행된다. handle 연산만 사용해도 `runtime/cgo.Handle`은 cgo runtime symbol을 링크하므로, `sync.Map`과 atomic token 할당을 사용한다.

공유 native header `native/darwin/src/host_callbacks.h`는 기본 callback 41개와 진단 callback 7개의 native-to-host ABI를 선언한다. 각 profile은 해당 작업 시작 전에 한 번 등록한다. native library는 완전한 table을 복사하며 누락이나 교체를 거부한다. 함수 주소는 process 종료까지 유효하다. native code는 Go export를 링크하는 대신 등록된 `sp_host_callback_*`와 `sp_host_diagnostic_callback_*` 진입점을 참조하며, 각 호출은 여전히 `hostRunOnWorker`나 `ON_WORKER`를 거친다. profile 등록 전 callback을 호출하면 진입점 이름을 남기고 abort한다. `make create-host-callbacks`는 clang을 통해 header에서 cgo 등록을 생성하고, `make check-host-callbacks`는 오래된 binding을 거부하며 native build의 선행 조건이다. 진단 등록은 Go의 `diagnostics` build tag에서만 선택된다. native library의 구성은 하나이며, 기본과 진단의 함수와 callback을 모두 담는다. `diagnostics` build option이 없는 host build는 진단 callback을 등록하지 않고 진단 함수를 부르지 않는다.

mygo adapter의 cgo 없는 callback binding은 같은 header에서 `src/platform/darwin/nativecallback`으로 생성한다. Darwin LP64 scalar의 정확한 폭과 native pointer 간접 참조를 유지하며 지원하지 않는 선언은 거부한다. callback 주소 할당 전 필수 함수 전부를 확인한다. `Bind`는 시작 시 profile마다 한 번 호출하며 반환 table을 재사용하고 함수 주소는 process 종료까지 유지한다. `make test-host-callbacks`는 격리된 native ABI fixture를 컴파일하고 callback 43개와 native table 크기·offset을 확인하는 cgo 없는 소유 test를 실행한다. 이 ABI test는 main-thread worker 통합이나 drag frame 성능의 근거가 아니다.

ABI 후보는 새 foreign-call runtime을 만들지 않고 mygo adapter가 이미 선언한 purego 버전을 사용한다. 이 구현은 Go 함수를 process 종료까지 유지하고 유한한 callback 주소 pool을 가지므로 adapter는 한 번 binding하고 주소를 재사용한다. 불완전한 profile 검증은 주소를 할당하지 않아야 한다. 현재 서명은 부호 있는 32-bit C `int`, 부호 있는 64-bit Darwin `long`, 부호 없는 64-bit counter, pointer 폭의 정수 token, 혼합 `double` 인수, bool과 native pointer 출력을 요구한다. purego는 이 인수 형태를 받지만 실수 callback 반환형은 거부하므로 생성기는 binding 출력 전에 해당 반환형을 명시적으로 거부한다. native fixture는 malloc 호환 저장소에 응답 byte와 MIME 문자열을 할당하고 내용을 검증한 뒤 해제하며, host callback은 별도로 넘겨받은 오류 문자열을 해제한다. 호출 전 강제 garbage collection으로 callback 수명 유지를 확인한다. native field offset·table 크기·명시적인 callback 호출 순서가 독립적인 layout·함수 식별 기준이다. 호출 횟수만으로는 같은 서명의 함수 교환을 놓치며 첫 두 주소를 교환한 통제 변이는 순서 검사에서 실패한다. scalar-only 생성기 fixture도 cgo를 끄고 컴파일한다. 이 검사에서 사용하지 않는 unsafe import가 드러났으며 import는 생성 서명의 필요에 따른다. 이 근거는 후보 ABI에 한정된다. 실제 framework worker 전달, main-thread 재진입, drag frame 비용과 cgo 없는 application 전체 build는 후보 통합 전에 계속 필요하다. callback 수명과 지원 반환형의 제약은 [고정된 purego callback 구현](https://github.com/ebitengine/purego/blob/v0.11.1/syscall_unix.go)에 따른다.

공개 mygo worker 주소 함수는 해당 실행 문맥에서만 전달한다. worker 수명주기가 실행 중일 때 main thread의 호출은 worker로 넘기고, 그 step 안의 worker 호출은 main thread로 넘긴다. 관계없는 thread에서는 둘 다 inline 실행한다. 따라서 일반 Go thread의 ABI fixture는 worker 전달을 증명하지 못한다. 통합 test는 공개 framework 수명주기를 시작하고 native main-thread code에서 진입하며 재진입 completion 양쪽의 native thread 식별자를 관찰해야 한다.

cgo 없는 worker consumer는 별도 native test library를 읽고 window나 활성화 없이 공개 framework 수명주기를 실행한다. 시작 시 native main thread에서 `sp_block_async_signals`를 호출한다. 공유 native 연산은 fault mask를 보존하고 다른 thread를 거부하며 기존 cgo preamble 구현을 동작 변경 없이 대체한다. test는 callback thread를 공개 framework step의 정확한 worker thread와 비교하고, 중첩 작업과 넘겨받은 presentation completion 실행 시 native main-thread 식별자를 관찰한다. 빌린 native stack 문자열은 동기 반환까지 유효 범위 안에 둔다. 실패는 framework 종료 전에 비정상 종료하며 성공 종료는 event loop 반환 후에만 찍는 marker를 요구한다. framework가 종료 유예 이후 상태 0으로 강제 종료할 수 있기 때문이다. 부모 subprocess는 60초 deadline을 둔다. worker 전달을 직접 호출로 바꾼 변이는 native main thread에서 Go에 진입하기 전에 실패한다. Objective-C block fixture는 native 상태 pointer를 통해 stack buffer에 접근하고 block 정리를 위해 Objective-C runtime을 명시적으로 링크한다.

Test command는 선택된 Go import graph와 pkg-config 선언에서 실행 전에 native 입력을 해석한다. Native `.pc`는 절대경로 `static_library`·`dynamic_library` 변수를 선언하고 test 선언은 별도 callback ABI·worker artifact도 명명한다. 정확한 public binding·test package 식별자가 필요한 artifact를 선택한다. 환경값이 명시되어 있으면 빈 값도 검증하며 잘못된 값에서 pkg-config로 넘어가지 않는다. 값이 없을 때만 선언된 변수를 쓴다. Native 요구가 없는 graph는 native 조회를 수행하지 않는다. Static production·fixture 내용 모두 cgo cache key에 반영한다. Mygo run record는 CGO_ENABLED=0을 명시하고 Wails는 cgo를 선택하며 같은 환경을 source inventory·package 발견·compile·binary listing·실행에 전달한다. Listing도 TestMain을 실행할 수 있어 환경과 무관한 단계가 아니다. 일반 Go linker flag는 caller 입력으로 유지하며 cgo 전용 flag는 별도 선언 입력으로 cgo 없는 build에 전달하지 않는다. Loader의 절대경로 계약과 runtime 탐색 금지는 유지한다.

Cgo 없는 개발 계약은 application뿐 아니라 test 의존성도 포함한다. Canonical test 전용 native 선언은 `native/darwin/tests/support/host_test_api.h`에 두며 구현과 export 선택 manifest도 같은 곳에 둔다. Sampler·native run-loop recorder·IOSurface 공급자·직접 block runner는 배포 native API에 넣지 않는다. `make build-host-test`는 `native/darwin/build/host-tests` 아래 static test library, 별도 dynamic artifact `native/darwin/build/host-tests/dynamic/libhost_test.dylib`와 `soksak-host-test` pkg-config 선언을 만든다. Fixture는 production native object를 link하지 않는다. 한 번 설치하는 stall table은 count와 wait 주입을 수행하는 실제 production C 함수 주소 두 개를 받으며 누락과 교체는 명시적인 오류다. Native 관찰과 thread를 중지한 sampling은 모두 C에서 실행한다. 공유 Go facade의 판정, recorder 누락 오류, 정확한 stack 범위와 IOSurface nonce·InUse 동작은 유지한다.

기존 Clang 생성기가 이 선언에서 독립 test ABI type, cgo binding과 cgo 없는 binding을 만든다. 공유 독립 test provider는 진단 profile을 포함해 `darwin && cgo`와 `darwin && !cgo`로 선택하는 완전한 compile-time 구현이며 runtime fallback이 아니다. Dynamic 구현은 framework adapter를 import하지 않고 자기 생성 binding을 사용한다. Purego는 공유 Go module에서는 test가, mygo에서는 framework가 소유하며 공유 production Go는 import하지 않는다. Dynamic test artifact는 절대경로 `SOKSAK_NATIVE_TEST_LIBRARY`로 선언하고 `SOKSAK_NATIVE_LIBRARY`는 adapter가 쓰는 같은 production image를 가리킨다. 다른 경로를 탐색하지 않고 모든 loading 오류를 보고한다. Fixture 설치와 main-thread capture는 framework event loop와 sampling 시작 전에 시작 thread에서 수행한다. 두 adapter는 test가 주입하는 같은 production stall 상태를 관찰해야 하며 shared contract coverage를 없애지 않고 mygo의 발견·build·inventory·실행 모두 CGO_ENABLED=0을 사용해야 한다.

Adapter test process도 application 시작과 같은 native 준비 계약을 따른다. TestMain은 signal 차단, native window 생성, menu 설치와 framework event loop 진입 전에 시작 thread에서 RequireMainThread를 호출한다. 각 선택 test는 다른 test 순서와 독립적이다. 잘못 선언한 artifact는 framework 실행 전에 경로를 포함한 loading 오류로 종료해야 하며 다른 test가 provider를 초기화해 주는 데 기대지 않는다.

별도 divider prototype보다 실제 application 통합을 우선한다. 공유 Darwin Go code에는 C import가 없으며 framework adapter가 host 준비 전에 typed native interface를 설치하고 한 번 초기화한다. 함수·provider 누락, 중복 설치와 시작 후 설치는 오류다. callback factory와 두 outbound binding은 canonical native header에서 생성한다. Wails는 cgo와 static native library를 유지한다. mygo binding은 기존 purego 의존성으로 canonical native dynamic artifact를 한 번 읽어 process 수명 동안 유지한다. 개발 환경은 절대경로 `SOKSAK_NATIVE_LIBRARY`를 선언할 수 있다. 그렇지 않으면 executable은 application bundle 안에 있어야 하며 artifact는 `Contents/Frameworks/libsoksak-darwin.dylib`다. 상대경로, 작업 디렉터리 탐색과 loading fallback은 거부한다. dynamic build는 `native/darwin/build/mygo`에 두어 static consumer의 link 방식이 묵시적으로 바뀌지 않게 한다. application과 bundle의 Go command 모두 `CGO_ENABLED=0`으로 build한다. `make create-host-api`는 outbound binding과 record 검증을 다시 생성하며 `make check-host-api`는 양 native build 전에 오래된 결과를 거부한다. Host 준비 전에도 쓸 수 있는 framework ShowWindow는 같은 provider를 초기화하고 binding 오류를 반환한다. 이른 show와 이후 host 준비는 실패를 포함해 한 번의 초기화를 공유한다. 실제 application 시작과 production S5 측정은 여전히 필요하며 생성 code와 native library의 build만으로 완료를 입증하지 않는다.

화면을 표시하는 cgo 없는 divider prototype은 공개 `ui.Split`, `Content.RecordFrames`, `mygo.RecordSteps`, `Window.NativeHandle`과 native pointer-input 전달을 사용하고 입력 완료를 worker를 통해 생성된 callback table로 보낼 수 있다. divider 이동을 입증하고 재사용되는 frame record를 즉시 복사하며 누락 record와 입력 실패를 거부해야 한다. frame·step 표본 수, thread 식별, display 조건과 build 출처를 기록한다. frame 공식은 `Request - Start - DrawableWait`이고 step 공식은 전달된 native 호출 시간을 포함한 `Return - Entry`다. timestamp 연결에는 `CLOCK_UPTIME_RAW`를 사용한다. prototype 수치를 8.33 ms와 비교하는 것으로 G8-S5를 입증하지 못한다. 일반 split에는 production terminal·webview surface 배치와 callback 구성이 빠져 있기 때문이다. 해당 최종 지표는 통합 application 또는 동일한 production S5 컴포넌트·실행 경로가 필요하다. 측정 전에 native-to-Go ABI도 정수 handle context가 C 범용 void-pointer 표현에 기대지 않고 Go stack 확장과 collection 중 정수로 유지되는지 확인해야 한다.

host callback의 context 인수는 `uintptr_t`로 선언한 정수 handle token이다. 범용 native API가 cookie를 `void *`로 보관할 수는 있지만 C bridge는 host callback 호출 전에 이를 정수로 바꾼다. Go binding은 그 token으로 `unsafe.Pointer`를 만들지 않는다. 앞선 ABI fixture는 context에 실제 native 주소를 넣어 정수 handle 의미를 놓쳤다. 소유 fixture는 이제 정수 context를 사용하고 실제 작은 값·상위 bit token을 유지한 채 stack을 확장한다. 기존 pointer 선언은 무효했다. native token 1이 `reflect.Value.call`의 살아 있는 pointer slot에 남아 callback stack을 강제로 확장하자 `invalid pointer found on stack`으로 종료됐다. foreign-call runtime이 이미 pointer 인수를 구성하므로 Go handler 안에서 정수로 바꾸는 것은 늦다. native ABI 회귀 test는 작은 token과 상위 bit가 설정된 token을 stack 복사·collection 중 유지한다. 실제 native 객체·문자열·held-input·출력 buffer pointer는 pointer로 남긴다. 회귀 test는 작은 값·상위 bit 값의 정확한 ImageChanged 호출 순서를 요구한다. native callback을 없앤 변이는 빈 호출 기록으로 실패한다. runtime의 무효 pointer 검사는 끄지 않는다.

## 규칙

- 코드는 `src/`에 둔다. 테스트는 `tests/`에 두며, 두 언어 모두 테스트 파일 이름은 `_test`로 끝난다. `tests/`의 Go 테스트는 자기 language host library나 framework adapter의 패키지를 가져온다. Cargo는 각 `tests/*_test.rs` 파일을 크레이트의 통합 테스트로 빌드한다.
- 각 디렉터리의 대표 파일은 디렉터리 이름과 같다: `host.*`, `platform/platform.*`, `darwin/darwin.*`, `windows/windows.*`.
- Rust 모듈은 `#[path = "..."]` 속성을 사용하므로 크레이트에 `lib.rs`와 `mod.rs`가 없다.
- 플랫폼 코드는 `src/platform/<os>/` 아래에만 있으며 `os`는 `darwin`, `windows`, `linux` 중 하나다.
- 대체(stub) 파일은 없다. 플랫폼이 구현하지 않은 연산은 `src/platform/<os>/unsupported.*`에서 오류를 반환한다.
- `native/darwin`이 내보내는 C 이름이 프레임워크의 이름과 겹치면 `sp_`로 시작한다. Wails는 자기 `windowFullscreen`을 컴파일하고, 링커가 둘 중 하나를 골라 호출이 프레임워크 함수로 갔으며 호스트는 그 반환값을 실패로 읽었다.

두 호스트의 `platform/darwin/ui_queue.go`와 `ui_queue.rs`는 프레임워크 이벤트 잠금 밖의 네이티브 메인 큐 실행을 제공한다. 표면 커밋과 취소는 이 경계에서 실행한다.

## 플랫폼 선택

Go: 각 `src/platform/<os>/` 디렉터리는 Go 패키지다. 대표 파일(`darwin.go`, `windows.go`)은 빌드 태그가 없고 패키지 문서만 가진다. 나머지 파일은 `//go:build <os>` 태그를 가지며, 그중 한 파일이 `init`에서 `platform.Register`를 호출한다. Go language host library의 `host.go`는 모든 운영체제 패키지를 빈 식별자로 가져오므로 빌드는 대상 운영체제의 구현만 등록한다. `Prepare`는 `platform.Current()`로 구현을 얻고, 등록된 구현이 없으면 실패한다. Wails framework adapter도 같은 방식으로 자기 `src/platform/darwin` 패키지를 가져온다([Framework 표](#framework-표)의 H31 행).

Rust: `src/platform/platform.rs`는 각 운영체제 모듈을 `#[cfg(target_os = "macos")]` 또는 `#[cfg(windows)]`와 `#[path = "<os>/<os>.rs"]`로 선언한다. `platform::current()`는 대상 운영체제의 구현을 반환하고, 다른 대상에서는 오류를 반환한다. 각 운영체제 모듈은 자신의 파일을 `#[path]`로 선언한다.

셸 사이드카 repository는 자기 `src/platform/`에서 같은 Go 방식을 사용한다([Repository](plugins.ko.md#repository)).

## 플랫폼 인터페이스

`src/platform/platform.*`가 인터페이스를 정의하고, 각 `src/platform/<os>/`가 이를 구현한다. 연산은 네이티브 창과 뷰 핸들을 받는다. Go에서 창 핸들은 `platform.Window`이고 모든 운영체제에서 정수다. HWND는 Windows가 소유한 값이지 주소가 아니므로 Go pointer가 그것을 담지 않고, darwin 구현만 native code를 부르는 자리에서 핸들을 NSWindow의 주소로 바꾼다. 뷰 핸들은 native code 객체를 가리키는 `unsafe.Pointer`다.

Windows에서는 구현하지 않는다 |
| 엔드포인트 | [로컬 엔드포인트](endpoint.ko.md) 전송: macOS는 Unix 소켓, Windows는 미구현 |

녹화 시작은 still 0이 기록된 뒤에만 성공한다. 실패한 still 0, 만들지 못한 still 요청 timer, still 0 대기의 끝은 그 오류로 시작을 실패시키고 녹화를 끝낸다.

정지 캡처는 녹화 오류와 분리된 호출자 소유 오류 문자열을 반환하며 호출자는 free()로 해제한다. 정지 캡처 실패는 기존 녹화 오류를 지우거나 정상 녹화를 실패하게 만들지 않는다. 잘못된 UTF-8 경로는 플랫폼 API 호출 전에 거부한다. 네이티브 sp_capture_still 오류 출력 포인터는 필수이며 성공은 그 값을 NULL로 설정하고 실패는 UTF-8 오류 문자열을 할당한다. 두 호스트는 sp_capture_error 대신 호출별 출력을 읽고 해제한다.

macOS에서 정지 캡처와 녹화는 세 host 모두 window server에서 창을 읽는다. application은 `CGWindowListCreateImageFromArray`로 자기 창의 image, 곧 window server가 합성한 image를 장치 픽셀 해상도로 요청한다. Still은 window server가 화면에 있다고 나열하는 창과 그 child window를 그 앞뒤 순서대로 받고, `display`가 있는 녹화에서는 창의 중심이 있는 display에 있는 process의 화면 위 모든 창을 받는다. macOS 15 SDK가 이 함수를 obsolete로 표시하므로 capture는 실행 시 함수를 찾고, 함수가 없는 macOS에서는 open과 still이 `CGWindowListCreateImageFromArray is not available on this macOS`로 실패한다([private native API](../operations/private-native-apis.ko.md)). Capture는 자기 process의 창만 요청한다. 이것에 화면 기록 권한이 필요한지는 확인되지 않았다. Apple은 [WWDC19 session 701, Advances in macOS Security](https://developer.apple.com/videos/play/wwdc2019/701/)의 화면 기록 부분(macOS 10.15)에서 app이 자기 창의 내용, menu bar, desktop 배경 image를 자유롭게 기록할 수 있다고 말했지만, 이를 적은 reference 문서는 없다([private native API](../operations/private-native-apis.ko.md)). 캡처는 cursor를 받지 않고 아무것도 활성화하지 않는다. 다른 창 아래에 있는 창은 web view, WebGL canvas, composited layer, Metal layer, IOSurface layer까지 가리기 전과 같은 byte로 캡처되고, 가려진 동안의 변경은 다음 캡처에 나타난다. 이는 host가 main web view, view page, modal web view의 occlusion 감지를 끄기 때문이다. 켜져 있으면 가려진 캡처에서 web layer가 빠지고, 가려진 창에서 연 modal은 올라오지 않는다. Document region은 감지를 유지하므로 가려진 region의 문서는 숨고 animation frame을 그리지 않는다. 그 창에 `diagnostics.window.draw-covered`가 켜져 있는 동안은 host가 그 창의 document region의 감지도 끄므로, 가려진 창의 still capture가 그 문서와 가려진 동안의 변경을 담는다([문서 영역](native-surfaces.ko.md#문서-영역)). layer를 직접 읽는 경로는 이 pixel을 내지 못해 쓰지 않는다. `takeSnapshot`에는 Metal과 IOSurface layer가 없고, `renderInContext:`에는 Metal layer와 창 배경이 없고, `cacheDisplayInRect:`에는 Metal layer가 없고 값이 1 다르며, `takeSnapshot`, Metal readback, IOSurface의 합성은 title bar가 없고 글자와 둥근 모서리가 다르다.

녹화 대상 준비·시작은 이미 활성 녹화가 있으면 대상·프레임 계수·녹화 오류 변경 전에 거부한다. 각 open/start 호출은 필수 출력 포인터로 별도의 호출자 소유 UTF-8 오류를 반환한다(성공은 NULL, 실패는 free()로 해제). 거부된 중첩 작업은 정상 녹화 준비를 무효화하거나 이전 녹화 실패를 지울 수 없다.

대상 준비는 호출될 때 실행된다. window server가 창을 화면에 나열하는지 확인하고(보류한 새 창은 제외), 다음 시작을 위해 창 번호와 display 선택을 보존한다. 실패한 준비는 창을 보존하지 않는다. 준비 오류는 호출별 출력으로 반환하며 녹화 오류를 바꾸지 않는다. 녹화가 실행 중인 동안의 준비는 거부하고 활성 녹화를 유지한다.

실패한 프레임 파일 열기·쓰기·닫기·커밋은 각 작업·프레임 경로·저장한 시스템 오류를 보고한다. 부분 파일 삭제 실패는 원래 실패를 대체하지 않고 추가 녹화 오류로 보고한다. 쓰기 실패 뒤에도 닫기를 시도하고 닫기 실패를 따로 보고한다. 쓰기가 파일 열기에 성공한 경우에만 삭제를 시도하며 열기 실패로 기존 경로를 삭제하지 않는다. 실패한 프레임은 기록 수를 증가시키거나 첫 프레임 준비를 알리지 않는다.

문서 연산은 view page의 웹뷰를 창의 공통 표면 컨테이너에 직접 두지 않고 그 표면의 `SurfaceHost` 안, 그 호스트 네이티브 평면 아래에 배치한다. 메인 웹뷰를 빼면 어느 표면에도 속하지 않는 웹뷰는 창을 채우는 모달뿐이다. 문서 영역과 그림 영역은 그 호스트 네이티브 평면의 하위 뷰다. 플랫폼 인터페이스는 영역을 `SurfaceHost`의 형제로 배치하는 연산을 노출하지 않는다. 두 언어 호스트는 플랫폼 코드를 호출하기 전에 [표면 합성](surface-composition.ko.md)을 검증한다.

두 호스트에서 place는 답하기 전에 더 이상 나열하지 않는 각 표면의 문서 영역과 그림 영역을 모두 닫는다(Wails에서 `closeSurfaceDocuments`와 `images.CloseSurface`, Tauri에서 `documents::close_surface`와 `images::close_surface`). 그 뒤 page는 영역을 detach하지 않고 그 표면을 release한다([region lifetime](native-surfaces.ko.md#region-lifetime)).

### 창 단추

AppKit 이 창 자신의 단추를 소유한다. 제목줄 높이가 AppKit 이 단추를 두는 자리를 정한다. AppKit 은 단추를 제목줄의 세로 가운데에 두고, 제목 변경, 크기 변경, 이동 뒤에도 그 자리를 지킨다. 각 호스트는 AppKit 의 `-[NSWindow setTitlebarHeight:]`(`windowSetTitlebarHeight`, [비공개 네이티브 API 목록](../operations/private-native-apis.ko.md)에 있다)로 제목줄 높이를 정하고, 창에는 도구막대가 없다. 각 호스트는 창을 만들 때, 창이 보이기 전에 높이를 40pt 로 정하고, 창 페이지의 시작 문서에 답하기 전에 저장된 프레임 배율의 행 높이로 정하며, 창이 아직 이전 페이지를 보이면 시작 트랜잭션 안에서 정한다. 그래서 준비를 기다리지 않는 페이지의 첫 그리기가 자기 제목줄을 가진다([제목줄 높이](native-surfaces.ko.md#제목줄-높이)).

페이지가 첫 행의 높이를 소유한다. `packages/workbench/app.css` 의 `--chrome-row` 는 `round(max(--chrome-h, 36px × 프레임 배율))` 이고, `--chrome-h` 는 고정된 40px 최솟값, 프레임 배율은 프레임의 [글자 크기](text-size.ko.md)다. `packages/workbench/frame-text.js` 의 `chromeRow` 가 페이지의 요청에 쓰는 같은 높이를 계산한다. 페이지는 행을 창의 답에서 얻지 않으므로 제목줄이 바뀌어도 행은 바뀌지 않는다. 제목줄 높이는 배치 트랜잭션에 속한다([제목줄 높이](native-surfaces.ko.md#제목줄-높이)). 각 준비(`syncSurfaces`)는 다음 그리기가 보이는 첫 행의 높이 `titlebar` 를 담고, 호스트는 창의 열린 트랜잭션 안에서 제목줄을 그 높이로 정하므로 제목줄과 행은 같은 표시 프레임에서 바뀐다. 페이지는 시작할 때와 창 크기가 바뀔 때마다 `windowControls` 를 읽어 첫 행에서 단추 영역의 폭을 비우고, 제목줄이 행과 다르면 행을 담은 배치를 준비한다. `host.window` 는 보이는 영역을 `controls` 로 보고한다.

`titlebar` 는 32 이상 200 이하의 point 수다. 두 호스트는 트랜잭션을 시작하기 전에, 이 값이 없는 요청을 인자 decoder 의 `argument request.titlebar is missing`([host 호출](native-host.ko.md#host-호출))으로, 다른 값을 `title bar height must be a finite number from 32 through 200 points` 로 거부한다. 표준 단추나 content view 가 없는 창은 `the window has no standard buttons or content view for a title bar` 로 실패하고, 그 실패는 시작한 트랜잭션을 취소한다. 전체 화면인 창은 제목줄을 보이지 않고, AppKit 은 창이 전체 화면에 들어갈 때 높이를 저장하고 나올 때 되돌리므로 그 사이에 정한 높이는 사라진다. 그래서 호스트는 창이 전체 화면인 동안 제목줄을 바꾸지 않고, 준비는 `chrome.row` 0 으로 답한다. 전체 화면에서 나오면 창 크기가 바뀐다. 페이지는 그때 `windowControls` 를 읽고, 되돌린 높이가 행과 다르면 행을 다시 준비한다.

단추를 페이지 쪽 뷰로 옮기면 제목이나 녹화 표시가 바뀔 때 AppKit 이 되찾아 갔고, 창 이동·크기 변경 48회당 한 번꼴로 단추가 사라지거나 제목줄 자리에 있는 프레임이 화면에 나왔다. 제목줄 높이는 도구막대에서 오지 않는다. 항목이 없는 unified compact 도구막대는 제목줄을 40pt 로 고정하므로, 프레임 배율이 키운 첫 행에서 단추가 가운데를 벗어난다.

## Wayland 한계

Wayland에서 client는 toplevel을 배치하거나 focus할 수 없다. 둘 다 compositor가 정하고, GDK의 `set_accept_focus`와 `set_focus_on_map`은 거기서 아무 일도 하지 않는다. 둘 중 하나가 필요한 연산은 `<operation> is not implemented on wayland`를 반환하고, 둘 중 하나가 필요한 창 검사는 X11에서 실행한다. page 입력에는 둘 다 필요 없다. X11과 Wayland에서 host는 process 안에서 `GdkEvent` 값을 만들어 `gtk_main_do_event`에 주며, XTEST를 쓰지 않고 실제 pointer를 움직이지 않는다.

## Windows 상태

Windows에서 두 호스트는 디렉터리 식별(`platform/windows/identity.*`), WebView2 의 pointer·키 입력(`platform/windows/input.*`, `devtools_input.*`), still capture(`capture.*`), 앞을 지키는 show(`show.*`, `show_windows.*`), UI thread 의 queue(`ui_queue.*`, `ui_thread.*`), mouse 버튼과 창 입력의 감시(`mouse_watch.*`), WebView2 process failure 의 의미(`process_failure.*`)를 구현한다. Go platform 은 `SetWebview` 가 이름 붙인 web view 의 `ProcessFailed` 를 구독하고, browser process 나 render process 가 끝나면 `SetWebview` 가 받은 `ended` 를 UI thread 에서 부르며, 다른 종류는 standard error 에 쓴다. web view 를 set 하는 framework adapter 는 자기 창의 window event `WindowWorkbenchEnded` 를 내는 `ended` 를 넘기고, 그 listener 는 macOS 와 같이 `web_process_ended` 를 기록하고 error line 을 쓴다. 아직 web view 를 set 하는 framework adapter 는 없다. `platform/windows/unsupported.*`의 나머지 연산은 `<operation> is not implemented on windows` 형식의 오류를 반환한다. Windows에서는 애플리케이션 시작이 첫 platform 연산에서 실패한다. Wails의 `Run`과 Tauri의 `run`은 창을 열기 전에 `window resize animation is not implemented on windows`와 상태 1로 끝난다. Linux 구현은 없으며, 그곳에서 `platform.Current()`와 `platform::current()`는 오류를 반환한다.

`make check-host-files`는 `make check-windows-build`를 실행하며, 이 target은 Go language host library와 Wails framework adapter의 source를 기본 build와 diagnostics build에서 `windows/arm64`용으로 vet한다.

`make check-host-files`는 `make check-host-debug`도 실행하며, 이 target은 세 host와 세 앱의 source와 test를 debug 앱의 feature와 tag로 macOS용으로 컴파일한다. `make build-tauriv2`, `make build-wailsv3`, `make build-mygo`, 이 check는 그 구성을 Makefile의 정의 하나에서 읽는다.

## Wails host의 main thread

Wails host의 main thread에서는 host에서도 framework에서도 Go code가 실행되지 않는다. Go code는 main thread가 아닌 thread에 고정된 worker goroutine에서 실행된다. native code가 Go를 부르는 각 callback(delegate method, script message, menu action, main-thread task)은 C 함수다. callback은 인자의 record를 쓰고 worker를 깨운 뒤 C에서 기다린다. 기다리는 동안 main thread는 worker가 그 단계를 위해 전달한 C 호출만 실행하고, callback은 worker가 쓴 답을 돌려준다. Go code가 시작하는 단계(`application.InvokeSync`, `EnqueueUI`)는 같은 방식으로 기다리는 C 함수를 main thread에 dispatch하고, 단계를 시작한 goroutine이 그 단계의 C 호출을 전달한다. 따라서 Wails host의 main-thread 단계는 main thread가 callback 하나 또는 시작된 단계 하나를 위해 C에서 기다리는 구간이다. host의 registry 상태를 읽고 native code를 부르는 단계는 한 main-thread 단계로 남고, 각 delegate 답은 동기로 남는다. nested run loop에 들어가는 전달 호출(modal dialog, menu, drag)은 다른 callback을 전달할 수 있다. worker는 전달 호출을 기다리는 동안 그 record를 받으므로, nested 단계는 바깥 단계 안에서 끝난다. script message나 commit 알림처럼 답이 필요 없는 callback은 record를 쓴 뒤 돌아가고, worker는 그 record를 그 webview의 goroutine에 넘긴다. 한 webview의 record는 main thread가 전달한 순서대로 처리되고, 다른 webview의 record는 그것을 기다리지 않는다. stall heartbeat에는 main thread의 C 함수가 답하므로, stall 측정은 계속 main thread를 측정한다. main thread는 application run loop가 시작되기 전에 비동기 signal을 막으므로, Go signal handler와 그 signal stack은 main thread에서 실행되지 않는다. main thread의 동기 fault는 막을 수 없고 프로세스를 끝낸다. main thread는 priority를 전달하지 않는 condition variable로 worker를 기다리므로, worker는 application main thread의 class인 user-interactive class로 돈다.

단계는 나중의 main-thread turn이 만드는 어떤 것도 기다리지 않는다. main thread는 단계의 Go code가 실행되는 동안에만 worker를 기다리고, 그 code는 나중 turn의 event 없이 끝난다. 나중 callback이 채우는 channel에서 받지 않고, 다른 goroutine이 단계나 native 결과를 기다리는 동안 쥔 lock을 잡지 않으며, presentation, 주입한 입력의 전달, WebKit의 completion처럼 나중 turn이 전하는 native 결과를 기다리지 않는다. 그런 결과는 event다. 단계는 결과의 handler를 등록하고 돌아가며, 결과는 자기 단계에서 실행된다. 앞 요청이 답한 뒤에만 시작할 수 있는 요청은 앞 요청의 답이 시작시키는 순서 있는 queue에서 기다리며, 앞 요청이 답할 때까지 쥔 lock에서 기다리지 않는다. 주입한 pointer 입력의 queue는 native에 있다([named pointers](exposure.ko.md#named-pointers)). 다른 thread에서 system framework를 기다리는 일은 단계가 아니라 그 요청의 goroutine에서 실행된다. diagnostics의 window recording과 still capture는 거기서 자기 still을 기다리고, 그 main-thread 부분은 Tauri host에서처럼 main queue로 가므로 main thread는 그것을 기다리지 않는다. main thread의 monitor는 native 상태로 답하고 보고할 때만 Go에 들어간다. 창의 surface input monitor는 누름, 또는 first responder가 창의 view인 key down을, 그 view나 그 위의 view가 surface host일 때 surface 누름으로 받는다. surface host는 자기 surface의 모든 document region과 view page를 담는다. native code는 자기가 만든 view의 class로 그것을 안다. monitor는 그 누름을 답이 필요 없는 callback으로 Go에 보고하므로, 누름과 key는 위로 올라가는 view마다 단계를 쓰지 않는다.

host는 `application.Run` 바로 앞에서 framework가 init에서 main thread에 고정한 main goroutine으로 platform의 `BlockAsyncSignals`를 불러 signal을 막는다. 막는 signal은 동기 fault인 SIGILL, SIGTRAP, SIGABRT, SIGEMT, SIGFPE, SIGBUS, SIGSEGV, SIGSYS를 뺀 모든 signal이다. kernel은 SIGCHLD, SIGINT, SIGTERM, SIGPROF처럼 프로세스에 보낸 signal을 그것을 막지 않는 thread에 전달하고, Go runtime이 만드는 각 thread는 runtime이 프로세스 시작 때 기록한 mask(`initSigmask`)로 시작하므로 `signal.Notify`와 profiling은 자기 thread를 유지한다. Go runtime은 실행 중인 goroutine을 비동기로 선점하려고 그 thread에 SIGURG를 보낸다(`preemptM`). 애플리케이션이 실행되는 동안 main thread에서는 goroutine이 실행되지 않으며, run loop 전후에 그곳에서 실행되는 main goroutine은 여전히 함수 호출 지점에서 선점된다. main thread가 시작한 프로세스는 이 mask를 물려받는다. host는 자식 프로세스를 다른 thread에서 실행되는 goroutine에서 시작한다.

공유 native library의 header `native/darwin/src/main_thread.h`는 두 main-thread 함수 `hostRunOnWorker`와 `hostRunOnMain`, 그리고 이 함수로 식을 평가하는 macro `ON_WORKER`와 `ON_MAIN`을 선언한다. `native/darwin/src/main_thread.m`은 framework adapter가 설치한 함수를 가진다. Wails framework adapter는 library 시작 전에 자기 darwin 패키지의 `init`에서 Wails fork의 함수(`wailsRunOnWorker`와 `wailsRunOnMain`)를 이 함수로 설치하므로, library의 어떤 파일도 Wails를 이름으로 부르지 않는다. library의 시작은 둘 다 요구한다. `Prepare`는 첫 native call 전에 platform의 `RequireMainThread`를 부르고, 이 함수는 `main-thread functions are not installed`와 빠진 함수 각각의 이름으로 실패한다. 설치되지 않은 함수를 부르면 프로세스가 그 이름을 내고 끝난다. block을 호출한 thread에서 실행하면 Go code나 native call이 잘못된 thread에서 실행되기 때문이다. framework adapter 없이 darwin layer를 실행하는 test는 자기 `TestMain`에서 둘 다에 test 함수를 설치한다.

`make check-host-files`는 Go language host library darwin layer의 C code, 즉 `packages/host/go/src/platform/darwin/`의 각 Go 파일의 cgo preamble과 각 Objective-C 파일에서 이 규칙을 검사한다(`scripts/check-host-files.mjs`의 `auditMainThreadCalls`. 이 함수는 `scripts/cgo-sources.go`를 통해 `go/parser`로 Go 파일을 읽고, macro를 펼치고 호출한 각 함수를 그것을 선언한 header로 해석한 clang의 JSON AST로 C code를 읽는다). C code가 Go 파일이 export(`//export`)한 함수를 `hostRunOnWorker`나 `ON_WORKER` 밖에서 참조하면 실패한다. Go code가 `native/darwin/src`의 header가 선언한 함수를 `main_` wrapper 대신 직접 부르면 실패한다. 단 thread가 필요 없는 함수(`MAIN_THREAD_FREE`, 각각 이유를 가진다: host 시작 전 dispatch pointer 설치와 조회, termination signal을 보낸 process의 기록 설치와 그 조회, event ring과 그 clock, `sp_observe_flush`, `sp_phys_footprint`, `sp_diagnostic_reports_directory`, 호출한 thread에서 자기 still을 기다리고 main-thread 부분을 main queue에 넣는 window recording과 still capture(`sp_capture_*`), `sp_facts_free`, `sp_window_facts_begin`이 main thread에서 AppKit facts를 읽은 뒤 window server에서 창의 order를 읽는 `sp_window_facts_finish`, `sp_ui_enqueue`)는 예외다. Go code가 부르는 layer의 C 함수가 `hostRunOnMain`이나 `ON_MAIN` 밖에서 Objective-C message를 보내거나, native 함수나 `NS` 함수나 block을 부르거나, 그렇게 하는 layer의 다른 함수를 부르면 실패한다. native 함수, Objective-C message, block이 `hostRunOnWorker`나 `ON_WORKER` 안에서 실행되어도 실패한다.

이유: 애플리케이션 프로세스는 WebKit과 다른 in-process client가 만든 JavaScriptCore VM을 가지며, VM의 lock은 그것을 잡은 thread를, main thread를 포함해, collector가 suspend하고 scan하는 thread에 더한다. collector는 각 thread의 stack을 stack pointer부터 그 thread stack의 origin까지 복사하고, 합한 크기의 두 배인 buffer를 할당한다. main thread의 Go code는 Go heap이 main thread의 stack 밖에 둔 goroutine stack에서 실행되므로, 그때의 scan에서 크기 `origin − sp`가 wrap되고 buffer 할당이 실패하며, JavaScriptCore는 `pas_panic_on_out_of_memory_error`에서 프로세스를 끝낸다. Tauri host에는 이 규칙이 필요 없다. 그 main thread는 main thread의 stack에서 Rust를 실행한다. 그 main thread도 같은 방식으로 나중의 main-thread turn이 만드는 어떤 것도 기다리지 않는다. `on_main`에 준 일은 main thread에서 불리면 바로 실행되므로, 그 일은 나중 turn의 결과를 기다리지 않는다. title bar가 창의 start transaction을 기다리는 start document는 비동기 scheme handler가 자기 thread에서 만들고([page start](native-host.ko.md#page-시작)), 애플리케이션 exit가 main thread에서 실행하는 sidecar stop은 sidecar start를 기다리지 않는다([declaration and startup](sidecars.ko.md#선언과-시작)).

기각한 선택: script message와 script 결과를 WebKit script message 대신 scheme handler로 나르는 방식은 기각했다. WebKit 7621은 page가 `CryptoKey`를 저장할 때도 VM을 만들고 host는 그것을 막을 수 없으며, WebKit 7622 이후는 이 호출들에 VM을 만들지 않기 때문이다. 최소 WebKit 버전도 기각했다. 다른 in-process JavaScriptCore client가 남기 때문이다. 늦춘 delegate 답(모든 quit의 `NSTerminateLater`, 거절한 뒤 Go가 나중에 다시 하는 close, Go가 미리 C에 넣어 둔 상태)도 기각했다. delegate 답은 자기 turn의 host 상태를 읽으며, 미리 넣어 둔 사본은 낡기 때문이다. 사이드카의 quit 중지가 실행되는 동안의 quit 거절은 그런 늦춘 답이 아니다. quit hook은 자기 turn에서 그 중지가 실행되는지 읽고, 호스트는 중지를 끝내는 event에서 quit을 다시 요청한다([프로세스 생명주기](#프로세스-생명주기)). 여기에는 `NSTerminateLater`를 쓰지 않는다. Wails와 mygo framework는 quit hook의 boolean 답으로 terminate 답을 만들고, tao는 `applicationShouldTerminate:`를 구현하지 않기 때문이다. input monitor의 surface 누름은 그런 사본이 아니다. view의 class는 view가 만들어질 때부터 닫힐 때까지 지니는 native 상태이기 때문이다. main thread가 worker를 전혀 기다리지 않는 방식, 즉 각 native callback을 worker에 post하고 Go code의 각 native call을 main queue에 post하는 방식도 기각했다. Wails와 mygo는 자기 delegate 답과 mygo의 각 frame을 turn 안에서 답하는 Go code의 단계로 실행하고, worker가 전달하는 호출에는 그것을 기다리는 main thread가 필요하며(main thread가 기다리지 않을 때 worker가 호출을 전달하면 Wails fork는 프로세스를 끝낸다), 준비한 turn에서 commit하는 placement처럼 host가 입력의 turn에서 만드는 결과에는 main thread가 기다리는 동안 그 turn의 Go code가 실행되어야 하기 때문이다. 위의 규칙은 main thread의 기다림을 아무것도 기다리지 않는 Go code의 실행으로 한정한다.

## 허용 차이

허용 차이는 두 표이며, 행 ID는 두 표를 통틀어 하나다. 언어 표는 `packages/host/go`와 `packages/host/rust`(H 행), `packages/sok/go`와 `packages/sok/rust`(C 행), 두 언어의 endpoint method(E 행), 두 언어의 framework port method(P 행)를 비교한다. Framework 표는 `packages/host/wailsv3`를 `packages/host/tauriv2` 및 `packages/host/mygo`와(H 행), `apps/wailsv3`를 `apps/tauriv2` 및 `apps/mygo`와(A 행) 비교한다. `scripts/check-host-files.mjs`는 각 쌍의 표에서 ID가 그 쌍의 글자로 시작하는 행을 읽는다. 내용만 다름 칸은 그 열의 쌍이 양쪽에 가진 파일을 뜻하므로, 그 행은 그 쌍에 파일을 나열하지 않는다.

## Memory pressure

호스트는 native memory pressure source 하나를 소유한다. 이 source는 호스트와 함께 시작하며 프로세스의 유일한 등록이다(macOS에서는 공개 dispatch memory pressure source). 수준 `normal`, `warn`, `critical`을 관찰하고, 보고마다 `seq`로 번호를 매기며, 수준이 바뀔 때만 보고한다. back-forward cache를 지우는 문서 영역 소비자([네이티브 표면](native-surfaces.ko.md#문서-영역))는 source를 소유하지 않고 이를 구독하며 `warn`과 `critical`에서만 지운다. 각 호스트는 모든 보고를 각 창의 메인 페이지에 page 이벤트 `memory-pressure` `{level, seq}`로 `seq` 순서대로, 보고를 받는 thread를 붙잡지 않고 보내므로 페이지는 현재 수준으로 끝난다. 그리고 [메모리 절약](plugins.ko.md#메모리-절약)이 이를 소비하며 `core.tab.memory`가 `pressure`로 알린다. 진단 빌드의 선언된 fault injection이 검사를 위해 보고를 보내고, contract case가 두 호스트를 같은 이벤트로 묶는다.

메모리 절약이 탭을 unload하기 전에 page는 선언된 호스트 메서드 `documentInteractionState`(Wails에서 `DocumentInteractionState`, Tauri에서 `document_interaction_state`)로 `{surface, document}`, 곧 표면과 그 표면이 attach하고 detach하지 않은 각 문서 영역의 이름을 주어 탭의 각 문서 영역의 `interactionState`를 읽는다. page는 그 이름을 각 `documentAttach`와 `documentDetach` 답에서 기록하고 표면을 release할 때 잊는다. 호스트는 영역 web view의 공개 `interactionState`, 곧 문서나 프로세스를 담지 않는 직렬화된 session history를 base64로 답하고, 영역이 아무것도 load하지 않았으면, 곧 직렬화된 history에 restore가 받을 entry가 없으면, 그리고 web content 프로세스가 이미 끝난 경우처럼 읽기가 아무것도 내지 않으면 빈 글로 답한다. 탭을 restore하면 그 값을 `documentAttach`의 `interactionState`로 넘기고, 이 호출은 새 영역의 첫 load 전에 그 값을 복원하며, web view가 거부하는 값은 attach를 `document <name>: <reason>`으로 실패시킨다([네이티브 표면](native-surfaces.ko.md#문서-영역)).

결정마다 page는 선언된 호스트 메서드 `documentQuery`(Wails에서 `DocumentQuery`, Tauri에서 `document_query`)로 `{surface, document}`를 주어 탭의 각 문서 영역에 묻는다. 호스트는 `{media, capture, form}`으로 답한다. `media`는 영역이 소리가 나는 media를 재생하는지이고, `capture`는 camera 또는 microphone capture가 active인지이며, `form`은 영역의 어느 frame이 form 표시를 가졌는지다. 닫힌 경우처럼 답할 수 없는 영역은 호출을 `document <name>: <reason>`으로 실패시킨다.

## 프로세스 생명주기

host의 goroutine과 스레드는 진입점으로만 시작한다. Go는 `routine.Go(name, fn)`(`src/routine/routine.go`), Rust는 `spawn_named(name, body)`(`src/routine/routine.rs`)이다. Go는 `fn`의 panic을 recover하고 메시지와 stack을 표준 오류에 쓰고, `name`, panic 값의 `text`, `stack`을 담은 event `host.panic`([events](events.json))을 저장하고, event가 event log에 들어갈 때까지 최대 2초 기다린 뒤 상태 2로 프로세스를 끝낸다. writer가 붙기 전의 panic은 먼저 writer를 기다리므로, event가 시작 buffer에 남지 않고 writer에 들어간다. 그 기다림은 두 event 중 하나에서 끝난다. writer가 붙거나, host의 시작이 writer를 붙이지 않고 끝난다(writer가 생기기 전의 시작 실패). 두 번째 경우 record와 stack을 표준 오류에 전부 쓴다. host의 시작은 writer를 붙이거나 끝나므로 어떤 시간 한도도 그 기다림을 끝내지 않는다. Rust panic hook은 panic한 스레드의 이름(이름이 없는 스레드는 `<unnamed>`)으로 같은 event를 저장하고(Rust panic 값에는 위치가 없으므로 `text`는 `<file>:<line>: `로 시작한다), 자기 스레드를 깨운다. 그 스레드는 writer가 붙거나 host의 시작이 writer 없이 끝날 때까지(둘 중 하나가 이미 일어났으면 기다리지 않음) 기다리고, event가 event log에 들어갈 때까지 최대 2초 기다린 뒤 상태 101로 프로세스를 끝낸다. Rust host는 프로세스의 첫 동작으로 hook을 설치하므로, writer가 열리기 전의 panic은 시작 buffer에 남고 writer가 열릴 때 저장된다. Rust host의 시작은 writer를 여는 endpoint 시작이 돌아올 때 끝난다. 그것이 writer 없이 돌아오면 record와 stack은 표준 오류에 전부 쓰인다. hook은 writer를 기다리지 않으므로 인터페이스 스레드의 panic이 writer가 멈춘 동안 그 스레드를 붙잡지 않는다. backtrace는 panic한 스레드에서 만든다. 정책은 두 host가 같다. panic이 남긴 상태는 믿지 않으므로 panic은 기록 뒤에 프로세스를 끝내고, panic 뒤에 계속하는 모드는 없다. 인터페이스 스레드의 panic으로 프로세스가 abort하는 시점이 writer가 큐의 event를 쓰기 전이면 메시지는 표준 오류에만 남는다. 시작 실패를 호출자에게 오류로 돌려주는 스레드(Rust host의 event writer, 성능 sampler, debug follower, termination watcher)만 `std::thread::Builder`를 직접 쓰며, 그 panic도 hook이 다른 스레드와 같이 기록한다.

시작 단계의 실패는 두 호스트 모두 그 메시지를 표준 오류에 쓰고 상태 1로 프로세스를 끝낸다. Tauri 호스트는 setup 단계의 실패를 event loop에 돌려주지 않는다. event loop의 시작 callback은 unwind할 수 없어서 실패가 프로세스를 abort시키고, 시스템이 메시지 없이 충돌 대화상자를 보이기 때문이다.

호스트는 세 자식 프로세스 계열을 각각 하나의 규칙으로 소유한다.

**WebKit XPC 는 애플리케이션과 함께 죽는다.** WebKit은 애플리케이션과의 연결이 닫히면 WebContent 프로세스를 끝낸다(`AuxiliaryProcess::didClose`가 프로세스를 끝낸다). 그래서 애플리케이션 프로세스가 끝나면 그 WebContent 프로세스도 끝나고, 호스트는 WebContent 프로세스를 직접 끝내지 않는다. 종료 신호는 두 호스트 모두에서 정상 quit 를 요청하므로 `host.quit` 처럼 창이 저장하고 사이드카가 멈춘다. quit 가 끝나지 않으면 두 번째 신호가 프로세스를 끝낸다. `application_end_processes_test`는 `-[NSApplication terminate:]`로 끝나는 애플리케이션이 main web view와 document region의 WebContent 프로세스를 남기지 않는지, 그리고 native library가 WebContent 프로세스를 죽이는 동작을 제공하지 않는지 검사한다.

종료 경로를 거치지 않고 끝난 호스트도 WebKit 프로세스를 남기지 않는다: launchd 는 애플리케이션의 WebKit service 를 그 프로세스의 launchd domain 에서 실행하고 그 프로세스가 끝나면 끝낸다(macOS 26.6.2 실측: 호스트를 `kill -9` 한 뒤 GPU·Networking·WebContent service 가 0.2초 안에 끝났고, 호스트마다 두 번 같았다). 따라서 호스트는 WebKit 프로세스 기록을 두지 않고 시작할 때 어떤 프로세스도 끝내지 않는다. 프로세스 목록은 이 호스트의 WebKit 프로세스와 다른 애플리케이션의 것을 구분하지 못하며, 목록의 프로세스를 끝내던 시작은 함께 실행 중이던 다른 애플리케이션의 프로세스를 끝냈다.

**종료는 영역이 닫히기 전에 탭 session을 모은다.** 종료가 닫는 창의 저장은 page가 `windowClose`를 부르기 전에 문서 영역이 있는 각 탭의 session history를 `tab-sessions/<tab>.json`([메모리 절약](plugins.ko.md#메모리-절약))에 쓴다. 그래서 호스트는 session이 저장된 뒤에야 창의 문서 영역을 닫는다.

**수정된 탭을 지키면 종료가 끝난다.** 종료는 준비된 창마다 닫기를 요청하고, 수정된 탭을 지킨 창의 페이지는 host 호출 `windowCloseKept`로 답한다([plugins](plugins.ko.md#탭-알림)). 그러면 host가 종료 상태를 끝낸다. 이후 마지막 창을 닫아도 애플리케이션이 종료되지 않고, WebContent process의 종료는 다시 오류 줄이 된다. `host.window`가 이 상태를 `quitting`으로 보고한다.

**page의 끝은 page가 빚진 것에 답한다.** window main page의 시작마다, 그리고 mygo window workbench의 build마다 그 page의 generation 하나가 시작되고, generation은 다음 event 가운데 처음 오는 것으로 끝난다: host의 다시 읽기 요청(`page-reload`), main webview의 WebContent process 종료(Wails host의 window event `WindowWorkbenchEnded`, Tauri host의 main webview web content process 종료), 그 window의 다음 page나 workbench의 시작, window 닫기. 그 event의 handler는 generation이 빚진 모든 것에 같은 turn 안에 답하므로, page의 어떤 요청도 오지 않을 수 있는 다음 page 시작을 기다리지 않는다: window를 준비되지 않은 상태로 두어 이후 page로 가는 요청은 곧바로 1003을 돌려받는다. host가 page와 그 window의 surface document로 보낸 요청을 모두 1003(`the document closed before it replied`)으로 끝내고, 다음 page가 시작할 때까지 그 surface document로 가는 요청을 1003으로 거부한다. page의 답이 필요한 surface document는 page가 끝난 뒤 답을 받지 못하기 때문이다. 그리고 window가 닫기나 종료를 위해 `project-close-request`로 page에 물었고 page가 아직 `windowClose`나 `windowCloseKept`로 답하지 않은 닫기 질문에 답한다: page가 준비되지 않은 window가 닫히듯 window가 닫힌다. 끝난 page는 탭을 지키지 않으므로, 그 window에 물은 종료는 계속된다. 빚진 것이 없는 끝은 아무것도 바꾸지 않으므로, process 종료 뒤에 오는 page 시작은 같은 generation을 다시 끝내도 효과가 없다. window의 surface document와 image 영역은 답을 빚지지 않으며 다음 page가 시작해 닫을 때까지 남는다([page 시작](native-host.ko.md#page-시작)).

**quit은 애플리케이션이 끝나기 전에 사이드카를 멈춘다.** 호스트가 quit을 받아들이면, 준비된 창의 저장 뒤에, 애플리케이션을 아직 끝내지 않는다. quit이 실행하는 사이드카의 중지를 시작하고([사이드카](sidecars.ko.md#선언과-시작)), framework의 quit 요청을 거절하며(Wails와 mygo framework의 quit hook은 false로 답하고, Tauri host는 exit 요청을 막는다), run loop를 비워 둔다. 그 중지의 마지막 프로세스가 종료하고 마지막 persistent owner의 close가 끝나면 호스트는 quit을 다시 요청하고 그 요청을 받아들인다. 그래서 framework의 shutdown 단계는 실행 중인 사이드카를 찾지 않는다. 애플리케이션 업데이트나 relaunch는 persistent service의 detach로 이 중지를 실행한다. 중지가 실행되는 동안 Quit 항목, Command+Q, Dock, quit Apple event, `host.quit`이나 호스트의 다른 quit으로 들어온 quit 요청은 중지를 끝낸다. 호스트는 아직 종료하지 않은 표준 입출력 사이드카마다 그 프로세스 그룹에 강제 종료 신호(SIGKILL)를 보내고 `info` level로 `sidecar <name>: the second quit kills process <pid>`를 쓰며, close가 끝나지 않은 persistent service마다 그 연결을 끝내고 `info` level로 `sidecar <name>: the second quit ends the connection of the service`를 쓴다. 그 뒤 중지는 그 종료와 연결의 끝으로 끝나고, 호스트는 그 요청을 첫 요청처럼 거절한다. quit Apple event는 호스트가 shutdown 단계 뒤에 답할 때까지 보류된 채로 있다. 종료 신호는 첫 요청처럼 quit을 요청하고, 두 번째 신호는 기본 동작으로 프로세스를 끝낸다.

**영속 사이드카는 애플리케이션보다 오래 살고 다시 붙는다.** 영속 서비스는 앱 재시작과 연결 단절을 지나 세션을 유지하며, 끊긴 연결은 즉시 다시 맺고 죽은 서비스는 재스폰한다([영속 서비스](persistent-services.ko.md)). 애플리케이션은 종료 시 영속 서비스를 죽이지 않는다. 두 호스트는 platform 연산 `NewSession`(Go) 또는 `new_session`(Rust)으로 영속 서비스를 새 session에서 시작하므로, 서비스는 애플리케이션의 process group이나 terminal의 signal을 받지 않는다.

**비영속 사이드카는 창과 함께 죽는다.** 표면 제거나 창 닫기가 닫힘을 알리고 프로세스는 채널과 함께 끝난다.

## Launch activation

Launch Services는 실행 요청이 activation을 요청하지 않은 경우(`open -g`, `kLSLaunchDontSwitch`, `NSWorkspaceOpenConfiguration.activates` false)를 빼고 자신이 실행한 애플리케이션을 activate하므로, host는 실행 시점의 activation을 시스템에 맡긴다. host는 다른 애플리케이션이 active인 동안 실행을 마칠 때 스스로 activate하지 않는다. Wails는 기본으로 regular activation policy의 모든 애플리케이션을 실행 시점에 activate하므로 Wails host는 `MacOptions.DisableActivationOnLaunch`를 설정하고, Tauri는 기본으로 다른 애플리케이션과 상관없이 activate하므로 Tauri host는 `activate_ignoring_other_apps(false)`를 설정하고, mygo는 기본으로 regular activation policy의 모든 애플리케이션을 실행 시점과 `Window.Show`마다 activate하므로 mygo host는 `App.SetSelfActivation(false)`를 호출한다. tao 0.37.2는 Tauri 설정에서도 `activateIgnoringOtherApps(false)`를 부르고, 그 호출은 다른 애플리케이션이 활성이 아닐 때 애플리케이션을 활성화한다. 그래서 workspace는 그 설정에서 activation 호출을 하지 않는 tao fork commit을 쓴다(`Cargo.toml`의 `[patch.crates-io]`). wry 0.57.0은 모든 webview를 만들 때 애플리케이션을 활성화하고, 이 호출도 다른 애플리케이션이 활성이 아닐 때 애플리케이션을 활성화한다. 그래서 workspace는 생성 시 activation 호출을 하지 않는 wry fork release를 쓰고, activation은 window의 show가 정한다. 애플리케이션을 연 사람은 애플리케이션이 앞으로 오는 것을 보고, `sok app relaunch`의 relaunch 같은 background 실행은 frontmost 애플리케이션을 바꾸지 않는다.

host 가 보이는 window 는 한 규칙을 따르고, 그 값은 시스템이 애플리케이션을 active 로 보는지 하나다(`NSRunningApplication.active`. virtual key window 가 대신 답하는 `NSApp.isActive` 가 아니다). 시스템이 active 로 보는 애플리케이션은 window 를 key 로 만들고 앞으로 올린다. 시스템이 active 로 보지 않는 애플리케이션은 앞 애플리케이션과 그 window 를 그대로 둔다. window 는 애플리케이션의 가장 앞 window 바로 위에 놓이고, 다른 window 가 보이지 않으면 모든 window 뒤에 놓이며, 애플리케이션의 key window 가 된다. virtual key window 가 답하는 동안에는 virtual key window 가 된다([virtual key window](exposure.ko.md#virtual-key-window)). check 와 endpoint run 은 실행 파일이나 `open -g` 로 시작하므로 activation 이 오지 않아, 그 window 는 사람이 쓰는 것 뒤에 머문다. 가려진 window 가 이들의 보통 경우다. Launch Services 로 애플리케이션을 연 사람에게는 앞으로 온다. activation 이 activation 전에 보인 window 까지 애플리케이션의 window 를 앞으로 가져온다. terminal 에서 실행 파일을 시작한 사람도 activation 을 요청하지 않았으므로 window 는 terminal 뒤에 열린다. 규칙은 `sp_window_show`(`native/darwin/src/window_reveal.h`)에 있다. mygo host 는 이것을 `App.SetWindowShow` 에, Wails host 는 `MacOptions.WindowShow` 에 넘기고, Tauri frontend 는 `Window::show` 대신 이것을 부른다. tao 가 보이는 모든 window 를 앞으로 올리기 때문이다. `Focus` 는 사람의 요청(사람이 누른 notification)이고 activate 한다. `input.pointer` 의 `activate: true` 는 activation 을 흉내 내고 아무것도 activate 하지 않는다([메서드](exposure.ko.md#메서드)).

새 window 는 애플리케이션의 가장 앞 window 가 있는 display 의 작업 영역 가운데에 열리고, 애플리케이션이 다른 window 를 보이지 않으면 main screen 에 열린다. Wails, tao, mygo 는 자기가 만든 window 를 active 애플리케이션의 key window 가 있는 display 인 `NSScreen.mainScreen` 에 놓으므로, active 가 아닌 애플리케이션의 새 window 는 다른 애플리케이션이 key window 를 둔 display, 곧 그 window 를 연 window 와 떨어진 곳에 열린다. 각 host 는 새 window 를 보이기 전에 `sp_window_place_new`(`native/darwin/src/window_reveal.h`)를 부르고, 저장된 frame 을 복원하는 host 는 그 뒤에 window 를 옮기거나 크기를 바꾼다.

그래서 check 는 자기가 보인 window 를 다른 애플리케이션의 window 가 바꾸지 않는 상태로 판정한다. window 가 order in 되었는지, frame 을 그렸는지, 가려진 동안에도 그리는지다(mygo window 는 가려진 동안에도 그리고, `diagnostics.window.draw-covered` 는 window 의 image region 을 가려진 동안에도 그리게 한다). window 가 열리는 위치를 보는 check 는 애플리케이션이 inactive 로 남는지와 그 window 뒤에 다른 애플리케이션의 window 가 없는지를 판정하고, 앞 애플리케이션이나 window 의 순번은 판정하지 않는다. 그동안 다른 애플리케이션을 쓰는 사람은 그 앞에 window 를 놓을 뿐이기 때문이다(`e2e/window-show-behind.test.mjs`). framework window event `WindowShow` 와 `WindowHide` 는 window 의 occlusion 변화를 알리고, 다른 애플리케이션의 window 가 전부 덮은 채로 열린 window 는 둘 다 알리지 않는다([image region](native-surfaces.md#image-regions)). 그래서 check 는 그 변화가 자기 대상일 때만 이 event 를 기다린다. 자기 window 의 pixel 을 재는 check 는 앞의 window 가 바꾸지 않는 window 자체를 녹화하고, 녹화하는 동안 `diagnostics.window.draw-covered` 를 유지한다. 그래서 가려진 window 도 화면에서처럼 그리고, check 는 다른 애플리케이션의 window 와 무관하게 그것을 잰다. 어떤 check 도 자기 window 를 올리거나 사람의 window 앞으로 가져오지 않는다. 모든 check 는 그 뒤에서 시작하고, window 의 occlusion 이 대상인 check 는 그 window 를 자기 window 로 덮은 뒤 덮인 window 가 `occluded` 를 보고하고 document 를 숨기는지를 판정한다. 이 판정은 그전에 무엇이 덮고 있었든 성립한다. window server 는 화면의 모든 window 로 occlusion 을 계산하고 `orderWindow:relativeTo:` 는 같은 level 의 모든 window 사이에서 순서를 정하므로, check 는 자기 window 끼리만 순서를 정할 수 없다. 덮개가 걷히는 것처럼 덮이지 않은 window 에서만 보이는 occlusion 의 변화는 window check 가 판정하지 않는다.

이 규칙은 최소화한 window 의 복원을 다루지 않는다. `deminiaturize:` 는 애플리케이션이 active 인지와 상관없이 window 를 다른 모든 window 위에 놓는다. active 가 아닌 애플리케이션은 active 가 아닌 채로 있고 앞 애플리케이션도 그대로 앞에 있으므로, 복원된 window 가 사람이 쓰는 것을 가린다. 사람은 Dock 으로 window 를 복원하고 Dock 이 애플리케이션을 activate 한다. endpoint 에는 window 를 최소화하는 command 가 없어 check 와 endpoint run 은 이 경우에 닿지 않으므로, host 는 복원을 AppKit 에 맡긴다.

Windows 의 창도 같은 규칙을 따르며, 그 값 하나는 foreground 창이 이 프로세스의 것인지다. Tauri host 는 visibility 를 쥔 tao 로 창을 보이고, 창의 subclass 가 그 show 의 위치 변경에 `SWP_NOACTIVATE` 와 `SWP_NOZORDER` 를 더한다. Go 플랫폼은 `SW_SHOWNOACTIVATE` 로 `ShowWindow` 를 호출하며, Wails 는 아직 이를 부르지 않는다 ([features](../features.ko.md)). 이 경로는 Windows 에서 실행된 적이 없어 효과가 확인되지 않았다.

## 애플리케이션 로그

[진단](diagnostics.ko.md)이 모든 기록과 그 형태, 각 실패가 기록을 남기는 곳을 정한다. 애플리케이션의 모든 진단 파일은 고정된 폴더 하나, 설정 디렉터리의 `logs/`에 있다: 애플리케이션 로그, [성능 트레이스](performance-trace.md), 서비스 로그, 응답 멈춤 sample, 그리고 `logs/captures/`의 정지 캡처와 녹화. 결함을 만난 사람은 이 폴더를 넘겨준다.

각 호스트는 기록을 설정 디렉터리의 event log `logs/host-<boot>.jsonl`(level `error`, `warn`, `info`)과 `logs/host-<boot>.debug.jsonl`(`debug`, `trace`)([로깅](logging.ko.md#파일))에, raw 표준 오류를 `logs/host-<boot>.stderr`에 쓴다. `<boot>`는 시작 시각(초)과 프로세스 식별자다. 호스트는 설정 디렉터리의 process lock을 잡는 [엔드포인트](endpoint.ko.md)를 만든 직후 event log의 writer를 시작하고, stderr 파일을 mode 0600의 덧붙이기로 열고 플랫폼 표준 오류 연산으로 프로세스의 표준 오류를 그 파일로 바꾼다. 각 실행은 기록 `info host run: <애플리케이션 식별자> pid <pid>`로 시작한다. stderr 파일에는 계약의 writer가 쓰지 않는 것만 담긴다. 런타임의 crash 출력과, signal handler가 호출할 수 있는 호출만으로 쓰는 native 라이브러리의 fatal 줄(`<time> error native fatal: <name>`)이다. Wails 호스트는 Go runtime 치명 오류의 출력을 `logs/host-<boot>.crash`에도 쓰고(`debug.SetCrashOutput`) traceback level `crash`를 정한다. 그래서 그 출력 뒤에 runtime이 `SIGABRT`로 프로세스를 끝내고, 시스템이 모든 thread의 native frame을 담은 crash report를 쓴다. Tauri 호스트의 native code fault는 그 fault의 signal로 프로세스를 끝내고, 시스템이 report를 쓴다. 엔드포인트가 생기기 전에 쓴 출력은 프로세스가 시작될 때의 표준 오류로 간다. 호스트의 기록, 호스트가 줄 단위로 읽는 모든 비영속 사이드카의 표준 오류 줄, 페이지가 host 호출 `log`의 배치로 중계하는 기록은 stderr 파일의 줄이 아니다. 호스트가 그 기록을 [event log](logging.ko.md#파일)에 `where`와 `text` field를 가진 event `<layer>.record.<level>`로 저장하고, event log의 writer가 생기기 전에 쓴 기록은 1024개를 담는 시작 buffer에서 기다리며 buffer가 거부한 기록은 writer가 `log.dropped`로 센다.

워크벤치 기록은 layer가 `workbench`이고, 오류를 알리면 level이 `error`, 아니면 `info`다. 워크벤치는 메인 문서에 보이는 모든 오류, 처리되지 않은 모든 오류와 promise rejection, 거부된 모든 상태 변경, 실패한 모든 표면 mount와 배경 session, 실패한 모든 자체 검증(`error workbench verify: <n> fail — …`)을 이 형식으로 보고한다. 나중의 reload가 문서에서 오류를 지워도 event log에는 각 오류 기록이 남으므로, window check는 event log로 모든 오류 발생을 판정한다. host가 없는 페이지는 실패를 콘솔에 오류로 쓴다.

오류를 알리는 호스트 기록은 level이 `error`이고 layer가 `host`다. `<where>`는 실패한 연산이나 대상의 이름이고 `<text>`는 실패 내용이다. 각 호스트는 helper 하나(Go의 `LogError`, Rust의 `log_error`)로 그 기록을 event `host.record.error`로 쓰며, 두 호스트에 모두 있는 site는 두 호스트에서 같은 `<where>`와 `<text>`를 쓴다. 호스트의 record helper(Go의 `LogError`, `LogWarn`, `LogInfo`, Rust의 `log_error`, `log_warn`, `log_info`, `log_failure`)가 쓰는 기록마다 helper를 부른 호출의 `<file name>:<line>`인 field `site`를 담는다. 그래서 여러 호출이 같은 `<where>`와 `<text>`를 쓰는 기록도 자기 호출을 밝힌다. file name은 source 경로의 마지막 요소이므로 site는 build 폴더에 따라 달라지지 않으며, 두 호스트의 source가 다르므로 호스트마다 다르다. native 라이브러리는 `sp_log_error`와 `sp_log_info`로 기록을 event `native.record.error`와 `native.record.info`로 프로세스의 ring에 저장하고, host의 writer가 그것을 event log로 pull한다. 로그를 연 뒤의 치명적 실패는 프로세스가 끝나기 전에 기록을 쓰고 writer가 저장할 때까지 기다린다. level이 `info`인 호스트 기록은 관측이며 event `host.record.info`로, Go의 `LogInfo`, Rust의 `log_info`로 쓴다. 관측은 예상된 상태를 기록하며 그 상태를 말한다. 예를 들어 `exposure reply <id> of removed surface "<surface>" arrived after its request ended`, 그리고 호출자가 이미 자신의 실패를 반환한 뒤에 완료가 쓰는 `<operation> arrived after its request ended`가 있다. 호스트는 실패를 관측으로 쓰지 않는다. 요청이 받는 실패는 그 실패를 받은 요청자가 보고하며, 다른 곳은 그 실패의 줄을 쓰지 않는다. 호스트는 어떤 요청도 보고하지 않는 실패에만 오류 줄을 쓴다. 예를 들어 그림 표시 제한 시간은 그것을 기다린 표면 준비나 표시 요청의 답이므로 두 호스트 모두 그 줄을 쓰지 않는다. 페이지의 배치 대기열이 그 답을 받아 기록 `error workbench surface presentation failed: <text>`로 보이며, 이것이 그 실패의 유일한 기록이다. 배치 대기열은 실패한 배치를 거절이 아니라 실패한 상태로 그 배치를 예약한 코드와 그 배치를 기다리는 모든 대기에 답하므로, 그 배치를 기다린 프로젝트 전환이나 다른 명령, 그리고 어떤 명령도 기다리지 않는 몸짓의 배치는 그 실패의 줄을 쓰지 않는다. 애플리케이션 framework의 오류 출력도 같은 helper를 거친다(`<where>`는 `wails`). Tauri runtime에는 설치된 logger가 없다.

영속 서비스는 자신을 시작한 호스트보다 오래 살기 때문에 호스트의 표준 오류를 물려받지 않는다. 호스트는 영속 서비스를 시작할 때 `logs/<실행 파일 이름>.log`를 mode 0600의 덧붙이기로 열어 서비스의 표준 오류로 넘긴다. 서비스는 표준 오류를 글 기록 형식으로, layer `sidecar`와 서비스 이름을 `<where>`로 써서 남긴다([sidecars](sidecars.ko.md)).

호스트가 100 MB 이상인 로그 파일을 열 때는 먼저 그 파일을 `<이름>.1`로 바꾸고, 이전 세대 `<이름>.1`부터 `<이름>.4`까지를 하나씩 뒤로 옮기고 `<이름>.5`를 지운 뒤 새 파일을 시작한다. 호스트는 다른 프로세스가 쓰지 않을 때만 로그 파일을 연다. 애플리케이션 로그는 process lock을 잡은 동안 실행마다 한 번 열고, 서비스 로그는 그 서비스를 시작할 때만 연다. 실행이나 서비스는 다음에 열 때까지 크기 제한 없이 덧붙이므로, 다음 실행이나 다음 서비스 시작이 상한을 적용한다.

애플리케이션 로그를 열 수 없거나 표준 오류를 바꿀 수 없는 호스트는 시작하지 않으며, 그 오류를 시작할 때의 표준 오류에 보고한다. 서비스 로그를 열 수 없는 호스트는 그 서비스를 시작하지 않고 `sidecar <name>: service log: <error>`로 시작을 실패시킨다.

`apps/wailsv3/go.mod`는 Go language host library의 모듈과 Wails framework adapter의 모듈을 요구한다. `apps/tauriv2/Cargo.toml`은 경로로 지정한 `soksak-host-tauriv2`와 `tauri`에 의존한다. `apps/tauriv2/build.rs`는 `tauri_build::build()`만 호출한다.

Wails 바인딩 서비스 이름은 `github.com/soksak-app/core/packages/host/wailsv3/src.Bindings`다. Wails가 Wails framework adapter의 바인딩 타입 `Bindings`의 Go 패키지 경로와 타입 이름으로 이 이름을 만들고, `apps/wailsv3/runtime/index.js`가 이를 사용한다. 이 서비스의 바인딩 메서드는 `Call(method, args)` 하나이며, 각 호출을 Go language host library의 바인딩으로 넘긴다. 바인딩은 `Host`의 내보낸 메서드 `method`를 이름으로 찾아 실행한다(`binding_record.go`). 그래서 main page의 모든 호출은 event `host.binding.call`을 저장하는 한 곳을 지나고, 선택적 context 뒤에 `json.RawMessage`가 아닌 매개변수를 가지거나 선택적 값과 선택적 오류가 아닌 결과를 가진 host 메서드는 그 메서드의 이름을 말하는 오류로 host 시작을 멈춘다. Tauri framework adapter는 모든 command를 `bindings!` 매크로(`bindings.rs`) 안에서 정의한다. 매크로는 각 command에 첫 인자로 `BindingCall`을 주고, command의 결과로 그것을 끝내며, 등록을 생성하므로 등록된 command가 곧 기록되는 command다. Tauri는 command의 invoke 결과를 프레임워크의 resolver에만 넘기고 host가 그것을 감쌀 수 없으므로, 매크로는 resolver가 아니라 command 함수를 감싼다.

## 애플리케이션 인자

애플리케이션은 `--config-dir PATH`([projects](projects.ko.md#저장))를 두 인자 또는 `--config-dir=PATH`로 받는다. 두 host는 창을 열기 전에 하나의 규칙으로 인자를 읽는다. 애플리케이션이 선언하지 않은 인자는 `unknown argument <argument>`로, 값 없는 flag는 `--<flag> needs a value`로, 두 번 준 flag는 `--<flag> is given twice`로 실패한다. 애플리케이션은 그 문장을 표준 오류에 쓰고 상태 2로 끝난다.

애플리케이션은 macOS 의 argument domain 쌍 `-Name value` 도 받는다. 이름은 글자나 밑줄 뒤에 글자, 숫자, 밑줄이 오는 식별자다. Foundation 이 그 쌍을 명령행에서 직접 `NSUserDefaults` 의 `NSArgumentDomain` 으로 읽으므로, 쌍 하나는 그 process 에만 default 를 정한다(다른 플랫폼은 그 쌍을 읽지 않는다). 예를 들어 `-AppleShowScrollBars Always` 는 native view 와 page 의 scroller style 을 정한다. 두 host 는 같은 규칙으로 그 쌍을 넘긴다. 값이 없거나 빈 쌍은 `-<Name> needs a value` 로, 두 번 준 이름은 `-<Name> is given twice` 로, `-` 하나뿐이거나 식별자가 아닌 이름은 `unknown argument <argument>` 로 실패한다.

진단 build는 `--registry-ca PATH`도 받는다. host의 registry 받기가 운영체제의 인증 기관 대신 신뢰하는 인증 기관을 담은 PEM 파일이며([받기](installation.ko.md#받기)), window check가 local TLS registry를 쓸 수 있게 한다. 읽을 수 없거나 인증서가 없는 파일은 `--registry-ca <path>: <reason>`과 상태 2로 시작을 끝낸다. release build는 이 인자를 선언하지 않으므로 모르는 인자로 거부한다.

## 프런트엔드와 실행 파일

`sok-copy-frontend`는 프런트엔드를 `apps/<app>/src/frontend/`에 배치하며, 각 애플리케이션의 `.gitignore`가 이 디렉터리를 제외한다. `apps/mygo`에서 이것은 view root이고([스테이징 배치](plugins.ko.md#스테이징-배치)), `src/main.go`가 Wails처럼 포함한다. `go:embed`는 포함하는 패키지 디렉터리 아래의 파일만 포함할 수 있으므로 Wails는 `src/main.go`의 `//go:embed all:frontend`로 이 디렉터리를 포함한다. Go language host library의 `Prepare`는 `frontend/`를 자산 루트로 사용한다. Tauri는 `tauri.conf.json`의 `"frontendDist": "src/frontend"`로 이 디렉터리를 읽고, `src/main.rs`는 `frontend/background.js`를 포함한다.

macOS에서 각 애플리케이션은 애플리케이션 번들에서 실행된다. 운영체제의 알림 센터가 번들에서 실행된 프로세스만 받기 때문이다([플러그인](plugins.ko.md#탭-알림)). 두 release 애플리케이션은 표시 이름 `soksak`의 `soksak.app`이다. release 번들은 `target/release/wailsv3/soksak.app`과 `target/release/tauriv2/soksak.app`이고, 번들 식별자는 설정 디렉터리의 식별자인 `app.soksak.wails`와 `app.soksak.tauri`다([projects](projects.ko.md#저장)). 디버그 번들은 release 애플리케이션 옆에서 함께 실행되도록 이름을 유지한다. `target/debug/sok-wailsv3.app/Contents/MacOS/sok-wailsv3`와 `target/debug/sok-tauriv2.app/Contents/MacOS/sok-tauriv2`이며, 번들 이름은 실행 파일 이름이고 식별자는 `app.soksak.wails.dev`와 `app.soksak.tauri.dev`다. 각 번들 안의 실행 파일은 `sok-wailsv3` 또는 `sok-tauriv2`다. 빌드는 각 번들의 `Contents/Info.plist`를 release 값을 선언한 `apps/<app>/platform/darwin/Info.plist`에서 쓰고, 디버그 빌드는 번들 식별자와 번들 이름을 바꾼다. Dock이 보이는 soksak 아이콘 `apps/<app>/platform/darwin/AppIcon.icns`를 `Contents/Resources/`에 복사하며, 번들에 ad hoc 서명을 하고 LaunchServices에 다시 등록한다. Dock은 등록된 번들의 아이콘을 보이며, 번들 안의 파일만 바뀌면 LaunchServices는 번들을 다시 읽지 않는다. 번들에는 플러그인도 사이드카도 없다. 호스트는 설정 디렉터리에 설치된 플러그인을 제공하고 사이드카를 시작하며, `plugins/installed.json`이 기록한 폴더를 쓴다([설치](installation.ko.md#설치된-plugin-제공)).

## mygo host

mygo host는 framework mygo 위의 세 번째 host다. workbench를 native UI로 그리므로 window는 main page 없이 실행된다. 이 절은 mygo host를 기술하며, [기능 상태](../features.ko.md)가 그 구현과 그것이 요구하는 Wails host와 Tauri host의 각 변경을 기록한다. [Performance goals](#performance-goals)가 그 비용의 상한을 둔다.

### Main page의 비용

Wails host와 Tauri host는 workbench를 window마다 WKWebView 하나 안의 JavaScript page(main page)로 그린다. Plugin view, document region, image region은 그 page의 layout을 따르는 native view다. 측정된 비용은 다음과 같다.

### mygo 사실 (v0.7.4)

mygo에 관한 모든 진술은 tag v0.7.4에서 읽은 [출처](#출처)를 `[Sn]`으로 인용하며, 이 대괄호 번호는 benchmark의 scenario S0부터 S16과 다르다. purego와 Go runtime에 관한 진술은 mygo가 요구하는 version을 인용한다.

#### Threading과 native 호출

- `mygo.go`는 `Version`을 `0.7.4`로 설정하고 `init`에서 `runtime.LockOSThread()`를 호출하므로, main goroutine은 process를 시작한 thread에서 실행된다[S1]. 이 module은 Go 1.27.3과 purego v0.11.1을 요구한다[S3].
- mygo는 cgo를 쓰지 않는다: native API는 실행 시점에 purego(`dlopen`과 assembly trampoline)를 통해 호출한다[S4][S5]. AppKit이 호출하는 Objective-C method는 callback으로 등록된 Go function이며, purego callback은 결코 해제되지 않는 희소한 자원이다[S4][S7]. purego callback은 calling thread에서 `crosscall2`를 통해 Go로 들어가며, Objective-C method는 purego callback으로 등록된다(`objc.NewIMP`)[S29].
- main goroutine은 main thread에 고정된 채로 있다; 모든 platform method와 모든 handler는 main thread에서 Go로 실행되며, listener는 main thread에서, IPC handler는 goroutine에서 실행된다[S6]. main thread는 `pthread_main_np`가 true를 반환하는 thread다; `RunOnMain`은 main thread에서는 function을 즉시 실행하고 그 밖에서는 function을 main thread에 post한 뒤 기다리며, `await`는 main thread에서 기다리는 동안 `Backend.Step`으로 native event를 처리한다[S2].

#### Window, web view와 native handle

- window는 page와 native UI 중 하나를 보인다(`WindowOptions.Content`). `Window.NewWebView`는 native UI를 보이는 window에서만 web view를 만들며, page를 보이는 window에서는 `errNoContent`로 실패한다[S11][S12].
- native UI window에서 WKWebView는 content view 안의 Metal surface 아래에 있는 뒤집힌 clip view(`MyGoClipView`)에 놓인다. native UI는 web view가 보이는 자리에 구멍(`OpHole`)을 칠하며, surface의 `hitTest:`는 web view가 pointer를 받는 자리에서 nil을 반환한다[S12][S13].
- `ui.WebView`는 window가 만든 web view만 배치한다: `surface.WebView`는 `*mygo.WebView`의 native 쪽을 반환하고, web view element만 구멍을 칠하며, window는 자기 web view의 배치(frame, clip, cover)를 그것을 그리는 frame에서 surface에 넘긴다[S14]. mygo에는 임의의 native view를 배치하는 element가 없다.
- 유일한 공개 native handle은 window다: `Window.NativeHandle`은 `NSWindow`를 반환한다[S10]. web view handle(`WebViewHandle`)은 internal package에 있다[S10].
- mygo는 각 web view를 자기 구성과 delegate로 만든다(`createWebView`)[S10]; v0.7.4에는 다른 library가 만든 `WKWebView`를 받는 operation이 없다.
- mygo surface view는 file URL에 대해 등록하며, drop된 파일을 content의 event로서 직접 받는다[S27].

#### 이미지

- `ui.NewBitmap`은 자기 pixel을 CPU와 GPU에 둔다; `Update`는 그림을 교체하고 새 pixel을 업로드한다[S15]. Metal renderer는 이미지의 version이 바뀌면 진행 중인 frame을 기다린 뒤 `replaceRegion:`으로 이미지 전체를 업로드한다[S15]. v0.7.4의 tree에는 IOSurface 사용이 없다.

#### IPC

- page bridge는 JSON 메시지를 나른다; `[]byte` 값은 base64 문자열이다[S16]. custom protocol handler는 main thread에 body를 256 KiB chunk로 넘긴다[S16].

#### Application 수명 주기

- `applicationShouldTerminate:`는 종료가 수락되면 run loop를 멈추고 `NSTerminateCancel`을 반환한다; mygo는 `applicationWillFinishLaunching:`에서 quit Apple Event에 대한 자기 handler를 설치한다[S8][S9].
- `applicationDidFinishLaunching:`은 activation policy가 regular일 때 애플리케이션을 활성화하며, `Window.Show`는 애플리케이션을 활성화한다; `Window.ShowInactive`는 활성화 없이, 그리고 key로 만들지 않고 window를 보인다[S9][S22]. `Window.OnReadyToShow`는 숨겨진 채 만들어진 window가 첫 frame을 그리면 한 번 실행된다[S22].
- `App.Run`은 `quitOnSignals`를 호출하며, 이는 SIGINT와 SIGTERM이 애플리케이션을 종료하게 한다[S20]. 애플리케이션 delegate는 알림이 지원될 때 notification center delegate(`MyGoNotificationDelegate`)를 설정하고[S9][S21], `applicationDockMenu:`에 mygo `Dock` API의 menu로 응답한다[S9].

#### Native UI 렌더링

- native UI는 Metal로 그리고 Core Text로 텍스트 layout을 잡는다; 텍스트 입력은 `NSTextInputClient`를 사용한다[S18].
- frame은 요청이 있을 때 그린다: 일시 정지된 `CADisplayLink`는 frame이 연이어 이어지는 동안에만 tick한다[S17]. frame은 자기 drawable이 그려진 뒤 바뀐 것만 그린다(`gpu.Ages`, `scene.Differ`)[S17]. 안정된 window는 frame을 요청하지 않고 timer를 걸지 않는다(`TestSettledWindowSleeps`); macOS에서 작은 유휴 native UI window는 44 MB를 차지하며, counter 예제는 유휴 시 코어 하나의 약 0.005%를 쓴다[S5].
- Metal layer는 정지 시 drawable 하나, window가 animation 중인 동안 세 개를 유지하며, timer가 마지막 frame 후 이 초가 지나면 drawable을 줄인다; Metal driver는 일시 정지 후 command queue의 첫 command buffer를 위해 target의 크기, shader, queue의 최대 command buffer 수와 상관없이 process footprint 중 약 92 MB를 차지하고, 마지막 command buffer가 끝난 약 1.5초 뒤 또는 queue를 놓는 즉시 이를 돌려준다(macOS 26.6 arm64, F768)[S17]. scale 2의 1200×760 point window는 animation 중 device memory 47.6 MB(14.6 MB drawable 세 개와 frame의 texture)를, 정지 시 16.7 MB를 쥔다.
- layer를 바꾸는 frame, 또는 web view를 보이는 window가 그리는 frame은 Core Animation transaction으로 present하며(`presentsWithTransaction`), 그래서 web view는 frame과 같은 transaction에서 움직인다; 그런 frame은 그 안에서 아무것도 바뀌지 않았어도 그려지며, 진행 중인 fetch가 있으면 그 뒤에 main thread에서 drawable을 얻는다. 그 밖의 frame은 GPU가 받는 즉시 present하며, presenter가 자기 thread에서 fetch한 drawable을 쓰므로 main thread는 display를 기다리지 않는다[S17][S26].
- engine은 보이지 않는 window의 frame을 hold하며, 그런 window의 frame 요청은 display link를 기다린다[S28].
- engine은 보조 기술이 surface의 내용을 요청하면(`AccessibilityOn`) 그때부터 모든 frame을 accessibility tree로 기술한다[S18]; automation hook은 automation plugin이 tree를 읽을 때 tree를 만든다. element key와 action은 애플리케이션이 automation plugin을 link하고 `MYGO_AUTOMATION`이 요청할 때에만 automation plugin에게 넘겨지며, tag `mygo_noinspector`를 둔 build는 그 hook을 뺀다[S19].
- 측정된 native UI frame: 정적 label 1,000개는 CPU renderer에서 할당 없이 frame당 397 µs가 들고, label 1,000개를 가진 warm-up된 view는 Go heap 약 2.50 MB를 유지한다; 이 측정은 native window와 GPU 메모리를 제외한다[S23].

#### 성숙도

mygo는 version 0.7.4이며, tag의 이력은 2026-09-26에 시작한다[S25]. version 0 module은 어느 release에서든 API를 바꿀 수 있다.

### Native workbench

**Page 모드는 이득이 없다.** JavaScript workbench를 page로 보이는 mygo window는 main page와 그 WebContent process(C1, C4, C5), 그 그래픽 메모리(C3), 그리고 각 layout transaction에서 main page의 presentation에 대한 대기(C9의 세 대기 중 하나)를 그대로 유지한다. 이득을 얻으려면 host가 workbench를 native UI로 그려야 한다: 결정 D1.

**mygo는 main thread 규칙을 어긴다.** 애플리케이션 process는 view page나 document region이 존재하는 즉시 JavaScriptCore VM을 가지며, 그러면 main thread의 Go 코드가 `pas_panic_on_out_of_memory_error`에서 process를 끝낸다([Wails host의 main thread](#wails-host의-main-thread)). mygo는 모든 handler와 모든 native UI build를 main thread에서 Go로 실행한다[S6]. 이 규칙은 framework 변경으로만 충족된다: U1(D3).

**Native view에는 element가 필요하다.** plugin view page, document region, image region은 `native/darwin`(`sp_document_create`, `sp_region_create`)이 만들며, 만드는 자리는 `sp_surface_create`가 main web view의 window 합성 안에 배치하는 `SurfaceHost` 안이다([`webview_geometry.h`](../../native/darwin/src/webview_geometry.h)). mygo는 자기 web view만 배치하며[S14] IOSurface 경로가 없다[S15]. 따라서 설계에는 mygo의 native view element(U2)와 main web view 없는 surface host(N1)가 필요하다(D4).

**View는 device pixel에 선다.** Framework는 native view element의 각 edge를 자기가 칠하는 edge와 똑같이 가장 가까운 device pixel로 반올림한다. 그래서 mygo workbench는 layout이 말하는 slot을 소수든 아니든 그대로 view에 준다. View와 그 옆의 선은 같은 device pixel을 쓰고 그 사이에 card pixel이 보이지 않는다. `core.surfaces`는 slot을 `declared`로, 그 device pixel을 `applied`로 적는다. 이 판정은 각 slot에서 host가 view에 적용한 frame의 device pixel을 page가 선언한 frame의 device pixel과 비교한다(`e2e/view-edges.test.mjs`).

**Native workbench가 더하는 비용.** host process는 workbench의 상태를 Go heap에 가지며, Go runtime은 이를 적어도 이 분마다 수집한다[S30]. 또 보조 기술이 요청하면 모든 frame의 accessibility tree를 가진다[S18]. Metal layer는 정지 시 window 크기 drawable 하나, window가 animation 중인 동안 세 개를 유지하며, Metal driver는 일시 정지 후 첫 command buffer를 위해 30~45 MB를 차지한다; 둘 다 마지막 frame 후 약 이 초 뒤에 돌아오며, 그때 timer가 GPU instance buffer, atlas, image, backdrop texture와 command queue도 해제하므로, 일시 정지 후 첫 frame은 main thread가 기다리는 동안 step 안에서 drawable을 얻고 그 buffer, texture, queue를 다시 만든다[S17]. focus된 편집 가능한 텍스트 필드는 focus를 얻거나, 그 텍스트가 바뀌거나, 그 window가 key가 된 뒤 30초 동안 530 ms마다 frame을 그리며, 이로 인해 그 30초 동안 drawable과 driver 메모리가 유지된다[S31]. layer나, web view 또는 native view element의 배치(box, clip 또는 cover)나, native glass view의 배치를 바꾸는 frame은 Core Animation transaction으로 present하며 main thread가 기다리는 동안 step 안에서 drawable을 얻으므로, 그런 frame마다 AppKit display cycle 한 번과 commit 한 번이 든다[S17]; v0.7.4에서는 web view를 보이는 window의 모든 frame이 그 안에서 아무것도 바뀌지 않아도 그렇게 present하며[S26], U2는 이를 layer나 배치를 바꾸는 frame으로 한정한다. 각 step과 각 전달된 call은 worker와 main thread 사이에서 thread 깨우기 두 번으로 이루어진 교환 하나다(U1): 크기, layer, 배치를 바꾸지 않는 frame은 step 2개와 전달된 call 6개이고, pointer 이동은 step 1개와 전달된 call 4개, 커서가 바뀌면 6개이며, mygo host에서 pointer 이동은 `native/darwin`의 pointer routing이 이동마다 보내는 `hitTest:`를 위한 별도 step 뒤에 온다(D3). framework가 등록하는 각 Objective-C callback은 process 수명 동안 등록된 채로 있고, process 하나는 그런 callback을 최대 2,000개 가지며, 그 수를 넘는 등록은 panic으로 process를 끝낸다[S7][S32]. G2, G3, G8이 이 비용에 상한을 둔다. G2와 G8은 이동의 `hitTest:`와 `mouseMoved:` step을 `input.pointer`의 이동(`scripts/measure-app-usage.mjs`의 `--step pointer`)으로 측정한다. host는 그 이동을 애플리케이션의 event dispatch가 사람의 이동을 전달하듯 전달한다. 창의 content view를 hit-test해 그 점 아래의 web view를 찾고, 그 점을 담은 각 tracking area에 `mouseMoved:`를 준다(`native/darwin/src/input_inject.m`의 `moveTo`).

### Workbench

`packages/workbench-mygo`(Go module, package `workbench`)는 mygo `ui` widget과 layout으로 workbench를 그린다. `src/layout`은 Go layout model을 담는다: `packages/soksak`의 grid와 card geometry, `packages/workbench`의 project, space, tab과 그 저장 형식, 배치가 읽는 카드의 값(탭 순서, 활성 탭, 머리가 폭을 재는 탭 이름, 글자 배율, 접힘 상태를 포함한 sidebar), 그리고 카드 머리의 접힘 단계다. 이 model은 mygo package를 import하지 않는다. mygo `ui`의 path에는 arc가 없으므로, outline은 공유 case와 page workbench가 기술하는 대로 arc를 유지하고 shell은 사분원 arc 하나를 cubic 하나로 그리며, 그 cubic은 반지름의 0.03 % 안에 머문다. layout case는 `docs/spec/cases`의 JSON 파일이며, `packages/soksak`, `packages/workbench`, `packages/workbench-mygo`의 test가 이를 읽는다. 화면: rail, library, card와 tab strip, sidebar frame과 seat, menu, settings window, plugin 화면, debug view, error 표시, modal. mygo host에서 interactive element는 U4의 element tree의 element 중 action에 press, increment, decrement, value 또는 expansion이 포함된 element다(`ActionPress`, `ActionIncrement`, `ActionDecrement`, `ActionSetValue`, `ActionExpand` [S38]); `packages/workbench-mygo`의 binder는 각 interactive element를 만들 때 그 element를 선언된 command에 연결하고 그 element name(D7)을 주며, 보이는 각 상태는 선언된 status다. `core.workbench.audit`와, plugin API의 `audit(root)` 및 `core.surface.document`의 `unbound`는 command나 element name이 없는 각 interactive element를 모든 host에서 `{role, expose, command, text}`로 나열하며, 여기서 `role`은 ARIA role 이름이다: mygo host에서는 `packages/workbench-mygo`의 표 하나가 `ui.Role`의 각 role에 주는 이름이고 [S38], document에서는 element의 `role` attribute 또는 그 tag의 암묵적 ARIA role이며, `contenteditable` element에는 `textbox`다. mygo workbench의 modal은 workbench의 일부이며, 그 control은 같은 binder를 통해 command를 실행한다. `packages/workbench`는 Wails와 Tauri host의 workbench로 남는다.

두 workbench는 하나의 제품을 구현하며, 세 mechanism이 둘을 같게 유지한다:

- **선언.** `packages/workbench-mygo`는 `packages/workbench`의 `exposure.json`, `shortcuts.json`, `workbench.json` 사본을 embed하며, `make check-exposure`는 지금 `core-exposure.json`을 그렇게 하듯 이 사본들을 원본과 같게 유지한다. `make check-exposure`는 또한 exposure check의 규칙 1과 2를 `packages/workbench-mygo`의 Go source에 적용한다: Go source가 registry나 binder에 넘기는 모든 status, command, element name은 선언되어 있고, 선언된 모든 status와 command는 등록되어 있으며, 선언된 모든 element name은 어떤 element에 주어진다. 그 test는 `packages/plugin-api`의 `contributions.json`과 `apps/mygo`의 `environment.json` 사본을 같은 검사 아래 가진다.
- **Host call.** `packages/workbench-mygo`는 language host library의 host handler를 각 handler의 이름을 적은 표 하나, 즉 `src/host_calls.go`의 `hostCalls`를 통해서만 호출한다. Wails host의 각 service call이 자기 goroutine에서 도착하듯, workbench는 `hostCalls`의 각 handler를 자기 goroutine에서 실행하고 그 answer를 나중 step에서 받는데, `SyncSurfaces`와 `PresentSurfaces`가 U1의 worker에서 실행되는 작업을 기다리기 때문이다; 그런 goroutine은 각각 language host library의 `routine.Go`를 통해 시작하고, 한 sidecar로의 send처럼 specification이 순서를 요구하는 call은 그 순서의 이전 call이 끝난 뒤에야 시작한다. [Host parity](host-parity.ko.md) 명제 1은 `runtime/index.js`의 `METHOD`와 `COMMAND`를 읽듯 그 표를 읽는다: 각 표의 각 이름은 그 host의 handler를 가지며, 세 표는 framework 표의 B 행이 나열하는 call, 즉 mygo에 없는 call(native modal web view의 overlay call과 shape call)과 mygo에만 있는 call(dialog background)을 제외하면 같은 이름을 담는다.
- **동작.** [host parity](host-parity.ko.md)의 명제 8은 세 application이 같은 status, command, element name을 선언하고, 모든 window check가 세 application에 대해 실행된다고 말한다. 단, 대상이 main page나 modal web view인 check는 `MAIN_PAGE_APPS`를 순회한다; `scripts/check-hosts-same.mjs`가 `make check-exposure`의 사본 규칙과 `scripts/check-e2e-host-parity.mjs`의 규칙으로 이를 판정한다.

workbench의 element tree(U4)가 binder audit, element 사각형, element action에 answer를 주므로, window check는 `endpoint.json`을 통해 세 application에 대해 실행된다. 단, 대상이 main page나 modal web view인 check는 제외한다. head가 숨긴 tab처럼 page가 `display:none`으로 두는 element는 크기 없이 tree에 있다: 같은 이름의 element 사이에서 index를 유지하고, `element.rect`는 0으로 답하며, `element.act`는 그것을 누르고, pointer와 keyboard는 그 위에 멈추지 않는다.

host는 요청을 [relay](exposure.ko.md#전달)의 event `exposure-request`로 workbench에 보내며, 이 event는 `Frontend.Emit`과 `Workbench.Emit`을 거쳐 workbench에 닿는다. `src/requests.go`의 `Requests`는 각 요청을 main thread의 한 step에서 `Registry.Answer`로 처리하고(눌린 element의 command도 이 thread에서 실행된다) 그 answer를 host call `exposureReply`로 돌려보낸다. watch 중인 status는 그 값을 `exposureChanged`로 보낸다. `Registry.Answer`는 page registry의 answer와 refusal을 같은 순서로 낸다. element 요청은 그 step에서 마지막 frame의 element tree를 읽는다: 사각형은 window point 단위의 element frame이고 `zoom`은 1, `document`는 `{x: 0, y: 0}`이며, `click`과 `input`은 assistive technology가 element에 주는 press와 value이고, `dispatch`는 `the mygo workbench has no DOM events`로 실패한다. workbench는 첫 화면이 서면 `windowReady`를 호출하며, 그 전의 요청을 host는 준비되지 않은 main page에 대한 요청처럼 1003으로 거절한다.

`src/events.go`의 `Events`는 window 하나의 layer `workbench` event writer다. [writer](logging.ko.md#writer)가 page에 정한 큐, 상한, 한 step의 배치, 시계 anchor, gate를 가지며, event는 host call `log`로 host의 writer에 닿는다. window의 workbench는 window를 만들 때 `start`를 뽑는다. `workbench.start`는 그 시각을 `started_at`으로 적고, workbench는 문서가 아니므로 `url`은 `mygo://workbench`다. page가 기록하는 `Calls`의 모든 호출은 event `workbench.call`이고, command를 이름 붙인 모든 요청 `command.run`은 event `workbench.command`이며, workbench가 보여 주거나 중계하지 못한 모든 오류는 event `workbench.record.error`다. writer는 action `policy-read`로 시행 중인 정책을 한 번 읽고 host event `log-policy`를 따른다. window를 닫을 때는 큐의 event를 기다린다. writer는 count가 기다리고 진행 중인 batch가 없을 때만 gate count 보고 timer를 잡으며, batch가 끝나면 때가 된 count를 보내거나 1초의 나머지를 기다린다. writer 자신의 실패는 writer로 나갈 수 없으므로 place `workbench`의 host 기록이 된다.

### Native view

- **View page와 document region**은 `native/darwin`(`sp_document_create`, document region)과 view contract를 바꾸지 않고 유지한다. window의 surface host들의 container는 window의 native view(U2) 안에 있으며, 이 native view는 Metal surface 아래에서 window의 content를 채운다; workbench는 각 surface를 native view element(U2)를 통해 보여주는데, 이 element는 surface 위에 구멍을 칠하고 workbench가 그 위에 그리는 곳의 cover를 계산하며, layout transaction은 surface host들의 frame을, 다른 host에서처럼 window의 content 좌표로, card를 그리는 frame의 Core Animation transaction 안에서 설정한다. window의 layout transaction이 열려 있지 않을 때 마지막 배치와 다른 surface line을 그리는 frame은 present하기 전에 transaction을 연다(language host library의 `OpenLayout`, `BeginLayout`을 통해). 그 line의 preparation이 이 transaction을 넘겨받으므로, frame은 image region이 새 크기의 raster를 present한 뒤의 commit과 함께 비로소 새 geometry를 보인다([region](native-surfaces.ko.md#영역)). transaction은 window의 frame을 hold하므로 이후 frame이 이를 끝내지 못한다: frame이 결정하는 배치는 transaction을 자신의 preparation에 넘기거나, preparation을 만들지 않으면 그 결정이 끝나기 전에 cancel한다. 그동안 실행 중이던 배치의 응답은 그 사이에 그려진 frame을 대신해 결정하며 그 line을 곧바로 배치하고, 실패한 preparation은 넘겨받은 transaction을 cancel한다(`SyncSurfaces`). 창의 close는 그 창의 layout transaction을 모두 cancel하고, close 뒤에 main thread에 닿은 그 창의 preparation은 transaction을 시작하지 않고 실패한다. 닫힌 창의 workbench는 commit하지 않으므로, 그 transaction은 모든 창의 frame을 붙잡는 Core Animation hold를 열어 두기 때문이다([배치 트랜잭션](native-surfaces.ko.md#배치-트랜잭션)). framework는 다른 창의 transaction이 열려 있지 않을 때 어떤 창의 transaction이 시작하는 때부터 마지막으로 열린 transaction이 끝날 때까지 모든 창의 frame을 붙든다. 어떤 창의 frame이든 그 hold 안에서 표시되기 때문이다. 다른 transaction이 열려 있는 동안 한 창의 transaction이 끝나도 아무것도 놓지 않는다. plugin page는, library로 만든 page와 WebAssembly를 load하는 page를 포함해, view page 안에서 그대로 실행되는데, view page, 그 channel, view contract가 바뀌지 않기 때문이다. mygo host는 `ui.WebView`로 web view를 만들지 않는다: mygo는 각 web view를 자체 configuration과 delegate로 만들며 [S10][S14], view page에는 soksak scheme handler와 view channel의 script message handler를 갖춘 `native/darwin`의 configuration이 필요하다([`document_view.m`](../../native/darwin/src/document_view.m)).
- frame은 그리면서 surface의 surface host와 view page의 web view를 읽고, 나중에 main thread에서 이를 배치하므로, 그 사이에 닫힌 surface는 닫힌 view를 가진 frame을 남긴다. frame이 읽는 surface 목록이 그 view들을 붙들고, 목록을 떠난 surface는 떠난 뒤 시작된 window의 다음 settled frame까지 이를 유지한다. 끝난 view page를 잇는 view page도 같은 방식으로 web view를 교체한다.
- Layout transaction은 view document가 떠나기 전, 그리고 frame이 떠난 view에서 keyboard를 가져가기 전에 surface를 숨긴다. 그래서 `native/darwin`은 surface 안에서 keyboard를 가졌던 대상을 찾고, surface가 다시 보일 때 돌려준다. surface는 그 view를 기록하되 붙잡지 않는다: reload에서처럼 surface가 숨겨진 동안 닫힌 view document는 그 web content process와 함께 해제되고, 다시 보이는 surface는 닫힌 view에 keyboard를 주지 않는다.
- 창에는 다시 불러올 page가 없다. 창의 다시 불러오기(`host.window.reload`, `plugins-changed`, `core.plugins.apply`)는 창의 workbench를 끝내고 다시 만든 뒤 main page의 시작을 실행한다. 그래서 host는 이전 page를 떠나듯 이전 workbench를 떠나고, 새 workbench는 새 `start`를 받는다. page의 host call이 그 document와 함께 끝나듯 이전 workbench의 host call도 그 workbench와 함께 끝난다. 끝난 workbench는 host call을 하지 않고 그 전에 한 call의 응답도 실행하지 않으므로, 시작이 취소한 배치의 응답은 창에 아무 상태도 남기지 않는다. WebKit이 reload의 이전 page를 새 page가 render할 때까지 화면에 두듯이([page 시작](native-host.ko.md#page-시작)), 보여진 창은 새 workbench의 시작부터 그 workbench가 첫 화면을 보일 때(`FirstScreen`)까지 frame을 hold한다. 첫 화면은 host가 창의 project를 받은 뒤의 library나 그 project이며 `windowReady` 전이고, workspace를 읽지 못한 시작에서는 그 실패다. 새 창은 launch의 첫 창도 포함해, command가 마지막 frame의 element를 읽으므로 첫 frame 뒤에 workbench를 시작하고, workbench의 첫 화면 다음 frame이 그려진 뒤 화면에 올라간다. 다른 host가 main page의 첫 load 뒤에 창을 드러내는 것과 같다([page 시작](native-host.ko.md#page-시작)). 창은 전과 같이 `Window.Show`로 화면에 올라가므로 그 show는 activation을 하지 않는다.
- window마다 container 하나를 두면 각 geometry의 배치자가 하나로 유지된다: layout transaction은 모든 surface host를 window의 content 좌표에 배치하고, `native/darwin`은 그 frame을 적용할 때 container의 좌표로 변환하므로(`webview_geometry.m`, `webviewSetFrame`), mygo가 같은 frame에서 옮긴 holder가 있다면 host를 잘못된 곳에 두게 된다.
- **Image region**은 lease된 IOSurface를 가진 `image_region.m`의 `CALayer`를 유지하므로, lease의 in-use 규칙, color 처리, frame identity가 세 host에 대해 하나의 구현으로 남고, mygo renderer는 terminal frame을 위해 frame을 그리지 않는다. IOSurface를 Metal texture로 import하는 방식은 기각한다: 그러면 mygo renderer가 각 terminal frame을 upload하고 그것을 위한 frame을 그리며, lease 규칙이 framework 안으로 옮겨진다.
- **Modal**(settings window, menu, dialog)은 native UI이며, mygo host는 native modal web view를 만들지 않는다. Dialog가 열린 동안 workbench는 자신을 3 point blur한 위에 50% opacity의 검정을 그리고, `{enabled}`를 받는 host call `setDialogBackground`는 host가 mode `dialog`의 modal web view일 때처럼 각 document web view와 image region을 blur하게 한다([region](native-surfaces.ko.md#영역)).

### Framework 변경

Wails host가 자신의 Wails fork를 고정하듯, mygo host는 go.mod `replace`로 framework fork를 고정한다. 각 변경은 framework package의 변경이며, 각각 그 package 안의 test와 그 변경을 사용하는 core item으로 검증된다.

| ID | 변경 | 이유 |
| --- | --- | --- |
| U1 | Main-thread worker: Go code는 main thread가 아닌 thread에 고정된 goroutine에서 실행된다. worker는 `App.Run` 안에서 `Backend.Init` 전에 시작하고 `App.Run`이 반환할 때 끝난다. `App.Run`은 run loop 전의 Go code(`Backend.Init`, `Run` 전에 한 설정, `quitOnSignals`와 `Signal`)를 한 step으로, `OnQuit` listener를 포함한 `finish`를 또 다른 step으로 실행한다. main goroutine은 main thread에서 호출되어 block을 worker에서 실행하는 function을 통해 각 step을 시작하므로, main thread는 자신의 stack 위에서 각 step을 기다리며 그동안 worker와 다른 thread가 자신에게 forward하는 call을 실행한다. 그 step 동안 main thread에 도달한 callback은 worker에서 nested step으로 실행된다. mygo가 purego로 만드는 각 Objective-C method와 block(`objc.RegisterClass`, `objc.NewBlock`), 그리고 mygo가 넘기는 각 C callback(`purego.NewCallback`)은 mygo의 assembly trampoline을 통해 진입한다: `objc.RegisterClass` 뒤에 mygo는 그 class의 각 method의 구현을 trampoline으로 설정하고(`method_setImplementation`), 자신이 만드는 각 block의 descriptor의 invoke function과 dispose function을 trampoline으로 교체하며, 각 C callback pointer 대신 trampoline을 넘긴다. trampoline은 purego가 그것을 위해 만든 function을 호출하며, purego는 바뀌지 않는다. main thread에서 호출되면 trampoline은 argument register를 저장하고 Mach semaphore로 worker를 깨운 뒤 기다린다; 기다리는 동안 main thread는 자신에게 forward된 call, 즉 그 step을 위한 worker의 call과 다른 thread의 call만 실행하고, worker가 쓴 answer를 반환한다. 각 step은 step이 끝날 때 worker가 drain하는 worker의 autorelease pool 안에서 실행된다; 그 drain 전에 worker는 callback이 caller에 반환하는 object를 retain하고 forward된 call을 통해 main thread의 pool에서 autorelease하는데, 이는 worker pool의 drain이 callback이 worker에서 autorelease한 object를 deallocate하지 않고, main thread에서의 autorelease가 callback이 주지 않은 reference를 가져가지 않게 하기 위해서다. worker를 포함한 다른 thread에서 호출되면 trampoline은 그 thread에서 Go로 진입한다. step 동안 worker는 `onMain`, `RunOnMain`, `await`에 대해 main thread로 간주되며, `await`는 `Backend.Step`을 forward한다; 다른 callback을 전달하는 forward된 call(modal panel, menu, drag, `resignFirstResponder`와 `becomeFirstResponder`를 보내는 `makeFirstResponder:`)은 그 callback을 기다리는 worker에서, 바깥 step 안에서 끝나는 nested step으로 실행한다. mygo가 main thread가 아닌 thread에서 Objective-C object나 system framework function으로 하는 각 call은 main thread로 forward되며, 다음은 예외로 calling thread에서 실행된다: drawable이 아닌 Metal object(Metal protocol을 따르는 object: device, command queue, command buffer, encoder, texture, buffer, library, function, pipeline state 또는 sampler state)로 보내는 message(frame의 encoding, queue의 `commandBuffer`, command buffer의 `presentDrawable:`, `commit`, `waitUntilScheduled`, `waitUntilCompleted`, `status`, texture의 `width`와 `height` 포함), Metal descriptor class와 그 instance로 보내는 message(`MTLRenderPassDescriptor`, `MTLRenderPipelineDescriptor`, `MTLSamplerDescriptor`, `MTLTextureDescriptor`와 이들이 반환하는 attachment descriptor와 descriptor array), drawable의 `texture`, 그리고 `nextDrawable`; Core Text와 Core Graphics; `objc_msgSend`, `objc_msgSend_stret`, `objc_msgSendSuper`를 제외한 Objective-C runtime의 function(이 셋의 call은 U1이 selector와 receiver로 판단하는 message send다)과 `NSObject`가 구현하는 message `retain`, `respondsToSelector:`, `isKindOfClass:`; `NSString`, `NSAttributedString`, `NSNumber`, `NSData` 또는 그 mutable 형태, Metal object(Metal protocol을 따르는 object), Metal descriptor 또는 `CAMetalLayer`의 drawable에 보내는 message `release`와 `autorelease`, 반면 그 밖의 object(`NSArray`, `NSDictionary`와 그 mutable 형태 포함)의 `release`나 `autorelease`는 forward되는데, 마지막 release가 그것을 보내는 thread에서 object의 `dealloc`을 실행하고 collection의 `dealloc`은 자신이 담은 object를 release하기 때문이며, 그러면 autorelease된 window는 AppKit이 아직 닫는 중인 window에 대해 mygo가 의도하는 대로 main thread의 pool로 간다; ### 결정

각 결정은 mygo host가 무엇을 하는지와 그 이유를 밝힌다.

- **D1 Native workbench.** mygo host는 workbench를 native UI로 그린다. 이유: page mode는 C1, C3, C4, C5와 C9의 main page 대기를 남긴다([Native workbench](#native-workbench) 참조).
- **D3 Assembly trampoline에 의한 main-thread worker (U1).** mygo host의 Go code는 worker thread에서 실행된다; AppKit이 main thread에서 하는 각 callback은 step을 worker에 넘기는 assembly trampoline을 통해 들어오고, main thread는 자신에게 forward된 call을 실행한다. 이유: [main-thread 규칙](#wails-host의-main-thread)은 main thread에서 Go code가 실행되지 않을 때만 성립한다; purego callback은 calling thread에서 Go를 실행하고 [S29], AppKit은 mygo가 등록하는 method를 main thread에서 호출하며 [S4][S6], mygo는 cgo 없이 build되므로 [S5], Wails fork의 C worker는 그 mechanism이 될 수 없고, forward된 call을 가진 step이 곧 Wails host가 모든 callback에 대해 실행하는 그 step이다. U1의 비용은 각 step과 forward된 각 call마다, Mach semaphore를 통한 두 번의 thread wake로 이루어진 교환 한 번과 native wait에서의 worker 복귀이며, 이 복귀에는 Go scheduler의 P가 필요하다: garbage collection mark phase 동안처럼 sysmon이 대기 중인 worker의 P를 가져갔고 idle인 P가 없으면, worker는 어떤 thread가 그것을 schedule할 때까지 global run queue에서 기다린다. window size, layer나 placement의 변경 없이 content가 바뀐 window의 frame은 두 step, 곧 display link의 tick과 각 frame이 arm하는 run loop observer의 callout이며, forward된 call 6개를 가진다: superlayer의 bounds 두 번, occlusion state 두 번, 그리고 tick에서의 layer와 그 display flag; display link를 다시 시작하는 frame은 그 `setPaused:`를 더한다. surface는 view의 size, window의 scale, 그 screen의 refresh rate를 AppKit이 변경을 알릴 때까지 보관하므로, frame은 이 값들을 읽지 않는다. transaction과 함께 present하는 frame은(U2는 이를 layer나 placement를 바꾸는 frame으로 제한한다) 그 drawable의 `present`를 더하고, mygo web view의 바뀐 placement는 call 4개를 더한다. live resize에서 window size의 한 번 변경은 다섯 step, 곧 `setFrameSize:`, `windowDidResize:`, `wantsUpdateLayer`, `updateLayer`, 그리고 `updateLayer`의 frame이 arm하는 run loop observer의 callout으로 forward된 call이 모두 13개에서 15개이고 `NSView`의 `setFrameSize:`가 surface view에 보내는 `isFlipped`의 nested step 네 개를 가지며, pointer move는 forward된 call 4개를 가진 한 step이며 cursor가 바뀌면 2개가 더해지고 그 `convertPoint:fromView:`가 보내는 `isFlipped`의 nested step 하나를 가지고, mygo host에서는 view page가 input을 위해 등록되어 있는 동안 그 앞에 두 번째 step, 곧 `native/darwin`의 pointer routing이 각 move마다 content view에 보내는 mygo surface view의 `hitTest:`가 자체 forward된 call 및 `NSView`의 `hitTest:`가 보내는 `isFlipped`의 nested step 하나와 함께 더해진다; key는 forward된 call 5개를 가진 한 step이며(`interpretKeyEvents:`에 event를 넘기는 array의 `release`가 그 가운데 포함), 그 안에서 input method의 각 callback은 nested step이다 [S33]. text shaping은 system font style을 처음 사용할 때만 call을 forward한다 [S34]. framework test는, mygo host의 어떤 window도 `ui.WebView`로 만든 web view를 담지 않으므로, web view를 담지 않는 window에서 각 종류의 step의 forward된 call이 frame에 15, window size의 한 번 변경의 step에 20, pointer move에 6, key에 7 이하임을 test하고, G8은 final phase에서 frame, pointer step과 resize의 step에 forward된 call을 포함해 120 Hz의 display 주기 하나(8.33 ms)의 상한을 둔다.
- **D4 Native layer로서의 image region.** window의 native view(U2)는 그 `SurfaceHost`들의 container를 담고, image region은 lease된 IOSurface를 가진 자신의 `CALayer`를 유지한다(N1). 이유: 세 host를 위한 하나의 lease 구현, 그리고 mygo renderer는 terminal frame을 위해 frame을 그리지 않는다.
- **D5 image region 화면은 view page를 유지한다.** composition의 image region 하나(`input: "dom"`)가 화면인 view는 세 host에서 그 view composition을 유지한다. raster probe fixture `rasterprobe`가 이 composition을 가진다. 이유: view page가 그 화면의 screen state, input과 exposure를 소유한다(C8): 그 overlay, tab report, clipboard, link, settings, theme과 text size call, shortcut forwarding과 element name이다. surface는 자신의 plugin의 page를 보여주며, screen의 layer는 measurement로 선택되지 않는다([plugin process](plugin-processes.ko.md#층-규칙)).

## Performance goals

목표 G1부터 G8까지는 Wails host와 Tauri host 옆에서 mygo host가 드는 비용을 정한다. [three-host benchmark](../operations/examples.ko.md#three-host-benchmark)가 그 scenario S0부터 S16까지에서 이 목표를 측정하고, `make check-b3`가 그 각 session을 판정한다. other host는 mygo host의 revision에서 build한 Wails host와 Tauri host이고, baseline host는 benchmark가 정하는 baseline revision에서 build한 Wails host와 Tauri host이다. `docs/spec/performance-goals.json`이 목표의 수치 한계를 가진다; 이 section의 두 표는 그 file의 사본이며 `scripts/test/performance-goals.test.mjs`가 둘을 같게 유지하고, idle tab benchmark와 split load benchmark는 `IDLE_TAB_BOUND_KB`와 `SPLIT_LOAD_GROWTH_BOUND_KB`를 그 file에서 읽는다. [plugin process](plugin-processes.ko.md#통과값)나 [native surface](native-surfaces.ko.md#인수-기준)가 정하는 값은 file에 복사하지 않는다: 그 값을 가진 benchmark가 판정하고, judge는 그 benchmark의 verdict만 읽는다.

judge는 다음 규칙을 적용한다:

- session은 조건 표가 정하는 수만큼 각 application의 run을 가지며, run은 그 표의 조건에서만 시작한다; `make benchmark-b3`는 조건이 맞지 않는 run을 실패시킨다.
- median으로 판정하는 값은 그 run들의 median이다; 각 run에서 판정하는 값은 run 하나가 한계를 넘으면 실패한다. 값의 spread는 그 run들의 범위다.
- 한계는 mygo host의 값에 적용한다.
- host가 어느 run에도 기록하지 않은 값은 `not measured`로 출력한다. 단, 기준이 그 host의 값을 요구하면 실패한다. 이 값은 그 host의 통과도 실패도 아니다. Wails host와 Tauri host에서는 `host.window`의 `frames`와 `commandBuffers`가 null이므로 그 host의 `G2-S0-frames`는 `not measured`이고, 그 창에 대한 idle 대기는 frame을 읽지 않는다.
- 각 other host와 baseline host와 비교하는 값은 mygo host의 spread가 그 host 중 하나의 같은 값의 spread보다 완전히 한계 쪽에 있을 때 실패한다: 시간, CPU 시간, footprint(`s`, `ms`, `KB`)에서는 가장 낮은 run이 그 host의 가장 높은 run보다 위에 있을 때, frame rate(`frames/s`)에서는 가장 높은 run이 그 host의 가장 낮은 run보다 아래에 있을 때다. other host의 같은 값은 그 spread가 같은 뜻으로 그 baseline host의 같은 값의 spread보다 완전히 한계 쪽에 있을 때 regression이며, regression은 session을 실패시킨다.
- mygo host의 다른 값과 비교하는 값은 그 spread가 그 값의 spread보다 완전히 위에 있을 때 실패한다.
- 단위 `verdict`의 값은 그 행의 benchmark가 그 run에 기록한 verdict이다.

각 목표의 값:

- **G1 Process set.** application 시작 이후 view를 보인 적이 없는 window는 WebContent, GPU, Networking process를 실행하지 않는다. WebKit process는 첫 view page나 document region이 보일 때에만 시작한다. application의 마지막 web view가 닫힌 뒤, application이 가졌던 view page나 document region의 모든 WebContent process는 [plugin process](plugin-processes.ko.md#통과값)의 pass value (ii)의 시간 안에 종료한다; S0b는 그런 각 process의 `diagnostics.process.exit` 뒤에 남은 process를 센다. 그 뒤에 WebKit이 유지하는 GPU나 Networking process는 G3가 S0b에서 세는 비용이다. 이 기준은 증거를 적은 adversarial review로만 바뀐다.
- **G2 Idle.** 모든 plugin의 settings가 그 manifest가 선언한 기본값일 때, 마지막 입력, status `<plugin>.cursor`를 노출하는 plugin의 각 tab에 대해 그 status가 보고하는 cursor idle timeout `idleTimeout`, `host.window`의 `frames`가 바뀌지 않는 3초, 그리고 측정의 마지막 요청 뒤 gate count가 기록을 기다리는 시간([logging](logging.ko.md#정책))이 지난 뒤, S0, S1, S9, S12의 모든 window는 240초 동안 frame을 present하지 않고 Metal command buffer를 commit하지 않는다: frame 값과 command buffer 값은 그 구간 동안 scenario의 window 중 `host.window`의 `frames`와 `commandBuffers`가 가장 크게 바뀐 양이고, CPU 값은 그 구간 동안 host process의 CPU 시간이다. S0과 S1에서는 다른 window가 가리지 않는 window를 아무것도 활성화하지 않는 `input.pointer`의 move로 가로지르는 pointer move 뒤의 합산 footprint를 그 move 전의 합산 footprint와 비교한다. S12에서는 실패하는 layout draw가 그 fault의 `error:` 행 하나를 application log에 쓰고, 그 뒤에 S1의 값이 성립한다. S1, S9, S11, S12, S15 target의 `TAB`과 `PAGE`는 호출자의 인자이다: 이 target은 설치된 환경의 plugin을 재며 아무것도 gate하지 않는다.
- **G3 Memory.** footprint는 모든 process의 reading이 안정된 뒤(5초 간격의 연속한 두 reading의 차가 1,024 KB 미만), 마지막 frame에서 3초 이상 지난 뒤 읽는다. S0과 S0b에서 값은 mygo application의 host process와 모든 WebContent, GPU, Networking process의 합산 footprint이고, other host나 baseline host에서는 host process만의 footprint이다; 모든 host에서 같은 sidecar build를 실행하는 sidecar process는 그 합과 따로 출력한다. S1에서 값은 application의 합산 footprint에서 main page process를 뺀 것이다. S5와 S13에서는 그 scenario를 위해 시작한 application에서, capture 없이 실행하는 drag의 전과 후에 읽은, application의 process에 걸친 lifetime peak footprint(`footprint`의 `phys_footprint_peak`)의 합이 값이다; drag 뒤의 peak가 drag 전의 peak보다 높으면 그 차이가 drag의 비용이다. S11과 S15에서 값은 두 번째 window나 열린 settings window가 application에 더하는 footprint이다. S14에서 값은 key 뒤 10초, caret이 깜박이는 동안 settle 규칙과 마지막 frame 규칙 없이 읽은 합산 footprint이다. S3에서 changed count는 `runtime` member 밖의 `diagnostics.objects` count 중, 두 번째부터의 repetition 뒤에 첫 repetition 뒤의 값과 다른 count의 수이며, workbench element, native view element, 등록된 framework callback이 그 count에 들어간다. growing figure는 host footprint와, system에 돌려준 memory를 세는 `heapReleasedBytes`를 뺀 Go runtime figure 중 repetition 21부터 30까지의 가장 낮은 값이 repetition 11부터 20까지의 가장 높은 값보다 위인 figure의 수이다. S4에서는 입력 없는 60분 뒤의 host footprint를 S1의 host footprint와 비교한다. S10에서 값은 split load benchmark의 round 동안 host process의 resident set size가 늘어난 양이다. 증가가 없는 수치는 S3의 증가 규칙에 run 184,756번 중 1번 우연히 실패한다(1/C(20,10)).
- **G4 Views and gestures.** [plugin process](plugin-processes.ko.md#통과값)의 모든 pass value((i), (ii), (iii), (iii-b), (v), (viii))는 mygo host의 모든 plugin view에 그대로 적용한다. mygo host에서 (iii)과 (iii-b)의 DOM mount baseline은 (iii)이 정한 대로 Wails host와 Tauri host의 baseline 중 낮은 것이다; 각 section view는 기록된 DOM mount baseline이 없으며, 기록된 값이 없는 plugin에 대해 (iii)이 정한 한계만으로 판정한다. mygo host에서 (viii)(a)는 S5의 maximise와 restore의 기록된 모든 frame에서 S5 tab의 view에 적용한다. native surface의 [성능 목표](native-surfaces.ko.md#성능-목표)와 [인수 기준](native-surfaces.ko.md#인수-기준)의 maximise와 restore catch-up 한계는 그대로 적용한다. 각 G4 행의 benchmark가 이 값을 판정하고, 그 verdict가 그 행의 값이다. 측정한 floor는 세 host 각각의 floor가 target을 넘을 때에만, 그리고 증거를 적은 adversarial review로만 target을 바꾼다.
- **G5 Terminal.** 가려지지 않은 760×614 point window의 `term` tab에서, 33 ms마다 다시 쓰는 status line 하나와 20행에 대해, CPU 값은 application CPU 시간을 같은 구간에 region이 present한 frame으로 나눈 것이고, frame rate는 region이 present하는 초당 frame이다. target의 `PLUGIN=term`은 호출자의 인자이다: 이 target은 설치된 환경의 plugin을 재며 아무것도 gate하지 않는다.
- **G6 Idle tab.** document region을 가진 idle tab, 곧 region에 content 없는 자기 plugin document를 둔 layout probe fixture tab의 비용은 그 tab의 모든 document process의 안정된 footprint에 host process의 안정된 증가를 더한 것이고, 그 document part는 document process의 안정된 footprint이다. 나중의 review가 도출한 상한은 그것을 적은 review 뒤의 run에만, 모든 host에 대해 적용된다.
- **G7 Input.** trace off와 기본 gate의 두 configuration의 24 key에 대해, 값은 주입한 key가 input probe fixture의 document에 도착하기까지의 시간의, run 하나의 key에 걸친 median과 90th percentile이며, view의 text field와 native document region의 field 각각에 대해 잰다.
- **G8 Gesture CPU and frame time.** CPU 값은 기본 policy에서 capture 없이 실행하는 S5와 S13의 drag 동안, 그리고 S1의 `STEP=pointer` pointer move 동안 application process의 합산 CPU 시간이다; view drag benchmark는 그 drag를 모든 host에서 `native: true`의 `diagnostics.drag`와 capture한 drag의 plan으로 전달한다. class `frame`을 `debug`로 저장하는 policy에서, frame 값은 frame 시작부터 presentation request까지의 시간에서 frame이 drawable을 기다린 시간을 뺀 것의 90th percentile이고, step 값은 forwarded call을 포함한 각 pointer move step의 90th percentile이며, S5, S13, S16의 drag와 capture 없는 S5의 maximise와 restore에서 잰다. first-frame 값은 frame 없는 3초 이상 뒤에 오는 S5와 S13 drag의 첫 frame이 시작부터 presentation request까지 걸린 시간이며 drawable 대기를 포함한다. pointer-move 값은 S1의 pointer move에서 전달된 이동마다, 가장 바깥 `mouseMoved:` step에 바로 앞의 `hitTest:` step이 있으면 그 시간을 더한 값의 90th percentile이다. 중첩 step은 그것을 담은 step의 시간에 포함된다. S1의 pointer move는 창을 활성화하지 않는 `input.pointer`로 전달한다. 각 90th percentile과 각 first-frame 시간은 run 하나의 frame과 step에 걸쳐 잡으며, 그 한계는 그 측정에서 window가 보고한 refresh rate(`host.window.refreshRate`)에서 display period 하나이고, 120 Hz에서는 8.33 ms, 60 Hz에서는 16.67 ms이다. maximise and restore에서 step 값은 pointer 이동만이 아니라 U1의 모든 step을 대상으로 한다. first-frame 값이 drawable 대기를 포함하는 것은 첫 frame 앞에 진행 중인 frame이 없고 [S17]의 timer가 drawable, buffer, texture를 놓았기 때문이다. S16이 collection 중의 drag에 상한을 두는 것은 U1의 worker가 깨어날 때마다 Go scheduler의 P가 필요하고 collection이 유휴 P를 잡고 있기 때문이다.

값은 맞추기 어렵다는 이유로 낮추지 않는다; 측정한 floor가 값을 넘으면 그 값은 증거를 적은 adversarial review로만 바뀐다.

## 구조 검사

`scripts/check-host-files.mjs`는 네 쌍을 비교한다: [언어 표](#언어-표)로 `packages/host/go`와 `packages/host/rust`, `packages/sok/go`와 `packages/sok/rust`를, [Framework 표](#framework-표)로 `packages/host/wailsv3`와 `packages/host/tauriv2`, `apps/wailsv3`와 `apps/tauriv2`를 비교한다. `.go`와 `.rs` 파일은 확장자를 제외한 상대 경로로, 그 밖의 파일은 상대 경로로 비교한다. 한쪽에만 있는 파일은 그 쌍의 표에서 ID가 그 쌍의 글자(호스트 패키지는 H, command line은 C, 애플리케이션은 A)로 시작하는 행이 그 파일을 나열할 때만 통과한다. 검사는 Git이 추적하거나 추적할 파일만 읽으므로 생성된 `src/frontend/` 파일은 비교하지 않는다.

경로 prefix로 파일을 고르는 검사의 audit은 prefix 하나라도 파일을 고르지 못하면 실패한다. main-thread audit은 `packages/host/go/src/platform/darwin/`을, 해석하지 않은 명령 인자 audit은 `packages/host/tauriv2/src/`의 Rust source를, stub 검사는 language host library, framework adapter, `native/darwin`의 `src` 폴더를 쓴다. Library import audit은 `packages/host/go`의 Go 파일이 Wails의 패키지를 가져오거나 그 `go.mod`가 Wails를 요구할 때, 그리고 `packages/host/rust`의 Rust 파일이 Tauri의 크레이트를 이름으로 부르거나 그 `Cargo.toml`이 그런 크레이트에 의존할 때 실패한다. Library name audit(`auditLibraryNames`)은 `packages/host/go`나 `packages/host/rust`의 source와 test의 주석 밖 code가 framework나 그 host를 이름으로 부르는 단어를 가질 때, 그리고 그 파일의 contract 선언이 그런 단어를 가질 때 실패한다. 단어는 identifier나 문자열을 밑줄과 대소문자 변화에서 나눈 부분이다.

`scripts/check-platform-files.mjs`는 `platform/<os>/` 밖에서 `_darwin`, `_windows` 등의 운영체제 접미사가 붙은 파일 이름과 Go 파일의 `runtime.GOOS` 및 운영체제 build tag, Rust 파일의 운영체제 `cfg`, JavaScript 파일의 실행 가능한 Node `process.platform` member expression을 보고한다. JavaScript는 syntax로 분석하므로 string과 comment는 selector가 아니다. 유일한 metadata 예외는 `environment()` 함수가 반환하는 object의 `platform` property에 쓰는 `process.platform`, 그리고 test 경로의 `assert.equal(result.environment.platform, process.platform)` 또는 `assert.strictEqual`이다. test 경로 안의 selector를 포함해 다른 모든 실행 가능한 사용은 finding이다. `native/<os>/`, `scripts/check-tools.sh`, `platform/platform.{go,rs,js}`, 검사 파일 자신은 건너뛴다. `Cargo.toml`은 읽지 않으므로 대상별 의존성 표는 허용된다.

플랫폼별 test는 소유 package의 `tests/platform/<os>/` 또는 root script의 해당 `platform/<os>/` directory에 둔다. Cargo target이나 test-runner 경로를 명시적으로 등록한다. 공통 directory의 test는 운영체제를 선택하거나 가정하지 않는 동작을 검증한다.

## native/darwin

`native/darwin`은 두 호스트가 호출하는 공용 macOS 라이브러리다. 최소 macOS 버전은 14.4다. native code가 호출하는 가장 새 API인 창이나 view의 display link(`displayLinkWithTarget:selector:`)는 macOS 14.0이 필요하다. Makefile은 이 값을 `MACOS_MINIMUM`에 선언하고 라이브러리와 두 애플리케이션을 그 값으로 build한다. 두 애플리케이션의 `Info.plist`는 `LSMinimumSystemVersion`에, `apps/tauriv2/tauri.conf.json`은 `bundle.macOS.minimumSystemVersion`에 같은 값을 선언하는데, Tauri bundler가 그 값으로 애플리케이션을 build하기 때문이다. 번들이 다른 값을 선언하거나, 애플리케이션 실행 파일이 다른 macOS version으로 build되었거나, 번들의 다른 실행 파일이 더 새 version으로 build되었으면 `make check-release`가 실패한다. Bundled Rust 실행 파일은 application과 같은 선언된 Cargo deployment target을 사용하므로 deployment 환경만으로 공용 의존성의 build identity가 달라지지 않는다. 저장소의 모든 compile과 모든 외부 link는 선언된 이 값 하나를 사용하고, 어느 build 명령도 version을 다시 쓰지 않는다. 루트 Makefile은 각 clang 호출에 쓸 `MACOS_MINIMUM`을 `native/darwin`의 Makefile에 넘기고, 그 Makefile은 이를 process identity package의 Makefile에 그 clang 호출과 pkg-config file의 Cflags에 쓰도록 넘기며, 두 Makefile은 단독으로 실행될 때 루트 Makefile에서 이 값을 읽고, cgo Go 명령에는 `MACOSX_DEPLOYMENT_TARGET`, `CGO_CFLAGS`의 `-mmacosx-version-min`, `-extldflags`를 통한 외부 linker 최소 버전을 전달한다. cgo-free mygo 앱, 번들 CLI, 네이티브 테스트 프로필과 empty-window 벤치마크에는 Go 내부 linker의 `-macos=$(MACOS_MINIMUM)`을 전달한다. 내부 linker는 `MACOSX_DEPLOYMENT_TARGET`을 읽지 않기 때문이다([Go linker 계약](https://go.dev/doc/go1.27#linker)). 이식 가능한 `repeat-go` 타깃은 macOS 기본값을 강제하지 않고 명시적인 `GO_LDFLAGS` 값을 전달하며, 네이티브 mygo 호출자는 `GO_LDFLAGS='$(GO_INTERNAL_LINK)'`을 사용한다. 컴파일러 SDK 기본값은 deployment 최소 버전과 별개다. 또한, 모든 Cargo 명령은 `MACOSX_DEPLOYMENT_TARGET`으로 실행된다. 따라서 object가 link보다 새 macOS version으로 build되었다는 linker 경고는 어느 compile이나 link가 다른 version을 받았다는 뜻이며, 그 경고를 출력한 build나 test는 object와 두 version을 밝히고 실패한다. 반복된 `-lobjc`를 무시한다는 ld 경고는 build를 실패시키지 않는다. cmd/go는 Objective-C 파일이 있는 package마다 link에 `-lobjc`를 추가하고, Wails host의 link에는 그런 package가 둘 있으며, 저장소의 어느 link flag도 `-lobjc`를 지정하지 않는다.
