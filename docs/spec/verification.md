# Verification contracts

Common window-check preparation declares executable paths and builds nothing. A complete explicit declaration works independently of default platform discovery. A window check reads the content of a view from the public value of the plugin that holds it, and judges that it is shown from the presentation state of the host; no text recognition runs in the verification pipeline.


Window sessions acquire clipboard preservation only through an explicit `open(t, app, { clipboard: true })` declaration before any action that can change the clipboard. Copy shortcuts, direct fixture writes, terminal selection release and allowed OSC 52 output require ownership. An unrelated session does not read or restore the clipboard. Ownership failure rejects the check; it never skips preservation. Connection and execution-slot cleanup is registered before preparation and runs immediately on preparation rejection, preserving both preparation and cleanup failures.


The view-drag benchmark separates structurally valid capture collection from threshold judgment. Missing frames, invalid geometry and incomplete gestures stop collection immediately. After a valid captured gesture, the third drag and its metrics are collected and published before the captured-performance assertion. A third-stage collection or publication failure still runs that assertion; both original errors are preserved when both fail. The B3 writer keeps its existing selected-condition and failed-verdict rules. This collection order does not establish a performance pass or change any threshold.

## Coverage and evidence

View display acceptance opens the view plugin of each content case, which must be installed and enabled, and identifies the actual opened tab. Each opened plugin requires an explicit content case that checks its declared readiness and returns a content verifier. A missing case fails with the plugin and tab identifiers. Colour variation alone does not prove plugin content; rejecting a missing case removes a false pass without lowering the acceptance criterion.

The content verifier of a view reads its fixed expected content after the recording stops from a content read that the view exposes in its own namespace and that answers the text the view shows; the check names the command and the document region, and the value is read while that region is visible. The core check reads `probeplain.content.read` of the plain view probe fixture, which answers the line `Plain view probe content` of its document region `page`. The complete recording is decoded and its finalized frame count is checked. Readiness without a content verifier is rejected.

Terminal background samples use the same view crop conversion: buffer coordinates include the capture content origin, display scale and content scale. A sample lies inside that crop, including at small sizes. Unit fixtures distinguish the requested pixel from surrounding pixels independently for each transform. Stopped capture folders are removed only after successful session finalization; decoding, geometry or finalization failures retain them.

The canonical work status is [features](../features.md). A source-file inventory is structural evidence only. It must not report feature parity or application correctness.

The feature-link audit's self-check invokes the actual audit module. Its controlled mutations remove one error-reporting effect or response in an isolated copy, after the unchanged module passes the same assertion. These two omitted-error cases require that assertion to fail; a load error, interruption or failed baseline does not establish their detection. This validates the audit's own error contract, not the behavior of the product files it inventories.

Current inventory and checklist totals are generated from their canonical inputs and are not repeated as manually maintained document counts. Parent and child checklist rows count separately. Required checks on historical evidence wording belong to the documentation gate and apply to both translations when the corresponding record exists; they do not count as product behavior validation.

### Requirement scenario inventory

The following table declares the bounded requirement scope of the scenario audit. It is separate from the implementation-to-test links so deleting an entire mapping remains detectable. Both translations must retain the same ordered keys. This is not a list of every product requirement; new scope requires a contract change here and owning links in the existing `FEATURE_LINKS` inventory.

| Key | Required contract |

Each scoped feature declares one unique requirement key. Its existing owning test references declare the dimensions their assertions exercise: `normal`, `failure`, `race` and `recovery`. Normal and failure always require tests. A race or recovery dimension without a test needs a concrete inapplicability reason tied to that contract; an asynchronous state transition cannot be exempted merely because no test exists. The same test may cover multiple dimensions only when its assertions actually exercise each. Recovery means a refused state can progress through the intended subsequent operation, or failure cleanup completes as required; a fresh fixture that passes independently does not prove state recovery. Missing dimensions, unknown or repeated keys/dimensions, duplicate scenario references and invalid existing implementation/test references fail `make check-tests`.

Every row declares `darwin`, `linux` and `win32` applicability: `required` means behavior still needs execution evidence on that platform; `unavailable` requires both an implementation reason and the condition that restores verification. A platform is never unavailable merely because this run uses another OS. The generated report labels mapped scenarios as unexecuted and required platforms as unverified; unavailable platforms remain unverified too. This structural check reads no run results, assigns no coverage percentage and grants no application or publication acceptance. Review must still compare each scenario tag with its owning assertions, and the existing runners and acceptance gates judge actual execution.

The modified-close row owns only the core consumer's reported modified state and save response, including the file-write failure boundary represented by a rejected response. File persistence and PTY wire implementations belong to their independent repositories and retain their own requirements and tests; core does not inspect those implementations or claim their coverage. Layout identity and topology comparisons remain in their owning tests alongside this transition scope. Capture rows describe the sampler and its current native capture dependency. The lifecycle race scenario covers a late application error after stop and before the final audit; it does not verify parallel or repeated finalization. Candidate publication describes report validation, not an executed native application run.

Core test ownership follows independently declared core packages. The root `e2e` package owns its window checks and the installable payloads under `e2e/fixtures/`; a fixture `package.json` describes an installed payload, not an independent core test owner. E2E tests may read their fixture manifests and sources. Core package tests remain unable to read E2E fixture files, and E2E tests remain unable to read another core package's implementation paths.

Documentation checks require unique task identifiers and only waiting (`[ ]`), in-progress (`[~]`), complete (`[o]`), or temporarily bypassed (`[!]`) states. A `[!]` item records a nonempty cause and retry condition in both translations. Checklist identifiers, ordering, indentation, and states must match across translations. The text may be translated; the task state must not differ. The changelog and its translation must have the same sections, the same number of entries in each section, and, at each position, the same task identifiers and code spans.

Additional work must receive a priority and acceptance criteria in that same checklist before implementation. A completed task retains its status and the scope of its evidence. A subsequent issue uses a linked identifier with a numeric suffix instead of reopening the completed task or starting another checklist.

Discover workspace packages, build manifests, implementation languages, public commands, statuses, settings, and host operations. Every supported feature maps to explicit implementation entry points, behavior test identifiers, expected outcomes, and required verification levels. Derive executable implementation languages from the repository inventory, and make `make check-tests` fail when the language adapter manifest omits an executable implementation language or declares a language with no implementation. Each language adapter executes named tests and reports actual counts, failures, skips, cancellations, todos, crashes, and timeouts through the same result contract. JS/TS, Rust, Go, Objective-C, and shell currently have the same evidence obligations. A shared native test does not replace integration through each host. Host comparisons use the same expected outcomes; identical incorrect results fail. The Wails and Tauri host tests declare the [host contract cases](host-contract.md) they execute, and `make test-hosts` runs both hosts' tests and fails when a host has no passing test for a case in its scope. `make test-native` runs this check, so a host change that leaves a case without a passing test in either host fails the native gate.

Missing implementations, missing tests, unregistered build targets, unresolved references, excluded required tests, zero tests, mandatory skips, stale evidence, crashes, and timeouts fail the applicable gate. Audit self-tests must demonstrate those failures. Behavioral mutation checks replace an implementation with a no-op or remove a required effect or response and require the corresponding test to fail. File names and source patterns do not establish behavior.

Discovered Node test files, repeated selections and JS/TS language cases use the same file-owned execution evidence and acceptance rule. A successful file wrapper or command exit is insufficient: an empty file, an exit before registration, no selected tests, skipped cases, todo cases, cancellations and failures fail. Skipped or todo suites also fail even when Node omits them from its test totals. Nested selected cases pass when they execute successfully; cases outside the name selection are not required. JS/TS language cases declare their executable test entrypoints in `testFiles`, and every declared file must supply its own summary. Rust language results sum every target summary, so a later passing or empty target cannot hide an earlier failure or ignored case. Package scripts with support modules select test entrypoints with explicit globs. Directory arguments retain Node's selection of every JavaScript file, and every selected file must supply test evidence. Commands without a Node test contract retain command-result semantics.

Go language results count named passing and failing tests as executed cases. A package without test files emits separate output and package-skip events and does not decide a run that executes tests in another selected package. A named test skip fails; a selection with no executed tests also fails, including a successful package whose name filter selected nothing.

Declared Node scripts preserve argument boundaries through the maintained Yarn shell parser. Literal arguments, quoting, escaping and `&&` command chains are supported; no shell is executed. Only `pnpm` preparation commands before one Node test command and the existing trailing `pnpm -r test` declaration are accepted. Variables, substitutions, backticks, redirections, pipelines, background commands and malformed syntax fail explicitly. Literal dollar signs use single quotes or backslash escapes, as the parser requires. Node name and skip patterns accept both attached and separate values. Every declared path must resolve to at least one test file, including each glob and directory; a valid sibling path cannot hide a missing selection. Actual child execution must prove that the selected case ran and excluded cases did not run.

A unit check for a presentation wait holds the presentation unresolved until queue completion reactions have had a task in which to run. It checks both the current layout's incomplete result and the next queued layout's absence, then releases the presentation and requires both to complete. A missing await must fail that check; an observation before promise completion can propagate does not prove a wait.


Evidence identifies the feature and test, verification level, language, host and platform, source and test content hashes including uncommitted content, build options, executable and sidecar hashes, expected and actual outcomes, and elapsed time. A changed dependency invalidates previous evidence. Structural coverage, behavior validation, and release approval are separate results.

The language evidence recorder (`scripts/test-evidence.mjs`) stores those fields in schema version 1. `runWithEvidence` records source, test, dependency, dirty-worktree, build-flag and process inputs before starting the command, then compares them after completion. Changed or unreadable inputs fail acceptance while the record retains the original input snapshot, the actual command outcome and the input error; a later hash never identifies the implementation that an earlier command tested. `collectEvidence` collects metadata at one instant and does not establish that a command ran against it. `make test-language` emits one execution-bound record for each declared executable-language case. Passing `--evidence-file PATH` persists the records; a later run appends a numbered attempt only when the immutable input snapshot is identical. It retains the first failure and rejects stale or malformed records. A required running host or sidecar must be supplied by PID and executable path. The platform process API must report that same canonical executable before and after its content is hashed; an unrelated file, an exited process or unavailable identity fails explicitly. On macOS the public `proc_pidpath` API supplies the kernel path. The dispatcher in `scripts/platform/platform.js` selects native lookup only when requested; metadata-only consumers remain importable on other platforms, and unsupported lookup fails explicitly at the operation boundary. It also supplies the sidecar release key using the declared operating-system name (`windows` for Node `win32`) and rejects unknown systems or architectures. Shared acceptance fixtures declare their platform, while actual kernel lookup and adapter checks live under `scripts/test/platform/darwin/`. An empty process list is explicit evidence that the case owns no running process.

## CI and release ownership

Language and host jobs install the toolchains and locked dependencies they need, build their own outputs and run their owning checks. A Wails job does not require Rust, and a Tauri job does not require Go. Frontend generation and the native library remain direct prerequisites of either host when needed. Shared setup procedures run independently inside each job; a cache is optional acceleration, not a supplied installation or required build output.

The host-equivalence job installs every language and toolchain required for its comparisons, fetches its own locked dependencies and runs the static comparison of the two hosts and their contract declarations; it does not run the host suites again. It has no dependency on language jobs and downloads none of their build outputs. Cross-toolchain JavaScript harness checks belong to this job; pure JavaScript package checks remain separate. The assigned scopes preserve the full test inventory without mandatory skips or omitted owners. Each host job reports the coverage of its own host; cross-host equivalence is the success of the static comparison together with both host jobs in the required decision, because the contract audit of one host reads no result of the other. A run of both hosts in one job builds the same run configurations with the same flags and reaches the same verdict per host; it adds the Rust deployment variable to the Go build, which the Wails release build does not use, and one queue of both suites, which adds load and checks nothing more. The Tauri host job sets `CARGO_INCREMENTAL=0`, as the Rust builds of the other jobs do.

Dependency acquisition precedes offline build and check stages. CI installs the Node and pnpm versions that the repository declares, and the build environment check of a local build compares only their major versions; Go follows its module/workspace declaration, and Rust uses an exact declared toolchain. Frozen pnpm locks, Cargo.lock and Go module sums remain enforced. Offline checks do not fetch a missing dependency or update locks; they fail with the missing input.

Each release host job builds and audits its own bundle, and packages its release file. The release reads no registry: the [registry check](registry.md#check) checks, for each core version that `core.json` lists, the plugin versions that installation selects for it, so no job of the release checks the registry. The final decision requires success from every required job, including independent equivalence. Publication consumes the exact audited host release files only through the authenticated candidate acceptance gate. The report binds the candidate run and attempt, immutable artifact IDs, the hashes of every published file (the bundle of each candidate host and the five packages), complete bundle and executable identities, clean source/test/dependency identity, a frozen registry and verified installed component content to the required local outcomes. The canonical application and activation scripts and every declared dedicated benchmark each need two independent initial states, every candidate host (mygo, Tauri and Wails), complete native cases where declared, the full application audit, preparation and cleanup. Inputs are compared before and after checks and after cleanup; an observed host relaunch may change its independently verified PID without changing its bytes. Failed, cancelled, skipped, missing, stale or mismatched required evidence prevents publication. Gate unit tests do not establish candidate application acceptance.

An explicitly selected registry index may carry a pinned SHA-256. When supplied, the digest is exactly 64 lowercase hexadecimal characters, requires a nonempty explicit index URL, and is checked against the downloaded bytes before JSON parsing. A mismatch fails acceptance. The default public-index check and an explicit index without a digest retain their existing behavior.


## Bounded execution

The E2E runner requires nonempty `SOKSAK_RUN_ID` and `SOKSAK_RUN_FOLDER` values together before it starts a test child. Missing or partial metadata fails at the runner boundary. The runner passes the supplied values to the child unchanged; it does not synthesize an identifier or folder. This keeps every window-check child attributable to its run and audit output.

Each independently executed case has its own timeout: 10 seconds for pure unit behavior, 30 seconds for native-process behavior, and 60 seconds for application behavior by default. A longer case must declare its limit and concrete reason. Build time is reported separately and is not a test result. A whole-suite timeout does not replace per-case limits.

A check decides its outcome by events and not by elapsed time. A check that something happens waits for the event that shows it, and a bound on that wait only ends a check that hangs; a check whose runner ends each case at its limit sets no bound of its own. A check that something does not happen first waits for an event after which nothing can cause it, and then looks without blocking. A sleep, a time window that a check polls and a comparison of elapsed time decide no outcome. A wait polls a state only when the product gives no event for it, and the check states that reason. A product rule stated in time enters a check as an input, such as a clock or a limit that the check sets, and the end that the product reports at that limit decides, not a time that the check measures. A benchmark measures elapsed time and reports it.

The runner emits a start event, progress at least every five seconds while running, and a terminal pass, fail, timeout, or cancellation event. Every event identifies its case and elapsed milliseconds. Child stdout and stderr remain visible. A command exiting successfully is command evidence only, not proof that tests ran or that assertions passed. Language adapters must separately validate discovered test identities and outcomes. Empty or skipped execution cannot validate a required test. Retrying retains the initial failure.

The command supervisor takes an explicit identifier, executable/arguments, working directory, and positive timeout. It does not use a shell, silently substitute a missing executable, or convert nonzero exits to success. On timeout or cancellation it terminates only its own command process group and waits for cleanup; descendants cannot outlive a successfully completed supervised command. It must not terminate an independently running inspection application or persistent user session.

## Application acceptance

A window check does not capture, restore or judge the frontmost application. An application action may activate its window as specified, and another application that a person brings forward during a check is not caused by the check; activating an earlier application would take the activation away from that person. A check that needs activation state asserts it through the declared status of the action it tests.

An acceptance condition without observation at its required verification level remains unresolved. Unit passes, successful command replies, and inferred behavior do not establish application acceptance.

During stabilization, each change runs its local tests plus terminal, shell, browser, and modal basic behavior tests on the tested build. Verify declared input, resulting state, actual output, isolation, and cleanup, not only dispatch success. Window tests attach to disposable running instances and preserve reported failed windows. They do not start applications or compensate for incorrect state to obtain a pass.

Input-method behavior is verified only by activation-tier checks run with the user's approval, because the OS input method serves only the key window of the active application. Each such run also sends the same keys to an AppKit text view in the same window; the result counts as evidence only when that control produces the expected document.

Native geometry and pixel checks include complete gestures at the requested capture rate. Reaching a recording cap is a normal result with actual frame count and `limited: true`; it cannot validate a gesture whose end was not recorded. Remove recordings only after successful session finalization, including cleanup and the application error audit; preserve recordings when the check or finalization fails. Repeat acceptance from two independent initial states and repeat create/use/close/recreate in the same instance. Run the complete required suite after all implementation changes, without weakening assertions or substituting old-build results.

IME functional acceptance requires the complete approved input gesture, matching same-window AppKit reference documents, coherent terminal states, and recorded glyph and underline proof for every input stage. Capture cadence is recorded as a separate performance measurement. A fixed ScreenCaptureKit sample-gap target is not a functional acceptance criterion because the API does not guarantee its requested update interval. Truncated recordings, missing frames, undecoded identities, missing required stage proof, and incorrect input remain failures.

The older terminal-focus activation consumer verifies the click, exact native input and AppKit documents, and complete callback-to-frame correspondence. It retains raw callback timing and cadence exceedances as observations. This consumer does not measure glyph or underline pixels and does not replace the full IME visual-proof consumer.
