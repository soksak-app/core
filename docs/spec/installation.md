# Plugin installation formats

[한국어](installation.ko.md)

These are the formats that plugin installation uses. The [command line `sok`](cli.md) validates them in both implementations, and the host contract cases `install.*` state each rule ([host contract](host-contract.md)). Every check rejects an unknown field and names the field that is wrong; fields are checked in a fixed order, so a file with several errors reports the same one in both implementations. A version part is at most 4294967295. [Serving installed plugins](#serving-installed-plugins) states how the hosts and the workbench load them.

## Versions and ranges

A version is `x.y.z` with numeric parts and no leading zeros; versions compare by number. A range is one of:

| Range | Versions |
| --- | --- |
| `*` | `>=0.0.0`: every version |
| `x.y.z` | that version only |
| `^x.y.z` | from `x.y.z` below the next major version, and below the next minor version when the major part is 0: `^1.2.3` is below `2.0.0`, `^0.2.3` below `0.3.0`, `^0.0.2` below `0.1.0`. A patch release is a compatible release, also in `0.0` |
| `~x.y.z` | from `x.y.z` below `x.(y+1).0` |
| `>=x.y.z` | `x.y.z` and every later version |
| `>=x.y.z <a.b.c` | from `x.y.z` below `a.b.c`; an empty range is rejected |
| `<range> \|\| <range>` | the union of its parts: a version is inside when one part contains it. Each part is one of the forms above, and the parts are joined by exactly one space, two vertical bars and one space, as in `^0.0.39 \|\| ^0.1.0` |

Other forms, such as `latest`, `**` or pre-release suffixes, are rejected, and so is a union with an empty part or with other spacing around `\|\|`.

## Core release identity

The version of `@soksak/plugin-api` identifies the core manifest and installation contract used to build a plugin. A change to a released contract uses a new core version; a development checkout does not reuse the version of an immutable published release for a different contract. The checkout may declare the next release candidate before publication, but the candidate is not a published release until its tag and assets are published. Plugin `engines.soksak` ranges select against this core version, so one version identifies one released contract.

## Plugin release

A plugin release is the file that `pnpm pack` writes for the plugin, `<scope>-<name>-<version>.tgz` for the package `@<scope>/<name>`: a gzip tar whose entries are `package/package.json` and `package/<path>` for each file that `files` of `package.json` lists. A release whose entries do not all start with `package/` is refused with `<release>: entry <path> is outside package/`. Its `package.json` declares:

| Field | Meaning |
| --- | --- |
| `name` | The name under which the installed files are served at `/modules/<name>/` |
| `version` | Plugin version |
| `engines.soksak` | Range of core API versions the plugin supports |
| `files` | Paths inside the plugin that the release holds; it includes `plugin.json` |

Other `package.json` fields belong to package tools and are not read, except `soksak`, which is refused: the sidecars of a plugin and their ranges are the `dependencies` of its `plugin.json` ([plugins](plugins.md#pluginjson)).

A plugin repository builds against the `@soksak/plugin-api` of one core release. Its `engines.soksak` is `*`, which every core version satisfies, `^<version>` of that `@soksak/plugin-api`, which that release and its later patch releases satisfy, or `>=<x.y.z>` with a lower bound up to that version, which that core release and every later one satisfy; a plugin that uses a manifest field that core added in a release declares `>=` that release. Each plugin repository checks it in its own tests.

`sok plugin install` checks `plugin.json` with every rule of the reader's `validateManifest` (`@soksak/plugin-api`) in the reader's order, and refuses each manifest that the reader refuses: it fails with the location of the `plugin.json` and the reader's error text, and writes nothing. It also refuses a release that holds a file under a `.binary` segment, the path that the binary store of a page reserves ([native surfaces](native-surfaces.md#document-regions)), or that lacks the surface module or the view page that `plugin.json` loads. The reader checks the members of each object in sorted key order, and so does install, so the first refused member is the same whatever the order of the members in the file. The case table `docs/spec/cases/manifest-validation.json` lists the manifests and their results; the reader and the install of both `sok` implementations replay it, and a case on which one of them differs fails.

## Sidecar release

A sidecar version is released as one release per platform, `<file name>-<version>-<platform>.tgz`: the file that `npm pack` writes for the built sidecar folder, a gzip tar whose entries are `package/package.json` and `package/<path>` for each file that `files` of `package.json` lists, with the mode of each file. `pnpm pack` does not keep the execute bit of a file, so a sidecar release is written with `npm pack`. A release whose entries do not all start with `package/` is refused with `<release>: entry <path> is outside package/`, and a release that does not hold the `executable` or the `replay.executable` that its `sidecar.json` names is refused with `<release>: sidecar.json: <field> <path> is not in the release`. The file name of a sidecar `@scope/name` is `scope-name`; an unscoped name is used as it is. A platform is one of `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-x64`, `windows-arm64` and `windows-x64`. Beyond these checks, the installer checks a sidecar release only against the `sha256` of its registry entry before it extracts and runs it; a sidecar, including one from a third party, is not signed or otherwise reviewed by the application.

## Registry index

The registry index `index.json` has `format` 2 and these lists:

| Field | Entry |
| --- | --- |
| `plugins` | `{ id, package, name, description, license, repository, versions }`; each version is `{ version, release: { url, sha256 }, engines: { soksak }, sidecars, plugins }` where `sidecars` maps the sidecar dependencies of the version's `plugin.json` to their ranges and `plugins` maps its plugin dependencies to their ranges; each is `{}` when there is none |
| `sidecars` | `{ name, repository, versions }`; each version is `{ version, protocol: 1, releases }` where `releases` maps platforms to `{ url, sha256 }` |
| `core` | Optional; an index without it lists no core release. `{ versions }`; each version is `{ version, releases }` where `releases` maps `<platform>-<host>` to `{ url, sha256 }`, the zip of the application bundle of that platform and host (`wailsv3`, `tauriv2` or `mygo`), for example `darwin-arm64-wailsv3` ([application update](#application-update)) |
| `packs` | `{ name, description, plugins }`: plugin ids installed together |
| `revoked` | `{ plugins: [{ id, version, reason }], sidecars: [{ name, version, reason }], core: [{ version, reason }] }` |

`url` is an `https:` URL of a published release or an absolute `file:` URL of a local one ([fetching](#fetching)); `sha256` is 64 lowercase hexadecimal digits. A description has 1 to 200 characters (Unicode code points). The index check also rejects a repeated plugin id, package, sidecar, pack or version; a pack that names an unknown plugin; a plugin version that needs an unknown sidecar or a range that no listed sidecar version satisfies; and a revoked version that is not listed. `sok registry build` also reads the `plugin.json` of each plugin and fails when a dependency names neither a listed plugin nor a listed sidecar, or when no listed version of a plugin dependency satisfies its range. A carried version keeps its recorded `plugins` and `sidecars` and is judged by the same check ([build](registry.md#build)). An index whose `format` is not 2, or whose plugin version lacks `plugins`, is refused with an error that names the index and what it found.

## Application update

An application update replaces the bundle of the running application with the bundle of a newer core release. The registry index lists the releases of core in `core`, and `revoked.core` withdraws a version.

The candidate is the newest version in `core` that is newer than the version of the running core, is not in `revoked.core`, and has a release for `<platform>-<host>` of the running application. The application reads the index when it starts and when a window becomes active, as it does for the plugins ([plugin state and commands](#plugin-state-and-commands)).

| Host call | Meaning |
| --- | --- |
| `appUpdateState()` | Returns `{ version, available }`: `version` is the version of the running core and `available` is `{ version, release: { url, sha256 } }` of the candidate or `null`; it rejects with the error of the index |
| `appUpdateStage({ version })` | Downloads the release of the candidate `version`, checks its `sha256`, removes `<config-dir>/updates/<version>/`, extracts the zip into it with `ditto -x -k`, checks that it holds one `<name>.app` whose `Contents/Info.plist` `CFBundleShortVersionString` is `version`, and returns `{ bundle }`, the path of that bundle; a failure rejects with a message that names the step |
| `appUpdateApply({ bundle })` | Copies the `sok` executable of the running application to `<config-dir>/updates/sok`, starts `sok app update --wait <pid> --bundle <bundle> --target <running bundle>` in a new session with the standard error of the application and the event `host.update.start` ([logging](logging.md#entrances)), and quits the application as `host.quit` does, which keeps the persistent services and their sessions running |

`sok app update --wait <pid> --bundle <path> --target <path> [-- <argument>...]` waits until the process `<pid>` has ended, moves `<target>` to `<target>.previous`, moves `<bundle>` to `<target>`, removes `<target>.previous`, and starts `<target>` with the arguments after `--`. When a step fails after `<target>` moved, it moves `<target>.previous` back, starts that bundle, and fails with the message of the step.

`core.app.update` refuses an executable that runs from a folder that macOS made for App Translocation, before `appUpdateStage` downloads anything and before `appUpdateApply` copies `sok` or quits the application. The host detects the folder with the path rule that the setup of the application uses ([agents in the application](cli.md#agents-in-the-application)): the executable path contains the folder element `/AppTranslocation/`. The refusal is the error `application update: <executable path> runs from a translocated location of macOS, so the application bundle must be moved out of quarantine and started again`; it creates no file under `<config-dir>/updates/`, requests no quit, and the application keeps running.

The 설치됨 page of the settings tab lists the core update first in the update list with `core: <running> → <available>`, a link to the release page of the version, and the action 업데이트, which runs `core.app.update`. The release page is derived from the release URL `https://<host>/<owner>/<repository>/releases/download/<tag>/<file>` as `https://<host>/<owner>/<repository>/releases/tag/<tag>`; a release URL of another form has no release page, and the row has no link. The link runs `core.app.release`, which opens the page in the default application. `core.app.update` runs `appUpdateStage` and then `appUpdateApply`; the status `core.app` reports the operation as `staging`, `applying` or `failed` with the version and the error of the failed step, and the row shows the step and the error. The window reads the candidate when it starts, when it becomes active, when the registry changes and when the 설치됨 page opens. An installed plugin whose installed version has an `engines.soksak` that does not contain the candidate is listed under the row with `<id> <installed> (<range>)` and the newest version of that plugin whose range contains the candidate and that is not revoked, or the note that no version does, before the update; a plugin whose installed version the index does not list is not judged. The status `core.app` carries them as `incompatible`.


## Fetching

A registry index and an release are read from a location: an `https:` URL, an absolute `file:` URL, or, where a command takes a path, a file path. Any other URL fails with `<url>: the URL must be https: or an absolute file: URL`. An `https:` URL is read with these rules, which both implementations follow with the same texts:

- The connection uses TLS with the certificate authorities that the operating system trusts.
- A redirect is followed when its target is an `https:` URL, at most 5 times; a redirect to another scheme fails with `<url>: redirect to <target> is not https`, and a sixth redirect fails with `<url>: more than 5 redirects`.
- A response other than 200 fails with `<url>: HTTP <status>`, except the answer 304 to a conditional index request (below).
- The whole request, from connecting to the last byte, takes at most 60 seconds for an index and 600 seconds for an release; a slower request fails with `<url>: timed out after <seconds> s`. The request otherwise ends at its own events: the last byte of the response, an error of the connection or its close. A server that keeps the connection open and sends nothing gives no event, and TCP reports no end for such a peer, so this limit is the end of a request that the server does not end.
- An index holds at most 8 MiB and an release at most 256 MiB; a larger body fails with `<url>: larger than <bytes> bytes`.
- A failure to connect or to read fails with `<url>: cannot connect: <reason>`, where the reason is the text of the network library.

A process reads every `https:` location through one HTTP client, which keeps its connections open between requests, so a read after the first does not connect and negotiate TLS again. Nothing is written to disk: each command and each plugin operation reads the index and the releases it needs again, and an release is checked against its `sha256` before it is extracted. The application reads the index each time a window becomes active ([plugin operations](#plugin-operations-in-the-application)), so a read that finds the index unchanged transfers no body:

- The process keeps in memory, for each index URL, the body of the last 200 answer together with its `ETag` and `Last-Modified` headers, when the answer has either. The next request of that URL sends them as `If-None-Match` and `If-Modified-Since`, and the answer 304 gives the kept body, which is checked again as an index. A 200 answer replaces the kept body, and an answer without either header keeps none. A 304 answer to a request that sent no validator fails with `<url>: HTTP 304`.
- A read of an index URL that starts while a read of the same URL runs receives the result of that read and sends no request, so the plugin state and the application update state that a window reads when it becomes active share one request.
- A release is never kept, because it is read once for an installation and checked against its `sha256`.

## Version selection

Installing a plugin for a core version and platform selects the newest plugin version whose `engines.soksak` contains the core version and that is not revoked. Each installation has one version of a sidecar, shared by every installed plugin that names it. For each sidecar of the selected plugin version, the ranges are the range of that version and the ranges of the other installed plugins that name the sidecar. The version in use is kept when it satisfies every range, is not revoked and has a release for the platform; otherwise the newest sidecar version that satisfies every range, is not revoked and has a release for the platform is selected. When a selection is empty, installation fails with the plugin, the version or ranges and the core version or platform; for a sidecar it names each plugin and range.

A dependency of the selected version's `plugin.json` that names the package of a plugin of the index is a plugin dependency; installation reads the `plugin.json` from the downloaded release before it extracts anything. Installing the plugin installs each plugin dependency by the same rules, recursively: an installed provider is kept when its version satisfies the range of every installed plugin that names it, and otherwise the newest provider version that satisfies every range, `engines.soksak` and revocation is selected; a provider that is installed but not enabled is enabled. A dependency that names neither a plugin of the index nor a sidecar of the index fails with `<plugin> <version>: dependency <package> is neither a plugin nor a sidecar of the registry`, and a cycle fails with `plugin dependency cycle: <id> -> <id> -> <id>`. `sok plugin update` selects only provider versions that satisfy the range of every installed plugin that names the provider. `sok plugin remove` and `sok plugin disable` fail with `plugin <id> is required by <dependent> <range>` when an enabled installed plugin names its package; `installed.json` and the folders stay unchanged.

## Installation layout

Inside the configuration directory, plugin version `<version>` of `<id>` is extracted into `plugins/<id>/<version>`, and the platform release of a sidecar version into `sidecars/<file name>/<version>/<platform>`. An installation reads an existing version folder as that version, so an installation that is refused or stopped before it writes `plugins/installed.json` removes each version folder that it extracted. `plugins/installed.json` has `format` 3, `plugins` and `sidecars`. `plugins` maps each plugin id to `{ version, path, enabled, sidecars }`: the version in use, the folder that installation extracted that version into, `plugins/<id>/<version>`, whether the plugin loads, and the sidecar ranges of that version. An installation keeps only the folder of the version in use, because no operation restores an earlier version. The name of a plugin is the `name` of the `package.json` in its recorded `path`, which the hosts and `sok` read from there; `installed.json` does not hold it. `sidecars` maps each sidecar that an installed plugin names to `{ version, path }`: the version in use, which satisfies the range of every installed plugin that names it, and the folder that installation extracted its platform release into, `sidecars/<file name>/<version>/<platform>`; a sidecar that no installed plugin names is not listed. Each `path` is relative to the configuration directory and must equal the folder that these rules give, so the configuration directory can move ([projects](projects.md#persistence)). Installation records each `path` when it extracts the release, and the hosts and `sok` read files only from recorded paths, resolved against the configuration directory. A file whose `format` is not 3 fails with `<file>: plugins/installed.json: format must be 3`, and a file of the current format whose plugin holds a `package` field fails with `<file>: plugins/installed.json <id>: unknown field package`, and one whose plugin holds a `previous` field fails with `<file>: plugins/installed.json <id>: unknown field previous`; the file stays unchanged. A file of format 2 is refused the same way, with the same error text ([stored data formats](#stored-data-formats)). A release whose `plugin.json` `id` differs from the id of its installation record is refused before anything is extracted: installation fails with `plugin.json id <a> differs from the installed plugin <b>` and writes nothing, and reading `plugins/installed.json` fails with the same text when the `plugin.json` in a recorded folder names another id. A configuration directory without `plugins/installed.json` has nothing installed: the file is absent until the first installation writes it, so a reader of the installed sidecars reads none, and a file that does not parse is an error.

## Stored data formats

Each stored file of the contract carries its form in the member that the table names. A reader accepts only the current number of its file. A file whose member holds another number, or that has no member, fails with `<file>: <name>: format must be <n>`, where `<file>` is the path of the file, `<name>` its name in the table and `<n>` the current number; the file stays unchanged. A refused file does not stop the start of the application: the start leaves it out and shows its error, as a refused `plugins/installed.json` installs no plugin and a refused `projects.json` or `settings.json` is reported in the workspace snapshot ([projects](projects.md#settings)), and every write of a refused file fails with its error. A file that does not parse fails with an error that names it. A release that changes the form of a stored file raises the file's format number and records the change in its changelog. While the release version is 0.0.x, such a release ships no migration: it carries no migration definition, as data or as code, and no reader converts an earlier form. A change that moves folders or crosses files is a replacement change: its release documents it, and reinstalling carries it out.

The stored files of the contract, with their owner, the member that carries their format number, and their file class:

| File | Owner | Number | Class |
| --- | --- | --- | --- |
| `plugins/installed.json` | core | `format` | numbered |
| `plugins/starter.json` | core | `format` | numbered |
| `plugins/registry.json` | core | `format` | numbered |
| `log-policy.json` | core | `schema` | numbered |
| `settings.json`, `<project root>/.soksak/settings.json` | core | `format` | numbered |
| [User `agent-setup.json`](cli.md#user-path-registration) | core | `format` | numbered |
| `projects.json` | core | `format` | numbered |
| `plugin-data.json` | core | `format` | numbered |
| `tab-state.json` | core | `format` | numbered |
| `tab-sessions/<tab>.json` | core | `format` | numbered |
| `roles.json` | core | `format` | numbered |
| `agents/<surface>/role.md`, `agents/<surface>/identity.txt` | core | rewritten by the host at each launch and role change | transient |
| `logs/<role>-<boot>.jsonl` and their index | core | per file (`log.open`, the index header) | log |
| `endpoint.json`, `process.lock`, `performance` | core | rewritten each run | transient |
| `plugins/<id>/<version>/`, `sidecars/<file name>/`, `updates/` | the release payload | the version in the path | external |
| `services/<name>/` | the sidecar | set by the sidecar | external |
| the fetched registry index | the registry | its `format` | fetched |

Every reader checks the member when it reads the file, at the entry of the shared reader of each contract file, so every reader in every process — the host at start and on every later read, every `sok` entry that reads the file — refuses a form that is not current. A reader never creates an absent file: a missing file is the empty state of the current format. Each writer writes the current form only.

A plugin owns no stored file of a configuration folder: the values it persists live as keys of `projects.json`, or of `plugin-data.json` for a key of the plugin, under the per-key format that the [project data](plugins.md#project-data) check reads, and the tab state it writes lives in `tab-state.json`, which core owns, under the format the plugin declares in `surface.unload` ([memory saver](plugins.md#memory-saver)). A sidecar owns the files under its `services/<name>/` tree and sets their form itself. Released identifiers of plugins and their settings sections are immutable once published: a rename leaves the stored references to them unresolved.

## Serving installed plugins

Both hosts serve these paths from the configuration directory and read `plugins/installed.json` for each request, so a page that loads after a change sees it. A file under `/modules/` that the application frontend holds is not one of these paths: the frontend serves it and its request reads nothing of the installation, so no plugin replaces a core file. Another request under `/modules/` reads the `package.json` of the enabled plugins in id order up to the plugin of its package; a `package.json` that cannot be read names no package, and `/installed-plugins.json` carries its error. A request under `/modules/` or `/shared/` reads the `plugin.json` of the plugin that it names and of no other:

| Path | Content |
| --- | --- |
| `/installed-plugins.json` | `{ "plugins": [{ id, package, version, folder, manifest, sidecars?, diagnostics? }] }`: each enabled plugin of `installed.json`, sorted by id, with `folder` the absolute path of its recorded `path` in the configuration directory and `manifest` the content of its installed `plugin.json`. `sidecars` maps each sidecar dependency of the plugin, by sidecar name, to the `message` field of that sidecar's `sidecar.json`; a plugin without sidecar dependencies has no `sidecars`. In a diagnostic build `diagnostics` is the content of the plugin's `diagnostics.json` when its installed package holds one; a release build never sends it. A missing `installed.json` gives `{ "plugins": [] }`. When `installed.json`, a `plugin.json` or a `diagnostics.json` cannot be read or checked, the document is `{ "error": "<message>" }` |
| `/modules/<package>/<path>` | A file that the application frontend holds comes from the frontend. Otherwise, for the package of an enabled installed plugin, the file `<path>` inside the plugin's recorded `path`; a path with an empty, `.` or `..` segment, or a missing file, is not found. Other packages come from the application frontend |
| `/shared/<plugin id>.<point>/<specifier>.js` | The file that `extends.<point>.modules` of the enabled installed plugin `<plugin id>` maps `<specifier>` to, inside that plugin's recorded `path`; the provider can read its own declared modules without a connected contributor, while another page requires an item's range to include the provider point's version; a path that does not end in `.js`, a point that no enabled plugin declares, a specifier that the point does not map, or a missing file is not found |

The workbench imports `/installed-plugins.json` as a JSON module and registers each plugin that it accepts from its `manifest`. A plugin whose entry or manifest the workbench refuses is left out, and its error is shown through the error display, which writes it to the application log: a refused manifest as `installed plugin <id> <version> (<package>): <reason>`, and an `error` document as `installed plugins: <error>` with no plugin registered. The other plugins and the page start, and the page reports ready; a tab of a left-out plugin opens as the placeholder of a plugin that is not loaded. When `plugins/installed.json` cannot be read, the host serves `/installed-plugins.json` as the `error` document and serves every path under `/modules/` from the bundled frontend, because no installed plugin can be named; the core modules load and the page starts. A document of another form, or two accepted plugins with one id or package, is an error of the host: the main page installs its error display and reserves the window button area before it registers the plugins, so such a document stops the page start with that error shown and written to the application log; the page does not report ready, and `host.window.reload` starts it again. A staged page of a plugin finds its plugin among the accepted plugins, so another refused plugin does not stop it, and the error of its own refused plugin names the refusals.

When a host starts, it reads the sidecars that the `dependencies` of the `plugin.json` of each enabled installed plugin name, in name order, leaving out the packages of installed plugins. A sidecar runs from the `path` that `installed.json` records for it, and its executable is the `executable` path of the `sidecar.json` in that folder. A plugin installed or enabled while the application runs is served to pages that load after the change: a `pluginsRun` install, update or enable that succeeds declares the sidecars of the enabled installed plugins that the host has not declared yet, so a page that loads after it, such as the page that the first run reloads, starts them. After each `pluginsRun` operation the host applies the change to the sidecars that it has declared, as [applying a change](#applying-a-change) states.

## Plugin operations in the application

Both hosts run plugin operations with the installer library of their command line (`packages/sok`), so an operation in the application and the same `sok plugin` command change the configuration directory identically. The runtime adapter exposes these host calls and events:

| Host call or event | Meaning |
| --- | --- |
| `pluginsState()` | Returns `{ core, registry, index, installed, firstRun, starter, held }`: `core` is the version of the running core, with which installation selects plugin versions; existing fields keep their meanings; `held` lists the latest held operation of each plugin ([persistent services](persistent-services.md#updates)), sorted by plugin, as `{plugin, action, version, error, sidecars: [{sidecar, planned, running, sessions}]}`, where `version` is the planned version of the plugin, `error` the error of the held operation and `sessions` the `sessions` count of the service as `outdated` counts it, or `null` before the first list of the layouts; `starter` is `null` when no starter job exists, else the current `{ format: 1, state, pack, registry, plugins }` job. A failure to read either state file rejects the call with its path and message |
| `pluginsStarter({ state, pack, registry, plugins })` | Creates the current starter job with `state: "pending"` only while `installed.json` is absent, or marks that exact pending job `complete` after all its plugins are installed. The requested registry URL must equal the configured registry. Existing jobs require the same pack, registry and ordered plugin list; mismatched transitions reject without changing either state file. Repeating the same pending or completed transition is idempotent; a completed job cannot return to pending. Completion requires every listed plugin to be present in `installed.json` and does not require it to be enabled. The host serializes this call with other plugin operations, and the file is replaced atomically. A failed write rejects and prevents the caller from starting or completing the job |
| `pluginsRun({ action, plugin, end? })` | Runs `install`, `update`, `remove`, `enable` or `disable` for the plugin id with the core version and platform of the application, and returns the output of the matching `sok plugin` command. `end: true` runs a held `install`, `update` or `enable` and ends the services that hold it ([persistent services](persistent-services.md#updates)); `end` is absent otherwise. Any other `action`, a plugin id that is not a non-empty string, or an `end` that is not `true` rejects the call without a change. An operation that fails rejects the call with the message of the matching command and leaves `installed.json` as that command defines |
| `pluginsUseRegistry({ index })` | Sets the registry index as `sok registry use <index>` does and returns its output `{ index }`; an `index` that is not a non-empty string rejects with `index must be a non-empty string` |
| `plugins-changed` | Sent to every window after `pluginsRun` changed `installed.json`, with `{ action, plugin }` |
| `window-active` | Sent to a window each time it becomes the key window. The settings tab reads the plugin state and the application update again, because the remote registry sends no change event; a read that finds the state and the failure that the window already shows draws nothing, so a change of the key window redraws no window for it |
| `sidecarsOutdated()` | Returns the `outdated` list of `host.sidecars`: `[{sidecar, running, installed, sessions, surfaces}]`, sorted by sidecar ([persistent services](persistent-services.md#updates)) |
| `sidecarsReplace({ sidecar })` | Replaces the outdated persistent service of the sidecar as [persistent services](persistent-services.md#updates) states, and rejects with an error that names the sidecar when it has no running service of another version |
| `sidecars-changed` | Sent to every window, without a value, when `host.sidecars` changes |

A host runs one operation at a time: a `pluginsRun` call while another runs rejects with `another plugin operation is running`. A writing command of the command line of `sok` owns the configuration directory for the duration of its write through `process.lock` ([stored data formats](#stored-data-formats)): a command beside a running host refuses with the ownership error of the hosts, and two commands cannot race. The plugin operations of the application run inside the ownership of the host and take no lock of their own. A host does not observe changes that a `sok` process makes; the next `pluginsState` call and pages that load later read them. A change of a `pluginsRun` operation applies at once, as [applying a change](#applying-a-change) states; a change that a `sok` process makes applies to pages that load later and to sidecars when the application starts. The browser application has no host, so it has no plugin operations.

### Applying a change

After a `pluginsRun` operation succeeds, the host applies it to its sidecars before it answers the call and sends `plugins-changed`:

- It declares each sidecar that the enabled installed plugins name, from the folder that `installed.json` records. A standard input and output sidecar whose recorded folder changed is replaced: the host stops its running process by the stop rules of [sidecars](sidecars.md#declaration-and-startup), and the next send starts the executable of the new folder. A sidecar that no enabled installed plugin names is stopped and no longer declared, so a send to it fails as a send to an undeclared sidecar does.
- A persistent sidecar whose running service has another version than `installed.json` records is reported and replaced as [persistent services](persistent-services.md#updates) states. An install, update or enable that would give a sidecar with a live service another version is held before it writes anything, so no operation creates such a service ([plugin operations](persistent-services.md#updates)).

A window that receives `plugins-changed` starts its workbench again from its stored state, so it loads the plugins that `installed.json` lists, and the new start shows the project of the window address: the address names the project that the window shows and, while the window shows the library, no project to show but `library=<id>`, the project that the window holds and that the library returns to, so a window at the library stays at the library, and its 작업 화면으로 돌아가기 activates that project while a window holds it open, without drawing it at the start: a host with a main page reloads it through the host call `pageReload` ([page reload](native-host.md#page-reload)), and the mygo host builds its native workbench again. Before the new start it asks for each modified tab of the window with the selection layer `<name> 탭에 저장하지 않은 변경이 있습니다` at the tab: 저장하고 적용 (only with `surface.save`) runs the save command and continues when the tab is no longer modified, 저장하지 않고 적용 continues and discards the changes with the new start, and 적용하지 않기 or closing the layer keeps the workbench of that window; a failed save reports its error as the tab's error, as closing a tab does ([plugins](plugins.md)), and keeps the workbench. A kept workbench: its plugins stay as loaded, and the cards of the changed plugins show the state `reload` until `core.plugins.apply` starts the workbench again after the same questions; `core.plugins.apply` answers `{reloaded}` before the new start: the mygo workbench starts again once the host took the replies of the requests delivered before the apply decided to start again, the reply of `core.plugins.apply` among them, and a request delivered later does not delay the start, which ends it with 1003 ([page end](hosts.md#process-lifecycle)). A window whose new start fails shows the error through the error display. A workbench follows `plugins-changed` only after it has initialised its projects, because the apply saves them. It subscribes first and then reads the plugin state once: when the installed plugins differ from the loaded ones, it applies the change, so a change made before the subscription is applied and a later change sends an event. At most one apply runs: an event during a running apply marks one more apply due, which runs after it settles and reads the state again, so a newer change is not served by an apply that read an earlier state.

### Update at start

Each start of a host updates the installed plugins that the running core cannot use as installed, once, after the registry index is read. An installed plugin is a candidate when either holds:

- its installed `plugin.json` is refused by the reader's `validateManifest` (the check of [plugin release](#plugin-release)), or
- its installed version is older than the newest accepted version.

The newest accepted version is the newest version of the index that is not revoked and whose `engines.soksak` contains the running core. A plugin whose installed version the index does not list is a candidate only when it is refused.

The start runs these steps in the order of the plugin ids:

- With no registry configured, the start updates nothing and stores the info record `plugins: no registry is configured`.
- When the index cannot be read, the start updates nothing and stores the error record `plugins update: <error>`.
- A refused plugin that has no accepted version newer than its installed version stays as it is and stores the error record `plugin update <id>: <reason>`, where `<reason>` is the reader's error text of its installed `plugin.json`.
- A candidate whose update is held ([persistent services](persistent-services.md#updates)) stays as it is and stores the info record `plugin update <id>: <error>`, and `held` of `pluginsState` lists it.
- Any other candidate runs the operation `update` of [pluginsRun](#plugin-operations-in-the-application) for its id: the same installer call, the same [applying a change](#applying-a-change) and the same `plugins-changed` event as `core.plugins.update`. A success stores the event `host.plugins.update` (`plugin`, `from`, `to`) at the level `info`; a failure stores the error record `plugin update <id>: <error>`, and the next candidate runs.

The failures of the start update are kept by the host until it ends, and `pluginsState` reports them as `startUpdate`: a list of `{where, text}` with the place of each record (`plugins update` or `plugin update <id>`) and its text. Each window shows each entry of `startUpdate` through its error display when it reads the state, so the person sees a failure without reading the application log. When the host quits while the start update runs, the start update starts no further plugin, and an installation that has not yet written `plugins/installed.json` writes nothing: it extracts no release, writes no `installed.json` and runs no apply step after the quit began. An `installed.json` written before the quit stays as written, and the start update records the stop as the error record `plugin update <id>: the host is shutting down`.

The start does not refuse a candidate because another plugin operation runs; it waits for that operation to end. The start runs on its own thread, so the window opens without waiting for the registry. It begins at the end of the setup of the host, after the setup added the plugins and sidecars states, and a start of the update without the plugins state is refused with an error and starts no thread. A repeated start changes nothing when every installed plugin is accepted and holds the newest accepted version. Each failure, including a failed read of the index, is an error record of the application log; the settings tab shows the registry error as [plugin state and commands](#plugin-state-and-commands) states.

## Plugin state and commands

The settings tab shows the plugins on its 설치됨 and 찾아보기 pages and on the page of each plugin, before and after installation. [Settings](settings.md#plugins) defines those pages, their search, their layout and their texts. This section defines the plugin states, the statuses and the commands that those pages run.

The plugin list holds each plugin that the window loaded, that `installed.json` lists, or that the registry index lists with a version that is not revoked, sorted by id. A plugin that the index lists only with revoked versions is not in the list unless it is installed or loaded.

### Plugin states

Each plugin has one state:

| State | Text | Condition |
| --- | --- | --- |
| `loaded` | 사용 중 | The window loaded the plugin, and `installed.json` lists the same version enabled |
| `disabled` | 사용 안 함 | `installed.json` lists the plugin disabled, and the window did not load it |
| `available` | 설치 안 됨 | Only the registry index lists the plugin |
| `reload` | 창을 다시 불러오면 적용 | `installed.json` differs from what the window loaded, because the window kept its workbench when a modified tab was kept ([applying a change](#applying-a-change)) |
| `refused` | 불러오지 못함 | `installed.json` lists the plugin enabled, and the window refused its entry or manifest ([serving installed plugins](#serving-installed-plugins)); a reload does not load it, so the state does not make the page wait for one |
| `requires` | 필요한 플러그인 없음 | `installed.json` lists the plugin enabled, and no loaded and enabled plugin of the window is of a category that it requires ([plugin categories](plugins.md#plugin-categories)); installing or enabling a plugin of the category and reloading loads it |

Each plugin shows:

- The description of the loaded manifest, else of the registry entry ([plugins](plugins.md) and [registry index](#registry-index) require one); a plugin that only `installed.json` lists has no description and shows its id as its name.
- A version line with 설치된 버전 <version> and 최신 버전 <version>, the version that installation selects for the running core ([version selection](#version-selection)), each when present, and core <version>에 맞는 버전 없음 when the plugin is `incompatible`.
- A sidecar line, 사이드카 followed by each sidecar that the plugin names, sorted by name: the installed version from `installed.json` `sidecars`, or else the range that the plugin declares. The sidecars and ranges come from the `installed.json` entry of an installed plugin, else from the registry version that installation selects for the running core, else from the `dependencies` of the loaded manifest. A plugin without sidecars shows 사이드카 없음; an `incompatible` plugin that is neither installed nor loaded has none of these sources and shows no sidecar line.
- Actions, each bound to its command: 설치 `core.plugins.install` when the plugin has a `latest` version and it is not installed; 업데이트 `core.plugins.update` when it is installed and its `latest` version is newer than the installed one; 적용 `core.plugins.apply` when its state is `reload`; 사용 `core.plugins.enable` or 사용 안 함 `core.plugins.disable` when it is installed, by its `enabled` value; 제거 `core.plugins.remove` when it is installed. While an operation runs, every action of every plugin is disabled and the plugin shows "<plugin> <action> 진행 중". After a failed operation the plugin shows its error. A plugin that `held` lists shows its error and the action 세션 <n>개를 끝내고 업데이트, 세션 <n>개를 끝내고 설치 or 세션 <n>개를 끝내고 사용, by the `action` of the entry, bound to its command with `{plugin, end: true}`, where `<n>` is the sum of the `sessions` of its sidecars; the action is absent while a `sessions` is `null`.

The settings tab reads the plugin state with `pluginsState` and the outdated sidecars with `sidecarsOutdated` when it shows a plugin page, after each `plugins-changed` event and after each `sidecars-changed` event. A read that finds what the settings tab holds calls no listener of the plugin state or of the application update, so it draws nothing. `core.plugins` reports the outdated sidecars as `outdated`, and the 설치됨 page shows each of them above the plugin list with `<running> → <installed>` and the action 세션 <sessions>개를 끝내고 적용, or 세션 <sessions>개를 끝내고 종료 for a sidecar that is no longer declared, bound to `core.plugins.replace {sidecar}`. `<sessions>` counts the surfaces of every plugin that have sent to the service ([persistent services](persistent-services.md#updates)). A registry index that cannot be read shows "레지스트리를 읽지 못했습니다: <message>" above the plugin list, and the page keeps the loaded and installed plugins. A plugin state that cannot be read, such as an invalid `installed.json`, shows "플러그인 상태를 읽지 못했습니다: <message>" and no plugin entries. Both messages go through the error display path ([exposure](exposure.md)). Without a host, as in the browser application, the settings tab has only the loaded plugins, each `loaded`, and no action.

While `updates` is not empty, the 설치됨 page shows the badge `업데이트 <latest>` on the row of each plugin of `updates`, the filter choice `업데이트 <n>`, and the button `모두 업데이트 (<n>)` bound to `core.plugins.update-all` ([settings](settings.md)). `core.plugins.update-all` runs the host call `pluginsRun` with the action `update` for each plugin of `updates` in id order, one after the other, reads the plugin state again after each, and stops at the first failure with the host error; it takes no parameters, fails with "plugin operations need a native host" without a host and when another operation runs, and does nothing when `updates` is empty. The action is `core.settings-tab.plugins.update-all`. `core.plugins.show-updates` opens the settings tab on its 설치됨 page with the filter `updates`.

`core.plugins.registry` takes `{index}`, runs the host call `pluginsUseRegistry` and reads the plugin state again; it fails with -32602 (invalid params) when `index` is not a non-empty string and with the host error when the index cannot be read or checked. `core.plugins.install`, `core.plugins.update`, `core.plugins.remove`, `core.plugins.enable` and `core.plugins.disable` take `{plugin}` and run the host call `pluginsRun` with their action; `core.plugins.install`, `core.plugins.update` and `core.plugins.enable` also take `end: true`, which they pass to `pluginsRun`. A command fails with -32602 (invalid params) when `plugin` is not a non-empty string or `end` is present and not `true`, with the host error when the operation fails or another operation runs, and with "plugin operations need a native host" without a host. A command records its operation in `core.plugins` before it calls the host, and its result after the call. `core.plugins.apply` asks for each modified tab of the window and starts its workbench again as [applying a change](#applying-a-change) states, answering `{reloaded: true}` before the new start; it answers `{reloaded: false}` when a tab is kept. `core.plugins.replace` takes `{sidecar}` and runs the host call `sidecarsReplace` ([persistent services](persistent-services.md#updates)); it fails with -32602 (invalid params) when `sidecar` is not a non-empty string and with the host error when the replacement fails. `core.plugins.browse` opens the settings tab and selects its 설치됨 page.

`core.settings-tab` reports `query`, `listed` and `actions`: the installed-plugin search text, the plugin ids of the entries shown in order, and the action buttons of the entries in document order as `{plugin, action, disabled}`, whose position is the index of the element name `core.settings-tab.plugins.action`; `listed` and `actions` are `[]` on the pages other than 설치됨 and 찾아보기. The description line of each plugin that has a description is the element name `core.settings-tab.plugins.about`, and each contribution line of a plugin, its state or its error, is the element name `core.settings-tab.plugins.contribution`, both in document order. `core.plugins` reports:

| Field | Value |
|---|---|
| `core` | The version of the running core that `pluginsState` reports, or `null` before the state is read, when it cannot be read and without a host |
| `registry` | The registry index URL, or `null` |
| `error` | The registry index error or the plugin state error, or `null` |
| `plugins` | One entry per plugin in the list, sorted by id: `{id, name, description, state, composition, installed, latest, incompatible, sidecars}`; `composition` is the surface composition kind of the manifest loaded in this window, or `null` when no surface declaration is loaded; it does not depend on whether a tab is open. `installed` is `{version, enabled}` or `null`, `latest` is the newest version that the registry index lists, that is not revoked and whose `engines.soksak` contains the running core, or `null`, `incompatible` is `true` when the registry index lists a version of the plugin that is not revoked and none of them contains the running core, and `sidecars` lists `{name, range, version}` sorted by name, or is `null` for an `incompatible` plugin that is neither installed nor loaded, where `range` and `version` are `null` when unknown |
| `operation` | `null` before the first operation, then `{action, plugin, state, error}` of the latest one: `state` is `running`, `done` or `failed`, and `error` is the message of a failed operation or `null` |
| `reload` | `true` when a plugin has the state `reload`; a plugin of the state `refused` does not set it |
| `updates` | The installed plugins whose `latest` version is newer than the installed one, sorted by id: `{id, installed, latest}` |
| `held` | The `held` list of `pluginsState`, or `[]` before the state is read and without a host |

Acceptance:

- The 설치됨 and 찾아보기 pages of the settings tab list loaded, installed and registry plugins with their name, description, state, versions and sidecars, filtered by the search, and `core.plugins.browse` opens the 설치됨 page from any window.
- Installing, updating, disabling, enabling and removing a plugin from its entry changes `installed.json` as the matching `sok plugin` command does, reports the operation in `core.plugins`, applies the change to the sidecars, and reloads every window page that keeps no modified tab, so the windows show the changed plugins without an application restart.


## First run

`environment.json` names the starter pack in `starter`. On a first run with no `plugins/installed.json` and no starter job, the workbench snapshots the pack name, current registry URL and ordered plugin IDs to `plugins/starter.json` as a pending job before it installs the first plugin. The file is `{ "format": 1, "state": "pending" | "complete", "pack": "<name>", "registry": "<url>", "plugins": ["<id>", ...] }`. `format` must be 1; the state must be `pending` or `complete`; the pack, registry and every plugin id must be a non-empty string; plugin IDs must be unique and ordered; no other fields are accepted. A reader reports the file and the invalid field or value. A missing file means there is no pending job; it is not converted from `installed.json`.

Each successful `pluginsRun` writes the installed state before the next plugin starts, so a restart resumes only IDs that are absent from the pending job's installed state. A failed install leaves the job pending. After all listed IDs are installed, the workbench marks the matching job complete and reloads the page if an install changed `installed.json`. A completed job is never enforced again: a later user removal or disable is preserved. A pending job resumes its saved pack and plugin list; its registry URL must still match the configured registry. A registry mismatch leaves the job pending and reports an error instead of changing the configured registry or installing from another index.

A missing job file with an existing `installed.json` means no job is pending and does not trigger starter installation; this keeps existing profiles from reinstalling plugins that their users removed. A profile with a partial starter install created before this job contract is indistinguishable from a completed install followed by user removal, so automatic recovery of that legacy ambiguity is not provided. When `environment.json` names a default registry in `registry` and `pluginsState` reports no registry, the workbench first sets that registry with `pluginsUseRegistry` and reads the state again. Without either registry, or if the registry index or starter pack cannot be read, the window starts without installing the pack, logs `first run: the starter pack <name> was not installed: <error>`, and shows the application error `시작 플러그인 묶음 <name>을 설치하지 못했습니다 · <error>.`; no job is created, so a later first run can try again. If a plugin install fails after the pending job was written, the same message is shown and the pending job resumes on the next start even though `installed.json` now exists. The displayed text preserves `<error>` and makes no claim about the failure's cause or remedy. An environment without `starter`, or without a host, installs nothing.
