# Private native API inventory

[한국어](private-native-apis.ko.md)

Read this document first when native behavior fails after updating native source, framework dependencies, the SDK, macOS, or its WebKit runtime. Review it before those updates as well. Checking a dependency first does not establish that it caused the failure.

This is the canonical inventory for application calls, diagnostic calls, and the private framework paths used by the current macOS hosts. The shared layout library has no native API dependency. Windows and Linux native execution remains unverified.

## Necessity review

### Device scale

Keep this correction. A half-point native height previously left an uncovered strip because the native drawing size became integral before document layout. `sp_document_create` sets each root view, the web view of a view page, to `pageZoom` 1 and sets `_setOverrideDeviceScaleFactor:` to the backing scale when it places the view in its surface, and `updateScale` sets both again when the backing scale of the window changes, in a container whose coordinates are AppKit points. One CSS pixel is then one point, and the backing scale sets only the raster density. Public `pageZoom` keeps CSS dimensions but does not set that density, so the override is required. Main and modal webviews do not use this setting. A document region is a subview of its surface. `document_view.m` sets its `pageZoom` to `document.zoom` in `sp_document_create`, `surfaceScaleChanged` and `applyInsets`, and its device scale factor to the surface scale in `sp_document_create` and `surfaceScaleChanged`; at page zoom 1 its CSS size is its native size in points, and its page zoom is the [text size](../spec/text-size.md) factor of its card. [`webview_geometry_test.m`](../../native/darwin/tests/webview_geometry_test.m) checks the device pixel ratio and CSS size of the root view and a document region at 2×, after changing to 1×, and back.

Review the selector's signature and the meaning of custom versus intrinsic scale after an update. A changed interpretation can cause incorrect CSS size, rendering density, or input coordinates. Verify half-point document coverage, the last device pixel, and 2×↔1× transitions with [`webview_geometry_test.m`](../../native/darwin/tests/webview_geometry_test.m), and window resizing with [`geometry.test.mjs`](../../e2e/geometry.test.mjs). The coordinate contract is in [native surfaces](../spec/native-surfaces.md).

The declaration is in [`WKWebViewPrivate.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewPrivate.h); the implementation uses `WebPageProxy::setCustomDeviceScaleFactor` and `deviceScaleFactor` in [`WebPageProxy.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebPageProxy.cpp).

### Rendering update rate

Keep this setting for the app DOM webview, plugin root views and attached document regions. WebKit on macOS enables `PreferPageRenderingUpdatesNear60FPSEnabled` by default, so a page updates its rendering near 60fps on a 120Hz display. Each placement waits for the next presentation of the app DOM webview, so a divider drag advanced at most once per 60Hz frame. The feature is a WebKit feature flag, and `_setEnabled:forFeature:` is the interface WebKit provides to change such a flag on a `WKPreferences` object. Registration of the app DOM webview fails when the feature is missing, and both hosts then fail to start. Attached document creation also fails when the feature is missing. Document regions render at the display rate so their prior paint widths do not lag the surrounding layout. Background plugin hosts keep the default. `host.window` reports the value per webview as `near60fps`.

Verify with [`window_facts_test.m`](../../native/darwin/tests/window_facts_test.m) and [`document_core_root_test.m`](../../native/darwin/tests/document_core_root_test.m), which fail without their corresponding setting, and `native content, cards, and the sidebar rail stay aligned` in [`outside.test.mjs`](../../e2e/outside.test.mjs). Review the feature key in [`UnifiedWebPreferences.yaml`](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml) and the declarations in [`WKPreferencesPrivate.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferencesPrivate.h) and [`_WKFeature.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/_WKFeature.h).

### Presentation completion

Keep this correction. Completing a JavaScript evaluation or a DOM animation-frame callback does not confirm that a webview has presented its new geometry. The host waits for the owning project window's single app DOM before committing each native layout transaction, and joins the changed plugin root view to that transaction so its pixels match the committed frame. The join is ticket- and generation-specific. Before native cancellation, the host removes pending ticket state and abandons its joins because cancellation does not call presentation callbacks. Native cancellation releases the active `CATransaction` and removes queued owner requests; it does not roll back applied geometry. The cancelled request returns an error and is not reported as a successful presentation. A hidden, ended, or unresponsive root view follows the existing abandonment path. Nested document regions do not join the root view transaction. Preparations from different windows are serialized because `CATransaction` belongs to the UI thread; navigation and closing cancel only the owning window's preparations. Native image raster readiness remains a separate required check.

Review callback timing, painting completion, and behavior during navigation or process termination. The callback alone is not proof of captured pixels: its implementation can complete immediately without a running process or drawing area. Document readiness and complete recordings remain required. Run [`surface_layout_test.m`](../../native/darwin/tests/surface_layout_test.m), which checks which documents the wait includes, and verify [`outside.test.mjs`](../../e2e/outside.test.mjs), [`paint.test.mjs`](../../e2e/paint.test.mjs), and [`hosts.test.mjs`](../../e2e/hosts.test.mjs), including reload cleanup. [`projects.test.mjs`](../../e2e/projects.test.mjs) also verifies independent project windows, modal routing, and close/reopen cleanup.

Review `_doAfterNextPresentationUpdate:` in [`WKWebView.mm`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebView.mm) and `WebPageProxy::callAfterNextPresentationUpdate` in [`WebPageProxy.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebPageProxy.cpp).

The native `surface_layout_test` confirms that the application-document callback completes while the outer layout transaction remains open. Removing the wait on an assumed transaction deadlock is not justified by that implementation. Both hosts wait for the DOM documents, then the current visible image rasters, before committing; they report a rejected preparation instead of returning success for an obsolete ticket.

The Tauri event-dispatch callback holds Tao's event-handler mutex. A transaction commit from that callback can synchronously redraw the window and re-enter the same mutex. A macOS thread sample reproduced this deadlock during the project-library check. Both hosts dispatch presentation completion through the public native main queue (`ui_queue.m`), retaining the document and raster waits. Reload and close cancellation use the same queue. This scheduling boundary adds no private API and does not modify framework state. `ui_queue_test` verifies execution after the caller releases its lock; rebuilt-host library and drag checks verify integration.

### Pointer tracking

Keep this correction. Overlapping native tracking areas can deliver movement to more than one webview; choosing a view with public AppKit hit testing does not disable the other webview's tracking. The shared module applies the private flag according to that hit result. It does not disable keyboard, click, or drag handling, change keyboard focus, or replace the native event with a DOM event.

The private flag also affects mouse-enter and mouse-exit processing. The local monitor changes the selected target on mouse-move and mouse-enter events; it does not change that target on mouse-exit. WebKit drops an exit once the flag is set, and AppKit fixes no order between the exit of a view and the move that takes the pointer from it, so the monitor sends the view that loses the pointer an exit outside it before it sets the flag, and the page hovers nothing. Do not describe exit delivery as unconditionally enabled. Registration rejects an unavailable selector, and removal resets the flag. Review tracking-area behavior, event ordering, hover cleanup, hiding, removal, and retained keyboard input after an update. This API does not cancel work already submitted to WebKit; delayed cursor responses are not validated by the retained check.

Use the baseline and registered runs of the [standalone input check](examples.md#diagnostics), plus [`modal.test.mjs`](../../e2e/modal.test.mjs). Review `_setIgnoresMouseMoveEvents:` in [`WKWebViewMac.mm`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/mac/WKWebViewMac.mm) and its tracking handlers in [`WebViewImpl.mm`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/mac/WebViewImpl.mm).

### Transparent background

Keep this correction for hybrid-surface and modal transparency. Transparent DOM content cannot reveal native content below an opaque webview. Public `underPageBackgroundColor` controls the color behind page content; setting CSS transparency and that color alone does not disable native background drawing. The private `drawsBackground` state supplies that separate requirement. Hybrid stacking is specified by [surface composition](../spec/surface-composition.md); the 50% shading and blur remain CSS behavior specified in [native modals](../spec/native-modals.md). DOM-only surfaces remain opaque.

Review the exact KVC key, its receiver class, and whether configuration-time and instance-time settings still have the expected effect. Wails checks the assigned value and fails view creation on a KVC exception or an unchanged opaque state; the diagnostic read itself has no such exception handling. Geometry and presentation selectors are also called directly. Do not assume every unavailable private API produces a handled error.

Verify hybrid native content below the DOM plane, anchor transparency, overlay stacking, initial modal transparency, captured shading and blur, clear settings content after navigation, menus without a backdrop, and close/reload cleanup with the composition checks, [`modal.test.mjs`](../../e2e/modal.test.mjs), and [manual acceptance](examples.md#manual-acceptance). Transparency does not correct fractional geometry; surface dimensions must independently pass the footer checks.

The view and configuration declarations are in [`WKWebViewPrivate.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewPrivate.h) and [`WKWebViewConfigurationPrivate.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewConfigurationPrivate.h). ### Page focus in surface and modal webviews

Keep this setting for surface and modal webviews. When a page focuses an element while its web view is not the first responder, WebKit sends `MakeFirstResponder` to the UI process, and `PageClientImpl::makeFirstResponder` makes the web view the window's first responder. A shell surface that focused its input after loading took the keys from an open menu, so a native Escape did not close the menu. `_setShouldSuppressFirstResponderChanges:YES` makes `PageClientImpl::makeFirstResponder` return without changing the first responder. AppKit clicks and the host's own `-[NSWindow makeFirstResponder:]` calls are not affected. The main page does not use the setting and can still move the focus. The function reports failure when the selector is missing, and both hosts then fail to create the webview.

Verify with [`webview_focus_test.m`](../../native/darwin/tests/webview_focus_test.m), which fails without the setting, and the menu Escape steps of [`modal.test.mjs`](../../e2e/modal.test.mjs). ### Document-region data store

Keep this store for document regions. The public `+[WKWebsiteDataStore dataStoreForIdentifier:]` keeps every persistent store in the application's WebKit container (`~/Library/WebKit/<bundle>/WebsiteDataStore/<identifier>`), so window checks with a disposable `--config-dir` reused cookies from earlier runs and from the user's own instance. `-[_WKWebsiteDataStoreConfiguration initWithDirectory:]` creates a persistent configuration whose data directories are under the given directory, and `-[WKWebsiteDataStore _initWithConfiguration:]` creates the store from it; this is the interface WebKit provides for a store in a caller-chosen directory. The library keeps one store per directory until `sp_document_store_close` ends it, because two store objects for one directory write the same files. The hosts keep the store of `<config-dir>/document-data` for the life of the application, since the configuration directory outlives the process and no project has its own store. `sp_document_store_close` serves a caller that removes the directory, such as a check that removes its temporary folder: the network session of a store ends only when its last reference goes away (`WebsiteDataStore::~WebsiteDataStore` calls `NetworkProcessProxy::removeSession`), and the network process writes `Cookies/Cookies.binarycookies` into the directory until then, also after the process exits. The function rejects a directory with an open document, removes its store from the library and sets `-[WKWebsiteDataStore _setCompletionHandlerForRemovalFromNetworkProcess:]`, which the destructor hands to `removeSession` and which runs after `NetworkProcess::destroySession` has destroyed the session and closed its storage. `+[WKWebsiteDataStore removeDataStoreForIdentifier:completionHandler:]` applies only to identifier stores, not to a store in a caller-chosen directory. Document creation fails when the directory cannot be created or the store cannot be initialized, and the host then reports the error.

### WebContent process memory after reload

The measured cause of the memory that repeated reloads keep is in WebKit, not in this application. `Document` keeps the results of cacheable `querySelectorAll` calls (a simple class or tag selector) in `m_querySelectorAllResults`; each entry holds a `NodeList` of the result elements, the elements hold their document, and document teardown does not clear the map ([`Document.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/Document.cpp)). A reload in the same WebContent process therefore leaves the previous document alive until WebKit's memory-pressure release calls `clearQuerySelectorAllResults` ([`MemoryRelease.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/MemoryRelease.cpp)). [`webview_process_test.m`](../../native/darwin/tests/webview_process_test.m) reproduces it with one class query: four reloads keep about 55 MB per reload of a document-owned marker, and the same page without the query keeps none. On the application page every reload left one more document (one to seven after six reloads); WebKit's simulated memory warning returned the count to one and the physical footprint from 267 MB to 106 MB.

The main-page reload formerly ended the WebContent process with `_killWebContentProcessAndResetState`, which discarded this memory together with the process and left the window without a page until the new process drew. WebKit has no interface that releases the cache for one process. The library therefore wraps the navigation delegate that the framework sets on the app DOM webview: every message still reaches that delegate, and when it allows a main-frame navigation that replaces the document (a reload, a page change, or a load; not a fragment navigation), the wrapper answers `_WKNavigationActionPolicyAllowInNewProcess`, so WebKit opens the new document in a new WebContent process while the previous page stays on screen until the new one commits ([`WebProcessPool.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebProcessPool.cpp) `processForNavigationInternal` swaps when the client requests it). After the commit it calls `_clearBackForwardCache`, because WebKit keeps the previous page suspended in its process for a back navigation. The previous process then ends with the documents it held. [`webview_navigation_test.m`](../../native/darwin/tests/webview_navigation_test.m) checks that each reload and load uses a new process and ends the previous one, that a fragment navigation keeps the process, and that the framework delegate decides every navigation; `e2e/reload-memory.test.mjs` checks the same on both hosts and bounds the page footprint after the reloads. Review the `querySelectorAll` result cache in `Document.cpp` and the process-swap decision after every WebKit update.

### Mouse-processing completion

The runtime and standalone checks use `_doAfterProcessingAllPendingMouseEvents:` because native mouse handling is asynchronous. The runtime drains pending work before sending a press or release and after its receipt. It waits on the document that owns the gesture, including a release over another native view. ### Title bar height

Keep this call. AppKit centres the window buttons vertically in the title bar and moves them back whenever the title or the recording indicator changes, so the host does not move the buttons; it sets the title bar height instead. The page's first row grows with the frame text factor ([text size](../spec/text-size.md)), and the public API has no title bar height: an empty toolbar with the unified compact style gave a fixed 40pt title bar, and at the frame factor 1.5 the buttons sat 13pt below the top and 27pt above the bottom of a 54pt row. `-[NSWindow setTitlebarHeight:]` is AppKit's own setter for this value and is missing from the SDK headers. It forwards to `-[NSThemeFrame setCustomTitlebarHeight:]`, which returns without work when the value is unchanged; AppKit's layout reads the custom height for the title bar height (`-[NSThemeFrame _titlebarHeight]`), the content layout rect, and the button origins (`_closeButtonOrigin`, which centres the buttons in it). `-[NSThemeFrame _windowWillEnterFullscreen:]` saves the value and clears it, and `_windowWillExitFullscreen:` restores it.

Call conditions: the window has standard buttons and a content view, it is not in full screen, and the height is a positive finite number; `windowSetTitlebarHeight` rejects a window without standard buttons or a content view and a height that is not positive and finite with an error, and both hosts accept only 32 through 200 points from the page. A value of 0 or less clears the custom height without laying the title bar out again, so the function never passes one. A height set during full screen would be replaced by the saved value when the window leaves full screen, so in full screen the function does not call the setter and succeeds; the preparation then answers a title bar row of 0, and the page prepares its row again after the window leaves when the restored height differs from it. With a custom height, a toolbar no longer decides the title bar height, so the windows have no toolbar.

Measured on macOS 26.6.2 (arm64): at 40, 45, 54, 63, 72, 90, and 108pt, with and without an empty compact toolbar, the title bar equals the requested height, the buttons are centred to 0.5pt, and the layout holds after a title change, a resize, and a move. A height set while the window's layout transaction is open (`surfaceLayoutBegin`) changes the button frames and layers at once, but the presentation layers and the recorded window keep the earlier place for 12 display refreshes until `surfaceLayoutCommit`, and show the new place after it ([`window_titlebar_layout_test.m`](../../native/darwin/tests/window_titlebar_layout_test.m)). Failure signs: [`window_controls_test.m`](../../native/darwin/tests/window_controls_test.m) reports a title bar other than the requested height, buttons off centre after a title change or a resize, or a title bar that does not shrink, and the page's verification W fails (`W 창 단추는 첫 행 가운데`) with unequal space above and below the buttons. Review the selector, its forwarding, and the full-screen save and restore with a disassembly of `-[NSWindow setTitlebarHeight:]` and `-[NSThemeFrame setCustomTitlebarHeight:]` after an OS update.

### Audible media of a document region

Keep this read. The `media` protection of the memory saver keeps a tab only while it plays sound. The public `requestMediaPlaybackStateWithCompletionHandler:` does not answer that: `WebPage::requestMediaPlaybackState` in [`WebPage.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/WebProcess/WebPage/WebPage.cpp) answers `none` only without a media session, `paused` only when a session of the page is in the paused state (`MediaSessionManagerInterface::mediaPlaybackIsPaused`) and `playing` otherwise, so a page whose media element has never played (a session in the idle state) answers `playing`. `_isPlayingAudio` in [`WKWebViewPrivate.h`](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewPrivate.h) returns `WebPageProxy::isPlayingAudio`, the `IsPlayingAudio` flag of the media state of the page, which `HTMLMediaElement::mediaState` sets only while the element plays and `computeCanProduceAudio` holds (not muted, a volume above zero, an audio track). The property is observable with key-value observing, and WebKit sends its changes to the page client for the audio indicator of a tab.

Call conditions: the main thread and an open region. [`document_report_test.m`](../../native/darwin/tests/document_report_test.m) requires `false` for an element that has never played, `true` while it plays and `false` after it is paused; review the flag computation after a WebKit update when that check fails.

## Native input injection

[`input_inject.m`](../../native/darwin/src/input_inject.m) delivers pointer and key input to an application window without activating the application. It uses public AppKit calls, except for scroll, with these conditions:

- Keys: `-[NSWindow sendEvent:]` with `+[NSEvent keyEventWithType:...]`. A focused element receives the keys in a window that is not the key window.
- Pointer press, drag, release of the key window of an application that is really active: `-[NSApplication sendEvent:]`, as for a person's press. The local monitors of the application see the gesture, AppKit moves the first responder and routes the drag and the release to the view of the press, and the monitor of the press origin records the origin. A gesture keeps the path of its press.
- Pointer press, drag, release of any other window, also of a window that AppKit holds as the key window of an application that is not active: the event method (`mouseDown:`, `mouseDragged:`, `mouseUp:`, right-button variants) of the view returned by `hitTest:`. AppKit treats a press there as a first click and does not deliver it to the view, so the application path is not used. The driver moves the first responder before the press and records the press origin, and the local monitors of the application do not see this press.
- Press context: `input_inject.m` pushes the target window and point on a main-thread scoped context and restores the previous context in `@finally`. It covers the delivery of a press on either path. For receipt-backed pointer input, phase one uses the requested window point and phase three uses the stored press origin around only the synchronous `webviewInputSendThen` responder preflight; the context ends before asynchronous receipt handling. `image_region.m` uses the scoped point to classify click-through focus changes when `NSApp.currentEvent` is not a mouse event; ordinary AppKit events continue to use their current event. The context does not alter AppKit state. `-[NSApplication sendEvent:]` does not set `NSApp.currentEvent`, so the context also covers the application path. V5-45-1 measured 20 failed window checks for synthetic input to inactive windows through `-[NSApplication sendEvent:]`, so a window that is not the key window keeps direct delivery, and the scoped context preserves that no-activation contract while fixing responder-transfer classification. `webviewInputSendThen` moves the responder before the wait only in a window that is not the key window.
- Pointer movement: the web view routing of `webview_input.m` runs first, as for an event that AppKit dispatches. Then `mouseExited:` and `mouseEntered:` of the owners of the tracking areas that the point left or entered, and `mouseMoved:` of the owner of each area that holds the point and tracks moves, in every shown view of the window, also under a view that covers it. A press in the key window sends this move first. An event sent through `-[NSWindow sendEvent:]` does not reach those owners, so the move calls them directly. WebKit updates hover only in an active page: `WebFrame::handleMouseEvent` passes a move without a button to `passMouseMovedEventToScrollbars` unless `FocusController::isActive()`, and that state comes only from `PageClientImpl::isViewWindowActive` (the window's `isKeyWindow`). No WebKit interface sets it. `sp_input_pointer` therefore returns `SP_INPUT_INACTIVE` for a move to a window that is not key, and does not fake the key state.
- Activation: `sp_input_activate` calls `-[NSWindow makeKeyAndOrderFront:]` and `-[NSApplication activate]`, waits for both the key-window and the application-active notifications, and then calls `_doAfterActivityStateUpdate:` for every visible webview in the window on the next main-queue turn. Hidden webviews are not input targets and do not block this explicit activation. The callback runs after WebKit has sent the scheduled active state (`WebPageProxy::dispatchActivityStateChange`), so a following mouse event reaches the web process after that state on the same connection. The system can decline activation, and another application or window can take the focus. The function reports the step that stopped (`sp_activate_result`) and the frontmost application; `tests/input_activate_test.m` creates each of these conditions.
- Scroll: **private CoreGraphics use.** No public API creates a scroll `NSEvent` that carries a window. The code creates the event with `CGEventCreateScrollWheelEvent2`, sets the undocumented window-number field (`CGEventField` 51) and the private `CGEventSetWindowLocation`, and converts it with `+[NSEvent eventWithCGEvent:]`. The result has `window` and `locationInWindow` set, and `-[NSWindow sendEvent:]` delivers it to the view under the point. The code rejects the input when the converted event has no window. With only field 51 the location is wrong; with only `CGEventSetWindowLocation` the event has no window. `CGEventPostToPid` did not deliver the scroll to an inactive application.

Failure signs: `tests/input_inject_test.m` reports missing, untrusted, or misplaced pointer events, no wheel event, a scroll distance other than the requested 120 pixels, or a lost focus after a click. After an OS or WebKit update, run `make -C native/darwin test` and `make -C native/darwin test-app-activation` (the latter takes the keyboard focus); replace the private scroll calls when a public method creates a windowed scroll event.

## Update review procedure

1. Record the old and new application revision, OS/build, installed WebKit version, SDK/toolchain, and resolved framework revisions. Read this inventory first when diagnosing a failure after any native update.
2. Match the symptom to the relevant entries. Compare receiver classes, selectors or keys, argument and callback types, availability, threading, and actual semantics in the changed source. Inspect framework callers even when the application uses a public wrapper. Source review narrows the investigation; reproduce the failure before assigning its cause.
3. Reassess necessity. Remove a correction when the required behavior is now implemented correctly without it. Preserve the behavior contract and remove harmful or unnecessary code instead of adding compatibility branches, fixed delays, reduced precision, or background recoloring to conceal a failure.
4. Follow [build and verification](examples.md): rebuild and restart both hosts, run the affected checks and `make test-app`, and run `make -C native/darwin test` and `make test-app-activation` when input dependencies change. Verify actual gestures and pixels. Record unavailable platforms or skipped checks explicitly.
5. Update this inventory and its Korean translation in the same change as API additions, replacements, removals, or changed call conditions. Record changed behavior and new validation in [features](../features.md) and [changes](../../CHANGELOG.md). Run `make check-docs`; source review must also confirm the inventory's accuracy.

The necessity decision belongs to the specific correction. Private status alone does not invalidate a correction, and successful tests alone do not justify its design. Each new entry requires a concrete cause, the public API limitation, exact implementation location and scope, failure signs, and verification steps.
