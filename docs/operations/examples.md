## Build

```sh
make prepare
pnpm build
make wailsv3-build tauriv2-build mygo-build
```

Before a bundle build, confirm that the current working directory is the intended verification checkout and that its output bundle is disposable. The debug and release build targets refuse before replacing `Contents` when a process is running from the exact output bundle, and report its PID and bundle path. Use a separate verification checkout for a build while a user application is running; do not override a build target to write into that application bundle.

`native/darwin` builds `libsoksak-darwin.a` and `soksak-darwin.pc` in `native/darwin/build/`. The Makefile adds that directory to `PKG_CONFIG_PATH`; Wails and Tauri locate the headers and link flags through pkg-config. Both native applications require macOS 14.4 because the capture code uses a ScreenCaptureKit API introduced in macOS 14.4 ([native/darwin](../spec/hosts.md#nativedarwin)). The Makefiles of `native/darwin` and of its process identity package build every part for arm64, the architecture of the release platform `darwin-arm64`: each clang call and the ZXing configure name it, so a make that runs as a translated process for another architecture builds no part for that architecture. ZXing is configured in a new build folder each time it is built, and it is built again when the Makefile changes, so no value that an earlier configure detected remains. The Makefile passes this minimum to Go through `CGO_CFLAGS` and `-extldflags`, and to Rust through `MACOSX_DEPLOYMENT_TARGET`. The release profile of the Rust workspace strips the release executable but not the proc-macro libraries and build scripts that it builds for the host (`[profile.release.build-override]` in `Cargo.toml`): no release carries them, and on macOS 27 dyld refuses a proc-macro library stripped for this deployment target, so rustc could not load it.

`make registry-install` runs `make install`, the installation stage, once in every plugin and sidecar repository that `scripts/workspace-registry.json` declares; a fresh local checkout runs it before it builds. `make registry` builds the workspace registry in `target/registry`: it builds the sidecars, packs every plugin that `scripts/workspace-registry.json` declares with its `make pack OUT=<folder>`, which writes the `pnpm pack` file of the plugin into the folder, releases the sidecars that their `plugin.json` names for the current platform, writes the registry files with the packs of that declaration, and runs `sok registry build`. `make registry SIDECARS=diagnostic` runs `make release PROFILE=release FEATURES=diagnostics` of each sidecar repository, so a Rust sidecar builds the release profile with its feature `diagnostics` and the files sidecar, a Go program without diagnostic code, builds as it always does, and writes beside the index `target/registry/sidecar-revisions.json`, `{ sidecars: [{ repository, revision, changes }] }` in the order of the declaration: the declared folder of each sidecar repository that it built, the revision of its `HEAD`, and whether its working tree held changes outside that revision, a tracked file that differs from it or an untracked file that is not ignored. The default run reads no Git metadata of the sidecar repositories and removes that record. `make registry SIDECARS=diagnostic PLUGINS=public` packs no plugin and builds no sidecar: it reads the index of the [public registry](../spec/registry.md) and writes `target/registry-public/index.json`, which lists its plugins, its packs and the revoked entries of the listed plugin versions beside the sidecar entries and releases that `make registry SIDECARS=diagnostic` wrote into `target/registry`, and it fails when `target/registry/sidecar-revisions.json` or a sidecar release is missing. A public plugin version whose sidecar ranges those sidecar releases do not satisfy is left out and printed, because the index check refuses it; the target fails when a left-out version that is not revoked is newer than a listed version of its plugin or when a plugin keeps no version, so an installation from that index selects, for every core version, the plugin version that the public registry selects or none. With `PLUGINS=public`, `REGISTRY` is `target/registry-public`, so `make install-plugins` installs from that index. `make install-plugins CONFIG=DIR` builds that registry, removes the plugins installed in `DIR`, and installs every plugin of the registry there; workspace plugins keep their version while they change, so a repeated install of the same version would leave the earlier files. `sok registry use target/registry/index.json --config-dir DIR` and `sok plugin install <id> --config-dir DIR` then install from it ([command line](../spec/cli.md#installing-plugins)).

Run the browser application with `pnpm example` and open `http://localhost:8749/index.html`. Run every package test with `pnpm test`.

The build targets build `native/darwin` and the workbench, then run `soksak-stage src/frontend` in each application. The tool stages the workbench, the layout library, the plugin API and the application's `runtime/` directory into the generated `apps/<app>/src/frontend/`. The bundles hold no plugin and no sidecar: the hosts serve the plugins installed in the configuration directory ([installation](../spec/installation.md#serving-installed-plugins)). Debug targets add `--diagnostics`, which stages the page diagnostic module (`diagnostics.js`); release targets stage an empty module. Both executables embed the frontend at build time. A running process does not acquire a newly built frontend; restart the corresponding application after building.

Debug executables are `target/debug/soksak-wailsv3.app`, `target/debug/soksak-tauriv2.app` and `target/debug/soksak-mygo.app`. Release builds use `make wailsv3-build-release tauriv2-build-release mygo-build-release` and write `target/release/wailsv3/soksak.app`, `target/release/tauriv2/soksak.app` and `target/release/mygo/soksak.app`. The release executables carry no symbol table: the Wails and mygo builds link with `-s -w`, and the root `Cargo.toml` release profile sets `strip = true`; `make release-check` therefore finds diagnostic code by strings that stripping keeps (diagnostic method names and the capture class name `SPCapture`). `make examples-size` builds both profiles and reports their sizes.

`make hosts-check` also vets the Wails host source for Windows (`windows-build-check`) and compiles the two hosts and the two apps for macOS in the configuration of the debug apps (`host-debug-check`).

Rust builds grow `target/` quickly (a debug build with the tests is tens of gigabytes). Run Cargo with `CARGO_INCREMENTAL=0`. Work that happens in a second checkout or worktree builds Rust in the `target/` folder of the main checkout, not in a folder of its own, because a folder of its own rebuilds every dependency; the crate of the host that the second checkout changed is then removed with `cargo clean -p soksak-host-tauriv2` after the last test and before the main checkout builds again, because the main checkout links the crate that the other checkout built when it does not (`cargo clean -p` only while no other `cargo` process runs). Remove build output that is not needed again (`target/debug/deps` files not used for a day, `native/darwin/build` of a worktree) after the verification, and keep the disk free space above the size of one full debug build. `target/test-runs/` keeps the runs of the test runner (see Test runner) until `node scripts/test-runs.mjs prune` removes the runs without a failure.

## Test parity

Run the structural inventory gate with `make parity-check`. It discovers Git-visible JS/TS, Rust, Go, Objective-C, native headers, HTML/CSS, shell scripts, contract declarations, and build manifests without fixed language roots. Generated library output and Tauri schemas have explicit exclusions; source/output equality remains a separate build check. Unclaimed implementation or test files, empty patterns, and duplicate ownership fail. Shared tests do not permit duplicate implementation ownership.

`make host-contract-check` runs every test of both hosts as a process of its own, in parallel, and compares the results with the [host contract cases](../spec/host-contract.md). The run builds each package first and names every build with its elapsed time. Then it writes `RUN`, `PASS`, `FAIL` or `TIME` with the elapsed time for each test, the tests in flight at an interval of 10 s, the slowest tests and the totals. Each test has a limit of 120 s, and a test over it is killed and fails the run. During development run a part: `node scripts/check-host-contract.mjs --go-ldflags=<flags> --run <text of a run id> --only <text of a test name>` builds only the runs whose id contains the first text and runs only the tests whose name contains the second, without the contract audit; an item is completed by its owning tests, not by the full run; `make native-test` runs it, and it first runs `make rust-format-check`, which fails when a Rust package of the root or `sidecars` workspace is not formatted by `rustfmt`, and `make go-format-check`, which fails and lists every tracked Go file that `gofmt` would change. The current inventory has 128 lanes, 879 implementation files, and 1334 test files. The current mapping is incomplete. A structural pass would not establish behavior parity: named behavior mappings, actual per-language execution, and matching-build evidence remain required by the [verification contract](../spec/verification.md). Do not expand unrelated globs or exclude discovered files to obtain a pass.

`pnpm test` runs `scripts/node-tests.mjs`, which reads the `test` script of every workspace package (`test:scripts` for the root), runs the commands that precede `node --test` (such as `pnpm build`) one at a time, and then runs each test file as a process of its own through the test runner: it writes `RUN`, `PASS`, `FAIL` or `TIME` with the elapsed time for each file, the files in flight at an interval, the slowest files and the totals, and `--only <text>` runs the files whose path contains the text. `--changed <range>` runs the files of the packages that hold a file that `git diff --name-only <range>` lists and of the packages whose `package.json` declares that file in `specFiles`, the files of `docs/spec` that the sources of the package read (a path that ends in `/` names a folder). The root package holds `docs/spec`, so a changed specification file also selects the root tests. `make boundaries` fails when a JavaScript source of a workspace package other than the root reads a file of `docs/spec` that `specFiles` of its package does not declare, and when `specFiles` names a path that does not exist or that no source of the package reads; a read is a string literal with `../` that resolves from the folder of the source into `docs/spec`, as `new URL(path, import.meta.url)` resolves it. Each test of a file has a limit of 120 s: the harness passes it to `node --test` as `--test-timeout`, and a test that declares its own `timeout` keeps that value. A file has no limit of its own. The harness does not pass `--test-force-exit`, because `process.exit` drops the reports still queued on the asynchronous pipes of macOS: the file process ends by itself when its tests end, and a file that keeps a handle open after its tests ended is failed by the exit limit. The event watchdog and the exit limit are the only bounds of a file. The event watchdog ends a file only when its test events stop: `scripts/test-event-reporter.mjs` writes one line per test event on the standard error, the runner re-arms a deadline of `MAX_TEST_TIMEOUT_MS` (600 s, passed to the runner as `eventLimitMs`) at each event and at the start of the file, and when the deadline passes the runner stops the file's process group and fails the file with `no test event for <ms> ms, the largest limit of a test; last event: <type> <name>`. A file whose events keep arriving is not ended, whatever its total duration. The exit limit ends a file whose process does not exit after its tests ended: the runner arms a deadline of 20 s (`exitLimitMs`) at each `test:summary` event, the last event of the tests of a file, and any later event re-arms the event watchdog; when the deadline passes, the runner writes the thread stacks of each running process of the group with `sample` to `<output>.exit-<pid>.sample.txt` in the folder of the run, ends the group and fails the file with `the file process did not exit within <s>s after its tests ended; last event: test:summary; samples: <paths>`, followed by `; sample errors: <errors>` when a sample fails. A process that does not exit then waits in its shutdown, which a deadlock of the Node.js runtime at exit causes; the files of `scripts/test` exit at most 155 ms after the summary. The events of a test that blocks the event loop are not delivered while it blocks, so the failure names the last event that arrived, which is the event before the blocked test. A global setup has its own limit in an in-process timer: `withSetupLimit` in `packages/window-check/session.mjs` rejects with `global setup <name> exceeded its limit of <ms> ms`, and the core setup (`e2e/setup.mjs`, 300 s) and the window-check session start (`SESSION_SETUP_LIMIT_MS`, 120 s) use it. A synchronous call in a setup, such as the `cargo metadata` read, is not interrupted by that timer, so the event watchdog of the file ends it. A process that a file leaves running is ended with the file: when the file's process exits, the runner stops the rest of its process group (SIGSTOP), lists it, ends it (SIGKILL) and fails the file with `left running after exit: pid <n> <command>`. The list reads `ps` only for the members of the group, because the commands of every process of the system can exceed the output buffer of the read, and the kill follows the list even when the list fails, so a failed list fails the file with its error and never leaves the group stopped. A file whose process ends while a test runs fails with the tests that have no result: node --test reports the results of the earlier tests and no result, error or cancellation for the running test, and its exit status is 0 when no earlier test failed, so the runner pairs the `test:dequeue` and `test:complete` events of each test by its `nesting` and name and fails a file that ends with a test dequeued and not complete with `the test process ended by <exit n | signal name> while a test ran; started without a result: <names>`, followed by `; queued without a start: <names>` for the tests enqueued and not dequeued. The exit code and the signal are those that node --test sets on the result of the file (`exitCode`, `signal`), which the event reporter passes on, so a file process that a crash ends is named with its signal, such as `SIGSEGV`. A command with a declared `timeoutMs`, such as a build step, is ended at that limit in the same way, and its `TIME` line names the processes of its group that remain as `left running: pid <n> <command>`. An item that declares `stackSignal` receives that signal at its limit before its group is ended: the runner ends the group at the exit of the process, or `STACK_LIMIT_MS` (10 s) after the signal with `; it did not exit within 10.000s and was killed`, and its `TIME` line reads `exceeded <s>s and was sent <signal> for its stacks`. Each Go test of `make go-repeat` and `make host-contract-check` declares SIGQUIT, on which the Go runtime writes the stacks of every goroutine and exits, so the output of a Go test over its limit names where each goroutine waits. macOS refuses a group signal with EPERM when only zombies remain in the group; the runner treats that refusal as an ended group, and it fails with the error only when a running member is named in the error. A package `test` script that is run with `pnpm -F <package> test` outside the runner has no limit; `pnpm test` runs every package script through the runner. Each file reports in the spec form on the standard output and in the TAP form on the standard error, because the spec form writes the errors of failed tests at the end of the file and the TAP form writes each error when its test ends, so a file that is killed keeps the errors of the tests that failed before. A package that owns native tests exposes them to workspace discovery through a `node --test` entrypoint; each Node test delegates to one declared native test target, whose native runner preserves per-test progress, limits and failure output instead of copying native assertions. `make e2e` runs the window checks the same way, one file at a time because they share the applications, with a limit of 600 s for each test that declares no timeout. `--when-idle <seconds>` starts a file only after the person gave no keyboard or pointer input for that long (the line `WAIT <file>` names the wait, which is not part of the limit), because a check of an application action that activates a window takes the focus of the person and the person's input refuses its synthetic input: `make e2e WHEN_IDLE=60`. Each run has an identifier (`SOKSAK_RUN_ID` for every test, and `SOKSAK_RUN_FOLDER` for the folder) and a folder `target/test-runs/<run>/` that holds the output of every test, stored as it arrives, and `manifest.json` with the status, start and end (microseconds) of each test; `node scripts/test-runs.mjs prune` removes the runs without a failure and the runs whose failures `classified.json` (an array of `{name, record}`) names, and keeps every other run. The package scripts stay valid for a single package. The audit/checklist/command-supervision self-tests are the files of `scripts/test`. The two Rust terminal packages invoke their actual Cargo tests; package-command tests replace Cargo with a failing fixture to verify invocation and failure propagation, not engine behavior.

The wait of `--when-idle` reads the idle time of the input every 5 s (`HIDIdleTime` of `IOHIDSystem`) because no examined event source serves the gate. Each source reports the input itself, which the gate would have to turn into an idle time, and each needs either a permission that an unattended run cannot grant or a state that is not a number of seconds:

- A listen-only `CGEventTap` on the session (`kCGSessionEventTap`) needs the Input Monitoring permission of the process (`CGPreflightListenEventAccess`, `CGRequestListenEventAccess`). macOS asks the person once for the process that runs the tap, which for a helper started by a node script is the terminal or the runner that started it, and the grant is made in System Settings. A check run that has not been granted the permission receives no event, and the request opens a dialog that waits for a person, so a gate that waits on it can neither pass nor fail on its own.
- `IOHIDManager` opened on the keyboard and pointer devices needs the same Input Monitoring permission (`IOHIDCheckAccess`, `IOHIDRequestAccess` with `kIOHIDRequestTypeListenEvent`) and reports reports of each device, so it has the same dependence on a grant.
- `NSEvent` global monitors (`addGlobalMonitorForEventsMatchingMask:`) report mouse events without a permission but report key events only when the process is trusted for Accessibility (`AXIsProcessTrusted`). They also need a running application and its run loop, so a node script would need a native helper executable, and a gate that sees only the pointer would start a check while the person types.
- `IOServiceAddInterestNotification` on `IOHIDSystem` and the notifications of the display and the session (screen lock, display sleep) report no input. The power management reports the activity of the user as its own level (`IOPMLibPrivate.h`, a private interface), which follows the idle policy of the power management and not a number of seconds, so `--when-idle <seconds>` cannot be expressed with it.
- `CGEventSourceSecondsSinceLastEventType` reads the same value as `HIDIdleTime` without a permission and without starting `ioreg`, but it is a read and not an event.

The gate therefore keeps the read of the idle time, which needs no permission, and the interval of 5 s bounds the delay between the end of the input of the person and the start of a file. A gate that uses an event source needs the permission granted to the process that runs the checks; it is added when the runner has that grant.

A bounded command can be run with:

node scripts/test-command.mjs --id inventory --timeout-ms 10000 -- node scripts/check-test-parity.mjs

The supervisor streams stdout/stderr and emits JSON start/progress/final events with elapsed milliseconds. It reports nonzero exits, missing executables, timeout, cancellation, and cleanup errors. A permission-denied cleanup probe is not proof of process absence: macOS answers `kill(-pgid, sig)` with EPERM when no member of an existing group may receive the signal, which includes a group whose members have all exited and wait as zombies until their parent reaps them. After such a refusal the supervisor reads the group's members from the process table (`ps -A -o pid=,pgid=,stat=`), records them in the `verify` cleanup observation, and counts the group as cleaned only when no member is listed or every listed member is a zombie (state `Z`); a running member keeps the cleanup failing with the EPERM error. This supervises one command process group; language adapters still need case discovery, per-case execution, zero-test/skip rejection, and source/binary evidence. It does not close independently running inspection applications.

Run the four-language adapter gate with `make language-test`. It emits case-level expected/actual test counts and evidence hashes for the declared JS/TS, Rust, Go, and Objective-C cases. To retain failures across a retry, provide a file outside the repository: `node scripts/language-test-adapters.mjs --evidence-file "$TMPDIR/soksak-language-evidence.json" scripts/language-test-cases.json`. The next run appends an attempt only when the source, test, dependency, dirty-worktree, build-flag, and process snapshots are unchanged; otherwise it fails as stale evidence.

`make node-repeat FILE=<test> NAME=<pattern> COUNT=<n>` reports the run number and streams child test stdout/stderr while executing, stopping on the first failure. Output forwarding must preserve the child failure status, and a run without a matching passed test fails.

The release of core reads no registry: the registry lists a core release in its `core.json`, and the registry checks, for every core version that it lists, the plugin version that installation selects for it ([public registry](../spec/registry.md)). Release verification requires the exact bundle paths: `node scripts/check-release.mjs --wailsv3-bundle PATH --tauriv2-bundle PATH`. Both options are required; unknown options, duplicate options and missing values fail before inspecting files. `make release-check` supplies `WAILS_RELEASE_BUNDLE` and `TAURI_RELEASE_BUNDLE` to this command. Override those build variables to prepare separate bundles without modifying a running bundle; the checker must inspect the same specified paths. The checker reads every executable in each bundle's `Contents/MacOS` and never reads the staged frontend. Both applications embed the frontend uncompressed (Wails `go:embed`; Tauri without its `compression` feature), so the application executable must contain every file published by the workbench and `release-diagnostics.js` verbatim; otherwise the checker reports that the frontend is not readable. It then rejects plugin diagnostic entry names and diagnostic module sources found in the executable. The workbench and plugins are resolved through the application's `package.json` dependencies.

## Temporary folders

A check removes every folder and file that it writes to the temporary folder, also when it fails: Go tests use `t.TempDir`, Rust tests the reporting folder guard `tests/support/folder.rs`, Node tests remove their folders in `t.after` with `fs.rmSync`, which throws when the removal fails, and Objective-C checks create their folders with `temporaryFolder` of `native/darwin/tests/support/temporary_folder.h`, which removes them when the process returns from `main` or calls `exit` and fails the process when a removal fails. `temporaryFolder` reads `TMPDIR`, because `NSTemporaryDirectory` returns the temporary folder of the user and ignores `TMPDIR`.

`make temp-audit COMMAND="<command>"` (`scripts/temp-audit.mjs`) runs the command with `TMPDIR` set to a new empty folder, names each entry with the prefix `soksak-` that the command left there (`TEMP LEFT <path>`), and fails when there is one or when the command fails; it removes its folder when it ends. The configuration folders of the window checks, `soksak-check-*`, are not counted, because they live across runs by design. A folder that a check writes outside `TMPDIR`, such as a fixed path under `/tmp`, is not seen by the audit.

## View drag benchmark

Use `make e2e-benchmark-plain-view` to measure the floor of a view drag: it installs the fixture of `e2e/fixtures/plain-view/probe`, a view with an empty document region and no plugin code, runs the same width drag and recording, and reports the in-gesture source intervals. It judges no target, because the floor is an input of the targets. It also runs a drag with traces disabled and reports its latency, convergence, load and transaction stages.

Build local optimized diagnostic candidates with `make DIAGNOSTIC_RELEASE=1 wailsv3-build-release tauriv2-build-release` and build each installed sidecar with its release profile and diagnostic feature. Record the exact executable hashes and source revisions before running the benchmark; local compilation does not publish a release. Preserve earlier debug-profile measurements as separate observations because the Rust development profile leaves the host crate unoptimized.

With the disposable diagnostic hosts already running, use `make e2e-benchmark-view-drag` with the same run metadata and binary/configuration declarations as the window checks. Leave `SOKSAK_PERFORMANCE_TRACE` and `SOKSAK_VT_TRACE_DIR` unset in both hosts and the check process. The benchmark verifies disabled performance tracing, null terminal renderer metadata and the default error-only log policy. It records the complete synthetic drag without activating either host; diagnostic recording remains enabled because the performance contract measures captured frames.

The benchmark runs three drags in the order of B3: a drag without capture through `diagnostics.drag` with `native: true` and the plan of the captured drag, the captured drag, and, after `frames` of `host.window` has not changed for 3 seconds, a drag without capture under the policy that stores the class `frame` at `debug`, whose U7 records it reads on a window without a main page. It reads the CPU time and the peak footprint of each process of the application before and after the first drag. `ACCESSIBILITY=1` reads the elements of the window through the accessibility API before the drags and needs the Accessibility permission. `FLOOR=1` installs the fixture plugin `floorpage` from a registry of its own and drags the terminal card with its view, a page that draws one colour and runs no plugin code. `GC_LOOP=1` turns `diagnostics.gc.loop` on around the third drag, on a window without a main page. `B3_OUT=FILE TRACE=0|frame-records` writes the B3 output of that state. `make e2e-benchmark-resize-catch-up` takes `B3_OUT` and `TRACE=captured|frame-records` the same way: `captured` is the state of its captured maximise and restore, under the settings that its layout stages need. Each state applies its settings of `B3_SETTINGS` in `e2e/benchmark/measurements.mjs` and fails when the window runs with others, and `make e2e-benchmark-idle-tab` and `make e2e-benchmark-split-load` take `B3_OUT` alone.

Recorded drag already collects native transaction timestamps independently of the performance and renderer trace settings. The benchmark preserves these original rows in `layouts.json` before analysis and includes their cadence summaries in `result.json`. The `committing` interval runs from DOM presentation to transaction commit; `total` runs from native preparation start to commit. Missing stages remain null, and invalid or reversed timestamps fail explicitly.

Each host writes `logs/view-drag-benchmark-*/result.json` before judging the unchanged cadence and refresh-rate latency targets. The report includes every decoded-frame timestamp, measured card position, input tick, layout boundary, unmeasured-frame index, system load and tracing mode. Missing frames, incomplete movement and invalid data fail independently of slow but valid measurements. Failed target measurements retain their recordings and report; a passing functional geometry check is not a benchmark pass.

Run `SOKSAK_NATIVE_TEST_RUN_FOLDER=<unique-dir> make -C native/darwin benchmark-webview-resize-cadence` to isolate root-view ResizeObserver-to-next-requestAnimationFrame delivery from host layout and plugin work. The inactive native fixture observes its initial 300×200 source row before applying 48 one-point width increments. It preserves the baseline, every native setter interval, predicted display-link timestamps, actual setter clocks and source rows. Only intervals between pulse response rows use the unchanged 33 ms gate; baseline idle time and first-pulse response latency are not judged. This is a dedicated performance reproduction target, outside the default native suite. It neither records rendered pixels nor establishes application drag, initial-response or convergence acceptance. Keep its runner manifest and executable output, including failed measurements.

## Input latency

Use `make input-latency` to measure the time from a key to the prompt in a `terminal` tab and a `term` tab of an application that is already open. Start the application with `--config-dir <folder>` and run the target with `SOKSAK_CONFIG_DIR=<folder>`. `APP` names the application, by default `mygo`. The output of the check, in the folder of the run under `target/test-runs`, holds the median, the 90th percentile and the time of each key for each configuration of the trace and the log gate. `B3_OUT=<file>` writes the values of the trace off and the default gate to the file.

## Test kinds

A test is a unit test or an end-to-end check. An end-to-end check needs one of three things that a CI runner does not provide: a running application (the window checks of `e2e/`, including `e2e/activation/`, `e2e/person/`, `e2e/real/` and `e2e/observation/`), a display that presents frames (`NATIVE_E2E_TESTS` of `native/darwin/Makefile`, `make -C native/darwin e2e`), or a person or the activation of the application (the activation tier `make e2e-activation`, the real-input tier `make e2e-real` and the person-operated checks `make e2e-person`). The Go tests that need a display or the activation of a process carry the build constraint `e2e` and a name that starts with `TestE2E`, and `make e2e-host-go` runs them. Every other test is a unit test: the Node tests that `scripts/node-tests.mjs` runs, including the tests of the harness itself (`e2e/test/`, `packages/window-check/test/`), the host tests, `NATIVE_TESTS` and the process identity tests.

The CI and release jobs of a repository run only its unit tests and its structure checks, and check out no other repository of the workspace. The end-to-end checks run only locally, on a computer with a display, through make. The name of a make target decides the kind of its checks: a target whose name starts with `e2e` runs end-to-end checks, and `test` and every other test target run unit tests only; `scripts/test/test-kinds.test.mjs` checks the targets, the test script of `@soksak/e2e` (`node --test test/`, the unit tests of the window-check helpers) and that no workflow names an `e2e` target or a window-check script.

## Window checks

`make e2e-check` audits unresolved activation-fixture names through the installed TypeScript compiler API, filtering TS2304, TS18004 and TS2552 for the view sources. Unrelated semantic type diagnostics do not stop that lexical audit. Compiler configuration, global and syntax errors remain explicit failures; diagnostics without valid source metadata are rejected, and external-library exclusion requires compiler metadata. Compiler-session and temporary-configuration cleanup errors are reported together with analysis errors. This source check sends no input and activates no application.

The focused `HWP startup resource timing snapshot is preserved` cases in `e2e/hwp.test.mjs` open one document per inactive host through `core.card.add-tab` and call the declared diagnostic frame start/read/stop commands. Each response and the read native-clock bracket is written immediately to the run folder, including partial replies and cleanup failures. The lifecycle info policy stores the declared phase reads. Resource entries contain only the browser snapshot still available at read time; absent entries do not prove absent fetches, and fetch durations do not measure WASM compilation. A successful query does not override error-audit or cleanup failure.

The focused `e2e/view-restart.test.mjs` case ends the exposed browser view process four times, records each complete fault/recovery phase, verifies the saved address, callable reload command and visible view/document placement after each replacement, and checks the fourth-failure stop reason. It hides and unloads that same tab, then opens it again and requires restored state without the stopped error. It declares only the deliberate process-end diagnostics and the fourth-failure display, checks their exact counts, and leaves unexpected registration or lifecycle errors failing the run. It uses the normal running diagnostic hosts and run metadata.

The view display check enumerates installed enabled view plugins from `core.plugins`, including plugins with no open tab. It identifies the surface by the tab returned by `core.card.add-tab`, checks its document, and measures only its applied surface rectangle using the capture content offset and scale. Colour variation in that rectangle is a blank-area check, not evidence of the first content frame of that plugin.

View display acceptance requires an explicit content case for each installed view plugin. A missing case fails with the plugin and the actual opened tab. Colour variation in the applied surface area provides an area observation only and does not prove first content. Rejecting a missing content case removes a false pass without lowering the acceptance criterion.

The macOS window-check setup resolves the workspace from cargo metadata, builds the content recognizer through `capture-text-path` of the native Makefile and sets `SOKSAK_CAPTURE_TEXT`. An explicit `SOKSAK_CAPTURE_TEXT` selects an already-built executable. Select `e2e/view-display.test.mjs` for the content cohort. The executable uses public Vision recognition on BGRA crops and supports a maximum crop of 64 MiB. Its default invocation tests drawn text and unsupported-language refusal. Each crop is written to a unique OS temporary directory for one recognition call, then removed after success or failure; a cleanup error is reported with the recognition error. The window check retains source recording frames and OCR evidence, not crop scratch files. It rejects a missing content case, a readiness-only case, missing finalized frame files, invalid crop geometry and absent expected text.

To observe a terminal click in the current layout, run `SOKSAK_CONFIG_ROOT=<root> make e2e-terminal-focus-current`. The check requires a visible terminal view, records the native click without activating either application, and requires a visible view document, a new trusted pointer event and the matching native first responder. It preserves the layout and checks that every recorded frame decodes, the recording is not limited, and frame gaps are at most 33 ms. This check does not type characters; character input is checked in the activation tier. Failed recordings are retained automatically for diagnosis.

The E2E runner requires nonempty `SOKSAK_RUN_ID` and `SOKSAK_RUN_FOLDER` values together before it starts a test child. It passes both values unchanged; missing or partial metadata fails before a child starts. Each check marks its start and end in the application's event log (`diagnostics.test.mark`, [test marks](../spec/logging.md#test-marks)) and appends each mark's `(boot, seq)` position to `marks.jsonl` in the run folder. `make e2e` and `make e2e-activation` run through this runner and finish by auditing every event file named by the marks (`node scripts/audit-run.mjs <run folder>`, [checking](../spec/logging.md#checking)); a finding fails the run. The audit also writes `judgment.json` with each test's verdict by its log range. Run activation checks through the root `pnpm verify:activation` command so the required run metadata and audit are present; invoking the package script directly without run metadata is rejected.
The fixed-sidebar window checks restore temporary explicit card-sidebar selections before disconnecting, including after preparation fails. An explicit card `off` takes precedence over plugin defaults; use the declared `core.card.sidebar.set` command with `set: "inherit"` to clear that selection while retaining size and fold choices. To observe an existing normal window without replacing its project or settings, run `SOKSAK_APP=tauriv2 SOKSAK_CONFIG_DIR=<config-dir> make e2e-terminal-sidebar-current`. This check requires an active terminal card and a saved terminal `card-right` assignment, records normal/fullscreen/restored presentation, and retains the original tabs and settings. It does not create a fixture or repair a disabled selection.

### End-to-end run

Keep the display on and run `make e2e`. `make e2e-section-design` leaves stills of the files and browser sections of the applications in light and dark modes in `target/section-design` for inspection at original resolution. Each e2e target (`e2e`, `e2e-activation`, `e2e-real`, `e2e-person`) builds the three debug applications and the workspace registry and runs `scripts/e2e-run.mjs` with the window-check script of its tier and the native end-to-end target of that tier:

1. It makes a new configuration root `target/e2e/<time>-<random>` for the run.
2. It creates the registry certificates in that root (`make e2e-registry-tls`) and installs the plugins of the workspace registry into `soksak-check-wailsv3`, `soksak-check-tauriv2` and `soksak-check-mygo` of that root (`make install-plugins`).
3. It starts the applications with `--config-dir` and `--registry-ca` of that root, writes their output to `<root>/<app>.out`, and waits for each `endpoint.json` with a file watch, at most 60 s.
4. It runs the window checks of the tier (`node scripts/node-tests.mjs --script <script>`), which audits the run, and then the native end-to-end target of the tier.
5. It quits each started application with the declared `host.quit` command and waits for its exit, at most 60 s; an application that ends with another status fails the step, and the system crash reports that the application left since the start of the run are printed with their fault (`scripts/crash-fault.mjs`). The step then waits, within the same limit, until no process holds `<config-dir>/process.lock` ([endpoint](../spec/endpoint.md)): `diagnostics.host.relaunch` replaces the started application with a new process, which the run did not start; `lockf(1)` takes the lock and returns when its owner exits.
6. It fails when a process whose command names the root or an application bundle remains.

Each step prints `running`, then `passed` or `failed` with its elapsed time. A failed preparation skips the checks and runs the steps of the end; a SIGTERM, SIGINT or SIGHUP ends the running step with SIGTERM, skips the later checks with `interrupted by <signal>` and runs the steps of the end, so an interrupted run ends its applications and services and fails; a request whose document does not reply within its limit is followed by one probe, and when the probe gets no reply either the harness writes `unresponsive.json` into the configuration folder of that application, and every later request and check of that application fails at once with the check, the request and the stall dumps of that record; a failed check skips no other check. A passed run removes its root, and a failed run keeps it with the application logs and prints its path; a failed run removes the `services` folder of each application, so the persistent services of a host that ended without `host.quit` exit ([persistent services](../spec/persistent-services.md)), so every run starts from a new root and a second run of the same source gives the same result. `make e2e WHEN_IDLE=<seconds>` starts each window-check file only after the person gave no input for that long.

`make e2e-registry-tls` creates a test-owned certificate authority and a server certificate for `127.0.0.1` in the root; `e2e/registry.test.mjs` serves the workspace registry over https with them, and the diagnostic `--registry-ca` lets the applications trust that authority ([application arguments](../spec/hosts.md#application-arguments)).

The harness is the package `@soksak/window-check` (`packages/window-check`), which other repositories pin to run their own window checks. It takes the executable of each application from the environment variables `SOKSAK_BINARY_WAILSV3`, `SOKSAK_BINARY_TAURIV2` and `SOKSAK_BINARY_MYGO` and fails with the variable name when a checked application has none; core's entry points run `e2e/setup.mjs` as the node:test global setup, which declares the debug bundles of the cargo target directory that `cargo metadata` reports (so `CARGO_TARGET_DIR` applies) unless the run already declares them. Core's checks start from `fresh` in `e2e/fixture.mjs`, which prepares the fixture through the harness's `prepareFixture` and waits for its terminal. The default log policy stores only `error` ([policy](../spec/logging.md#policy)), so a check that reads records below `error` declares the policy it needs (`log`, the value of the setting `diagnostics.log`) and the records it reads (`reads`); `prepareFixture` refuses a declaration whose policy does not store a record that the check reads, refuses the policy given as the setting, stores the class `call` at least at `debug` while the performance trace is on, and waits until `<config-dir>/log-policy.json` holds the policy. A wait on the event files (`untilEventLines`, `untilEventLine`) names the records that its predicate reads and fails at once with an error that names the record and the policy when the policy file does not store it, instead of waiting until its deadline. The harness (`packages/window-check/app.mjs`) connects through `<config-dir>/endpoint.json` with `@soksak/client` ([local endpoint](../spec/endpoint.md)). It checks that `application` names the expected host and that `executable` is the executable of this checkout. A lock file `soksak-check.lock` in the temporary directory prevents two concurrent runs; a second run fails without measuring. Tests never start applications. They read and change state only through declared entries ([exposure](../spec/exposure.md)): status values, commands, element entries, host entries, and the diagnostic methods of debug builds. Waits use `status.watch` notifications and `host.window.presented`; the harness has no polling loops or fixed delays. Real input checks use `input.pointer` and `input.key`, which do not activate the application. `input.key` builds every key without explicit text, named keys included, from its macOS key code, so AppKit and the input method compute its characters as for hardware input; a check that types Latin text therefore selects the ABC layout with `session.selectInputSource`. The session tree captures the original source on its first call and restores it once, after the pasteboard restoration. `make e2e-check` rejects timers, `eval`, the `Function` constructor, the removed native probe, and the removed TCP control port in `e2e/`. A missing running application fails the check. The required set is the application that `SOKSAK_APP` names, or every application of `APP_NAMES` when it is unset (`requiredApps` in `app.mjs`); an application of the set whose executable does not exist fails `open` with an error that names the executable, and an application outside the set is not opened. A check that compares the hosts with each other runs when `requiresAll` holds, that is when the required set holds every application of `APP_NAMES`, and it compares every application of `Object.values(APPS)`. A check whose subject is the main page or a modal web view iterates `MAIN_PAGE_APPS`, the applications that have a main page; `scripts/check-e2e-host-parity.mjs` fails on a window check that iterates anything other than `Object.values(APPS)` or `MAIN_PAGE_APPS`. A run with skipped host tests does not validate every host.

`make e2e` also runs `make e2e-check`, `make exposure-check` and the documentation check before the run. The build refuses to change a bundle from which an application runs, so an application of the user that runs from the debug bundle stops the run before its first step.

Use disposable configuration directories: the harness replaces their project list and common settings and creates a `test-project` folder with test-only overrides. A new configuration directory gets the plugins of the workspace with `make install-plugins CONFIG=<directory>` before its application starts; without them the start is a [first run](../spec/installation.md#first-run), which sets the public registry, and a diagnostic build started with `--registry-ca` trusts only the authority of the check, so the first run installs nothing. Project-window checks create additional temporary project folders and exercise the normal file and window APIs. `fresh` places the Wails check window at the top left and the Tauri check window at the top right of the main screen's visible area with `host.window.move`, which does not activate either application, so every check starts from the same window frames (`placement.test.mjs`); on a screen narrower than both windows their middles overlap. Windows of another application can still cover a check window, which the drag checks report.

Before each check, the harness saves every item type of the general pasteboard; after the check's other cleanup it writes them back and fails the check when the pasteboard then differs from before the check. A rejected `input.pointer` error names its phase, button, position and window. For each synthetic press whose release was not delivered, the cleanup waits until `host.buttons` reports mask 0, sends the release, and prints a `released open press:` diagnostic with the time it waited. Every cleanup step runs even when an earlier one fails, and each failure is printed as a `cleanup failed:` diagnostic as well as failing the check, because `node:test` does not print an error of an `after` hook when the test body has already failed. After the cleanup the harness reads the events of level `error` in every `logs/host-<boot>.jsonl` ([event log](../spec/logging.md#files)) from the end of each host event log that existed when the check started (`sessionEventStart`, the position `{offset, inode}` of each file), and reads a file that the writer rotated on from the generation that holds that inode, prints them as `error <layer> <event>: <fields>`, and fails when a folder holds no host event log. It prints each recorded error as an `application error:` diagnostic and fails the check when one of them does not match a pattern that the check declared with `expectError(pattern)` because the check causes it on purpose. The errors of a check are the errors written between its start mark and its end mark, and the harness keeps no position between checks. An error written after one check's end mark and before the next check's start mark is read by neither check; the audit of the run reports it as a finding, which fails the run ([checking](../spec/logging.md#checking)). A check judges each error written during it, including an error that an operation of an earlier check caused, because the harness does not match an error to the operation that caused it. It also closes other windows, restores the 1200×760 start size, runs `diagnostics.fixture`, reloads the main document with `host.window.reload`, waits until every visible terminal surface has registered `core.surface.document`, `terminal.session` and `terminal.view` with its theme applied, and confirms presentation. `diagnostics.drag` supplies drag steps from the host at 16ms intervals; with `capture: true` the host records the window from before the first step until the gesture has been presented, and the harness stops the capture with `diagnostics.capture.stop`, passing the `displayed` time from `host.window.presented` so the recording includes the presented screen. `diagnostics.capture.start` records around any other request; with `display: true` it records this application's windows on the window's display, which keeps recording when a window moves to a full-screen Space. Each frame file stores, before the BGRA pixels, the rectangle the window occupies in the buffer, the content scale, the backing scale, and the display time; a window larger than the buffer is scaled into it. When frames are not written, the capture reports the count of blank and suspended frames. The capture copies each frame in its sample handler and losslessly compresses its complete pixel buffer with LZ4 RAW on the separate writer queue before writing it. The callback rejects an exhausted 64-frame pending-write capacity without blocking; the recording fails explicitly and stop preserves earlier and stop errors. The separate 600-frame burst cap remains reported; `diagnostics.capture.stop` returns `longestGap`, and a drag recording with a gap over 100ms between frames fails because part of the gesture was not recorded. A drag that runs outside 1/1.25–1.25 of the requested duration is repeated once and then fails. A test rejects an incomplete gesture, too few frames, or too few measurable frames.

Each stopped recording has `callback-status.jsonl`, also named by `callbackStatus` in the stop reply. It records every ScreenCaptureKit callback in order with its status, exact mach display time, delegate-entry `callbackTime`, synchronous frame-processing `writeStartTime` and `writeCompleteTime`, the `mach_timebase_info` numerator and denominator, and the exact relative frame filename written for that callback; a missing metadata value is `null`. The three processing times are decimal strings in one raw mach clock domain. Synchronous processing ends after validation, buffer copy and writer-queue submission; it excludes asynchronous compression and file writing. The actual timebase pair converts a raw delta to seconds as `delta * numerator / denominator / 1e9`; no frame timestamp conversion is inferred. A callback that did not write a frame has `frame: null`. The filename directly associates a callback with its frame. The trace holds at most 4096 callbacks, and exceeding the bound fails the recording. A complete-frame display gap can therefore be compared with callback arrival and processing intervals and with idle or other incomplete callbacks in the same recording.

Recordings of a passing check are temporary and are removed only after every cleanup and the application error audit succeed. `s.record(params)` starts a recording and returns its `frames` folder and a `stop(options)` that sends `diagnostics.capture.stop` once; a failed stop is not sent again, because the host may have ended the recording before the failure. The session cleanup sends stop only when none was sent. A capture whose stop or artifact validation fails also fails the check, even when the caller catches the error, and its folder is preserved. The harness lists the folders under `<config-dir>/logs/captures` when the session opens; after cleanup it compares canonical filesystem identities for tracked frame paths, failed recordings and folders, and resolves only folders that remain. It then reports any new untracked folder, fails the check, and preserves that folder as evidence. Failed recordings are retained automatically; no environment variable is required. A failure message reports measurements and frame numbers only; the harness writes no images.

The card fullscreen window checks cover the card icon, fullscreen/restore geometry, retained surfaces and settings application in both states. Automatic/sidebar space conditions belong to `card-sidebar-space.test.mjs` and the [card-sidebar contract](../spec/example-model.md). Assigning large sidebars folds an insufficient axis instead of creating an empty slot. The compositor owner test covers independently controlled zero-width and zero-height slots, hiding them without disposal and restoring visibility when their area returns.

The space-condition check retains all configured external window columns. A manual fold need not release enough width to expand the opposite side: its expected state follows the measured card space including borders. Check insufficient normal space, an explicitly wider normal window that allows expansion, fullscreen, and short restoration while preserving the saved manual choice.

The four-side assignment check separates saved assignments from effective automatic folding. On a short normal card, top/bottom may be folded while all four sets remain assigned. Different-plugin tab selection must preserve assigned sets and complete card geometry. Manual fold checks use requestedCollapsed and saved state rather than an already automatically folded appearance.

The linked-default check verifies requested fold state, stored fold/size results and the absence of an explicit set after each command. An automatically folded appearance does not prove a manual request changed. Fault-injection tests at the window-check owner must reject a no-op fold and a command that converts a derived set to an explicit assignment.

Window-sidebar persistence checks record independent window/card link changes, column widths, edge hiding/restoration and a saved-project document reload. Compare stable owner records and assignments with actual section output, DOM/native rectangles and final recorded pixels. This acceptance is separate from structural ownership and complete border-transition gesture checks.

The card-sidebar gesture checker rejects every frame without its expected border. Its error includes frame index/count, capture geometry/scales/time, sampled colors, matching border positions along the full axis and the initial/drag/release presented pose timeline, and layout-transaction start/DOM-presentation/native-commit times returned by recording start/stop. These diagnostics locate a failing frame; they do not replace complete-gesture acceptance.

The native capture acceptance requires both a positive recorded-frame count and no stop error. The owning checker fault test executes the actual acceptance body with a positive count and a controlled stop error; it must reject that result. A recorded frame does not prove that capture completed successfully.

The owning capture_lifecycle_test executes the same strict acceptance with pass-through SCStream start/stop callbacks and delegate-stop observation. It reports callback sequence, monotonic elapsed time, stream identity, error domain/code/message and point-in-time frame counters without changing callback results. Use its tracked repeat target for a real stop failure; passing observations do not diagnose an earlier unobserved failure.

The owning capture_pressure_test also checks still-result isolation with a written first frame: null-path and asynchronous missing-window failures must preserve recording errors and healthy readiness. It rejects invalid UTF-8 paths and holds the public still-query completion past the real 10000ms timeout before delivering the late failure. The returned timeout remains caller-owned, the later recording error remains unchanged and the callback error is logged. Run its tracked native repeat target after changing either recording or still error boundaries.

The owning capture_preparation_test holds public query completions through the actual 10000ms deadline, then delivers real-content success or an explicit callback failure. It verifies obsolete inactive target/config deallocation, caller-owned timeout, and unchanged later target and recording error. A separate on-time completion activates a recording immediately before publication and requires rejection without state changes. Each run has a 35000ms failure deadline and reports phase starts and elapsed results; use make -C native/darwin repeat TEST=capture_preparation_test COUNT=3 after changing preparation ownership or publication.

The owning capture_cleanup_test controls file open, write, close, commit and removal results while running the actual sample writer. It checks original system-error preservation, additional removal errors with retained paths, pre-existing file preservation after failed open, first-frame/count rejection, capacity restoration, and healthy commit/cleanup. It creates real partial files, removes all fixtures, reports each phase, and has its own 5000ms failure deadline. Run make -C native/darwin repeat TEST=capture_cleanup_test COUNT=3 after changing frame-file ownership or error reporting.

The owning capture_callback_test prepares a real inactive-window target and registers real stream outputs, then holds start completions at the public API boundary without starting capture. It delivers earlier start/delegate errors after replacement and compares exact current errors, healthy/error readiness and stream identity. It reads complete diagnostic output to require both late failures are reported, restores the public method and removes temporary files. Its own 15000ms deadline covers the real preparation query. Run make -C native/darwin repeat TEST=capture_callback_test COUNT=3 when changing start or delegate error ownership.

Native recording-file acceptance requires the complete 80-byte LZ4 header, exactly the declared compressed block and pixel CRC-32 verification after restoring exactly stride × height BGRA bytes. A correct dimension header alone does not satisfy the frame contract. Its owning fault test truncates a genuinely recorded frame after stop and requires the actual acceptance body to reject it.

The native `surface_layout_test` also records a controlled static composition: an app DOM border, a native surface container and a delayed transparent-background clip change while a layout transaction stays open. ScreenCaptureKit can return only the two changed frames while the held composition remains idle; this control case does not apply the complete-gesture frame-gap criterion or accept an application gesture. A passing control case does not resolve a missing border reproduced by the application checker. `outside.test.mjs` requires zero surface pixels outside the card on every measurable frame, two complete round trips, and consistent relative positions of terminal content, card chrome, the sidebar, and its rail; the terminal content is measured after an OSC 11 sequence sets its default background to a measurement colour, because its usual background equals the card colour. `paint.test.mjs` checks unrendered areas and requires that every `core.verify` result during the drag has no failed row. `footer.test.mjs` checks footer pixels throughout a vertical divider drag at the scale of the display the window is on. `modal.test.mjs` checks ordering, transparency, background blur (`core.window.workbench`, `core.surface.document`, `core.modal`), native input routing with `host.hit`, dismissal, movement with native drag input, resizing, and reload cleanup. `commands.test.mjs` runs the card, tab, menu, settings, library, and rename commands and checks each result in status. `audit.test.mjs` visits every screen, settings section and scope, menu, rename state, and visible plugin surface and requires empty `core.workbench.audit` and `core.surface.document` `unbound` lists. `controls.test.mjs` reads `host.window` button geometry after maximization, recording, moving, resizing, and renaming. It waits for the window to reach the screen's visible frame before restoring it: Wails replaces the AppKit zoom with its own animation, and a restore requested while that animation runs leaves the window maximized. `resize.test.mjs` records maximizing to `host.screens` `visible` and restoring up to 100ms after the `displayed` time of the presented layout, removes each recording after measuring it, requires the last frame to show the layout at the window size and the layout to catch up with the window within 150ms, and reports how many frames showed the layout behind the window frame; the window frame and WebKit content are presented separately (WebKit/WebKit#72971, tauri-apps/tao#1207), so those frames are measured, not rejected. `hosts.test.mjs` compares final requests and displayed geometry from the `diagnostics.transcript` lines; preparation identifiers are local to the owning window.

`titlebar-recording.test.mjs` records the window while the frame factor steps from 1 to 3 and back to 1 through `core.text.larger` and `core.text.smaller`, and while the main window reloads after another window changed the common `textSize` with `core.settings.change`. In every recorded frame it measures from pixels the bottom of the first row, where the row's bottom border ends in an empty column right of the window buttons, and the centre of the window buttons, between the first and the last pixel row that differs from the row background in the middle half of each button's column (`e2e/titlebar-measurement.mjs`). It fails on a frame whose button centre differs from the first-row centre by more than 0.5px, on a frame where either cannot be measured, and when a displayed row is not recorded within two display frames of its presentation at the window's refresh rate. It restores `textSize` 1 and removes its recordings.

Preview checks compare card order and split directions with the workspace and require equal row heights, uniform sidebar widths and gaps, and no stored renderer coordinates. `browser.test.mjs` serves documents from a loopback HTTP server started by the test. It opens them with `browser.navigate`, goes back and forward, and types an address into `browser.address` with `input.key`. It then requires `host.hit` to report the document region, requires a native `input.pointer` scroll to change `browser.location.scroll` by the requested 120 pixels without changing application activation, and requires the `host.window` region frame to match `browser.document` after the surface moves and resizes. It also checks that a second browser surface does not receive the first surface's document, and that closing the tab closes only that surface's region. Setting precedence and browser storage transactions are checked by `pnpm test` in `packages/workbench` and `apps/browser`. `make native-test` runs `make -C native/darwin test`, `go test` for `packages/host/wailsv3`, and `cargo test -p soksak-host-tauriv2`; the host tests cover file storage, the sidecar relay, the endpoint, and document-region ownership and cleanup. `webview_geometry_test` also checks the scale of a document region, and `document_view_test` checks its navigation, state reports, placement, and isolation.

`window-release.test.mjs` sets `projectOpening` to `windows`, opens and closes a project window four times, and requires `diagnostics.native.objects` with `equal` set to the counts before the first open to succeed after the last close; each open window must raise every count, so the counts measure the window. The check also reads each open window's `host.window` `pageProcess` and, after the counts return, requires `diagnostics.process.exit` to report that every one of those web content processes has exited. The request compares after each event that it posts has been handled, and posts one each time the main run loop is about to wait, because AppKit releases the objects of a closed window when it drains the autorelease pool of an event iteration, keeps a window that was on screen until its close animation ends, and releases an object autoreleased during a drain at the next drain; the check therefore needs no user input and no timer. The native `window_objects_test` closes a window that was on screen and checks the counts and that reading in the library: an autoreleased window keeps its objects until its event iteration ends, the counts return to their starting values after the close animation, and counts that do not reach the expected values are given as not reached when the bound ends.

Record at the window’s backing-pixel resolution. Point-sized downsampling blends half-point lines with adjacent pixels and prevents exact color measurement. Frame files retain width, height, row stride and all seven metadata values in the 80-byte header defined by the [endpoint contract](../spec/endpoint.md#diagnostic-builds). The single LZ4 block restores all BGRA bytes and row padding; readers reject the retired raw format, partial or extra blocks, wrong decoded sizes and checksum failures. Do not treat a missing or partial recording as a pass.

`geometry.test.mjs` compares native frames (`host.window`), DOM slots (`core.surfaces`), and surface document and viewport sizes (`core.surface.document`) after window resizing. It checks the owner of the final device pixel with `host.hit`, presses and releases there with `input.pointer`, and checks the trusted event coordinates in `core.surface.input`. Scale factors and scale changes do not depend on the connected displays: `native/darwin/tests/webview_geometry_test.m` sets the window's backing scale to 2, 1, and 2 again and checks half-point surface heights, document coverage of the last device-pixel row, and native input in that row. No window check requires a particular display.

The fast terminal divider check requires four complete round trips and zero white pixels in the terminal card. The three-terminal check requires five uninterrupted complete round trips, three measurable terminal regions in every frame, no DOM-border intrusion, and unchanged first-glyph dimensions and pixel count. A stationary screen or a recording missing any requested round trip fails. Each diagnostic recording is a bounded burst of at most 600 frames; reaching that bound is an explicit incomplete-recording error, not silent frame loss. The terminal project-return check repeats five-trip gestures and library returns three times and checks all three native rasters immediately after each return. The library workflow also rejects a presentation error that was reported and later cleared. These composition gestures use the page-driven diagnostic route described in the [endpoint contract](../spec/endpoint.md#diagnostic-builds); they do not validate OS button state.

When preserving a failed application while inspecting a new build, use separate disposable configuration directories. ScreenCaptureKit can identify Tauri capture clients by executable path: simultaneous processes at that same path caused replayd to cancel their capture connections. Run a byte-identical copy and its sidecars from a separate inspection directory, verify its hash, and explicitly set `APPS.tauriv2.binary` to that path before opening the harness connection. Do not disable the executable check or restart the preserved application. Remove inspection recordings when each check ends.

Copy and compare hashes for the application after each build, and reinstall the plugins with `make install-plugins` into the configuration directory the copy uses; a configuration that keeps earlier plugin and sidecar files does not test the current implementation. A live persistent service must also match the implementation being tested; preserve it only for an explicit reconnect/update test. Record a mixed-build run as invalid for validating the current implementation, not as a current-code pass or failure.

The three-terminal hide check first waits for all three native snapshots, then compares each native frame and snapshot after entering the library. Hidden surfaces must retain both. Project-return checks inspect all three current rasters immediately after the return command; an extra presentation wait must not hide an incomplete return.

The fixture must present before the harness reloads its main document. A timeout fails setup and preserves that state instead of letting a reload clear the open transaction. The harness also collects presentation-error log notifications, because the latest verification status alone may no longer contain an earlier error.

The project-return process check reads the tested configuration's terminal service endpoint and the OS process table. It requires exactly one service for that configuration, one direct shell child per open terminal (including hidden tabs), no PTY helper child, and no zombie child. Returning from the library must preserve the exact service and shell PIDs, not merely their count. Other running applications are excluded by configuration identity. Parser unit checks do not validate service lifecycle; the rebuilt-host run remains required.

The Go and Rust Sok CLI tests run in the two host jobs. Linux and Windows are not verified platforms, so CI runs no check on them. The required job fails unless every CI job succeeds. `release.yml` calls this CI graph on each push to `main` ([release](#release)); a pull request runs it on its own. CI runs no window check.

Every runner label that a workflow of this repository names is a hosted label, and no workflow runs an end-to-end check ([test kinds](#test-kinds)); `scripts/test/workflows.test.mjs` checks both.

## Release

Core releases itself, and its release waits for no release of a plugin or sidecar repository, because the repositories connect only through the records of an installation (`plugin.json`, `installed.json`). A push to `main` starts `.github/workflows/release.yml`. It runs the jobs of `ci.yml`, and beside them the `gate` job runs `soksak-release-gate packages/plugin-api/package.json docs/features.md` (the records kit). The gate releases the version that `packages/plugin-api/package.json` declares, which is the release version of every workspace package (`scripts/check-versions.mjs`), when the remote has no tag `v<version>`; on a release the two host bundle jobs build beside the checks, and `publish` requires the success of the checks, the gate and both builds, so the run takes the time of its longest job. The checks of the workflow determine whether the code is releasable; an item of the checklist in the state `[ ]`, `[~]` or `[!]` does not hold the release, and the gate prints those items as carried into the next version. The gate reads the tags with `git ls-remote` and fails when git fails, so an unknown tag set never reads as empty, and it fails on a checklist error or an open item without an identifier. The workflow never chooses a version: a new version is a committed change of the declared workspace version.

When the gate releases, the run builds and packages both hosts and checks the registry manifests. The `publish` job runs only when every one of these jobs succeeded, the commit of the run is still the head of `main` and the tag is still absent; it creates the tag `v<version>` on that commit together with the release. The body of the release is `docs/operations/install.md`, which `scripts/release-notes.mjs` writes with each relative link resolved to its file at the tag, because the release page resolves a relative link against the root of the tag. The workflow runs one run at a time (`concurrency: release`), so two pushes never publish one version twice. A tag pushed with the workflow token starts no other workflow, so the release jobs run in the same run instead of on a tag push.

The release holds what the plugin and sidecar repositories build with, so their workflows check out no source of core: the `sok` inside each application zip `soksak-<version>-darwin-arm64-<host>.zip` (`soksak.app/Contents/MacOS/sok`), which the release publishes nowhere else, and the packed releases `soksak-plugin-api-<version>.tgz` and `soksak-native-process-identity-darwin-<version>.tgz`, which `pnpm pack` makes from `packages/plugin-api` and `native/darwin/process-identity`. The tarball of the process identity package holds the static library that the release job builds.

## Page memory

## Three-host benchmark

The three-host benchmark B3 measures the [performance goals](../spec/hosts.md#performance-goals) on five applications in one session. The other hosts are the Wails and the Tauri host built from the same revision as the mygo host. The baseline hosts are the Wails and the Tauri host built from the revision that completes the measurement targets (F502-2), which precedes every item that changes code that the Wails or the Tauri host runs. Each baseline host is built and run from a verification checkout of the head of the branch `test/b3-baseline-F502-25`, which holds after that revision only the commits that change measurement targets: an item that changes a measurement target applies that change to this branch as a commit of its own and writes the new head into the baseline record `target/b3/baseline.json` of the checkout of the other hosts. The baseline record holds the heads of that branch in order, the revisions of each sidecar repository in order and the version and `sha256` of each plugin release that the baseline hosts install; it is not a record of the repository. The branch is never merged into `main`, because each of its commits after that revision applies a change that `main` holds.

The baseline hosts install the plugin releases of the index of the [public registry](../spec/registry.md) that the baseline record lists, which the version selection chose for the core version of the baseline revision; a run fails when an installed version or `sha256` differs from that record. The core version of the baseline revision is one that `core.json` of the public registry lists, and the baseline hosts run the plugin releases published before the releases that declare `exposes.element`. The other hosts and the mygo host install their plugins from the workspace registry, as every window check does. All five applications run the sidecar releases that `make registry SIDECARS=diagnostic` builds once in each phase in the checkout of the other hosts, so every application runs the same sidecar builds; `make registry SIDECARS=diagnostic PLUGINS=public` writes the index of the baseline hosts from the same checkout.

Run it with the display on, with the Accessibility permission and the approval of the real-input tier, because `STEP=pointer` brings a window to the front:

```
make e2e-b3 PHASE=1|final RUNS=7 BASELINE=<checkout of the baseline branch>
```

`scripts/e2e-b3.mjs` runs these steps; each step prints `running`, then `passed` or `failed` with its elapsed time:

1. It fails before its first run when the head of `BASELINE` differs from the last head of the baseline record or the working tree of `BASELINE` holds changes outside that head, untracked files among them.
2. It builds the release bundles of the mygo, the Wails and the Tauri host of its checkout and of the Wails and the Tauri host of `BASELINE`, and the two registry indexes; phase 1 also builds the debug bundles. It then fails when a revision of `target/registry/sidecar-revisions.json` differs from the last revision that the baseline record holds for that repository, or when the working tree of a sidecar repository held changes outside the revision that the registry built.
3. It writes a new session folder `target/b3/<time>-phase-<phase>-<random>` with `session.json` (the phase, the runs, the applications, the source revision and the executable hash of each application, and the Go and Rust toolchain versions) and copies of the baseline record and of the sidecar revision record.
4. For each run of each scenario, it checks that swap use is below half of its total, or zero, and that `fseventsd` uses less than 10% of a core over 5 seconds, and fails the run otherwise. It then makes a new configuration folder under the session folder, installs the index of the application into it with the `sok` of the bundle, and starts the executable of the release bundle through the step `start` of `runPlan` (`scripts/e2e-run.mjs`). It fails the run when a window reports a refresh rate other than 120 Hz or a backing scale other than 2 in `host.window`, and for a baseline host when its installed plugins differ from the baseline record.
5. It runs the target of each value of the scenario in the order of `docs/spec/performance-goals.json`, each once, with `STEP=pointer` after every other reading of the scenario. Each target runs in the checkout of its application with `APP`, `CONFIG`, `CONFIG_DIR`, `SOK` (the `sok` of the bundle), `TRACE=0` for a target that takes the trace state of the run, `PLUGINS` (the installed plugins that declare a surface) and `B3_OUT`, and with `SOKSAK_CONFIG_ROOT`, `SOKSAK_APP`, `SOKSAK_BINARY_<HOST>`, `SOKSAK_RUN_ID` and `SOKSAK_RUN_FOLDER` for the window checks. A make target takes the file of its output as `B3_OUT=<file>` and passes it to its script as `--b3-out <file>`, and a check of `e2e/` reads it from the environment variable `SOKSAK_B3_OUT`. Each target writes into that file one JSON object `{"measurements": {<key>: <number> | "passed" | "failed"}, "conditions": {"refreshRate", "backingScale", "traceState", "logPolicy", "window": {"width", "height"}}}`, whose form `scripts/b3-out.mjs` holds. The keys of `measurements` are the flat camelCase names of the measurements of the target, which the header of its script declares; a target knows neither the ids of the goals nor which hosts compare a value, so it writes every measurement that it makes, and a target with an error exits with another code than 0, writes no output and fails the run. Each value of `docs/spec/performance-goals.json` names in `measurement` the key that holds it in the unit of the value, and the run records that number under the id of the value. On the mygo host every value of the target requires its key, and on another application the values that are compared with other hosts; a missing key fails the run and names the value, the target and the key. The verdict of a benchmark of S5 and S7 is its measurement `passed` or `failed`, never its exit code. The run also fails when a target reports a refresh rate, a backing scale or a window outside the run conditions of its scenario, or a `traceState` and a `logPolicy` other than the `diagnostics.performance` and the classes of the policy of the settings of its measured interval. A target of `app-usage`, `terminal-redraw-usage`, `object-counts` or `host-allocations` measures in the settings that `traceSettings` of `scripts/measure-trace.mjs` gives for the `TRACE` argument of its entry, which the pointer step of `make app-usage` names for each of the two trace states of its outputs, or else for the `TRACE` of the run. An e2e benchmark takes no `TRACE` of the run and measures in the settings that `B3_SETTINGS` of `e2e/benchmark/measurements.mjs` declares for it in the shape of its keys in `B3_MEASUREMENTS` of that module: one settings object for a list of keys, and for an object of states, as for the view drag and the resize catch-up benchmarks, the same states, of which the `TRACE` argument of the entry names one, so each of them runs once in each state. ## Three-host benchmark

The three-host benchmark B3 measures the [performance goals](../spec/hosts.md#performance-goals) on five applications in one session. The other hosts are the Wails and the Tauri host built from the same revision as the mygo host. The baseline hosts are the Wails and the Tauri host built from the revision that completes the measurement targets (F502-2), which precedes every item that changes code that the Wails or the Tauri host runs. Each baseline host is built and run from a verification checkout of the head of the branch `test/b3-baseline-F502-25`, which holds after that revision only the commits that change measurement targets: an item that changes a measurement target applies that change to this branch as a commit of its own and writes the new head into the baseline record `target/b3/baseline.json` of the checkout of the other hosts. The baseline record holds the heads of that branch in order, the revisions of each sidecar repository in order and the version and `sha256` of each plugin release that the baseline hosts install; it is not a record of the repository. The branch is never merged into `main`, because each of its commits after that revision applies a change that `main` holds.

The baseline hosts install the plugin releases of the index of the [public registry](../spec/registry.md) that the baseline record lists, which the version selection chose for the core version of the baseline revision; a run fails when an installed version or `sha256` differs from that record. The core version of the baseline revision is one that `core.json` of the public registry lists, and the baseline hosts run the plugin releases published before the releases that declare `exposes.element`. The other hosts and the mygo host install their plugins from the workspace registry, as every window check does. All five applications run the sidecar releases that `make registry SIDECARS=diagnostic` builds once in each phase in the checkout of the other hosts, so every application runs the same sidecar builds; `make registry SIDECARS=diagnostic PLUGINS=public` writes the index of the baseline hosts from the same checkout.

## Browser example check

`make browser-example-check` runs `apps/browser/check/served.test.mjs` against the staged browser example. The check serves `apps/browser/build` from a loopback HTTP server of its own, starts the installed Google Chrome headless with a disposable profile (`CHROME` names another executable), and drives it through the Chrome DevTools protocol over Node's built-in `WebSocket`, so no browser automation package is a dependency. It opens a project the way a person does in that application: it presses `core.library.add`, types a folder path into `core.library.form.parent`, and presses `core.library.form.submit`, because the browser example registers a typed path and needs no folder picker ([projects](../spec/projects.md)). It waits until the page shows the workspace and all sidebar sections are mounted, and fails on any uncaught exception, `console.error`, or browser log entry of level `error`, reporting each one. A second case serves a plugin list without `terminal` in place of the staged `installed-plugins.json`, opens a project the same way, and checks that the `terminal` tabs of the environment open as placeholder cards with the reason `host` in `core.surfaces` and their placeholder text, without an error ([plugins that are not loaded](../spec/plugins.md#plugins-that-are-not-loaded)). A missing Chrome fails the check; it does not skip. The check stops Chrome, waits for it to exit, removes its profile, and stops the server when it ends.

## Manual acceptance

The terminal keyboard check uses native clicks and keys in three visible terminals per host. It verifies characters, Backspace, Ctrl+U, Enter, exactly-once command output, and unchanged screens in the other terminals. It reads the current screen once and waits for `terminal.screen` notifications; `terminal.input` is not used to validate keyboard delivery. Run this check separately from composition recordings so an input pass cannot substitute for a drag result.

- Add two existing project folders, reorder the projects, close the application, and restart it. The library lists the saved projects without starting their surfaces or shells. Select a project and confirm that its layout and settings restore in the same OS window.
- In New Project, cancel the parent-folder chooser once, then select a directory. Creation failure must preserve existing directories. Open the Dock menu and select New Window, including after closing all windows. Return from the workspace to the project list and back; layout and shells must remain available.
- Select Global and Project from the General pane tabs, change a value in each scope, and reset a project override. ## Diagnostics

Debug builds (`make wailsv3-build tauriv2-build mygo-build`) include the diagnostic methods of the [local endpoint](../spec/endpoint.md): `diagnostics.fixture`, `diagnostics.drag`, `diagnostics.capture.start`, `diagnostics.capture.stop`, `diagnostics.modal.hold`, `diagnostics.modal.held`, `diagnostics.notifications`, and `diagnostics.transcript`. The `soksak` command and the `soksak-mcp` server send the same requests; for example `soksak status core.screen --window main --config-dir DIR`. `soksak element dispatch NAME --window main --event '{"type":"click"}' --config-dir DIR` dispatches a synthetic event to a declared element entry; checks of real input use `input.pointer` and `input.key` instead.

`pnpm -F @soksak/client run bench:application -- --config-dir DIR` measures sequential round trips of a running application on three paths: `windows.list` (host only), `status.get core.screen` (relayed to the main page), and `status.get core.surface.document` with a surface (relayed through the main page to a surface page). `bench` measures the transports alone. On 2026-09-17 (M3 Pro, debug builds, 2000 requests per path, two runs) the p50 values were: Wails host 142–157µs, page 1.5–1.7ms, surface 4.4–4.5ms; Tauri host 443µs, page 2.6–2.7ms, surface 1.4–7.5ms.

The shared library has two native input suites. Run both when changing the shared input code:

```sh
make -C native/darwin test
make -C native/darwin e2e-activation
```

`test` runs `input_inject_test` in a window of an inactive application. It checks presses, drags, scroll, keys, focus, and the inactive result for a move without a button, and it does not activate the application. Every native test links `tests/support/no_activation.m`, which fails the test at exit when its process is active; a test that activates the application for `e2e-activation` calls `sp_test_declare_activation` first.

`e2e-activation` activates the test application and therefore takes the keyboard focus. Its windows set `ignoresMouseEvents`, but AppKit still delivers a movement to the tracking areas the real pointer is in. The overlapping-webview check therefore places its window away from the pointer and fails with that reason if the pointer enters the window. It runs `input_activate_test` (hover after activation), the overlapping-webview check `webview_input_test` (first as the baseline run and then as the registered-input run), `document_view_test --activation` (an OS event-queue click and key into a document region), `image_region_ime_test` (Korean 2-Set composition in an image region and an AppKit text view control), and `view_focus_test --activation` (a page press and key after the test app becomes active).

The activated view-focus path stores the previously frontmost process, requests its activation during cleanup, and fails unless the request succeeds and the process becomes frontmost within 10 seconds. If the previous process is already frontmost, no activation request is needed. It does not request a frontmost change when activation was not attempted. Its activation request has a 5-second timeout; page readiness and page receipt of the press/key each have a 10-second timeout. The press and key are synthetic AppKit events, not physical HID input. The test does not select an input source.

`terminal-view-focus.test.mjs` compares the native keys `echo focuscheck` and Enter in an independent AppKit text view and the terminal view in the same window. The declared reference `focus` action selects the ordinary AppKit control without inserting text; native keys supply its document. It requires the reference document to equal `echo focuscheck\n` without marked text, the terminal output to occur once, trusted terminal pointer down and up, and matching native focus. Both gestures are recorded in full; every frame must decode and the capture must remain unlimited. Reported and decoded frame gaps are validated finite nonnegative measurements, not functional gates. The stop response callbackStatus JSONL is checked for contiguous sequence, status, exact displayTime, and a one-to-one ordered match between each non-null callback frame filename and the emitted frame files. Callbacks with a null frame are counted by status and reported around gaps above 33 ms. For each callback, the check also reports raw display-to-callback-entry and synchronous-processing start-to-completion deltas with the captured mach timebase. The processing completion timestamp precedes asynchronous compression and file writing; it does not measure disk-write completion. These values classify observations without treating a gap above 33 ms as a functional failure or inferring timing across clock formats. Failure recordings remain owned by the session finalizer. The terminal click uses its declared applied native frame. The check restores the input source, closes the reference and restores the session baseline application.

Activation-tier window checks live in `e2e/activation/` and run only with `make e2e-activation` in a run the user approves; `make e2e` does not include them. They may activate the application with `input.pointer` `activate: true` (`make e2e-check` rejects it elsewhere) and change the keyboard input source with `diagnostics.input.source`, restoring the previous source in cleanup. `ime.test.mjs` types ABC `ddd`, switches to Korean 2-Set, types `g k s r m f`, Space, and Enter, and requires the preedit sequence `ㅎ`, `하`, `한`, `ㄱ`, `그`, `글`, ` ` and the committed command `ddd한글` exactly once on the screen. `marked-text.test.mjs` selects Japanese (Romaji), types `n i h o n n`, which the input method shows as marked text, switches to ABC to end the composition, and requires the last marked text to reach the PTY exactly once with no preedit after the commit; it requires the `com.apple.inputmethod.Kotoeri.RomajiTyping.Japanese` input source to be enabled. `terminal-keyboard.test.mjs` types, edits, and executes commands with native keys in three terminals and after a browser tab, a resize, a modal, a project return, and a second project window, selecting ABC after each focus because an input context can restore its own input source; a second check opens a second project window, which becomes the key window, sends a character key to the first window's focused terminal, and requires the terminal to report that the input method did not answer. Before activating the application, each check moves its window beside the system pointer when the window covers it (`keepPointerOutside` in `packages/window-check/app.mjs`), because the key window receives the pointer location as a move; when the window fits on neither side, it first narrows the window to the wider side. Start the application alone before the run, because the check takes the keyboard focus. For a manually selected host case, set `SOKSAK_APP` to the endpoint application (`wailsv3` or `tauriv2`), set `SOKSAK_CONFIG_DIR` to that profile and `SOKSAK_BINARY_WAILSV3` or `SOKSAK_BINARY_TAURIV2` to the matching executable, provide a unique `SOKSAK_RUN_ID` and `SOKSAK_RUN_FOLDER`, and create the run folder before invoking `node ./run.mjs`; the check appends `marks.jsonl` directly.

`activation/manual/native-ime-lifecycle.test.mjs` is a separately selected, approval-gated file and is not part of the default activation glob. It defines the F8-9 `ddd` + Korean 2-Set `g k s r m f` sequence, the F143 `g k s k Space Enter` resyllabification sequence, whose same-window AppKit reference must end as `하나 \n`, and ten numbered lifecycle cycles per host. The terminal side checks `하나 ` before Enter and confirms the shell receives the command. Each cycle sends only the previously approved eight `k` keys, Backspace and Space; it compares the same-window AppKit document with committed terminal screen cells plus the current marked buffer, and preserves the full gesture capture and input transactions. It then performs two project close/reopen passes and requires image-region teardown and replacement readiness. It does not claim to exercise an overlay operation. Each cycle has a 120-second timeout; the two additional Korean sequence cases have 60-second timeouts and require separate user approval. Select one test by running `node ./run.mjs --test --test-concurrency=1 --test-global-setup=./setup.mjs --test-name-pattern='F239-47-33 lifecycle cycle 01' activation/manual/native-ime-lifecycle.test.mjs` from the e2e package with `SOKSAK_RUN_ID` and `SOKSAK_RUN_FOLDER` set. Change the pattern only to select another numbered cycle or an explicitly approved sequence. Do not run the native `--backspace-trace-abc-baseline` target without its own approval because it forces an ABC baseline.

Real-input window checks live in `e2e/real/` and run only with `make e2e-real` in a run the user approves; the default run does not include them. The default window checks measure an inactive application: an active window receives AppKit cursor updates when its layout changes and passes the system pointer location to the page, which mixes with a synthetic `diagnostics.drag`. The harness therefore fails a drag with an explicit error when the application is active. The frontmost application is not a criterion of a check result: the harness neither captures, restores nor judges it. An application action may activate its window as specified (the project-open command creates or focuses windows), and another application that a person brings forward during a check is not caused by the check; activating an earlier application would take the activation away from that person. A check that needs activation state asserts it through the declared status of the action it tests. Before the first check of a run, the declared entry points (`verify`, `verify:activation`, `verify:real`, `verify:terminal-sidebar-current`, and `repeat`) run `e2e/setup.mjs` once as the node:test global setup, which declares the executables to check. The real-input checks post HID events with `CGEventPost` through `e2e/real/hid.mjs`, which needs Accessibility permission for the terminal that runs them and fails at once without it. They take the pointer and keyboard, activate the application, and require the application's window to be frontmost at every posted point, because an event posted over another window goes to that window. They set the flags of every posted event, because an event created without a source inherits HID-system modifier flags (V5-25-1). `input.test.mjs` requires the system pointer to reach the posted point and a posted click to give a terminal region native focus.

Person-operated window checks live in `e2e/person/` and run only with `make e2e-person` while a person is at the machine; the default run does not include them. A native panel, such as the save panel of the debug view, is not the key window that the native input of a check names, so the check opens the panel through a declared command and waits for the person; the instruction is in the diagnostics of the run.

`host.window.reload` terminates the main WebContent process before it reloads the page. A ready page reloads itself only after every call it sent has its answer ([page reload](../spec/native-host.md#page-reload)), and no forward waits without a time limit, so a reload of a ready page leaves no call running. A page call that a terminated process left running, as a reload of a page that has not reported ready can, still completes on the host; Wails v3 then logs `Unable to write json payload. Please report this to the Wails team! error=request has been stopped` once for each reply it cannot deliver, because it runs binding calls without the request's cancellation (`context.WithoutCancel`). Such a line is a reply to a page that no longer exists, not a lost reply.

`sok capture --window main --config-dir DIR` writes a still PNG of a running diagnostic build's window without focusing it and prints the result with its path, for looking at the result during development. Remove the printed `still-*` directory after viewing; numeric checks use recording frames instead.

The tracked `capture-still.test.mjs` verifies the still-file artifact: device-pixel dimensions, opacity and expected border pixels at declared native coordinates. `png.test.mjs` owns PNG alpha and invalid-coordinate/decoded-length checks. This verifies output integrity; gesture completeness and presentation timing continue to use recorded frames. A capture of a native modal waits for `host.window` to report `modal.shown` and then for `host.window.presented`: a page status such as `core.settings-modal` `open` reports the main page's state, which precedes the modal webview's first render, so a still taken after it can show the window without the modal. `modal.test.mjs` checks that every recorded frame from the presented time on shows the settings scrim.

`SOKSAK_PERFORMANCE_TRACE=1` enables the performance trace in every check preparation (`fresh()`), and a terminal-readiness failure then reports the surface registration timeline written since that preparation started; any other value is rejected. The trace changes timing, so a failure that disappears with it still needs an untraced reproduction.

`SOKSAK_APP=<wailsv3|tauriv2> make e2e-shutdown` checks the declared quit lifecycle (`command.run` of `host.quit`) on the one running host that `SOKSAK_APP` selects; `SOKSAK_SHUTDOWN_BY=signal` sends SIGTERM instead, which requests the same quit, and `SOKSAK_SHUTDOWN_TERMINAL=1` opens a terminal session first. In terminal mode the check reads the service PID from its protocol-1 `endpoint.json` without connecting to the service, waits for the host endpoint to close, then invokes the bundled `sok process wait` command and requires the original service endpoint file to be absent. The reported service duration is observation latency after host endpoint closure, not the service's lifetime. After the shutdown request and bounded waits, the check reads application event logs from the captured start offset and fails on every error in that interval. If a shutdown wait and the log audit both fail, the wait failure remains the primary cause and the audit findings are reported with it. The host ends, so the check runs alone and the host is started again afterwards (`e2e/normal-shutdown.mjs`).

Without terminal mode, the runner queries `diagnostics.objects` for the main window and requires no sidecar sessions and no service endpoint files before requesting quit. It records this precondition; it does not infer sidecar absence from plugin installation state.

`make e2e-repeat FILE=<file> NAME=<test name pattern> COUNT=<n>` runs one window check repeatedly against the running applications (`SOKSAK_APP` selects one host), each run in a new `node:test` process; it stops at the first failed run, prints that run's output, and fails when no test ran. `make -C native/darwin repeat TEST=<name>_test COUNT=<n>` runs one default test repeatedly and `make -C native/darwin repeat-suite COUNT=<n>` runs the default suite repeatedly; each stops at the first failure and reports the run number and system load. `make rust-tests-alone PACKAGE=<package> [MANIFEST=<Cargo.toml>]` runs each test of a Rust package alone in a new process and reports the first test that fails alone; a test that passes only after another test has run depends on shared state or timing. `make rust-repeat PACKAGE=<package> COUNT=<n> [TEST=<name>] [FEATURES=<features>] [MANIFEST=<Cargo.toml>]` runs the tests of a Rust package, or the one test named `TEST`, `COUNT` times in a row; it stops at the first failed run and reports its output, the run number, and the system load, and fails when `TEST` names no test. `make go-repeat PACKAGE=<go package path> COUNT=<n> [TEST=<regexp>] [TAGS=<tags>]` does the same for Go tests, with `TEST` as the `go test -run` pattern and `TAGS` as the `go test -tags` value; a run that builds no test file (`[no test files]`) or matches no test fails. `TEST_TARGET=lib` or `TEST_TARGET=test:<Cargo target name>` limits Rust target compilation and discovery to that target and excludes other targets and library doctests; without it, package-wide discovery is unchanged. `FEATURES=<features>` passes `--features` to every `cargo test` of `rust-repeat` and `rust-tests-alone`; tests behind the `diagnostics` build tag or feature run only with `TAGS=diagnostics` or `FEATURES=diagnostics`. `make node-repeat FILE=<test file> NAME=<test name pattern> COUNT=<n>` runs the matching tests of a Node test file from the repository root the same way and fails when no test matched.

The baseline expects duplicate pointer movement in overlapping DOMs. The registered-input run requires exclusive pointer tracking, retained keyboard input, and cleanup after hiding or removing the overlay. Neither run tests delayed cursor responses.

The focused e2e/capture-lifecycle.test.mjs runs three consecutive recordings per inactive host. Each recording changes the declared text-size setting, waits for presentation, stops at that checkpoint and requires the returned frame count to equal the finalized frame files. Recursive SHA-256 snapshots require every earlier recording directory and artifact to remain unchanged after later recordings. The harness restores settings, audits application errors and removes successful recordings. Controlled native callback owners cover delayed delivery; sequential runtime checks do not force a delayed callback or prove capture cadence.

When Cargo compilation or metadata discovery fails, the Rust owner runner prints the captured stdout before reporting the command failure. This preserves JSON compiler diagnostics and plain metadata errors. It retains the failed outcome and starts no test from a failed discovery.

Stall sampling and launchd process discovery use asynchronous child processes with a ten-second limit for each process. The check continues to read endpoint messages while samples run. Host and page samples start together; page failures are reported individually and a host failure fails the sample operation.

IME window checks end their owned terminal status observer after capture stop and before copying artifacts or running visual analysis. Every input stage and the terminal sequence boundary are already saved. Cleanup may call stop again safely and retries only subscriptions whose earlier release failed.

The Terminal view benchmark keeps full performance tracing for process and one-shot layout evidence and disables only `diagnostics.performance` around the continuous drag. Source-frame events use the independent `diagnostics.log.frame` policy, and capture, clocks and error auditing remain enabled. Setting propagation completes before gesture timing; the host may wait for its sampler to stop. The prior setting is restored before reclaim sampling even when the drag fails. The phase mode is part of the recorded result. Full profiling is diagnostic context rather than cadence proof; keeping it throughout the timed gesture adds unrelated host observations. The alternative of disabling all debug settings is rejected because it also removes required frame records. The earlier layout retains tracing because its applied native-placement evidence requires it. The 33 ms, 2 pt and two-frame limits remain unchanged.
