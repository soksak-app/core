# Build and verify applications

[한국어](examples.ko.md)

Run commands from the repository root. Use the package-manager version in `package.json`, a Go toolchain compatible with `go.work` and `packages/host/wailsv3/go.mod`, and a Rust toolchain compatible with the root `Cargo.toml` workspace. The [native host specification](../spec/hosts.md) describes the host packages, applications, and workspace files. Native validation currently runs on macOS with the Command Line Tools SDK. Tauri diagnostic capture uses the current-process ScreenCaptureKit query and does not require Screen Recording permission.

## Native updates

Read the [private native API inventory](private-native-apis.md) before updating native source, frameworks, the SDK, or the OS. If native behavior fails after an update, review that document first. It records active calls, necessity, failure signs, and required verification.

## Build

```sh
make prepare
pnpm build
make wailsv3-build tauriv2-build
```

`native/darwin` builds `libsoksak-darwin.a` and `soksak-darwin.pc` in `native/darwin/build/`. The Makefile adds that directory to `PKG_CONFIG_PATH`; Wails and Tauri locate the headers and link flags through pkg-config. Both native applications require macOS 14.0 because the capture code uses ScreenCaptureKit APIs introduced in macOS 14.0. The Makefile passes this minimum to Go through `CGO_CFLAGS` and `-extldflags`, and to Rust through `MACOSX_DEPLOYMENT_TARGET`.

`make registry` builds the workspace registry in `target/registry`: it builds the sidecars, packs as a diagnostic package (`--diagnostics`) every plugin that `scripts/workspace-registry.json` declares, releases the sidecars that their `plugin.json` names for the current platform, writes the registry files with the packs of that declaration, and runs `sok registry build`. `make install-plugins CONFIG=DIR` builds that registry, removes the plugins installed in `DIR`, and installs every plugin of the registry there; workspace plugins keep their version while they change, so a repeated install of the same version would leave the earlier files. `sok registry use target/registry/index.json --config-dir DIR` and `sok plugin install <id> --config-dir DIR` then install from it ([command line](../spec/cli.md#installing-plugins)).

Run the browser application with `pnpm example` and open `http://localhost:8749/index.html`. Run every package test with `pnpm test`.

The build targets build `native/darwin` and the workbench, then run `soksak-stage src/frontend` in each application. The tool stages the workbench, the layout library, the plugin API and the application's `runtime/` directory into the generated `apps/<app>/src/frontend/`. The bundles hold no plugin and no sidecar: the hosts serve the plugins installed in the configuration directory ([installation](../spec/installation.md#serving-installed-plugins)). Debug targets add `--diagnostics`, which stages the page diagnostic module (`diagnostics.js`); release targets stage an empty module. Both executables embed the frontend at build time. A running process does not acquire a newly built frontend; restart the corresponding application after building.

Debug executables are `target/debug/soksak-wailsv3.app` and `target/debug/soksak-tauriv2.app`. Release builds use `make wailsv3-build-release tauriv2-build-release` and write `target/release/wailsv3/soksak.app` and `target/release/tauriv2/soksak.app`. Both release executables carry no symbol table: the Wails build links with `-s -w`, and the root `Cargo.toml` release profile sets `strip = true`; `make release-check` therefore finds diagnostic code by strings that stripping keeps (diagnostic method names and the capture class name `SPCapture`). `make examples-size` builds both profiles and reports their sizes.

`make hosts-check` also vets the Wails host source for Windows (`windows-build-check`).

## Test parity

Run the structural inventory gate with `make parity-check`. It discovers Git-visible JS/TS, Rust, Go, Objective-C, native headers, HTML/CSS, shell scripts, contract declarations, and build manifests without fixed language roots. Generated library output and Tauri schemas have explicit exclusions; source/output equality remains a separate build check. Unclaimed implementation or test files, empty patterns, and duplicate ownership fail. Shared tests do not permit duplicate implementation ownership.

`make host-contract-check` runs the tests of both hosts and compares them with the [host contract cases](../spec/host-contract.md); `make native-test` runs it, and it first runs `make rust-format-check`, which fails when a Rust package of the root or `sidecars` workspace is not formatted by `rustfmt`, and `make go-format-check`, which fails and lists every tracked Go file that `gofmt` would change. The current inventory has 60 lanes, 372 implementation files, and 415 test files. The current mapping is incomplete. A structural pass would not establish behavior parity: named behavior mappings, actual per-language execution, and matching-build evidence remain required by the [verification contract](../spec/verification.md). Do not expand unrelated globs or exclude discovered files to obtain a pass.

`pnpm test` runs the audit/checklist/command-supervision self-tests before package tests. The two Rust terminal packages invoke their actual Cargo tests; package-command tests replace Cargo with a failing fixture to verify invocation and failure propagation, not engine behavior.

A bounded command can be run with:

```sh
node scripts/test-command.mjs --id inventory --timeout-ms 10000 -- node scripts/check-test-parity.mjs
```

The supervisor streams stdout/stderr and emits JSON start/progress/final events with elapsed milliseconds. It reports nonzero exits, missing executables, timeout, cancellation, and cleanup errors. A permission-denied cleanup probe is not proof of process absence: macOS answers `kill(-pgid, sig)` with EPERM when no member of an existing group may receive the signal, which includes a group whose members have all exited and wait as zombies until their parent reaps them. After such a refusal the supervisor reads the group's members from the process table (`ps -A -o pid=,pgid=,stat=`), records them in the `verify` cleanup observation, and counts the group as cleaned only when no member is listed or every listed member is a zombie (state `Z`); a running member keeps the cleanup failing with the EPERM error. This supervises one command process group; language adapters still need case discovery, per-case execution, zero-test/skip rejection, and source/binary evidence. It does not close independently running inspection applications.

Run the four-language adapter gate with `make language-test`. It emits case-level expected/actual test counts and evidence hashes for the declared JS/TS, Rust, Go, and Objective-C cases. To retain failures across a retry, provide a file outside the repository: `node scripts/language-test-adapters.mjs --evidence-file "$TMPDIR/soksak-language-evidence.json" scripts/language-test-cases.json`. The next run appends an attempt only when the source, test, dependency, dirty-worktree, build-flag, and process snapshots are unchanged; otherwise it fails as stale evidence.

`make node-repeat FILE=<test> NAME=<pattern> COUNT=<n>` reports the run number and streams child test stdout/stderr while executing, stopping on the first failure. Output forwarding must preserve the child failure status, and a run without a matching passed test fails.

Release verification requires the exact bundle paths: `node scripts/check-release.mjs --wailsv3-bundle PATH --tauriv2-bundle PATH`. Both options are required; unknown options, duplicate options and missing values fail before inspecting files. `make release-check` supplies `WAILS_RELEASE_BUNDLE` and `TAURI_RELEASE_BUNDLE` to this command. Override those build variables to prepare separate bundles without modifying a running bundle; the checker must inspect the same specified paths. The checker reads every executable in each bundle's `Contents/MacOS` and never reads the staged frontend. Both applications embed the frontend uncompressed (Wails `go:embed`; Tauri without its `compression` feature), so the application executable must contain every file published by the workbench and `release-diagnostics.js` verbatim; otherwise the checker reports that the frontend is not readable. It then rejects plugin diagnostic entry names and diagnostic module sources found in the executable. The workbench and plugins are resolved through the application's `package.json` dependencies.

## Window checks

The fixed-sidebar window checks restore temporary explicit card-sidebar selections before disconnecting, including after preparation fails. An explicit card `off` takes precedence over plugin defaults; use the declared `core.card.sidebar.set` command with `set: "inherit"` to clear that selection while retaining size and fold choices. To observe an existing normal window without replacing its project or settings, run `SOKSAK_APP=tauriv2 SOKSAK_CONFIG_DIR=<config-dir> pnpm -F @soksak/e2e verify:terminal-sidebar-current`. This check requires an active terminal card and a saved terminal `card-right` assignment, records normal/fullscreen/restored presentation, and retains the original tabs and settings. It does not create a fixture or repair a disabled selection.

Install the workspace plugins into the configuration directories the harness reads (`os.tmpdir()` of Node.js, `$TMPDIR` on macOS), then start each application once, from separate terminals, with that directory:

```sh
make install-plugins CONFIG="$TMPDIR/soksak-check-wailsv3"
make install-plugins CONFIG="$TMPDIR/soksak-check-tauriv2"
make e2e-registry-tls
./target/debug/soksak-wailsv3.app/Contents/MacOS/soksak-wailsv3 --config-dir "$TMPDIR/soksak-check-wailsv3" --registry-ca "$TMPDIR/soksak-check-registry-tls/ca.pem"
./target/debug/soksak-tauriv2.app/Contents/MacOS/soksak-tauriv2 --config-dir "$TMPDIR/soksak-check-tauriv2" --registry-ca "$TMPDIR/soksak-check-registry-tls/ca.pem"
```

`make e2e-registry-tls` creates a test-owned certificate authority and a server certificate for `127.0.0.1` once; `e2e/registry.test.mjs` serves the workspace registry over https with them, and the diagnostic `--registry-ca` lets the applications trust that authority ([application arguments](../spec/hosts.md#application-arguments)).

Keep the display on and both windows available for rendering. Run:

```sh
pnpm -F @soksak/e2e run verify
```

The harness is the package `@soksak/window-check` (`packages/window-check`), which other repositories pin to run their own window checks. It takes the executable of each application from the environment variables `SOKSAK_BINARY_WAILSV3` and `SOKSAK_BINARY_TAURIV2` and fails with the variable name when a checked application has none; core's entry points run `e2e/setup.mjs` as the node:test global setup, which declares the debug bundles of the cargo target directory that `cargo metadata` reports (so `CARGO_TARGET_DIR` applies) unless the run already declares them. Core's checks start from `fresh` in `e2e/fixture.mjs`, which prepares the fixture through the harness's `prepareFixture` and waits for its terminal. The harness (`packages/window-check/app.mjs`) connects through `<config-dir>/endpoint.json` with `@soksak/client` ([local endpoint](../spec/endpoint.md)). It checks that `application` names the expected host and that `executable` is the executable of this checkout. A lock file `soksak-check.lock` in the temporary directory prevents two concurrent runs; a second run fails without measuring. Tests never start applications. They read and change state only through declared entries ([exposure](../spec/exposure.md)): status values, commands, DOM entries, host entries, and the diagnostic methods of debug builds. Waits use `status.watch` notifications and `host.window.presented`; the harness has no polling loops or fixed delays. Real input checks use `input.pointer` and `input.key`, which do not activate the application. `input.key` builds every key without explicit text, named keys included, from its macOS key code, so AppKit and the input method compute its characters as for hardware input; a check that types Latin text therefore selects the ABC layout with `session.selectInputSource`, which restores the previous source when the check ends. `make e2e-check` rejects timers, `eval`, the `Function` constructor, the removed native probe, and the removed TCP control port in `e2e/`. A missing running application fails the check; a missing binary is reported as skipped. A run with skipped host tests does not validate both hosts.

`make examples-verify` runs `make e2e-check`, `make exposure-check`, the documentation check, and the window checks. Build both applications and restart them before verification. Rebuilding an executable does not replace an already running process. The terminal service of a check configuration keeps the sessions of an application that ended without a normal quit, because a lost connection preserves sessions ([terminal runtime](../spec/terminal-runtime.md)); the terminal process checks count the shells of that service, so after forcing an application to end, stop the `soksak-vt-alacritty` process whose `--service-dir` is in that configuration directory before the checks.

Use disposable configuration directories: the harness replaces their registry and common settings and creates a `test-project` folder with test-only overrides. Project-window checks create additional temporary project folders and exercise the normal file and window APIs. `fresh` places the Wails check window at the top left and the Tauri check window at the top right of the main screen's visible area with `host.window.move`, which does not activate either application, so every check starts from the same window frames (`placement.test.mjs`); on a screen narrower than both windows their middles overlap. Windows of another application can still cover a check window, which the drag checks report.

Before each check, the harness saves every item type of the general pasteboard; after the check's other cleanup it writes them back and fails the check when the pasteboard then differs from before the check. A rejected `input.pointer` error names its phase, button, position and window. For each synthetic press whose release was not delivered, the cleanup waits until `host.buttons` reports mask 0, sends the release, and prints a `released open press:` diagnostic with the time it waited. Every cleanup step runs even when an earlier one fails, and each failure is printed as a `cleanup failed:` diagnostic as well as failing the check, because `node:test` does not print an error of an `after` hook when the test body has already failed. After the cleanup the harness reads the lines that the checked application wrote to `logs/application.log` since the previous check of that configuration directory read it, and records each line that states an error (`error: `, [application log](../spec/hosts.md#application-log)), also one whose display a later reload removed from the document. It keeps the read position in `<config-dir>.log-offset`, so a line written between two checks or two runs is read by the next check; without that file it reads the log from the start, so errors of the application start are judged too. It prints each recorded error as an `application error:` diagnostic and fails the check when one of them does not match a pattern that the check declared with `expectError(pattern)` because the check causes it on purpose. It also closes other windows, restores the 1200×760 start size, runs `diagnostics.fixture`, reloads the main document with `host.window.reload`, waits until every visible terminal surface has registered `core.surface.document`, `terminal.session` and `terminal.view` with its theme applied, and confirms presentation. `diagnostics.drag` supplies drag steps from the host at 16ms intervals; with `capture: true` the host records the window from before the first step until the gesture has been presented, and the harness stops the capture with `diagnostics.capture.stop`, passing the `displayed` time from `host.window.presented` so the recording includes the presented screen. `diagnostics.capture.start` records around any other request; with `display: true` it records this application's windows on the window's display, which keeps recording when a window moves to a full-screen Space. Each frame file stores, before the BGRA pixels, the rectangle the window occupies in the buffer, the content scale, the backing scale, and the display time; a window larger than the buffer is scaled into it. When frames are not written, the capture reports the count of blank and suspended frames. The capture copies each frame in its sample handler and losslessly compresses its complete pixel buffer with LZ4 RAW on the separate writer queue before writing it. The callback rejects an exhausted 64-frame pending-write capacity without blocking; the recording fails explicitly and stop preserves earlier and stop errors. The separate 600-frame burst cap remains reported; `diagnostics.capture.stop` returns `longestGap`, and a drag recording with a gap over 100ms between frames fails because part of the gesture was not recorded. A drag that runs outside 1/1.25–1.25 of the requested duration is repeated once and then fails. A test rejects an incomplete gesture, too few frames, or too few measurable frames.

Recordings are temporary. Each check deletes its frame directory in its cleanup, whether it passed or failed. `s.record(params)` starts a recording and returns its `frames` folder and a `stop(options)` that sends `diagnostics.capture.stop` once; a failed stop is not sent again, because the host may have ended the recording before the failure, and the session cleanup sends a stop only when none was sent and removes the folder. The harness lists the folders under `<config-dir>/captures` when the session opens; after the cleanup it removes each folder that was not listed and fails the check with the paths of those folders. With `SOKSAK_KEEP_FAILURE_CAPTURE` set it keeps them and prints each path as a `kept recording:` diagnostic. A failure message reports measurements and frame numbers only; the harness writes no images.

The card fullscreen window checks cover the card icon, fullscreen/restore geometry, retained surfaces and settings application in both states. Automatic/sidebar space conditions belong to `card-sidebar-space.test.mjs` and the [card-sidebar contract](../spec/example-model.md). Assigning large sidebars folds an insufficient axis instead of creating an empty slot. The compositor owner test covers independently controlled zero-width and zero-height slots, hiding them without disposal and restoring visibility when their area returns.

The space-condition check retains all configured external window columns. A manual fold need not release enough width to expand the opposite side: its expected state follows the measured card space including borders. Check insufficient normal space, an explicitly wider normal window that allows expansion, fullscreen, and short restoration while preserving the saved manual choice.

The four-side assignment check separates saved assignments from effective automatic folding. On a short normal card, top/bottom may be folded while all four sets remain assigned. Different-plugin tab selection must preserve assigned sets and complete card geometry. Manual fold checks use requestedCollapsed and saved state rather than an already automatically folded appearance.

The linked-default check verifies requested fold state, stored fold/size results and the absence of an explicit set after each command. An automatically folded appearance does not prove a manual request changed. Fault-injection tests at the window-check owner must reject a no-op fold and a command that converts a derived set to an explicit assignment.

Window-sidebar persistence checks record independent window/card link changes, column widths, edge hiding/restoration and a saved-project document reload. Compare stable owner records and assignments with actual section output, DOM/native rectangles and final recorded pixels. This acceptance is separate from structural ownership and complete border-transition gesture checks.

The card-sidebar gesture checker rejects every frame without its expected border. Its error includes frame index/count, capture geometry/scales/time, sampled colors, matching border positions along the full axis and the initial/drag/release presented pose timeline, and layout-transaction start/DOM-presentation/native-commit times returned by recording start/stop. These diagnostics locate a failing frame; they do not replace complete-gesture acceptance.

The native capture acceptance requires both a positive recorded-frame count and no stop error. The owning checker fault test executes the actual acceptance body with a positive count and a controlled stop error; it must reject that result. A recorded frame does not prove that capture completed successfully.

The owning capture_lifecycle_test executes the same strict acceptance with pass-through SCStream start/stop callbacks and delegate-stop observation. It reports callback sequence, monotonic elapsed time, stream identity, error domain/code/message and point-in-time frame counters without changing callback results. Use its tracked repeat target for a real stop failure; passing observations do not diagnose an earlier unobserved failure.

The owning capture_pressure_test also checks still-result isolation with a written first frame: null-path and asynchronous missing-window failures must preserve recording errors and healthy readiness. It rejects invalid UTF-8 paths and holds the public still-query completion past the real 10000ms timeout before delivering the late failure. The returned timeout remains caller-owned, the later recording error remains unchanged and the callback error is logged. Run its tracked native repeat target after changing either recording or still error boundaries.

The owning capture_preparation_test holds public query completions through the actual 10000ms deadline, then delivers real-content success or an explicit callback failure. It verifies obsolete inactive target/config deallocation, caller-owned timeout, and unchanged later target and recording error. A separate on-time completion activates a recording immediately before publication and requires rejection without state changes. Each run has a 35000ms failure deadline and reports phase starts and elapsed results; use make -C native/darwin repeat TEST=capture_preparation_test COUNT=3 after changing preparation ownership or publication.

The owning capture_cleanup_test controls file open, write, close, commit and removal results while running the actual sample writer. It checks original system-error preservation, additional removal errors with retained paths, pre-existing file preservation after failed open, first-frame/count rejection, capacity restoration, and healthy commit/cleanup. It creates real partial files, removes all fixtures, reports each phase, and has its own 5000ms failure deadline. Run make -C native/darwin repeat TEST=capture_cleanup_test COUNT=3 after changing frame-file ownership or error reporting.

The owning capture_callback_test prepares a real inactive-window target and registers real stream outputs, then holds start completions at the public API boundary without starting capture. It delivers earlier start/delegate errors after replacement and compares exact current errors, healthy/error readiness and stream identity. It reads complete diagnostic output to require both late failures are reported, restores the public method and removes temporary files. Its own 15000ms deadline covers the real preparation query. Run make -C native/darwin repeat TEST=capture_callback_test COUNT=3 when changing start or delegate error ownership.

Native recording-file acceptance requires the complete 80-byte LZ4 header, exactly the declared compressed block and pixel CRC-32 verification after restoring exactly stride × height BGRA bytes. A correct dimension header alone does not satisfy the frame contract. Its owning fault test truncates a genuinely recorded frame after stop and requires the actual acceptance body to reject it.

The native `surface_layout_test` also records a controlled static composition: an app DOM border, a native surface container and a delayed transparent-background clip change while a layout transaction stays open. It checks complete pixel buffers, the initial border before commit and the final moved border, and removes recordings after measurement. ScreenCaptureKit can return only the two changed frames while the held composition remains idle; this control case does not apply the complete-gesture frame-gap criterion or accept an application gesture. A passing control case does not resolve a missing border reproduced by the application checker. The frame `displayTime` is the window-server display time ([Apple documentation](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/displaytime)); compare it with the transaction timeline without treating correlation as a cause.


`outside.test.mjs` requires zero surface pixels outside the card on every measurable frame, two complete round trips, and consistent relative positions of terminal content, card chrome, the sidebar, and its rail; the terminal content is measured after an OSC 11 sequence sets its default background to a measurement colour, because its usual background equals the card colour. `paint.test.mjs` checks unrendered areas and requires that every `core.verify` result during the drag has no failed row. `footer.test.mjs` checks footer pixels throughout a vertical divider drag at the scale of the display the window is on. `modal.test.mjs` checks ordering, transparency, background blur (`core.window.document`, `core.surface.document`, `core.modal`), native input routing with `host.hit`, dismissal, movement with native drag input, resizing, and reload cleanup. `commands.test.mjs` runs the card, tab, menu, settings, library, and rename commands and checks each result in status. `audit.test.mjs` visits every screen, settings section and scope, menu, rename state, and visible plugin surface and requires empty `core.page.audit` and `core.surface.document` `unbound` lists. `controls.test.mjs` reads `host.window` button geometry after maximization, recording, moving, resizing, and renaming. It waits for the window to reach the screen's visible frame before restoring it: Wails replaces the AppKit zoom with its own animation, and a restore requested while that animation runs leaves the window maximized. `resize.test.mjs` records maximizing to `host.screens` `visible` and restoring up to 100ms after the `displayed` time of the presented layout, removes each recording after measuring it, requires the last frame to show the layout at the window size and the layout to catch up with the window within 150ms, and reports how many frames showed the layout behind the window frame; the window frame and WebKit content are presented separately (WebKit/WebKit#72971, tauri-apps/tao#1207), so those frames are measured, not rejected. `hosts.test.mjs` compares final requests and displayed geometry from the `diagnostics.transcript` lines; preparation identifiers are local to the owning window.

`titlebar-recording.test.mjs` records the window while the frame factor steps from 1 to 3 and back to 1 through `core.text.larger` and `core.text.smaller`, and while the main window reloads after another window changed the common `textSize` with `core.settings.change`. In every recorded frame it measures from pixels the bottom of the first row, where the row's bottom border ends in an empty column right of the window buttons, and the centre of the window buttons, between the first and the last pixel row that differs from the row background in the middle half of each button's column (`e2e/titlebar-measurement.mjs`). It fails on a frame whose button centre differs from the first-row centre by more than 0.5px, on a frame where either cannot be measured, and when a displayed row is not recorded within two display frames of its presentation at the window's refresh rate. It restores `textSize` 1 and removes its recordings.

`terminal.test.mjs` creates at least three terminal surfaces in one project, sends visible markers through each PTY, performs five fast horizontal divider drags, and measures every recorded frame for input pacing, frame gaps, unchanged terminal cell metrics, complete native-region coverage, and absence of a full-height white stripe in the terminal regions. The native `image_region_test` Red case also requires a presented image region to apply a new placement immediately; a presented snapshot must not leave its native frame at the previous placement.

`terminal-protocols.test.mjs` writes the implemented CSI and OSC sequences through the shell into the PTY and reads their result from the screen cells, `terminal.cursor`, `terminal.session`, `core.grid`, the pasteboard, or the reply, which a shell `read` prints in hexadecimal; the vendor OSC sequences have their own checks in `terminal.test.mjs` and `e2e/real/terminal.test.mjs`.

`projects.test.mjs` checks common and folder settings files, General scope-tab placement, writes from each tab, scope preservation across categories, override reset, library-only Global scope and appearance actions, workspace override restoration, folder aliases, tab/window policy, independent modals, and saved layout and window geometry after native close/reopen. `library.test.mjs` checks window reuse after creation and selection; failed directory operations; actual open status, pins, search, workspace return, and Dock New Window through `host.dock`. Preview checks compare card order and split directions with the workspace and require equal row heights, uniform sidebar widths and gaps, and no stored renderer coordinates. `browser.test.mjs` serves documents from a loopback HTTP server started by the test. It opens them with `browser.navigate`, goes back and forward, and types an address into `browser.address` with `input.key`. It then requires `host.hit` to report the document region, requires a native `input.pointer` scroll to change `browser.location.scroll` by the requested 120 pixels without changing application activation, and requires the `host.window` region frame to match `browser.document` after the surface moves and resizes. It also checks that a second browser surface does not receive the first surface's document, and that closing the tab closes only that surface's region. Setting precedence and browser storage transactions are checked by `pnpm test` in `packages/workbench` and `apps/browser`. `make native-test` runs `make -C native/darwin test`, `go test` for `packages/host/wailsv3`, and `cargo test -p soksak-host-tauriv2`; the host tests cover file storage, the sidecar relay, the endpoint, and document-region ownership and cleanup. `webview_geometry_test` also checks the scale of a document region, and `document_view_test` checks its navigation, state reports, placement, and isolation.

`window-release.test.mjs` sets `projectOpening` to `windows`, opens and closes a project window four times, and requires `diagnostics.native.objects` with `equal` set to the counts before the first open to succeed after the last close; each open window must raise every count, so the counts measure the window. The check also reads each open window's `host.window` `pageProcess` and, after the counts return, requires `diagnostics.process.exit` to report that every one of those web content processes has exited. The request compares after each event that it posts has been handled, and posts one each time the main run loop is about to wait, because AppKit releases the objects of a closed window when it drains the autorelease pool of an event iteration, keeps a window that was on screen until its close animation ends, and releases an object autoreleased during a drain at the next drain; the check therefore needs no user input and no timer. The native `window_objects_test` closes a window that was on screen and checks the counts and that reading in the library: an autoreleased window keeps its objects until its event iteration ends, the counts return to their starting values after the close animation, and counts that do not reach the expected values are given as not reached when the bound ends.

Record at the window’s backing-pixel resolution. Point-sized downsampling blends half-point lines with adjacent pixels and prevents exact color measurement. Frame files retain width, height, row stride and all seven metadata values in the 80-byte header defined by the [endpoint contract](../spec/endpoint.md#diagnostic-builds). The single LZ4 block restores all BGRA bytes and row padding; readers reject the retired raw format, partial or extra blocks, wrong decoded sizes and checksum failures. Do not treat a missing or partial recording as a pass.

`geometry.test.mjs` compares native frames (`host.window`), DOM slots (`core.surfaces`), and surface document and viewport sizes (`core.surface.document`) after window resizing. It checks the owner of the final device pixel with `host.hit`, presses and releases there with `input.pointer`, and checks the trusted event coordinates in `core.surface.input`. Scale factors and scale changes do not depend on the connected displays: `native/darwin/tests/webview_geometry_test.m` sets the window's backing scale to 2, 1, and 2 again and checks half-point surface heights, document coverage of the last device-pixel row, and native input in that row. No window check requires a particular display.

The fast terminal divider check requires four complete round trips and zero white pixels in the terminal card. The three-terminal check requires five uninterrupted complete round trips, three measurable terminal regions in every frame, no DOM-border intrusion, and unchanged first-glyph dimensions and pixel count. A stationary screen or a recording missing any requested round trip fails. Each diagnostic recording is a bounded burst of at most 600 frames; reaching that bound is an explicit incomplete-recording error, not silent frame loss. The terminal project-return check repeats five-trip gestures and library returns three times and checks all three native rasters immediately after each return. The library workflow also rejects a presentation error that was reported and later cleared. These composition gestures use the page-driven diagnostic route described in the [endpoint contract](../spec/endpoint.md#diagnostic-builds); they do not validate OS button state.

When preserving a failed application while inspecting a new build, use separate disposable configuration directories. ScreenCaptureKit can identify Tauri capture clients by executable path: simultaneous processes at that same path caused replayd to cancel their capture connections. Run a byte-identical copy and its sidecars from a separate inspection directory, verify its hash, and explicitly set `APPS.tauriv2.binary` to that path before opening the harness connection. Do not disable the executable check or restart the preserved application. Remove inspection recordings when each check ends.

Copy and compare hashes for the application after each build, and reinstall the plugins with `make install-plugins` into the configuration directory the copy uses; a configuration that keeps earlier plugin and sidecar files does not test the current implementation. A live persistent service must also match the implementation being tested; preserve it only for an explicit reconnect/update test. Record a mixed-build run as invalid for validating the current implementation, not as a current-code pass or failure.

The three-terminal hide check first waits for all three native snapshots, then compares each native frame and snapshot after entering the library. Hidden surfaces must retain both. Project-return checks inspect all three current rasters immediately after the return command; an extra presentation wait must not hide an incomplete return.

The fixture must present before the harness reloads its main document. A timeout fails setup and preserves that state instead of letting a reload clear the open transaction. The harness also collects presentation-error log notifications, because the latest verification status alone may no longer contain an earlier error.

The project-return process check reads the tested configuration's terminal service endpoint and the OS process table. It requires exactly one service for that configuration, one direct shell child per open terminal (including hidden tabs), no PTY helper child, and no zombie child. Returning from the library must preserve the exact service and shell PIDs, not merely their count. Other running applications are excluded by configuration identity. Parser unit checks do not validate service lifecycle; the rebuilt-host run remains required.

## Page memory

`make page-memory APP=wailsv3|tauriv2 CONFIG=DIR [BUILD=release|debug] [MINUTES=60] [RELOADS=20]` measures the main page process of a running application, by default a release build: it reads the window's `pageProcess` from `host.window` through the bundle's `sok`, records the physical footprint that `footprint` reports at start, after `MINUTES` minutes without input, and after `RELOADS` runs of `host.window.reload`, and prints one JSON line `{phase, elapsedMs, pageProcess, footprint}` for each. The idle phase waits for a duration because no event marks idleness. A reload opens the page in a new process, so the last line also records `startProcessAlive`, whether the page process of the start still exists. The measurement does not judge the values; it fails when the window has no page process. Start the application with a disposable configuration directory (`open -g -n <bundle> --args --config-dir DIR`) so the measurement does not use an interactive configuration.

## Browser example check

`make browser-example-check` runs `apps/browser/check/served.test.mjs` against the staged browser example. The check serves `apps/browser/build` from a loopback HTTP server of its own, starts the installed Google Chrome headless with a disposable profile (`CHROME` names another executable), and drives it through the Chrome DevTools protocol over Node's built-in `WebSocket`, so no browser automation package is a dependency. It opens a project the way a person does in that application: it presses `core.library.add`, types a folder path into `core.library.form.parent`, and presses `core.library.form.submit`, because the browser example registers a typed path and needs no folder picker ([projects](../spec/projects.md)). It waits until the page shows the workspace and all sidebar sections are mounted, and fails on any uncaught exception, `console.error`, or browser log entry of level `error`, reporting each one. A second case serves a plugin list without `terminal` in place of the staged `installed-plugins.json`, opens a project the same way, and checks that the `terminal` tabs of the environment open as placeholder cards with the reason `host` in `core.surfaces` and their placeholder text, without an error ([plugins that are not loaded](../spec/plugins.md#plugins-that-are-not-loaded)). A missing Chrome fails the check; it does not skip. The check stops Chrome, waits for it to exit, removes its profile, and stops the server when it ends.

## Manual acceptance

The terminal keyboard check uses native clicks and keys in three visible terminals per host. It verifies characters, Backspace, Ctrl+U, Enter, exactly-once command output, and unchanged screens in the other terminals. It reads the current screen once and waits for `terminal.screen` notifications; `terminal.input` is not used to validate keyboard delivery. Run this check separately from composition recordings so an input pass cannot substitute for a drag result.

- Add two existing project folders, reorder the projects, close the application, and restart it. The library lists the saved projects without starting their surfaces or shells. Select a project and confirm that its layout and settings restore in the same OS window.
- In New Project, cancel the parent-folder chooser once, then select a directory. Creation failure must preserve existing directories. Open the Dock menu and select New Window, including after closing all windows. Return from the workspace to the project list and back; layout and shells must remain available.
- Select Global and Project from the General pane tabs, change a value in each scope, and reset a project override. Confirm inheritance in both windows and scope preservation after changing categories. The opening mode must appear only in Global. Every library screen, including one opened from a workspace, must apply common settings and show only the Global tab. Library edits and the title-bar mode button must leave project overrides unchanged. Returning to the workspace must restore its overrides and both scope tabs.

- Open settings over a browser and terminal. Confirm 50% black shading, visible blur, and clear settings content. Background clicks and scrolling must not operate the underlying content.
- Move settings by its header, resize the main window, and use the window manager. Settings must stay inside the main window. Only × closes settings; background clicks and Escape do not.
- Open add and split pickers. Confirm a transparent background, no blur, and closing by selection, outside click, or Escape.
- Close settings and confirm restored appearance and input. Reload a browser while settings is open and confirm the new document is blurred.
- Record a divider drag and enter/exit fullscreen. Native buttons must remain vertically centered in the first row.

Manual appearance validation confirmed settings blur in both macOS hosts on 2026-09-07. This is manual appearance evidence, separate from automated geometry and input checks. Record new results in [features](../features.md) and [changes](../../CHANGELOG.md); Windows and Linux still require native execution and verification.

## Diagnostics

Debug builds (`make wailsv3-build tauriv2-build`) include the diagnostic methods of the [local endpoint](../spec/endpoint.md): `diagnostics.fixture`, `diagnostics.drag`, `diagnostics.capture.start`, `diagnostics.capture.stop`, `diagnostics.modal.hold`, `diagnostics.modal.held`, `diagnostics.notifications`, and `diagnostics.transcript`. The `soksak` command and the `soksak-mcp` server send the same requests; for example `soksak status core.screen --window main --config-dir DIR`. `soksak dom dispatch NAME --window main --event '{"type":"click"}' --config-dir DIR` dispatches a synthetic event to a declared DOM entry; checks of real input use `input.pointer` and `input.key` instead.

`pnpm -F @soksak/client run bench:application -- --config-dir DIR` measures sequential round trips of a running application on three paths: `windows.list` (host only), `status.get core.screen` (relayed to the main page), and `status.get core.surface.document` with a surface (relayed through the main page to a surface page). `bench` measures the transports alone. On 2026-09-17 (M3 Pro, debug builds, 2000 requests per path, two runs) the p50 values were: Wails host 142–157µs, page 1.5–1.7ms, surface 4.4–4.5ms; Tauri host 443µs, page 2.6–2.7ms, surface 1.4–7.5ms.

The shared library has two native input suites. Run both when changing the shared input code:

```sh
make -C native/darwin test
make -C native/darwin test-activation
```

`test` runs `input_inject_test` in a window of an inactive application. It checks presses, drags, scroll, keys, focus, and the inactive result for a move without a button, and it does not activate the application. Every native test links `tests/support/no_activation.m`, which fails the test at exit when its process is active; a test that activates the application for `test-activation` calls `sp_test_declare_activation` first.

`test-activation` activates the test application and therefore takes the keyboard focus. Its windows set `ignoresMouseEvents`, but AppKit still delivers a movement to the tracking areas the real pointer is in. The overlapping-webview check therefore places its window away from the pointer and fails with that reason if the pointer enters the window. It runs `input_activate_test` (hover after activation), the overlapping-webview check `webview_input_test` (first as the baseline run and then as the registered-input run), `document_view_test --activation` (an OS event-queue click and key into a document region), and `image_region_ime_test` (Korean 2-Set composition in an image region and an AppKit text view control; it selects Korean 2-Set during the run and restores the previous input source).

Activation-tier window checks live in `e2e/activation/` and run only with `pnpm -F @soksak/e2e verify:activation` in a run the user approves; `pnpm -F @soksak/e2e verify` does not include them. They may activate the application with `input.pointer` `activate: true` (`make e2e-check` rejects it elsewhere) and change the keyboard input source with `diagnostics.input.source`, restoring the previous source in cleanup. `ime.test.mjs` types ABC `ddd`, switches to Korean 2-Set, types `g k s r m f`, Space, and Enter, and requires the preedit sequence `ㅎ`, `하`, `한`, `ㄱ`, `그`, `글`, ` ` and the committed command `ddd한글` exactly once on the screen. `marked-text.test.mjs` selects Japanese (Romaji), types `n i h o n n`, which the input method shows as marked text, switches to ABC to end the composition, and requires the last marked text to reach the PTY exactly once with no preedit after the commit; it requires the `com.apple.inputmethod.Kotoeri.RomajiTyping.Japanese` input source to be enabled. `terminal-keyboard.test.mjs` types, edits, and executes commands with native keys in three terminals and after a browser tab, a resize, a modal, a project return, and a second project window, selecting ABC after each focus because an input context can restore its own input source; a second check opens a second project window, which becomes the key window, sends a character key to the first window's focused terminal, and requires the terminal to report that the input method did not answer. Before activating the application, each check moves its window beside the system pointer when the window covers it (`keepPointerOutside` in `packages/window-check/app.mjs`), because the key window receives the pointer location as a move; when the window fits on neither side, it first narrows the window to the wider side. Start the application alone before the run, because the check takes the keyboard focus.

Real-input window checks live in `e2e/real/` and run only with `pnpm -F @soksak/e2e verify:real` in a run the user approves; the default run does not include them. A window check that makes the application active, such as a real-input check, full screen, or a new project window, makes the previously active application active again when it ends through the harness, because the default window checks measure an inactive application: an active window receives AppKit cursor updates when its layout changes and passes the system pointer location to the page, which mixes with a synthetic `diagnostics.drag`. The harness therefore fails a drag with an explicit error when the application is active. Before the first check of a run, the declared entry points (`verify`, `verify:activation`, `verify:real`, `verify:terminal-sidebar-current`, and `repeat`) run `e2e/setup.mjs`, which ends with the harness's `session.mjs`, once as the node:test global setup: it reads the endpoint of each tested host whose executable exists and refuses the run once, before any check starts, when the frontmost application is one of those hosts, because every synthetic pointer measurement of the run would then measure an active application. The refusal names the frontmost application by pid, name, and bundle identifier, and the tested hosts with their pids; an endpoint that cannot be read also fails the run there. After each check the harness compares the frontmost application with the baseline captured at the first check of the test file, reactivates the baseline when the checked host is frontmost, reports the frontmost application before the check, after it and after restoring, and fails the check when a host opened by the test file is still frontmost. Checks never activate other applications, so another frontmost application is a change the user made; the harness reports it and does not take it away. The real-input checks post HID events with `CGEventPost` through `e2e/real/hid.mjs`, which needs Accessibility permission for the terminal that runs them and fails at once without it. They take the pointer and keyboard, activate the application, and require the application's window to be frontmost at every posted point, because an event posted over another window goes to that window. They set the flags of every posted event, because an event created without a source inherits HID-system modifier flags (V5-25-1). `input.test.mjs` requires the system pointer to reach the posted point and a posted click to give a terminal region native focus.

`host.window.reload` terminates the main WebContent process before it reloads the page. A page call that the terminated process left running still completes on the host, and when the new page requests its [start document](../spec/native-host.md#page-start) the host ends the previous page's forwarded `status.next` requests; Wails v3 then logs `Unable to write json payload. Please report this to the Wails team! error=request has been stopped` once for each reply it cannot deliver, because it runs binding calls without the request's cancellation (`context.WithoutCancel`). In window checks this is three lines per reload, one for each `status.next` forward of the replaced page; such a line is a reply to a page that no longer exists, not a lost reply.

`sok capture --window main --config-dir DIR` writes a still PNG of a running diagnostic build's window without focusing it and prints the result with its path, for looking at the result during development. Remove the printed `still-*` directory after viewing; numeric checks use recording frames instead.

The tracked `capture-still.test.mjs` verifies the still-file artifact: device-pixel dimensions, opacity and expected border pixels at declared native coordinates. `png.test.mjs` owns PNG alpha and invalid-coordinate/decoded-length checks. This verifies output integrity; gesture completeness and presentation timing continue to use recorded frames. A capture of a native modal waits for `host.window` to report `modal.shown` and then for `host.window.presented`: a page status such as `core.settings-modal` `open` reports the main page's state, which precedes the modal webview's first render, so a still taken after it can show the window without the modal. `modal.test.mjs` checks that every recorded frame from the presented time on shows the settings scrim.

`SOKSAK_PERFORMANCE_TRACE=1` enables the performance trace in every check preparation (`fresh()`), and a terminal-readiness failure then reports the surface registration timeline written since that preparation started; any other value is rejected. The trace changes timing, so a failure that disappears with it still needs an untraced reproduction.

`SOKSAK_APP=<wailsv3|tauriv2> pnpm -F @soksak/e2e run verify:shutdown` checks the declared quit lifecycle (`command.run` of `host.quit`) on the one running host that `SOKSAK_APP` selects; the host ends, so it runs alone and the host is started again afterwards (`e2e/normal-shutdown.mjs`).

`pnpm -F @soksak/e2e run repeat --file <file> --name <test name pattern> --count <n>` runs one window check repeatedly against the running applications (`SOKSAK_APP` selects one host), each run in a new `node:test` process; it stops at the first failed run, prints that run's output, and fails when no test ran. `make -C native/darwin repeat TEST=<name>_test COUNT=<n>` runs one default test repeatedly and `make -C native/darwin repeat-suite COUNT=<n>` runs the default suite repeatedly; each stops at the first failure and reports the run number and system load. `make rust-tests-alone PACKAGE=<package> [MANIFEST=<Cargo.toml>]` runs each test of a Rust package alone in a new process and reports the first test that fails alone; a test that passes only after another test has run depends on shared state or timing. `make rust-repeat PACKAGE=<package> COUNT=<n> [TEST=<name>] [MANIFEST=<Cargo.toml>]` runs the tests of a Rust package, or the one test named `TEST`, `COUNT` times in a row; it stops at the first failed run and reports its output, the run number, and the system load, and fails when `TEST` names no test. `make go-repeat PACKAGE=<go package path> COUNT=<n> [TEST=<regexp>]` does the same for Go tests, with `TEST` as the `go test -run` pattern. `make node-repeat FILE=<test file> NAME=<test name pattern> COUNT=<n>` runs the matching tests of a Node test file from the repository root the same way and fails when no test matched.

The baseline expects duplicate pointer movement in overlapping DOMs. The registered-input run requires exclusive pointer tracking, retained keyboard input, and cleanup after hiding or removing the overlay. Neither run tests delayed cursor responses.
