# Screen hash decision

[한국어](screen-hash-decision.ko.md)

This proposal decides F236-9: which parts of the screen hash and its replay contract core keeps, and which parts are the engine rules of the terminal sidecar or the page parser of the terminal plugin that move out of core. It is removed after its approved content is in [replay](../spec/replay.md) and the decision record is in the changelog.

## Scope

Decide four questions.

1. Does core keep the byte definition of the screen hash, the generic screen message format, and the golden vectors that every implementation reproduces?
2. Which parts of the drawn-screen rules (how the cursor, the blank cells and the selection highlight of a drawn screen are computed) are generic, and which are engine behaviour of the terminal sidecar?
3. Where does the page-side parser `screenFromMessage` belong?
4. Which core checks prove decisions 1 to 3, and how is each removal gated on an observable check?

- A *core objection* is a sentence or code in core that (a) names the terminal, a plugin or a sidecar as the owner or producer of a definition, (b) encodes a behaviour that only the terminal sidecar or the terminal page implements, or (c) defines the same thing in two places without a sync check that core can run.
- *Out of scope*: wording that no implementation resolves differently; cases every implementation resolves the same way; details the unit tests settle.

## Decision

1. **Core keeps the byte definition, the generic screen message format, and all vectors.** `docs/spec/replay.md` keeps "Screen hash", "Golden vectors", and the input-kind table in "Records" (lines 11 to 18). The vector file `packages/log-contract/fixtures/replay/screen-hash.json` keeps all its vectors, including the three that show a drawn screen (`scrolled viewport with the cursor outside it`, `selected cells with the highlight colors`, `the same text under another theme`), because each is a screen in the hash form and core's hash test runs it. The generic member table of the screen message (`event`, `sequence`, `segment`, `rows`, `cols`, `cursor`, `cells`, with the cell members) moves from `terminal-runtime.md` "Screen message" into `replay.md` under a new heading "### Hashed members"; the table names no plugin.
2. **Core keeps `screenBytes` and `screenHash`, and their import entry.** `packages/plugin-api/screen-hash.js` keeps `screenBytes` and `screenHash`, with line 1 changed to "The hash of a screen, a grid of cells with a cursor". The entry `@soksak/plugin-api/screen-hash` in `PAGE_IMPORTS` (F2) stays. The terminal page imports `screenHash` from it (F4), and the installed plugin's version is independent of the core version (F9), so the entry cannot be removed while any installed plugin imports it. Core's tests `packages/log-contract/test/screen-hash.test.mjs` and `replay-vectors-named.test.mjs` run these functions against the vectors in core.
3. **The drawn-screen engine rules move to the sidecar; generic rules stay.** The sentences of "View state" that describe how the terminal engine computes a drawn screen move to the sidecar's specification in `sidecars/vt/docs/spec/`: the selection geometry and its reactions (lines 74 to 80, the selection bullet), the viewport moves and their effect on the offset (the viewport bullet), the theme's effect on trimming and palette (the theme bullet's trimming sentence), the cursor rule that `visible` is `false` outside the viewport (line 82), the lock and the engine's scrollback and default theme (lines 81 and 84), and the subsection "Decision" (89 to 98). `replay.md` keeps one generic sentence under "### Hashed members": the hashed cells and the cursor are the ones the sidecar reports for the drawn screen, and each sidecar states in its own specification how it computes them. Line 97 ("The golden vectors that fix the drawn screen under a scroll, a selection and another theme are ...") stays with "Golden vectors", because the vectors stay.
4. **The page-side parser moves to the terminal plugin.** `screenFromMessage` (`screen-hash.js` lines 104 to 134), the refusal list of `packages/log-contract/fixtures/replay/screen-message.json` and its runner `packages/log-contract/test/screen-message.test.mjs`, and the `screenFromMessage` tests of `packages/plugin-api/test/screen-hash.test.mjs` move to the terminal plugin repository. The plugin's copy imports `screenBytes` (and so the byte definition) from `@soksak/plugin-api/screen-hash`, which its declared dependency already provides; the plugin does not copy `screenBytes`. The paragraph of `terminal-runtime.md` (line 124) that specifies `screenFromMessage` and its refusal list moves to the plugin's specification. Core then keeps no refusal case of the parser.
5. **Sync and gate.** Core's vector test is the reference for the byte definition. The owners that hold vectors run them in their own tests against a copy pinned to a core tag (AGENTS: shared contract cases run in the owning package; core may not read another repository's files). Decision 4's removal is gated as follows: core keeps `screenFromMessage` until its end-to-end window check `e2e/terminal-replay.test.mjs` passes with the terminal plugin's copy installed through the registry (the AGENTS exception for installation-based window checks), and a checklist sub-item in `docs/features.md` names the plugin release tag that holds the copy and the gate. The sub-item is written in the implementation step. Core's record is then a passing check, not a promise.
6. **The replay input validator stays in core until a sidecar check replaces it.** `replayInputProblem` and `replaySessionProblem` (`packages/log-contract/index.js`), `packages/log-contract/fixtures/replay/inputs.json`, the sidecar copy `replay-inputs.json` (F5), and the `sok` copies (`packages/sok/tauriv2/src/replay_inputs.rs`, `packages/sok/wailsv3/src/replay_inputs.go`) hold the terminal engine's bounds (selection against the grid, theme colors). That is a core objection under (b). Removal needs a contract change first: "### Replay executable" in `replay.md` gets a new sentence that the executable refuses every input of `inputs.json` that the validator refuses, with the same error text. The requirement applies to sidecar releases that carry it. Core keeps the validator, and the command keeps `replaySessionProblem` (line 85 of `replay.md`), until an installed sidecar release passes the invalid `inputs.json` cases through its executable in an end-to-end window check. The sidecar's copy and `sok`'s copies are then removed in the same change. The sub-item in `docs/features.md` names the owner (the sidecar repository), the release, and the gate. This decision adds the requirement and the sub-item; it does not remove the validator.
7. **The vocabulary changes.** `packages/plugin-api/terms.json` "replay" (line 151) becomes "Rebuilding the screen of a session from its stored inputs with the replay executable of its sidecar, to compare the stored hashes of the screens (docs/spec/replay.md)". "screen hash" (line 170) becomes "The SHA-256 of the canonical bytes of a screen, a grid of cells with a cursor, as docs/spec/replay.md defines it". `replay.md` line 101 "it holds the terminal engine" becomes "it holds the replay engine of the sidecar".
8. **The application-level divergence test stays in core.** `e2e/terminal-replay.test.mjs` runs the installed plugins through the registry. AGENTS.md line 33 states: "Window checks are end-to-end checks of the application with the plugins its environment installs, not package tests, and this rule does not apply to them." The test's assertions depend on terminal-plugin behaviour (the replay of a terminal session with a scroll, a selection and a theme), which is why its removal is gated in decision 5, not decided here. Its parity entries (F160.25 and F160.35) stay.

## Split decision 9-1

This section decides one question: which owner holds the byte definition of a terminal screen hash. That is `screenBytes`, `screenHash`, the golden vectors, the screen message form that the hash is computed from, and the rule that every implementation reproduces them. It does not decide the move list (F236-9-2) or the core-side changes (F236-9-3). It supersedes decisions 1 and 2 of the proposal above for the byte definition; the rest of the proposal stands as history.

Each fact below was checked at HEAD of its repository (`git show HEAD:<path>`), not in a working copy. `packages/`, `docs/`, `scripts/` and `e2e/` are core. `../plugins/terminal` (the terminal plugin), `../sidecars/vt` (the terminal sidecar) and `../registry` (the public registry) are sibling repositories. The registry's tracked source is `plugins/terminal.json`; its `index.json` is generated and not tracked.

### Candidates

- **C1, core.** Core keeps the definition, the vectors and the message form.
- **C2, a declared contract repository.** A separate repository holds the definition, the vectors and the message form. Its consumers declare it in their manifests; core does not know it.
- **C3, the terminal plugin.** The plugin holds the definition and the sidecar follows it.

The tracked registry source `../registry/plugins/terminal.json` lists the terminal versions with their `engines.soksak`: `0.0.3` `^0.0.3`; `0.0.4` to `0.0.10` `*`; `0.0.11` to `0.0.14` `>=0.0.11`. Whether each of these releases imports `@soksak/plugin-api/screen-hash` is verified only for the plugin repository's HEAD (H6); each release must be checked individually for G1. `../registry/revoked.json` revokes only the editor plugin `0.0.1`.
- H11. Versions. The version of a plugin or sidecar has no relation to the core version (`docs/spec/plugins.md` line 42). An installed page does not change when core changes, but its import of `@soksak/plugin-api/screen-hash` resolves against the core that is running. Removing that entry therefore breaks each released page that imports it, and an install of such a release is selected by its `engines.soksak` range (H10).
- H12. The binding rules. `AGENTS.md` line 10: common functionality belongs to core so that plugins do not reimplement it. `AGENTS.md` line 32: core, plugins and sidecars do not name each other in code or tests. `AGENTS.md` line 33: core, plugins, sidecars, kits, specifications and contracts are separate repository boundaries; they exchange only the declared wire contract and exposed commands; a relation between packages is declared only as `dependencies` of a manifest; a test does not read another package's paths. `docs/plans/plugin-processes-handoff.md` "No coupling" (lines 62 to 64): a plugin feature never moves into core; common functions belong to core.
- H13. Core spec generic wording. `docs/spec/persistent-services.md` line 66 says "A screen-producing sidecar of any kind follows the same rule", and `docs/spec/replay.md` line 5 says a screen-producing sidecar stores "a hash of each screen it produces". The producers in the repositories are the terminal sidecar only (H4), and the cell model is terminal-shaped (wide characters, SGR flags, cursor shape).
- H14. Uses of the hash in core: `e2e/terminal-replay.test.mjs` (H8), the `sok` format checks (H8), and the core tests of H3. Core's own log contract (`packages/log-contract`) holds the generic event and replay formats that the spec defines; the terminal screen definition is the only item among them that is terminal-shaped (H13).

### Comparison

- **C1 conflicts with the rule.** `AGENTS.md` line 10 places common functions in core, and core holds generic formats such as the event log and the frame record (H14). The byte definition is not generic: it is the wire of one feature, a terminal screen (H13), and the rule places a feature in its plugin and never in core (H12). Its two producers are the terminal page and the terminal sidecar (H4, H6), so the function is not common to several features. The contract boundary of `AGENTS.md` line 33 also places a feature's exchanged wire in a contract repository, not in core. C1 therefore conflicts with the rule. The sync problem below is the same under C2, so it does not favour C1.
- **C2 satisfies the rule, with one declared gap.** A contract is a separate repository boundary (H12). The page declares it as a package dependency of its plugin (H7). The sidecar declares it as a `devDependencies` entry of its `package.json`, the same form that `sidecars/vt/package.json` line 9 already uses for `@soksak/plugin-api` (H7), and its `node --test` check imports the contract's vectors through that declared package and compares them with its Rust fixture copy (Sync). Core knows neither: after the move core has no import of the contract and no registry entry for it. The costs are recorded and none is a rule violation: one new repository, a release tag, the pins of two repositories, the Rust fixture copy and its comparison (Sync), and the transition gaps of F236-9-2.
- **C3 needs an undeclared direction.** The sidecar would follow the plugin, so the sidecar would depend on the plugin. No manifest declares that (H7), and the rule permits a relation only as a declared manifest dependency (H12). C3 is rejected.
- **Sync (all candidates).** The Rust implementation needs the vectors. Under C2 the sidecar holds a vendored copy of the vectors in its fixture folder, pinned to a contract tag; its Rust tests read only that copy, which is the existing pattern of H5. The declared relation is the `devDependencies` entry (C2 above): a `node --test` check in the sidecar imports the contract package's vector export and fails when the Rust fixture copy differs from it. A Rust test that reads the contract's path is forbidden (H12). The Rust copy is therefore checked by a declared dependency, not by a path or a README claim. Until the core copies are removed, core's copies, the contract's copy and the sidecar's copies exist side by side, and no check that core can run compares them; drift is detected only by `e2e/terminal-replay.test.mjs` through the installed pair (H8). This gap is recorded and closes with the gate.

### Decision 9-1

The owner of the byte definition is **C2, a declared contract repository**. The screen contract repository (its folder and package name are set when the repository is created; this document calls it the screen contract) holds:

1. the byte definition: `screenBytes` and `screenHash`, their JavaScript reference implementation, and the magic `SKSCR1`;
2. the golden vectors and the refusal messages, with the tests that run them in that repository;
3. the screen message form and its validator `screenFromMessage`, because the message is the wire between the sidecar and the page;
4. the text now at `persistent-services.md` lines 51 to 68 and `replay.md` lines 33 to 70 (the sections "Screen hash" and "Golden vectors") that defines these parts.

The terminal page declares the contract as a package dependency of its plugin and bundles the module into its own page files, so the page imports no core entry for the hash. The terminal sidecar declares the contract in its `devDependencies` and keeps a vendored copy of the vectors pinned to a contract tag (Sync). Core keeps no import of, and no registry entry for, the contract.

Format rule. A change of the bytes changes the magic (`SKSCR1`, H1 and H4), so it is a new contract tag. A plugin and a sidecar move their pins in the same change. A released terminal page keeps the tag it bundled and keeps working; an installed pair that mixes tags produces a divergence in `e2e/terminal-replay.test.mjs`, which is reported, not accepted.

What C2 does not do. C2 does not make core rule-compliant overall. Core keeps terminal content after this decision: the `sok` segment rule of H9 and its layer name, the terminal names in `packages/plugin-api/terms.json` (lines 150 and 169), the producer rules of "View state" (`replay.md` lines 74 to 98), and the replay input validator (below). Each is handled by F236-9-2 or F236-9-3, not by this decision.

### Gate G1 (summarized; F236-9-2 states it in full)

Removal of the first three bullets above happens in a core release only when (a) the contract repository has a tag that holds the bytes, the vectors and the message form; (b) a terminal plugin release that bundles that tag is published; and (c) no served terminal release that imports core's entry remains installable on the core release that drops it. Under H10 the check is per release: each release from `0.0.3` to the latest, whose import of the entry is verified, is either revoked (`../registry/revoked.json`) or its `engines.soksak` range excludes the removing core release. Condition (c) is not met today: the registry serves releases with `engines.soksak` `*` (`0.0.4` to `0.0.10`) and `>=0.0.11` (`0.0.11` to `0.0.14`), and at least the `0.0.11`-and-later line imports the entry (H6, H10); the imports of the earlier releases are unverified. Conditions (a) and (b) are not met today either: no contract repository exists (H8 and H10 show no contract entry), and no terminal release bundles a contract tag. Until the gate holds, core keeps its copies and its entry, and the Sync gap stays recorded.
