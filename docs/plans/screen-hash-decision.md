# Screen hash decision

[한국어](screen-hash-decision.ko.md)

This proposal decides F236-9: which parts of the screen hash and its replay contract core keeps, and which parts are the engine rules of the terminal sidecar or the page parser of the terminal plugin that move out of core. It is removed after its approved content is in [replay](../spec/replay.md) and the decision record is in the changelog.

## Scope

Decide four questions.

1. Does core keep the byte definition of the screen hash, the generic screen message format, and the golden vectors that every implementation reproduces?
2. Which parts of the drawn-screen rules (how the cursor, the blank cells and the selection highlight of a drawn screen are computed) are generic, and which are engine behaviour of the terminal sidecar?
3. Where does the page-side parser `screenFromMessage` belong?
4. Which core checks prove decisions 1 to 3, and how is each removal gated on an observable check?

- A *core objection* is a sentence or code in core that (a) names the terminal, a plugin or a sidecar as the owner or producer of a definition, (b) encodes a behaviour that only the terminal sidecar or the terminal page implements, or (c) defines the same thing in two places without a sync check that core can run.
- *Out of scope*: wording that no implementation resolves differently; cases every implementation resolves the same way; details the unit tests settle.

## Decision

1. **Core keeps the byte definition, the generic screen message format, and all vectors.** `docs/spec/replay.md` keeps "Screen hash", "Golden vectors", and the input-kind table in "Records" (lines 11 to 18). The vector file `packages/log-contract/fixtures/replay/screen-hash.json` keeps all its vectors, including the three that show a drawn screen (`scrolled viewport with the cursor outside it`, `selected cells with the highlight colors`, `the same text under another theme`), because each is a screen in the hash form and core's hash test runs it. The generic member table of the screen message (`event`, `sequence`, `segment`, `rows`, `cols`, `cursor`, `cells`, with the cell members) moves from `terminal-runtime.md` "Screen message" into `replay.md` under a new heading "### Hashed members"; the table names no plugin.
2. **Core keeps `screenBytes` and `screenHash`, and their import entry.** `packages/plugin-api/screen-hash.js` keeps `screenBytes` and `screenHash`, with line 1 changed to "The hash of a screen, a grid of cells with a cursor". The entry `@soksak/plugin-api/screen-hash` in `PAGE_IMPORTS` (F2) stays. The terminal page imports `screenHash` from it (F4), and the installed plugin's version is independent of the core version (F9), so the entry cannot be removed while any installed plugin imports it. Core's tests `packages/log-contract/test/screen-hash.test.mjs` and `replay-vectors-named.test.mjs` run these functions against the vectors in core.
3. **The drawn-screen engine rules move to the sidecar; generic rules stay.** The sentences of "View state" that describe how the terminal engine computes a drawn screen move to the sidecar's specification in `sidecars/vt/docs/spec/`: the selection geometry and its reactions (lines 74 to 80, the selection bullet), the viewport moves and their effect on the offset (the viewport bullet), the theme's effect on trimming and palette (the theme bullet's trimming sentence), the cursor rule that `visible` is `false` outside the viewport (line 82), the lock and the engine's scrollback and default theme (lines 81 and 84), and the subsection "Decision" (89 to 98). `replay.md` keeps one generic sentence under "### Hashed members": the hashed cells and the cursor are the ones the sidecar reports for the drawn screen, and each sidecar states in its own specification how it computes them. Line 97 ("The golden vectors that fix the drawn screen under a scroll, a selection and another theme are ...") stays with "Golden vectors", because the vectors stay.
4. **The page-side parser moves to the terminal plugin.** `screenFromMessage` (`screen-hash.js` lines 104 to 134), the refusal list of `packages/log-contract/fixtures/replay/screen-message.json` and its runner `packages/log-contract/test/screen-message.test.mjs`, and the `screenFromMessage` tests of `packages/plugin-api/test/screen-hash.test.mjs` move to the terminal plugin repository. The plugin's copy imports `screenBytes` (and so the byte definition) from `@soksak/plugin-api/screen-hash`, which its declared dependency already provides; the plugin does not copy `screenBytes`. The paragraph of `terminal-runtime.md` (line 124) that specifies `screenFromMessage` and its refusal list moves to the plugin's specification. Core then keeps no refusal case of the parser.
5. **Sync and gate.** Core's vector test is the reference for the byte definition. The owners that hold vectors run them in their own tests against a copy pinned to a core tag (AGENTS: shared contract cases run in the owning package; core may not read another repository's files). Decision 4's removal is gated as follows: core keeps `screenFromMessage` until its end-to-end window check `e2e/terminal-replay.test.mjs` passes with the terminal plugin's copy installed through the registry (the AGENTS exception for installation-based window checks), and a checklist sub-item in `docs/features.md` names the plugin release tag that holds the copy and the gate. The sub-item is written in the implementation step. Core's record is then a passing check, not a promise.
6. **The replay input validator stays in core until a sidecar check replaces it.** `replayInputProblem` and `replaySessionProblem` (`packages/log-contract/index.js`), `packages/log-contract/fixtures/replay/inputs.json`, the sidecar copy `replay-inputs.json` (F5), and the `sok` copies (`packages/sok/tauriv2/src/replay_inputs.rs`, `packages/sok/wailsv3/src/replay_inputs.go`) hold the terminal engine's bounds (selection against the grid, theme colors). That is a core objection under (b). Removal needs a contract change first: "### Replay executable" in `replay.md` gets a new sentence that the executable refuses every input of `inputs.json` that the validator refuses, with the same error text. The requirement applies to sidecar releases that carry it. Core keeps the validator, and the command keeps `replaySessionProblem` (line 85 of `replay.md`), until an installed sidecar release passes the invalid `inputs.json` cases through its executable in an end-to-end window check. The sidecar's copy and `sok`'s copies are then removed in the same change. The sub-item in `docs/features.md` names the owner (the sidecar repository), the release, and the gate. This decision adds the requirement and the sub-item; it does not remove the validator.
7. **The vocabulary changes.** `packages/plugin-api/terms.json` "replay" (line 151) becomes "Rebuilding the screen of a session from its stored inputs with the replay executable of its sidecar, to compare the stored hashes of the screens (docs/spec/replay.md)". "screen hash" (line 170) becomes "The SHA-256 of the canonical bytes of a screen, a grid of cells with a cursor, as docs/spec/replay.md defines it". `replay.md` line 101 "it holds the terminal engine" becomes "it holds the replay engine of the sidecar".
8. **The application-level divergence test stays in core.** `e2e/terminal-replay.test.mjs` runs the installed plugins through the registry. AGENTS.md line 33 states: "Window checks are end-to-end checks of the application with the plugins its environment installs, not package tests, and this rule does not apply to them." The test's assertions depend on terminal-plugin behaviour (the replay of a terminal session with a scroll, a selection and a theme), which is why its removal is gated in decision 5, not decided here. Its parity entries (F160.25 and F160.35) stay.

## Split decision 9-1

This section decides one question: which owner holds the byte definition of a terminal screen hash. That is `screenBytes`, `screenHash`, the golden vectors, the screen message form that the hash is computed from, and the rule that every implementation reproduces them. It does not decide the move list (F236-9-2) or the core-side changes (F236-9-3). It supersedes decisions 1 and 2 of the proposal above for the byte definition; the rest of the proposal stands as history.

Each fact below was checked at HEAD of its repository (`git show HEAD:<path>`), not in a working copy. `packages/`, `docs/`, `scripts/` and `e2e/` are core. `../plugins/terminal` (the terminal plugin), `../sidecars/vt` (the terminal sidecar) and `../registry` (the public registry) are sibling repositories. The registry's tracked source is `plugins/terminal.json`; its `index.json` is generated and not tracked.

### Candidates

- **C1, core.** Core keeps the definition, the vectors and the message form.
- **C2, a declared contract repository.** A separate repository publishes the definition, the vectors and the message form in two languages: an npm package and a Rust crate, each passing the same vectors inside the contract repository. The consumers declare it in their manifests; core does not know it.
- **C3, the terminal plugin.** The plugin holds the definition and the sidecar follows it.

### Facts

Line 1 reads "The hash of a terminal screen". The tracked registry source `../registry/plugins/terminal.json` lists 12 terminal versions with their `engines.soksak`: `0.0.3` `^0.0.3`; `0.0.4` to `0.0.10` `*`; `0.0.11` to `0.0.14` `>=0.0.11`. - H11. Versions. The version of a plugin or sidecar has no relation to the core version (`docs/spec/plugins.md` line 42). An installed page does not change when core changes, but its import of `@soksak/plugin-api/screen-hash` resolves against the core that is running. Removing that entry therefore breaks each installed page that imports it, whether or not the release is still in the registry index (H10).
- H12. The binding rules. `AGENTS.md` line 34: common functionality belongs to core so plugins do not reimplement it, and plugin functionality does not move into core. `AGENTS.md` line 32: core, plugins and sidecars do not name each other in code or tests. `AGENTS.md` line 33: core, plugins, sidecars, kits, specifications and contracts are separate repository boundaries; they exchange only the declared wire contract and exposed commands; a relation between packages is declared only as `dependencies` of a manifest; a test does not read another package's paths. `docs/plans/plugin-processes-handoff.md` "No coupling" (lines 62 to 65): packages exchange only the wire of a contract; a test of A that reads the paths or real names of B is forbidden.

### Comparison

- **C1 conflicts with the rule.** The decisive ground is that core is not a party to the exchange. The byte definition is the wire between two packages of one feature, the sidecar and the page (H4, H6, H13), and the rule keeps a feature's content out of core (H12, line 34). Core holds generic formats (H14), and the generic formats are not this wire. The commonality of the function is not the ground: the rule's common-function clause concerns functions that plugins would otherwise reimplement, and only the two packages of this feature compute the hash (H4, H6). C1 therefore conflicts with the rule. The sync problem below is the same under C2, so it does not favour C1.
- **C2 satisfies the rule.** The wire between the two packages is exchanged through a declared contract, which is the form `AGENTS.md` line 33 gives for exchange. The contract is a separate repository boundary (H12). It publishes an npm package (`screenBytes`, `screenHash`, `screenFromMessage`, and the vectors) for the page and a Rust crate (the same functions and vectors) for the sidecar. Each implementation passes the vectors inside the contract repository, which is where the shared contract cases run (`plugin-processes-handoff.md` line 65). The consumers declare it as a production dependency: the terminal plugin declares the npm package under `dependencies` (not `devDependencies`), because the module ships in its runtime files; the terminal sidecar declares the crate under `[dependencies]` in `Cargo.toml`. The sidecar keeps the engine that draws the screen and `message_cells`, which builds the message from it (H4); only the hash, the form of the message and the validation move. Core knows neither: after the move core has no import of the contract and no registry entry for it. The costs are recorded and none is a rule violation: one new repository, a release tag, the declarations of two repositories, a new build step in the plugin (below), and the transition gaps of F236-9-2.
- **C3 requires a dependency the rule does not provide.** Under C3 the sidecar's production code would take the hash from a plugin. The rule lets packages exchange the wire of a declared contract (H12); a plugin is not a contract, and the rule does not provide for a sidecar to depend on a plugin's code. No manifest declares that direction (H7), and the plugin's own build cannot depend on the sidecar either. C2 needs only a declaration that the rule already provides, and C3 needs a new form of dependency. C3 is rejected.
- **Plugin copy step (a gap, not a fact of HEAD).** Under C2 the terminal plugin's release gains a step, before `make pack`, that copies the contract's browser module into the plugin's `ui/` at the pinned tag, with the copy listed in `files` (`package.json` lines 16 to 20). The page imports the copy by a relative path. The step is part of F236-9-2's gate; this decision does not claim it exists, and it does not verify what `sok plugin pack` does with `files`.
- **Sync (all candidates).** Drift between the JavaScript and Rust implementations is checked by the shared vectors in the contract repository (C2 above), not by a copy in the sidecar. Until the core copies are removed, core's copies, the contract's copies and the sidecar's existing fixture copies (H5) exist side by side, and no check that core can run compares them; drift is detected only by `e2e/terminal-replay.test.mjs` through the installed pair (H8). This gap is recorded and closes with the gate.
- **Installed copies (not solved by the registry).** A revoked release stays installed on a user's machine (H10). If the core entry is removed, an installed page that imports it stops working (H11). No registry action prevents that. Whether released terminal versions keep working after the removal is therefore a product decision: they keep working only while core keeps the entry. The supervisor decision in the section "Supervisor decision" below makes that decision: released terminal versions do not keep working after core removes its copies. The gate cannot make removal safe for installed copies, so G1 (e) requires the decision and its changelog record before any removal.

### Decision 9-1

The owner of the byte definition is **C2, a declared contract repository**. The screen contract repository (its folder and package names are set when the repository is created; this document calls it the screen contract) holds:

1. the byte definition in both languages: `screenBytes` and `screenHash`, their JavaScript and Rust reference implementations, and the magic `SKSCR1`;
2. the golden vectors and the refusal messages, with the tests in the contract repository that run them against both implementations;
3. the screen message form and its validator `screenFromMessage`, in both languages, because the message is the wire between the sidecar and the page;
4. the text now at `persistent-services.md` lines 51 to 68 and `replay.md` lines 33 to 70 (the sections "Screen hash" and "Golden vectors") that defines these parts.

The terminal plugin declares the npm package under `dependencies` and copies its module into `ui/` at release (the gap above). The terminal sidecar declares the Rust crate under `[dependencies]` and calls it for the hash. Core keeps no import of, and no registry entry for, the contract.

Format rule. A change of the bytes changes the magic (`SKSCR1`, H1 and H4), so it is a new contract tag. A plugin and a sidecar move their pins in the same change. An installed pair that mixes tags produces a divergence in `e2e/terminal-replay.test.mjs`, which is reported, not accepted.

What C2 does not do. C2 does not make core rule-compliant overall. Core keeps terminal content after this decision: the `sok` segment rule of H9 and its layer name, the terminal names in `packages/plugin-api/terms.json` (lines 150 and 169), the producer rules of "View state" (`replay.md` lines 74 to 98), and the replay input validator (below). Each is handled by F236-9-2 or F236-9-3, not by this decision.

### Gate G1 (summarized; F236-9-2 states it in full)

Every removal and pointer replacement in the first four core bullets above happens in a core release only when all of the following hold. (a) The contract repository has a tag that publishes the npm package and the crate with the bytes, the vectors and the message form, and both implementations pass the vectors. (b) A terminal plugin release copies that tag's module into `ui/` (listed in its `files`), and a terminal sidecar release depends on that tag's crate for its hash. (c) Every terminal release in `../registry/plugins/terminal.json` that imports core's entry is revoked (`../registry/revoked.json`), checked for every release from `0.0.3` to the latest, including the releases whose import is unverified; a release whose import is unverified blocks the gate until it is checked. The `engines.soksak` range cannot satisfy (c): `0.0.11` to `0.0.14` are `>=0.0.11`, which admits every core release after `0.0.11`, and `0.0.4` to `0.0.10` are `*`. (d) `e2e/terminal-replay.test.mjs` passes with that released plugin and sidecar installed through the registry, as the proposal's decision 5 requires. (e) The product decision in "Installed copies" is made and recorded in the changelog with its user-facing consequence for installed pages. The supervisor made it in "Supervisor decision" below: released terminal versions do not keep working after core removes its copies, and the affected versions are revoked. Revocation alone is not the record, because it does not remove an installed copy (H10, H11). Conditions (a) to (e) are not met today: no contract repository exists (H8 and H10 show no contract entry); no terminal release copies a contract module; (c) fails because at least the `0.0.11`-and-later line imports the entry (H6, H10) and the earlier imports are unchecked; (d) has not been run against such a pair; and (e) has no changelog record yet; the supervisor decision settles which answer applies. Until the gate holds, core keeps its copies, its entry and its pointers, and the Sync gap stays recorded.

### Supervisor decision

The supervisor answered two questions that round 5 left open. Both bind F236-9-2 and F236-9-3, and the round 6 auditors check them as decided.

- **Installed terminal versions.** Question: do installed terminal versions that import from core keep working after core removes its copies? Answer: no. The binding rule is no backward compatibility, no compatibility layers, and removal of old paths, and core and plugins are 0.0.x. Reason: an entry kept for installed copies would be the compatibility layer that the rule forbids. So an installed terminal version that imports from core stops working after the removal and is revoked, and the new terminal release copies the contract package (G1 (b)). Question 5 is therefore no longer an open question. G1 (e) is met by this answer and by the changelog entry of its user-facing consequence.
- **Layer of a page frame.** The layer of a page frame is `page`, the name that `docs/spec/events.json` declares. The name `plugin` in `replay.md` line 22 and in the `sok` layer checks is the wrong name and is changed in F236-9-2. F236-9-3 writes the Red test first.
