# Plugin dialogs

[한국어](plugin-dialogs.ko.md)

This proposal defines how a view of a plugin opens a page of its plugin as a dialog over the whole window (F1129). Its approved content moves into [plugins](../spec/plugins.md), [native surfaces](../spec/native-surfaces.md) and [native modals](../spec/native-modals.md), and this file is removed.

## Problem

A section view draws only inside the body of its section, so a form with many fields is confined to the width of the sidebar. The native modals of the window copy an element of the main page into a modal web view; no plugin page can be the content of a modal, because a plugin page runs in a view surface with its own view channel (`sok-view`), and the copied document of a native modal has no view channel.

## Decision

A dialog is a view surface of the plugin, the dialog surface, whose seat is the content of the window: the whole plane, sidebars included, below the title bar. A window holds at most one dialog, and a dialog and a native modal are never open together.

1. **Declaration.** `plugin.json` declares the pages that the plugin opens as dialogs in the member `dialogs`, a row of the manifest table: `{<name>: {page}}`, where `name` has the form of a command segment and `page` is a path of a page of the plugin, as the `page` of a view composition. A plugin that declares `dialogs` declares `surface` or `sections`, because only a view opens a dialog. The reader refuses a `dialogs` that is not an object, a name of another form, an entry with another member and a page that is not a path inside the plugin, with the errors of the view composition page.
2. **Open.** A view calls `runtime.dialog.open {name, params}`; the SDK sends it for `runtime.dialog(name, params)`, and `params` is a JSON value that the page of the dialog validates. The main page refuses a name that the plugin does not declare (`view call runtime.dialog.open <name> is not a dialog of <plugin>`), an open while a dialog is open (`view call runtime.dialog.open: the window shows the dialog <name> of <plugin>`) and an open while a native modal is shown (`view call runtime.dialog.open: the window shows the modal <id>`). `overlay.show()` refuses a native modal while a dialog is open with `the window shows the dialog <name> of <plugin>`, and the command that opened the modal fails with that error. Otherwise the main page adds the dialog surface to the layout of the window. Its start values are those of a view with `params`, `origin` `{directory: null}`, the `project` of the window, `section` `null`, and the new member `dialog` `{name, opener}`, where `opener` is the surface of the calling view.
3. **Seat and order.** The compositor measures the dialog seat, the frame of the content of the window, while the layout holds a dialog surface, and a layout with a dialog surface is complete only when that seat is measured; the seat is visible. The dialog surface is placed by the same placement sequence as a tab or section surface. The native container keeps the surface host of a dialog surface above every other surface host: a host created while a dialog host exists is inserted below it, and no operation raises a surface host. The document of the dialog is transparent; `@soksak/plugin-api` sets the backdrop, black at 50% opacity, on the root element of a page whose start values carry `dialog`, on every host, and the page draws its own card.
4. **Input.** While a dialog is open, the workbench sends no grab area of a boundary in the window overlays and the main page holds no element that takes the pointer over the dialog, so every point of the content of the window is a point of the dialog host; the elements of the main page are inert, as behind a dialog modal ([exposure](../spec/exposure.md)). The main page derives both from the open dialog surface as it does from a shown native modal: `windowOverlays` and `behindDialog` of `packages/workbench/host.js` read either. The dialog is a modal of the kind `dialog` for the keyboard: while it is open the keyboard stays in it, a move of the focus ring does not take it, and its close returns the keyboard to the active surface of the card with the focus ring ([exposure](../spec/exposure.md)). The placement that first shows the dialog starts a key wait of the window, and the wait ends when that placement has presented, which includes the first frame of the dialog view; the workbench then gives the dialog the keyboard (`surfaceFocus`), and the keys that waited are delivered to it in their order. The other ends of the key wait of [native modals](../spec/native-modals.md#keyboard) end it too.
5. **Background.** The host derives the dialog state from the placed surfaces: while a dialog surface is placed and visible, the dialog state of the window is on, and the host blurs each document web view, the page of each view surface other than the dialog, each region and each image region, as for a native modal of the mode `dialog`. The main page of the Wails and Tauri hosts applies the blur of its own content; the mygo workbench draws the blur over itself, as for the dialogs that it draws.
6. **Close.** The dialog view calls `runtime.dialog.close {result}`, and the main page removes the dialog surface and replies to the open call with `result`. A close call from another view is refused with `view call runtime.dialog.close is served only to a dialog`. A cancel of the open call removes the dialog surface. The open call follows the reasons of [plugin processes](../spec/plugin-processes.md) rule 3, which this change states in two sentences: a view call is answered by the main page, also when the main page derives the reply from another view, so a process end ends only the calls that the ending view made; and a call whose calling surface closes ends with `surface-closed`; the unload of a tab view closes no surface and ends the calls of its view by its process end. So the opener surface that closes ends the open call with `surface-closed` and removes the dialog, the end of the opener process ends it with `process-ended`, and the end of the main page ends both. The dialog view restarts after a process end as every view does, from its start values, and the open call stays open; a dialog surface whose restarts come to the limit of [view surfaces](../spec/plugins.md#view-surfaces) closes, the error display shows `the view failed 4 times within 300 seconds and is created again when its dialog is opened again` with the place `dialog <plugin> <name>`, and the open call fails with that text. The page decides its dismissal, such as a close button or Escape, and calls `runtime.dialog.close` for it.
7. **Statuses.** `core.modal` reports an open dialog as `{id, mode: "dialog", document: null, plugin}`, where `id` is the dialog surface and `plugin` its plugin; a native modal reports `plugin` `null`. `core.surfaces` lists the dialog surface with its plugin and `dialog` `{name, opener}` instead of a card or a section.
8. **Records.** The served view calls of [view surfaces](../spec/native-surfaces.md#view-surfaces) list both calls with their refusals.

## Answered objections

- A dialog process that ends restarts the view; the restart is the rule of every view, and the open call stays open (item 6).
- The open call uses the reasons of rule 3; rule 3 states that a process end ends only the calls that the ending view made, and that a call ends with `surface-closed` when its calling surface closes (item 6).
- The restart limit of a dialog has its own text, because a dialog has no tab to reopen (item 6).
- `core.modal` keeps its form and adds `plugin`, and the inert rule of a dialog applies behind the dialog surface (items 4 and 7).
- A native modal and a dialog refuse each other, so one rule holds in both directions (item 2).
- A cancel of the open call removes the dialog; the page owns its dismissal (item 6).
- The start values name `origin`, `project`, `section` and the new member `dialog` (item 2).
- The seat covers the sidebars, so no section view behind the dialog takes the pointer (item 3).
- The window overlays put the main page before the surface hosts, so the workbench sends no grab area while a dialog is open (item 4).
- The host derives the blur from the placed dialog surface, because `dialog()` of the hosts reads only the modal and the workbench flag (item 5).
- The native container inserts later hosts below the dialog host, because `addSubview:` puts each new host on top (item 3).
- The keyboard follows the rule of a modal of the kind `dialog`: it stays in the dialog, and ring moves do not take it (item 4).
- The key wait starts at the placement that first shows the dialog and ends when that placement has presented, after the first frame of the dialog view, because `view.ready` is posted at document start (item 4).
- A dialog whose restarts come to the limit shows the error through the error display (item 6).
- The page of each view surface is blurred already, because the host registers it in its documents (`mountView` of the Go host), and the blur loops over the documents; the change is the dialog state only (item 5).
- The dialog process is not a peer of the open call: rule 3 ends the calls that the ending view has open, and the open call belongs to the opener (item 6).
- `windowOverlays` and `behindDialog` read the dialog surface as well as the native modal (item 4).
- The sentence of [native modals](../spec/native-modals.md) that a dialog web view remains above newly created surfaces names the native modal web view, which opens only while no dialog surface is open, and the stacking rule of the dialog surface goes to the surface host container of [native surfaces](../spec/native-surfaces.md#surface-host-container) (item 3).
- The table of [native modals](../spec/native-modals.md) gains the row of the dialog surface, whose area is the content of the window; a native modal of the mode `dialog` keeps the main content viewport (item 3).
- No operation raises a surface host; the raise of the native modal web view runs only while no dialog is open (item 3).
- The dialog seat is a seat kind with its completeness rule (item 3).
- The backdrop is the root of the dialog page on every host, and the mygo workbench blurs itself (items 3 and 5).

## Rejected

- A modal web view that loads the plugin page: it gives the page no view channel, no surface identity for its calls and no place in the placement sequence, so the calls, statuses and records of a view would need a second route.
- A page inside the copied document of a native modal through a document region: a document region shows web documents of a surface, not a page of the plugin with the view channel ([document regions](../spec/native-surfaces.md#document-regions)).
- The backdrop drawn by the main page under the dialog surface: the surfaces of the window lie above the main web view, so a backdrop of the main page stays below them.
- A dialog page named by its path in the call: a declared page is a contract that the reader checks before a call runs.
