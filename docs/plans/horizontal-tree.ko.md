# 가로 tree와 tree 상세

[English](horizontal-tree.md)

이 제안은 F230을 정한다. 가로 사이드바 section에서 선언된 `tree`가 무엇을 보여줄지, 그리고 tree 노드가 `detail` 필드를 가질지 정한다. 근거, 대안, 적대적 검토를 기록한다. 받아들인 내용은 [선언된 UI](../spec/declared-ui.ko.md)와 [plugin 프로세스](../spec/plugin-processes.ko.md)에 들어간다. F230이 끝나면 이 문서는 지운다.

## 문제

검증기는 가로 section의 `tree`를 `tree cannot be drawn in a horizontal section`으로 거부한다([선언된 UI](../spec/declared-ui.ko.md#사이드바-section-형태), 거부 표). 가로 방향 tree section을 가진 plugin은 그 section의 형태가 없다. 같은 값이 세로 section에서는 받아들여지고 가로 section에서는 거부된다. 카드 사이드바의 방향은 카드 측면을 따른다(`packages/workbench/plane.js:1021`: 위와 아래는 가로). 창 사이드바는 항상 세로다(`plane.js:249`). 그래서 카드를 측면에서 위나 아래로 옮기면 유효한 tree가 거부로 바뀌고, plugin은 방향을 고를 수 없다.

코드의 근거:

- `packages/workbench/declared-ui.js`는 문맥 방향이 `horizontal`인 tree를 거부한다(`treeHorizontal` 행). 방향에 기대는 다른 요소는 없다.
- `packages/workbench/app.css:642`는 가로 set의 선언된 본문을 한 줄로 줄바꿈하는 행(`flex-direction:row;flex-wrap:wrap`)으로 놓는다. 어떤 규칙도 루트 상자(`.declared-tree`, `.declared-list`, `.declared-row`)의 너비를 정하지 않으므로, 루트 상자는 내용 크기에 맞는 flex 항목이다.
- 가로 `list` 본문은 list 레이아웃에서 `min-height:0; overflow:auto`로 제한된다(`app.css:665`). 다른 레이아웃에서는 set이 스크롤한다(`app.css:607`, `.set{overflow:auto}`).
- list 항목에는 이미 `detail`(평문, 500 코드 포인트 이하, label 뒤에 그린다)이 있다. tree 노드에는 `label` 말고 행별 텍스트 필드가 없다.
- tree 단계마다 들여쓰기 한 칸이 더해진다(`.declared-children{padding-left:1em}`, `app.css:634`). 가지 행에는 펼침 제어도 있고(`.declared-expand` 너비 1em, `app.css:635`), 간격은 .25em이다(`.declared-row`, `app.css:633`). section 본문에는 양쪽 14 px 여백이 있다(`app.css:650`). 12 px 글자에서 깊이 d의 가지는 라벨에 W − 28 − 15 − 12(d−1) px을 쓴다. 여기서 W는 section 너비다. W = 120이면 깊이 8에서 0이 되고, W = 96이면 깊이 6에서 0이 된다. 사이드바 최소값은 pt 단위다(`packages/workbench/settings.js:194`). 카드 최소값은 px 단위다(`packages/soksak/src/soksak.ts:266`). 이 계산은 1 pt = 1 px을 가정하며, 여기서 검증하지 않았다. 레벨 16은 들여쓰기가 15칸(180 px)이다.

## 결정 1: 가로 section에서 tree는 한 줄을 모두 차지하고, 자기 상자 안에서 스크롤한다

가로 section의 `tree`는 받아들여져 그려진다. section 너비의 한 줄을 모두 차지하고, section의 다른 루트 요소는 그 앞뒤 줄로 줄바꿈된다. 윤곽은 세로 section과 같다. 들여쓴 하위 노드, 가지마다 펼침 제어, 유지된 펼침 상태, `empty` 텍스트가 같다.

이 방식을 두 규칙이 가능하게 한다:

```css
.set[data-orientation=horizontal] .set__body[data-declared] > .declared-tree{flex:1 1 100%;min-width:0}
.declared-tree{overflow-x:auto}
```

첫 규칙은 tree에 한 줄을 준다. 둘째 규칙은 모든 방향에 적용된다. tree의 내용이 상자보다 넓으면 tree는 자기 상자 안에서 가로로 스크롤하며, 얇은 스크롤바(`scrollbar-width:thin`)를 쓴다. 그래서 상자 밖 라벨은 보이는 신호 없이 숨겨지지 않고 스크롤로 닿는다. 세로 section에서는 tree 상자가 section 너비이므로, 스크롤은 라벨이 section보다 넓을 때만 적용된다. 그때 라벨은 전에는 section 가장자리를 넘어 set 스크롤로 들어갔고, 이제는 tree 상자 안에서 스크롤된다. 스크롤바의 표시는 시스템 스크롤바 설정을 따른다(오버레이 스크롤바는 스크롤하는 동안 보인다).

한 줄을 주는 이유, 코드에 근거한다: tree의 너비는 가장 깊은 보이는 행이 정한다. 그 행의 들여쓰기는 단계마다 더해진다. 가지를 펼치거나 접으면 보이는 깊이가 바뀌므로 tree 너비도 바뀐다. 내용 너비의 행 흐름에서는 그 변화가 tree 옆의 형제 요소를 다시 배치한다. 한 줄을 주면 그 변화가 tree 자체에 머문다. `list`에는 펼침 제어가 없으므로 사용자 동작으로 너비가 이렇게 바뀌지 않고, 내용 너비를 유지한다. 이 이유는 코드에 근거하며, 재배치는 CSS의 결과이고 측정한 결과가 아니다.

스크롤 규칙의 이유: 들여쓰기는 단계마다 라벨의 너비를 가져가므로, 좁은 너비에서는 깊은 라벨에 여유가 거의 없거나 전혀 없다(문제의 계산). 스크롤은 모든 라벨을 자기 tree 상자 안에서 읽을 수 있고 닿을 수 있게 하며, section 너비에 기대지 않는다. 들여쓰기를 없애지는 않는다. 들여쓰기는 윤곽이 요구하는 대로 단계마다 한 칸이다. 그러므로 좁은 너비의 배치는 잘린 라벨이 아니라 보이는 스크롤바가 있는 스크롤이며, 그 스크롤은 set의 것이 아니라 tree 자신의 것이다. 이 항목은 깊은 라벨에 여유가 줄어드는 들여쓰기를 줄이지 않는다. 스크롤이 그 라벨을 닿을 수 있게 유지한다.

결정의 이유(결정 자체):

1. 결정적인 이유는 카드 측면이다. 카드 사이드바의 방향은 카드 측면을 따른다. 가로 section에서 거부된 tree는 카드를 옮길 때 유효한 값을 실패하게 하고, section은 거부를 보인다([선언된 UI](../spec/declared-ui.ko.md#거부)의 거부 표시). 계약은 유효한 값을 카드 측면에 의존하게 하면 안 된다.
2. 받아들여지는 값이 하나이면 plugin은 모든 배치에서 한 형태를 가진다. 두 방향 모두에서 tree를 받아들이면 값의 검사가 배치에 독립적으로 된다.
3. tree의 크기는 직렬화된 값의 크기, 루트 수, 그리고 자체 제한인 노드 5000개와 16단계로 제한된다. list는 항목 1000개의 자체 제한을 가진다. 문제 절의 list 높이 규칙(`app.css:665`, list 레이아웃)은 tree 본문에도 같은 방식으로 적용된다. 다른 레이아웃은 둘 다 제한하지 않는다. 새 제한은 필요하지 않다.
4. 추론이며 측정된 것이 아니다: 들여쓴 윤곽은 짧은 요소의 왼쪽에서 오른쪽 행 흐름에 맞지 않는다. 코드와 명세는 거부의 이유를 주지 않으므로, 이 이유는 추론으로 표시하며 결정의 근거로 삼지 않는다.

기각한 대안:

- 거부를 유지하고 plugin에 `list`를 쓰라고 한다. 평탄화된 list에는 위계와 펼침 제어가 없으므로, plugin은 데이터를 평탄화하고 유지된 펼침 상태를 잃는다([status 대응](../spec/declared-ui.ko.md#status-대응)). 거부는 그 평탄화를 강요한다.
- 모든 list에도 한 줄을 준다. 기각: list의 너비는 사용자 동작으로 바뀌지 않으므로(펼침 제어 없음) 재배치의 이유가 적용되지 않으며, F230에 list 동작의 변경은 필요하지 않다.
- 라벨을 단계마다 여러 줄로 줄바꿈한다(`overflow-wrap:anywhere`). 기각: 여유가 0 px이면 라벨이 글자마다 한 줄이 되어 읽을 수 없다. 스크롤은 각 라벨을 한 줄에 둔다.
- 루트 노드만 줄바꿈되는 칩 행으로 그린다. 가지의 하위 노드는 그릴 형태가 없게 된다. 칩 행에는 중첩된 노드 목록의 자리가 없다(`declared-ui.js`, `paintNode`). 이는 한 방향에 두 번째 그리기 규칙을 더한다.
- 가로 행 흐름에서 들여쓰기 없이 윤곽을 그린다. 중첩이 사라지고, 줄바꿈된 노드가 부모의 형제처럼 읽힌다.

## 결정 2: 방향은 선언된 값에 영향을 주지 않는다

거부를 없애면 방향은 배치의 선택일 뿐이다. 계약 자체에서 결과가 따른다:

- `packages/workbench/declared-ui.js`: `ROWS`의 `treeHorizontal` 항목(32행), `checkElement`의 검사(278~280행), `validateValue`의 `orientation` 옵션(290행)을 없앤다.
- `packages/workbench/declared-section.js`: `createDeclaredSection`의 `orientation` 매개변수(39행)와 `receive`에 넘기는 `orientation` 옵션(51행)을 없앤다. `orientationChanged()`(119~123행)와 반환 객체의 항목(127행)을 없앤다. 머리 주석(26행과 34~35행)은 아래 변경 규칙으로 다시 쓴다.
- `packages/workbench/sidebar-sections.js`: `createDeclaredSection`의 `orientation` 옵션(130행)을 없앤다. `apply()`(177~187행)에서 방향 변경은 module section만 unmount한다: `if (orientationChanged && !entry.declared) unmount(entry);`. 선언된 section은 방향 변경으로 unmount, 닫기, pull되지 않는다. `unmount`는 해제로 이어지고, 그다음 `reconcile()`이 다시 pull하기 때문이다. 177~178행과 216행의 주석은 같은 규칙으로 다시 쓴다. `drawSet`의 `orientationChanged` 플래그(219행, 281~284행)는 module remount를 위해 남긴다. 249행의 주석은 본문이 여전히 CSS로 루트 요소를 방향별로 배치하므로 남긴다.
- "이전 방향에서 버린 값이 새 방향에서 유효할 수 있다"는 pull 이유는 [선언된 UI](../spec/declared-ui.ko.md)(172행, 사이드바 section 형태)와 [plugin 프로세스](../spec/plugin-processes.ko.md) 규칙 2(51행)에서 없앤다. "실행 중인 view는 마지막 값을 새 독자에게 보낼 다른 수단이 없다"는 문장은 load와 출처 변경 pull의 이유이므로 남긴다.
- module section은 방향 변경 때 remount를 유지한다([plugin](../spec/plugins.ko.md#섹션)). 그 규칙은 module에 관한 것이며 그대로 둔다.

## 결정 3: tree 노드는 `detail` 필드를 가진다

tree 노드는 선택적 `detail`을 받는다. 평문이며 500 코드 포인트 이하이고, list 항목의 `detail`이 그려지는 것처럼 라벨 뒤에 그린다. `command` 요구는 없다. 라벨은 명령 묶기를 유지하며, `detail`은 텍스트만이다.

이유:

1. tree는 행의 개요다. 행별 상태(예: 나열된 파일의 상태) 같은 행 속성은 자기 필드에 속한다. list 항목에는 이미 그런 필드가 있다. tree 노드에 그런 필드가 없으면 plugin은 상태를 라벨에 넣어야 하는데, 라벨은 사용자가 고르고 읽는 이름, 즉 식별자다.
2. 한 개념은 두 행 종류에서 같은 필드 이름을 가진다. 어휘는 list 항목의 `detail`이 그려지는 것처럼, 행의 라벨 뒤 텍스트에 `detail`을 쓴다.
3. 필드는 다른 모든 텍스트 필드와 같은 텍스트 규칙을 가진 평문이다. 어조, 색, 오류를 더하지 않는다. `status-line`에는 어조가 없고, 오류는 로그 표시 경로로만 사용자에게 닿는다([선언된 UI](../spec/declared-ui.ko.md#요소-종류)).

기각한 대안: 노드의 `tone`이나 `status` 열거형. 어휘는 어조와 색을 정의하지 않으며, 하나를 더하면 다른 요소가 쓰지 않는 시각 개념을 더하게 된다.

## 명세 변경

각 변경은 영어 문서와 한국어 번역을 같은 변경에서 한다.

- [선언된 UI](../spec/declared-ui.ko.md)(`declared-ui.md`), 요소 표: `tree` 노드 행 `detail`(문자열, 선택, 500 코드 포인트 이하, label 뒤에 그린다). `tree` 행에서 "가로 section에서는 tree를 그리지 않는다"를 뺀다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 85행 근처의 한국어 `declared-ui.ko.md` 85행), 제한 표: "텍스트 필드 | 500 코드 포인트 | section 안 텍스트 한 줄의 너비를 제한한다."를 "텍스트 필드 하나의 길이를 제한한다. 그린 너비는 제한하지 않는다: `tree` 상자는 상자보다 넓은 라벨을 상자 안의 가로 스크롤로 그리고, `list` 라벨은 공백에서 줄바꿈하며, 공백이 없는 한 단어가 section보다 넓으면 section 가장자리 밖으로 그려져 set과 함께 스크롤된다. status 줄 텍스트는 자기 상자에서 잘린다."로 바꾼다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 171행, 한국어 `declared-ui.ko.md` 172행), 사이드바 section 형태: 가로 section의 tree에 관한 글머리표를 "`tree`는 그 너비의 한 줄을 모두 차지하고 세로 방향과 같은 윤곽을 그려서, tree 앞뒤로 행이 줄바꿈된다. `list`는 내용 너비를 유지하며, 내용이 더 넓을 때만 줄에 맞춰 줄어든다. tree는 그 자리에서 펼치고 접는다: 너비는 가장 깊은 보이는 행을 따르므로 자기 줄을 가지며, 라벨이 tree보다 넓으면 tree 안에서 가로로 스크롤한다."로 바꾼다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 172행, 한국어 173행), 사이드바 section 형태: "section의 방향이 바뀌면 방향 검사를 받아들인 값에 다시 한다..." 문단을 방향 pull의 이유 문장과 함께 뺀다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 151행), status 대응: pull 규칙의 "방향이 바뀔 때"를 뺀다. 한국어 줄은 `declared-ui.ko.md`의 대응 줄이다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 230행, 한국어 231행), 거부 표: "가로 section의 `tree`" 행을 뺀다.
- [선언된 UI](../spec/declared-ui.ko.md)(영어 85행), 제한 표: 위 제한 표 변경과 같다.
- [plugin 프로세스](../spec/plugin-processes.ko.md)(영어 51행과 영어 124행의 pull 행, 한국어 대응 줄), 규칙 2: "section의 방향이 바뀔 때 한 번"과 "이전 방향에서 버린 값은 새 방향에서 유효할 수 있으며, 그 값을 가진 것은 출처뿐이다" 절을 뺀다. "실행 중인 view는 마지막 값을 새 독자에게 보낼 다른 수단이 없다" 문장은 남긴다. 메시지 표의 pull 행은 "load, 출처 변경"이다.

## 체크리스트 항목

- F230(`docs/features.md`, `docs/features.ko.md`): 이 항목이 끝나면 Red와 Green 결과와 함께 `[o]`로 표시한다. 등록된 재시도 문구("Retry when: F229 is decided.")는 이 항목을 지금 진행하라는 지시로 대체된다. 변경은 두 파일의 F230 아래에 이 줄을 더해, F229 조건이 그 지시로 대체되었다고 적는다. F229는 이 브랜치에 없다.
- 등록된 후속 ID는 없다. 모든 라벨은 tree의 스크롤로 닿을 수 있으므로(결정 1), 어떤 라벨도 보이는 신호 없이 숨겨지지 않으며, 이 항목은 닿을 수 있는 결함을 열린 채로 두지 않는다.

## 검증 계획

- Red, 변경 전 코드에서(테스트 커밋에 기록): 가로 section의 tree 값은 `tree cannot be drawn in a horizontal section`으로 거부된다(라벨 `[]`, 기대값 `["b", "c", "l"]`). 가로 문맥의 tree 값은 거부된다. tree 노드 `detail`은 `unknown field "detail"`로 거부된다. 가로 `.declared-tree`의 `flex-basis`는 `auto`이고 기대값은 `100%`다. 방향이 바뀐 뒤 section은 거부를 보인다. 기대값은 마운트된 tree다.
- 스크롤 규칙의 Red: 변경 전 CSS에서 `.declared-tree`의 계산된 `overflow-x`는 `visible`이며, 기대값은 두 방향 모두 `auto`다. 이 단언은 CSS 변경 전에 CSS 테스트에 더해 Red를 기록한다.
- Green: 같은 테스트가 통과한다. 방향 검사와 방향 pull 테스트는 받아들인 tree가 유지되고 방향 변경에서 pull이 없다는 테스트로 대체된다. 진행 중 pull 테스트는 제거된 메서드 없이 낮은 seq 규칙을 확인한다.
- CSS 규칙은 jsdom 계산 스타일 테스트로 확인한다(가로 선언된 본문의 `.declared-tree`의 `flex-basis`와 `min-width`, 두 방향의 `overflow-x`). jsdom은 텍스트를 배치하지 않으므로 깊이에서의 라벨 여유는 여기서 측정하지 않는다. 이 규칙은 CSS 수준의 결정이며, 배치 효과는 실행한 창 확인에서 관찰한다.
- 해당 검사: workbench 선언 UI 테스트(`declared-ui.test.mjs`, `declared-section.test.mjs`, `sidebar-sections.test.mjs`), `make docs-check`, 변경 없는 DOM 이름을 위한 `make exposure-check`.

## 검토 기록

검토 범위. 검토는 결정 1부터 3까지와, 결정 2가 요구하는 방향 검사와 pull의 제거를 정한다. 핵심 반대는 다음 중 하나다: 어떤 배치에서 유효한 선언 값에 형태가 없는 결정, 두 번째 그리기 규칙이나 기존 개념과 겹치는 필드를 더하는 결정, 이유가 적히지 않은 규칙을 남기는 제거, 변경 후 코드와 어긋나는 명세 문장, 코드가 뒷받침하지 않는 주장, 공유 규칙의 근거 없는 예외, 이 항목이 열린 채로 두는 닿을 수 있는 결함. 범위 밖: 한국어 번역의 표현, 단위 테스트가 정하는 세부 사항.

### 4라운드

두 새 감사자(G, H)가 3라운드 개정을 읽었다.

- G-O1과 H-1(tree만 전체 줄을 갖는 이유가 코드가 뒷받침하지 않는 메커니즘을 말함: 줄을 나눠 쓰면 항목이 줄어들지 않는다). 받아들임. 메커니즘을 바꾼다: tree의 너비는 가장 깊은 보이는 행을 따르므로, 펼침으로 너비가 바뀌어 행 흐름에서 형제를 재배치한다. list에는 펼침 제어가 없다. CSS에서 확인함: 줄바꿈되는 flex 줄은 항목을 내용 크기로 두고, 줄을 넘칠 때만 항목을 줄인다.
- G-O2, H-1(닿을 수 없는 결함을 F230-1로 미루면서 F230을 완료로 표시함; 재시도 조건은 조건이 아니라 결정임). 받아들임. F230-1은 뺀다. 결정 1은 tree 자신의 가로 스크롤(`.declared-tree{overflow-x:auto}`)로 좁은 너비의 라벨을 해결하므로, 어떤 라벨도 잘리지 않고 텍스트도 tree 상자를 벗어나지 않는다. 상자는 같은 요소이므로 변경은 두 방향 모두에 있다. 들여쓰기는 단계마다 한 칸으로 남는다.
- G-O3, H-2(등록된 재시도 조건 "F229 is decided"가 대체된 것으로 기록되지 않음). 받아들임. 체크리스트 항목이 대체 지시를 말하며, 두 features 파일에 그 줄을 더한다.
- G-O4, H-4(인용: 펼침 제어 `app.css:635`, 간격 `app.css:633`, list 레이아웃의 스크롤은 section 본문 안의 `app.css:665`). 받아들임. 문제와 결정 1에서 고쳤다.

- H-5(96 px와 120 pt 단위). 받아들임. 단위 가정을 문제 절에 한 번 적는다.
