## Problem

The Wails and Tauri hosts draw the workbench as a JavaScript page in one WKWebView per window (the main page). Plugin views, document regions and image regions are native views that follow the layout of that page. The measured costs:

| ID | Cost | Measurement |
| --- | --- | --- |
| C1 | Main page memory | 242 MB (Wails) and 291 MB (Tauri) after three days of use (F196); 103.8 MB, peak 181.9 MB, in a window with one project, two sidebar sections and eight tabs (F368); 446.6 MB (Wails) and 399.9 MB (Tauri) after reloads ([plugin processes](../spec/plugin-processes.md#reasons)) |
| C2 | Main page CPU | The main page process of each application stayed at 100% CPU after a failing draw (F349) |
| C3 | Main page graphics | About five window-sized buffers (71 MB at 1200×760) before F196.10.3; 20 MB at 1200×760 after it, about 1.4 window buffers: the root tiles of the page and the layers of its surface documents (F196.10.3) |
| C4 | Processes of an empty window | An empty library-screen instance of the release Wails host costs about 208 MB: host 108, WebContent 54, GPU 32, Networking 14; the WebKit processes are 100 MB of it (V5-96-14-6-4-9) |
| C5 | Modals | The settings window and each menu are web views with their own documents ([native modals](../spec/native-modals.md)); a closed modal leaves no web view and no attached native object (`e2e/modal-release.test.mjs`), so their cost lasts while one is open |
| C6 | View processes | About 11 MB for each WebContent process of a small page, growing linearly with the number of views (F212.1); an idle browser tab costs 53,808 KB on Wails (documents 29,040 KB, main web view growth 24,768 KB) and 45,504 KB on Tauri (documents 30,880 KB, growth 14,624 KB) against the bound of 51,200 KB of the idle tab benchmark (`IDLE_TAB_BOUND_KB`, F292-40); the growth is a cost of the main page, which the host process takes on the mygo host |
| C7 | Host posts to a view | Each post runs `callAsyncJavaScript`, after which WebKit queries RunningBoard synchronously when the reply releases the foreground activity of the view process and no other activity holds that process, as for every view of an occluded window (F374-7) |
| C8 | Terminal frames | On the Tauri host, in a window of 760×614 points that was not occluded, at a load average of 14 to 21, a status line updated every 33 ms costs 1.6 ms of application CPU per frame at 27.6 frames per second with the `term` plugin 0.0.4 and the sidecar `alacritty` 0.0.4, and 20 rewritten rows cost 3.1 ms at 27.5, with the CPU and the frame counts taken from separate runs of the same output (sidecar alacritty S21, term P1-4); no record divides this CPU between the host, the view page and the sidecar; the `term` view page owns the screen state, the input and the exposure of the terminal |
| C9 | Divider drag of a `terminal` tab | At 120 Hz with the trace off: Wails latency median, p90 and worst 68.3, 97.6 and 127.4 ms and cadence 34.1 ms, Tauri 90.0, 141.5 and 196.6 ms and 33.7 ms, against 20.8, 25 and 33.3 ms and 33 ms; at a 60 Hz display mode: Wails 61.0, 88.7 and 116.9 ms and 34.2 ms, Tauri 66.8, 97.9 and 130.6 ms and 33.9 ms, against 41.7, 50 and 66.7 ms (F212.14). The cohorts differ in display mode and load and do not attribute the latency to a stage (F239-223) |
| C10 | Browser documents | A document web view of a browser tab held 1.31 GB (F196) |
| C11 | Browser sections | The four sections of the browser plugin declare no `unload`, so they keep their views while hidden |
| C12 | Host process memory | About 154 MB in each host after three days of use (F196); 108 MB on an empty library screen of the release Wails host (V5-96-14-6-4-9); over 30 repetitions of `make object-counts` the Wails host settles between 80 and 89 MB with 3 to 5 MB of Go heap objects and 50 to 52 goroutines, and the Tauri host between 70 and 76 MB (F196.23) |

C1, C4 and C5 are the cost of the workbench as a page: its state, its WebContent process and the WebKit processes that it starts. C3 is the graphics memory of that page; the native workbench replaces it with the drawables of its Metal layer (one window-sized buffer at rest, three while the window animates) and the memory that the Metal driver takes after a pause [S17]. Each layout transaction of C9 waits for the presentation of the main page, the presentation of each joined root view and the required image rasters ([placement sequence](../spec/native-surfaces.md#placement-sequence), step 4), and a layout reaches the screen across four frame boundaries (the input's arrival, the frame of the layout before it, WebKit's rendering update and the display refresh). The native workbench removes only the wait for the main page; a divider drag still waits for the root views that it resizes and for the rasters of their image regions, and G4 applies the latency targets of that drag to the mygo host unchanged. C2 is the defect F349 of the main page, not a cost of the page, and the mygo host has no main page; G2 requires that a failing draw does not keep the mygo host busy. C6 and C7 are the cost of plugin views as web views, which the [plugin process decision](../spec/plugin-processes.md#decision) keeps. C8 is the cost of terminal frames that pass through the image region of a view page, a path that the mygo host keeps (D5) and that G5 bounds on the three hosts. C10 is WebKit's own document memory and is not a host cost. C11 is a declaration of the browser plugin, which browser P110 corrects. C12 is the process that holds the state of the workbench on the mygo host.

## Goals

F502-2 writes the values of G1 to G8 into a section Performance goals of [hosts](../spec/hosts.md) without checklist IDs, each value with the scenario and the target that measure it, and G4 there refers to the pass values of [plugin processes](../spec/plugin-processes.md#pass-values); it writes their numeric bounds into `docs/spec/performance-goals.json`, which `scripts/b3-judge.mjs` (`make b3-judge`) reads and from which the idle tab and split load cases read `IDLE_TAB_BOUND_KB` and `SPLIT_LOAD_GROWTH_BOUND_KB`, which no specification defines, in place of their constants, as `e2e/chains.mjs` reads `docs/spec/events.json`, with the file in `specFiles` of `e2e/package.json`; the tables of that section in `hosts.md` and `hosts.ko.md` are copies of that file, which `scripts/test/performance-goals.test.mjs` holds equal to it, and a value that [plugin processes](../spec/plugin-processes.md#pass-values) or [native surfaces](../spec/native-surfaces.md#acceptance-criteria) defines, the DOM mount baselines and the catch-up limit of a maximise and restore among them, is referred to there and not copied, because the benchmark that holds it judges it and the judge does not read it; and it writes the procedure (the definitions of the other hosts and the baseline hosts, the runs, the median and the spread, the regression rule, the run conditions, the scenarios of B3 and its phases) into a section Three-host benchmark of [examples](../operations/examples.md) and of its translation, which names the revision of the baseline hosts by its checklist item. All of this precedes every measurement item. A value is never lowered because it is hard to meet; a floor that exceeds a value changes it only through an adversarial review that states the evidence (F212.14-6 is the precedent).

"The other hosts" means the Wails and the Tauri host built from the same revision as the mygo host; "the baseline hosts" means the Wails and the Tauri host built from the revision that completes the measurement target item (F502-2), which precedes every item that changes code that the Wails or the Tauri host runs; each baseline host is built and run from a verification checkout of the head of the branch `test/b3-baseline-F502-25`, which F502-25 makes at that revision and which holds after it only the commits that change measurement targets in sub-items of F502-26 and F502-27: a sub-item that changes a measurement target applies that change to this branch as a commit of its own and writes the new head into the baseline record `target/b3/baseline.json` of the checkout of the other hosts, the record of F502-25, which `make e2e-b3` reads; that record holds the revisions of the baseline hosts and of each sidecar repository and the version and `sha256` of each plugin release that the baseline hosts install, outside the records of the repository, which name no commit id. The branch is never merged into `main`, because each of its commits after the revision of F502-2 applies a change that `main` holds, and a sub-item of F502-25 states its removal once F502-27 has recorded the final phase. Each baseline host installs, in every run of F502-26 and F502-27, exactly the plugin releases that F502-25 recorded when it installed from the index of the [public registry](../spec/registry.md), which selects for the core version of that revision the newest versions whose ranges contain it ([version selection](../spec/installation.md#version-selection)), so the baseline hosts run the plugin releases published before the D7 releases, and a run fails when an installed version or `sha256` differs from that record; the core version of that revision is one that `core.json` of the public registry lists. The other hosts and the mygo host install their plugins from the workspace registry, as every build and window check does (`make registry`). All five applications run the sidecar releases that the workspace registry builds for diagnostics (`make registry SIDECARS=diagnostic`, F502-2), so every application runs the same sidecar builds. F502-25 fails when the installation of a baseline host selects no release for a plugin of a scenario, or when a selected plugin excludes the version of a sidecar of the workspace registry. Each run records the version and the `sha256` of the release of every installed plugin and sidecar and the Go and Rust toolchain versions of each build. All five applications are measured in the same session in interleaved order, one run of each application before the next run of any, seven runs each; a value is the median of its runs, and the spread of a value is the range of its runs. A relative criterion fails only when the spread of the mygo host lies wholly on the bounded side of the spread of the same value of an other host or a baseline host: its lowest run above that host's highest run for a time, a CPU time or a footprint, and its highest run below that host's lowest run for a frame rate. A value of an other host is a regression when a relative criterion of G2, G3 or G5 to G8 compares that value and its spread lies wholly on the bounded side of the spread of the same value of its baseline host in the same sense. Two applications with the same distribution of a value meet either condition by chance in 1 of 3,432 comparisons (1/C(14,7)); the 24 values that the relative criteria compare (G2: the host CPU time in S0, S1, S9 and S12; G3: S0, S0b, S1, the peaks before and after the drag of S5 and of S13, S11, S15 and S14; G5: one and 20 rows; G6: the document part; G7: the median and the 90th percentile in each of the two tabs; G8: the drags of S5 and of S13 and the pointer move of S1) give 144 comparisons, four with the other hosts and the baseline hosts and two regressions for each value, and with the three comparisons of a value of the mygo host with its own earlier value (G2 in S0 and S1, G3 in S4) these meet one by chance in about 4.2% of sessions (1 − (1 − 1/3,432)^147, with the comparisons taken as independent); with three runs and the median rule, a mygo host equal to the others would fail a relative criterion in 4 of 5 sessions, and an unchanged value of an other host would be a regression in 1 of 5 comparisons. The cause of a regression is found among the core items, the measurement target changes, the plugin versions and the Go and Rust toolchain versions between the two revisions, and it is fixed with Red/Green at the owning module before G1 to G8 are judged. A run starts only while swap use is below half of its total and `fseventsd` uses less than 10% of a core (the conditions of F374-6-3).

The region cost benchmark and the view process benchmark run no host; they are floors of F502-25, not scenarios. `make page-memory`, `make host-calls` and `e2e/benchmark/main-page-footprint.test.mjs` measure the main page; on the mygo host they fail with the error `the mygo host has no main page`.

Both phases build the three applications and the baseline hosts with the release compilation profile and diagnostic support, and every sidecar once for diagnostics (`make registry SIDECARS=diagnostic`), which all five applications run. Each phase records the source revision and executable hash of each application, the Go and Rust toolchain versions, the version and the `sha256` of the release of every installed plugin and sidecar, the display mode and refresh rate, the window size and backing scale, the trace switch and the log policy of each run, and the load average at the start and end of each run. Every run uses a display mode of 120 Hz; a run at another refresh rate fails. The window of every scenario is 1200×760 points at backing scale 2 on the same display, except S2, which uses the window of sidecar alacritty S21 (760×614 points); S9 and S11 add the second window that their state names. Each window check sets the trace switch and the log policy when it prepares its window:

- the view drag benchmark runs its drags with the trace off, under the default policy, and its last drag, after `frames` of `host.window` has not changed for 3 seconds (after 3 seconds on a window whose `frames` is `null`), under the policy that stores the class `frame` at `debug`;
- the idle tab benchmark runs with the trace on and the class `call` at `debug`, and the view benchmarks run with the trace on and the class `frame` at `trace`;
- the resize catch-up benchmark runs its captured maximise and restore with the trace on and the classes `lifecycle`, `call` and `frame` at `debug`, and, on a window whose `host.window` reports `pageProcess` `null`, a maximise and restore without capture with the trace off under the policy that stores the class `frame` at `debug`;
- the split load benchmark runs with the class `call` at `debug`;
- the input latency check runs with its four configurations.

## mygo facts (v0.7.4)

### Threading and native calls

- `mygo.go` sets `Version` to `0.7.4` and calls `runtime.LockOSThread()` in `init`, so the main goroutine runs on the thread that started the process [S1]. The module requires Go 1.27.3 and purego v0.11.1 [S3].
- mygo uses no cgo: native APIs are called at run time through purego (`dlopen` and assembly trampolines) [S4][S5]. Objective-C methods that AppKit calls are Go functions registered as callbacks, and purego callbacks are a scarce resource that is never freed [S4][S7]. A purego callback enters Go through `crosscall2` on the thread that calls it, and an Objective-C method is registered as a purego callback (`objc.NewIMP`) [S29].
- The main goroutine stays locked to the main thread; every platform method and every handler runs on the main thread, in Go; listeners run on the main thread and IPC handlers on goroutines [S6]. The main thread is the thread for which `pthread_main_np` answers true; `RunOnMain` runs a function at once on the main thread and otherwise posts it to the main thread and waits for it, and `await` processes native events through `Backend.Step` while it waits on the main thread [S2].

### Windows, web views and native handles

- A window shows either a page or native UI (`WindowOptions.Content`). `Window.NewWebView` makes a web view only in a window that shows native UI, and fails with `errNoContent` in a window that shows a page [S11][S12].
- In a native-UI window the WKWebView sits in a flipped clip view (`MyGoClipView`) under the Metal surface in the content view. Native UI paints a hole (`OpHole`) where the web view shows, and the surface's `hitTest:` returns nil where the web view takes the pointer [S12][S13].
- `ui.WebView` places only web views that the window made: `surface.WebView` returns the native side of a `*mygo.WebView`, only the web view element paints a hole, and the window gives the placements of its web views (frame, clip and covers) to the surface in the frame that draws them [S14]. mygo has no element that places an arbitrary native view.
- The only public native handle is the window: `Window.NativeHandle` returns the `NSWindow` [S10]. The web view handle (`WebViewHandle`) is in an internal package [S10].
- mygo makes each web view with its own configuration and delegate (`createWebView`) [S10]; v0.7.4 has no operation that takes a `WKWebView` that another library created.
- The mygo surface view registers for file URLs and receives a dropped file itself, as an event of the content [S27].

### Images

- `ui.NewBitmap` keeps its pixels on the CPU and on the GPU; `Update` replaces the picture and uploads the new pixels [S15]. The Metal renderer uploads the whole image with `replaceRegion:` when its version changes, after waiting for the frames in flight [S15]. The tree at v0.7.4 contains no use of IOSurface.

### IPC

- The page bridge carries JSON messages; a `[]byte` value is a base64 string [S16]. A custom protocol handler gives the main thread its body in 256 KiB chunks [S16].

### Application lifecycle

- `applicationShouldTerminate:` stops the run loop when the quit is accepted and returns `NSTerminateCancel`; mygo installs its own handler for the quit Apple Event in `applicationWillFinishLaunching:` [S8][S9].
- `applicationDidFinishLaunching:` activates the application when its activation policy is regular, and `Window.Show` activates the application; `Window.ShowInactive` shows a window without activation and without making it key [S9][S22]. `Window.OnReadyToShow` runs once a window created hidden drew its first frame [S22].
- `App.Run` calls `quitOnSignals`, which makes SIGINT and SIGTERM quit the application [S20]. The application delegate sets a notification center delegate (`MyGoNotificationDelegate`) when notifications are supported [S9][S21], and answers `applicationDockMenu:` with the menu of the mygo `Dock` API [S9].

### Native UI rendering

- Native UI draws with Metal and lays out text with Core Text; text input uses `NSTextInputClient` [S18].
- A frame is drawn on request: a paused `CADisplayLink` ticks only while frames follow each other [S17]. A frame draws only what changed since its drawable was drawn (`gpu.Ages`, `scene.Differ`) [S17]. A settled window asks for no frame and arms no timer (`TestSettledWindowSleeps`); a small idle native-UI window takes 44 MB on macOS, and the counter example idles at about 0.005% of a core [S5]; F502-25 measures the floor at the size of the B3 window.
- The Metal layer keeps one drawable at rest and three while a window animates, and a timer shrinks the drawables two seconds after the last frame; the Metal driver takes 30 to 45 MB of the process footprint for the first command buffer after a pause and returns it a second or two after the last frame [S17].
- A frame that changes the layer, or that a window showing web views draws, presents with the Core Animation transaction (`presentsWithTransaction`), so the web views move in the same transaction as the frame; such a frame is drawn even when nothing in it changed, and takes its drawable on the main thread after any fetch in flight. Other frames present as soon as the GPU has them, with a drawable that a presenter fetches on a thread of its own, so that the main thread does not wait for the display [S17][S26].
- The engine holds the frames of a window that is out of sight, and a frame request of such a window waits for the display link [S28].
- The engine describes every frame as an accessibility tree once assistive technology asks for a surface's content (`AccessibilityOn`) [S18]; the automation hook builds the tree when the automation plugin reads it. The element keys and actions are handed out only to the automation plugin, when the application links it and `MYGO_AUTOMATION` asks for it, and builds with the tag `mygo_noinspector` leave that hook out [S19].
- Measured native UI frames: 1,000 static labels take 397 µs per frame on the CPU renderer with no allocation, and a warmed view of 1,000 labels retains about 2.50 MB of Go heap; the measurement excludes native window and GPU memory [S23].

### Maturity

mygo is at version 0.7.4; the history of the tag starts on 2026-09-26 [S25]. A version 0 module may change its API in any release.

## Consequence

**Page mode gives no gain.** A mygo window that shows the JavaScript workbench as a page keeps the main page with its WebContent process (C1, C4, C5), its graphics memory (C3) and the wait for the presentation of the main page in each layout transaction (one of the three waits of C9). The gain requires the workbench to be drawn by the host in native UI: decision D1.

**mygo violates the main-thread rule.** The application process holds JavaScriptCore VMs as soon as a view page or a document region exists, and Go code on the main thread then ends the process in `pas_panic_on_out_of_memory_error` ([main thread of the Wails host](../spec/hosts.md#main-thread-of-the-wails-host)). mygo runs every handler and every native UI build on the main thread in Go [S6]. The rule is met only by a change of the framework: U1 (D3).

**Native views need an element.** Plugin view pages, document regions and image regions are created by `native/darwin` (`sp_document_create`, `sp_region_create`) inside a `SurfaceHost` that `sp_surface_create` places in the window composition of the main web view ([`webview_geometry.h`](../../native/darwin/src/webview_geometry.h)). mygo places only its own web views [S14] and has no IOSurface path [S15]. The design therefore needs a native view element in mygo (U2) and a surface host without a main web view (N1) (D4).

**Costs that the native workbench adds.** The host process holds the state of the workbench in the Go heap, which the Go runtime collects at least every two minutes [S30], and, once assistive technology asks for it, the accessibility tree of every frame [S18]. The Metal layer keeps one window-sized drawable at rest and three while a window animates, and the Metal driver takes 30 to 45 MB for the first command buffer after a pause; both return about two seconds after the last frame, when a timer also releases the GPU instance buffers and the atlas, image and backdrop textures, so the first frame after a pause takes its drawable inside a step, while the main thread waits, and builds those buffers and textures again [S17]. A focused editable text field draws a frame every 530 ms for 30 seconds after it takes the focus, its text changes or its window becomes key, which keeps the drawables and the driver memory during those 30 seconds [S31]. A frame that changes the layer or the placement (box, clip or covers) of a web view or a native view element presents with the Core Animation transaction and takes its drawable inside a step, while the main thread waits, which costs a pass of the AppKit display cycle and a commit for each such frame [S17]; at v0.7.4 every frame of a window that shows a web view presents that way, even when nothing in it changed [S26], and U2 limits it to the frames that change the layer or a placement. Each step and each forwarded call is one exchange of two thread wakes between the worker and the main thread (U1): a frame that changes no size, layer or placement is 2 steps with 15 forwarded calls, and a pointer move is 1 step with 6 forwarded calls, 8 when the cursor changes, which on the mygo host follows a step of its own for the `hitTest:` that the pointer routing of `native/darwin` sends for each move (D3). Each Objective-C callback that the framework registers stays registered for the life of the process, a process holds at most 2,000 of them, and a registration past that number ends the process with a panic [S7][S32]. G2, G3 and G8 bound these costs; the `hitTest:` step runs only for a move that the event dispatch of the application delivers, so G2 and G8 measure it with HID moves of the real-input tool (`e2e/real/hid.mjs`).

## Architecture

### Host packages

The two Go hosts share their code; the framework is a framework adapter.

```
packages/host/go/          language host library (module, package host)    from packages/host/wailsv3/src
packages/host/rust/        language host library (crate soksak-host)       from packages/host/tauriv2/src
packages/host/wailsv3/     framework adapter: Wails v3
packages/host/mygo/        framework adapter: mygo
packages/host/tauriv2/     framework adapter: Tauri v2
```

- The language host library holds everything that does not name a framework: bindings, windows, workspace, surfaces, documents, images, sidecars, exposure, endpoint, event log, diagnostics and the darwin platform layer (`src/platform/darwin`, cgo with the `soksak-darwin` pkg-config package). The mygo host links this layer, so the mygo application is built with cgo; the packages of the mygo framework contain no cgo. Its framework port is two interfaces, named the same in both languages: `Framework` (application name, main-thread step, quit, dialogs, menus, Dock, and window creation with its title bar) and `Frontend` (event emit, window title, show, focus, the window events resize, move, focus, loss of focus, show and hide, the presentation notice, the settled presentation, the workbench start, and the workbench call channel). The application name (`wailsv3`, `mygo`, `tauriv2`) is the `application` of `endpoint.json`, the name of the endpoint socket, the host of the release key of the application update and the `host` of the state file of the debug view. The non-test Go files of `packages/host/wailsv3/src` hold 29,644 lines today; a second Go host without the language host library would repeat them.
- `surfaces.*` stays one file in the language host library. Its layout transaction waits for the presentation notice of the `Frontend` port: the Wails and Tauri framework adapters implement it with `AfterPresentation` of the main page, and the mygo framework adapter with U3 and the frame hold of the Surface layout row ([Operation groups](#operation-groups)). The workbench start reloads the main page on the Wails and Tauri framework adapters and builds the native workbench again on the mygo framework adapter, through its `Workbench` interface (build the workbench of a window, close it, deliver an event, deliver a call), which `packages/workbench-mygo` implements.
- The framework adapters hold `Run` and the implementations of the framework port. A file that only one language needs stays in its language host library; a file that only one framework needs is in its framework adapter. Each row of the allowed differences names its package. `scripts/check-hosts.mjs` compares `packages/host/go` with `packages/host/rust`; `packages/host/wailsv3`, `packages/host/mygo` and `packages/host/tauriv2` with each other; `packages/sok/go` with `packages/sok/rust`; and `apps/wailsv3`, `apps/mygo` and `apps/tauriv2` with each other. The audits of `scripts/check-hosts.mjs` that select files by a path prefix take these prefixes, and each fails when one of its prefixes selects no file: the main-thread audit takes `packages/host/go/src/platform/darwin/`; the undecoded command argument audit takes the Rust sources of `packages/host/tauriv2/src/`; the stub check takes the `src` folders of the language host libraries and of the framework adapters and the `src` folder of `packages/workbench-mygo`, each from the item that creates the package (F502-7, F502-12 and F502-15).
- The Rust language host library exists because the structure check compares the host packages of the two languages by relative path ([structure checks](../spec/hosts.md#structure-checks)): once the Go code divides into a language host library and framework adapters, the Rust code divides the same way. The Rust `Framework` and `Frontend` traits have one implementation, the Tauri framework adapter; they exist for that comparison. The Rust language host library takes about 40,800 lines of non-test code; 35 of its 105 non-test files name Tauri and divide between the library and the framework adapter.
- The Go framework adapters are packages named `adapter`, and the Rust framework adapter is the crate `soksak-host-tauriv2`. The Wails framework adapter defines the bound type `Bindings`, which passes each call to the bindings of the language host library, so the Wails binding service keeps the name `github.com/soksak-app/core/packages/host/wailsv3/src.Bindings`.
- `packages/sok/{wailsv3,tauriv2}` become `packages/sok/{go,rust}`. The command line has no framework code. Go selects the release identifier by a file that one build constraint compiles: `src/wailsv3.go` (`!mygo`, `app.soksak.wails`) and `src/mygo.go` (`mygo`, `app.soksak.mygo`); Rust keeps `RELEASE_IDENTIFIER` (`app.soksak.tauri`) in `src/identity.rs`. Row C7 of the allowed differences lists the two Go files.
- `apps/mygo` has `src/main.go`, `environment.json`, the staged view root (`frontend/modules`, `core-root.json`, `view-imports.json`), tests and manifests. It has no `runtime/index.js`, because no page runs the workbench: `environment.runtime` is required only for an application with a main page, the staging script stages no main page for `mygo`, and row A6 of the framework table lists the files of the main page runtime as absent on mygo: `runtime/`, `test/fixtures/start.json`, `test/clipboard.test.mjs`, `test/runtime.test.mjs`, `test/runtime-contract.test.mjs`, `test/runtime-lifecycle.test.mjs`, `test/start-module.test.mjs` and `test/surface-calls.test.mjs`. `make host-parity-check` reads `hostCalls` of `packages/workbench-mygo` as it reads `runtime/index.js` for the other hosts.

### Workbench

`packages/workbench-mygo` (Go module, package `workbench`) draws the workbench with mygo `ui` widgets and layout. `src/layout` holds the Go layout model: the grid and card geometry of `packages/soksak` and the projects, spaces and tabs of `packages/workbench`, with their stored formats. It imports no mygo package. The layout cases are JSON files in `docs/spec/cases`, which the tests of `packages/soksak`, `packages/workbench` and `packages/workbench-mygo` read. Screens: rail, library, cards and tab strip, sidebar frame and seats, menus, settings window, plugin screen, debug view, error display, modals. On the mygo host an interactive element is an element of the element tree of U4 whose actions include a press, an increment, a decrement, a value or an expansion (`ActionPress`, `ActionIncrement`, `ActionDecrement`, `ActionSetValue`, `ActionExpand` [S38]); the binder of `packages/workbench-mygo` connects each interactive element to a declared command and gives it its element name (D7) when it creates the element, and each visible state is a declared status. `core.workbench.audit`, and `audit(root)` of the plugin API with `unbound` of `core.surface.document`, list each interactive element that has no command or no element name as `{role, expose, command, text}` on every host, where `role` is an ARIA role name: on the mygo host the name that one table of `packages/workbench-mygo` gives each role of `ui.Role` [S38], and in a document the `role` attribute of the element or the implicit ARIA role of its tag, `textbox` for a `contenteditable` element; F502-13 changes `audit` of the plugin API, its contract cases (`create-binder.json`, `interactive.json`) and [exposure](../spec/exposure.md), and each plugin item of D7 takes them with its copies of the plugin API cases. A modal of the mygo workbench is a part of the workbench, and its controls run their commands through the same binder. `packages/workbench` stays the workbench of the Wails and Tauri hosts.

The two workbenches implement one product, and three mechanisms hold them equal:

- **Declarations.** `packages/workbench-mygo` embeds copies of `exposure.json`, `shortcuts.json` and `workbench.json` of `packages/workbench`, which `make exposure-check` holds equal to their source as it holds `core-exposure.json` today. `packages/workbench/workbench.json` is a new declaration file with the theme catalog (`THEMES`, `MODES`), the fonts (`FONTS`), the menu languages (`MENU_LANGUAGES` and the default language), the setting definitions (defaults, ranges, choices with the text size steps, switches and the keys that only the common scope holds) and the chrome metrics (every literal length, ratio and duration of `app.css`, `library.css` and `overlay.html`). `settings.js` and `text-size.js` import it as a JSON module instead of defining these values, the JavaScript workbench sets the chrome metrics as custom properties of the document root, which the stylesheets use, and a test of `packages/workbench` fails when a stylesheet of the workbench holds a literal length, ratio or duration. The keys that only the common scope holds are one list, the common-only keys of `workbench.json`. Each language host library embeds a copy of `workbench.json`, which `make exposure-check` holds equal to its source, as it holds the copies of `packages/workbench-mygo` ([projects](../spec/projects.md#persistence)). `make exposure-check` also applies rules 1 and 2 of the exposure check to the Go sources of `packages/workbench-mygo`: every status, command and element name that a Go source passes to the registry or the binder is declared, every declared status and command is registered, and every declared element name is given to an element.
- **Host calls.** `packages/workbench-mygo` calls the host handlers of the language host library only through one table, `hostCalls` in `src/host_calls.go`, which names each handler. The workbench runs each handler of `hostCalls` on a goroutine of its own and receives its answer in a later step, as each service call of the Wails host arrives on a goroutine of its own, because `SyncSurfaces` and `PresentSurfaces` wait for work that runs on the worker of U1; each such goroutine starts through `routine.Go` of the language host library, and a call whose order a specification requires, as the sends to one sidecar, starts only after the previous call of that order has finished. [Host parity](../spec/host-parity.md) proposition 1 reads that table as it reads `METHOD` and `COMMAND` of `runtime/index.js`: each name of each table has a handler of its host, and the three tables hold the same names except the calls that a row B of the framework table lists as absent on mygo (the overlay calls of the native modal web views and the shape calls).
- **Behavior.** Proposition 6 of [host parity](../spec/host-parity.md) states that the three applications declare the same statuses, commands and element names and that every window check runs against the three applications, except a check whose subject is the main page or a modal web view, which iterates `MAIN_PAGE_APPS`; F502-16 adds it, and `scripts/check-host-parity.mjs` decides it with the copy rule of `make exposure-check` and the rule of `scripts/check-e2e-host-parity.mjs`.

### Native views

- **View pages and document regions** keep `native/darwin` (`sp_document_create`, document regions) and the view contract unchanged. The container of the surface hosts of a window lies in the native view of the window (U2), which fills the content of the window under the Metal surface; the workbench shows each surface through a native view element (U2) that paints a hole over it and computes the covers where the workbench draws over it, and the layout transaction sets the frames of the surface hosts, in the content coordinates of the window as on the other hosts, in the Core Animation transaction of the frame that draws the cards. Plugin pages, those built with a library and those that load WebAssembly among them, run in view pages unchanged, because the view page, its channel and the view contract are unchanged. The mygo host makes no web view through `ui.WebView`: mygo makes each web view with its own configuration and delegate [S10][S14], and a view page needs the configuration of `native/darwin`, with the soksak scheme handler and the script message handlers of the view channel ([`document_view.m`](../../native/darwin/src/document_view.m)).
- One container per window keeps one placer for each geometry: the layout transaction places every surface host in the content coordinates of the window, and `native/darwin` converts that frame into the coordinates of the container when it applies it (`webview_geometry.m`, `webviewSetFrame`), so a holder that mygo moved in the same frame would put the host in the wrong place.
- **Image regions** keep the `CALayer` of `image_region.m` with the leased IOSurface, so the lease's in-use rule, the color handling and the frame identity stay one implementation for three hosts, and the mygo renderer draws no frame for a terminal frame. Importing the IOSurface as a Metal texture is rejected: the mygo renderer would upload each terminal frame and draw a frame for it, and the lease rule would move into the framework.
- **Modals** (settings window, menus, dialogs) are native UI; the native modal web views are not created by the mygo host.

### Exposure and window checks

The element tree of the workbench (U4) gives the binder audit, element rectangles and element actions their answers, so the window checks run against the three applications through `endpoint.json`, except the checks whose subject is the main page or a modal web view ([Shared contract changes](#shared-contract-changes)).

## Framework changes

The mygo host pins a framework fork with a go.mod `replace`, as the Wails host pins its Wails fork (F292-37-3). Each change is a change of the framework's packages; each is verified by a test in those packages and by the core item that uses it.

| ID | Change | Reason |
| --- | --- | --- |
| U1 | Main-thread worker: Go code runs on a goroutine locked to a thread other than the main thread. The worker starts in `App.Run` before `Backend.Init` and ends when `App.Run` returns. `App.Run` runs its Go code before the run loop (`Backend.Init`, the settings made before `Run`, `quitOnSignals` and `Signal`) as one step, and `finish` with its `OnQuit` listeners as another step. The main goroutine starts each step through the function that runs a block on the worker from the main thread, so the main thread waits for each step on its own stack and meanwhile runs the calls that the worker and other threads forward to it. A callback that reaches the main thread during those steps runs on the worker as a nested step. Each Objective-C method and block that mygo makes through purego (`objc.RegisterClass`, `objc.NewBlock`) and each C callback that it passes (`purego.NewCallback`) enters through an assembly trampoline of mygo: after `objc.RegisterClass`, mygo sets the implementation of each method of the class to a trampoline (`method_setImplementation`); mygo replaces the invoke function and the dispose function of the descriptor of each block it makes with trampolines; and mygo passes a trampoline in place of each C callback pointer. A trampoline calls the function that purego made for it, and purego is unchanged. Called on the main thread, the trampoline stores the argument registers, wakes the worker through a Mach semaphore and waits; while it waits, the main thread runs only the calls that are forwarded to it, those of the worker for that step and those of other threads, and returns the answer that the worker writes. Each step runs in an autorelease pool of the worker that the worker drains when the step ends; before that drain the worker retains an object that a callback returns to its caller and autoreleases it through a forwarded call in the pool of the main thread, so that the drain of the worker pool does not deallocate an object that the callback autoreleased on the worker and the autorelease on the main thread does not take a reference that the callback did not give. Called on another thread, the worker among them, it enters Go on that thread. During a step the worker counts as the main thread for `onMain`, `RunOnMain` and `await`, and `await` forwards `Backend.Step`; a forwarded call that delivers another callback (a modal panel, a menu, a drag, `makeFirstResponder:`, which sends `resignFirstResponder` and `becomeFirstResponder`) runs that callback on the waiting worker as a nested step that ends inside the outer step. Each call that mygo makes on a thread other than the main thread into an Objective-C object or a system framework function is forwarded to the main thread, except these, which run on the calling thread: the messages to a Metal object other than a drawable (an object that conforms to a protocol of Metal: the device, the command queue, a command buffer, an encoder, a texture, a buffer, a library, a function, a pipeline state or a sampler state), the encoding of a frame, the `commandBuffer` of the queue, the `presentDrawable:`, `commit`, `waitUntilScheduled`, `waitUntilCompleted` and `status` of a command buffer and the `width` and `height` of a texture among them, the messages to the Metal descriptor classes and their instances (`MTLRenderPassDescriptor`, `MTLRenderPipelineDescriptor`, `MTLSamplerDescriptor`, `MTLTextureDescriptor` and the attachment descriptors and descriptor arrays that they return), the `texture` of a drawable and `nextDrawable`; Core Text and Core Graphics; the functions of the Objective-C runtime other than `objc_msgSend`, `objc_msgSend_stret` and `objc_msgSendSuper`, a call of which is a message send that U1 judges by its selector and receiver, and the messages `retain`, `respondsToSelector:` and `isKindOfClass:` that `NSObject` implements; the messages `release` and `autorelease` sent to an `NSString`, `NSAttributedString`, `NSNumber` or `NSData` or a mutable form of one, a Metal object (an object that conforms to a protocol of Metal), a Metal descriptor or a drawable of a `CAMetalLayer`, while a `release` or an `autorelease` of any other object, an `NSArray`, an `NSDictionary` and their mutable forms among them, is forwarded, because the last release runs the `dealloc` of the object on the thread that sends it and the `dealloc` of a collection releases the objects that it holds, and an autoreleased window then goes to the pool of the main thread, as mygo intends for a window that AppKit is still closing; ### Native library change N1

`sp_surface_create` takes the main web view today: it wraps that web view in a window composition (`SPWindowComposition`), which holds the window overlays, the file drop view and, above the web view, the container of the surface hosts (`SPSurfaceCoordinates`), and places the surface host in that container. The language host library takes the block from the settled presentation of the `Frontend` port: the Wails and Tauri framework adapters implement it with the block of their main web view, and the mygo framework adapter with the block that the Surface layout group makes from a Go function of the adapter, which asks the workbench for a frame without a hold and calls back on its U3 notice; a notice that the scene presented nothing for want of damage calls back at once, a notice that its frame found no drawable asks for the frame again, and a notice that the window holds its frames asks for the frame again when the adapter releases that hold. The mygo host calls neither `sp_surface_set_window_overlays` nor `sp_window_file_drop`: the workbench draws over native views through the covers of U2, and the mygo surface view receives a dropped file as a workbench event.

## Decisions

Each decision states what the mygo host does and why.

- **D1 Native workbench.** The mygo host draws the workbench in native UI. Reason: page mode keeps C1, C3, C4, C5 and the wait for the main page in C9 (see [Consequence](#consequence)).
- **D2 Host packages.** A language host library per language, a framework adapter per framework, and `packages/sok/{go,rust}`. Reason: a second Go host otherwise repeats about 29,600 lines, and the structure check compares the packages of the two languages by relative path.
- **D3 Main-thread worker by assembly trampolines (U1).** Go code of the mygo host runs on a worker thread; each callback that AppKit makes on the main thread enters through an assembly trampoline that hands the step to the worker, and the main thread runs the calls that are forwarded to it. Reason: the [main-thread rule](../spec/hosts.md#main-thread-of-the-wails-host) holds only when no Go code runs on the main thread; a purego callback runs Go on the thread that calls it [S29], AppKit calls the methods that mygo registers on the main thread [S4][S6], and mygo builds without cgo [S5], so the C worker of the Wails fork cannot be the mechanism, and the step with its forwarded calls is the one that the Wails host runs for every callback (F292-37-1, F292-37-3). The cost of U1 is, for each step and for each forwarded call, one exchange of two thread wakes through a Mach semaphore and the return of the worker from a native wait, which needs a P of the Go scheduler: when sysmon took the P of the waiting worker and no P is idle, as during a garbage collection mark phase, the worker waits on the global run queue until a thread schedules it. A frame of a window whose content changed, without a change of the window size, the layer or a placement, is two steps, the tick of the display link and the callout of the run loop observer that each frame arms, with 15 forwarded calls: the size and the scale of the window three times, the screen and its refresh rate twice, the bounds of the superlayer twice, the occlusion state, and the layer and its display flag in the tick. A frame that presents with the transaction, which U2 limits to a frame that changes the layer or a placement, adds the `present` of its drawable, and a changed placement of a mygo web view adds 4 calls. One change of the window size in a live resize is five steps, `setFrameSize:`, `windowDidResize:`, `wantsUpdateLayer`, `updateLayer` and the callout of the run loop observer that the frame of `updateLayer` arms, with 20 forwarded calls together and four nested steps of the `isFlipped` that the `setFrameSize:` of `NSView` sends to the surface view, a pointer move is one step with 6 forwarded calls and 2 more when the cursor changes and a nested step of the `isFlipped` that its `convertPoint:fromView:` sends, and on the mygo host, while a view page is registered for input, a second step before it, the `hitTest:` of the mygo surface view that the pointer routing of `native/darwin` sends to the content view for each move, with its own forwarded calls and a nested step of the `isFlipped` that the `hitTest:` of `NSView` sends; a key is one step with 7 forwarded calls, the `release` of the array that hands the event to `interpretKeyEvents:` among them, in which each callback of the input method is a nested step [S33]. Shaping text forwards a call only for the first use of a system font style [S34]. F502-3 tests, in a window that holds no web view, as no window of the mygo host holds a web view made through `ui.WebView`, that the forwarded calls of each kind of step are at most these counts, and G8 bounds the frame, the pointer step and the steps of a resize at one display period at 120 Hz (8.33 ms), forwarded calls included, in the final phase.
- **D4 Image regions as native layers.** The native view of a window (U2) holds the container of its `SurfaceHost`s, and image regions keep their `CALayer` with the leased IOSurface (N1). Reason: one lease implementation for three hosts, and the mygo renderer draws no frame for a terminal frame.
- **D5 Terminal surfaces keep their view page.** The `term` plugin keeps its view composition with one image region (`input: "dom"`) on the three hosts. Reason: the view page owns the screen state, the input and the exposure of the terminal (C8): its overlays, tab reports, clipboard, links, settings, theme and text size calls, shortcut forwarding and element names. A surface shows a page of its plugin, and the layer of a screen is not chosen by measurement ([plugin processes](../spec/plugin-processes.md#layer-rules)).
- **D6 Toolchain.** Go 1.27.3 for `go.work` and every module of it. Reason: mygo requires Go 1.27.3 [S3]; the `go` line of `go.work` is at least the `go` line of every module it uses, and CI installs the version of `go.work` with `GOTOOLCHAIN=local`, so every Go build of core runs on Go 1.27.3 once `packages/host/mygo` is in the workspace, and one language version holds for every module.
- **D7 Element names.** The exposure kind `dom` becomes `element` on every host and in every plugin declaration (see [Shared contract changes](#shared-contract-changes)). Reason: the window checks address workbench elements by name; on the mygo host those elements are native UI, so `dom` would name them wrongly, and one concept has one term ([terms](../spec/terms.md)). Each plugin repository changes `exposes.element` in `plugin.json`, its `expose.element` calls, its tests, its copies of the plugin API cases and every other record that the term check of KR9 rejects (the comments of `ui/view-exposure-port.js` of term and terminal, of `ui/section-view.js` of browser and of `ui/tree.js` and `ui/bookmarks.js` of files, and `docs/spec/tree-view.md` of files), pins the records kit release of KR9, and raises `engines.soksak` to the core release of F502-13. The core release of F502-13 publishes first; each plugin release follows it, and one registry pull request lists that core version in `core.json` together with the plugin versions ([registry](../spec/registry.md)). The core release of F502-13 refuses `exposes.dom` with `plugin <id>: exposes.dom is removed; an exposed element is declared in exposes.element`, as it refuses the removed members `host` and `hostOperations`. This makes a core release require plugin releases, which [plugins](../spec/plugins.md#repositories) does not allow today; F502-5 states it there as the one exception. The core release of F502-13 is the item F502-13-1 of core. Each plugin change and release of D7 is complete before F502-25 starts, because the other hosts and the mygo host install the plugins of the workspace registry, which the core of F502-13 refuses while a plugin declares `exposes.dom`.
