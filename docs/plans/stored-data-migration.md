# Stored data migration from shipped definitions

This proposal is pending; its approved content moves into `docs/spec/installation.md`, `docs/spec/plugins.md`, `docs/spec/host-contract.md`, `docs/spec/settings.md`, `docs/spec/projects.md` and the agent guidance, and the proposal is then removed (checklist F188, F189).

## Background

The release 0.0.13 refuses to start on a configuration whose `plugins/installed.json` a release of the same product line wrote earlier: `installed plugins: <file>: browser: unknown field package`. The change that removed the `package` field from the entries (the plugin vocabulary change, 2026-10-11) did not raise the format number (`InstalledFormat` stayed 2), so no version difference announced the change, no migration could attach to it, and the reader—correct under the guidance that forbade migrations—left the person with no path: the host fails at startup, so not even a reinstall command runs. Removing only the `package` member lets the stored file start (measured: both applications started after that single edit), so the range grammar is not part of the defect.

The check suites never meet this transition: every check starts from a configuration the current installer just wrote, and no check executes a release build at all. The transition "data of the previous release plus the binary of the new one" has no coverage.

Two earlier migrations (the installed format 1→2 path conversion, the stored layout and settings conversions) were deliberately removed under the no-migration guidance days before; the guidance amendment below answers those recorded reasons instead of ignoring them.

## Decision

Stored data migrates mechanically from definitions that ship with the package. The contract names every stored file of a configuration folder with its owner, its format-number carrier and its class (numbered, transient, log, external, fetched):

1. **A format change raises the format number and ships a migration definition.** A definition is an ordered list of named, parameterized operations implemented once in the engine (`setFormat`, `removeField`, `renameField` initially); a change no operation covers adds one operation to the engine as a deliberate change with paired tests. A definition names exactly one file (validated at load); a change that moves folders or crosses files is refused in the schema and takes a different, named path.
2. **The definition ships with the package.** Core's definitions live in this repository as one source (`packages/sok/migrations/*.json`) embedded by both `sok` builds (`go:embed`, `include_str!`). A plugin or sidecar ships its definitions in its release when it owns a stored file; its manifest declares them; the form is the same for the three owners. A definition uses only the operations of the core its `engines.soksak` range requires; an unknown operation is refused naming the definition, its owner and the operation. Released plugin and section identifiers are immutable once published.
3. **Core performs every migration.** One engine (in `packages/sok`, Go and Rust twins; the write behavior is a unification the engine introduces: the Go `replaceFile` gains a sync before the rename that the Rust twin already has—the existing helper is extended, no second writer, and the parity record states the change) applies definitions **at the entry of the shared reader of each contract file** (`ReadInstalled`/`read_installed`, and the registry reader): every reader in every process—the host start after the event log starts, the host's plugin-change path, every `sok` entry that reads the file (`plugin install|update|remove|enable|disable|list`, `debug replay`, `app update`, `registry use`)—migrates before it reads, so an enumeration of entries cannot go stale. The engine never creates a file that is absent, and never runs while another process owns the configuration (the existing ownership error names it; the `sok` commands gain the ownership check as their own registered item). A migration the engine applies is a record of the process that applied it—a host event for a host entry, an event of the tool process for a `sok` entry—and a refusal is the record. Plugin-owned values inside a file keep the `convertData` contract; a plugin's definitions can name no file today. A sidecar's definitions name only paths under its own `services/<name>/` tree and apply while its service is stopped.
4. **The engine is idempotent and bounded.** Definitions accumulate within a release series; the chain migrates every form from the floor to the current one. The floor is the oldest format of the current configuration-folder lineage: format 2 (installed by the identity change that created the lineage on 2026-10-04). The format-1 form belonged to the earlier application identity, and the recorded removal that closed that lineage is the boundary: a configuration of that lineage is refused with an error that names the file and its format, and no 1→2 definition ships. This floor strands a shipped form by an owned decision, stated here, and applying twice writes the same bytes. A form below the floor or above the newest target is refused with an explicit error naming the file and both numbers. The reader keeps accepting only the current format, and the reading code of an earlier form is not kept: the definition and the engine replace it.

## First application (F188)

- `plugins/installed.json` becomes format 3; the definition `2→3` removes the `package` member of every entry and sets the format number. Nothing else changes.
- Engine `MigrateInstalled` in both `sok` packages; application at the corrected anchors: Wails `host.go` between the event log start and `ApplyPluginEventClasses`; Tauri `host.rs` between the event log start and `apply_plugin_event_classes`; the `sok` entries above.
- `settings.json` and `projects.json` receive format numbers and engine coverage as registered sub-items (F188.4, F188.5): both carry no number today, their readers refuse earlier forms, and the records show settings.json refusing people four times and projects.json once (the layout refusal of the same configurations).

## Checks (F189)

- Owning tests (both languages): the released format-2 form migrates, the host starts, the file is format 3, a second start writes nothing, a reload re-reads current form; a missing file stays missing; a form above the newest target and an unparseable file are refused naming file and numbers.
- A declared release step runs a release-built host once on the format-2 form and requires the migration and the first host log line, and runs the release `sok` against the same fixture; a workflows test asserts the step.
- A mechanical check ties the writer's stored schema, the reader's strictness and `InstalledFormat` together at change time, and reports every spec, test and fixture mention of the installed format number that differs from `InstalledFormat`; the F189 fixture names the previous released form, so the check holds it to that form.
- The new concepts (migration definition, floor, the operation names, the file classes, and the named path for a change that moves folders or crosses files—a replacement change, documented in its release and carried out by reinstalling) are registered in the term list with the spec move.
- Spec corrections ride the same change: `installation.md` (no-file default), `host-contract.md` (format-1 default line, absolute-`path` line, the changed installed cases), the stale comments that still describe the removed format-1 conversion (`installed.go`, `installed.rs`), and the guidance amendment in both languages, which states why it answers the two recorded removals: a definition is release-shipped data applied once at the install moment; after application the data is ordinary current-format data; no earlier-form reader code is kept.

## Adversarial review

Three reviewers examined (a) whether the definition form covers this repository's real format changes, (b) the runtime failure modes, (c) the design against alternatives and the defect class beyond `installed.json`. Round 1 produced 21 consolidated objections; the decision above incorporates the answers. The corrections adopted: exact application anchors (installed.json is read before the originally cited points), the `sok` entries that read contract files before any host, one-file-per-definition, one durable write in both twins, never creating an absent file, explicit refusal for forms above the newest target, the caret conversion dropped (the grammar accepts `^` today), the honest operation vocabulary, the file inventory with `settings.json` and `projects.json` registered, `convertData` kept as the plugin-data contract, released identifiers immutable, the stale spec lines, and the recorded-removals answer.

Round 2 (of at most 5) used NEW reviewers, two of them, whose criteria were reconciled with the owner's before their audits began. Outcome: the verifier confirmed all ten factual claims against the code in both language twins (with corrected anchors, adopted as binding) and found the race registration missing (answered: registered as F190) and one records gap (the "twice" count; the text now states the recorded counts); the independent auditor upheld the architecture, rejected none of its own outright conditions, upheld the three resolved conflicts, and objected on four points (the entry enumeration, the race registration and the sok ownership check, the floor wording against the format-1 lineage, the write unification stated as a change), all answered by the amendments above, together with its minor content (the term registrations, the named replacement path, the record form of a sok-entry application, the fixture tie of the format-mention check). Both reviewers stated no further objection once answered. Each round is audited by agents that took no part in earlier rounds, so no reviewer confirms its own objections; a round ends when its audit leaves no unanswered objection. The three conflicts resolved in round 1 that the new reviewers judge independently: definitions accumulate within a release series with a floor (against one-step pruning); `settings.json` and `projects.json` join as sub-items rather than staying refusal-only; the ownership rule for the `sok` command path (refuse while a live process owns the configuration; the unlocked read-modify-write race of the plugin commands is registered as its own defect).
