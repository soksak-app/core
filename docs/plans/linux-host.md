## Framework facts on Linux

### Wails v3.0.0-beta.27

- The default Linux build uses GTK4 and WebKitGTK 6.0: `linux_cgo.go` has the build constraint `linux && cgo && !gtk3` and the directive `#cgo linux pkg-config: gtk4 webkitgtk-6.0` [S1].
- GTK3 and WebKitGTK 4.1 are used only with the `gtk3` build tag: `linux_cgo_gtk3.go` has the constraint `linux && cgo && gtk3` and `#cgo linux pkg-config: gtk+-3.0 webkit2gtk-4.1 gdk-3.0` [S2]. The benchmark notes of the same release call the GTK3 build "legacy, opt-in via -tags gtk3, removed in v3.1" [S3].
- Native handles: `WebviewWindow.NativeWindow()` returns `impl.nativeWindow()`, which on Linux is the `window` field of `linuxWebviewWindow`, the `GtkWindow` pointer; the same struct also holds `webview` and `vbox` pointers, which are not exported [S4]. In the GTK3 build `windowNew` creates a vertical `GtkBox`, adds it to the window, and creates the `WebKitWebView` with `webkit_web_view_new_with_user_content_manager` [S5]. The host can therefore reach the `WebKitWebView` only by walking the children of the `GtkWindow` it receives, as the macOS host walks the content view today (`MainWebview`).
- Wails has no child-webview API on any platform (allowed difference H4 in [hosts](../spec/hosts.md#allowed-differences)); on Linux the host would create surface, modal, and document webviews in C, as `webview.m` does on macOS.

### Tauri v2.12.1 (tao 0.37.1, wry 0.57.0)

- Tauri on Linux uses GTK3 and WebKitGTK 4.1 only. wry depends on `gtk` 0.18 and `webkit2gtk` =2.0.2 with feature `v2_38` on Linux targets [S6]; `webkit2gtk-sys` 2.0.2 links the system library `webkit2gtk-4.1` [S7]; tao depends on `gtk` 0.18 [S8]; `gtk-sys` 0.18 links `gtk+-3.0` [S13]. No GTK4 variant exists in these crate versions (no GTK4 dependency appears in [S6] or [S8]).
- Native handles: tao `WindowExtUnix::gtk_window()` returns `&gtk::ApplicationWindow` and `default_vbox()` returns `Option<&gtk::Box>` [S8]; Tauri exposes them as `Window::gtk_window()` and `Window::default_vbox()` [S12]. `Webview::with_webview` gives a `PlatformWebview` whose `inner()` is a `webkit2gtk::WebView` on Linux [S12]; wry `WebViewExtUnix::webview()` returns the same type [S9].
- Child webviews: on Linux `tauri-runtime-wry` builds a `WindowChild` webview with `build_gtk(window.default_vbox())` [S11], and wry packs a webview built in a `GtkBox` with `pack_start(webview, true, true, 0)` [S10]. wry applies `set_bounds` only to a webview in a `GtkFixed` or an X11 child window [S10]. A webview from Tauri's `add_child` is therefore stacked in the box and does not take the bounds the host gives it. `build_as_child` works only on X11, and wry recommends `build_gtk` with `gtk::Fixed` to support X11 and Wayland [S9].

### Consequence

The two hosts share one platform interface and, on macOS, one native library. On Linux they can share one native library only if both use the same toolkit, because GTK3 and GTK4 widgets, events, and drawing APIs differ. Tauri offers only GTK3 [S6][S8]; Wails offers GTK3 only until v3.1 [S3]. This is decision D1 below.

Both frameworks place the main webview in a `GtkBox`. The Linux platform layer must move each webview it composes (main, surface, modal, document) into a container that it owns, so that it can set bounds, stacking, and input regions. Moving a `WebKitWebView` between GTK3 containers (`g_object_ref`, `gtk_container_remove`, `gtk_container_add`) without reloading its page is **unverified**.

## vt sidecar on Linux

The macOS sidecar draws each frame with CoreText into a global IOSurface (`kIOSurfaceIsGlobal`, BGRA, a 16-byte nonce in the `soksak.frame` value) and sends the IOSurface ID in the [image envelope](../spec/sidecars.md#image-envelope) with `token.kind` `iosurface-global` (`vt-core/src/platform/darwin/frame.m` in the sidecar repository). The host looks the IOSurface up by ID, checks nonce, size, pixel format, and scale, copies the pixels, and replies `consumed` ([`image_region.m`](../../native/darwin/src/image_region.m)). Linux has no IOSurface; the rasterizer and the token change, the copy-then-`consumed` rule of [surface composition](../spec/surface-composition.md#image-transfer) stays.

### Font rasterization

1. Pango with cairo, written in C under the sidecar's `platform/linux/`: Pango lays out and draws glyph strings into a cairo context [S48], and its fontconfig base (PangoFc) finds fonts through fontconfig and FreeType [S49]. The structure matches `frame.m`: a font descriptor instead of `CTFontDescriptor`, a cairo image surface instead of a `CGBitmapContext`.
2. A Rust text stack such as cosmic-text: shaping with harfrust, font discovery with fontdb, rasterization with swash [S50]. Whether fontdb applies the user's fontconfig substitution and fallback rules is **unverified**.

### Frame transport

The persistent transport is a Unix socket between the host and the service ([terminal runtime](../spec/terminal-runtime.md)). Proposed token: `token.kind` `memfd`. The sidecar creates the transfer image with `memfd_create` (Linux 3.17 [S51]), seals it against shrinking (`F_SEAL_SHRINK`, which protects the receiver from `SIGBUS` [S51]), and sends the descriptor with the envelope line as `SCM_RIGHTS` ancillary data on the same socket; `memfd_create` documents this transfer [S51]. The host maps the descriptor read-only, checks its size against `stride × height`, copies it into its cairo surface, closes it, and replies `consumed`. The sidecar then reuses or closes its own descriptor. The authenticated connection replaces the nonce: only the peer that holds the descriptor can name the image, so `notFound` and `forbidden` become a missing or extra descriptor on the message.

Each language reads ancillary data differently. Go has `UnixConn.ReadMsgUnix` with an out-of-band buffer in the standard library [S52]. Rust's `UnixStream` ancillary-data methods are nightly-only (feature `unix_socket_ancillary_data`) [S53], so the Tauri host needs a crate for `recvmsg`, which is a new dependency. Both hosts must read the line and its descriptor with the same `recvmsg` call, because a buffered line reader cannot associate a descriptor with its line.

### Composition in the host

Group 12: the region is a `GtkDrawingArea` in its surface's `GtkFixed`, painting the host-owned `CAIRO_FORMAT_ARGB32` surface [S30] at device scale [S31]. A frame is accepted only when its width, height, and scale equal the region's raster at the integer GTK scale [S26]. The commit rule of [native surfaces](../spec/native-surfaces.md) (every visible region has its exact current raster before a layout commits) is unchanged.

### Decisions for the user

Each decision states the recommended choice and the reason. The choice is the user's because it fixes a dependency or a contract that later items build on.

- **D1 Toolkit.** Recommended: GTK3 and WebKitGTK 4.1 for both hosts, with the Wails `gtk3` build tag [S2]. Reason: Tauri has only GTK3 [S6][S8], and one shared `native/linux` library keeps one implementation and one test set for both hosts, as `native/darwin` does. Wails states that v3.1 removes the GTK3 build [S3]; that release reopens this decision, and the choice then is a GTK4 library for Wails beside the GTK3 library for Tauri.
- **D2 Display servers.** Recommended: build on GTK's backend selection so the application runs on X11 and Wayland (`GDK_BACKEND` selects the backend [S54]); window checks run on X11, because window capture [S36][S37] and `MoveWindow` [S28] are not available on Wayland without user interaction. Operations that a backend cannot provide return `<operation> is not implemented on wayland`.
- **D3 Font rasterizer.** Recommended: Pango with cairo (option 1). Reason: GTK3 and WebKitGTK already require these libraries on every machine that runs the host, fontconfig applies the user's font configuration and fallback [S49], and the C structure mirrors `frame.m`.
- **D4 Frame transport.** Recommended: sealed memfd passed with `SCM_RIGHTS` on the persistent socket. Reason: no file name exists that another process could open, the descriptor is the authorization, and the copy-then-`consumed` rule needs no change. The cost is a Rust `recvmsg` dependency [S53].
- **D5 Presentation wait.** Recommended: make R2-7-4 a prototype that measures, in a tracked test, whether the toplevel frame clock's `after-paint` [S24] after a DOM change follows WebKitGTK's drawing of that change. If it does not, the [native surfaces](../spec/native-surfaces.md) commit contract cannot be met with public WebKitGTK API, and that finding returns to the user before any other Linux host item.
- **D6 Window buttons.** Recommended: a `GtkHeaderBar` title bar [S25] above the page, so the page reserves no button area on Linux and `WindowControls` reports the header bar's button box. Reason: the macOS layout depends on AppKit centring the buttons in a title bar of the height that the page requests ([hosts](../spec/hosts.md#window-buttons)), which GTK does not provide.
- **D7 Window motion.** Recommended: move `InstantWindowResize` out of the cross-platform interface into the macOS window preparation. Reason: no GTK3 resize animation to shorten was found (**unverified**), and an operation that succeeds without effect would be a stub, which [hosts](../spec/hosts.md#rules) forbids.
- **D8 Reload memory.** Recommended: replace the app DOM `WebKitWebView` with a new view in a new web process for each main-frame document load, keeping the old view on screen until the new one commits. Reason: it uses only public API and ends the process that holds replaced documents; **unverified** that a new view gets a new web process under the WebKitGTK process model.

## Implementation order

Each item is a sub-item of R2-7 and is entered in [features](../features.md) before it starts. Verification runs on the build-machine Linux lane unless an item says otherwise. Item 1 decides whether the remaining items are feasible.

Verification: the test's measured pixels and timestamps; a negative result is reported to the user.
2. R2-7-5 — Toolkit and build (D1): `native/linux` library with pkg-config file, Wails `gtk3` tag, Tauri Linux target, `make platforms` and `make hosts-check` accepting `platform/linux/`. Verification: both hosts build on Linux and fail at startup with each unimplemented operation named.

5. R2-7-8 — Surfaces, shapes, input monitoring, and the layout transaction (groups 9, 10, 14, 15). Verification: the geometry and presentation window checks under X11.
6. R2-7-9 — Document regions (group 11). Verification: `browser.test.mjs` document-data and navigation cases.
