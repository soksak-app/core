# mygo host 제안

[English](mygo-host.md)

상태: checklist item F502에 대한 승인 대기 중인 proposal이다([기능 상태](../features.ko.md)의 F502-1). 이 proposal의 어느 것도 구현되지 않았다. F502-3은 U1을 구현하고 F502-4는 U2를 N1과 함께 구현하며, 각각 framework의 package와 `native/darwin`에 자기 test를 둔다. 각 item은 자기가 바꾸는 계약의 specification 문구와 지침을 쓰며, 여기에는 check 데이터 `docs/spec/events.json`, `docs/spec/hosts.md`, `docs/spec/host-contract.md`와 `dom`, `page.start` 또는 두 host를 언급하는 [AGENTS](../../AGENTS.ko.md)의 줄이 포함된다. F502-5는 승인된 나머지 내용을 specification([host](../spec/hosts.ko.md), [native host 인터페이스](../spec/native-host.ko.md), [surface 합성](../spec/surface-composition.ko.md), [native surface](../spec/native-surfaces.ko.md), [native modal](../spec/native-modals.ko.md), [plugin](../spec/plugins.ko.md), [plugin process](../spec/plugin-processes.ko.md), [exposure](../spec/exposure.ko.md), [endpoint](../spec/endpoint.ko.md), [설치](../spec/installation.ko.md), [host 계약](../spec/host-contract.ko.md), [host 동일성](../spec/host-parity.ko.md), [성능 trace](../spec/performance-trace.ko.md), [로그](../spec/logging.ko.md), event catalog(`docs/spec/events.json`), [진단](../spec/diagnostics.ko.md), [registry](../spec/registry.ko.md), [command line](../spec/cli.ko.md), [debug view](../spec/debug.ko.md), [예제 모델](../spec/example-model.ko.md), [프로젝트](../spec/projects.ko.md), [설정 window](../spec/settings.ko.md), [용어](../spec/terms.ko.md), [글자 크기](../spec/text-size.ko.md), [sidecar](../spec/sidecars.ko.md), [검증](../spec/verification.ko.md)), 운영 문서 [예제](../operations/examples.ko.md)와 [private native API](../operations/private-native-apis.ko.md), 그리고 [AGENTS](../../AGENTS.ko.md)로 옮기고, 이후 item이 시작되기 전에 [기능 상태](../features.ko.md)에 있는 각 이후 item의 entry에 그 item이 바꾸는 계약을 쓰며, 그 뒤 이 파일은 제거된다.

mygo에 관한 모든 진술은 [출처](#출처)의 출처를 `[Sn]`으로 인용하며, 출처는 tag v0.7.4에서 읽었다. purego와 Go runtime에 관한 진술은 mygo가 요구하는 version을 인용한다. 현재 host에 관한 진술은 그것을 측정한 checklist item이나 그것을 구현한 파일을 인용한다.

## 문제

Wails host와 Tauri host는 workbench를 window마다 WKWebView 하나 안의 JavaScript page(main page)로 그린다. Plugin view, document region, image region은 그 page의 layout을 따르는 native view다. 측정된 비용은 다음과 같다.

| ID | 비용 | 측정 |
| --- | --- | --- |
| C1 | Main page 메모리 | 사흘 사용 후 242 MB(Wails)와 291 MB(Tauri)(F196); 프로젝트 하나, sidebar section 두 개, 탭 여덟 개가 있는 window에서 103.8 MB, 최고치 181.9 MB(F368); 재로드 후 446.6 MB(Wails)와 399.9 MB(Tauri)([plugin process](../spec/plugin-processes.ko.md#근거)) |
| C2 | Main page CPU | 각 애플리케이션의 main page process는 그리기가 실패한 뒤 CPU 100%에 머물렀다(F349) |
| C3 | Main page 그래픽 | F196.10.3 전에는 window 크기 buffer 약 다섯 개(1200×760에서 71 MB); 그 뒤에는 1200×760에서 20 MB로 window buffer 약 1.4개이며, page의 root tile과 그 surface document의 layer다(F196.10.3) |
| C4 | 빈 window의 process | release Wails host의 빈 library 화면 instance 하나는 약 208 MB가 든다: host 108, WebContent 54, GPU 32, Networking 14이며, 그중 WebKit process가 100 MB다(V5-96-14-6-4-9) |
| C5 | Modal | 설정 window와 각 menu는 자기 document를 가진 web view다([native modal](../spec/native-modals.ko.md)). 닫힌 modal은 web view도, 붙어 있던 native 객체도 남기지 않으므로(`e2e/modal-release.test.mjs`) 그 비용은 modal 하나가 열려 있는 동안 지속된다 |
| C6 | View process | 작은 page의 WebContent process 하나마다 약 11 MB이며 view 수에 따라 선형으로 늘어난다(F212.1); 유휴 브라우저 탭 하나는 Wails에서 53,808 KB(document 29,040 KB, main web view 증가 24,768 KB), Tauri에서 45,504 KB(document 30,880 KB, 증가 14,624 KB)가 들며, 비교 대상은 유휴 탭 benchmark의 상한 51,200 KB(`IDLE_TAB_BOUND_KB`, F292-40)다; 이 증가는 main page의 비용이며, mygo host에서는 host process가 이를 떠맡는다 |
| C7 | Host가 view에 보내는 post | 각 post는 `callAsyncJavaScript`를 실행하며, 그 뒤 응답이 view process의 foreground activity를 해제하고 다른 activity가 그 process를 hold하고 있지 않으면, 가려진 window의 모든 view에서처럼 WebKit이 RunningBoard를 동기적으로 조회한다(F374-7) |
| C8 | 터미널 frame | Tauri host에서, 가려지지 않은 760×614 point window에서 부하 평균 14에서 21일 때, 33 ms마다 갱신되는 status line 하나는 `term` plugin 0.0.4와 sidecar `alacritty` 0.0.4로 초당 27.6 frame에서 frame당 애플리케이션 CPU 1.6 ms가 들고, 다시 쓰는 20개 행은 27.5 frame에서 3.1 ms가 들며, CPU와 frame 수는 같은 출력의 별도 run에서 얻었다(sidecar alacritty S21, term P1-4); 어떤 record도 이 CPU를 host, view page, sidecar 사이에 나누지 않는다; `term` view page가 터미널의 화면 상태, 입력, exposure를 소유한다 |
| C9 | `terminal` 탭의 구분선 drag | trace를 끈 120 Hz에서: Wails 지연 median, p90, 최악 68.3, 97.6, 127.4 ms와 간격 34.1 ms, Tauri 90.0, 141.5, 196.6 ms와 33.7 ms이며, 비교 기준은 20.8, 25, 33.3 ms와 33 ms다; 60 Hz display 모드에서: Wails 61.0, 88.7, 116.9 ms와 34.2 ms, Tauri 66.8, 97.9, 130.6 ms와 33.9 ms이며, 비교 기준은 41.7, 50, 66.7 ms다(F212.14). cohort들은 display 모드와 부하가 다르며 지연을 단계에 귀속시키지 않는다(F239-223) |
| C10 | 브라우저 document | 브라우저 탭의 document web view 하나가 1.31 GB를 hold했다(F196) |
| C11 | 브라우저 section | 브라우저 plugin의 section 네 개는 `unload`를 선언하지 않으므로 숨겨진 동안에도 자기 view를 유지한다 |
| C12 | Host process 메모리 | 사흘 사용 후 각 host에서 약 154 MB(F196); release Wails host의 빈 library 화면에서 108 MB(V5-96-14-6-4-9); `make object-counts`를 30번 반복하는 동안 Wails host는 Go heap 객체 3~5 MB와 goroutine 50~52개로 80 MB에서 89 MB 사이에 안정되고, Tauri host는 70 MB에서 76 MB 사이에 안정된다(F196.23) |

C1, C4, C5는 page로서의 workbench가 치르는 비용이다: 그 상태, 그 WebContent process, 그것이 시작하는 WebKit process다. C3은 그 page의 그래픽 메모리다. native workbench는 이를 자기 Metal layer의 drawable(정지 시 window 크기 buffer 하나, window가 animation 중인 동안 세 개)과 일시 정지 후 Metal driver가 차지하는 메모리로 대체한다[S17]. C9의 각 layout transaction은 main page의 presentation, 합류한 각 root view의 presentation, 필요한 image raster를 기다리며([배치 순서](../spec/native-surfaces.ko.md#배치-순서), step 4), layout 하나는 frame 경계 네 개(입력의 도착, 그 앞 layout의 frame, WebKit의 rendering update, display 갱신)를 거쳐 화면에 이른다. native workbench는 main page에 대한 대기만 없앤다. 구분선 drag는 여전히 자기가 크기를 바꾸는 root view와 그 image region의 raster를 기다리며, G4는 그 drag의 지연 target을 mygo host에 그대로 적용한다. C2는 page의 비용이 아니라 main page의 결함 F349이며, mygo host에는 main page가 없다. G2는 실패하는 그리기가 mygo host를 계속 바쁘게 하지 않을 것을 요구한다. C6과 C7은 web view로서의 plugin view가 치르는 비용이며, [plugin process 결정](../spec/plugin-processes.ko.md#결정)이 이를 유지한다. C8은 view page의 image region을 지나는 터미널 frame의 비용이며, 이 경로는 mygo host가 유지하고(D5) G5가 세 host에서 상한을 둔다. C10은 WebKit 자체의 document 메모리이며 host 비용이 아니다. C11은 브라우저 plugin의 선언이며, browser P110이 이를 바로잡는다. C12는 mygo host에서 workbench의 상태를 가지는 process다.

## 목표

F502-2는 G1부터 G8까지의 값을 checklist ID 없이 [host](../spec/hosts.ko.md)의 Performance goals section에 쓰고, 각 값에 그것을 측정하는 scenario와 target을 함께 적으며, 거기서 G4는 [plugin process](../spec/plugin-processes.ko.md#통과값)의 통과값을 참조한다. 또 그 수치 상한을 `docs/spec/performance-goals.json`에 쓴다. 이 파일은 `scripts/b3-judge.mjs`(`make b3-judge`)가 읽으며, 유휴 탭 case와 분할 부하 case는 `e2e/chains.mjs`가 `docs/spec/events.json`을 읽듯이 자기 상수 대신 이 파일에서 어떤 specification도 정의하지 않는 `IDLE_TAB_BOUND_KB`와 `SPLIT_LOAD_GROWTH_BOUND_KB`를 읽고, 이 파일은 `e2e/package.json`의 `specFiles`에 들어간다. `hosts.md`와 `hosts.ko.md`에 있는 그 section의 표는 그 파일의 사본이며 `scripts/test/performance-goals.test.mjs`가 표를 그 파일과 같게 유지한다. [plugin process](../spec/plugin-processes.ko.md#통과값)나 [native surface](../spec/native-surfaces.ko.md#인수-기준)가 정의하는 값은, DOM mount baseline과 최대화와 복원의 따라잡기 한도도 그중에 포함되며, 거기서 참조하고 복사하지 않는다. 그 값을 가진 benchmark가 그 값을 판정하고 judge는 그 값을 읽지 않기 때문이다. 그리고 절차(other host와 baseline host의 정의, run, median과 spread, 회귀 규칙, run 조건, B3의 scenario와 그 phase)를 [예제](../operations/examples.ko.md)와 그 번역본의 Three-host benchmark section에 쓰며, 이 section은 baseline host의 revision을 그 checklist item으로 명명한다. 이 모든 것은 모든 측정 item보다 앞선다. 값은 맞추기 어렵다는 이유로 결코 낮추지 않는다. 값을 넘는 floor는 근거를 밝히는 adversarial review를 통해서만 그 값을 바꾼다(F212.14-6이 선례다).

"other host"는 mygo host와 같은 revision에서 build한 Wails host와 Tauri host를 뜻한다. "baseline host"는 측정 target item(F502-2)을 완료하는 revision에서 build한 Wails host와 Tauri host를 뜻하며, 이 revision은 Wails host나 Tauri host가 실행하는 코드를 바꾸는 모든 item보다 앞선다. 각 baseline host는 branch `test/b3-baseline-F502-25`의 head를 검증 checkout한 곳에서 build하고 실행한다. 이 branch는 F502-25가 그 revision에 만들며, 그 뒤로는 F502-26과 F502-27의 sub-item에서 측정 target을 바꾸는 commit만 담는다: 측정 target을 바꾸는 sub-item은 그 변경을 자기 commit 하나로 이 branch에 적용하고, 새 head를 other host checkout의 baseline record `target/b3/baseline.json`, 즉 `make e2e-b3`가 읽는 F502-25의 record에 쓴다. 그 record는 baseline host와 각 sidecar repository의 revision, 그리고 baseline host가 설치하는 각 plugin release의 version과 `sha256`을 담으며, commit id를 명명하지 않는 repository의 record 밖에 있다. 이 branch는 `main`에 결코 merge하지 않는다. F502-2의 revision 이후의 각 commit은 `main`이 가진 변경을 적용하기 때문이며, F502-27이 마지막 phase를 기록하면 F502-25의 sub-item 하나가 이 branch의 제거를 명시한다. 각 baseline host는 F502-26과 F502-27의 모든 run에서, F502-25가 [공개 registry](../spec/registry.ko.md)의 index에서 설치할 때 기록한 plugin release를 정확히 그대로 설치한다. 그 index는 그 revision의 core version에 대해 범위가 그 version을 포함하는 가장 새로운 version을 고르므로([version 선택](../spec/installation.ko.md#version-선택)) baseline host는 D7 release 이전에 발행된 plugin release를 실행하며, 설치된 version이나 `sha256`이 그 record와 다르면 run은 실패한다. 그 revision의 core version은 공개 registry의 `core.json`이 나열하는 version이다. other host와 mygo host는 모든 build와 window check가 그러듯이 workspace registry에서 plugin을 설치한다(`make registry`). 다섯 애플리케이션 모두 workspace registry가 진단용으로 build하는 sidecar release를 실행하므로(`make registry SIDECARS=diagnostic`, F502-2) 모든 애플리케이션이 같은 sidecar build를 실행한다. baseline host의 설치가 scenario의 plugin에 대해 release를 하나도 고르지 못하거나, 고른 plugin이 workspace registry의 sidecar version을 배제하면 F502-25는 실패한다. 각 run은 설치된 모든 plugin과 sidecar의 release version과 `sha256`, 그리고 각 build의 Go와 Rust toolchain version을 기록한다. 다섯 애플리케이션 모두 같은 session에서 교차 순서로 측정하며, 어느 애플리케이션이든 다음 run을 하기 전에 각 애플리케이션이 run을 하나씩 하고, 각각 run 일곱 번을 한다. 값은 그 run들의 median이며, 값의 spread는 그 run들의 범위다. 상대 기준은 mygo host의 spread가 other host나 baseline host의 같은 값의 spread보다 전부 제한 방향 쪽에 놓일 때에만 실패한다: 시간, CPU time, footprint에서는 mygo host의 가장 낮은 run이 그 host의 가장 높은 run보다 위에 있을 때이고, frame rate에서는 mygo host의 가장 높은 run이 그 host의 가장 낮은 run보다 아래에 있을 때다. other host의 값은 G2, G3 또는 G5부터 G8까지의 상대 기준이 그 값을 비교하고, 그 spread가 같은 의미에서 자기 baseline host의 같은 값의 spread보다 전부 제한 방향 쪽에 놓이면 회귀다. 값의 분포가 같은 두 애플리케이션은 비교 3,432번 중 1번 우연히 어느 한 조건을 만족한다(1/C(14,7)). 상대 기준이 비교하는 24개 값(G2: S0, S1, S9, S12의 host CPU time; G3: S0, S0b, S1, S5와 S13의 drag 전후 최고치, S11, S15, S14; G5: 한 행과 20행; G6: document 부분; G7: 두 탭 각각의 median과 90 percentile; G8: S5와 S13의 drag와 S1의 pointer 이동)은 값마다 other host 및 baseline host와의 비교 네 번과 회귀 두 번으로 비교 144번이 되며, mygo host의 값을 자기 이전 값과 비교하는 세 비교(S0과 S1의 G2, S4의 G3)를 더하면 이들은 session의 약 4.2%에서 우연히 하나를 만족한다(1 − (1 − 1/3,432)^147, 비교를 서로 독립으로 볼 때). run 세 번과 median 규칙이라면, 나머지 host와 같은 mygo host는 session 5번 중 4번 상대 기준에 실패하고, other host의 바뀌지 않은 값은 비교 5번 중 1번 회귀가 된다. 회귀의 원인은 두 revision 사이의 core item, 측정 target 변경, plugin version, Go와 Rust toolchain version 가운데서 찾으며, G1부터 G8까지를 판정하기 전에 그 원인을 소유한 module에서 Red/Green으로 고친다. run은 swap 사용량이 전체의 절반 미만이고 `fseventsd`가 코어 하나의 10% 미만을 쓰는 동안에만 시작한다(F374-6-3의 조건).

- **G1 Process 집합.** 애플리케이션 시작 이후 view를 하나도 보이지 않은 window는 WebContent, GPU, Networking process를 실행하지 않는다(`make app-usage STATE=S0`). WebKit process는 첫 view page나 document region이 보일 때에만 시작한다. 애플리케이션의 마지막 web view가 닫힌 뒤 통과값 (ii)의 시간([plugin process](../spec/plugin-processes.ko.md#통과값)) 안에, 애플리케이션이 hold하던 view page나 document region의 모든 WebContent process가 종료되어 있다(그런 각 process의 `diagnostics.process.exit`를 닫기 전에 읽는다, `make app-usage STATE=S0b`). 그 뒤 WebKit이 유지하는 GPU나 Networking process는 G3이 S0b에서 세는 측정된 비용이며, 이 기준은 근거를 밝히는 adversarial review를 통해서만 바뀐다; `make app-usage`는 이전 view가 시작한 sidecar process를 따로 출력한다.
- **G2 유휴.** S0, S1, S9에서, 모든 `term` 탭과 `terminal` 탭의 `cursor.idleTimeout`이 그 plugin의 manifest가 선언하는 기본값일 때, 마지막 입력, scenario의 그런 각 탭의 커서 유휴 제한 시간, 그리고 `host.window`의 `frames`가 바뀌지 않는 3초가 지난 뒤, scenario의 모든 window는 240초 동안 frame을 present하지 않고 Metal command buffer를 commit하지 않는다: 모든 log policy에서 세는 각 window의 `host.window`(U7)의 `frames`와 `commandBuffers`는 240초 전후에 같다. 같은 240초 동안 mygo host의 host process는 코어 하나의 0.05%(CPU time 0.12 s) 이하를 쓰고, 같은 커서 유휴 제한 시간과 3초 뒤에 읽은, 같은 scenario에서 각 other host와 baseline host의 host process CPU time 이하를 쓴다(`make app-usage STATE=<scenario> IDLE=1 INTERVAL=240`). S0과 S1에서, 실제 입력 도구(`e2e/real/hid.mjs`)의 `bringFront`로 앞으로 가져온 window에서, 그 도구의 HID 이동으로 window를 가로지르는 pointer 이동 뒤에 G3이 footprint를 읽는 방식으로 읽은 합산 footprint의 spread는 그 이동 전에 같은 방식으로 읽은 그 값의 spread보다 전부 위에 놓이지 않는다(`make app-usage STATE=<scenario> STEP=pointer`). S12에서 실패하는 layout 그리기는 자기 결함의 `error:` 줄을 애플리케이션 로그에 정확히 하나 쓰며, 그 뒤 S1의 조건이 성립한다(`make app-usage STATE=S12 IDLE=1 INTERVAL=240`).

## mygo 사실 (v0.7.4)

### Threading과 native 호출

- `mygo.go`는 `Version`을 `0.7.4`로 설정하고 `init`에서 `runtime.LockOSThread()`를 호출하므로, main goroutine은 process를 시작한 thread에서 실행된다[S1]. 이 module은 Go 1.27.3과 purego v0.11.1을 요구한다[S3].
- mygo는 cgo를 쓰지 않는다: native API는 실행 시점에 purego(`dlopen`과 assembly trampoline)를 통해 호출한다[S4][S5]. AppKit이 호출하는 Objective-C method는 callback으로 등록된 Go function이며, purego callback은 결코 해제되지 않는 희소한 자원이다[S4][S7]. purego callback은 calling thread에서 `crosscall2`를 통해 Go로 들어가며, Objective-C method는 purego callback으로 등록된다(`objc.NewIMP`)[S29].
- main goroutine은 main thread에 고정된 채로 있다; 모든 platform method와 모든 handler는 main thread에서 Go로 실행되며, listener는 main thread에서, IPC handler는 goroutine에서 실행된다[S6]. main thread는 `pthread_main_np`가 true를 반환하는 thread다; `RunOnMain`은 main thread에서는 function을 즉시 실행하고 그 밖에서는 function을 main thread에 post한 뒤 기다리며, `await`는 main thread에서 기다리는 동안 `Backend.Step`으로 native event를 처리한다[S2].

### Window, web view와 native handle

- window는 page와 native UI 중 하나를 보인다(`WindowOptions.Content`). `Window.NewWebView`는 native UI를 보이는 window에서만 web view를 만들며, page를 보이는 window에서는 `errNoContent`로 실패한다[S11][S12].
- native UI window에서 WKWebView는 content view 안의 Metal surface 아래에 있는 뒤집힌 clip view(`MyGoClipView`)에 놓인다. native UI는 web view가 보이는 자리에 구멍(`OpHole`)을 칠하며, surface의 `hitTest:`는 web view가 pointer를 받는 자리에서 nil을 반환한다[S12][S13].
- `ui.WebView`는 window가 만든 web view만 배치한다: `surface.WebView`는 `*mygo.WebView`의 native 쪽을 반환하고, web view element만 구멍을 칠하며, window는 자기 web view의 배치(frame, clip, cover)를 그것을 그리는 frame에서 surface에 넘긴다[S14]. mygo에는 임의의 native view를 배치하는 element가 없다.
- 유일한 공개 native handle은 window다: `Window.NativeHandle`은 `NSWindow`를 반환한다[S10]. web view handle(`WebViewHandle`)은 internal package에 있다[S10].
- mygo는 각 web view를 자기 구성과 delegate로 만든다(`createWebView`)[S10]; v0.7.4에는 다른 library가 만든 `WKWebView`를 받는 operation이 없다.
- mygo surface view는 file URL에 대해 등록하며, drop된 파일을 content의 event로서 직접 받는다[S27].

### 이미지

- `ui.NewBitmap`은 자기 pixel을 CPU와 GPU에 둔다; `Update`는 그림을 교체하고 새 pixel을 업로드한다[S15]. Metal renderer는 이미지의 version이 바뀌면 진행 중인 frame을 기다린 뒤 `replaceRegion:`으로 이미지 전체를 업로드한다[S15]. v0.7.4의 tree에는 IOSurface 사용이 없다.

### IPC

- page bridge는 JSON 메시지를 나른다; `[]byte` 값은 base64 문자열이다[S16]. custom protocol handler는 main thread에 body를 256 KiB chunk로 넘긴다[S16].

### Application 수명 주기

- `applicationShouldTerminate:`는 종료가 수락되면 run loop를 멈추고 `NSTerminateCancel`을 반환한다; mygo는 `applicationWillFinishLaunching:`에서 quit Apple Event에 대한 자기 handler를 설치한다[S8][S9].
- `applicationDidFinishLaunching:`은 activation policy가 regular일 때 애플리케이션을 활성화하며, `Window.Show`는 애플리케이션을 활성화한다; `Window.ShowInactive`는 활성화 없이, 그리고 key로 만들지 않고 window를 보인다[S9][S22]. `Window.OnReadyToShow`는 숨겨진 채 만들어진 window가 첫 frame을 그리면 한 번 실행된다[S22].
- `App.Run`은 `quitOnSignals`를 호출하며, 이는 SIGINT와 SIGTERM이 애플리케이션을 종료하게 한다[S20]. 애플리케이션 delegate는 알림이 지원될 때 notification center delegate(`MyGoNotificationDelegate`)를 설정하고[S9][S21], `applicationDockMenu:`에 mygo `Dock` API의 menu로 응답한다[S9].

### Native UI 렌더링

- native UI는 Metal로 그리고 Core Text로 텍스트 layout을 잡는다; 텍스트 입력은 `NSTextInputClient`를 사용한다[S18].
- frame은 요청이 있을 때 그린다: 일시 정지된 `CADisplayLink`는 frame이 연이어 이어지는 동안에만 tick한다[S17]. frame은 자기 drawable이 그려진 뒤 바뀐 것만 그린다(`gpu.Ages`, `scene.Differ`)[S17]. 안정된 window는 frame을 요청하지 않고 timer를 걸지 않는다(`TestSettledWindowSleeps`); macOS에서 작은 유휴 native UI window는 44 MB를 차지하며, counter 예제는 유휴 시 코어 하나의 약 0.005%를 쓴다[S5]; F502-25는 B3 window 크기에서 floor를 측정한다.
- Metal layer는 정지 시 drawable 하나, window가 animation 중인 동안 세 개를 유지하며, timer가 마지막 frame 후 이 초가 지나면 drawable을 줄인다; Metal driver는 일시 정지 후 첫 command buffer를 위해 process footprint 중 30~45 MB를 차지하고, 마지막 frame 후 일이 초 뒤에 이를 돌려준다[S17].
- layer를 바꾸는 frame, 또는 web view를 보이는 window가 그리는 frame은 Core Animation transaction으로 present하며(`presentsWithTransaction`), 그래서 web view는 frame과 같은 transaction에서 움직인다; 그런 frame은 그 안에서 아무것도 바뀌지 않았어도 그려지며, 진행 중인 fetch가 있으면 그 뒤에 main thread에서 drawable을 얻는다. 그 밖의 frame은 GPU가 받는 즉시 present하며, presenter가 자기 thread에서 fetch한 drawable을 쓰므로 main thread는 display를 기다리지 않는다[S17][S26].
- engine은 보이지 않는 window의 frame을 hold하며, 그런 window의 frame 요청은 display link를 기다린다[S28].
- engine은 보조 기술이 surface의 내용을 요청하면(`AccessibilityOn`) 그때부터 모든 frame을 accessibility tree로 기술한다[S18]; automation hook은 automation plugin이 tree를 읽을 때 tree를 만든다. element key와 action은 애플리케이션이 automation plugin을 link하고 `MYGO_AUTOMATION`이 요청할 때에만 automation plugin에게 넘겨지며, tag `mygo_noinspector`를 둔 build는 그 hook을 뺀다[S19].
- 측정된 native UI frame: 정적 label 1,000개는 CPU renderer에서 할당 없이 frame당 397 µs가 들고, label 1,000개를 가진 warm-up된 view는 Go heap 약 2.50 MB를 유지한다; 이 측정은 native window와 GPU 메모리를 제외한다[S23].

### 성숙도

mygo는 version 0.7.4이며, tag의 이력은 2026-09-26에 시작한다[S25]. version 0 module은 어느 release에서든 API를 바꿀 수 있다.

## 귀결

**Page 모드는 이득이 없다.** JavaScript workbench를 page로 보이는 mygo window는 main page와 그 WebContent process(C1, C4, C5), 그 그래픽 메모리(C3), 그리고 각 layout transaction에서 main page의 presentation에 대한 대기(C9의 세 대기 중 하나)를 그대로 유지한다. 이득을 얻으려면 host가 workbench를 native UI로 그려야 한다: 결정 D1.

**mygo는 main thread 규칙을 어긴다.** 애플리케이션 process는 view page나 document region이 존재하는 즉시 JavaScriptCore VM을 가지며, 그러면 main thread의 Go 코드가 `pas_panic_on_out_of_memory_error`에서 process를 끝낸다([Wails host의 main thread](../spec/hosts.ko.md#wails-host의-main-thread)). mygo는 모든 handler와 모든 native UI build를 main thread에서 Go로 실행한다[S6]. 이 규칙은 framework 변경으로만 충족된다: U1(D3).

**Native view에는 element가 필요하다.** plugin view page, document region, image region은 `native/darwin`(`sp_document_create`, `sp_region_create`)이 만들며, 만드는 자리는 `sp_surface_create`가 main web view의 window 합성 안에 배치하는 `SurfaceHost` 안이다([`webview_geometry.h`](../../native/darwin/src/webview_geometry.h)). mygo는 자기 web view만 배치하며[S14] IOSurface 경로가 없다[S15]. 따라서 설계에는 mygo의 native view element(U2)와 main web view 없는 surface host(N1)가 필요하다(D4).

**Native workbench가 더하는 비용.** host process는 workbench의 상태를 Go heap에 가지며, Go runtime은 이를 적어도 이 분마다 수집한다[S30]. 또 보조 기술이 요청하면 모든 frame의 accessibility tree를 가진다[S18]. Metal layer는 정지 시 window 크기 drawable 하나, window가 animation 중인 동안 세 개를 유지하며, Metal driver는 일시 정지 후 첫 command buffer를 위해 30~45 MB를 차지한다; 둘 다 마지막 frame 후 약 이 초 뒤에 돌아오며, 그때 timer가 GPU instance buffer와 atlas, image, backdrop texture도 해제하므로, 일시 정지 후 첫 frame은 main thread가 기다리는 동안 step 안에서 drawable을 얻고 그 buffer와 texture를 다시 만든다[S17]. focus된 편집 가능한 텍스트 필드는 focus를 얻거나, 그 텍스트가 바뀌거나, 그 window가 key가 된 뒤 30초 동안 530 ms마다 frame을 그리며, 이로 인해 그 30초 동안 drawable과 driver 메모리가 유지된다[S31]. layer나, web view 또는 native view element의 배치(box, clip 또는 cover)를 바꾸는 frame은 Core Animation transaction으로 present하며 main thread가 기다리는 동안 step 안에서 drawable을 얻으므로, 그런 frame마다 AppKit display cycle 한 번과 commit 한 번이 든다[S17]; v0.7.4에서는 web view를 보이는 window의 모든 frame이 그 안에서 아무것도 바뀌지 않아도 그렇게 present하며[S26], U2는 이를 layer나 배치를 바꾸는 frame으로 한정한다. 각 step과 각 전달된 call은 worker와 main thread 사이에서 thread 깨우기 두 번으로 이루어진 교환 하나다(U1): 크기, layer, 배치를 바꾸지 않는 frame은 step 2개와 전달된 call 15개이고, pointer 이동은 step 1개와 전달된 call 6개, 커서가 바뀌면 8개이며, mygo host에서 pointer 이동은 `native/darwin`의 pointer routing이 이동마다 보내는 `hitTest:`를 위한 별도 step 뒤에 온다(D3). framework가 등록하는 각 Objective-C callback은 process 수명 동안 등록된 채로 있고, process 하나는 그런 callback을 최대 2,000개 가지며, 그 수를 넘는 등록은 panic으로 process를 끝낸다[S7][S32]. G2, G3, G8이 이 비용에 상한을 둔다; `hitTest:` step은 애플리케이션의 event dispatch가 전달하는 이동에서만 실행되므로, G2와 G8은 이를 실제 입력 도구(`e2e/real/hid.mjs`)의 HID 이동으로 측정한다.

## 구조

### Host package

두 Go host는 code를 공유하고, framework는 framework adapter다.

```
packages/host/go/          language host library (module, package host)    from packages/host/wailsv3/src
packages/host/rust/        language host library (crate soksak-host)       from packages/host/tauriv2/src
packages/host/wailsv3/     framework adapter: Wails v3
packages/host/mygo/        framework adapter: mygo
packages/host/tauriv2/     framework adapter: Tauri v2
```

- language host library는 framework 이름을 쓰지 않는 모든 것을 담는다: binding, window, workspace, surface, document, image, sidecar, exposure, endpoint, event log, diagnostics와 darwin platform layer(`src/platform/darwin`, `soksak-darwin` pkg-config package를 쓰는 cgo). mygo host는 이 layer를 link하므로 mygo application은 cgo로 build되고, mygo framework의 package는 cgo를 담지 않는다. 그 framework port는 두 언어에서 같은 이름을 갖는 두 interface다: `Framework`(application 이름, main-thread step, quit, dialog, menu, Dock, 그리고 title bar를 포함한 window 생성)와 `Frontend`(event emit, window title, show, focus, window event인 resize, move, focus, focus 상실, show와 hide, presentation notice, settled presentation, workbench start, workbench call channel). application 이름(`wailsv3`, `mygo`, `tauriv2`)은 `endpoint.json`의 `application`, endpoint socket의 이름, application update의 release key의 host, debug view의 state file의 `host`다. `packages/host/wailsv3/src`의 test가 아닌 Go 파일은 현재 29,644줄이다; language host library가 없는 두 번째 Go host는 이 code를 반복하게 된다.
- `surfaces.*`는 language host library 안의 한 파일로 남는다. 그 layout transaction은 `Frontend` port의 presentation notice를 기다린다: Wails와 Tauri framework adapter는 이를 main page의 `AfterPresentation`으로 구현하고, mygo framework adapter는 U3와 Surface layout 행의 frame hold([Operation group](#operation-group))로 구현한다. workbench start는 Wails와 Tauri framework adapter에서는 main page를 다시 load하고, mygo framework adapter에서는 그 adapter의 `Workbench` interface(window의 workbench 만들기, 그것 닫기, event 전달, call 전달)를 통해 native workbench를 다시 만들며, 이 interface는 `packages/workbench-mygo`가 구현한다.
- framework adapter는 `Run`과 framework port의 구현을 담는다. 한 언어만 필요로 하는 파일은 그 language host library에 남고, 한 framework만 필요로 하는 파일은 그 framework adapter에 있다. 허용 차이의 각 행은 자신의 package를 명시한다. `scripts/check-hosts.mjs`는 `packages/host/go`를 `packages/host/rust`와, `packages/host/wailsv3`, `packages/host/mygo`, `packages/host/tauriv2`를 서로, `packages/sok/go`를 `packages/sok/rust`와, 그리고 `apps/wailsv3`, `apps/mygo`, `apps/tauriv2`를 서로 비교한다. path prefix로 파일을 고르는 `scripts/check-hosts.mjs`의 audit는 다음 prefix를 받고, 각 audit는 자신의 prefix 중 하나가 아무 파일도 고르지 않으면 실패한다: main-thread audit는 `packages/host/go/src/platform/darwin/`를 받고, decode되지 않은 command argument audit는 `packages/host/tauriv2/src/`의 Rust source를 받으며, stub check는 language host library들과 framework adapter들의 `src` 폴더와 `packages/workbench-mygo`의 `src` 폴더를 받되, 각각 그 package를 만드는 item(F502-7, F502-12, F502-15)부터 받는다.
- Rust language host library가 있는 이유는 structure check가 두 언어의 host package를 상대 경로로 비교하기 때문이다([structure check](../spec/hosts.ko.md#구조-검사)): Go code가 language host library와 framework adapter로 나뉘면 Rust code도 같은 방식으로 나뉜다. Rust `Framework`와 `Frontend` trait는 구현이 하나, 즉 Tauri framework adapter뿐이며, 그 비교를 위해 존재한다. Rust language host library는 test가 아닌 code 약 40,800줄을 가져가고, test가 아닌 파일 105개 중 35개가 Tauri를 이름으로 가리키며 library와 framework adapter 사이에서 나뉜다.
- Go framework adapter는 `adapter`라는 이름의 package이고, Rust framework adapter는 crate `soksak-host-tauriv2`다. Wails framework adapter는 각 call을 language host library의 binding에 넘기는 bound type `Bindings`를 정의하므로, Wails binding service는 이름 `github.com/soksak-app/core/packages/host/wailsv3/src.Bindings`를 유지한다.
- `packages/sok/{wailsv3,tauriv2}`는 `packages/sok/{go,rust}`가 된다. command line에는 framework code가 없다. Go는 build constraint 하나로 compile되는 파일로 release identifier를 고른다: `src/wailsv3.go`(`!mygo`, `app.soksak.wails`)와 `src/mygo.go`(`mygo`, `app.soksak.mygo`)이며, Rust는 `RELEASE_IDENTIFIER`(`app.soksak.tauri`)를 `src/identity.rs`에 둔다. 허용 차이의 C7 행은 두 Go 파일을 나열한다.
- `apps/mygo`는 `src/main.go`, `environment.json`, stage된 view root(`frontend/modules`, `core-root.json`, `view-imports.json`), test와 manifest를 가진다. 어떤 page도 workbench를 실행하지 않으므로 `runtime/index.js`는 없다: `environment.runtime`은 main page가 있는 application에만 필요하고, staging script는 `mygo`에 main page를 stage하지 않으며, framework 표의 A6 행은 main page runtime의 파일을 mygo에 없는 것으로 나열한다: `runtime/`, `test/fixtures/start.json`, `test/clipboard.test.mjs`, `test/runtime.test.mjs`, `test/runtime-contract.test.mjs`, `test/runtime-lifecycle.test.mjs`, `test/start-module.test.mjs`, `test/surface-calls.test.mjs`. `make host-parity-check`는 다른 host에 대해 `runtime/index.js`를 읽듯이 `packages/workbench-mygo`의 `hostCalls`를 읽는다.

### Workbench

`packages/workbench-mygo`(Go module, package `workbench`)는 mygo `ui` widget과 layout으로 workbench를 그린다. `src/layout`은 Go layout model을 담는다: `packages/soksak`의 grid와 card geometry, 그리고 `packages/workbench`의 project, space, tab과 그 저장 형식이다. 이 model은 mygo package를 import하지 않는다. layout case는 `docs/spec/cases`의 JSON 파일이며, `packages/soksak`, `packages/workbench`, `packages/workbench-mygo`의 test가 이를 읽는다. 화면: rail, library, card와 tab strip, sidebar frame과 seat, menu, settings window, plugin 화면, debug view, error 표시, modal. mygo host에서 interactive element는 U4의 element tree의 element 중 action에 press, increment, decrement, value 또는 expansion이 포함된 element다(`ActionPress`, `ActionIncrement`, `ActionDecrement`, `ActionSetValue`, `ActionExpand` [S38]); `packages/workbench-mygo`의 binder는 각 interactive element를 만들 때 그 element를 선언된 command에 연결하고 그 element name(D7)을 주며, 보이는 각 상태는 선언된 status다. `core.workbench.audit`와, plugin API의 `audit(root)` 및 `core.surface.document`의 `unbound`는 command나 element name이 없는 각 interactive element를 모든 host에서 `{role, expose, command, text}`로 나열하며, 여기서 `role`은 ARIA role 이름이다: mygo host에서는 `packages/workbench-mygo`의 표 하나가 `ui.Role`의 각 role에 주는 이름이고 [S38], document에서는 element의 `role` attribute 또는 그 tag의 암묵적 ARIA role이며, `contenteditable` element에는 `textbox`다; F502-13은 plugin API의 `audit`, 그 contract case(`create-binder.json`, `interactive.json`)와 [exposure](../spec/exposure.ko.md)를 바꾸고, D7의 각 plugin item은 plugin API case의 사본과 함께 이를 받는다. mygo workbench의 modal은 workbench의 일부이며, 그 control은 같은 binder를 통해 command를 실행한다. `packages/workbench`는 Wails와 Tauri host의 workbench로 남는다.

두 workbench는 하나의 제품을 구현하며, 세 mechanism이 둘을 같게 유지한다:

- **선언.** `packages/workbench-mygo`는 `packages/workbench`의 `exposure.json`, `shortcuts.json`, `workbench.json` 사본을 embed하며, `make exposure-check`는 지금 `core-exposure.json`을 그렇게 하듯 이 사본들을 원본과 같게 유지한다. `packages/workbench/workbench.json`은 새 선언 파일로, theme catalog(`THEMES`, `MODES`), font(`FONTS`), menu 언어(`MENU_LANGUAGES`와 기본 언어), setting 정의(기본값, 범위, text size 단계를 포함한 선택지, switch, common scope만 갖는 key)와 chrome metric(`app.css`, `library.css`, `overlay.html`의 모든 literal 길이, 비율, 지속 시간)을 담는다. `settings.js`와 `text-size.js`는 이 값들을 정의하는 대신 이 파일을 JSON module로 import하고, JavaScript workbench는 chrome metric을 document root의 custom property로 설정하며 stylesheet가 이를 사용하고, workbench의 stylesheet가 literal 길이, 비율 또는 지속 시간을 담으면 `packages/workbench`의 test가 실패한다. common scope만 갖는 key는 하나의 목록, 즉 `workbench.json`의 common-only key다. 각 language host library는 `workbench.json`의 사본을 embed하며, `make exposure-check`는 `packages/workbench-mygo`의 사본을 그렇게 하듯 이 사본도 원본과 같게 유지한다([project](../spec/projects.ko.md#저장)). `make exposure-check`는 또한 exposure check의 규칙 1과 2를 `packages/workbench-mygo`의 Go source에 적용한다: Go source가 registry나 binder에 넘기는 모든 status, command, element name은 선언되어 있고, 선언된 모든 status와 command는 등록되어 있으며, 선언된 모든 element name은 어떤 element에 주어진다.
- **Host call.** `packages/workbench-mygo`는 language host library의 host handler를 각 handler의 이름을 적은 표 하나, 즉 `src/host_calls.go`의 `hostCalls`를 통해서만 호출한다. Wails host의 각 service call이 자기 goroutine에서 도착하듯, workbench는 `hostCalls`의 각 handler를 자기 goroutine에서 실행하고 그 answer를 나중 step에서 받는데, `SyncSurfaces`와 `PresentSurfaces`가 U1의 worker에서 실행되는 작업을 기다리기 때문이다; 그런 goroutine은 각각 language host library의 `routine.Go`를 통해 시작하고, 한 sidecar로의 send처럼 specification이 순서를 요구하는 call은 그 순서의 이전 call이 끝난 뒤에야 시작한다. [Host parity](../spec/host-parity.ko.md) 명제 1은 `runtime/index.js`의 `METHOD`와 `COMMAND`를 읽듯 그 표를 읽는다: 각 표의 각 이름은 그 host의 handler를 가지며, 세 표는 framework 표의 B 행 하나가 mygo에 없는 것으로 나열하는 call(native modal web view의 overlay call과 shape call)을 제외하면 같은 이름을 담는다.
- **동작.** [host parity](../spec/host-parity.ko.md)의 명제 6은 세 application이 같은 status, command, element name을 선언하고, 모든 window check가 세 application에 대해 실행된다고 말한다. 단, 대상이 main page나 modal web view인 check는 `MAIN_PAGE_APPS`를 순회한다; F502-16이 이 명제를 추가하고, `scripts/check-host-parity.mjs`가 `make exposure-check`의 사본 규칙과 `scripts/check-e2e-host-parity.mjs`의 규칙으로 이를 판정한다.

### Native view

- **View page와 document region**은 `native/darwin`(`sp_document_create`, document region)과 view contract를 바꾸지 않고 유지한다. window의 surface host들의 container는 window의 native view(U2) 안에 있으며, 이 native view는 Metal surface 아래에서 window의 content를 채운다; workbench는 각 surface를 native view element(U2)를 통해 보여주는데, 이 element는 surface 위에 구멍을 칠하고 workbench가 그 위에 그리는 곳의 cover를 계산하며, layout transaction은 surface host들의 frame을, 다른 host에서처럼 window의 content 좌표로, card를 그리는 frame의 Core Animation transaction 안에서 설정한다. plugin page는, library로 만든 page와 WebAssembly를 load하는 page를 포함해, view page 안에서 그대로 실행되는데, view page, 그 channel, view contract가 바뀌지 않기 때문이다. mygo host는 `ui.WebView`로 web view를 만들지 않는다: mygo는 각 web view를 자체 configuration과 delegate로 만들며 [S10][S14], view page에는 soksak scheme handler와 view channel의 script message handler를 갖춘 `native/darwin`의 configuration이 필요하다([`document_view.m`](../../native/darwin/src/document_view.m)).
- window마다 container 하나를 두면 각 geometry의 배치자가 하나로 유지된다: layout transaction은 모든 surface host를 window의 content 좌표에 배치하고, `native/darwin`은 그 frame을 적용할 때 container의 좌표로 변환하므로(`webview_geometry.m`, `webviewSetFrame`), mygo가 같은 frame에서 옮긴 holder가 있다면 host를 잘못된 곳에 두게 된다.
- **Image region**은 lease된 IOSurface를 가진 `image_region.m`의 `CALayer`를 유지하므로, lease의 in-use 규칙, color 처리, frame identity가 세 host에 대해 하나의 구현으로 남고, mygo renderer는 terminal frame을 위해 frame을 그리지 않는다. IOSurface를 Metal texture로 import하는 방식은 기각한다: 그러면 mygo renderer가 각 terminal frame을 upload하고 그것을 위한 frame을 그리며, lease 규칙이 framework 안으로 옮겨진다.
- **Modal**(settings window, menu, dialog)은 native UI이며, mygo host는 native modal web view를 만들지 않는다.

### Exposure와 window check

workbench의 element tree(U4)가 binder audit, element 사각형, element action에 answer를 주므로, window check는 `endpoint.json`을 통해 세 application에 대해 실행된다. 단, 대상이 main page나 modal web view인 check는 제외한다([공유 계약 변경](#공유-계약-변경)).

## Framework 변경

Wails host가 자신의 Wails fork를 고정하듯(F292-37-3), mygo host는 go.mod `replace`로 framework fork를 고정한다. 각 변경은 framework package의 변경이며, 각각 그 package 안의 test와 그 변경을 사용하는 core item으로 검증된다.

| ID | 변경 | 이유 |
| --- | --- | --- |
| U1 | Main-thread worker: Go code는 main thread가 아닌 thread에 고정된 goroutine에서 실행된다. worker는 `App.Run` 안에서 `Backend.Init` 전에 시작하고 `App.Run`이 반환할 때 끝난다. `App.Run`은 run loop 전의 Go code(`Backend.Init`, `Run` 전에 한 설정, `quitOnSignals`와 `Signal`)를 한 step으로, `OnQuit` listener를 포함한 `finish`를 또 다른 step으로 실행한다. main goroutine은 main thread에서 호출되어 block을 worker에서 실행하는 function을 통해 각 step을 시작하므로, main thread는 자신의 stack 위에서 각 step을 기다리며 그동안 worker와 다른 thread가 자신에게 forward하는 call을 실행한다. 그 step 동안 main thread에 도달한 callback은 worker에서 nested step으로 실행된다. mygo가 purego로 만드는 각 Objective-C method와 block(`objc.RegisterClass`, `objc.NewBlock`), 그리고 mygo가 넘기는 각 C callback(`purego.NewCallback`)은 mygo의 assembly trampoline을 통해 진입한다: `objc.RegisterClass` 뒤에 mygo는 그 class의 각 method의 구현을 trampoline으로 설정하고(`method_setImplementation`), 자신이 만드는 각 block의 descriptor의 invoke function과 dispose function을 trampoline으로 교체하며, 각 C callback pointer 대신 trampoline을 넘긴다. trampoline은 purego가 그것을 위해 만든 function을 호출하며, purego는 바뀌지 않는다. main thread에서 호출되면 trampoline은 argument register를 저장하고 Mach semaphore로 worker를 깨운 뒤 기다린다; 기다리는 동안 main thread는 자신에게 forward된 call, 즉 그 step을 위한 worker의 call과 다른 thread의 call만 실행하고, worker가 쓴 answer를 반환한다. 각 step은 step이 끝날 때 worker가 drain하는 worker의 autorelease pool 안에서 실행된다; 그 drain 전에 worker는 callback이 caller에 반환하는 object를 retain하고 forward된 call을 통해 main thread의 pool에서 autorelease하는데, 이는 worker pool의 drain이 callback이 worker에서 autorelease한 object를 deallocate하지 않고, main thread에서의 autorelease가 callback이 주지 않은 reference를 가져가지 않게 하기 위해서다. worker를 포함한 다른 thread에서 호출되면 trampoline은 그 thread에서 Go로 진입한다. step 동안 worker는 `onMain`, `RunOnMain`, `await`에 대해 main thread로 간주되며, `await`는 `Backend.Step`을 forward한다; 다른 callback을 전달하는 forward된 call(modal panel, menu, drag, `resignFirstResponder`와 `becomeFirstResponder`를 보내는 `makeFirstResponder:`)은 그 callback을 기다리는 worker에서, 바깥 step 안에서 끝나는 nested step으로 실행한다. mygo가 main thread가 아닌 thread에서 Objective-C object나 system framework function으로 하는 각 call은 main thread로 forward되며, 다음은 예외로 calling thread에서 실행된다: drawable이 아닌 Metal object(Metal protocol을 따르는 object: device, command queue, command buffer, encoder, texture, buffer, library, function, pipeline state 또는 sampler state)로 보내는 message(frame의 encoding, queue의 `commandBuffer`, command buffer의 `presentDrawable:`, `commit`, `waitUntilScheduled`, `waitUntilCompleted`, `status`, texture의 `width`와 `height` 포함), Metal descriptor class와 그 instance로 보내는 message(`MTLRenderPassDescriptor`, `MTLRenderPipelineDescriptor`, `MTLSamplerDescriptor`, `MTLTextureDescriptor`와 이들이 반환하는 attachment descriptor와 descriptor array), drawable의 `texture`, 그리고 `nextDrawable`; Core Text와 Core Graphics; `objc_msgSend`, `objc_msgSend_stret`, `objc_msgSendSuper`를 제외한 Objective-C runtime의 function(이 셋의 call은 U1이 selector와 receiver로 판단하는 message send다)과 `NSObject`가 구현하는 message `retain`, `respondsToSelector:`, `isKindOfClass:`; `NSString`, `NSAttributedString`, `NSNumber`, `NSData` 또는 그 mutable 형태, Metal object(Metal protocol을 따르는 object), Metal descriptor 또는 `CAMetalLayer`의 drawable에 보내는 message `release`와 `autorelease`, 반면 그 밖의 object(`NSArray`, `NSDictionary`와 그 mutable 형태 포함)의 `release`나 `autorelease`는 forward되는데, 마지막 release가 그것을 보내는 thread에서 object의 `dealloc`을 실행하고 collection의 `dealloc`은 자신이 담은 object를 release하기 때문이며, 그러면 autorelease된 window는 AppKit이 아직 닫는 중인 window에 대해 mygo가 의도하는 대로 main thread의 pool로 간다; mygo는 각 array와 dictionary를 autorelease하는 method가 아니라 `alloc`과 `init` message로 만들어, mygo가 만드는 어떤 array나 dictionary도 worker의 autorelease pool에 닿지 않게 한다; Foundation value object(`NSString`, `NSAttributedString`, `NSNumber`, `NSData`, `NSArray`, `NSDictionary`와 그 mutable 형태)로 보내는 message와 그 class로 보내는 message(`alloc` 포함), 그리고 같은 object의 Core Foundation function(`CFRetain`, `CFRelease`, `CFHash`, `CFEqual`과 `CFString`, `CFAttributedString`, `CFNumber`, `CFData`, `CFArray`, `CFDictionary`의 function)과 mygo가 font lookup의 필수 attribute set으로만 만드는 `CFSet`의 function, 단 call 동안 다른 thread가 바꾸지 않는 object에 한하며 [S35], array, dictionary 또는 set의 `CFRelease`도 여기에 포함되는데, 이는 mygo가 `CFRelease`로 release하는 각 array, dictionary, set이 모든 깊이에서 위의 value object, 결코 deallocate되지 않는 `CFBoolean` 상수, 불변인 `CFURL`, 그리고 다음 구절이 나열하는 type의 Core Text object만 담기 때문이다; Core Text object(`CTFont`, `CTFontDescriptor`, `CTLine`, `CTParagraphStyle`, `CTRunDelegate`, `CTTypesetter`)의 `CFRetain`과 `CFRelease`(calling thread는 이 object를 자신에서 실행되는 Core Text call이나 forward된 call이 자신을 위해 가져간 reference로 hold한다) [S34], 그리고 run loop observer의 `CFRelease`(mygo는 observer를 main run loop에 추가한 뒤에만 release하며, 그 뒤로는 main run loop가 observer를 hold한다) [S33]; main run loop를 얻고, observer나 timer를 만들고, timer, source 또는 observer를 main run loop에 추가하고, timer의 다음 fire date를 설정하고, source에 signal을 보내고, main run loop를 깨우는 Core Foundation function, `CFAbsoluteTimeGetCurrent`와 `CFGetTypeID`(object의 type만 읽으며, receiver로 call을 결정하는 U1의 function이 이것으로 Core Foundation type을 읽는다); `netproxy`가 자신이 고정하는 thread에서 proxy를 resolve할 때 쓰는 function(setup script가 그 thread의 run loop에서 실행되고 그 thread에서 call back하기 때문이다): 자신이 bind하는 CFNetwork function(`CFNetworkCopySystemProxySettings`, `CFNetworkCopyProxiesForURL`, `CFNetworkExecuteProxyAutoConfigurationURL`, `CFNetworkExecuteProxyAutoConfigurationScript`)과, 그 thread의 run loop에 대한 `CFRunLoopGetCurrent`, `CFRunLoopAddSource`, `CFRunLoopRunInMode`, `CFRunLoopStop`, `CFRunLoopRemoveSource`, `CFRunLoopSourceInvalidate`; libdispatch; mygo가 bind하는 libSystem의 function(`pthread_main_np`, `pthread_set_qos_class_self_np`, `proc_listallpids`, `proc_pidpath`, `proc_pid_rusage`, `responsibility_get_pid_responsible_for_pid`, `realpath`)과 `CACurrentMediaTime`; 그리고 Security의 keychain function(`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`)으로, system이 user에게 하는 질문이 main thread를 막지 않도록 `offMain`이 이를 자체 goroutine에서 실행한다. `IsMainThread`는 main thread에서, 그리고 step이 실행되는 동안의 worker에서 true를 답하고, 그 밖의 모든 thread에서 false를 답한다. mygo는 `commit`, `release`, `autorelease`를 보내고 `CFRetain`, `CFRelease`, `_Block_copy`, `_Block_release`를 호출할 때 U1의 function 하나만 거치며, 이 function은 receiver의 class나 Core Foundation type을 읽어, 위 목록이 calling thread에서 실행하는 receiver와 mygo가 만든 block(그 flag가 copy function과 dispose function을 선언하고, 그 dispose function은 U1의 trampoline이다)에 대해서는 call을 calling thread에서 실행하고, 그 밖의 receiver(`CATransaction`의 `commit`과 system이 넘긴 block 포함)에 대해서는 forward한다. 하나의 selector나 function이 두 종류의 receiver에 모두 닿고 call site는 자신의 receiver를 보여주지 않기 때문이다. caller가 결과를 보관하는 forward된 call은, `Preload`의 font lookup이 `systemFontOfSize:weight:`의 font에 대해 하듯, 그 결과에 대한 caller의 reference를 main thread에서 forward된 call 안에서 가져간다. 그러지 않으면 결과는 main run loop가 기다리기 전에 drain하는 main thread의 autorelease pool만이 hold하고, 어떤 step도 hold하지 않는 caller는 그 drain과 순서가 정해지지 않기 때문이다. 다른 thread가 forward하는 call은 common mode에 추가된 main thread의 run loop source에 signal을 보내고 그 source의 C callback이 call을 실행하며, step이 실행되는 동안에도 step이 실행되지 않을 때와 같이 그렇게 하므로, main thread에서 run loop를 돌리는 forward된 call(`await`의 `Backend.Step`, modal panel, menu)이 다른 thread의 call을 기다리게 두지 않고, trampoline에서 기다리는 main thread도 그 call을 실행한다; text engine이 자체 goroutine에서 시작하는 font lookup(`Preload`)이 그런 call이다 [S34]. text engine의 `NSFont` call, Core Animation(transaction, layer property, transaction과 함께 present하는 drawable의 `present`), `NSRunLoop`, `NSTimer`, `NSAppleEventManager`, WebKit, Carbon event manager와 Carbon의 keyboard layout function은 forward되는 call에 속한다. presenter는 자신의 thread에서 계속 drawable을 가져온다. framework는 C에서 호출할 수 있는 assembly function 두 개의 주소를 준다. 하나는 main thread에서 호출되어 block을 worker에서 실행하고, 다른 하나는 worker에서 호출되어 block을 main thread에서 실행하며, 둘 다 그 밖의 thread에서는 block을 직접 실행한다; mygo framework adapter는 이 둘을 language host library의 `hostRunOnWorker`와 `hostRunOnMain`으로 설치한다 | [Main-thread 규칙](../spec/hosts.ko.md#wails-host의-main-thread); purego callback은 calling thread에서 Go를 실행하고 [S29], mygo는 cgo를 쓰지 않으므로 [S4], Wails fork의 C mechanism을 재사용할 수 없다 |

### Native library 변경 N1

`sp_surface_create`는 현재 main web view를 받는다: 그 web view를 window composition(`SPWindowComposition`)으로 감싸는데, 이 composition은 window overlay, file drop view, 그리고 web view 위에 surface host들의 container(`SPSurfaceCoordinates`)를 담으며, surface host를 그 container에 배치한다. N1은 이 function이 container를 담는 `NSView`를 받도록 바꾸며, container는 surface host들을 담고, 그 web view들에 backing scale을 적용하고(`updateScale`), 그 web view 중 하나에서 자신에게 도달한 `cursorUpdate:`에 대해 현재 위치의 pointer move를 그 web view의 tracking area owner에게 보낸다. 이는 지금 `SPWindowComposition`이 window의 모든 web view에 대해 하는 일이며, 모든 host에서 그렇다: `sp_window_set_main_webview`는 main web view를 등록할 때 그 주위에 window composition을 만들고 `true` 대신 composition을 반환하며, Wails와 Tauri host는 그 composition을 넘긴다; mygo host는 Metal surface 아래에서 window의 content를 채우는 window의 native view(U2)를 넘긴다; `sp_surface_create`는 받은 view에 container가 없으면 그 view 안에 container를 만든다. `webviewAttachSurface`는 이를 호출하는 Wails branch와 그 branch를 고르는 `FillParent` option(Wails host의 native web view는 항상 자기 window의 content를 채운다), 그리고 어떤 caller도 닿지 않는 Tauri port `attach_surface`와 그 darwin 및 Windows 구현과 함께 제거되며, native test는 surface web view를 `sp_surface_create`와 `sp_surface_place_view`로 배치한다. `sp_window_facts`와 `sp_window_hit`는 등록된 main web view를 요구하는 대신 window와 그 view를 받는다. N1은 `surfaceLayoutObserve(started, ended)`를 추가한다: `started(window)`는 window의 preparation이 시작될 때, 그 `ready` 전에 main thread에서 실행되고, `ended(window)`는 window의 transaction이 commit(defer되었든 아니든)이나 cancel로 끝날 때, Core Animation transaction이 commit한 뒤 다음 대기 transaction이 시작되기 전에 main thread에서 실행된다. N1은 `surfaceLayoutAfterSettled`가 main web view 대신 window와, window의 content를 현재 상태로 화면에 올리고 call back하는 block을 받도록 바꾸며, 현재의 단계(document 읽기와 `_doAfterNextPresentationUpdate:`)로 main web view용 그 block을 만드는 function을 추가한다. language host library는 `Frontend` port의 settled presentation에서 그 block을 얻는다: Wails와 Tauri framework adapter는 이를 자신의 main web view의 block으로 구현하고, mygo framework adapter는 Surface layout group이 adapter의 Go function으로 만드는 block으로 구현하는데, 이 Go function은 workbench에 hold 없는 frame을 요청하고 그 U3 notice에서 call back한다; scene이 damage가 없어 아무것도 present하지 않았다는 notice는 즉시 call back하고, frame이 drawable을 찾지 못했다는 notice는 frame을 다시 요청하며, window가 frame을 hold하고 있다는 notice는 adapter가 그 hold를 풀 때 frame을 다시 요청한다. language host library의 darwin platform layer는 자신의 Surface layout group의 operation을 통해 이 function들을 호출하며, mygo framework adapter도 이 operation을 통해 자신의 observer를 등록하고 block을 만든다; layer는 그런 observer나 block의 각 Go function을 `hostRunOnWorker`를 통해 worker에서 실행하며, 어떤 framework adapter도 `native/darwin`의 function을 호출하지 않는다; block의 Go function은 block의 completion을 `hostRunOnMain`을 통해 main thread에서 실행하는 layer의 function으로 call back하고, main-thread audit는 block의 call을 native function의 call로 센다. mygo host는 `sp_surface_set_window_overlays`도 `sp_window_file_drop`도 호출하지 않는다: workbench는 U2의 cover를 통해 native view 위에 그리고, mygo surface view는 drop된 파일을 workbench event로 받는다.

## Private native API

mygo host가 바꾸는 [목록](../operations/private-native-apis.ko.md#현재-목록)의 각 행. 같은 `native/darwin` code가 call을 하므로, 나머지 모든 행은 다른 host에 적용되듯 mygo host에도 적용된다.

## 공유 계약 변경

이 변경은 각각을 도입하는 item에서 세 host 모두를 바꾼다. 옛 이름은 제거되고, alias는 남기지 않는다.

- **Exposure (D7).** exposure kind `dom`은 exposed element를 가리키는 모든 곳에서 `element`가 된다: manifest member `exposes.dom`(`exposes.element`)과 그 validation case, page call `expose.dom`(`expose.element`), relay call `exposureRegister`와 view call `registered`의 `kind`, `exposure.list`의 result member `dom`(`element`), method `dom.rect`와 `dom.act`(`element.rect`, `element.act`), binder audit `core.page.audit`(`core.workbench.audit`), specification의 용어 dom entry(element entry)와 dom name(element name), exposure specification과 [AGENTS](../../AGENTS.ko.md#구조)의 제목, plugin API contract case, `packages/workbench/exposure.json`의 `exposes.dom`(`exposes.element`), exposure check, MCP tool, `sok`, `packages/client/testing`의 fake endpoint, `@soksak/window-check`의 helper, 그리고 이 이름을 읽거나 새 page process를 기다리는 모든 window check와 measurement script다. `window-responder`의, `host.window`의 `responder`의, 그리고 `core.focus` 표의 owner `page`는 `workbench`가 되고, `host.hit` kind `page`도 마찬가지다; mygo host는 first responder가 자신의 surface view일 때 `workbench`를 보고한다. exposure registration은 workbench의 registry로 relay된다. region input `input: "dom"`은 view page의 DOM을 가리키므로 이름을 유지한다. mygo host에서 workbench의 element에 대해 `element.rect`는 element의 frame을 window point로, `zoom` 1과 `document` `{x: 0, y: 0}`로 반환하고, `element.act`는 `click`과 `input`을 받는다; `dispatch`는 `the mygo workbench has no DOM events`로 실패한다. view page의 element는 모든 host에서 모든 action을 유지한다.
- **Workbench status.** workbench declaration의 각 status와 command는 page가 아니라 window의 workbench에 대해 정의된다: 지금 main document에 대해 정의된 status는 workbench에 대해 정의되고, 그 status가 지금 page 좌표로 주는 위치는 window point로 주어진다; plane 좌표의 위치는 plane 좌표로 남는다. `core.window.document`는 `core.window.workbench` `{start, startedAt, readyState, visibility, scheme, background, scale, width, height}`가 된다: `start`는 workbench의 한 번의 start를 식별하고 `startedAt`은 epoch 이후 millisecond 단위의 그 start 시각이다(Wails와 Tauri에서는 main page의 page identity와 time origin; mygo host에서는 workbench를 build할 때마다 새 값); `readyState`는 `loading`, `interactive` 또는 `complete`이며, mygo host는 workbench의 첫 presented frame까지 `loading`을, 그 뒤에는 `complete`를 보고한다; `background`는 workbench가 열린 modal의 background blur와 함께 그려지는지를 알린다; `width`와 `height`는 window의 content size를 point로 나타낸 값이다; `visibility`는 window가 최소화되어 있거나 보이지 않는 동안 `hidden`이고 그 밖에는 `visible`이다; `scheme`은 workbench의 color scheme(`dark` 또는 `light`)이다; `scale`은 window의 backing scale이다. `core.page.error`는 `core.workbench.error`가 된다. `core.modal`은 modal document의 상태인 `document`를 modal web view를 만드는 host에서만 보고한다; 그 밖의 member는 모든 host에서 같다.
- **Workbench event.** workbench가 쓰는 event는 layer `page`에서 layer `workbench`로 옮겨진다: catalog의 그런 각 event `page.<name>`은 `workbench.<name>`이 되고, 그 member `page`는 `core.window.workbench`의 `start`인 `start`가 되며, `workbench.start`는 `core.window.workbench`의 `startedAt`인 `started_at`을 싣는다; view page가 plugin API의 view writer를 통해 쓰는 record는, view contract가 바뀌지 않으므로, 자신의 layer(`page.start`와 그 batcher의 record에는 `page`, plugin의 event에는 `plugin`)와 view page의 page identity인 member `page`를 유지한다. error line `error page …`는 `error workbench …`가 되고, transcript line `info page page: …`는 `info workbench workbench: …`가 되며, debug view의 state file의 member `page`는 `workbench`가 된다. mygo workbench는 이 event를 host의 event log를 통해 쓰고, `scripts/census.json`이 그 emitter를 선언한다. `diagnostics.objects`의 member `page`는 이름과 의미, 곧 main page의 object를 유지하며, mygo host에서는 `null`이다.
- **Main page process.** `host.window` `pageProcess`는 이름과 의미, 곧 main page의 process를 유지한다; mygo host는 `null`을 보고한다. main page를 대상으로 하는 measurement(`make page-memory`, `make host-calls`, main page footprint benchmark)는 `host.window`가 `pageProcess` `null`을 보고할 때 `the mygo host has no main page`로 실패한다.
- **Reload.** `host.window.reload`는 window의 workbench를 저장된 state에서 다시 start하고, workbench가 ready를 보고한 뒤 resolve된다; `plugins-changed`를 받는 window와 `core.plugins.apply`는 같은 방식으로 `installed.json`이 나열하는 plugin으로 workbench를 다시 start하며, `core.plugins.apply`는 새 start 전에 `{reloaded}`로 답한다([설치](../spec/installation.ko.md#변경-적용)). Wails와 Tauri host는 main page를 reload하고, mygo host는 native workbench를 다시 build한다. workbench의 새 start를 기다리는 window check나 measurement target은 새 page process가 아니라 `core.window.workbench`의 새 `start`를 기다린다.
- **Main-page method.** `diagnostics.page.request`, `diagnostics.page.calls`, `diagnostics.host.events`와 `diagnostics.page.collect`는 main page에 작용하며, mygo host는 각각에 error `the mygo host has no main page`로 답한다. `diagnostics.modal.hold`와 `diagnostics.modal.held`는 modal web view에 작용하며, mygo host는 각각에 error `the mygo host has no modal web views`로 답한다. 이들의 host contract case는 scope `wailsv3, tauriv2 only: <reason>`을 가지고, 각 error의 case 하나는 scope `mygo only: <reason>`을 가진다. `diagnostics.surface.hold`, `diagnostics.surface.held`, `diagnostics.layout.fail`과 `diagnostics.transcript`는 모든 host에서 window의 workbench에 작용한다. `diagnostics.drag`는 모든 host에서 workbench의 divider drag를 구동하며, `native: true`이면 Wails host와 Tauri host는 mygo host가 늘 그러듯이 그것을 native event로 전달한다. mygo host에서 그것은 `input.pointer`가 그러듯이 `native/darwin`의 `sp_input_pointer`를 통해, window나 application을 활성화하지 않고, boundary에서 primary button의 press, host가 시간을 정하는 각 step을 그 button의 drag로, 그리고 각 왕복의 마지막 step 뒤에 release를 전달한다. 각각은 U1의 trampoline을 통해, 그것을 전달하는 step의 nested step으로 mygo surface view에 도달한다. 그것은 `boundary`를 workbench에서 답하고 `handled`를 각 step의 진입부터 그 callback의 반환까지의 시간으로 답하며, 그 각 layout의 `presented`는 U3이 그 transaction의 frame이 presented되었다고 보고하는 시각이다. `diagnostics.capture.start`/`stop` 기록의 layout에서 mygo host는 `requested`를 workbench가 그 transaction의 frame을 요청한 시각으로, `presented`를 U3이 그 frame이 presented되었다고 보고하는 시각으로 보고한다.
- **Window check.** `@soksak/window-check/app.mjs`의 `APP_NAMES`는 `mygo`를 더하고, `requiresBoth`는 `requiresAll`이 되며, 이것은 session이 세 application을 포함할 때 성립한다; `e2e/hosts.test.mjs`와 `e2e/placement.test.mjs`의 비교는 셋을 비교한다. 같은 module의 `MAIN_PAGE_APPS`는 main page를 가진 application인 `wailsv3`와 `tauriv2`를 나열하며, `scripts/test/`의 test 하나는 그것이 `environment.json`이 runtime을 지정하는 application과 다를 때 실패한다; main page(`e2e/page-process.test.mjs`, `e2e/reload-memory.test.mjs`, `e2e/page-asset.test.mjs`)나 modal web view(`e2e/modal-release.test.mjs`, 그리고 modal document, `diagnostics.modal.hold` 또는 `dispatch`를 읽는 `e2e/modal.test.mjs`의 case)를 대상으로 하는 window check는 `MAIN_PAGE_APPS`를 순회하고, `scripts/check-e2e-host-parity.mjs`는 `Object.values(APPS)`나 `MAIN_PAGE_APPS` 이외의 것을 순회하는 window check에서 실패한다. `e2e/split-load-memory.test.mjs`와 `e2e/window-release.test.mjs`는 `host.window`가 page process를 보고하는 각 window의 page process를 판정한다.
- **Identity.** `endpoint.json`의 `application` 값은 `mygo`를 더하고, [debug view](../spec/debug.ko.md)의 state file의 `host`는 `mygo`를 더한다. core release key의 host 이름(`sok`의 `CoreHosts`와 `CORE_HOSTS`)은 F502-8에서 `mygo`를 더하고, registry index의 release key는 `darwin-arm64-mygo`를 더한다. `sok`은 core key가 알 수 없는 host를 지정하면(`registry core <version>: unknown host mygo`) application update를 포함해 registry index 전체를 거부하므로, `core.json`은 `darwin-arm64-mygo`를, baseline host가 더 이상 그 index에서 설치하지 않게 된 F502-27 뒤의 F502-27-1 core release와 함께만, 그리고 그 key를 받아들이는 `sok`을 가진 core version을 나열한 뒤에만 나열한다; 그때까지 update하지 않은 이전 core version의 application은 더 이상 registry를 읽지 못한다. mygo release bundle은 bundle identifier와 configuration directory가 `app.soksak.mygo`인 `target/release/mygo/soksak.app`이다; debug bundle은 `app.soksak.mygo.dev`를 가진 `target/debug/soksak-mygo.app/Contents/MacOS/soksak-mygo`다.
- **Allowed difference.** allowed difference는 두 표다. language table은 column Go와 Rust를 가지고, framework table은 column Wails, mygo와 Tauri를 가진다. language table은 row H(language host library의 file), row C(`packages/sok/go`와 `packages/sok/rust`의 file)와 row E(한 language에 없는 endpoint method)를 가진다. framework table은 row H(framework adapter의 file), row A(application의 file)와 row B(한 framework의 workbench가 하지 않는 host call)를 가진다. row ID는 두 표 전체에서 유일하다. host contract scope는 `all`, 또는 `<host>[, <host>] only: <reason>`이 된다; language host library가 framework port 없이 구현하는 case는 library의 test가 선언하며, case의 scope 가운데 library를 link하는 각 host에 대해 인정된다; 동작이 `Framework`나 `Frontend`를 거치는 case는 case의 scope의 각 framework adapter의 test가 선언한다. row H19는 framework table의 row, 곧 Wails와 mygo framework adapter의 `tests/platform/darwin/main_thread_stack_test.go`가 되고, language table의 row H23은 그 두 test가 모두 사용하는 Go language host library의 `tests/platform/darwin/stack_sampler.go`를 담는다.
- **Plugin diagnostic module.** diagnostic build에서 mygo workbench는 `diagnostics.json`의 declaration을 plugin의 surface declaration에 더하고 diagnostic module을 view page에서만 import한다; Wails와 Tauri workbench는 그것을 workbench page에서도 import한다. Wails와 Tauri host의 각 OS window는 app DOM WebView 하나를 가지며, mygo host의 window는 하나도 가지지 않는다.

## 결정

각 결정은 mygo host가 무엇을 하는지와 그 이유를 밝힌다.

- **D1 Native workbench.** mygo host는 workbench를 native UI로 그린다. 이유: page mode는 C1, C3, C4, C5와 C9의 main page 대기를 남긴다([귀결](#귀결) 참조).
- **D2 Host package.** language마다 language host library 하나, framework마다 framework adapter 하나, 그리고 `packages/sok/{go,rust}`. 이유: 그렇지 않으면 두 번째 Go host가 약 29,600줄을 반복하며, structure check는 두 language의 package를 상대 경로로 비교한다.
- **D3 Assembly trampoline에 의한 main-thread worker (U1).** mygo host의 Go code는 worker thread에서 실행된다; AppKit이 main thread에서 하는 각 callback은 step을 worker에 넘기는 assembly trampoline을 통해 들어오고, main thread는 자신에게 forward된 call을 실행한다. 이유: [main-thread 규칙](../spec/hosts.ko.md#wails-host의-main-thread)은 main thread에서 Go code가 실행되지 않을 때만 성립한다; purego callback은 calling thread에서 Go를 실행하고 [S29], AppKit은 mygo가 등록하는 method를 main thread에서 호출하며 [S4][S6], mygo는 cgo 없이 build되므로 [S5], Wails fork의 C worker는 그 mechanism이 될 수 없고, forward된 call을 가진 step이 곧 Wails host가 모든 callback에 대해 실행하는 그 step이다(F292-37-1, F292-37-3). U1의 비용은 각 step과 forward된 각 call마다, Mach semaphore를 통한 두 번의 thread wake로 이루어진 교환 한 번과 native wait에서의 worker 복귀이며, 이 복귀에는 Go scheduler의 P가 필요하다: garbage collection mark phase 동안처럼 sysmon이 대기 중인 worker의 P를 가져갔고 idle인 P가 없으면, worker는 어떤 thread가 그것을 schedule할 때까지 global run queue에서 기다린다. window size, layer나 placement의 변경 없이 content가 바뀐 window의 frame은 두 step, 곧 display link의 tick과 각 frame이 arm하는 run loop observer의 callout이며, forward된 call 15개를 가진다: window의 size와 scale 세 번, screen과 그 refresh rate 두 번, superlayer의 bounds 두 번, occlusion state, 그리고 tick에서의 layer와 그 display flag. transaction과 함께 present하는 frame은(U2는 이를 layer나 placement를 바꾸는 frame으로 제한한다) 그 drawable의 `present`를 더하고, mygo web view의 바뀐 placement는 call 4개를 더한다. live resize에서 window size의 한 번 변경은 다섯 step, 곧 `setFrameSize:`, `windowDidResize:`, `wantsUpdateLayer`, `updateLayer`, 그리고 `updateLayer`의 frame이 arm하는 run loop observer의 callout으로 forward된 call이 모두 20개이고 `NSView`의 `setFrameSize:`가 surface view에 보내는 `isFlipped`의 nested step 네 개를 가지며, pointer move는 forward된 call 6개를 가진 한 step이며 cursor가 바뀌면 2개가 더해지고 그 `convertPoint:fromView:`가 보내는 `isFlipped`의 nested step 하나를 가지고, mygo host에서는 view page가 input을 위해 등록되어 있는 동안 그 앞에 두 번째 step, 곧 `native/darwin`의 pointer routing이 각 move마다 content view에 보내는 mygo surface view의 `hitTest:`가 자체 forward된 call 및 `NSView`의 `hitTest:`가 보내는 `isFlipped`의 nested step 하나와 함께 더해진다; key는 forward된 call 7개를 가진 한 step이며(`interpretKeyEvents:`에 event를 넘기는 array의 `release`가 그 가운데 포함), 그 안에서 input method의 각 callback은 nested step이다 [S33]. text shaping은 system font style을 처음 사용할 때만 call을 forward한다 [S34]. F502-3은, mygo host의 어떤 window도 `ui.WebView`로 만든 web view를 담지 않으므로, web view를 담지 않는 window에서 각 종류의 step의 forward된 call이 이 수 이하임을 test하고, G8은 final phase에서 frame, pointer step과 resize의 step에 forward된 call을 포함해 120 Hz의 display 주기 하나(8.33 ms)의 상한을 둔다.
- **D4 Native layer로서의 image region.** window의 native view(U2)는 그 `SurfaceHost`들의 container를 담고, image region은 lease된 IOSurface를 가진 자신의 `CALayer`를 유지한다(N1). 이유: 세 host를 위한 하나의 lease 구현, 그리고 mygo renderer는 terminal frame을 위해 frame을 그리지 않는다.
- **D5 Terminal surface는 view page를 유지한다.** `term` plugin은 세 host에서 image region 하나(`input: "dom"`)를 가진 view composition을 유지한다. 이유: view page가 terminal의 screen state, input과 exposure를 소유한다(C8): 그 overlay, tab report, clipboard, link, settings, theme과 text size call, shortcut forwarding과 element name이다. surface는 자신의 plugin의 page를 보여주며, screen의 layer는 measurement로 선택되지 않는다([plugin process](../spec/plugin-processes.ko.md#층-규칙)).
- **D6 Toolchain.** `go.work`와 그 모든 module에 Go 1.27.3. 이유: mygo는 Go 1.27.3을 요구한다 [S3]; `go.work`의 `go` line은 그것이 사용하는 모든 module의 `go` line 이상이고, CI는 `go.work`의 version을 `GOTOOLCHAIN=local`로 설치하므로, `packages/host/mygo`가 workspace에 들어가면 core의 모든 Go build는 Go 1.27.3에서 실행되며, 하나의 language version이 모든 module에 적용된다.
- **D7 Element name.** exposure kind `dom`은 모든 host와 모든 plugin declaration에서 `element`가 된다([공유 계약 변경](#공유-계약-변경) 참조). 이유: window check는 workbench element를 이름으로 가리킨다; mygo host에서 그 element는 native UI이므로 `dom`은 그것을 잘못 가리키게 되며, 한 개념은 한 용어를 가진다([용어](../spec/terms.ko.md)). 각 plugin repository는 `plugin.json`의 `exposes.element`, 그 `expose.element` call, 그 test, 그 plugin API case 사본, 그리고 KR9의 term check가 거부하는 그 밖의 모든 record(term과 terminal의 `ui/view-exposure-port.js`의, browser의 `ui/section-view.js`의, files의 `ui/tree.js`와 `ui/bookmarks.js`의 comment, 그리고 files의 `docs/spec/tree-view.md`)를 바꾸고, KR9의 records kit release를 pin하며, `engines.soksak`을 F502-13의 core release로 올린다. F502-13의 core release가 먼저 publish된다; 각 plugin release가 그 뒤를 따르고, registry pull request 하나가 `core.json`에 그 core version을 plugin version과 함께 나열한다([registry](../spec/registry.ko.md)). F502-13의 core release는 제거된 member `host`와 `hostOperations`를 거부하듯이 `exposes.dom`을 `plugin <id>: exposes.dom is removed; an exposed element is declared in exposes.element`로 거부한다. 이로써 core release가 plugin release를 요구하게 되는데, [plugin](../spec/plugins.ko.md#repository)은 지금 이를 허용하지 않는다; F502-5가 그곳에 이를 유일한 예외로 적는다. F502-13의 core release는 core의 item F502-13-1이다. D7의 각 plugin 변경과 release는 F502-25가 시작되기 전에 완료된다. other host와 mygo host는 workspace registry의 plugin을 설치하고, F502-13의 core는 plugin이 `exposes.dom`을 선언하는 동안 그것을 거부하기 때문이다.

## 구현 순서

각 item은 F502의 sub-item이며 [기능 상태](../features.ko.md)에 등록된다. features에 등록된 item은 자신이 바꾸는 contract를 이 파일이 적은 대로 그 entry에 적고, 자신이 쓰는 specification section에 link한다; 이 파일의 heading에는 link하지 않는데, F502-5가 이 파일을 제거하고 F502-5 이후의 각 item은 자기 contract의 specification text를 쓰기 때문이다. Red는 소유 module에 있는 tracked test로서 변경 전에 실패하는 것이다: unit test, 또는 display의 presentation time이나 frame이 필요한 동작에 대해서는 그 module의 end-to-end test다; Green은 변경 뒤에 같은 test가 통과하는 것이며, 변경이 건드리는 package의 build와 변경이 건드리는 structural check를 함께 포함한다; Green은 full suite, window check, benchmark나 CI run을 지정하지 않는다. core에서 display의 presentation time이나 frame이 필요한 test는 Go module에서는 build constraint `e2e`로, `native/darwin`에서는 목록 `NATIVE_E2E_TESTS`로 그 module의 unit test command에서 제외된다; 그것은 이름이 `e2e`로 시작하고 어떤 workflow도 실행하지 않는 make target을 통해 local에서 실행되며, `make -C native/darwin e2e`가 `NATIVE_E2E_TESTS`를 실행하고 `make e2e-host-go`(F502-12)가 그 constraint의 Go test를 실행하는 식이다; 그것은 window가 screen을 갖지 않으면 `the window is on no screen`으로 실패하고, host contract case를 선언하지 않는다;
