# The sidecar route of a plugin host

[한국어](plugin-host-routes.ko.md)

The decision of F229 and its review record. Remove this document after the decision is in [plugin host](../spec/plugin-host.md) and the implementation items of F229 are complete.

## Problem

A plugin whose sidebar section shows values that its sidecar computes from the project folder (for example a listing of the folder as a declared tree) has no source for those values while none of its views is open:

- A [plugin host](../spec/plugin-host.md) is the second source of a declared status, but its channel serves only the registration calls and the state calls. It answers every other call with `plugin host call <name> is not served` and has no sidecar send ([plugin host](../spec/plugin-host.md#channel)).
- A sidecar is no declared status source: the source of a declared status is a process that registers the status and pushes declared UI snapshots ([declared UI](../spec/declared-ui.md#declared-status)), and a sidecar does neither.

## Scope

F229 is the minimal generic route by which a plugin host sends to and receives from the sidecars that its manifest declares, checked against its own plugin. Nothing else is in F229. Behavior that exists outside this route is a separate sub-item (F229-n, listed below), not an objection to this decision.

## Options

1. **The plugin host gets a sidecar route.** The host page sends to and subscribes to the sessions of its own plugin's declared sidecars through its channel; the main page answers these calls.
2. **A sidecar supplies declared values directly.** A sidecar registers declared statuses and pushes snapshots. Rejected: a declared status binds commands of its plugin and needs a process that registers them, so a sidecar source would still need a view or a plugin host for every command. A sidecar process serves several windows and processes, and a declared status source is a process and its registration, so the source transitions of [declared UI](../spec/declared-ui.md#declared-status) would need a second form. Every sidecar would also implement the snapshot protocol in its own repository.

3. **A state module serves the declared status.** Rejected in round 13. A state status is `exposure.status(name, read, subscribe)` (`docs/spec/plugins.md`, plugin state), a pull and a subscription with no `seq`, no acknowledgement and no `skipped`. A declared status is a snapshot protocol whose senders are a view and a plugin host only (`docs/spec/declared-ui.md`, status mapping; the source branches of `packages/workbench/declared-source.js` and `hostRegistrant`, `packages/workbench/exposure.js` 528 to 531). The state route therefore needs a third source kind, an adapter and an acknowledgement path, which is not the smaller change.

Decision: option 1.

## The route

1. **Served calls.** The channel of a plugin host serves, beside the registration calls and the state calls, `runtime.sidecar.send`, `runtime.sidecar.on` and `runtime.sidecar.onFailure`. The host forwards each to the main page as `plugin-host-call {plugin, id, command, params}`, as it forwards a registration call. The main page answers `runtime.sidecar.on` and `runtime.sidecar.onFailure` with `{result: null}` after it records the subscription, and answers `runtime.sidecar.send` with the result of `pluginHostSidecarSend`; `servedPluginHostCall` in `packages/workbench/plugin-host.js` (line 20) lists the three calls. Every other name, including every `core.` name, is refused with `plugin host call <name> is not served`. Core commands are not part of F229 (F229-5). The three `runtime.sidecar.*` calls are added to `forwarded_call` in `packages/host/tauriv2/src/plugin_host_channel.rs` (68 to 73) and to the Go forwarder, and `answer` in `packages/workbench/plugin-host.js` routes them before its exposure branch; `docs/spec/host-contract.md` line 837 lists them.
2. **Checks of the main page.** A sidecar call of a plugin host is answered by a route that is bound to the plugin of the host, not to a surface. The host call `pluginHostSidecarSend` is, in Go, a method of the main-page binding beside `PluginHostReply` (`packages/host/wailsv3/src/bindings.go`), and never a case of the surface call route `runNative`, so a surface document cannot call it; in Rust it is accepted only through `authorize_main_caller` (`packages/host/tauriv2/src/exposure.rs` 702 to 709). Its `plugin` argument is the plugin of the `plugin-host-call` that the main page answers. The sidecar name must be one that the plugin lists in `dependencies` of its `plugin.json`; any other name is refused with `plugin host <plugin> cannot use sidecar <name>`. The session id has the form `plugin:<plugin id>:<project id>:<sidecar name>`, where the project id is the id of a project that the sender's window holds; a project id that the window does not hold is refused with `plugin host <plugin>: project <id> is not held by this window`. No id contains `:` (`validProjectID` in `packages/host/wailsv3/src/projects.go` and the inline check in `packages/host/tauriv2/src/windows.rs` 786 to 792), so the id parses. The project id keys the root of rule 3. A project has one holding window (`h.owners` in `projects.go`, set at line 145; in Rust `Windows.owners`, `windows.rs` 163), so one session id has one holding window at a time. Any other session id is refused with `plugin host <plugin> cannot use sidecar session <id>`. A plugin session is reached only through the call of rule 3: a `sidecarSend` of either caller, the view or the main page, is refused for every `plugin:` surface with `sidecar session <id> is reserved for a plugin host`. This refusal is a change of this decision in both hosts, in `sidecarSendFrom` (Go, `packages/host/wailsv3/src/surfaces.go` 359 to 363) and in `sidecar_send` (Rust, `packages/host/tauriv2/src/bindings.rs` 326 to 340).
3. **Send.** A plugin host send is the host call `pluginHostSidecarSend {plugin, sidecar, id, body, cids}` in Go and Rust. Its handler checks the prefix and the plugin of rule 2 and then runs the existing send path of the sidecar, with the session as a surface id. The existing owner record of the sidecar then applies to the session: the first send records the window as the owner, and a send from another window is refused by the existing check. A plugin session takes the root of its project at its first send, as a surface takes the root of its window today. Each window records the folder root of each project that it holds. In Go the record is `Surfaces.projects` (`surfaces.go` 251), changed from a set to a map of project id to root; `ProjectOpen` writes it in both of its branches (`projects.go` 119 to 124 and 141 to 144), and `ProjectRelease` (`projects.go` 172 to 192) removes the released id. In Rust a window holds a project when `Windows.owners` maps the project id to its label (`packages/host/tauriv2/src/windows.rs` 163); `WindowData` gains `projects: Mutex<HashMap<String, String>>` of project id to root, written by `project_open_on_main` in both branches (`windows.rs` 786 to 820) and removed for the released id by `project_release` (`windows.rs` 878 to 898). The send path takes the root as an argument: a surface send passes the window root as today, and a plugin send passes the recorded root of its project in place of the window root (Go `sidecars.go` 436 to 441; Rust `send` in `sidecars.rs` 1149). A send whose project has an empty recorded root is refused before any start or record with `plugin host <plugin>: project <id> has no folder`, and an empty root is never recorded, so `Retain` never sees one. The session keeps that root until its owner closes it. F229-1 defines the lifetime of the record across a project change.
4. **Events.** A sidecar message or failure of a plugin session reaches the owner window through the existing `sidecar-message` and `sidecar-failure` events. The host page subscribes through `runtime.sidecar(name).on(id, listener)` and `.onFailure(id, listener)` before its first send to that session, because a reply to a send with no subscription is dropped (below). The view bridge in `packages/plugin-api/view.js` changes from `sidecar()` to `sidecar(name)`, with `send(id, body, cids)` beside `on` and `onFailure`; its requests carry `{id, sidecar}`, as the specification list states. The main page records each subscription in `packages/workbench/plugin-host.js` under the plugin, the sidecar and the session id, and it posts a matching message or failure to the host page as `pluginHostEvent {plugin, event, sidecar, id, body}` or `{..., reason}`. When the main page receives `plugin-host-ended {plugin}`, it removes the subscriptions of that plugin with its registrations (`docs/spec/plugin-host.md`, line 62). `packages/workbench/plugin-host.js` exports the registry of subscriptions, and `packages/workbench/host.js` imports it (`plugin-host.js` imports no host module, so the import adds no cycle). For a `sidecar-message` or `sidecar-failure` whose surface begins with `plugin:`, `host.js` calls the registry and returns before `windowSidecar` (line 183) and before the failure dispatch (`listenSidecarFailures`, lines 146 to 154), so no alert is shown for a plugin session. A message or failure of a plugin session whose event kind (`message` or `failure`) has no subscription for its session is dropped and written at `warn` as `plugin host <plugin>: sidecar <name> <event> for <session> dropped: no subscription`, because the sidecar produced data that the page did not receive (`docs/spec/logging.md`: `warn` is a loss). A failed post to the host page is logged as in rule 5. A sidecar failure is logged once by the existing `failed:` error of the sidecar process (`sidecars.go` 1610), and this route adds no log line for it.
5. **Errors.** A refused call, including a call that rule 1 does not serve, is answered to the calling host page with its error text and is written to the application log at `error` as `error: plugin host <plugin>: <reason>`. The error texts are those of rules 1 to 3 and every error that the send path returns (`sidecars are stopped`, `sidecar <name> is not declared by any plugin`, the owner refusal `surface <id> belongs to another window`, the errors of starting the process, and `sidecar <name> is not keeping up`; `sidecars.go` 476 to 518), and each is passed to the host page unchanged. The restart-limit refusal is the exception: `restartRefused` writes it for each refused request, and rule 6 states it, so this rule does not write it again. A post that the host refuses (no ready document or a refusal of the document) is written at `error` with its reason.
6. **Failures and the restart limit.** For a standard input and output sidecar, a send whose sidecar fails ends as the sidecar failure contract states for any session ([sidecars](../spec/sidecars.md#failure)), and the restart limit counts the failure as any other. The restart limit of a persistent sidecar is not defined by the specification, and this rule does not apply to it. The failure record is per sidecar name, so the plugin sessions share it with every other session of the sidecar. Below the restart limit, the host page's next request starts a new process, and the host page opens its session again. After the limit stops the sidecar, each request for it is refused with `sidecar <name>: restart limit`. `restartRefused` (`sidecars.go` 254 to 260) writes `error` for each refused request, and the owner receives `sidecar-failure` with reason `restart limit`. A refused request is not counted. The stop is cleared only as [sidecars](../spec/sidecars.md#failure) states, by a surface of a plugin that lists the sidecar in `dependencies`; a plugin host creates no surface, so its requests alone do not clear the stop (the plugin host stop rule is F229-6). The host page's failure handler sends nothing, so a refusal gives no resend. The main page sends nothing on its own: each sidecar send is the answer to a request of the host page.
7. **Session end.** A plugin session ends with its host, its project and its window. The main page calls the host call `pluginHostSidecarClose {plugin}` when it receives `plugin-host-ended {plugin}` (rule 4 and `docs/spec/plugin-host.md` line 62). The call closes only the sessions that the calling window owns. The host, not the page, does the other closes: before the main page of a window loads again, the page start disposes the host web view without that event (`packages/host/wailsv3/src/start.go` 74 to 82; `packages/host/tauriv2/src/windows.rs` 984 to 991; F229-2), so the host closes every plugin session that the window owns at that point; `ProjectRelease` (`packages/host/wailsv3/src/projects.go` 172 to 192) and `project_release` (`packages/host/tauriv2/src/windows.rs` 878 to 898) close every plugin session that the releasing window owns whose id names that project; and the window close closes every plugin session the window owns. Each close is the existing close of a sidecar session: `closeSurface` in Go (`sidecars.go` 591 to 612) and the same path in Rust, which sends `{surface, closed: true}` to each running sidecar and keeps the surface in the closing list until its answer arrives ([sidecars](../spec/sidecars.md#protocol), lines 42 and 50). The keep list of a retain is rebuilt inside the same locked block that enqueues the retain line, after the sidecar's process has started, so a plugin session first sent during a start is kept (F229-7; `sidecars.go` 945 to 972 for the Go `Retain`, which reads `c.roots`, and `packages/host/tauriv2/src/sidecars.rs` 1576 to 1620). The close of the sessions of a window enumerates the owner records (`c.owners` in Go, `Windows.owners` and the sidecar owners in Rust) for the ids with the prefix `plugin:<plugin>:` whose owner is the calling window, and calls `closeSurface` for each one. A session that no owner holds is not closed. The route inherits the broadcast of `closeSurface` to every running sidecar (F229-3); a sidecar answers every `closed` it receives (`docs/spec/sidecars.md` line 50, for every sidecar).
8. **Operations.** The route serves four read operations of `@soksak/sidecar-files` only, keyed by the package name of the sidecar; every other sidecar of the `dependencies` is refused every operation: `list`, `git`, `read` and `readBytes` (`docs/spec/sidecars.md`, the operation table of the files sidecar, lines 173 to 178). The main page refuses every other operation of a host request with `plugin host <plugin>: operation <op> is not served`, so the host page never writes and never watches. A write or a watch is served only through a surface of the plugin, as it is today. The check is made by the main page on the body, because the host relays bodies and does not parse them ([sidecars](../spec/sidecars.md#protocol), line 41). The main page parses the body as an object, requires a string `operation` field, refuses an absent or non-string one, and forwards the re-serialized object, not the raw bytes, so that the check and the sidecar read the same value. The Go host call `pluginHostSidecarSend` checks that its caller is the main webview, as `authorize_main_caller` does in Rust (`packages/host/tauriv2/src/exposure.rs` 702 to 709), and does not rely on the placement of the method. A declared status that depends on a watch refreshes when the host page pulls it, not when the folder changes, until a view of the plugin is open; this is a stated limit of the route.

## Sub-items outside F229

These are objections raised in the review that concern behavior outside the route. Each is registered as its own item with its evidence, and none is part of the F229 decision.

- **F229-1** The shown project of a window and the lifetime of plugin sessions across a project change. Evidence: `ProjectOpen` changes `owner.root` in the local branch and returns only `{Local}` (`packages/host/wailsv3/src/projects.go` 96 to 132; `packages/host/tauriv2/src/windows.rs` ~796 to 815); `activateInTurn` switches the project of a window without an event (`packages/workbench/projects.js` 339 to 352); `ProjectRelease` clears the root only when no project is left (`projects.go` 172 to 192).
- **F229-2** Closing a plugin session at the end of its host, at a page start and at a reload. Evidence: the disposal at page start (`packages/host/wailsv3/src/start.go` 74 to 82; `packages/host/tauriv2/src/windows.rs` 984 to 991) emits no `plugin-host-ended`.
- **F229-3** `closeSurface` sends `closed` to every running sidecar (`packages/host/wailsv3/src/sidecars.go` 591 to 629); a close of one session should reach the sidecar that holds it.
- **F229-4** A reply to an owner-less session is written by `dropMessage` at `info` (`sidecars.go` 2064 to 2067); the level is checked against the logging contract.
- **F229-5** A core command route for plugin hosts. No plugin host needs one for the stated problem. It is a separate decision with its own review.
- **F229-6** The restart stop clear rule: a sidecar stop clears by a surface of any plugin that depends on it (`sidecars.md`); a plugin host stop clears by a surface of its own plugin (`plugin-host.md` line 80). The two rules are stated as they are in each specification; the joint rule needs its own decision.
- **F229-7** The retain of a window keeps every session that the process has sent to, and both hosts build the `keep` list before a service is started (`sidecars.go` 945 to 972; `packages/host/tauriv2/src/sidecars.rs` ~1576 to 1612). A session first sent during the start is missing from the list.
- **F229-8** The `state:<plugin id>:<project id>` session has the same lifetime defect as F229-1.
- **F229-9** The state module option is not compared. A state module runs on the workbench page and has `sidecar.send`, `on` and `onFailure` for its one declared sidecar, with session `state:<plugin id>:<project id>` (`docs/spec/plugins.md` 113 to 117). `docs/spec/declared-ui.md` line 145 excludes a state module registration from declared UI without giving a reason. Required: compare the smallest change of letting a state module serve a declared status with option 1, record the reason for the exclusion of line 145 or change it, and then choose.
- **F229-10** `docs/spec/plugin-host.md` line 59 forbids a sidecar send from a plugin host, and line 5 creates a host only when moving its logic to a sidecar or a view is impossible. Required: show that the plugin logic a host needs cannot move to a sidecar, or keep the prohibition.
- **F229-11** The lifetime of plugin sessions. Rule 3 keeps a session root until its owner closes the session, but rule 1 serves no close call, and F229-2 (no close at host end) and F229-7 (retain drops sessions first sent during a start) leak or lose exactly these sessions. Required: define the close path (a served close call, or a close at host end) and bring F229-2 and F229-7 into F229, or show that the route is sound without them.
- **F229-12** `docs/spec/plugins.md` line 58 names as users of a declared sidecar only the page surface and the state module, and requires `surface` or `state`. A plugin with `host` and `sections` and neither cannot declare the sidecar. Required: amend line 58 to name the plugin host and the host-only case, and add it to the specification list.
- **F229-13** The operation scope. The route is generic over every operation of the declared sidecar, so the files sidecar's `write` and `watch` (`docs/spec/sidecars.md`) would reach a hidden page with no open surface. Required: state which operations the host receives and justify them against the surface-open rule of `sidecars.md`, or restrict them.
