# 관측 감사 계획

[English](observability-audit.md)

상태: 대기 중인 제안. 정본 작업 체크리스트는 [features](../features.ko.md)(F160, F161, F158, F159)다. 이 제안은 2026-10-11 감사의 결과와 항목이 구현하는 결정을 적는다. 항목을 닫으면 그 내용은 명세로 옮기고 이 글을 지운다.

## 명제

일어나는 모든 일은 event log([logging](../spec/logging.ko.md))에 기록된다. 시험의 성공과 실패 결과는 각각 로그의 한 자리에 매핑된다. 관측만을 위해 나중에 소스를 고칠 일이 없다. 기록은 성능 문제를 일으키지 않는다. 기준은 상황이 요구하면 바꿀 수 있고, 그때는 관련 문서에 근거를 남긴다. 시험이 달성하기 어렵다는 이유로 기준을 낮추지 않는다.

## 감사의 결과

감사는 core, sidecar와 plugin, 검증의 소스를 읽었고 아무것도 실행하지 않았다. 명제는 지금 거짓이다.

- **검사는 범위가 아니라 이름을 증명한다.** `make events-check`는 선언한 이름이 소스에 글자로 있는지만 보므로 주석도 통과시킨다. 선언하지 않고 방출한 이름, 필수 field, event 없는 원천은 찾지 못한다. `scripts/check-fallbacks.mjs`는 사유 주석을 요구하지만 일부 형식만 본다(Objective-C observer, monitor, KVO, timer, delegate, `return NO`, `recover` 없는 Go `go` 문, 버려지는 channel은 보지 않는다).
- **시험 결과가 로그에 매핑되지 않는다.** 실행 id, 시험 이름, offset이 로그에 닿지 않는다. 실행기는 출력을 메모리에 두고 실패만 출력한다. 감사 `check-events.mjs --logs`는 손으로만 실행되고 CI에 없으며, `auditLog`는 `error` event와 sidecar의 파일을 보고하지 않고, offset 파일은 검사가 끝날 때마다 덮어쓴다. stall 파일, 충돌 리포트, 표준 오류에는 event가 없다.
- **사슬을 잇는 id가 없다.** 로그의 약 300,000건 중 `cids`를 가진 event는 없다. 입력의 id를 발급하는 층이 없고 `native.input.key_down`은 catalog에 없다. page command, host 호출, sidecar 요청, 창, 프로젝트, 설정 변경, plugin 작업은 표면과 시각으로만 맞춘다.
- **침묵하는 원천이 있다.** native library의 observer, monitor, KVO, timer 등록 약 36개 중 13개만 기록한다. Go 호스트에는 `go` 문 약 21개와 `recover()` 0개가 있다. endpoint 메서드는 성능 trace가 켜져 있을 때만 기록한다. 보류 응답과 close의 buffer는 한도 없이 자란다. event를 쓰는 sidecar는 터미널 sidecar뿐이며, Go sidecar 둘과 plugin 일곱에는 catalog, event 파일, `cids`가 없다.
- **기록의 성능은 설계이며 측정이 아니다.** benchmark 결과가 기록돼 있지 않고, 입력 지연을 기록을 켜고 끈 상태와 비교한 적이 없으며, 첫 응답자는 프레임마다 메인 스레드에서 dictionary로 기록하고, `pty_read`의 hex는 바이트마다 할당하며, `page.call`은 자르기 전에 모든 인자를 직렬화한다.
- **부피가 신호를 가린다.** 139,068건(47.8 MB)의 로그는 `error` 0.0%, `warn` 0.4%, `info` 4.8%, `debug` 94.8%(`page.call` 83,755건, `native.input.query` 42,621건)를 담는다. 100 MB 5세대 회전은 이 부피에서 약 7시간치다.

## 결정

각 결정에 이유를 적는다. 나중에 읽는 사람이 다시 판단할 수 있어야 하기 때문이다.

1. **모든 수준을 기록한다. 버리지 않고 생산 쪽 비용을 줄이며 증거를 보존한다.** 사람은 측정한 로그 event의 94.8%인 `debug`를 포함해 전부 기록되기를 요구한다. 최소 수준 미만을 버리면 편집기 쪽의 멈춘 시작을 진단하는 데 쓴 바로 그 `debug` event(`loadFile` 없는 `page.call ready-1`)도 잃는다. 측정한 처리율(최대 1,500 events/s, 손실 없음)은 큐 한도보다 훨씬 낮아 writer에서 버려도 비용이 줄지 않고, 비용은 생산 쪽에 있다(`page.call`의 직렬화, 프레임마다 첫 응답자 dictionary, `pty_read` hex의 바이트마다 할당). 그러므로 생산 지점이 field를 싸게 만들고(builder 함수, 자르기 전의 전체 값 직렬화 없음, 바이트마다 할당 없음), 모든 수준을 저장하며, 신호를 읽을 수 있도록 `error`, `warn`, `info`는 `host-<boot>.jsonl`에, `debug`와 `trace`는 `host-<boot>.debug.jsonl`에 쓰고, 회전은 세대를 모두 보존하며 압축하지 않는다. 압축한 파일은 그 자리에서 검색할 수 없기 때문이다. 파일은 명시한 명령이나 명시한 디스크 예산 초과로만 지우고, 지울 때마다 다음 파일에 event `log.pruned`(파일, 바이트, 시간 범위)를 남겨 손실이 조용하지 않게 한다. 두 질문을 아래 적대 검증에 넘긴다: class `frame`(프레임마다, 가장 높은 빈도)의 event를 어떻게 완전히 저장하는가, 그리고 event의 94.8%인 `debug`를 어떻게 더 많은 수준으로 나눠 사람이 일부를 읽고 gate가 이름을 붙일 수 있게 하는가(후보: `debug`와 `trace` 사이의 수준 `verbose`, 번호 수준 `debug1`~`debug3`, 새 수준 없이 class가 결정).
2. **구조가 새 침묵 원천을 찾아야 한다.** 이름을 비교하는 가드는 새 침묵 원천을 통과시킨다. 언어마다 한 규칙이 event도 사유도 없는 원천 줄을 기준선 없이 나열하고, 모든 저장소가 부르는 명령(`soksak-events`)이 그것을 적용한다.
3. **시험 결과는 로그의 한 범위다.** 실행마다 `log.open`에 id와 manifest가 있고, 시험마다 `test.start`와 `test.end`를 저장하며, 실패한 실행의 출력과 증거는 기록이 분류할 때까지 보존하고, 로그 감사는 실행마다와 CI에서 실행된다.
4. **원천 종류마다 입구 하나.** native 등록, goroutine, endpoint 메서드, 호출, plugin 작업은 각각 한 입구에서 기록하므로 새 원천이 지점마다의 기록 없이 덮인다.
5. **기록한 것은 찾을 수 있어야 한다.** 로그는 정본이며 추가만 한다(crash에 안전한 JSON lines). 그 옆에 점진적으로 만드는 색인이 시간 범위, 수준, 층, event 이름, 표면, 세션, `cids`, 실행 id, 글로 하는 질의에 답하고, host가 결과의 한 쪽과 cursor를 돌려준다. debug 화면, `sok`, 시험마다의 판정(F160.16), 로그 감사가 그 하나의 질의를 쓰며 페이지는 파일을 불러오지 않는다. debug 화면의 타임라인은 페이지가 10만 행 파일을 전부 불러 그려서 응답을 멈췄다(F157). 색인을 어디에 두는가(로그마다 옆의 offset 파일, 또는 내장 데이터베이스)는 아래 적대 검증의 질문이다.
6. **수치가 성능 항목을 닫는다.** benchmark 수치, gate를 켜고 끈 입력 지연, 할당, 등급별 분당 바이트, 보존 시간을 로그에 기록해 예산과 비교하고, 예산은 근거가 있을 때만 바뀐다.

## 검증

가드는 시험이 일부러 더한 원천이나 event에서 실패해 Red를 보인다. 실행은 manifest, 표지, 로그 감사로 판정하며 선언 없는 `error`가 없어야 한다. 원천은 두 애플리케이션에서 관측한다. 성능 항목은 기록한 수치로 닫는다. 닫은 항목은 다시 열지 않으며 빠진 관측은 후속 항목이 된다.

## 적대 검증

위 결정은 반대로 논증하고 해결안을 제안하는 에이전트가 이견이 없을 때까지 반복해 검토한다. 이견, 답, 결과 변경을 여기에 기록한다.
