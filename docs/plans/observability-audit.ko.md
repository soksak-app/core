# 관측 감사 계획

[English](observability-audit.md)

상태: 대기 중인 제안. 정본 작업 체크리스트는 [features](../features.ko.md)(F160, F161, F158, F159)다. 이 제안은 2026-10-11 감사의 결과와 항목이 구현하는 결정을 적는다. 항목을 닫으면 그 내용은 명세로 옮기고 이 글을 지운다.

## 명제

일어나는 모든 일은 event log([logging](../spec/logging.ko.md))에 기록된다. 시험의 성공과 실패 결과는 각각 로그의 한 자리에 매핑된다. 관측만을 위해 나중에 소스를 고칠 일이 없다. 기록은 성능 문제를 일으키지 않는다. 기준은 상황이 요구하면 바꿀 수 있고, 그때는 관련 문서에 근거를 남긴다. 시험이 달성하기 어렵다는 이유로 기준을 낮추지 않는다.

## 감사의 결과

감사는 core, sidecar와 plugin, 검증의 소스를 읽었고 아무것도 실행하지 않았다. 명제는 지금 거짓이다.

- **검사는 범위가 아니라 이름을 증명한다.** `make events-check`는 선언한 이름이 소스에 글자로 있는지만 보므로 주석도 통과시킨다. 선언하지 않고 방출한 이름, 필수 field, event 없는 원천은 찾지 못한다. `scripts/check-fallbacks.mjs`는 사유 주석을 요구하지만 일부 형식만 본다(Objective-C observer, monitor, KVO, timer, delegate, `return NO`, `recover` 없는 Go `go` 문, 버려지는 channel은 보지 않는다).
- **시험 결과가 로그에 매핑되지 않는다.** 실행 id, 시험 이름, offset이 로그에 닿지 않는다. 실행기는 출력을 메모리에 두고 실패만 출력한다. 감사 `check-events.mjs --logs`는 손으로만 실행되고 CI에 없으며, `auditLog`는 `error` event와 sidecar의 파일을 보고하지 않고, offset 파일은 검사가 끝날 때마다 덮어쓴다. stall 파일, 충돌 리포트, 표준 오류에는 event가 없다.
- **사슬을 잇는 id가 없다.** `native.input.key_down`은 catalog에 없고 입력의 id를 발급하는 층이 없다. `cids`의 두 집계가 다르므로(25개 파일 969,368건에는 없고 로그 폴더 네 곳에는 33,693건) F160.8의 감사 script가 항목을 닫기 전에 다시 센다. page command, host 호출, sidecar 요청, 창, 프로젝트, 설정 변경, plugin 작업은 표면과 시각으로만 맞춘다.
- **침묵하는 원천이 있다.** native library의 observer, monitor, KVO, timer 등록 약 36개 중 13개만 기록한다. Go 호스트에는 `go` 문 약 21개와 `recover()` 0개가 있다. endpoint 메서드는 성능 trace가 켜져 있을 때만 기록한다. 보류 응답과 close의 buffer는 한도 없이 자란다. event를 쓰는 sidecar는 터미널 sidecar뿐이며, Go sidecar 둘과 plugin 일곱에는 catalog, event 파일, `cids`가 없다.
- **기록의 성능은 설계이며 측정이 아니다.** benchmark 결과가 기록돼 있지 않고, 입력 지연을 기록을 켜고 끈 상태와 비교한 적이 없으며, 첫 응답자는 프레임마다 메인 스레드에서 dictionary로 기록하고, `pty_read`의 hex는 바이트마다 할당하며, `page.call`은 자르기 전에 모든 인자를 직렬화한다.
- **부피가 신호를 가린다.** 호스트와 terminal sidecar의 파일 31개가 970,468건(345.2 MB)을 담는다. 바이트로는 `page.call` 45.4%, `sidecar.vt.request` 19.1%, `native.input.query` 18.1%, `native.record.info` 6.5%이고, 139,068건(47.8 MB)의 로그는 `error` 0.0%, `warn` 0.4%, `info` 4.8%, `debug` 94.8%를 담는다. 피크 처리율은 9,715 events/s로 큐 한도 안이다. 100 MB 5세대 회전은 평균 19~23시간치, 가장 높은 부하에서 약 7시간치이며, 회전에 닿은 파일은 아직 없다(가장 큰 파일 48 MB). 디스크 여유가 18 GiB(96% 사용)이므로 모든 파일을 지우지 않으려면 명시한 예산이 필요하다.

## 결정

각 결정에 이유를 적는다. 나중에 읽는 사람이 다시 판단할 수 있어야 하기 때문이다.

0. **가치로 기록한다: 모든 입력과 경계 통과는 발생마다, 다른 기록이 이미 말하는 것은 남기지 않는다.** 로그는 소스를 나중에 바꾸지 않고도 무엇이 왜 실패했는지, 어떤 연산이 어떤 대상을 바꿨는지, 어떤 입력이 어떤 출력이 되었는지, 무엇을 잃었는지 답해야 하므로, 아직 아무도 묻지 않았다는 이유로 제외하지 않는다. 규칙: 로그는 모든 입력과 층, 프로세스, 창, sidecar의 모든 경계 통과를 발생마다 실제 시각과 함께 담고, 모든 결정과 모든 실패를 담는다. 반복된 내용(delta 부호화), 파생된 사본, 저장된 사실을 되풀이하는 서술은 버릴 수 있다. 발생은 버릴 수 없다. 전달, 지연, 손실은 발생마다의 시각으로만 관측된다(`native.input.query`는 16 µs 간격의 363,445건이며 개수만 세면 잃는다). 원리는 재생이 아니다. window server, native 층, sidecar, page는 재생할 수 없으므로 원리는 경계다. 최소성은 질문 시험이 아니라 중복 시험이다: 기록은 다른 저장된 기록에서 파생되거나 저장된 사실을 서술한다고 script가 보였을 때만 제외하고, 표준 시나리오의 파생 몫은 delta 부호화 뒤 50% 아래로 둔다. 상태 스냅샷만 변경 시에 반복 횟수와 함께 저장한다(`native.input.source_changed`, 반복 99.7%). event는 사례로 받아들인다: 사건 또는 질문, 그에 답하는 event, 고정 로그로 답하는 시험. 사건 모음은 충분성 시험이며(각 사건에 답할 수 있어야 한다) 지나간 질문만 담으므로 최소성 시험이 아니다. 경계 통과에는 표집이나 조건부 ring을 적용하지 않고, ring은 항상 저장되는 요약 아래의 세부에만 허용한다. 모든 기록은 실제 마이크로초 `ts_us`와 모든 층의 `mono_ns`를 갖고(표집된 `page.call`은 지금 1 ms로 반올림된다), `cids`가 없는 입력 event는 가드가 실패시킨다.

1. **가치로 결정하고, 수준은 의미로 정하며, 비용은 생산 쪽에서 줄인다.** 최소 수준 미만을 버리면 편집기 쪽의 멈춘 시작을 진단하는 데 쓴 바로 그 `debug` event(`loadFile` 없는 `page.call ready-1`)도 포기한다. 큐는 측정한 피크를 담으므로 writer에서 버려도 비용이 줄지 않고, 비용은 생산 쪽(`page.call`의 직렬화, 프레임마다의 첫 응답자 dictionary, `pty_read` hex의 바이트마다 할당)에 있다. 각 생산자는 builder 함수로 field를 만들되 `enabled(class, level)` gate 하나 뒤에서 만든다. 수준은 의미로 정한다(`error` 실패, `warn` 손실·저하, `info` 결정·수명 주기, `debug` 경계 통과·입력). event 줄이 `class`를 저장하고(schema 2) 번호를 붙인 새 수준이 아니라 class가 `debug`를 나누므로 새 수준은 두지 않는다. `error`, `warn`, `info`는 `host-<boot>.jsonl`에, `debug`는 `host-<boot>.debug.jsonl`에 둔다. 로그는 JSON lines 정본으로 남고, 닫힌 세대는 framed zstd로 쓸 수 있으며 색인으로 frame 단위 검색이 된다. 보존은 파일이 아니라 실행(run) 단위다: 전체 상한(6 GiB), 분류되지 않은 실패가 있는 run의 고정(`.keep`), 다음 파일의 `log.pruned`(파일, 바이트, 시간 범위) event로 침묵하는 삭제가 없게 한다. `kill -9` 뒤의 보장은 최대 batch 간격(100 ms)의 event로 적는다. class `frame`은 시각, 순번, 크기, frame의 hash를 담은 compact segment로 발생마다 저장하며 frame 내용은 저장하지 않는다. 터미널 상태는 저장된 `pty_read`와 resize 입력의 재생으로 파생되고 hash가 재생을 검증하기 때문이다(결정 0). segment는 전체 상한에 포함되며 자체 예산이 없다(측정한 기록은 약 40 byte, 26,883건이 약 1 MB). ring은 더하지 않는다: 큐(8192 event, 16 MiB)와 100 ms 간격을 유지하고 손실은 `log.dropped`로 센다. 읽는 쪽은 현재 schema만 받아들이고 schema 1 파일은 파일 이름과 발견한 내용을 적은 오류로 거부한다. 파일은 변환하지 않으며 명시적 prune 명령이 제거한다.
2. **구조가 새 침묵 원천을 찾아야 한다.** 이름을 비교하는 가드는 새 침묵 원천을 통과시킨다. 언어마다 한 규칙 집합이 event도 사유도 없는 원천 줄을 기준선 없이 나열하며, 각 규칙 집합은 그것이 덮는 입구의 항목에 속한다. 등록 API는 입구 파일에서만 허용하고(정확한 규칙), 반환 경로는 근사 규칙이다. 사유 표지는 한 형식이다: `(default|silent): <reason>`. 모든 저장소가 부르는 명령(`soksak-events`)이 규칙을 적용한다.
3. **시험 결과는 로그의 한 범위다.** 검사 대상 앱은 여러 run을 서비스하므로 run id는 `log.open`이 아니라 event `host.test.start`와 `host.test.end`(층 접두어, 시험 이름, 결과)에 담는다. `scripts/test-evidence.mjs`를 확장하며 두 번째 manifest를 만들지 않는다. 각 시험은 flush barrier(`diagnostics.log.flush`)로 끝나고, 위치는 세대와 debug 파일을 가로지르는 `(boot, seq)`다. 멈춘 호스트는 표지를 쓸 수 없으므로 시험 증거 항목이 stall 파일을 연결한다. 실패한 실행의 출력과 증거는 기록이 분류할 때까지 보존하며, 로그 감사는 실행마다 그리고 CI에서 돈다.
4. **원천 종류마다 입구 하나.** native 등록, goroutine, endpoint 메서드, 호출, plugin 작업은 각각 한 입구에서 기록하므로 새 원천이 지점마다의 기록 없이 덮인다.
5. **기록한 것은 찾을 수 있어야 한다.** JSON lines 로그가 정본이며 추가만 한다. 각 파일 옆에 segment 색인(`.idx`: event, 표면, 세션, `cids`, run의 Bloom filter와 시간 범위)을 점진적으로 만든다. host가 시간 범위, 수준, class, 층, event 이름, 표면, 세션, `cids`, run, 글 질의에 한 쪽과 cursor로 답한다. debug 화면, `sok`, 시험마다의 판정(F160.16), 감사가 그 하나의 질의를 쓰고 page는 파일을 읽지 않는다(F157).
6. **수치가 성능 항목을 닫는다.** benchmark 수치, gate를 켜고 끈 입력 지연, 할당, 등급별 분당 바이트, 보존 시간을 로그에 기록해 예산과 비교하고, 예산은 근거가 있을 때만 바뀐다.

## 검증

가드는 시험이 일부러 더한 원천이나 event에서 실패해 Red를 보인다. 실행은 manifest, 표지, 로그 감사로 판정하며 선언 없는 `error`가 없어야 한다. 원천은 두 애플리케이션에서 관측한다. 성능 항목은 기록한 수치로 닫는다. 닫은 항목은 다시 열지 않으며 빠진 관측은 후속 항목이 된다.

## 적대 검증

위 결정은 반대로 논증하고 해결안을 제안하는 에이전트가 이견이 없을 때까지 반복해 검토한다. 이견, 답, 결과 변경을 여기에 기록한다.

### 1차

검토 넷: 수준과 class `frame`, 색인 저장소, 가드와 시험 매핑, 옳은 로그의 정의. 판정은 모두 이견이 남았다. 답은 위 결정에 있고 변경은 다음과 같다.

| 이견 | 답 |
| --- | --- |
| 보존 약 7시간, 피크 1,500 events/s, "`cids` 없음"이 틀리게 적혔다. | 감사에서 고쳤다: 평균 19~23시간, 9,715 events/s, `cids` 집계는 다시 셀 때까지 열린 상태. |
| 디스크 여유 18 GiB에서 "모든 파일 유지"는 예산이 없다. | 전체 상한이 있는 run 단위 보존과 분류되지 않은 실패의 고정(결정 1). |
| 기준선 없는 가드는 첫 항목에서 닫을 수 없다. | 언어별 규칙 집합이 입구 항목에 속하고 사유 표지는 하나(결정 2). |
| 앱 하나가 여러 run을 서비스하면 `log.open`의 run id는 틀리다. | `host.test.start`와 `host.test.end`, `scripts/test-evidence.mjs` 확장, flush barrier, 위치 `(boot, seq)`(결정 3). |
| 멈춘 호스트는 표지를 쓸 수 없다. | 시험 증거 항목이 stall 파일을 연결한다. |
| 변경 시 저장은 입력의 전달과 지연을 잃고, 질문 기반 최소성은 다음 사건의 증거를 숨기며, 최소성에 쓴 사건 모음은 순환이고, 표집은 드문 실패를 버린다. | 결정 0을 다시 썼다: 입력과 경계 통과는 발생마다, 중복 시험, 사건 모음은 충분성 시험만, 경계 통과는 표집하지 않는다. |
| `page.call`의 `ts_us`가 1 ms로 반올림되고 page·native event에 `mono_ns`가 없으며 입력에 `cids`가 없다. | 모든 층에 실제 마이크로초와 `mono_ns`, `cids` 없는 입력은 가드 실패. |
| 970,468건에서 정확한 반복은 바이트의 10.3%이고 중복 내용은 약 51%다(`sidecar.vt.request`의 반복 경로, `page.call` 인자, `native.record.info`의 중첩 상태, `native.input.query` 반복). | delta 부호화, 큰 인자의 hash 참조, 연결당 한 번만 저장하는 `root`와 `owner`. 50% 미만 추정은 모형이며 F160.20이 실제 writer로 측정한다. |

로그로 답할 수 있던 사건: 9건 중 전부 3건(편집기 시작, sidecar 재시작, `loadFile` 손실), 일부 3건(page 정지, 입력 중복, 선언 외 오류), 불가 3건(전면 앱, modal 기하, Tauri 시험의 120초 대기). 빈 곳은 입력의 사슬, 시험의 표지, event 계약 밖의 파일(stall 파일, `installed.json` 오류 같은 표준 오류), 기하이며 F160.8, F160.12, F160.15, F160.24의 입력이다.

남은 이견: delta writer가 16 µs 입력 간격에서 생산 비용을 낮게 유지하는지(측정 안 함), `exposureReply` 내용이 파생 가능한지(확인 안 함), 120초 시험 대기의 로그 증거 없음.

규칙과 측정한 사실로 정한 결정이며 사람에게 묻지 않는다: `frame` segment는 hash를 저장하고 내용은 재생으로 파생한다, segment는 자체 예산이 없다, ring과 drain은 기존 한도를 유지한다, schema 1 파일은 거부하고 prune 명령이 제거한다(결정 1). 각각 다음 검토 회차의 대상이다.

다음: 이 변경을 항목 F160.1~F160.24에 반영하고, 각 검토가 이견 없음을 밝힐 때까지 검토를 다시 돌린다.
