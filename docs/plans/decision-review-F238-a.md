## D4. View regions (F228)

### Decision

1. Region operations are view calls. The view calls the host through `sok-view`; the workbench stamps each call with the sender surface and routes region calls through the region record.
2. Refusal set. `REGION_HOST_CALLS` in `packages/workbench/view-calls.js` is an explicit allowlist of the region-kind host commands: the composition, document and image commands that the host registers in its command table (`packages/host/tauriv2/src/bindings.rs` and the Wails equivalent). Names are compared after mapping the Rust snake_case idents (`document_attach`) and the Go PascalCase methods (`DocumentAttach`) to the camelCase name (`documentAttach`). `imagePlace` (`surface-modules.js:110`, the plugin `image.place` call) has no host command in either table and no caller in `packages/` or `plugins/`; it is removed from the workbench surface and from `REGION_HOST_CALLS` (`view-calls.js:82`), and the allowlist test asserts its absence (Required changes). The allowlist carries a reason per name. A test reads the table and asserts that its region-kind entries equal the allowlist, and that `documentWebviews` (a window fact, not a command) is not in either. A second test scans `packages/workbench/` for literal names matching `document*`, `image*` or `composition*` passed to `invoke`, `composed`, `hostClose`, `bridge.call` or `scoped.native.call`; this scan is secondary and fails when a literal is missing from the allowlist.
3. Refusal on every plugin-facing path. Plugin code reaches the host through two handles that both lead to `invoke` (`packages/workbench/host.js:204`): `runtime.native` (`native: { call: invoke, on }`, `host.js:251-252`) and `call(name)` (`host.js:257-261`, non-dotted names forward to `invoke`). `surface-modules.js:462` currently exposes the raw `scoped.native` as `runtime.native`; that is replaced by a gated wrapper. The wrapper's `call` refuses every name in `REGION_HOST_CALLS` with the region error, and its `on` accepts only the names of Decision item 4. The workbench page keeps the raw `scoped.native` for `pageRuntime` (`surface-modules.js:84`), which is not plugin code. The refusal is placed in the shared gated wrapper, so every plugin-facing path passes it. The view runtime's `native.call` (`surface-modules.js:280`) and its subscriptions (`surface-modules.js:249`, `createViewSubscriptions`) are built from the same wrapper, so `runtime.native.on` in the view run is gated too. `VIEW_BRIDGE_CALLS = {viewRequest, viewEvent, viewReply}` (host commands at `bindings.rs:494-510`; raw workbench calls at `surface-modules.js:257, 263, 333`) is refused by the same wrapper. Tests call `runtime.native.call`, `call` and the view `run` with each name of the allowlist and of `VIEW_BRIDGE_CALLS`, and assert a refusal and that no region name reaches `registry.handle` (`host.js:258`).
4. `runtime.native.on` accepts only the names in `REGION_EVENTS`. `REGION_EVENTS` is exactly the four region events that `surface-modules.js` subscribes to: `document-stream` (`:103`), `document-state` (`:105`), `document-message` (`:106`) and `image-event` (`:115`). A test asserts (a) `REGION_EVENTS` equals those four literals and (b) `runtime.native.on` rejects `view-call`, `view-reply`, `view-stopped`, `view-responsiveness` and `view-presentation-abandoned` (`surface-modules.js:320-507`), which are view-bridge internal events.
5. Stacking, visual and input order, from the top: view DOM overlays, then view regions, then the view page DOM. A point inside a visible view overlay rect is delivered to the overlay's DOM view (`webview` or `mainWebview`) when that view's DOM has a hit at the point, and to nothing otherwise. The `mainWebview` of a hybrid surface is hit-tested the same way as `webview`. It is never delivered to a region or to the native plane.
6. Reapply: an image region reapplies its insets inside a local `CATransaction`. A document region reapplies at placement and in its `NSViewFrameDidChangeNotification` observer; neither runs in a `CATransaction`. The spec does not claim a window transaction for document regions.
7. Hit-test owner. The hit-test fix has one owner: `fix/view-region-close-F228-5`, which already rewrites `hitTest` (`webview_geometry.m:283-300`), and `SPWindowComposition.hitTest` (`webview_geometry.m:183-194`), the hybrid counterpart, which returns `self.mainWebview`'s hit at `:189` without a DOM test. Both are under this one owner. `feat/view-region-F228` does not change `hitTest`; its version is superseded when the fix branch merges, and the feat branch must not merge a `hitTest` change of its own.

### Supervisor decision F238-a-14-5 (final)

F238-a-2 limited the events a view may subscribe to through `runtime.native.on` to the four region events. That also removed `exposure-request`, which is the declared route of view exposure (`docs/spec/exposure.md`, F212.7-12) and is not a region event. Restoring it is not widening the allowlist: it is a declared core route that the narrowing removed by mistake. The subscribable set is the four region events plus `exposure-request`, named once in the explicit list `PLUGIN_NATIVE_EVENTS` of `packages/workbench/view-calls.js` (spec: `docs/spec/native-surfaces.md#plugin-host-calls`). Every other event name stays refused with `native event <name> is not served`. `REGION_EVENTS` keeps the four region events. Red: a view test that subscribes to `exposure-request` and receives the request was refused on the unchanged gate (`native event exposure-request is not served`). Green after the list adds it; the refusal test for an unlisted event stays.

Resolved by this decision: F238-a-14-3 and F238-a-14-4 (the shell and editor `exposure-request` subscriptions) need no plugin change. F238-a-14-1 and F238-a-14-2 (the `report` call) stay open under their repositories.

### Why

Routing through the stamped view call makes the revision, the region lifetime and the region record the only path to a region. A raw host call would skip them (`view-calls.js:74-76`, feat). This is a workbench choice with that basis, not a consequence of rule 9 of the plugin process rules. Rule 9 supplies only the envelope check.

Stacking follows the surface composition contract: "Declared plugin overlays and workbench menus/dialogs own input above native document regions" (main `docs/spec/surface-composition.md:24`), and "native content is never allowed to ... own an overlay's point" (`:28`). A region is native content, so it sits below a view overlay.

## D7. Origin form (F235, F237)

### Supervisor decisions (round 16)

These decisions are binding. Each states its reason. The Decision items below apply them.

1. Format. `projects.json` stays at format 1. AGENTS.md requires a format-number bump and a migration when a stored format changes; that rule applies when a released file could hold the changed shape. No released core has view surfaces: views exist only on unmerged branches, and core `main` has no released view. So no released format-1 file holds a view tab, the optional origin member changes the reading of no released shape, and the rule is not triggered. It is not waived. The test of the rule: if a released file could hold a view tab, the rule would apply, and the format would be raised with a migration. Reason: the rule protects installed data, and no installed data holds the changed shape.
2. Read boundary. Origin is validated once, at the layout read. `restoreOrigin` runs the validator `checkViewOrigin` and carries each refusal as data on its tab: the tab is restored in a refused state that holds the named item 4 text, shows it, and writes it to the log. Restore never throws, and view start reads the refused state and starts no view. This is auditor A's proposal (round 15, objection 3). It does not reverse round 13: round 13 requires that restore not throw, and this decision keeps that; only the place of the validator moves from view start to the layout read. Reason: the named error appears once per tab at the moment the layout is read, and view start reports the state it finds instead of deciding again.
3. Round 15 accepted items. They are applied in the Decision items below: one restore wording; an absent origin counts as loaded and is refused; the `tabOrigin` fallback is removed in the same change as the strict view-start refusal; NUL and array classification; each refusal is logged and shown on its tab, and the tab stays in the layout; one stored reading rule; the downgrade consequence. Reason: each item was accepted in round 15, and decisions 1 and 2 make them consistent.
4. Plugins/shell item. It is numbered F238-a-17, owner the shell repository. Exact change: `plugins/shell/ui/view.js:22` and `plugins/shell/test/view.test.mjs:47-53` stop treating null as the default origin; the view start refuses a missing origin with the item 4 missing-origin text and a null origin with the item 4 form text. Test, Red first, in the shell repository. Reason: the defect is in another repository, so it needs a checklist number to be tracked; its sub-item stays open under its owner.

### Supervisor decision (round 15, read boundary and format wording superseded by round 16)

There is no migration of persisted data for D7. A persisted tab whose state lacks the origin form of item 4 is refused per tab with its named error: the error is reported in the log and shown on that tab, and the tab is not dropped silently. The user reopens the tab. Reason: Core is 0.0.x and unreleased views have no installed state to preserve; the binding rules forbid backward compatibility, compatibility layers, fallbacks and migrations, and forbid turning bad input into a plausible value. A migrated `{directory: null}` would be such a value, so the migration and its round 11 and round 14 argument are removed. The format number of `projects.json` stays 1 (item 7). Only the upgrade part of item 7 changes.

### Decision

1. `origin` is always the object `{directory}`, with exactly one member named `directory`.
2. `directory` is an absolute path or null. Null means the tab recorded no directory.
3. An absolute path is a path whose first character is `/`. The `//` (UNC form) and `/<letter>:` (drive form) prefixes are refused too: a `/` test alone accepts them, so one string rule rejects every non-local form on every platform. The workbench applies the same predicate in `reportDirectory` (`tab-reports.js:125`, which today checks only the `/` prefix): the predicate becomes one exported function that `reportDirectory` calls, so a non-local directory is refused when it is reported (a `TypeError`, as today for a non-`/` path), not first at view start. Each host and the page apply the same string test: `path.startsWith("/") && !path.startsWith("//") && !/^\/[A-Za-z]:/.test(path) && !path.includes("\u0000")` in TypeScript, and the same four checks with `strings.HasPrefix` and `strings.Contains` in Go and `starts_with` and `contains` in Rust. No platform path API is used. The drive rule also refuses `/a:b`, a legal POSIX name; the rule is a portability choice and is stated as one. The `//` form is refused for the same portability reason: it is a UNC share prefix on Windows and implementation-defined on POSIX. Non-local forms in scope are the `//` and `/<letter>:` prefixes only. `/\` is a legal POSIX name and is not refused. A NUL byte falls under the not-absolute-path trigger of item 4: the predicate refuses any string that contains NUL, so such a path never reaches a native call.
4. An absent origin, a null origin, an object of another form, a non-string non-null `directory`, an empty path, and a path not starting with `/` are refused with an explicit error. The four texts and their triggers are:
   - `surface "<id>": view start origin is missing`: the origin field is absent.
   - `surface "<id>": view start origin is not {directory} with a path or null`: the origin is null, is not an object (a JSON array is not an object), has a member other than `directory`, or has a `directory` that is neither a string nor null.
   - `surface "<id>": view start origin directory is empty`: the `directory` string is empty.
   - `surface "<id>": view start origin directory is not an absolute path`: the `directory` string is not an absolute path under item 3: it does not start with `/`, it starts with `//` or `/<letter>:`, or it contains a NUL byte.
5. The page does not coerce. `packages/plugin-api/surface.js:12` (default `origin = { directory: null }`) and `:72` (`origin.directory ?? null`) are removed; `createSurfaceContext` throws a `TypeError` unless origin is exactly `{directory}` with null or a `/`-prefixed value. The `TypeError` message is the item 4 text for the same fault, so the page and the hosts name one fault one way.
6. Every tab creation passes its origin explicitly. `newTab(kind, params)` (`packages/workbench/plane.js:142`) gains a required `fromTabId` argument (null when there is no source tab) and calls `recordOrigin(tab.id, fromTabId)` itself. Its callers pass the source explicitly: the card-creation paths at `plane.js:779` and `:797` (already calling `recordOrigin`), and the last-tab-close path at `plane.js:518` (`newTab(..., null)`, recording `{directory: null}`; the closed tab leaves no source tab, so the new tab starts with null, as the workbench does today; a fresh tab is not derived from the closed tab, and carrying its directory forward would be a product change this decision does not make), and the new-space path `initial()` at `plane.js:163`, which builds tabs with `tab(t.plugin, t.title)` and calls `recordOrigin(id, null)`.
7. Origin persists with the tab layout, not with the tab session. The saved layout entry of each tab carries `origin` as `{directory}`, with the shape `{id, plugin, origin: {directory}}` inside the card's `tabs` in `projects.json`. The save path writes origin: `capture()` (`packages/workbench/plane.js:1554`) writes the recorded origin of each content-card tab through `originOf(tab.id)`, which throws for a tab with neither a recorded origin nor a loaded value (no fallback). A tab that was loaded without a recorded origin counts as loaded: `capture()` carries its loaded value forward verbatim, and an absent loaded value writes no origin member. `capture()` never coerces, never persists `{directory: null}` for an unrecorded tab, and never throws for an opened layout, so every save of an opened layout succeeds; `tab()` (`plane.js:129`) carries no origin. The field is optional, and `projects.json` keeps format 1 (`docs/spec/projects.md:60`), so origin is written by the same confirmed atomic layout write that creates its tab. No second store, write ordering or reconciliation is needed, and `tab-state.json` is not used: its contract is coalesced per-tab writes for frequent state, while origin is written once per tab. A tab without an origin, or with one that fails the item 4 form and path checks, is restored in a refused state with the item 4 text (Decision item 2): it is logged, shown on the tab, and starts no view. The tab stays in the layout, and the layout opens and saves, because the refusal is per tab and not a failure of opening the space (`docs/spec/projects.md:66` says so). Upgrade: no migration (round 16, decision 1). A layout saved before this change has content-card tabs without `origin`; each such tab is restored refused with the item 4 text for a missing origin, and the layout still opens and saves. The user reopens the tab. Downgrade: a layout saved after this change is not supported on an older build; that build ignores the member and drops it on its next save, so a tab restored there has no origin. The format number stays 1 (round 16, decision 1), and a refusal of format-1 files would refuse whole layouts, which round 8 rejected. The tab session file `tab-sessions/<tab>.json` is not the store, because `packages/workbench/tab-session.js` removes the file for a tab without document regions (`put(tab, null)`, `:55`, `:65`). On restore, `build(kept)` (`plane.js:1414`) and `adopt(kept)` (`plane.js:1564`) both call one exported helper, `recordStoredOrigins(kept)`, which runs after `restoreWindowState(kept)` and before the tabs are created and calls `restoreOrigin(tab.id, tab.origin)` for each stored tab of the layout. `restoreOrigin` is a new export of `tab-reports.js`. It stores the loaded value verbatim, runs the one validator, `checkViewOrigin` (the item 4 rules), once, and carries the result as data on the tab: the item 4 text when the origin is refused, and none otherwise. It never throws. A tab entry without an `origin` member is loaded with an absent value, which `checkViewOrigin` refuses as missing, so a stored tab without the member is read as the missing-origin refusal and no reader fills a value (one stored reading rule). View start reads that data first: a refused tab logs and shows its text and starts no view, and only an unrefused tab reads its origin. `recordOrigin(tabId, fromTabId)` (`tab-reports.js:135`) takes a source tab id and cannot restore an origin object, so the helper is used instead. The test calls the helper without mounting the plane.
8. The workbench fallback is removed in the same change as the strict view-start refusal of item 7. `tabOrigin` (`packages/workbench/tab-reports.js:141`, `?? Object.freeze({ directory: null })`) loses its fallback in that change, so no interim state yields `{directory: null}` for an unrecorded tab. After it, `tabOrigin` throws for a tab with neither a record nor a loaded value, and the view start path checks the refusal of item 2 before it reads the origin.

### Round 16 decisions on the objections (binding)

Two fresh auditors objected in round 16 (runs c971e2d1 and f6f5cd04). Each ruling below answers one objection, states the decision, and gives the reason. Items 4, 5 and 7 are read with these rulings.

- R1, scope (auditor B, objection 1). A view tab is a tab whose surface is a view. The origin rules of items 4, 7 and 8 (refusal at the layout read, the carry-forward in `capture()`, the throw of `originOf`) apply to view tabs only. A content-card tab that is not a view tab has no origin member and no refusal, and its save writes no origin member. The layout read decides view-tab status from the plugin's declared view surface. Reason: supervisor decision 1 states that the required origin applies to view tabs only, and no released core has view tabs, so a refusal on another tab would show an error with no view to protect. Recovery: a refused view tab stays refused until the user closes it; reopening creates a new tab through `newTab` and `recordOrigin`, which records the new tab id.
- R2, precedence (auditor B, objection 2). `recordStoredOrigins` runs before any tab of the layout is created. A restored tab id is new, so no record exists for it; `originOf` returns the loaded value only when no record exists. No path calls `recordOrigin` on a restored tab.
- R3, presence (auditor B, objection 3). `restoreOrigin` receives the origin by presence: an absent member is tested with `"origin" in tab` in TypeScript, with `present_value` (an `Option`) in Rust, and with a key test in Go. A `null` member is a present value. No reader merges absent and null with `??`.
- R4, page predicate (auditor A, objection 1). Item 5 is replaced: `createSurfaceContext` applies the full item 3 string test and throws a `TypeError` with the item 4 text of the first failing check. The predicate is exported once from `packages/plugin-api`, which the workbench already imports, so `reportDirectory` imports it too; each host keeps its copy in the same form. Conformance is stated by these vectors, which each implementation's test asserts: `/a` is accepted; `//server/share`, `/C:/x`, `C:\x`, `relative` and a path with a NUL byte are refused. Reason: a `/`-only page check accepts forms that item 3 rejects, so the page and the hosts would disagree about one origin.
- R5, text order (auditor A, objection 2). The four checks of item 4 run in the listed order and the first match gives the text. An empty string gives the empty text (check 3), not the not-absolute text.
- R6, one validator (auditor A, objection 3). The layout read is the only place a refusal is decided. The view-start host and page checks are defence in depth: they use the same predicate, they never run for a tab that the layout read refused, and a host refusal of a tab that the layout read accepted is a defect to report.
- R7, downgrade. The v0.0.9 spec states that the stored layout is read only in its current form and names the fields that fail explicitly (`projects.md:62`); it does not state the result for an unknown tab member. The downgrade result is therefore unspecified, and the decision does not rely on it: a layout saved after the change is not supported on an earlier build. This replaces the downgrade sentence of item 7.

### Why

The workbench always sends an object (`tab-reports.js:137`), so refusing an absent or null origin in the host and the page breaks no code path that records origin. A coerced `{directory: null}` for a missing record hides a defect, which `AGENTS.md` forbids ("reject invalid values at the boundary"). The `/` rule is the one the workbench already applies to directories (`reportDirectory`, `tab-reports.js:125`), and item 3 tightens it with the `//` and `/<letter>:` refusals, which the workbench takes too, so a view's origin and a tab's directory cannot disagree. Windows support is a separate change to that rule. The object form is the existing contract: the workbench sends it (`tab-reports.js:137`), the page default is an object (`surface.js:12`), and both hosts read it as an object (`surfaces.rs:82-86`). A single-member rule turns a future member into a refusal rather than a silent value, so changing the form to a string would churn the contract without a safety gain.

Persisting origin with the layout instead of the tab session follows from E4 below: the tab session file is deleted for plain surfaces, so origin stored there would be lost.  The layout entry, rather than `tab-state.json`, holds origin because origin is written once per tab with that tab and restore reads it from the layout the tab comes from. The reader never fills a missing origin, so a missing origin surfaces as the item 4 refusal. The format number stays 1 because the only stored-form change is the optional member, and a bump would need a migration or would refuse every format-1 layout. Two simpler options were rejected: re-deriving origin on restore, which the data cannot support because origin lived only in memory (E6); and limiting `plugins.md:223` to session-only origin, which would leave restored tabs without the origin their view needs.
