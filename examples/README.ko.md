# 예제

[`README.md`](README.md) 의 한국어 번역이다.

## browser

`browser/` 가 페이지다. 브라우저에서 단독으로 실행되며 그때 표면은 모사된다.
아래 두 애플리케이션이 실행하는 페이지도 이것이다.

배치는 `soksak` 라이브러리가 담당한다. 사이드바, 레일, 터미널은 모두 같은
카드이고 역할만 다르다. 지분을 갖는지 px 크기를 갖는지, 배치가 옮길 수 있는지가
그 차이다. 그 위에 페이지는 네이티브 합성의 제약을 재현한다. 표면은 CSS 스택 위에
있고, 선언한 프레임과 적용된 프레임은 시차를 두고 따로 움직인다. 여기서 통과하는
것은 애플리케이션에서도 통과한다.

`+` 버튼과 쪼개기 버튼은 새 탭이 어느 플러그인의 것인지 묻는다(T2). 탭을 다른
카드의 가운데로 끌면 그 카드의 탭이 되고(T3), 가장자리로 끌면 그 옆에 자리가
생긴다(T4). 원래 카드에 탭이 하나 남아 있었으면 카드 자체가 이동하고 빈 카드는
남지 않는다(T5). ⚙ 설정의 커밋 지연은 V7a 를, 적용 편차는 V7b 를 실패시킨다.
검사 결과는 화면이 아니라 로그로 간다. 브라우저의 콘솔과 애플리케이션의 로그다.

    pnpm example        # dist/ 를 빌드하고 저장소를 :8749 에 서비스한다
                        # http://localhost:8749/examples/browser/index.html

역할마다 파일 하나이고, import 는 한 방향으로 흐른다.

    index.html      문서, 그리고 나머지를 연결하는 배선
    app.css         크롬을 그리는 토큰과 크롬의 규칙
    settings.js     사용자가 고른 값 하나. 알리기만 하고 아무도 호출하지 않는다
    settings-ui.js  ⚙ 모달. 누르면 만들고 닫으면 제거한다
    icons.js        크롬이 그리는 lucide 경로
    plugins/        등록된 것 — 플러그인과 그것이 기여하는 섹션
    projects.js     프로젝트와 그 안의 스페이스
    ids.js          prj- spc- tab- 을 발급한다
    plane.js        판 하나: 카드, 탭, 끌기, 레일, 레이어, 렌더
    card.js         [data-native-modal] 카드의 입력 처리. 메인 문서와 오버레이
                    뷰가 함께 사용한다
    compositor.js   판이 표시한 슬롯을 측정하고 게시한다
    verify.js       판과 컴포지터를 읽고 결과를 보고한다
    host.js         애플리케이션이 페이지를 들고 있을 때의 실제 네이티브 표면과
                    모달. 브라우저에는 없고 그때는 페이지가 모사한다
    observe.js      관측 부품이 요청하면 요소 하나를 누르고, 경계 하나를 끈다
    framework/      어느 런타임이 이 페이지를 실행하는지, 그리고 호출하는 법
    terminal.html   터미널 표면이 표시하는 페이지
    overlay.html    [data-native-modal] 뷰가 표시하는 페이지

경계를 넘는 것은 호출하지 않고 알린다. 설정은 변경을 알리고 페이지가 판을 다시
배치한다. 판은 렌더를 알리고 페이지가 검증하고 게시한다. 컴포지터는 커밋을 알리고
페이지가 살아 있는 표면을 호스트에 알린다.

### 모델

    project  열려 있는 루트. 스페이스와 이름과 색을 갖는다
      └ space  판 하나의 내용: 배치, 포커스했던 곳, 레일 너비
          └ card  Soksak 이 배치하는 것
              └ tab  플러그인과 제목

프로젝트는 id 가 아니라 루트로 식별한다. 이미 열린 루트를 열면 그것을 활성화한다.
스페이스 전환은 하나의 판 위에서 배치를 교체한다. Soksak.replace 가 그 하나의
동작을 만드는 지점이다.

### 플러그인과 사이드바

플러그인은 두 가지를 갖는다. `+` 메뉴에서의 자리와 표면이다. 사이드바를 소유하지
않는다.

섹션은 사이드바에 설 수 있는 하나의 항목이다. 플러그인 파일이 자신이 기여하는
섹션을 등록하고, 표면이 없는 파일도 플러그인 없이 섹션만 기여할 수 있다. 세트는
id 아래의 순서 있는 섹션 목록이다. 링크는 세트를 자리에 놓는다. 왼쪽, 또는
플러그인의 레일이나 오른쪽이며, 링크가 없는 자리에는 사이드바가 없다. 세트와
링크는 사용자가 구성하는 것이므로 설정에 있고 ⚙ 설정에서 편집한다.

표면은 자신이 표시할 것을 `{url}` 또는 `{page}` 로 선언한다. 임의의 주소이거나 이
호스트가 서비스하는 문서다. 페이지가 커밋마다 그것을 게시하므로, 표면의 종류를
페이지 밖에서 지칭하지 않는다.

[`NATIVE-HOST.ko.md`](NATIVE-HOST.ko.md) 는 초안이다. 호스트 인터페이스 셋이
무엇인지, 두 애플리케이션이 무엇을 두 번 구현하는지, 그것을 Wails 서비스와 Tauri
플러그인으로 내려면 무엇이 필요한지 적는다.

## 애플리케이션

각각 자기 네이티브 뷰로 표면을 그린다. 페이지는 공유되며 `dist/` 와 함께 각
애플리케이션의 `frontend/` 로 통째로 복사된다. 다시 쓰는 것도, 애플리케이션마다
더하는 것도 없다. `host.js` 하나, `terminal.html` 하나, `overlay.html` 하나이고 두
런타임 사이에서 다른 것은 페이지가 자기 애플리케이션에 닿는 방법뿐이다.

`framework/` 가 그 차이를 갖는다. 런타임마다 파일 하나다.

    framework/index.js      하나를 고르고 나머지가 import 할 것을 export 한다
    theme.js        이 애플리케이션이 서비스하는 문서에 테마를 적용한다
    framework/tauriv2.js    invoke / listen, 그리고 Tauri 자신의 문서 주소
    framework/wailsv3.js    Wails 바인딩과 그 런타임
    framework/webview.js    애플리케이션 없음: 평범한 브라우저이고 호스트가 없다

런타임은 각자 정의하는 것으로 판별한다. Tauri 는 `window.__TAURI__` 로, Wails 는
`wails:` 스킴으로 판별한다. 표면과 모달은 같은 애플리케이션의 문서이고 같은 방식으로
로드되므로 같은 판별이 적용된다.

복사는 make 타깃이다. `go:embed` 는 자기 모듈 밖에 닿을 수 없고 두 애플리케이션
모두 컴파일 시점에 프론트엔드를 포함하기 때문이다.

    make example-frontend

각 애플리케이션은 두 프로파일 중 하나로 빌드하고 실행하며, make 타깃이 복사를 먼저
수행한다.

    make tauri              make wails              # 디버그 빌드 후 실행
    make tauri-release      make wails-release      # 릴리스 빌드 후 실행
    make tauri-build        make wails-build        # 빌드만
    make tauri-build-release  make wails-build-release

    make examples-size      # 둘 다, 두 프로파일 모두, 그리고 각 크기

실행 파일은 `examples/tauriv2/src-tauri/target/` 과 `examples/wailsv3/bin/` 에
놓인다.

두 창에는 프레임이 없다. 두 프레임워크가 프레임을 그리는 방법이 서로 다르다. 한쪽은
높이를 콘텐츠로, 다른 쪽은 창 전체로 재고, 한쪽은 창의 단추를 숨길 수 있고 다른 쪽은
못 한다. 그래서 프레임을 쓰면 페이지가 받는 크기부터 제목 표시줄만큼 어긋난다.
프레임이 없으면 두 설정이 같은 숫자를 갖고 같은 것을 뜻하며, 페이지가 창 전체를
받는다. 1200×760 이다.

창의 단추는 애플리케이션이 그리고, 창을 끄는 자리도 애플리케이션이 지정한다.
페이지는 그 둘을 `framework/` 를 통해 자기 런타임에 요청한다. 브라우저에는 창이
없으므로 둘 다 나타나지 않는다. 창은 화면에도 들어가야 한다. 남은 공간보다 큰 창은
줄어들고 두 프레임워크가 줄이는 방식이 달라, 페이지가 각각 1픽셀씩 다른 크기를 받게
된다. 그때 `examples/test/hosts.test.mjs` 가 실패한다.

### 그려진 것을 관측하기

페이지는 합성된 결과를 읽을 수 없다. 표면과 모달은 애플리케이션이 만든 뷰와 창이고
합성은 윈도 서버가 수행한다. `--observe` 로 시작하면 각 애플리케이션은 부품을 하나
더 등록한다. Wails 에서는 서비스, Tauri 에서는 플러그인이며, 자기 창과 자기에게
붙은 창들의 윈도 서버 번호를 출력한다.

    ./examples/wailsv3/bin/wailsv3 --observe
    ./examples/tauriv2/src-tauri/target/debug/soksak-tauri --observe

    observe: windows 5921

캡처 도구는 그 번호로 창을 지정하므로, 창을 앞으로 올리지 않고 포커스를 옮기지 않고
합성 결과를 읽는다. macOS 에서는 `screencapture -l5921 out.png` 이고, 아래의
`--capture` 는 애플리케이션 안에서 같은 창을 읽는다. 화면 영역을 캡처하면 앞에 있는
것이 함께 담기고, 창을 앞으로 올리면 측정 대상 상태가 바뀐다.

첫 보고는 페이지가 처음 커밋할 때 이루어진다. 그때 창이 화면에 있고 표면이 존재한다.
그 뒤로는 창 목록이 바뀔 때 번호를 출력하며 주기로 확인하지 않는다. 창을 붙이고 떼는
것은 애플리케이션이므로 그 지점에서 이벤트를 발행하고 부품이 구독한다.

경계는 표면 위에 있으므로 끌기는 좌표로 도달한다. 페이지 크롬의 버튼은 DOM 요소이므로
`--click ms,selector` 가 페이지에게 렌더링 후 클릭을 전달하게 한다. `;` 으로 이은
선택자 여럿은 순서대로 누른다. 모달을 열고 그 안의 것을 바꾸는 실행이 그렇게 된다.

    ./examples/wailsv3/bin/wailsv3 --observe --click '5000,button.act[title="설정"]'

    observe: clicked button.act[title="설정"]
    observe: windows 7480 7489

창이 가만히 있으면 아무것도 보고되지 않으므로 `--drive` 가 경계를 스스로 흔든다.
형식은 `wait,axis,line,dx,dy,ms,times` 다. 페이지가 그려질 때까지 wait 밀리초 기다린
뒤 그 축과 선 번호의 경계를 누르고 ms 동안 dx,dy 만큼 왕복하며, 이를 times 번
반복한다.

    ./examples/wailsv3/bin/wailsv3 --observe --drive 3000,x,2,-250,0,48,15

    observe: shaking x:2 at (405,421) by -250,0 in 3 steps, 15 times
    observe: shaking done

경계는 좌표가 아니라 이름으로 지정한다. 좌표는 창의 크기가 달라질 때마다 다시 정해야
하고, 빗나간 누름은 아무것도 움직이지 않고 아무것도 보고하지 않는다.

끌기는 페이지가 수행한다. 두 애플리케이션이 그 페이지를 실행하므로 어느 경계를 어떻게
끄는지는 한 번만 적힌다. 각 단계는 표면 위의 누름이 사용하는 경로와 같은 경로로
전달되므로 측정은 제품 자신의 경로를 지난다. 운영체제에 키나 버튼을 합성하지 않으므로
포커스는 움직이지 않는다.

누름은 전 구간 유지된다. 놓았다 다시 누르면, 경계가 최소 카드 크기에서 멈췄을 때
다음 누름이 경계가 없는 자리에 떨어진다.

`--transcript` 는 호스트 호출과 그 답을 한 줄씩 적는다. 기록기가 페이지에 있으므로 두
애플리케이션이 같은 형식으로 적는다. `examples/test/hosts.test.mjs` 가 두
애플리케이션을 이렇게 실행하고 두 기록이 일치할 것을 요구한다. 요청이 같다는 것은 두
호스트가 페이지에게 같은 판을 주었다는 뜻이고, 답이 같다는 것은 그것을 같은 자리에
놓았다는 뜻이다.

`--capture <디렉터리>` 는 갱신이 이어지는 동안 창을 녹화한다. 페이지가 갱신이 더
있는지를 보고하므로, 사람이 끄는 경계도 `--drive` 가 끄는 경계와 같은 방식으로
녹화된다.

    ./examples/wailsv3/bin/wailsv3 --observe --capture /tmp/frames

    observe: wrote 249 frames to /tmp/frames

다시 그려지지 않는 창은 — 디스플레이가 꺼져 있거나 창이 화면 밖에 있으면 —
프레임을 계속 전달하되 모두 idle 로 표시하고 이미지를 담지 않는다. 한 장도 적히지
않은 녹화는 그런 프레임이 몇 장 왔는지 보고한다.

프레임은 도착하는 대로 적힌다. 너비, 높이, 한 줄의 바이트 수 뒤에 원시 BGRA 가
온다. 프레임마다 인코딩하면 프레임이 버려지고, 버려진 프레임이 측정 대상이다.
스크린샷은 쓸 수 없다. 시스템이 요청마다 합성을 새로 만들어 반환하므로, 리사이즈와
다음 렌더 사이의 한 프레임짜리 상태는 담기지 않는다.

`make examples-verify` 가 두 애플리케이션을 이 방식으로 실행하고 프레임을 읽는다.
`examples/test/` 를 보라. 파일은 한 번에 하나씩 실행한다. 각 검사가 실제 창을 끌고
녹화하므로, 둘이 동시에 돌면 각자 재려던 프레임을 얻지 못한다.

이 검사들은 실제 창과 실제 끌기를 몰고, 그 끌기의 시각은 페이지 자신의 시계가 만든다.
플랫폼이 그 시계를 묶으면 — 16 ms 한 걸음이 900 ms 가 되면 — 끌기는 어떤 예산 안에서도
끝나지 않고, 그 실행은 느리게 잰 것이 아니라 아무것도 재지 못한 것이다. 묶인 시계를
보고하지 않은 실행의 결과만 믿을 수 있다.

창 번호는 macOS 만 구현되어 있다. Windows 에서는 HWND 를, Linux 에서는 X 창 id 를
보고할 것이다. 플래그가 없으면 두 부품 모두 등록되지 않는다.

## 각각이 네이티브로 그리는 것

브라우저 표면은 google.com 을 여는 웹뷰다. 터미널 표면은 이 애플리케이션이
서비스하는 페이지를 여는 웹뷰이고 뒤에 셸이 있다. `[data-native-modal]` 요소는 그
위에 놓인 자기 웹뷰가 그린다.

macOS 만 작성되어 있다. `examples/wailsv3/native_other.go` 와
`examples/tauriv2/src-tauri/src/native.rs` 가 다른 플랫폼이 무엇을 쓸지 적는다.
