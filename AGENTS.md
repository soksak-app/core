## Implementation

- Choose the simplest implementation that fully meets the current contract, never a reduced one. Remove obsolete code paths; keep no compatibility layer, fallback, or backward compatibility, and remove the reading code of an earlier form. A reader accepts only the current stored format and rejects any other with an explicit error that names the file and what it found. While the release version is 0.0.x, a stored-format change ships no migration, as code or data: the reader rejects the earlier form, and an earlier-form file, tracked or held by a person, is edited into the current form in the same change. No conversion code exists, and no person is asked to create the file again. Avoid abstractions, settings, and indirection for uncertain future requirements; choose a durable architecture rather than a temporary implementation that requires replacement.
- Native bundle builds follow the [native bundle build](docs/operations/examples.md#native-bundle-build) guard.
- Use a maintained library for any function it provides. Write one only when none meets the contract, and state in the code which requirement the libraries miss.
- Publish events for state changes and let subscribers consume them. Poll or use timers only when no event source exists, and state why. Make operations idempotent and make every occurrence observable mechanically through an event, status, or log, without searching for it.
- No code starts `ps`, `kill`, `pgrep` or `lsof` as a subprocess. Read a process through the platform interfaces or the native library, signal it through `kill(2)`, and judge a child by its wait status; Node reads it through the [process table](docs/spec/verification.md#process-table) module, and `make check-process-tools` enforces this for Go, Rust and Node sources.
- Local development links installed dependencies to development directories with symbolic links, never clones or copies. Builds use linked and real installations through the same declared paths, and resolve paths from declarations or discovery ([local development links](docs/operations/install.md#local-development-links)).
- The refresh rate of a window's display is unknown in advance and changes when the window moves to another display. Neither the application nor a check assumes a rate: code either observes the refresh rate of the window's display at the moment it needs it and follows that value, or is designed so the rate does not matter, such as by pacing work by the window's display frames or by judging in the frames that the display delivered. A fixed frame time (16 ms, 8.33 ms, 1/60 s) or a required refresh rate is a defect.
- Repository and workspace folders hold only tracked files and declared build output. Run logs, temporary scripts, and message files go to the session's temporary folder; no record cites them. `sok-check docs` reports each untracked file.
- No check repeats a declared tool or dependency version. Package managers and CI read the declaration, a local toolchain check compares major versions, and `scripts/check-versions.mjs` judges only this repository's own declared versions in `pnpm test`.
- The kit is the one tool that repositories run. It installs nothing, has no installation step, compares no tool versions, and loads only the module each check needs. Installation belongs to the consumer and its package manager.
- Command names state their work in plain words ([command names](docs/operations/examples.md#command-names)); `make check-commands` enforces them in every repository.
- Archiving a repository removes its local checkout.
- Separate responsibilities. Add native platform code only when existing APIs cannot provide the behavior.
- Keep the [private native API inventory](docs/operations/private-native-apis.md) current with each API or call-condition change, and read it first when diagnosing failures after native, framework, SDK, or OS updates; review each correction's necessity and actual API semantics.
- Evaluate existing changes for harm first. Revert harmful changes at once, and remove incorrect or unnecessary ones even when harmless; preserve correct changes. Commit unrelated changes separately where possible, stating their purpose; unrelated work is no evidence for the assigned task.
- Match the formatting, naming, and idiom of the surrounding files.
- A new shipped runtime module updates its package files declaration and passes its owning staging test before a native build.
- Verify behavior before rewriting commits. Merge or push only with authorization.
- Report every error. Never ignore a result, swallow an error, coerce invalid input into a valid-looking value, or drop input or output silently. Reject invalid values at the boundary with an explicit error; a bounded buffer that sheds data signals it and documents it.
- Keep one canonical task checklist with the states `[ ]` waiting, `[~]` active, `[o]` complete, `[!]` held, and `[-]` closed. Each repository keeps its own. A parent is `[~]` only while a child is `[~]`.
- `[~]` states what remains and what it waits for. `[!]` is not completion: it states its answer, the reason it is held, and the condition that resumes development, and stays held until that condition is met. Hold an item only for a condition outside the active work, such as a release, a pin, the end of development, or a measurement phase, and audit it only against that reason, without rerunning unrelated full suites.
- `[-]` states `Closed:` with its reason, or one of the [closure forms](docs/operations/examples.md#closure-forms). No closure is a fix, and none closes an executable check or release condition.
- For assigned work, set priority and update the contract and checklist before implementing. Never reopen a completed item; add a linked follow-up ID. Record a new instruction in the checklist and run it by priority at the next stopping point, stopping active work only when the user asks or priority requires it.
- Size each item to one unit of function that can be developed, verified, and committed alone; split larger work. Keep uncommitted changes to one item and commit by unit of function. Parallelize independent items, but finish an active item's work, verification, documentation, and commit before starting more.
- Verify and commit an item before marking it `[o]`; its changelog entry goes in that commit. Process rules stay in this guidance, never in checklists or changelogs.
- A correction that is delivered to users only through another repository's release is a checklist item when recorded, and is reported as unreleased until published. Release, publication, deployment, and registry actions count as completion criteria only when the task scope names them; otherwise they are tracked separately and are no prerequisite for local work.
- Classify each request before recording it: process rules go to this guidance, project work to the checklist, durable user context to memory. A simple question needs only an answer.
- Work on `main` by default. Use a branch `{type}/{shortname}-{checklist id}` or a worktree `{project}-{shortname}-{checklist id}` when isolation is needed. Immediately after a merge into `main`, remove that worktree and branch; never remove an unmerged one.
- Test code that cannot merge into `main` is cherry-picked while it has meaning, or discarded, and removed before the commit. If immediate removal is impossible, a checklist sub-item states the removal condition.
- Keep a standard once set: fix code that fails a check. Change a criterion only when it is wrong, and state why in the same change.
- Judge by what is right, never by principle or convenience. A criterion changes only when the situation requires it, with evidence in the related document, and is never lowered because a test or a goal is hard to meet. A hard decision, or one resting on a new argument, goes to adversarial review by agents, which argue against it with evidence and give a solution for each objection, until no objection remains. The decision, reasons, and answered objections go in the related document.
- Treat an unexpected finding in existing code as a defect to report and resolve: fix it, or record the verification that shows it is correct, and add any missing rule. Existing code is no reason by itself.
- Before changing production code for a reported or hypothesized behavior defect, add a tracked test at the owning module that reproduces it, and record its Red and Green results ([agent verification rules](docs/spec/verification.md#agent-verification-rules)).
- When a request cannot be met the standard way, state which part needs another approach and why before implementing. No workarounds: fix the cause, not the symptom, and never solve a problem by adding another problem.
- Decide what the contract, the rules, and the measured facts determine, and proceed without offering options. Ask the user only for a decision that is theirs and cannot be derived, or when a new finding changes an earlier decision; then state the finding, the affected decision, and the concrete change, plainly. Do not ask again about what is already decided.
- When your judgement or change is wrong, state the cause and your part first, completely. Do not explain it away, redefine a contract to make the fault expected, or cover it with another change.

## Structure

- Core (`packages/`), plugins, and sidecars never name each other in code or tests. Plugins and sidecars live in their own repositories ([repositories](docs/spec/plugins.md#repositories)); only declarations connect them: `environment.json` names plugins only as references in `workspace`, `sidebars` and `settings` and installs none, `plugin.json` lists required sidecars and plugins in `dependencies`, its extension points in `extends` and `contributes`, and its plugin categories and the categories it requires in `categories` and `requires`, and `sidecar.json` describes a sidecar ([plugins](docs/spec/plugins.md)). `make check-boundaries` knows no plugin: it checks that core sources name no `@soksak/` package other than a core package, and that core's window checks, benchmarks and harness modules name no plugin or sidecar other than the `e2e/fixtures` fixtures ([plugin processes](docs/spec/plugin-processes.md#verification-boundaries)). Each plugin and sidecar repository checks its own sources.
- Repository boundaries exchange only declared contracts, exposed commands, DOM, statuses, and extension points, and no core build or check reads another repository. A package relation is declared only as `dependencies` of a manifest; a plugin category names a function and no package ([plugin categories](docs/spec/plugins.md#plugin-categories)).
- Common functionality belongs to core. Plugin functionality never moves into core. A sidecar holds native functionality for one domain.
- Platform code lives only under `platform/<os>/` (`darwin`, `windows`, `linux`) in the owning package, with no stub files for other platforms. Native package layout (`src/`, `tests/`, root manifests, `_test` files) follows the [native host specification](docs/spec/hosts.md).
- Test placement, shared contract cases, and the real-input rule follow [test kinds](docs/operations/examples.md#test-kinds).
- Private framework declarations live under `private/` in the platform directory and follow [private native APIs](docs/operations/private-native-apis.md). Never fake framework state to work around a missing interface.
- A platform implements every host platform interface operation or returns `not implemented on <os>` from `platform/<os>/unsupported.*`; a host missing a required operation fails at startup ([host specification](docs/spec/hosts.md)).
- A check ends or removes the recordings, processes, and services it started, and fails when any remain.
- Every user operation runs a declared command, and every visible state has a status. Elements connect only to declared commands through the shared binder, which the runtime audit judges ([exposure](docs/spec/exposure.md)).
- A surface shows a page of its plugin. A page shows web documents only in document regions attached to its own elements ([native surfaces](docs/spec/native-surfaces.md#document-regions)); a web address is never a surface.
- Diagnostic code exists only in diagnostic builds; its event-log rules are in [logging policy](docs/spec/logging.md#policy).
- Runtime diagnosis uses the existing application event log as the single record. Add missing observations to its gated writer; create no separate histories, collectors, or profiling runs.
- Every error the user can see goes through one display path, which writes `error: <where>: <text>` to the application log when it appears. Any other display of an error is a defect, and only this path uses the error color. A display shows only the current state, so the log keeps each error that the next draw removes.
- A ResizeObserver of core starts observing at an animation frame, which runs before that frame's observation round; observation that starts during the round defers its first notifications and WebKit reports a loop error ([native surfaces](docs/spec/native-surfaces.md)).

## Documentation

- Read the applicable specification before changing behavior. When the contract changes, update the specification first, and mark incomplete implementation in [features](docs/features.md).
- Keep one canonical document per topic. `docs/spec/` defines current contracts without checklist IDs, progress, or history. `docs/features.md` separates implementation, validation, and release. `docs/operations/` holds current procedures. `CHANGELOG.md` records actual changes and validation.
- README files hold only an introduction, minimum startup steps, and document links. `docs/plans/` holds pending proposals only; remove one once its approved content is in the specification.
- Write documents, comments, identifiers, logs, errors, and test names in English. Update the matching `.ko.md` in the same change with the same information; Korean text keeps technical terms in English and translates only the surrounding context.
- Describe current behavior and its actual reasons. Personal preferences and conversation context belong in memory outside Git.
- Use direct action names with explicit subjects and objects, and state a cause in one sentence. Use no metaphors, personification, or colloquial wording in comments, documents, logs, or commits.
- Name each concept with one term. Add a new concept to the term list (`terms.json` of the kit, [terms](docs/spec/terms.md)) before using it.
- Every record (documents, identifiers, comments, test names and fixtures, checklists, changelogs, commit messages, and configuration file descriptions) states facts about this repository only: what a subject does, requires, and guarantees; a defect's input, behavior, and expected behavior; a change and its reason. Records never name who requested, decided, or found something, how records were cleaned or rewritten, the local environment, local or personal paths, commit ids, pull request numbers, or CI run numbers. Other work is cited by checklist ID. External code that the repository copies or forks keeps its license notice and names its source.
- Commit messages follow the form in [commit hooks](docs/operations/examples.md#commit-hooks). They have no footer, and the author is `min-0-max <max@blue.tools>`.

## Verification

- CI and release jobs own their toolchain, dependency acquisition, builds, and checks, and check out no other repository ([CI and release ownership](docs/spec/verification.md#ci-and-release-ownership)). End-to-end checks run only locally through make.
- Start long operations with a short yield and keep their live process or session handle. Do not block on foreground waits or retry loops. Report the current step, and inspect the same live handle before deciding that an operation ended.
- Completion, check selection, full-suite timing, time limits, progress output, and evidence rules are in [agent verification rules](docs/spec/verification.md#agent-verification-rules). Native and example checks follow [example verification](docs/operations/examples.md).
- Window checks, captures, recordings, visual and timing evidence, and IME verification follow [window check operation](docs/operations/examples.md#window-check-operation).
- Run `make check-docs` for every change, and review documents against the code; structural checks do not verify meaning. `make check-docs` requires that the document and anchor of each section reference exist in every text file, and that the target of each link of a document exists. A section reference in a text file is `docs/<path>.md#<anchor>`; an anchor ends at the first character that is not a letter, digit, `-`, or `_`, so a Korean particle after a reference needs a code span.
- Accept an intermittent failure only through a tracked repeat target ([repeat an intermittent failure](docs/operations/examples.md#repeat-an-intermittent-failure)).
- Waiting and held items stay out of work selection until their recorded conditions are demonstrably resolved; their implementation or verification does not run beforehand.
- Independent development may run in parallel, but only the lead runs and schedules builds and verification. Disk and cleanup rules: [temporary folders](docs/operations/examples.md#temporary-folders).
- Record discovered facts, failure causes, architectural decisions with their evidence, and unresolved verification conditions in the owning specification, checklist, or changelog, without quoting the operator. Transient chat and raw run logs do not replace durable records.
