# Development

[한국어](AGENTS.ko.md)

This workspace contains the headless layout library `soksak`, the workbench frontend, plugins, and applications. The [plugin specification](docs/spec/plugins.md) defines the directory roles and their interfaces.

## Implementation

- Choose the simplest implementation that fully satisfies the current contract. Remove obsolete code paths instead of adding compatibility layers or fallbacks. Do not keep backward compatibility or add migrations: when a stored format or location changes, the reader accepts only the current one and rejects another with an explicit error that names the file and what it found, and the code for the earlier one is removed. Avoid abstractions, settings, and indirection for uncertain future requirements; choose a durable architecture rather than a temporary implementation that requires replacement.
- Publish events for state changes and let subscribers consume them; use polling or timers only when no event source exists, and state why. Make operations idempotent, and make each occurrence observable mechanically through an event, status, or log without searching for it. Do not use symbolic links. Resolve paths from declarations or discovery (manifests, module resolution, build variables), not from assumed relative locations.
- Keep responsibilities separate. Add native platform code only when the required behavior cannot be implemented through existing APIs.
- Maintain the [private native API inventory](docs/operations/private-native-apis.md) with each API or call-condition change. Read it first when diagnosing failures after native source, framework, SDK, or OS updates; review each correction's necessity and actual API semantics.
- Evaluate existing changes for harm first and revert harmful changes immediately. Remove incorrect or unnecessary changes even when they are harmless. Preserve correct changes, but commit unrelated changes separately where possible and state their actual purpose; unrelated work is not evidence for the assigned task.
- Write code in the formatting, naming, and idiom of the surrounding files.
- Verify behavior before rewriting commits. Do not merge or push without authorization.
- Report every error. Do not ignore a result, catch an error without reporting it, coerce an invalid input into a valid-looking one, or drop input or output silently; reject invalid values at the boundary with an explicit error, and signal and document any bounded buffer that sheds data.
- Maintain one canonical task checklist with `[ ]` waiting, `[~]` active, `[o]` complete, and `[!]` temporarily bypassed states; `[!]` is not completion and requires a cause and retry condition, and work resumes when the recorded retry condition is met. For assigned work, determine priority and update the applicable contract and checklist before implementation. Do not reopen completed items: add a linked follow-up ID. Keep uncommitted changes within one checklist item. Parallelize independent items, but control work in progress: finish active work, verification, documentation, and its commit before starting more items, so completed items grow instead of active items. A parent item is `[~]` only while one of its children is `[~]`. Use `[!]` only when an item blocks all further progress; audit a `[!]` item only against its cause and retry condition, without rerunning unrelated full suites. Verify and commit an item before marking it `[o]`. Each repository keeps its own checklist. Keep these process rules only in agent guidance, not in checklists or changelogs.
- Classify each request before recording it: durable work-process rules belong in agent guidance; project work belongs in the single canonical checklist; durable user-specific context belongs in memory; a simple question may need only an answer.
- Work directly on `main` by default. Use a branch named `{type}/{shortname}-{checklist id}` or a worktree named `{project}-{shortname}-{checklist id}` when agents or the situation call for isolation. Immediately after merging into `main`, remove that worktree and its local branch to prevent stale storage, folder fragmentation, and merge-state ambiguity. Do not remove an unmerged worktree or branch.
- Test code that could not be merged into `main` is either cherry-picked while it still has meaning or discarded; remove it before committing. When immediate removal is impossible, record a checklist sub-item stating the removal condition.
- Keep a standard once it is set. When code does not meet a check's criterion, fix the code; change the criterion only when it is itself wrong, and state why in the same change.
- Treat an unexpected finding in existing code as a defect to report and resolve: fix it, or record the verification that shows it is correct, and add a rule when the finding shows one is missing. Existing code is not a reason by itself.
- For every reported or hypothesized behavior defect, add a tracked test at the owning module that reproduces the failure before changing production code. Run it against the unchanged implementation and record the failing assertion as Red; after the correction, run the same test and record Green. If ordinary inputs cannot reproduce the failure deterministically, use an explicit test-controlled fault injection that exercises the same contract. A diagnosis, temporary script, or test written only after the correction is not Red evidence. Keep the test and its consumer contract in their respective owning packages.
- When a request cannot be met the standard way, state which part needs another approach and why before implementing it. Workarounds are not accepted: a fix removes the cause, not its symptom, and a problem is not solved by adding another problem.
- Decide what the contract, the rules, and the measured facts already determine, and proceed; do not offer a menu of options. Ask the user only for a decision that is genuinely theirs and cannot be derived, or when a new finding requires changing an earlier decision; then state the finding, the decision it affects, and the concrete change, plainly. Do not ask again about what is already decided.
- When a judgement or change of yours is wrong, state the cause and your part in it first, plainly and completely. Do not explain it away with surrounding circumstances, do not redefine a contract so that the fault becomes expected behaviour, and do not cover it with another change; concealment hides the real problem and makes the next decision harder.

## Structure

- Core (`packages/`), plugins, and sidecars do not name each other in code or tests; plugins and sidecars live in their own repositories ([repositories](docs/spec/plugins.md#repositories)). Only declaration files connect them: `environment.json` lists plugins, `plugin.json` lists sidecar packages, and `sidecar.json` describes a sidecar. `make boundaries` checks that core sources name no plugin id or sidecar package of the repositories that `scripts/workspace-registry.json` declares; each plugin and sidecar repository checks its own sources.
- Core, plugins, sidecars, kits, specifications, and contracts are separate repository boundaries. They exchange only the declared wire contract and exposed commands, DOM, and statuses; manifests such as `environment.json`, `settings`, and `plugin.json` list what is installed at which version, and a relationship between packages is declared only as `dependencies` of a manifest. A package's tests do not verify another package's implementation: consumer tests use fakes or fixtures at the consumer boundary, while implementation and shared contract cases run in the owning package. Tests must not read another package's paths, SDK, build, or implementation names.
- Common functionality belongs to core so plugins do not reimplement it. Plugin functionality does not move into core. A sidecar holds native functionality for one domain.
- Platform-specific files live only under `platform/<os>/` (`darwin`, `windows`, `linux`) in the owning package. Do not add stub files for other platforms.
- Native code packages (Go, Rust, Objective-C) keep code in `src/`, tests in `tests/`, and manifests and build files at the root. Go and Rust files that serve the same role have the same name; test files end in `_test` in both languages. The [native host specification](docs/spec/hosts.md) lists the allowed differences.
- Put each test beside the module that owns the behavior under test. Tests of a consumer verify the contract from the consumer's point of view; tests of basic functionality live with the implementation's owning package. Do not centralize tests in a convenient directory across unrelated modules. A test exercises a module through its exports or declared interfaces; it does not extract and execute source text of another file. Repository audits must discover implementation and test languages from tracked files and fail when an executable implementation language has no declared, runnable test coverage.
- Private framework declarations live in the platform directory under `private/` (for macOS `native/darwin/src/private/`). Sources and tests include those headers instead of declaring private APIs themselves. Each private API is listed in `docs/operations/private-native-apis.md`, and it is used only for its intended purpose; do not fake framework state to work around a missing interface.
- A platform either implements an operation of the host platform interface or returns a `not implemented on <os>` error from `platform/<os>/unsupported.*`; a host that cannot provide a required operation fails at startup instead of running partially. `make platforms` and `make hosts-check` check the layout.
- Recordings, processes, and services started by a check end or are removed when the check ends; the check fails when any remain.
- Every user operation of a document runs a declared command: controls point to it with `data-command`, and handlers run it through the registry instead of calling module functions. Continuous gestures have a command for their result, and shortcuts run commands. Commands are declared first, and elements are connected only to declared commands through the shared binder (`createBinder` in `@soksak/plugin-api`). Every visible state has a status, and every interactive element has a command binding and a dom name. Coverage is judged at runtime by the binder audit (`core.page.audit`, `unbound` in `core.surface.document`, `e2e/audit.test.mjs`), not by source patterns; `make exposure-check` checks only that names in sources are declared and declarations are registered. The [exposure specification](docs/spec/exposure.md) defines the rules.
- A surface shows a page of its plugin package. A page shows web documents only in document regions attached to its own elements ([native surfaces](docs/spec/native-surfaces.md#document-regions)); a web address is never a surface.
- Diagnostic code (host diagnostic methods, recording, and the page diagnostic module) exists only in diagnostic builds. Release staging omits the page diagnostic module.
- Every error that the user can see is shown through one display path that writes it to the application log at the moment it appears (`error: <where>: <text>`); a display that shows an error by any other path is a defect, and the error color is used only by that path. A display shows only the current state, so the log is the record of an error that the next draw removes.
- A ResizeObserver of core starts observing at an animation frame, which runs before that frame's observation round; observation that starts during the round defers its first notifications and WebKit reports a loop error.
- A command whose reply takes longer than 10 seconds declares `timeout` (milliseconds, at most 600000); the host relay uses it.

## Documentation

- Read the applicable specification before changing behavior. Update it first when the contract changes and mark incomplete implementation in [features](docs/features.md).
- Keep one canonical document per topic. `docs/spec/` defines current contracts without checklist IDs, progress, or history; `docs/features.md` separates implementation, validation, and release; `docs/operations/` contains current procedures; `CHANGELOG.md` records actual changes and validation.
- Keep README files limited to an introduction, minimum startup steps, and document links. Use `docs/plans/` only for pending proposals; remove a proposal after incorporating its approved content into the specification.
- Write documents in English. Update the matching `.ko.md` translation in the same change with the same information; Korean text keeps technical terms in English and translates only the surrounding context.
- Describe current behavior and actual reasons. Personal preferences and conversation context belong in memory outside Git.
- Use direct action names and explicit subjects and objects. State a cause in one sentence. Do not use metaphors, personification, or colloquial wording in comments, documents, logs, or commits.
- Comments in `packages/soksak` use English. Comments in other directories use Korean. Identifiers, logs, errors, and test names use English.
- Commit messages use `type(scope): Subject`. The type is `feat`, `fix`, `docs`, `style`, `refactor`, `test`, or `chore`; the subject is an imperative phrase of at most 50 characters that starts with a capital letter and has no final period. A blank line separates the body, which is wrapped at 72 characters and states what changed and why. An optional footer names the checklist ID as `Refs: <id>`. Commit messages have no generated-by text, co-author trailers, or session links.

## Verification

- An acceptance condition that has not been observed remains unresolved. Unit passes, command replies, and inferred behavior do not substitute for observation at the required verification level.
- Run `make docs-check` for every change and review the documents against the code; structural checks do not verify meaning.
- Run `pnpm test`, `make boundaries`, and `make exposure-check` for every code change; each package runs its own tests. Run `make native-test` for native code changes. Run `make verify` for library changes. Commit generated `dist/` changes together with their source; the final check requires no difference between source output and committed files.
- While an item is in development, run only the owning tests of what changed; run the full suites exactly once, when every item of the active checklist is complete — never after each correction or each item. A check that can run for minutes must report each test it starts, its result, and its elapsed time — a run that shows only a start and an end is not acceptable, and each test carries its own timeout instead of one global bound. A long operation is observed with detailed step logs and verified by its errors and results; a timer is never the judge of success.
- For native or example behavior, follow [example verification](docs/operations/examples.md). Build both hosts, then run the affected checks against those binaries.
- A window check fails on every application error logged while it runs unless the check causes that error on purpose and declares it with `expectError`; an error is never declared to make a check pass. A check starts from the state its preparation sets and leaves no state that changes another check; a difference between checks or hosts that leftover state causes is a defect of the check that left it.
- Window tests connect through `<config-dir>/endpoint.json` to applications already running with `--config-dir PATH`. They use only declared exposure entries and native input, wait on status notifications instead of timers (`make e2e-check`), a disposable configuration directory, and project folders. They must not launch applications or independently activate windows. Project-window checks may invoke the application’s project-open command, which creates or focuses windows as specified. Keep automated window-check configurations separate from configurations used for interactive review. Once a check configuration is used for interactive review, create a new disposable configuration for subsequent automated checks.
- A multi-host window-check session captures the application that is frontmost before the checks once and restores that same baseline after every session. It must never restore focus from one tested host to another; tested hosts remain inactive for synthetic pointer measurements.
- Use `diagnostics.capture.still` for non-activating window captures and `diagnostics.capture.start/stop` for recordings whenever visual observation helps diagnose or review behavior. Never focus or activate a window for capture; the capture works without activation. Inspect captures as visual observation, but do not use an image or recording alone as a pass/fail test result.
- Inspect captures at original resolution (`view_image` with `detail: "original"`). A resized preview is not evidence that the source image is clipped or blank; compare the original image and measured pixels before diagnosing a composition failure.
- For visual or time-dependent behavior, recording the full gesture at the requested rate is mandatory. Derive tracked, machine-checkable Red/Green evidence from the recording: measure elapsed time or frame gaps for animation, and compare measured coordinates for DOM, native, or WebView composition. Missing frames or incomplete input is a failure, not a passing measurement. If required state or measurements are not exposed, add the declared command and test interface that provides them; missing exposure is work to implement, not a reason to stop verification.
- Verify input-method (IME) behavior only through activation-tier checks run with the user's approval (`make -C native/darwin test-activation`, `pnpm -F @soksak/e2e verify:activation`); the OS input method serves only the key window of the active application. Each run sends the same keys to an AppKit text-view control in the same window, and a result is evidence only when the control produces the expected document.
- Every declared workspace version is the current release version, 0.0.3; `scripts/check-versions.mjs` enforces it in `pnpm test`.
- Keep the check output and host logs of a failing run until every failure is classified and recorded; removing them earlier discards the only evidence of an intermittent failure.
- Record the tested implementation and platform. Do not use an earlier result to validate later code or describe a test pass as a release.
- Reproduce and accept an intermittent failure through a tracked repeat target (for native tests, `make -C native/darwin repeat TEST=<name>_test COUNT=<n>` for one test and `make -C native/darwin repeat-suite COUNT=<n>` for the default suite; for Rust packages, `make rust-repeat PACKAGE=<package> COUNT=<n> [TEST=<name>]` repeats the tests; for Go packages, `make go-repeat PACKAGE=<path> COUNT=<n> [TEST=<regexp>]` repeats them; for Node tests outside window checks, `make node-repeat FILE=<file> NAME=<pattern> COUNT=<n>` and `make rust-tests-alone PACKAGE=<package>` runs each test alone to find a dependence on test order). A failing check reports the measured state needed to locate its cause. Commands typed in a shell session, temporary scripts, and temporary folders are not reproduction or acceptance evidence; a needed check becomes a tracked test or target.
- A check that exceeds its time limit on a loaded machine by less than 100 times its expected time is not a defect: record the load and the measured time, classify the failure as load, and complete the item. Performance is measured and improved with dedicated benchmarks after development is complete; an item is not held open for load-dependent timing.
